假设你要设计一块芯片中的数据缓冲模块：上游不断送来数据，下游按照自己的节奏读取，中间需要一个 FIFO 保存尚未被消费的数据。功能听起来很简单，写出几十行 RTL 似乎就完成了主要工作。

但几份仿真波形不足以回答这些问题：FIFO 写满时同时发生读写，应该接受哪一个请求？复位后是否可能读出旧数据？综合出来的存储结构是寄存器阵列还是存储器宏？布线以后还能否达到目标频率？芯片生产出来后，又怎样检测内部连线或单元上的制造缺陷？

这些问题分属不同的抽象层次，却会相互影响。本文围绕数字 ASIC 的典型流程，解释设计如何从时钟周期层面的行为描述，逐步变成满足实现约束的电路与版图。论文提供方法背景，工具文档补充工程细节；FIFO 则作为贯穿全文的教学案例，不代表已经执行过工具流程的实验结果。[1–9]

## 一、先看全局：设计流程不断增加约束与证据

RTL 是 Register Transfer Level，即寄存器传输级。它描述寄存器保存什么状态、组合逻辑如何计算，以及状态如何随时钟变化。设计工具进一步把这些描述转换为逻辑结构、标准单元和物理几何信息。[2]

在典型的标准单元 ASIC 流程中，可以用下面的主线理解数据的流动。实际项目中的验证、时序分析和可测试性工作会跨越多个阶段，不能只按图中的先后顺序执行。[5–7,9]

```text
需求规格与微架构
       ↓
RTL 设计 ←──────── 功能验证、断言、静态检查的反馈
       ↓
逻辑综合 ←──────── 等价性检查、面积与时序分析的反馈
       ↓
DFT 相关变换与检查（具体安排取决于项目流程）
       ↓
布图规划 → 单元布局 → 时钟树综合 → 布线
       ↑                                 ↓
       └──── 时序、拥塞与电源分析反馈 ────┘
                                         ↓
                           提取寄生参数、最终检查与签核
                                         ↓
                              GDSII 等流片交付数据
```

最值得关注的是每个阶段的输入、输出及其检查依据：[2,5–7]

| 阶段 | 主要输入 | 主要输出 | 需要回答的问题 |
| --- | --- | --- | --- |
| 规格与微架构 | 使用场景、接口要求、性能目标 | 功能规格、模块划分、时序约定 | 要实现的行为是否清楚、可检查？ |
| RTL 设计 | 微架构与编码约定 | RTL、模块接口与设计说明 | 状态和逻辑是否准确表达了规格？ |
| 功能验证 | 规格、RTL、验证计划 | 测试结果、覆盖率、属性检查结果 | 设计在哪些场景或假设下满足要求？ |
| 逻辑综合 | RTL、单元库、综合与时序约束 | 门级网表、面积与时序报告 | 行为如何映射为目标工艺中的逻辑结构？ |
| 物理实现 | 网表、物理库、工艺信息、约束 | 放置与布线数据、提取信息、版图 | 电路能否在物理限制下实现？ |
| 签核与交付 | 最终设计数据、规则、分析场景 | 检查报告、批准记录与交付文件 | 是否满足本项目约定的交付条件？ |

EDA 工具负责处理这些转换与检查。设计团队还需要决定：功能规格是否正确、约束是否覆盖实际使用场景，以及报告是否构成足够的证据。

## 二、读懂工具链：几类文件分别表达什么

先区分逻辑信息、时序信息与物理信息，会更容易理解工具之间的衔接。[2,7]

| 文件或数据 | 主要作用 |
| --- | --- |
| Verilog / SystemVerilog RTL | 表达寄存器传输级行为和结构 |
| 门级网表 | 表达单元实例及其逻辑连接 |
| Liberty（通常为 `.lib`） | 描述单元功能、时序弧、功耗等库模型 |
| SDC | 描述时钟、输入输出时序要求、时序例外等约束 |
| LEF | 提供工艺或单元的物理抽象信息，例如布线层、尺寸和引脚 |
| DEF | 表达设计中的放置、连接和布线等物理实现信息 |
| SPEF | 交换互连寄生电阻、电容等信息 |
| GDSII | 表达用于版图交付的几何层次数据 |

PDK，即工艺设计套件，提供与特定制造工艺有关的模型、规则和技术信息。标准单元库、存储器宏、IO 库等还需要与工艺、工具和分析条件相匹配；项目采用的具体打包方式并不统一。[6,7]

因此，解释一份实现报告时，至少要知道它对应什么 RTL 版本、什么工艺与库、什么约束、什么实现阶段。两个设计即使使用同样的模块名称，如果一个面积来自综合估计，另一个来自布线后的实现统计，也不能直接据此判断谁更好。

## 三、RTL 设计：先定义行为，再选择电路结构

### 1. 把 FIFO 的接口约定写清楚

本文选择一个单时钟同步 FIFO：数据位宽为 32，深度为 16，采用同步高有效复位。写接口包含 `wr_en` 和 `wr_data`，读接口包含 `rd_en`、`rd_data` 和 `rd_valid`，另外输出 `full` 与 `empty`。

这是教学案例的设计约定：

- 所有请求在时钟上升沿被采样。
- 能否接受请求，由该边沿之前的 FIFO 状态决定。
- FIFO 满时拒绝写请求，空时拒绝读请求。
- 非满且非空时，同拍读写都可以接受，已有数据先读出，新数据加入队尾。
- 满状态下同拍读写，只接受读；空状态下同拍读写，只接受写。
- 成功读取后，`rd_data` 和 `rd_valid` 在该边沿之后更新，在随后的周期内有效；`rd_valid` 表示本次接受了读请求。
- 复位具有最高优先级，清空有效数据状态，同时令 `rd_valid` 为零。

这是一种刻意保持简单的接口。也可以设计成满状态下接受同拍读写，或者空状态下支持数据旁路，但这些属于另一份规格，需要相应修改逻辑和验证计划。

可以用下面的伪代码表达操作是否被接受；其中 `occupancy` 表示边沿前的有效数据数量：

```text
if reset:
    occupancy_next = 0
    rd_valid_next = false
else:
    write_accept = wr_en and (occupancy < DEPTH)
    read_accept  = rd_en and (occupancy > 0)

    occupancy_next = occupancy + write_accept - read_accept
    rd_valid_next = read_accept

    if write_accept:
        把 wr_data 写到尾指针指向的位置，并推进尾指针
    if read_accept:
        把头指针指向的数据送入 rd_data 寄存器，并推进头指针
```

这里采用伪代码，是为了把接口语义与具体 HDL 的位宽、类型转换及非阻塞赋值语义分开。真正的 RTL 需要明确这些细节。

### 2. 状态如何编码，会影响实现

在这个例子中，读写地址各需要表示 16 个位置；有效数据数量则需要表示 0 到 16，共 17 种取值。因此，地址可以用 4 位表达，数量计数器需要 5 位。

如果把深度改为可配置参数，需要继续检查深度为 1 和非二次幂时的行为。对于深度 10，地址计数器不能仅依赖自然溢出来回绕，必须在最后一个有效位置显式回到零。

存储结构也需要单独考虑。同样的数组式 RTL，可能在不同映射条件下成为触发器和多路选择器组成的逻辑，也可能映射到适配的存储器宏；能否完成映射取决于可用资源、端口行为、读延迟和复位等条件。[11]

案例只要求复位后 FIFO 为空，因此可以通过复位指针、数量和有效标志，使之前写入的数据不再被当作有效数据。是否还需要清除每个存储位，应由明确的功能或安全需求决定，不能在没有要求时默认添加。[11]

### 3. 可综合、行为正确和实现合适，需要分别判断

可综合性描述的是工具能否把所用语言结构转换为支持的硬件。综合成功并不能说明设计符合需求，更不能说明它已经满足目标频率和面积要求。[2]

RTL 评审可以分别检查三件事：接口行为是否完整，状态与位宽是否正确，结构是否适合目标实现。Lint 等静态检查有助于发现可疑编码，但它们不能代替规格驱动的验证。

Chisel 论文提供了另一种组织硬件设计的方法：利用宿主语言中的抽象和参数化能力生成硬件。它适合讨论设计复用和生成器，但生成出来的设计仍需要进入后续验证与实现流程。[1]

## 四、功能验证：把规格转化为可检查的证据

### 1. 验证计划从接口规则出发

对于本文 FIFO，可以先把约定拆成以下检查项：

| 检查目标 | 激励场景 | 观察内容 |
| --- | --- | --- |
| 复位行为 | 空闲或已有数据时复位 | 复位后为空，旧数据不可作为有效读结果 |
| 数据顺序 | 连续写入不同数据，再连续读取 | 读出顺序与被接受的写入顺序一致 |
| 满边界 | 写满后继续写 | 拒绝额外写入，已有数据不被破坏 |
| 空边界 | 读空后继续读 | 不产生成功读取的有效标志 |
| 同拍读写 | 空、满和中间占用状态下同时请求 | 接受行为与前述三种状态的约定一致 |
| 指针回绕 | 执行超过深度的写读序列 | 回绕后顺序正确，数量不越界 |
| 读输出时序 | 单次读、连续读、读请求中断 | 数据和 `rd_valid` 的更新关系符合约定 |

仿真环境据此产生输入，并使用独立的参考行为判断输出。UVM 用户指南中的 Driver、Monitor、Scoreboard 与覆盖率机制，为组织这种环境提供了成熟的框架。[8]

### 2. 参考模型应表达规格

FIFO 的参考模型可以是一个软件队列：接受写请求时入队，接受读请求时取出队首，再与 DUT 输出比较。参考模型需要根据自己的队列长度和规格判定操作是否应该被接受，并把 DUT 的 `full`、`empty` 也作为被检查的输出。

如果直接相信 DUT 的满空标志，再用这些标志决定参考队列是否更新，就可能让参考模型与 DUT 同时跳过一次本应发生的操作，从而漏掉标志错误。

时序也要对应起来：参考模型在边沿处确定期望读值，监视器应在 RTL 的时序更新完成后检查数据和有效标志。UVM 的组件划分帮助组织职责，正确的采样时机和参考语义仍需要验证工程师设计。[8]

### 3. 覆盖率用来发现验证缺口

代码覆盖率关注代码或结构是否被激活，例如分支是否执行；功能覆盖率关注验证计划中的场景是否出现。FIFO 的“满状态下同时读写”就是一个功能场景，单纯看到读写两条分支都执行过，并不足以确认这个组合已经被检查。[8]

可以把占用状态划分为空、单元素、中间状态、差一个满、满，再与读写请求组合做交叉覆盖。发现未覆盖项之后，需要判断它属于合法但尚未触发的场景、规格禁止的场景，还是环境约束导致不可达的场景。

覆盖率需要与检查机制一起看。测试触发了错误行为，却没有任何断言或结果比对发现它，覆盖率仍可能很好看。[8]

### 4. 形式验证扩大检查范围，也引入证明条件

形式验证把设计和属性转化为数学问题。对于 FIFO，可以提出数量始终处于合法范围、被拒绝的操作不改变对应状态、成功读出的数据保持顺序等属性。[3,4]

属性通常需要配合环境假设。例如同步复位是否在启动时发生、输入如何被采样，都需要反映在模型中。假设过强可能排除真实使用场景；假设不足则可能引入规格之外的行为。[4,10]

必须区分有界检查与完整证明：有界检查在给定展开深度内寻找反例，未找到反例不等于对任意时间长度成立；证明模式则尝试建立超出固定深度的性质，结果仍取决于具体引擎、模型、属性与最终状态。[10]

同样，`occupancy <= DEPTH` 成立不能说明数据顺序一定正确；包含请求最终得到响应的活性属性，还需要考虑环境是否允许无限期阻塞。[4]

AutoSVA 研究了围绕 RTL 模块交互自动生成形式验证环境的方法，重点覆盖控制交互中的安全性与活性。它说明自动化能够减少重复工作，但属性范围、环境条件和未覆盖功能仍需要明确。[4]

## 五、逻辑综合：把 RTL 变成目标单元库中的电路

### 1. 综合逐步降低表示层次

Yosys 论文展示了一个可扩展的综合框架：前端读入设计，内部表示承载不同层次的结构，多个处理过程完成转换和优化，再输出目标表示。[2]

为了理解它，可以把主要工作概括为：展开参数和层次，将过程式描述转成内部结构，化简逻辑，处理寄存器与存储结构，最后完成目标映射。实际执行顺序会根据设计和脚本调整。[2,11]

例如，常量条件可能让一部分分支被删除；无可观察用途的逻辑可能被消除；多个逻辑表达式也可能在保持功能的条件下重写。因此，RTL 行数与最终电路规模没有直接的比例关系。[2,3]

### 2. 技术映射需要匹配具体资源

逻辑优化后的网络还需要用目标工艺可用的单元表达。不同单元的功能、面积和时序特性不同，综合工具需要在约束下选择实现。[2,3]

ABC 研究和实现了逻辑综合与验证中的多种方法。其常用内部表示之一是 AIG，即由二输入与节点和可取反边构成的逻辑网络。统一表示有利于进行逻辑重写、优化和形式推理。[3]

在常见的 Yosys 与 ABC 组合中，可以借助它们理解综合前端、内部变换、逻辑优化与映射之间的分工。不过，具体调用路径和支持能力仍应以所采用版本及脚本为准。[2,3]

### 3. 约束让“优化得好”有了判断标准

综合需要知道设计的时序环境。SDC 可以描述时钟、接口时序和例外，单元库提供相应模型；这些输入共同决定报告的含义。[7,12]

假设教学项目把目标时钟周期设为 2 ns，这只给出了名义上的周期目标。寄存器之间的可用时间还要结合时钟关系、建立时间、不确定性和数据路径延迟分析。输入输出路径则需要与外部接口时序要求对应。[12]

因此，只创建一个时钟并不保证所有路径都已得到合理分析。需要检查路径是否被覆盖、例外是否正确，以及约束是否反映真实接口条件。[12]

### 4. 面积报告可以反向揭示结构问题

FIFO 的数据容量是 32 × 16 = 512 位，但这不是完整的硬件成本。读写控制、指针、计数器、比较逻辑以及读取数据所需的选择结构也会占用资源。

如果存储没有映射到宏，而被实现为触发器阵列，面积和读取路径结构可能与预期明显不同。此时可以从报告追溯：目标流程是否提供了合适的存储器模型，RTL 行为是否符合映射条件，以及该规模下采用哪种结构更合适。[11]

综合报告由此成为设计反馈，而不仅是一张最终分数表。

### 5. 等价性检查验证转换是否保持功能

等价性检查比较参考设计与变换后设计是否在约定条件下保持一致，适合用于检查综合等变换对行为的影响。[3]

它检查的是两份表示之间的关系。如果 RTL 本身误解了 FIFO 的同拍读写规则，而网表忠实保留了这个错误，两者仍可能等价。因此，规格驱动验证与等价性检查承担不同职责。[3,4]

复位、初始状态、黑盒和存储模型也需要匹配，否则等价性结果的适用范围会不清楚。

## 六、物理设计：让逻辑连接具有位置、长度和电气代价

物理实现为单元确定位置，为连接选择实际布线路径，并持续检查由这些选择带来的影响。OpenROAD 与 OpenLANE 的论文和流程文档，为理解这一过程提供了开放的研究与工程入口。[5–7]

### 1. 布图规划决定空间组织

布图规划需要考虑核心区域、宏单元、引脚、电源网络以及后续布局布线空间。若 FIFO 使用存储器宏，其位置和引脚朝向会影响它与周围控制逻辑的连接。[7]

面积利用率过于激进可能增加后续布线压力，但更大的区域也可能增加线长。合适的参数需要结合设计、工艺和实际报告判断。[7]

### 2. 单元布局处理连接与拥塞

布局阶段确定标准单元的位置，并围绕线长、时序与拥塞等目标进行优化。逻辑上相邻的节点如果物理距离很远，连线代价可能使路径变差。[5,7]

布局结果也可能揭示微架构问题。例如一组控制信号需要跨越较大区域驱动很多负载时，仅靠局部优化未必足够，可能需要重新考虑逻辑分布或流水线边界。[5,7]

### 3. 时钟树综合建立实际时钟分发网络

时钟树综合使用缓冲器等结构把时钟送到寄存器，并控制时钟分发相关的延迟、偏斜和电气限制。实际时钟网络建立后，时序分析要更新对发射端和捕获端时钟到达时间的认识。[7,12]

因此，时钟树综合前后的报告不能简单当作同一条件下的结果。

### 4. 布线与提取让时序模型更加具体

全局布线对连接通道进行规划，详细布线则确定符合规则的具体走线。随后提取互连寄生参数，使分析能够反映更具体的物理实现。[7]

综合时的时序满足要求，并不能保证布线后的时序仍满足要求。线长、负载、缓冲和时钟网络等变化，都可能改变路径表现。[7,12]

处理问题时，先判断关键路径的组成：主要是逻辑级数、单元延迟、线延迟，还是扇出和负载。不同原因需要不同措施，修改 RTL、调整映射或改变物理布局都有可能成为合理选择。

## 七、签核与 DFT：把使用正确性和制造可测试性纳入交付

### 1. 静态时序分析依赖完整的分析条件

静态时序分析依据时序图、库模型、约束和互连信息计算路径要求。建立时间检查关注数据能否及时到达；保持时间检查关注数据是否过早变化。实际项目还需要覆盖适用的工作模式、工艺、电压和温度条件。[12]

“时序通过”应该附带分析范围：用了哪些模式和角点，检查了哪些路径，哪些路径被排除，以及这些排除是否有设计依据。缺少这些信息，单一的裕量数字很难解释。[12]

### 2. DRC 与 LVS 检查不同的一致性

DRC，即设计规则检查，依据规则检查版图几何是否满足相关要求。LVS，即版图与原理图或参考网表比对，检查从版图提取的连接是否与参考电路一致。它们与功能验证分别提供不同层面的证据。[6,7]

签核还可能包含电源完整性、可靠性及其他项目要求。具体检查项、工具、规则和豁免流程，应由工艺与项目交付规范确定。[6,7]

因此，生成 GDSII 表示产生了一份版图数据，并不自动说明所有流片条件已经满足。

### 3. DFT 让内部状态更容易测试

功能验证在设计模型上检查预期行为；制造测试需要观察实际芯片是否存在制造缺陷。DFT，即可测试性设计，通过专门结构提高内部状态的可控制性和可观察性。[9]

扫描链能够让一部分内部状态通过测试方式移入和移出。ATPG，即自动测试向量生成，则围绕选定故障模型生成测试激励，并评估相应的故障覆盖情况。[9]

扫描结构及相关控制需要在设计流程中提前考虑，并在集成后重新检查相关功能、时序和物理影响。它们的具体插入阶段取决于项目采用的工具链。[9]

Fault 论文展示了开源 DFT 工具链的一种实现，可以用来理解扫描与测试生成如何补充数字芯片实现流程。阅读时也需要把论文展示的能力与特定项目的测试要求分开。[9]

## 八、把 FIFO 案例组织成一次可复现的实践

前面的章节可以落实为一组明确的交付物。下面是建议的实践方案，尚未运行综合、形式验证或布局布线，因此没有实测面积、频率、功耗与覆盖率数据。

### 1. 先建立可追溯的输入

为 FIFO 固定一份规格，记录同拍读写、复位和读延迟语义。随后保存 RTL、测试平台、参考模型、属性、约束和工具脚本，并记录所用版本、随机种子、目标工艺与库。

这些信息用于解释结果和重复实验。某次测试失败时，应能恢复当时的输入与设置，而不只剩一张波形截图。

### 2. 从基础检查逐步推进

可以依次完成 RTL 静态检查、定向仿真、随机回归和覆盖率审查，再对关键属性进行形式检查；设计进入综合之后，检查资源映射、约束覆盖和等价性结果，再开展物理实现。[2–4,7,8,10]

工具运行状态也要被保留。超时、未知、未覆盖、失败和成功代表不同结果，不能统一归类为“没有报错”。[10]

### 3. 用一个小实验理解结构变化

第一组实验可以保持数据位宽、RTL 结构、时钟目标、工艺库和实现设置不变，只把深度从 16 改成 32、64，观察资源与关键路径如何变化。

这里的目的是探索深度变化对既有实现的影响，不预设面积必然线性增长。映射方式与优化决策可能发生变化，因此解释数据时应同时查看网表或资源报告。[2,11]

| 需要记录的项目 | 记录内容 | 用途 |
| --- | --- | --- |
| 设计版本 | RTL 提交标识与参数 | 确认比较对象 |
| 工具环境 | 工具版本、脚本版本和关键设置 | 支持复现 |
| 目标条件 | 工艺、库、角点、时钟和接口约束 | 明确比较边界 |
| 验证结果 | 测试范围、覆盖率、证明状态 | 确认行为检查范围 |
| 存储实现 | 寄存器阵列或具体宏 | 解释结构差异 |
| 面积 | 指明统计阶段与口径 | 避免混用单元面积和核心面积 |
| 时序 | 指明模式、角点和分析阶段 | 比较相同条件下的结果 |
| 功耗 | 指明活动数据或估计假设 | 避免脱离负载条件比较 |

第二组实验可以比较不同 FIFO 边界语义，例如当前的“满时拒绝写”与“满时若同时读出则接受写”。但这时功能规格已经改变，需要先更新参考模型、覆盖点和属性，再讨论吞吐与实现成本。

这种实验能揭示一个重要关系：架构选择决定了允许的行为，也同时影响验证难度和实现代价。

## 九、如何阅读相关论文与自动化研究

本文涉及的文献可以按问题组织，而不必按工具知名度阅读：

- 想理解硬件抽象与生成，阅读 Chisel。[1]
- 想理解 RTL 如何进入综合框架，阅读 Yosys。[2]
- 想理解逻辑网络优化与验证的联系，阅读 ABC。[3]
- 想理解模块交互的形式验证自动化，阅读 AutoSVA。[4]
- 想理解数字物理实现及工具集成，阅读 OpenROAD 和 OpenLANE。[5,6]
- 想补上制造测试视角，阅读 Fault。[9]

进一步研究 LLM 辅助 EDA 时，可以阅读 Pan 等人的综述，了解模型在不同设计任务中的应用与定制方法。[13]

对自动生成 RTL、断言或脚本的结果，本文建议按交付阶段评价：能否解析、是否符合规格、属性是否有意义、约束是否完整、实现是否满足目标。只统计生成成功率或工具退出状态，难以说明设计质量。

对于本文 FIFO，一项有价值的自动化结果可以是：从接口规格生成测试候选，识别尚未覆盖的满空边界组合，或者帮助解释一条失败路径。它最终需要回到明确的规格、可执行的检查和可追溯的报告中，才能成为设计决策的依据。
