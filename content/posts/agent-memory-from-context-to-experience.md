一个没有记忆的 Agent，很像一位能力很强、但每天都会失忆的同事。

你可以在一次对话里告诉它项目使用 TypeScript、数据库是 PostgreSQL、部署前必须执行迁移，它也能据此完成任务。但当会话结束，这些信息不会自动成为模型的一部分。下一次见面，它可能重新询问技术栈，也可能再次踩进已经解释过的坑。

最直接的补救办法是保存聊天记录。记录继续增长以后，再把相关片段放回上下文。于是系统接入向量数据库、增加检索接口，并把它称为“长期记忆”。

但这只解决了问题的一部分。

真正的记忆系统不仅要回答“过去说过什么”，还要回答：

- 哪些信息值得长期保留？
- 一次具体经历怎样沉淀为稳定事实或可复用方法？
- 新旧信息矛盾时，应该覆盖、并存还是请求确认？
- 检索到了十条相关记录，当前任务究竟需要哪几条？
- 一条记忆过期、被撤回或者具有安全风险时，系统如何忘记？

因此，Agent Memory 不是一个容量更大的历史记录，也不是向量数据库的别名。它是一套让智能体能够从交互中形成状态、从结果中提取经验，并让这些经验影响未来行动的系统。

> 日志记录过去，记忆改变未来。

## 一、先把三个概念分开：Context、RAG 与 Memory

上下文窗口、RAG 和记忆系统都会把信息交给大模型，因此经常被混为一谈。区分它们的关键，不是有没有 embedding，而是看系统是否形成了**写入、治理、读取和反馈的闭环**。

| 机制 | 主要问题 | 信息来源 | 是否持续演化 | 典型限制 |
| --- | --- | --- | --- | --- |
| Context Window | 模型这一轮能看到什么 | 当前 prompt、消息、工具结果 | 否 | 易失、有界、成本随长度增长 |
| RAG | 外部资料里写了什么 | 文档库、知识库、数据库 | 通常由离线流程更新 | 偏重读取，缺少交互状态治理 |
| Agent Memory | 智能体从过去学到了什么 | 交互、行动、观察、反馈 | 是 | 需要处理冲突、时效、权限与遗忘 |

### 上下文是工作台，不是档案室

大模型生成下一段内容时，只能直接使用当前输入中的 token。系统提示、最近消息、工具调用结果和检索材料共同组成了这个工作台。

工作台可以很大，但它仍有三个性质：

1. **易失**：一次调用结束后，模型不会自动把其中的信息写入持久存储。
2. **有界**：再长的上下文也有容量、延迟和成本边界。
3. **缺少治理**：上下文本身不知道哪条事实已过期，也不会主动合并重复记录。

长上下文解决的是“本轮能放多少”，记忆系统解决的是“跨时间保留什么、如何维护、什么时候使用”。

### RAG 是重要的读取机制，但不是完整记忆

传统 RAG 的主路径是：

```text
问题
  ↓
生成检索查询
  ↓
从外部知识库召回片段
  ↓
重排与上下文组装
  ↓
模型生成回答
```

这条路径同样可以用于读取记忆。但企业知识库中的产品手册，与用户刚刚表达的个人偏好，并不是同一种状态。

产品手册通常由离线摄入流程管理；用户偏好则来自持续交互，可能在下一轮就被修改。后者需要身份隔离、作用域、版本、置信度、冲突处理和删除能力。只有读取路径，没有写入和治理路径，系统仍然只是一套检索系统。

可以把两者的关系概括为：

```text
Agent Memory = RAG 式读取 + 交互式写入 + 状态治理 + 结果反馈
```

## 二、记忆不是一个桶，而是四种不同的能力

人类记忆常被用来帮助解释 Agent 的记忆结构，但这是一种工程类比，不意味着软件系统必须完整复制大脑机制。

CoALA 认知架构将语言智能体中的记忆组织为工作记忆、情景记忆、语义记忆和程序记忆。这套分类的价值在于提醒我们：**不同内容具有不同的生命周期，也需要不同的存储和检索策略。**

### 1. 工作记忆：当前正在处理什么

工作记忆保存当前任务必须保持活跃的信息，例如：

- 用户当前目标；
- 尚未完成的计划；
- 最近几轮关键消息；
- 工具刚刚返回的结果；
- 当前步骤必须遵守的约束；
- 已经尝试过但失败的临时方案。

它通常位于 context window 或线程状态中，生命周期可能只有几分钟或一个任务周期。

工作记忆的难点不是持久化，而是**上下文治理**。如果系统机械地保留最近 20 轮消息，最先被截断的可能恰好是用户在第一轮提出的硬约束。可靠的实现应当保留任务状态，而不是只保留消息顺序。

### 2. 情景记忆：过去发生过什么

情景记忆保存带有时间、参与者、环境和结果的具体经历，例如：

- 10 月 12 日部署服务时，数据库迁移未执行，健康检查失败；
- 上一次修复登录问题时，修改 Cookie 域名解决了跨子域认证；
- 用户在某次会话中拒绝了自动提交代码；
- 某个 API 在高峰期连续三次返回限流错误。

情景记忆保留“事情发生时的上下文”。它适合回答：以前遇到过类似问题吗？当时采取了什么行动？结果怎样？

Generative Agents 将智能体的观察保存在记忆流中，再根据相关性、时近性和重要性动态检索，并将多条经历综合成更高层反思。这个设计说明，记忆不只可以被召回，还可以被再次加工。

### 3. 语义记忆：现在认为哪些事实成立

语义记忆保存从具体经历中抽取出来、相对稳定的事实：

- 用户偏好简洁的技术回答；
- 当前项目使用 PostgreSQL；
- 生产发布必须经过人工审批；
- 订单服务由交易平台组负责。

情景记忆与语义记忆的差别可以用一个例子说明：

```text
情景记忆：10 月 12 日的项目讨论中，用户说生产库已经迁到 PostgreSQL。
语义记忆：项目的生产数据库是 PostgreSQL。
```

前者是证据和来源，后者是当前状态。可靠系统通常同时保存两者：语义事实用于快速决策，原始事件用于审计和重新判断。

### 4. 程序记忆：面对问题应该怎么做

程序记忆保存可复用的方法、规则和技能，例如：

- 数据库变更后的发布检查清单；
- 某类线上故障的排查顺序；
- 调用内部 API 的认证流程；
- 完成代码审查时必须检查的项目规范；
- 经过验证的计划模板和工具组合。

它既可以存在于模型参数中，也可以存在于外部 Skill、Prompt、工作流或代码中。外部程序记忆更容易审计、版本化和回滚，因此尤其适合组织规则与项目经验。

Reflexion 展示了从情景到程序的一个简化过程：Agent 根据任务反馈生成自然语言反思，把“哪里错了、下一次如何调整”保存在情景记忆中，并在后续尝试前重新读取。这里没有更新模型权重，但过去的失败已经改变了未来行动。

## 三、记忆系统的演进：从保存历史到形成经验

从工程演进看，Agent Memory 大致可以分成四个阶段。它们不是严格的产品代际，而是系统能力逐渐增加的四个层次。

### 第一阶段：保存历史

系统保存完整聊天消息或行动轨迹，并在下一轮继续拼接。

优点是实现简单、信息损失少；问题是历史会持续膨胀。随着消息增加，关键约束会被噪声淹没，成本和延迟也会不断上升。

常见补丁包括滑动窗口和对话摘要，但摘要本身也会丢失细节、混淆事实与推测。

### 第二阶段：按需检索

系统将历史切分、向量化并写入外部存储，在需要时召回相关记录。

这一阶段解决了“每次不必读取全部历史”的问题，却带来了新的问题：

- 相似不等于相关；
- 旧事实和新事实可能同时命中；
- 一条信息对用户全局有效，另一条只对当前项目有效；
- 原始对话中可能包含误解、玩笑或已经撤回的要求。

因此，检索系统必须逐步演化为状态系统。

### 第三阶段：反思与巩固

系统不再把所有事件视为彼此独立的记录，而是周期性完成：

- 从多次交互中抽取稳定偏好；
- 将重复事实合并为统一状态；
- 根据新证据修正旧结论；
- 从失败轨迹中总结教训；
- 将多条经历压缩成更高层认识。

这类似数据库中的物化视图：原始事件仍然保留，但系统还维护一份更适合当前决策的派生状态。

### 第四阶段：经验与能力沉淀

更进一步，系统会把经过验证的成功轨迹转化为可复用技能，并根据使用效果持续调整：

```text
事件
  ↓
事实与结果
  ↓
反思和模式发现
  ↓
可复用策略
  ↓
后续任务验证
  ↓
升级、降权或回滚
```

此时，记忆的目标不再是让 Agent “知道以前发生过什么”，而是让它在新任务上表现得更好。

## 四、真正的核心：一条完整的记忆生命周期

一套可用的记忆系统至少要覆盖八个环节：感知、准入、编码、存储、检索、注入、巩固和遗忘。

```text
交互、观察与行动结果
          ↓
      候选记忆
          ↓
重要性、安全性与作用域判断
          ↓
抽取、归一、去重、冲突处理
          ↓
  分层存储与索引构建
          ↓
按任务检索、过滤、重排
          ↓
   注入有限上下文
          ↓
执行结果与用户反馈
          ↓
 更新、巩固、降权或遗忘
          └──────────────↺
```

### 1. 感知：哪些事件可能成为记忆

候选信息不仅来自用户消息，也来自：

- 工具调用及返回结果；
- 环境状态变化；
- Agent 的计划与行动；
- 测试、编译器和评估器反馈；
- 用户对结果的接受、纠正或拒绝；
- 任务最终是否成功。

如果只记用户说过的话，系统会遗漏最有价值的行为经验。

### 2. 准入：什么值得长期保留

“全部保存，以后再搜索”看似稳妥，实际上会制造越来越多的噪声、矛盾与安全负担。

写入前至少要判断：

- 信息未来是否可能复用？
- 它是事实、偏好、事件，还是未经证实的推测？
- 它的适用范围是本轮、线程、项目、用户还是组织？
- 是否包含凭据、隐私或不应持久化的内容？
- 是否已经存在等价记忆？
- 用户是否明确要求保存或不要保存？

准入策略可以由规则和模型共同完成。密码、访问令牌等内容应由确定性规则直接拒绝；偏好和经验抽取则可以由模型生成候选，再经过结构校验。

### 3. 编码：把自然语言变成可治理状态

仅保存一段自由文本，不利于后续更新。更实用的记忆对象应带有结构化元数据：

```ts
type MemoryRecord = {
  id: string;
  kind: "episodic" | "semantic" | "procedural";
  subject: string;
  content: string;
  scope: {
    tenantId: string;
    userId?: string;
    projectId?: string;
    threadId?: string;
  };
  source: {
    eventId: string;
    actor: "user" | "agent" | "tool" | "evaluator";
  };
  confidence: number;
  importance: number;
  validFrom: string;
  validUntil?: string;
  status: "active" | "superseded" | "deleted";
  createdAt: string;
  updatedAt: string;
};
```

原始文本、摘要、向量、实体关系和时间字段可以同时存在。它们不是互斥方案，而是服务不同查询路径的多种表示。

### 4. 存储：按访问模式分层

存储选型不应从“流行哪个向量数据库”开始，而应从访问模式开始。

| 内容 | 主要查询 | 合适的基础设施 |
| --- | --- | --- |
| 当前计划与线程状态 | 按 `threadId` 精确读取 | 状态存储、KV、关系数据库 |
| 用户事实与偏好 | 按实体、字段和作用域读取 | 关系数据库、文档数据库 |
| 历史事件与相似经历 | 语义、时间和条件组合检索 | 事件库、全文索引、向量索引 |
| 实体关系 | 邻接、多跳与依赖查询 | 关系模型或图数据库 |
| 技能与流程 | 按版本、能力和适用条件加载 | 文件、对象存储、代码仓库 |

向量索引通常只是其中一层，而不是整个系统。

### 5. 检索：相关性只是一个维度

一条记忆是否应该进入当前上下文，至少取决于以下因素：

```text
score(memory, task) =
  semantic_relevance
  + scope_match
  + recency
  + importance
  + source_reliability
  + causal_or_entity_relation
  - staleness
  - conflict_risk
  - security_risk
```

这不是要求系统必须使用固定公式，而是在提醒我们：只用余弦相似度排序，无法表达真实的业务约束。

例如，“这个项目统一使用 Python”与“用户通常喜欢 TypeScript”都和“生成代码示例”高度相关，但项目级约束应该覆盖用户全局默认值。决定优先级的是作用域，不是语义相似度。

### 6. 注入：检索结果还不能直接交给模型

召回之后还需要进行：

- 权限过滤；
- 去重和聚类；
- 时间与版本过滤；
- 冲突标记；
- 可信度排序；
- 压缩和 Token 预算分配；
- 来源标注。

最终上下文应区分不同性质的信息：

```text
[Verified Facts]
- The project database is PostgreSQL. Source: architecture decision ADR-017.

[User Preferences]
- Prefer TypeScript examples unless the current project specifies another language.

[Relevant Past Episode]
- A previous deployment failed because migrations were skipped.

[Candidate Lesson]
- Verify migration status before deployment. Confidence: medium.
```

把“已确认事实”和“模型总结出的候选教训”混在一起，会让模型误把推测当成硬约束。

### 7. 巩固：从事件到事实，再到方法

巩固负责把多条低层记忆转化为更稳定的高层状态。

例如，系统连续观察到：

1. 用户三次要求代码示例使用 TypeScript；
2. 用户接受了 TypeScript 版本，并拒绝了 Python 版本；
3. 用户明确说“以后示例优先使用 TypeScript”。

系统可以据此建立一条高置信度语义记忆。但如果用户只在某个 Node.js 项目里提出过一次要求，就不应该将它提升为全局偏好。

巩固不是简单摘要，而是包含证据聚合、作用域判断和置信度更新的状态计算。

### 8. 遗忘：保持记忆质量的必要机制

遗忘不一定意味着物理删除。它可以有多种形式：

- 降低检索权重；
- 标记为被新版本取代；
- 从当前状态移入历史归档；
- 对原始事件做压缩；
- 到期自动失效；
- 根据用户请求彻底删除；
- 因安全风险立即隔离。

一套只会 `insert`、不会 `update` 和 `delete` 的系统，最终得到的不是长期记忆，而是长期污染。

## 五、一套实用的四层架构

将前面的分类和生命周期组合起来，可以得到一套相对清晰的参考架构。

```text
┌────────────────────────────────────────────────────┐
│  Layer 1: Working Memory                           │
│  当前目标、约束、计划、工具结果、上下文预算          │
└───────────────────────┬────────────────────────────┘
                        │ recall / write
┌───────────────────────▼────────────────────────────┐
│  Layer 2: Memory Control Plane                     │
│  准入、抽取、归一、去重、冲突、检索、重排、遗忘      │
└──────────────┬──────────────────────┬──────────────┘
               │                      │
┌──────────────▼─────────────┐  ┌────▼─────────────────┐
│ Layer 3: Long-term Memory  │  │ Layer 4: Skills       │
│ Episodes / Facts / Profile │  │ Rules / Workflows     │
│ Events / Relations         │  │ Prompts / Code        │
└──────────────┬─────────────┘  └────┬─────────────────┘
               │                     │
               └──────────┬──────────┘
                          ▼
                  Agent 推理、行动与评估
                          │
                          └──── feedback ────↺
```

### 数据平面与控制平面要分开

长期存储负责保存内容，控制平面负责决定内容怎样流动。控制平面通常包含：

- Memory Writer：生成候选记忆；
- Policy Engine：执行安全和准入规则；
- Reconciler：处理新增、更新、删除和冲突；
- Retriever：生成查询并执行混合检索；
- Reranker：按任务重新排序；
- Context Builder：在预算内组装上下文；
- Consolidator：定期巩固和抽象；
- Forgetting Worker：执行过期、归档和删除。

MemGPT 借鉴操作系统的分层存储和虚拟内存思路，在有限上下文与外部存储之间调度信息。后续的 MemOS 则进一步将明文记忆、激活状态和参数记忆视为可以表示、调度、迁移和演化的系统资源。它们共同提示了一个方向：记忆不只是数据库中的数据，也是运行时需要管理的资源。

## 六、为什么向量数据库不等于记忆系统

向量数据库擅长回答“哪些文本和当前查询语义相似”，但它天然不知道：

- 哪条记录仍然有效；
- 哪条信息来自用户明确确认；
- 两条冲突记录应该怎样合并；
- 当前项目约束是否覆盖用户全局偏好；
- 哪次失败值得抽象成通用经验；
- 哪些内容因为权限或隐私不应被取回；
- 用户要求删除后，派生摘要和向量是否也被清理。

例如，系统中同时存在两条记录：

```text
A: 2025-03-10, project.database = MySQL
B: 2026-09-30, project.database = PostgreSQL
```

面对“生成项目的数据访问代码”，向量检索可能同时返回 A 和 B。生成模型必须临场猜测哪条更可信。

状态系统的处理方式则是：

```text
A.status = superseded
A.validUntil = 2026-09-30
B.status = active
B.validFrom = 2026-09-30
```

检索只把当前有效状态注入上下文，需要审计时再沿版本链读取历史。这个差异说明：**向量检索解决相似性，记忆治理解决真实性和适用性。**

## 七、案例：编程 Agent 如何把一次失败变成经验

假设一个编程 Agent 接到任务：为现有服务增加登录限流。

### 第一步：形成工作记忆

Agent 从仓库和用户要求中得到：

- 项目使用 TypeScript；
- 服务框架是 Fastify；
- 限流状态存储在 Redis；
- 修改必须通过现有集成测试；
- 不允许自动提交代码。

这些内容进入当前任务状态，不必全部成为长期记忆。

### 第二步：读取长期状态

系统按仓库、项目和任务类型检索，找到：

- 语义记忆：该项目统一通过依赖注入获取 Redis 客户端；
- 情景记忆：上次直接创建 Redis 连接导致测试进程无法退出；
- 程序记忆：新增中间件必须运行认证和并发测试套件。

### 第三步：执行并观察失败

Agent 编写实现并运行测试。功能测试通过，但并发测试失败。日志表明多个请求之间的计数更新不是原子的。

这一轮产生一个新 Episode：

```text
task: add login rate limiting
action: GET counter, increment locally, then SET
result: concurrency test failed
cause: read-modify-write was not atomic
evidence: test/rate-limit-concurrency.spec.ts
```

### 第四步：生成候选反思

Agent 根据测试反馈生成教训：

```text
Redis counters used by concurrent requests must use an atomic command
or a transaction. Do not implement them with client-side read-modify-write.
```

此时它仍然只是候选记忆，因为模型可能总结错误。

### 第五步：通过结果验证

Agent 改用原子递增和过期策略，再次运行测试。功能、并发和回归测试全部通过。

系统据此提高候选教训的置信度，并将它写入项目级程序记忆，同时保留原始失败 Episode 作为证据。

### 第六步：影响下一次行动

一个月后，Agent 为同一项目实现短信验证码限流。检索器根据“并发计数”“Redis”“限流”等条件召回这条程序记忆，Agent 从一开始就采用原子操作。

这时，记忆系统完成了真正的闭环：

```text
失败经历 → 原因判断 → 候选教训 → 结果验证 → 技能沉淀 → 后续复用
```

如果只是保存两次任务的完整聊天记录，系统仍可能找到过去；只有当经验改变了下一次方案，它才真正产生了价值。

## 八、记忆系统最危险的不是忘记，而是记错

没有记忆时，Agent 可能表现得不够个性化；错误记忆则可能持续影响后续所有决策。

### 1. 错误记忆与错误抽象

模型可能把猜测写成事实，也可能从一次偶然失败中总结出错误规则。解决方法包括：

- 保存来源和原始证据；
- 区分事实、推测与反思；
- 让高风险事实必须由用户或外部系统确认；
- 使用任务结果更新记忆置信度；
- 允许沿来源链重新计算派生记忆。

### 2. 记忆投毒与持久化 Prompt Injection

一条恶意指令如果进入长期记忆，可能跨会话持续生效。因此写入侧的安全要求应高于普通聊天：

- 外部文档中的指令默认不能成为用户偏好或系统规则；
- 工具返回值只能描述观察，不能擅自升级为高权限程序记忆；
- 记忆必须携带来源、信任级别和权限边界；
- 系统指令、组织规则、用户偏好和外部内容必须分层处理。

### 3. 身份与作用域泄漏

多租户系统中，记忆检索必须先执行确定性的权限过滤，再做语义检索。不能指望 embedding 相似度替代租户隔离。

### 4. 过度个性化

记住用户偏好并不意味着每次都必须使用。用户过去喜欢简短回答，但当前明确要求详细设计文档时，当前指令具有更高优先级。

好的记忆系统应该允许模型忽略不适用的记忆，而不是强迫它展示“我记得你”。

### 5. 删除不完整

用户删除一条原始记录后，还要考虑：

- 从它生成的摘要；
- 对应向量；
- 图中的关系边；
- 巩固出的用户画像；
- 缓存和离线副本。

如果系统不能追踪记忆血缘，就很难真正完成删除。

## 九、怎样证明记忆真的有用

记忆系统不能只用“召回了多少条”衡量。最终问题是：它是否让 Agent 在可接受的成本下，更准确、更持续地完成任务。

### 能力维度

LongMemEval 将长期交互记忆拆成五类能力：

1. 信息提取；
2. 跨会话推理；
3. 时间推理；
4. 知识更新；
5. 信息不足时弃权。

MemoryAgentBench 又强调四类能力：准确检索、测试时学习、长程理解和选择性遗忘。两者都说明，静态长文本中的“针尖检索”不足以代表真实的记忆能力。

### 系统指标

工程评测还应覆盖：

- 候选记忆写入准确率；
- 错误写入率和敏感信息写入率；
- 冲突更新正确率；
- 有效记忆召回率；
- 无关记忆注入率；
- 上下文 Token 增量；
- 读取与写入延迟；
- 删除传播完成率；
- 单用户长期存储成本。

### 最重要的对照实验

每个真实任务集至少比较四组：

```text
A. 无记忆
B. 完整历史或长上下文
C. 简单向量检索
D. 带写入、更新、作用域和遗忘的完整记忆系统
```

除了任务成功率，还应观察系统是否因为错误记忆而退化。只统计“使用记忆后成功的案例”，会掩盖最危险的失败模式。

Mem0 等系统在长对话评测中尝试比较全量上下文、RAG 和结构化记忆方案，并同时报告准确率、延迟与 Token 成本。这种评测方向是正确的：记忆质量不能脱离最终任务效果和运行成本。

## 十、未来：从长期存储走向持续学习

Agent Memory 的未来，不只是建造更大的外部数据库，而是让记忆逐渐成为模型运行时的一等资源。

### 1. 学习型写入与检索策略

目前很多系统依靠固定规则、Prompt 和 Top-K 参数决定记什么、取什么。未来的策略会更多地根据任务结果学习：哪类事件值得保留，哪种查询方式真正提高成功率。

### 2. 从相关检索走向因果检索

语义相似可以找到“看起来相关”的经历，却未必找到真正导致结果的因素。面向复杂任务，系统需要保留行动、环境变化和结果之间的因果链，回答“上次为什么失败”，而不只是“上次谈到了什么”。

### 3. 多模态与环境记忆

桌面 Agent、机器人和工业智能体面对的不只是文本，还包括截图、声音、视频、传感器状态和操作轨迹。多模态记忆需要在统一时间线上对齐观察、行动与结果。

### 4. 个体记忆、团队记忆和组织记忆

未来系统需要明确不同层级的状态所有权：

- 哪些经验只属于单个 Agent；
- 哪些偏好属于用户；
- 哪些规则属于项目或团队；
- 哪些技能经过验证后可以提升为组织能力。

共享能够放大经验价值，也会放大错误传播风险，因此必须配套审批、版本和回滚机制。

### 5. 文本记忆与参数记忆的协同

频繁变化、需要审计的状态适合放在模型外部；稳定、通用、被大量任务验证的能力可能逐步进入参数或专门模型。未来系统可能在上下文、外部存储和模型参数之间迁移知识，根据更新频率、风险与成本选择表示方式。

### 6. 用户可见、可控的透明记忆

真正面向长期协作的产品，应该让用户知道系统记住了什么，并允许查看、纠正、限定范围和删除。记忆不应成为不可见的后台画像，而应成为双方可以共同维护的协作状态。

## 十一、结语：记住不是目的，改变未来才是

大模型本身擅长在当前上下文中推理，但跨时间的连续性来自模型之外的系统。上下文窗口提供工作空间，RAG 提供外部读取能力，记忆系统则负责把交互和行动转化为可持续演化的状态。

一套成熟的 Agent Memory 至少要做到：

- 分清工作、情景、语义和程序记忆；
- 在写入时判断价值、来源、范围和风险；
- 在存储时保留时间、版本、证据和血缘；
- 在读取时综合相关性、作用域、时效和可信度；
- 在使用后根据结果继续更新；
- 在信息失效或用户要求时可靠地遗忘。

因此，记忆系统的核心不是存储，而是治理；不是让 Agent 永远记住，而是让它在正确的时刻使用正确的过去。

当一次经历可以被验证、抽象、沉淀，并在未来任务中避免重复失败时，Agent 才从“能够调用大模型的程序”向“能够积累经验的系统”迈出关键一步。
