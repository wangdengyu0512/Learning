第一次接触 Agent 推理模式时，很容易得到一张越来越长的名词表：CoT、Zero-shot CoT、Self-Consistency、ReAct、Reflexion、Tree of Thoughts、Graph of Thoughts、Plan-and-Execute、ReWOO、LATS……

如果逐个背定义，这些名字会迅速混在一起。更有效的理解方式，是先问两个问题：

1. **它把额外的推理期算力花在了哪里？** 是多生成一些中间 token、多采样几条路径、搜索一棵树、多调用几次工具，还是失败后重新尝试？
2. **它有没有把外部真值带回推理循环？** 模型只是在自己的语言空间里自洽，还是能通过搜索、数据库、代码执行、测试结果和真实环境获得反馈？

沿着这两根轴，绝大多数 Agent 推理模式都能找到自己的位置。

> 所谓“推理模式”，本质上不是让模型突然拥有一种神秘的新能力，而是用不同方式分配 test-time compute，并决定推理循环是否与真实世界连接。

## 一、先建立总地图：算力花在哪，真值从哪来

可以把常见模式压缩成下面这张文字地图：

```text
                    不接外部真值：内部闭环

串行 token          CoT / Zero-shot CoT
并行采样            Self-Consistency
分支搜索            Tree of Thoughts / Graph of Thoughts
自我迭代            Self-Refine
结构自发现          Least-to-Most / Self-Discover

--------------------------------------------------

                    接入外部真值：Grounding

工具往返            ReAct
计划后执行          Plan-and-Execute / ReWOO
按需分解            ADaPT
跨回合重试          Reflexion
搜索 + 工具 + 反思  LATS
```

这张图不是严格的排行榜，也不是说越靠后就一定越强。它表达的是成本结构和失败方式：

- 串行 token 增加延迟与输出成本；
- 并行采样增加调用量；
- 树搜索同时放大生成、评估和调度成本；
- 工具往返受网络、权限和外部系统可靠性影响；
- 跨回合重试会拉长上下文，并可能把错误反思写进记忆。

模式升级并不等于免费获得可靠性。每向前走一步，都是用更多计算、更多时间或更复杂的控制流，换取某一种错误率的下降。

## 二、CoT：不是一句“认真想”，而是增加串行计算

Chain-of-Thought 最常见的解释是“让模型一步一步思考”。这句话没有错，但还不够深入。

一次普通生成中，模型如果直接回答最终结果，就要在有限的前向计算里完成问题理解、中间状态计算和答案组织。CoT 把中间状态写入 token 流，使后续 token 能够继续读取和利用已经生成的结果。于是，一条长推理链就形成了额外的串行计算过程。

例如：

```text
果园有 3 行树，每行 7 棵；摘走 5 棵，又补种 12 棵。

3 × 7 = 21
21 - 5 = 16
16 + 12 = 28
答案：28 棵
```

这里的中间步骤不只是展示给人看的解释，也是后续生成可以复用的工作状态。工程上可以把它理解成：**中间 token 是外化的临时计算结果，多生成一步，就多获得一次基于现有上下文继续计算的机会。**

### Zero-shot CoT 与 few-shot CoT

两者的区别在于怎样诱发中间推理：

- **Zero-shot CoT**：不给完整示例，只追加“让我们一步一步思考”之类的指令。经典方案通常先生成推理，再用第二次调用抽取最终答案。
- **Few-shot CoT**：在提示词中提供若干“问题—推理步骤—答案”的完整示例，让模型模仿这种结构。

在早期通用模型上，few-shot CoT 曾是激活复杂推理能力的重要方法。但它不是越多越好：示例会占用上下文，也可能把模型锁进一种并不适合当前问题的推理套路。

### CoT 的三个适用条件

CoT 更适合这些任务：

- 问题能够拆成连续的中间步骤；
- 中间状态可以用语言或符号清楚表示；
- 答案主要依赖已有上下文，不依赖实时外部事实。

反过来，如果问题是“这张订单为什么刚刚被取消”“今天某个接口返回什么”“这段代码能否通过测试”，只增加 CoT 并不能解决核心问题。模型需要的不是多想，而是去查、去运行、去观察。

## 三、Self-Consistency：不相信一条链，而相信答案分布

单条 CoT 仍然会被某一步的偶然错误带偏。Self-Consistency 的思路是：对同一道题采样多条推理链，抽取每条链的最终答案，再做多数投票。

```python
answers = []

for _ in range(5):
    reasoning = sample_chain(question)
    answers.append(extract_final_answer(reasoning))

return majority_vote(answers)
```

假设五条链得到：

```text
[28, 28, 30, 28, 16]
```

最终输出是 `28`。这里投票的是**最终答案**，不是挑选一条“文字写得最好”的推理链。不同路径只要抵达同一终点，它们的概率质量就被聚合到一起。

Self-Consistency 适合：

- 最终答案可以规范化和比较；
- 错误路径相对分散，正确答案更容易形成共识；
- 任务价值足以覆盖多次采样成本。

它不适合：

- 开放式写作，没有天然的多数答案；
- 所有采样都共享同一种系统性误解；
- 答案依赖外部事实，而所有链都在同一个封闭知识空间里猜。

多数投票可以压低随机误差，却无法自动消灭共同偏差。

## 四、CoT 最大的认知陷阱：解释不等于真实因果过程

人看到一段逻辑通顺的推理，容易自然地相信：“模型就是这样得出答案的。”但可读的解释与真实的计算因果之间，并没有必然对应关系。

模型可能先受位置偏置、示例偏置或表面模式影响选中了答案，再补写一段体面的理由。它也可能在推理链被截断或被注入错误后，仍然给出原答案。这说明文字链有时只是事后合理化，并没有真正驱动结论。

这就是 CoT 的 **faithfulness** 问题：

> 一段解释可以语言正确、逻辑完整、令人信服，却仍然不是模型做出决定的真实原因。

如果需要判断某类 CoT 是否相对忠实，可以设计因果干预，而不是靠肉眼评价“读起来顺不顺”：

1. **截断实验**：在不同位置截断推理，观察最终答案是否随可用步骤发生系统变化。
2. **错误注入**：故意改错某个关键中间结果，观察错误是否会传播到结论。
3. **偏置植入**：在示例中加入无关但稳定的答案偏置，观察模型是否被带偏，以及解释是否主动承认该线索。
4. **反事实改写**：只改一个应当影响结论的证据，检查答案和理由是否同步更新。

如果答案几乎不受推理链干预影响，那条链更像展示层，而不是可靠的审计日志。

因此，生产系统不应把自然语言 CoT 直接当作可验证证据。真正的审计应来自结构化输入、工具调用记录、数据库版本、代码执行结果和明确的决策规则。

## 五、ReAct：真正重要的不是 Thought，而是 Observation

ReAct 把 Reasoning 与 Acting 交错起来，形成一个循环：

```text
Thought → Action → Observation → Thought → ... → Answer
```

其中：

- `Thought`：根据当前上下文决定下一步；
- `Action`：调用搜索、数据库、API、代码解释器或其他工具；
- `Observation`：把工具真实返回的结果写回上下文。

很多实现看起来有 `Thought / Action / Observation` 三段格式，却并没有真正接地。如果所谓 Observation 仍由模型自己续写，没有真实工具执行，那么它只是穿着 ReAct 外衣的 CoT。

**判断 ReAct 是否成立的唯一关键，是外部结果有没有真实地回流。**

一个最小循环可以写成：

```python
state = initial_context

while not finished(state):
    decision = model.decide(state, tools=tool_schemas)

    if decision.type == "tool_call":
        args = validate(decision.arguments)
        result = execute_tool(decision.tool, args)
        state = append_observation(state, result)
    else:
        return decision.answer
```

生产级实现还必须补上模型之外的工程约束：

- 工具白名单与最小权限；
- 参数 schema 校验；
- 超时、重试、限流和熔断；
- 幂等键，避免重复扣款或重复发送；
- 高风险动作的人类确认；
- 完整的调用日志与可回放轨迹。

ReAct 解决的是“模型不知道真实世界当前发生了什么”，而不是单纯解决“模型推理不够长”。

## 六、Plan-and-Execute：先定路线，还是走一步看一步

ReAct 每走一步都重新判断，适应性强，但模型调用多、延迟高。Plan-and-Execute 则先由 Planner 生成完整计划，再由 Executor 逐项执行。

```text
目标
  → Planner：生成步骤 1、2、3、4
  → Executor：依次执行
  → 汇总结果
```

它更适合：

- 步骤相对固定；
- 环境在执行期间变化不大；
- 子任务可以清晰拆分；
- 希望提前估算成本并形成可审计任务单。

它的核心风险是 **计划陈旧**。如果后一步依赖前一步才会揭晓的真实状态，前置计划可能很快过时。

例如客服任务“查询物流；如果确认延误，再根据最新政策给补偿方案”，关键分支只有查询之后才能确定。这里 ReAct 更自然，因为它会根据 Observation 临场决定。相反，“把表格每一行翻译、校验格式并写回”流程稳定，更适合 Plan-and-Execute。

工程上不必把二者视为互斥选择。常见的混合方案是：

- 先制定高层计划；
- 每一步内部使用 ReAct 调工具；
- 当关键假设失效时触发重规划；
- 给重规划设置次数与预算上限。

## 七、Reflexion：把一次失败变成下一次尝试的上下文

ReAct 在一次尝试内部利用工具反馈，Reflexion 则把反馈扩展到多个 episode：完成一次尝试后，由 Evaluator 判断成败，再由模型生成一段反思，把它写入记忆，供下一次重试使用。

```text
尝试
  → 外部评估
  → 生成反思
  → 写入记忆
  → 带着反思重新尝试
```

它并不更新模型权重，因此更准确地说是一种“上下文中的口头强化”，而不是传统意义上的梯度强化学习。

Reflexion 特别适合具有明确外部信号的任务：

- 代码能否通过单元测试；
- 游戏是否获胜；
- SQL 是否执行成功；
- 页面操作是否到达目标状态；
- 数学答案是否被验证器接受。

它的成败几乎完全取决于 Evaluator。如果任务只是“把这封信写得更有感染力”，模型既当作者又当裁判，反思很容易变成主观自说自话。更危险的是，错误反思一旦进入记忆，会在后续回合中被当成经验反复强化。

所以 Reflexion 的正确使用顺序是：**先找到可信的评价信号，再谈重试与记忆。**

## 八、Tree of Thoughts：搜索不是难点，评估器才是

CoT 是一条线，第一步走错后通常只能继续错下去。Tree of Thoughts 把推理展开成树，在每个阶段生成多个候选状态，给它们打分，再用 BFS、DFS 或 beam search 扩展高价值分支、剪掉低价值分支，必要时回溯。

它包含三个关键组件：

1. **生成器**：从当前状态提出多个下一步候选；
2. **评估器**：判断每个中间状态有多大希望抵达成功；
3. **搜索控制器**：决定扩展、剪枝和回溯策略。

直觉上，人们最容易被“树搜索”吸引，但真正决定效果的是评估器。BFS 和 DFS 只是按照分数行动；如果模型把死路评为高分、把唯一活路提前剪掉，搜索只会更昂贵地犯错。

ToT 更适合：

- 解空间天然存在分支；
- 早期选择错误后需要回溯；
- 中间状态的质量可以相对可靠地判断；
- 单个问题价值较高，值得投入大量推理预算。

它不适合：

- 中间状态与最终成败几乎无相关性；
- 只有最后一步才能获得真值；
- 开放任务没有稳定的价值函数；
- 延迟和成本受严格限制。

Tree of Thoughts 的经验不是“复杂任务就上树”，而是：**只有能给中间状态提供可信价值信号时，搜索才值得。**

## 九、把其他新名字放回已知坐标

掌握两根轴以后，新模式不必逐个死记。

### Self-Refine

生成初稿，让同一个模型批评，再根据批评重写。它像去掉外部 Evaluator 的 Reflexion，因此通常仍属于内部闭环。适合润色、风格修改和结构改善；不适合把模型自评当作事实核验。

### Least-to-Most

先把复杂问题拆成较简单的子问题，再按依赖顺序解决。它主要改变串行推理的组织方式，减少后续步骤一次承担过多复杂度。若没有工具与验证，它仍是闭环推理。

### Graph of Thoughts

在 ToT 基础上允许分支合并、复用和形成一般有向图。它适合多个候选部分解能够汇总成更好整体解的任务，例如先并行生成多个草案，再抽取优点形成终稿。

### ReWOO

先生成包含工具依赖的计划，再按计划批量执行工具，最后综合 Observation。它试图减少 ReAct 每一步都重新调用模型的开销，代价是降低临场适应能力。环境越稳定，它越划算；分支越依赖实时结果，它越容易遇到陈旧计划。

### LATS

把树搜索、工具接地和失败反思组合在一起。可以把它看成 ToT、ReAct 与 Reflexion 的合体：搜索节点能够真实调用环境，失败信息还能进入后续探索。能力上限高，成本、延迟与系统复杂度也最高。

### ADaPT

ADaPT 采用“需要时才分解”的策略：先尝试直接完成任务，只有某个子任务真实执行失败时，才把失败点递归拆细，直到拆到可执行为止。它可以理解为 **Least-to-Most 的分解、ReAct 的接地执行，再加上失败触发的重试**。

这种方式避免了对简单任务过度规划，但它依赖明确的失败信号和严格的递归边界。没有最大深度、调用预算与终止条件时，自适应分解也可能退化成不断细分、不断重试的昂贵循环。

### Self-Discover

Self-Discover 先让模型从通用推理模块中选择并组合一套适合当前任务的推理结构，再沿着这套结构解题。它和 Least-to-Most 都会先搭“脚手架”，区别在于前者组合的是推理模块，后者拆出的是有依赖顺序的子问题。

由于选模块、组结构和解题都由模型内部完成，它仍位于“内部闭环 + 串行 token”的格子里：适合改善复杂问题的组织方式，却不能替代实时检索、代码执行或外部事实核验。

看见一个新缩写时，可以先忽略名字，只问：

- 它是在延长链、增加采样、展开搜索、调用工具，还是增加重试？
- 它的评价信号来自模型自身，还是来自外部世界？
- 它比最接近的旧模式多了哪条边、哪种记忆或哪种验证器？

回答完这三问，新模式通常就已经被看穿了大半。

## 十、推理模型时代：哪些模式交给权重，哪些仍要留在系统里

从 2024 年开始，推理模型把较长的内部推理行为通过训练固化进权重。资料目录将这一变化概括为：CoT 从手写 prompt 技巧，逐渐变成模型出厂自带的行为；“让模型在推理时多花计算”也成为一条独立于预训练规模的 scaling 轴。

这会直接改变工程选型。

### 应当弱化的部分

- 不要默认给推理模型堆很多 few-shot CoT 样板；
- 不要为了显得复杂，就在外部重复实现模型已经能够完成的普通分步推理；
- 不要默认给所有请求拉满推理预算；
- 不要把外部 ToT 当作通用性能增强器。

显式示例可能与模型已经学到的内部推理方式冲突。简单任务也可能因为过度推理而增加延迟、成本，甚至推翻原本正确的直觉。具体模型和任务仍应通过 A/B 测试验证，不能把“few-shot 一定有害”当作新的教条。

### 仍然必须保留的部分

- **ReAct 的工具编排**：模型再会推理，也不能凭空读取实时订单或真正执行退款。
- **结构化 Plan-and-Execute**：审计、权限、状态机与可回放步骤属于系统责任。
- **外部验证器**：单元测试、规则引擎、数据库约束和业务校验不能由模型自信替代。
- **并行执行**：真正独立的子任务仍可扇出，以降低墙钟时间。
- **预算路由**：简单请求使用低预算，难题再升级模型、思考强度或搜索深度。
- **风险控制**：高影响动作的确认、幂等、补偿和审计仍必须位于模型之外。

可以把推理模型时代的原则总结成一句话：

> 纯“想”的脚手架可以逐步交给模型权重；涉及真实世界、可验证结果、业务副作用和治理边界的部分，必须继续留在显式系统中。

## 十一、一棵实用的选型决策树

面对一个新任务，可以按下面的顺序判断：

```text
1. 模型是否已经是推理模型？
   ├─ 是：先用简洁指令建立基线，不默认手写长 CoT
   └─ 否：复杂多步任务可测试 CoT

2. 答案是否依赖实时事实、工具结果或环境状态？
   ├─ 是：优先 ReAct，或 Plan-and-Execute + 工具执行
   └─ 否：继续判断

3. 最终答案是否可规范化、可投票？
   ├─ 是：高价值任务可用 Self-Consistency
   └─ 否：继续判断

4. 问题是否需要探索、剪枝和回溯？
   ├─ 是：评估器可靠时再考虑 ToT / GoT
   └─ 否：普通分步推理通常足够

5. 是否存在可信的外部成功信号？
   ├─ 是：失败后可用 Reflexion 式重试
   └─ 否：谨慎使用自我批评，避免坏反思固化
```

此外，再给所有方案加四个硬约束：

- 最大模型调用次数；
- 最大工具调用次数；
- 总 token 或金额预算；
- 最大执行时长与终止条件。

没有预算和终止条件的“智能循环”，很容易退化成昂贵的随机游走。

## 十二、四个常见误区

### 误区一：CoT 越长，答案越可靠

更长只代表花了更多串行算力，不代表每一步都正确。错误也会沿着更长链条传播，并被包装得更加自洽。

### 误区二：有 Observation 字样，就是 ReAct

只有真实工具结果回到上下文才叫接地。模型虚构的 Observation 仍是内部闭环。

### 误区三：搜索算法越复杂，ToT 越强

搜索控制器不是价值来源。评估器不可靠时，更复杂的搜索只会更系统地放大错误评分。

### 误区四：模型升级后，Agent 架构都可以删除

模型升级主要改善推理内核，不能替代权限、工具执行、真实状态、流程编排、幂等、审计和安全边界。能力更强的模型，反而更需要清晰的工程外壳。

## 结语：不要背模式，要识别信息流

CoT、ReAct、Reflexion 和 ToT 并不是彼此孤立的技巧。它们都在回答同一个问题：**当一次直接生成不够可靠时，我们还能把额外算力和反馈放在哪里？**

- CoT 把算力放进串行 token；
- Self-Consistency 放进并行采样；
- ToT 放进搜索与回溯；
- ReAct 放进工具往返；
- Plan-and-Execute 放进显式计划与执行分离；
- Reflexion 放进带记忆的跨回合重试；
- ADaPT 把算力放在由真实失败触发的按需分解；
- Self-Discover 把算力放在任务专属推理结构的生成；
- LATS 则把搜索、行动和反思叠在一起。

而决定这些方法能否从“更会说”走向“更可靠”的关键，是外部真值是否进入循环。

真正成熟的 Agent，不是永远思考最多、调用工具最多或结构最复杂的 Agent，而是能够根据任务难度和风险，选择最便宜但足够可靠的推理路径；一旦涉及真实世界，又能把模型的自由度关进可验证、可停止、可审计的系统边界。
