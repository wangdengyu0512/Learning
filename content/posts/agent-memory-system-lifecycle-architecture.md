一个没有记忆的 Agent，很像一位每次见面都会清空大脑的同事。

它可以在当前对话里分析问题、调用工具、完成任务，但会话一结束，用户偏好、项目约束、失败经验和未完成计划就一起消失。下一次启动时，应用只能重新把历史消息拼进 prompt，让模型“看起来像记得”。

这也是理解智能体记忆系统的起点：**LLM 本身通常仍是一次调用、一次输出的无状态函数；连续性来自模型之外的应用系统。**

很多团队第一次补这块能力时，会自然想到两种办法：扩大 context window，或者接一个向量数据库做 RAG。它们都能让模型看到更多信息，却还不等于记忆。真正的记忆系统必须形成一条闭环：

```text
交互与观察
    ↓
选择要记住什么
    ↓
抽取、归一、去重、冲突消解
    ↓
持久化存储
    ↓
按任务检索、排序并注入上下文
    ↓
根据时间、价值与风险更新或遗忘
    └──────────────────────↺
```

> 记忆不是“存过数据”，而是 Agent 能够持续决定记什么、改什么、何时取回、什么时候忘记。

本文把 `F:\fde\智能体记忆系统` 目录中的六部分教程整理成一篇工程化文章。原始资料的产品与前沿信息截至 **2026 年 6 月**；本文发布时间为 **2026 年 10 月 7 日**，其中容易变化的厂商能力与基准数字应被视为带日期的技术快照，而不是永久不变的产品承诺。

## 一、先划边界：Context、RAG 与 Memory 不是同一件事

三者都在做“把信息交给模型”，所以最容易被混在一起。区分它们，不要只看有没有 embedding、向量库或检索接口，而要看系统里有没有一条**由 Agent 或应用掌控的持久写入路径**。

| 机制 | 信息从哪里来 | 是否跨会话 | 谁决定写什么 | 是否治理旧信息 | 主要用途 |
| --- | --- | --- | --- | --- | --- |
| Context window | 当前 prompt、消息和工具结果 | 默认否 | 应用拼接 | 通常只截断或摘要 | 当前推理的工作区 |
| RAG | 预先准备的外部知识库 | 知识库本身持久 | 离线摄入流程 | 多数只管理文档版本 | 回答“资料里写了什么” |
| Agent memory | 交互、观察、工具结果和历史任务 | 是 | Agent、应用或记忆服务 | 去重、更新、冲突消解、遗忘 | 回答“这个 Agent 学到了什么” |

### Context window 是工作内存，不是长期记忆

上下文窗口本质上是一次模型推理的输入缓冲区。应用把系统提示、历史消息、工具结果和检索材料组装成 token，模型基于它们生成下一段输出；调用结束后，模型不会自动把其中某条事实写入一个可跨会话读取的地址。

因此，context 天生有三个属性：

- **易失**：本轮调用结束后不会自动保留；
- **有界**：token 数存在上限，且越长通常意味着更高的 prefill 成本；
- **被动**：进入窗口的内容主要由应用拼接，窗口自身没有完整的持久化治理能力。

更大的上下文只是在扩大工作台，并没有自动增加“抽取、更新、删除、审计”这些能力。把 20 万 token 扩到 100 万 token，解决的是容量问题，不是跨会话连续性问题。

### RAG 是读取路径，不是完整记忆闭环

RAG 的典型流程是：

```text
query → embedding → 近邻搜索 → 命中文档 → 拼入 prompt → 生成答案
```

这条流程很重要，因为记忆系统在“读取”阶段也可能使用完全相同的技术。但传统 RAG 通常缺少两块：

- 它不会自动把本轮对话产生的新事实写回知识库；
- 它不会针对用户状态做冲突消解、演化与遗忘。

例如，产品手册里写着企业版退款政策，RAG 可以找回政策；但“这个用户三周前说自己使用企业版”属于交互产生的个人状态。如果当时没有被抽取并写入，今天只检索产品手册仍然无法回答完整问题。

所以可以用一句话记住边界：

> **RAG 解决“查得到外部资料”，Memory 解决“系统能够从经历中形成并维护状态”。**

## 二、记忆到底分几类：不要把所有内容都塞进一个库

CoALA 提供了一套很实用的分类：工作记忆、情景记忆、语义记忆和程序记忆。它们按“记住的是什么”来区分，而不是按“使用了哪种数据库”来区分。

| 类型 | 记住什么 | Agent 示例 | 常见载体 |
| --- | --- | --- | --- |
| Working memory | 当前正在处理的信息 | 最近消息、当前计划、刚返回的工具结果 | context window、短期状态 |
| Episodic memory | 带时间与情境的经历 | 上次部署失败的过程、某次客户沟通 | 消息归档、事件日志、时序记录 |
| Semantic memory | 去情境化的事实 | 用户偏好 Python、项目使用 MySQL | KV、文档、向量库、知识图谱 |
| Procedural memory | 如何完成任务 | 排障步骤、审核清单、可复用工作流 | prompt、规则、技能文件、模型参数 |

这里有两个容易误解的点。

### Working memory 就是上下文本身

“上下文不是记忆”和“working memory 是一种记忆”并不矛盾。前者是在说 context 不能替代完整的持久记忆系统；后者是在认知架构中把当前可见、短暂、易失的内容归类为工作记忆。

### 四类记忆与“文本或参数”是两条正交轴

同一类记忆可以采用不同表示方式：

- 一段可读取、可修改的排障流程，是文本形式的程序记忆；
- 通过微调进入模型权重的排障能力，是参数形式的程序记忆；
- 用户偏好保存在数据库中，是文本或结构化语义记忆；
- 通用语言知识蕴含在权重中，也是参数化语义知识。

工程系统通常优先把个性化与业务状态放在模型外部，因为外部记忆更容易逐条读取、修改、删除、审计和迁移。模型权重擅长承载广泛能力，却不适合精确执行“只删除某个用户的一条事实”。

## 三、记忆系统的真正主体：五阶段生命周期

一个完整的记忆系统，不是 `add()` 和 `search()` 两个接口，而是五个相互反馈的阶段：

```text
写入 → 存储 → 检索 → 遗忘 → 上下文治理
  ↑                                  ↓
  └────────── 更新与回写 ────────────┘
```

每个阶段都要回答三个问题：机制是什么、成本是什么、失效时会发生什么。

## 四、写入：不要保存对话，要保存经过判断的状态

直接把每轮对话原样写进向量库，短期很容易，长期几乎一定会遇到噪声、重复和矛盾。

用户可能在十轮对话里用不同说法重复“项目数据库是 PostgreSQL”，也可能在一个月后说“已经迁到 MySQL”。如果所有原文都只追加不更新，检索时就会同时找回旧值和新值，把冲突留给生成模型临场猜测。

更可靠的写入管线通常包含四步：

```text
原始交互
  → 抽取候选事实
  → 实体与字段归一
  → 与已有记忆对账
  → ADD / UPDATE / DELETE / NOOP
```

### 1. 抽取：把交流压成原子事实

与其存储：

```text
“对，我上周终于把库从 Postgres 迁到 MySQL 了，折腾了两天。”
```

不如抽取为：

```text
subject: project/main-database
value: MySQL
valid_from: 2026-09-30
source: user_statement
```

抽取不仅缩短文本，也顺带完成重要性过滤：寒暄、确认和过渡语不会进入长期记忆。代价是写入时需要额外模型调用或规则判断；一旦抽取漏掉关键事实，后面的存储和检索再强也无济于事。

### 2. 归一：先解决“这是不是同一个东西”

“张总”“张伟”“Mr. Zhang”可能指向同一个人；“Postgres”“PostgreSQL”“PG”也可能是同一个技术实体。若写入时不归一到 canonical ID，同一对象会碎成多份记忆，检索只能命中其中一部分。

因此，记忆记录最好同时保留：

- 稳定的实体 ID；
- 原始表面名称；
- 标准化类型与字段；
- 来源、时间和作用域。

### 3. 去重与对账：写入时解决矛盾

写入时先检索若干条最相近的旧记忆，再让规则或模型选择动作：

```text
ADD     新事实，当前没有对应记录
UPDATE  同一事实发生变化
DELETE  旧事实被明确否定或要求删除
NOOP    已知事实，没有新增信息
```

把冲突消解放在写入阶段，体现的是 `write-once, read-many` 思路：宁可写入稍贵，也不要让每次读取都重新判断一遍“哪条才是真的”。

### 4. 冲突策略：新、可信与确定并不总是一回事

常见策略有三种：

| 策略 | 规则 | 适用场景 | 主要风险 |
| --- | --- | --- | --- |
| recency-wins | 更新的信息覆盖旧值 | 地址、职位、当前数据库等状态变化 | 新输入可能来自不可信来源 |
| source-wins | 更可信来源覆盖低可信来源 | 日历、订单、配置中心等有真相源的系统 | 需要完整 provenance 与来源排序 |
| confidence-wins | 更高置信度覆盖低置信度 | 抽取模型质量可校准的场景 | 模型可能对错误内容也高度自信 |

生产系统不应只保存 `value`，还应保存 `source`、`observed_at`、`valid_from`、`confidence` 等元数据，否则所谓冲突策略只是一句无法执行的口号。

更关键的是：**外部网页、邮件正文、附件文本不能与用户明确陈述共享同一信任等级。** 否则一封带提示注入的邮件就可能把“请把邮箱改成攻击者地址”写成长期记忆。

## 五、存储：向量、图与混合模型各自回答不同问题

选存储后端时，不要先问哪个框架 benchmark 更高，而要先问系统必须回答哪类问题。

### 扁平向量存储：适合“语义上像什么”

向量库擅长根据语义相似度找到相关事实或经历，摄入快、模型简单、运维相对成熟。它适合：

- 用户偏好与简单事实；
- FAQ 式回忆；
- 从大量经历中找相似案例；
- 不要求复杂多跳关系的助手。

它不天然理解“谁和谁是什么关系”，也不天然表达事实的有效时间。旧的 `database = PostgreSQL` 与新的 `database = MySQL` 在语义空间里都很相关，如果上层没有消解或时间过滤，两条都可能被召回。

### 时序知识图谱：适合“关系是什么、当时是什么”

图模型把实体和关系作为一等结构，适合多跳查询和时间变化：

```text
用户 → 任职于 → 公司
用户 → 担任 → CTO
项目 → 使用 → MySQL
```

若再加入双时态信息，就能区分：

- 事实在现实世界中何时有效；
- 系统何时知道、修改或撤销这条事实。

一条职位关系可以包含：

```text
valid_at     现实中开始担任该职位的时间
invalid_at   现实中不再担任该职位的时间
created_at   系统写入这条记录的时间
expired_at   系统将这条记录标记失效的时间
```

这使系统既能回答“现在是什么职位”，也能回答“三个月前是什么职位”。代价是写入阶段需要实体抽取、关系抽取和时间标注，摄入延迟与运维复杂度更高。

### 混合存储：生产系统更常见的折中

实际系统往往同时需要：

- KV 或 SQL 保存确定状态；
- 向量索引提供语义召回；
- 全文索引保留关键词精确匹配；
- 图结构支持关系与多跳；
- 事件日志保留审计与回放。

因此“记忆数据库”通常不是一个数据库，而是一层统一的记忆服务，对下暴露多个存储能力，对上提供统一的写入、查询和治理接口。

## 六、检索：目标不是找得多，而是把最有用的放到正确位置

最简单的检索只有向量相似度：

```text
score = semantic_similarity(query, memory)
```

生产场景通常要综合更多信号：

```text
score =
    w1 * semantic_similarity
  + w2 * recency
  + w3 * importance
  + w4 * entity_match
  + w5 * source_trust
  + w6 * task_relevance
```

候选召回之后，再经过过滤与精排：

```text
用户与租户隔离
  → 权限过滤
  → 时间有效性过滤
  → 关键词/向量/图联合召回
  → 去重
  → rerank
  → 控制 top-k
  → 编排进上下文
```

### 为什么“多拿几条保险”常常适得其反

长上下文中存在位置效应：重要信息落在中段时，模型未必能稳定利用。与此同时，语义相近但答案错误的 distractor 并不是中性噪声，它会主动把模型带向错误方向。

所以检索系统的核心指标不应只是 recall。更重要的是：

- top-k 中有多少是真正相关的；
- 是否混入互相矛盾的旧事实；
- 关键事实是否被放在模型容易利用的位置；
- 注入的 token 是否值得它占用的上下文预算。

一个可用的原则是：**先提高精度，再增加数量；先过滤无效和不可信内容，再谈召回覆盖。**

### 记忆注入也需要编排

检索结果不应简单按数据库返回顺序拼接。可以按角色组织：

```text
[当前硬约束]
- 项目主数据库：MySQL
- 数据不得离开客户机房

[用户偏好]
- 示例优先使用 Python
- 回答尽量简洁

[相关历史经验]
- 上次迁移失败原因：字符集未统一

[待确认信息]
- 生产环境版本可能已更新，需要再次核验
```

把事实类型、可信度和时效性显式写给模型，比塞入一串没有边界的自然语言片段更可靠。

## 七、遗忘：有界记忆才会越来越有用

只写不删的系统，最终会从“拥有历史”退化成“被历史淹没”。遗忘不是缺陷，而是保持信号密度的必要机制。

常见策略包括：

- **TTL**：验证码、临时访问地址、短期任务状态到期自动删除；
- **时间衰减**：越久未使用，保留分越低；
- **访问强化**：被频繁检索且确实有用的记忆提高权重；
- **容量驱逐**：超过用户或租户配额时淘汰低价值记录；
- **事件失效**：项目结束、合同终止、用户撤回授权时立即失效；
- **摘要巩固**：多个相似 episode 合并为一条更稳定的经验。

可以把保留分数写成一个简单模型：

```text
retention =
    a * importance
  + b * access_frequency
  + c * source_trust
  + d * future_utility
  - e * age
  - f * privacy_risk
```

不同记忆需要不同策略。稳定偏好可以长期保存，订单物流状态应随业务事件更新，密码和敏感凭据则根本不应进入通用长期记忆。

### 误删比不删更难排查

遗忘策略的危险在于，它可能删除低频但承重的信息。例如某个合规约束一个月只触发一次，却决定整个执行方案是否合法。因此驱逐不应只看访问频率，还要允许：

- 对关键约束打 `pinned` 标记；
- 按类别设置最低保留期；
- 删除前归档或保留墓碑；
- 记录删除原因与策略版本；
- 为用户提供查看、纠正和清除入口。

## 八、上下文治理：给 working memory 做一次可回溯的 GC

遗忘管理的是长期存储里保留什么；上下文治理管理的是**当前这一轮模型调用里放什么**。两者都在收缩规模，但作用对象与时间尺度不同。

常见方法有两类。

### Compaction：用摘要替换旧上下文

把较早的对话与工具结果压成摘要，腾出 token 空间：

```text
原始 30 轮历史 → 决策摘要 + 当前约束 + 未完成事项
```

它能限制成本和 prefill 延迟，但本质上是有损压缩。摘要模型可能删掉后续仍会用到的 ID、参数或原话，也可能留下“按照前面方案 B”这种悬空引用，而方案 B 的定义已经被压掉。

这就是为什么可以把 compaction 类比为“没有写屏障的 GC”：系统在回收历史，却未必知道哪些细节仍被未来步骤引用。

### Memory tool：把信息换出到上下文之外

另一条路线是先把重要信息写入外部文件或记忆服务，再清理窗口。摘要中可以保留稳定指针，需要细节时再回取原文：

```text
context 摘要：部署方案见 memory://project-42/deployment-plan/v3
```

这样做把“永久删除”变成“换出”，更接近真正的分层存储。

### 给 compaction 增加一道轻量写屏障

可以采用以下组合：

1. 生成过程中允许 Agent 把关键事实标记为 `pinned`；
2. 压缩前检查未完成任务、工具参数、外部引用和用户硬约束；
3. 原文先归档到 context 外，再生成摘要；
4. 摘要中的引用必须指向可解析的稳定 ID；
5. 随机抽样做“摘要后能否完成原任务”的回归测试。

这不会让摘要变成无损操作，但能显著降低静默损坏的概率。

## 九、分层架构：把记忆当成操作系统的虚拟内存

当记忆持续增长，而 context window 始终有限时，一个自然的架构是分层：窗口内放当前最重要的信息，窗口外保存完整历史与可检索归档，Agent 在两层之间按需搬运。

```text
┌──────────────── In-context：快、贵、易失 ────────────────┐
│ 系统指令 │ core memory │ 最近消息 FIFO │ 当前工具结果 │
└───────────────────────┬──────────────────────────────────┘
                        │ 换入 / 换出
┌──────────────── Out-of-context：慢、廉、持久 ────────────┐
│ recall history │ archival memory │ graph │ files │ logs │
└───────────────────────────────────────────────────────────┘
```

### 窗口内的两类信息

- **FIFO 消息队列**：最近对话与工具结果，随着新消息进入而滚动；
- **Core memory blocks**：少量常驻信息，例如 Agent 身份、用户画像、当前任务硬约束。

Core memory 不是越大越好。它每一轮都会被读取，任何冗余都会持续付费。适合常驻的是高频、稳定、对多数决策都有影响的内容。

### 窗口外的两类信息

- **Recall storage**：完整消息历史，按时间、关键词或会话回取；
- **Archival storage**：Agent 主动归档的事实、经验、文档和计划，通常支持语义检索。

### “分页”为什么需要 Agent 会调用工具

在 MemGPT/Letta 一类架构中，换入和换出被实现为工具调用：模型发现窗口将满，或判断某段内容以后有用，就调用记忆函数完成归档；需要历史时，再调用检索工具取回。

这种设计把硬性的窗口上限，转换成额外的模型判断与存储往返成本。但它也引入新风险：模型可能该存时没存、该取时没取、或者取回了错误的页面。

因此，不能把分页完全交给模型自由发挥。生产系统通常还需要硬规则兜底：

- token 阈值触发强制整理；
- 关键事件自动归档；
- 用户偏好与安全约束走确定性写入；
- 检索失败时回退到时间索引或人工确认；
- 所有记忆工具调用可观测、可回放。

### 后台巩固：让 Agent 在空闲时整理笔记

在线请求强调低延迟，不适合每轮都做复杂去重、聚类和知识重写。可以把一部分治理移到后台：

- 合并重复事实；
- 从多次 episode 中提炼稳定经验；
- 重写 core memory；
- 发现矛盾并标记待确认；
- 将成功操作沉淀为 procedural memory。

这类 sleeptime 或 reflection 任务，本质上是把记忆治理从同步请求路径拆到异步计算路径。好处是在线更快，代价是要处理最终一致性、后台成本和错误巩固。

## 十、另一条架构轴：记忆状态归谁所有

“分几层”回答数据怎样组织；“归谁所有”回答数据存在哪里、谁控制保留策略。这两条轴相互独立。

| 归属模型 | 数据位置 | 控制与可移植性 | 代码与运维 | 主要风险 |
| --- | --- | --- | --- | --- |
| App-owned | 开发者自己的存储 | 最高 | 代码最多 | 自己承担全部实现与可靠性 |
| Framework-owned | 自部署框架及数据库 | 较高 | 中等 | 框架升级、扩容、备份和监控 |
| Vendor-owned | 模型或云厂商基础设施 | 较低 | 最少 | 厂商锁定、保留不透明、数据驻留 |

### App-owned：控制最多

应用只把必要内容交给模型，记忆文件、数据库和保留策略全部由自己管理。它适合强合规、需要跨模型迁移、需要细粒度删除与审计的系统。

代价同样直接：存储、抽取、索引、权限、TTL、备份、恢复、评测都要自己负责。

### Framework-owned：在控制与效率之间折中

Mem0、LangMem、Zep 等框架提供抽取、存储或检索能力，但底层数据通常仍由团队部署和运维。它们与具体模型相对解耦，适合希望保留迁移能力、又不想从零造完整记忆栈的团队。

### Vendor-owned：最省代码，但最早产生锁定

厂商托管对话状态或 memory bank 可以快速上线，却会把数据格式、生命周期和迁移能力绑定到外部平台。对于包含 PII、要求数据不出境或必须部署在客户机房的场景，这可能从一开始就不满足约束。

归属不是一个后期优化项。上线后再从 vendor-owned 迁回 app-owned，通常意味着重新实现抽取逻辑、重建索引、转换历史数据，并处理无法完整导出的状态。

## 十一、框架怎么选：先看存储模型，再看 API

下面的比较来自原始教程截至 2026 年 6 月的整理，重点不是给框架排总榜，而是说明它们分别把什么当作“记忆”的核心。

| 方案 | 核心模型 | 强项 | 更适合的场景 | 需要接受的代价 |
| --- | --- | --- | --- | --- |
| Mem0 | 原子事实 + 向量/KV/SQL，可选图 | 选择性抽取、冲突消解、易接入 | 聊天助手、用户偏好、快速个性化 | 写入要做模型抽取，复杂时间查询需补能力 |
| Letta | Core blocks + recall + archival 的分层 Agent OS | Agent 自编辑、长生命周期、后台巩固 | 自治型 Agent、持续维护 persona 与工作状态 | 控制流更复杂，依赖模型正确调用记忆工具 |
| Zep / Graphiti | 双时态知识图谱 | 时间正确、多跳关系、保留历史状态 | 客户状态演化、关系网络、历史追溯 | 摄入慢、图运维与实体抽取成本更高 |
| LangMem | LangGraph 的 BaseStore、namespace 与 thread | 与现有 LangGraph 状态模型衔接 | 已使用 LangGraph 的团队 | 能力上限取决于所接存储与应用治理 |
| Cognee | Knowledge graph + vector | 把异构语料转成实体、关系与语义块 | 大量异构资料的 grounding | ECL 管线和图结构增加复杂度 |

可以用下面的顺序做判断。

### 问题 1：事实会不会变化，还要不要查历史

- 只关心当前偏好：原子事实 + recency-wins 往往足够；
- 既要当前状态又要历史追溯：优先考虑时序或双时态模型；
- 有大量人物、组织、项目关系：图结构的价值会上升。

### 问题 2：Agent 是否需要主动整理自己的记忆

- 只需被动从对话中抽取偏好：选择简单的自动抽取层；
- 需要自己维护计划、persona、经验与技能：分层、自编辑、后台巩固更重要。

### 问题 3：现有技术栈是什么

- 已深度使用 LangGraph：复用 thread、namespace 和 store 往往成本最低；
- 已有 Neo4j 与图团队：时序图方案的额外门槛更低；
- 只有关系库与向量扩展：先做 SQL/KV + vector 的混合方案更务实。

### 问题 4：数据必须在哪里

合规和数据驻留是硬约束，不应被“接入更快”覆盖。若要求数据留在自有机房，vendor-owned 方案可能直接出局。

### 问题 5：真正的瓶颈是写、存、取，还是治理

有些系统不是召回不准，而是写入时就抽错了；有些不是数据库不够强，而是旧值从未失效；还有些是检索正确，却在上下文里被大量工具结果淹没。先定位生命周期环节，再决定是否更换框架。

## 十二、一个最小可用的工程设计

下面给出一套不绑定具体框架的设计骨架。

### 1. 记忆记录结构

```ts
type MemoryRecord = {
  id: string;
  tenantId: string;
  userId?: string;
  agentId?: string;

  kind: "episodic" | "semantic" | "procedural";
  subject: string;
  predicate: string;
  value: unknown;
  text: string;

  source: "user" | "tool" | "document" | "model_inference";
  sourceRef?: string;
  confidence: number;
  importance: number;

  observedAt: string;
  validFrom?: string;
  validUntil?: string;
  expiresAt?: string;

  canonicalEntityIds: string[];
  embedding?: number[];
  pinned: boolean;
  version: number;
  status: "active" | "superseded" | "deleted";
};
```

这个结构故意不只保存文本。只要系统要处理更新、删除、追溯和权限，就必须有作用域、来源、时间和状态。

### 2. 写入流程

```python
def write_memory(event, scope):
    if contains_secret(event) or not allowed_to_persist(event, scope):
        return []

    candidates = extract_atomic_memories(event)
    results = []

    for candidate in candidates:
        candidate = normalize_entities(candidate)
        neighbors = find_related_memories(candidate, scope, limit=8)
        action = resolve(candidate, neighbors)

        if action.type == "ADD":
            results.append(insert(candidate))
        elif action.type == "UPDATE":
            results.append(supersede(action.old_id, candidate))
        elif action.type == "DELETE":
            results.append(tombstone(action.old_id, reason=action.reason))

    emit_audit_log(event, candidates, results)
    return results
```

关键点有四个：写入前做敏感信息过滤；抽取后做实体归一；冲突在落库前处理；每一步都记录审计日志。

### 3. 读取流程

```python
def read_memory(query, scope, token_budget):
    candidates = hybrid_recall(
        query=query,
        scope=scope,
        vector_k=30,
        keyword_k=20,
        graph_k=20,
    )

    candidates = filter_permissions(candidates, scope)
    candidates = filter_valid_time(candidates, now())
    candidates = deduplicate(candidates)
    ranked = rerank(query, candidates)
    selected = pack_by_value(ranked, token_budget)

    return arrange_for_prompt(selected)
```

注意最后不是固定 top-k，而是按 token 预算做价值装箱：一条极重要的硬约束，可能比十条相似经历更值得进入窗口。

### 4. 后台治理

```text
每小时：处理过期 TTL、撤销授权、低风险去重
每天：聚类相似 episode、发现冲突、生成待确认项
每周：更新保留分、归档低价值记录、抽样评测
按事件：项目结束、用户删除、合同终止时执行强制失效
```

### 5. 在线请求编排

```text
接收请求
  → 读取会话 working memory
  → 判断本轮需要哪些长期记忆
  → 按作用域与权限检索
  → 把少量高价值记忆注入 prompt
  → 模型推理与工具调用
  → 对输出和观察做写入候选抽取
  → 高风险写入确认
  → 持久化并更新审计日志
```

不是每轮都必须写入，也不是每轮都必须检索。先由任务分类器或轻量规则判断是否需要，能显著降低成本和无意义记忆。

## 十三、六类生产失败模式，以及它们真正发生在哪一环

### 1. 记忆投毒

**现象**：不可信网页、邮件或工具结果中的指令被写进长期记忆，未来在特定条件下触发。

**根因**：把“模型看见的内容”误当成“可以信任并持久化的事实”。

**防线**：

- 所有写入带 provenance；
- 外部内容默认低信任；
- 文档中的指令与事实分离；
- 能触发动作的记忆在执行前二次授权；
- 关键账户、地址、权限变更不能只靠自然语言更新。

### 2. 陈旧与矛盾

**现象**：系统有时说用户使用 PostgreSQL，有时又说 MySQL。

**根因**：旧值没有在写入阶段失效，或存储模型无法表达时间。

**防线**：对状态类字段采用 UPDATE/supersede；需要历史追溯时使用有效期或双时态；检索时过滤非当前记录。

### 3. 检索漂移与 distractor

**现象**：相关内容很多，但真正关键的一条没有排到前面，或被相似错误案例带偏。

**根因**：只依赖 embedding，相似度被误当成任务价值。

**防线**：混合召回、实体匹配、时间过滤、来源权重、rerank、严格 top-k 与 prompt 编排。

### 4. 上下文膨胀与腐烂

**现象**：对话越长越慢、成本持续上升，模型反而更容易忘记关键约束。

**根因**：把全量历史当记忆，每轮重复发送；没有 compaction 与外部存储分层。

**防线**：设治理阈值，先归档再压缩；工具结果用引用替代全文；常驻 core memory 保持小而稳定。

### 5. 实体碎片化

**现象**：同一个人、公司或项目以多个别名保存，任何一次查询只能找到一部分。

**根因**：写入前没有 canonicalization 和 entity resolution。

**防线**：稳定实体 ID、别名表、合并审核、图约束和跨来源实体解析。

### 6. 错误评测与隐私泄露

**现象**：长文本找针测试几乎满分，却在真实跨会话任务中频繁记错；或者系统无意中长期保存了密码与 PII。

**根因**：把“窗口容量”当成“记忆连续性”，同时没有为不同数据类别定义保留规则。

**防线**：评测写入、更新、冲突、时间、多跳、遗忘和删除；写入前做敏感信息识别，按类别设置 TTL、加密、访问控制和用户删除能力。

## 十四、怎样评测：不要只测“能不能从长文本里找出来”

一个真正的记忆评测集，至少应该覆盖以下能力：

| 能力 | 测试问题 |
| --- | --- |
| 写入选择 | 系统能否记住关键事实，同时忽略寒暄与提示注入 |
| 跨会话连续性 | 新会话能否正确恢复用户状态与未完成事项 |
| 更新与冲突 | 新值出现后，旧值是否失效，历史是否可追溯 |
| 时间推理 | 能否区分“现在”“当时”和“系统何时知道” |
| 多跳关系 | 能否跨实体和事件组合答案 |
| 检索抗干扰 | 加入相似错误记忆后是否仍能选对 |
| 遗忘与删除 | TTL、撤回授权和用户删除是否真正生效 |
| 上下文效率 | 达到相同正确率需要注入多少 token、延迟多大 |
| 安全 | 不可信内容能否污染记忆并触发高风险动作 |
| 可解释与审计 | 能否说明答案用了哪条记忆、哪个版本和什么来源 |

评测时还要记录链路指标，而不只看最终答案：

```text
抽取 precision / recall
更新动作准确率
过期事实命中率
检索 precision@k 与 nDCG
注入 token 数
首 token 延迟与总延迟
错误记忆写入率
删除完成率
每用户每月存储与模型成本
```

最终答案错了，可能是抽取、存储、检索、编排或生成任一环节导致。没有链路指标，就只能不断换 embedding 或换大模型碰运气。

## 十五、把整套方法压缩成十条原则

1. **先定义记忆，再选数据库。** 你要记的是事实、经历、关系，还是技能？
2. **把写入路径当作第一等能力。** 这是 Memory 与纯 RAG 的真正分界。
3. **原始对话不是理想的长期记忆格式。** 先抽取、归一和对账。
4. **冲突尽量在写入时吸收。** 不要让每次读取都重新裁决旧值和新值。
5. **来源和时间必须进入数据模型。** 没有 provenance，就无法安全更新；没有时间，就无法回答“现在”。
6. **检索更多不等于知道更多。** distractor 会主动伤害答案，精排与编排比盲目扩大 top-k 更重要。
7. **遗忘是功能，不是损失。** 只有有界、可更新、可删除的记忆才会长期保持价值。
8. **压缩前先归档。** Compaction 是有损操作，关键细节必须有可回取的外部副本。
9. **把分层与归属分开决策。** in/out-of-context 是容量架构，app/framework/vendor-owned 是控制权架构。
10. **用连续性基准评测连续性。** 不要拿长文本找针的高分证明记忆系统已经可靠。

## 结语：记忆的价值不在“记得多”，而在“维护得对”

智能体记忆系统表面上像一个存储问题，实际更接近状态管理、数据库、信息检索、安全与操作系统设计的交叉地带。

最简单的实现可以只是一张表加一个向量索引，但只要 Agent 开始长期运行，真正困难的问题就会依次出现：

- 什么值得写入？
- 新事实与旧事实冲突时信谁？
- 当前真相和历史版本怎样共存？
- 为什么召回越多，答案反而越差？
- 哪些信息该忘，哪些信息必须永久保留？
- 上下文快满时，怎样压缩而不破坏未来任务？
- 记忆数据究竟归应用、框架还是厂商所有？
- 如果一条记忆来自不可信网页，它还能触发工具执行吗？

当这些问题都有明确答案时，系统才不只是“接了一个向量库”，而是真正拥有了一套可持续演化的记忆机制。

> **优秀的 Agent 记忆不是无限累积的历史，而是一份持续被验证、更新、压缩、遗忘并可追溯的当前认知。**
