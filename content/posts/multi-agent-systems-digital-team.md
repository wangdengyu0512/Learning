# 多智能体不是多开几个模型：从数字团队到生产系统

> 单智能体解决的是“一个 AI 能做什么”，多智能体解决的是“多个能力如何被组织起来”。

设想这样一个任务：在两小时内完成一份新能源汽车行业研究报告。报告既要覆盖市场规模、主要厂商和供应链，也要分析电池技术、政策变化和企业财务数据，还必须核验关键数字、保留资料来源，并最终形成结构清晰的结论。

如果把所有工作都交给一个大模型，它需要在同一段上下文中不断切换角色：先制订计划，再搜索资料，然后阅读网页、比较数据、计算指标、判断来源可靠性，最后组织文字。任务越长，早期信息越容易被后续内容淹没；工具调用越多，任何一步的错误也越可能污染最终答案。

多智能体系统给出的思路很像组织一支研究团队：由一个主管拆解目标，市场、技术、政策和财务智能体分别调查，核验智能体检查证据，写作智能体负责成文。每个成员只处理有限问题，再通过明确的接口汇总结果。

这听起来很自然，也很容易被过度想象。多智能体并不是把同一个模型复制几份，让它们在群聊中自由讨论。真正决定效果的，是任务能否被合理拆解、信息能否准确流动、冲突能否得到解决，以及系统是否知道何时停止。

## 一、什么是多智能体系统

在讨论“多个”之前，需要先明确什么是智能体。

一个大语言模型只能根据输入生成输出。一个智能体则在模型之外增加了目标、指令、工具、状态和执行循环。它能够观察当前环境，决定下一步动作，调用搜索、数据库、代码执行器或业务 API，再根据返回结果继续行动。

可以把单智能体的基本循环写成：

```text
读取目标与当前状态
        ↓
判断下一步行动
        ↓
调用工具或生成结果
        ↓
观察执行结果
        ↓
继续、重试、修正或终止
```

多智能体系统则包含两个或更多这样的执行单元。它们可以拥有不同的角色、提示词、工具、权限、上下文和模型，并通过消息或共享状态共同完成目标。

这里有一个关键区别：**多步骤不等于多智能体。**

“读取文件、提取字段、校验格式、写入数据库”虽然包含多个步骤，但如果执行顺序固定、分支规则明确，用普通工作流通常更合适。只有当系统需要在运行时判断“应该让谁处理”“是否需要增加新任务”“哪些方向值得继续探索”时，智能体的自主决策才真正产生价值。

因此，可以把三类系统放在一条连续线上：

| 系统形态 | 控制流由谁决定 | 优点 | 主要代价 |
| --- | --- | --- | --- |
| 固定工作流 | 开发者预先编码 | 稳定、便宜、容易测试 | 难以处理开放问题 |
| 单智能体 | 一个模型运行时决策 | 结构简单、上下文统一 | 容易过载，长任务不稳定 |
| 多智能体 | 多个模型节点协同决策 | 可分工、可并行、可隔离 | 协调复杂，成本和失败面扩大 |

## 二、为什么要让 AI 组队

多智能体最有价值的地方，不是生成更多文字，而是改变复杂任务的组织方式。

### 1. 专业化分工

一个智能体可用的工具越多、职责越宽，它就越难稳定选择正确动作。把检索、计算、编码、审查等职责拆开，可以让每个智能体拥有更窄的目标和更少的工具。

例如，一个代码智能体只访问代码仓库和测试命令，一个安全审查智能体只读取变更和规则库，一个发布智能体才拥有部署权限。这样的拆分不仅降低选择难度，也让权限边界更清楚。

但“给智能体起不同名字”不等于真正分工。如果三个智能体使用相同提示词、相同工具和相同上下文，只是分别叫“产品专家”“技术专家”和“业务专家”，它们很可能产生内容相似的答案。有效分工必须落实到任务、信息和能力边界上。

### 2. 并行探索

开放式研究任务往往不是一条推理链，而是一片需要搜索的空间。不同智能体可以同时调查不同市场、数据源或技术路线，再由协调者汇总。

Anthropic 在多智能体研究系统的工程复盘中，将这种模式概括为由主智能体负责规划和综合，多个子智能体在独立上下文中并行探索。它适合“先扩大覆盖面，再收敛结论”的任务，但并行调用也意味着明显更高的 Token 和计算成本。

### 3. 上下文隔离

复杂任务常见的隐性问题是上下文污染。搜索日志、失败尝试、临时猜测和无关材料全部塞进一条对话后，模型需要从越来越多的噪声中寻找真正重要的信息。

多智能体允许每个子任务拥有独立上下文。政策智能体不需要看到财务分析的全部计算过程，写作智能体也不必读取每一次失败的搜索，只需要获得经过整理的结论、证据和不确定性。

上下文隔离相当于给系统建立信息防火墙。不过隔离过度也会造成信息缺失。正确做法不是“越少越好”，而是只传递完成任务必需的稳定事实、约束和接口。

### 4. 独立验证

让生成者自己检查自己的答案，常常只能发现表面问题。独立的核验智能体可以使用不同提示词、不同信息来源，甚至不同模型，对事实、计算和引用逐项复查。

需要注意的是，多个智能体投票并不天然等于事实核验。如果它们共享同一份错误材料，或者使用高度相似的模型和推理方式，多数意见只会把相关性错误包装成共识。真正的验证需要证据独立，而不只是角色名称不同。

## 三、四种常见协作架构

多智能体系统可以有很多表现形式，但大部分设计都能归入四类。

### 1. 主管与执行者

主管智能体理解目标、拆分任务、选择执行者并汇总结果，执行者只处理被分配的局部任务。

```text
              主管智能体
          /       |       \
     市场研究   技术研究   财务分析
          \       |       /
              汇总与核验
```

这种结构的优点是控制权集中，容易设置预算、权限和人工审批。缺点是主管可能成为瓶颈：一旦它错误地理解目标或遗漏关键子任务，整个团队会沿着错误方向高效前进。

### 2. 专家交接

当前智能体发现问题超出自身职责后，把任务和必要上下文交给另一个智能体。例如客服入口识别出退款请求后，将控制权交给退款专员；退款专员发现疑似欺诈，再交给风控智能体。

交接模式适合阶段边界清晰、每个角色都能独立接管后续工作的流程。它的风险是循环路由和信息损失，因此每次交接都应说明原因、已完成工作、待解决问题和剩余预算。

### 3. 生成、批评与裁决

一个智能体提出方案，另一个智能体寻找漏洞，生成者据此修改，必要时由裁判决定是否通过。这种模式适合代码审查、方案评估和高价值内容生成。

问题在于，讨论轮次增加并不必然提高质量。没有新证据时，反复反思很容易变成措辞调整；裁判智能体也可能被更自信、更流畅但并不正确的答案影响。系统应限制轮次，并要求批评者给出可验证的问题，而不是笼统评价。

### 4. 图工作流

将智能体组织成显式有向图，是生产系统中更常见的方式。节点可以是模型、工具、规则或人工审批，边则表示顺序、并行、条件分支和重试关系。

图工作流保留了部分自主决策，又把关键控制流放回确定性程序中。例如研究方向可以由模型动态决定，但“引用未通过检查就不能发布”应由代码强制执行，而不是只写在提示词里。

实际系统很少只使用一种模式。更常见的组合是：图工作流控制总体阶段，主管智能体在某个阶段创建并行任务，专业智能体之间允许有限交接，高风险操作之前再进入人工审批。

## 四、一个研究团队如何完成任务

仍以新能源汽车研究报告为例。系统可以先把用户目标转换为一份结构化任务说明：研究范围是什么，数据截止日期是什么，必须回答哪些问题，哪些来源可以接受，最终输出采用什么格式。

主管智能体随后创建四个可并行任务：

- 市场智能体负责销量、区域分布和竞争格局；
- 技术智能体负责动力电池、补能和辅助驾驶；
- 政策智能体负责主要市场的法规和补贴；
- 财务智能体负责代表企业的收入、利润和研发投入。

每个智能体返回的不能只是一段自然语言，而应是一份结构化结果：

```json
{
  "task_id": "market-analysis",
  "status": "completed",
  "conclusions": [],
  "evidence": [],
  "source_dates": [],
  "uncertainties": [],
  "conflicts": [],
  "recommended_next_actions": []
}
```

主管收到结果后，先检查覆盖度，而不是立即写报告。如果两个来源给出的市场规模不同，它需要创建一个冲突核验任务；如果财务数据只覆盖三家公司，它需要判断这是范围限制还是执行遗漏。

核验智能体随后检查关键数字是否与原始来源一致、不同指标的统计口径是否兼容、引用是否真正支持结论。只有通过质量门禁的内容才进入写作阶段。

这个案例揭示了一个经常被忽略的事实：多智能体的核心产物不是“对话”，而是**带有来源、状态和责任边界的任务结果**。一旦所有协作都依赖自由文本，系统很快会遇到信息丢失、格式漂移和责任不清的问题。

## 五、多智能体为什么经常失败

多智能体增加了能力，也增加了新的故障类型。

### 1. 错误地拆分任务

并不是所有问题都能并行。写一份需要严密论证的技术方案时，后一个判断可能依赖前一个结论。强行拆给多个智能体，会让每个成员在缺少前置条件的情况下自行假设，最后产生彼此无法拼接的答案。

好的子任务应该目标清楚、输入充分、输出可验收，并且与其他任务尽量减少隐式依赖。

### 2. 角色重叠与责任真空

职责重叠会造成重复工作，职责之间存在空隙则会让关键问题无人处理。更麻烦的是，每个智能体都可能以为“最终会有人负责核验”，结果没有任何节点真正承担责任。

因此，每一类输出都需要明确唯一的责任方。协作者可以有多个，最终负责者只能清晰地落在一个节点或人工角色上。

### 3. 错误沿协作链传播

子智能体输出的内容一旦被写入共享状态，后续节点通常会把它当作事实。一个错误数字可能先被分析智能体引用，再被写作智能体扩展，最后被审查智能体因为“上下文中多次出现”而误认为可靠。

解决办法不是让所有智能体互相相信，而是区分“主张”和“已验证事实”。未经核验的内容必须保留来源和置信状态，不能悄悄升级为系统事实。

### 4. 无限讨论与错误终止

自由协作容易出现两种极端：一是智能体不断建议继续调查，系统无法结束；二是主管过早认为任务完成，实际上遗漏了关键部分。

终止条件应尽量由可计算的标准决定，例如必答问题覆盖率、引用校验状态、预算上限、最大轮次和无新增证据次数。模型可以建议终止，但程序应拥有最终控制权。

### 5. 成本和延迟失控

单智能体的一次重试只增加一次调用，多智能体中的一次重新规划却可能重新触发整个任务树。每个子智能体都有独立上下文，汇总时又要把结果传给上层，Token 消耗会随着分支数、深度和重试次数快速增长。

因此，多智能体系统必须像云服务一样管理预算，而不能把成本当作上线后的统计项。任务开始前分配预算，执行中记录消耗，接近上限时缩减搜索范围或降级为人工处理。

## 六、什么时候应该使用多智能体

一个实用的判断方法，是连续问四个问题。

第一，任务能否拆成相对独立的子问题？如果所有步骤都强依赖前序结果，单智能体或顺序工作流通常更合适。

第二，任务是否真的需要运行时决策？如果人员、步骤和路由都能提前确定，固定工作流会更稳定。

第三，多样化探索是否能显著提高结果价值？研究、方案搜索、复杂诊断和大型代码库分析通常受益较大；摘要、改写和格式转换通常不会。

第四，结果价值能否覆盖额外成本？低价值、高频、低延迟任务往往不适合使用昂贵的智能体团队。

可以用下面的经验表做初步判断：

| 任务特征 | 更合适的选择 |
| --- | --- |
| 步骤固定、规则明确 | 普通程序或工作流 |
| 工具不多、任务短、上下文统一 | 单智能体 |
| 多方向检索、子任务可并行 | 主管加多个执行者 |
| 阶段边界清晰、需要专家接管 | 交接模式 |
| 高价值结果、需要独立质检 | 生成加核验智能体 |
| 涉及资金、删除、发布等高风险动作 | 工作流加人工审批 |

最稳妥的演进顺序不是一开始就设计智能体组织，而是先建立单智能体基线。只有明确知道单智能体失败在哪里，才能判断增加的是有效分工，还是额外复杂度。

## 七、从演示走向生产

一个能在演示中完成任务的多智能体系统，距离生产可用通常还差五类工程能力。

### 1. 明确协作契约

每个智能体都应定义职责、输入、输出、可用工具、数据权限、完成标准和失败策略。自然语言提示可以解释目标，但关键字段应由 Schema 约束。

### 2. 把控制权放在合适的位置

开放判断交给模型，确定规则交给代码。是否需要补充搜索可以由模型判断，但支付金额上限、数据访问范围、重试次数和发布门禁必须由程序控制。

### 3. 为副作用建立安全边界

搜索和读取通常可以自动执行，发送邮件、修改数据库、下单和删除数据则需要更严格的权限。系统还应使用幂等键、事务或补偿机制，避免重试导致重复扣款、重复通知等真实损失。

### 4. 建立端到端可观测性

生产问题不能只靠阅读最终回答来定位。系统需要记录任务如何被拆分、智能体为何被选择、看到哪些输入、调用了什么工具、产生了哪些状态变化，以及每条分支消耗了多少时间和成本。

一次完整执行应该能够还原为一棵因果树，而不是散落的聊天记录。

### 5. 用任务指标评估，而不是看起来是否聪明

评估至少应覆盖：任务成功率、事实准确率、必答项覆盖率、工具调用成功率、人工接管率、平均延迟和单任务成本。对于高风险场景，还要单独评估越权操作、错误副作用和恢复能力。

只有在相同任务集上与单智能体基线比较，才能知道多智能体究竟带来了收益，还是只带来了更复杂的执行轨迹。

## 八、协议和框架解决不了什么

近年的智能体框架已经能够提供路由、交接、群组对话、共享状态、图工作流和运行追踪。A2A 等协议也试图解决不同平台智能体之间的发现、通信和任务状态交换。

这些基础设施很重要，但它们解决的是“如何连接”，不是“如何正确协作”。即使两个智能体能够互相发现并交换标准消息，系统仍然需要回答：

- 谁可以调用谁？
- 谁承担最终责任？
- 如何防止循环委派？
- 如何验证对方返回的信息？
- 如何撤销已经产生的副作用？
- 跨组织调用发生事故时如何审计？

这与微服务的发展很相似。RPC、消息队列和服务发现让系统更容易连接，却不会自动给出正确的服务边界、一致性策略和故障恢复方案。多智能体最终仍然是系统设计问题。

## 九、未来不是更多智能体，而是更好的组织

未来的多智能体系统可能不再使用固定团队，而是根据任务动态组建。协调器会从能力目录中选择合适的模型、工具或外部智能体，在成本、速度、质量和权限之间做权衡；简单任务交给小模型，高难度判断交给强模型，确定性计算交给传统程序。

智能体之间的差异也不会只来自角色提示词。它们可能拥有不同训练背景、私有数据、工具权限和运行环境。企业内部智能体可以安全地调用合作伙伴智能体，但只暴露完成任务所需的最小信息。

与此同时，治理会成为比“自治”更重要的主题。身份、授权、审计、预算、数据边界、责任归属和人工干预，不再是外围功能，而是智能体基础设施的一部分。

真正成熟的系统不会追求让智能体无限自由地交流，而会让每一次委派都有目标，每一条结论都有证据，每一个动作都有权限，每一次失败都有恢复路径。

## 结语

多智能体看起来像一个模型能力问题，实质上更接近组织设计和分布式系统问题。

当任务可以并行探索、需要专业分工、上下文必须隔离，并且结果价值足够高时，多智能体能够突破单智能体的覆盖面限制。但如果任务本身简单、流程固定或者缺少验证标准，引入更多智能体只会放大成本、延迟和错误传播。

因此，设计多智能体系统时，最先问的不是“需要几个智能体”，而是以下几个更基本的问题：

1. 目标是否能够被拆成可独立验收的子任务？
2. 每个角色是否拥有真实而清晰的能力边界？
3. 信息在传递过程中如何保留来源和可信状态？
4. 谁负责发现冲突、验证结论和决定终止？
5. 系统失败后，如何恢复并控制真实世界的副作用？

模型决定一个成员的能力上限，组织方式决定整个系统能否稳定地产生结果。多智能体真正重要的进步，不是让更多 AI 同时说话，而是让它们开始以一种可验证、可治理、可持续的方式共同工作。
