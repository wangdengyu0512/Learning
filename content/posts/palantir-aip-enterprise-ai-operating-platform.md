生成式 AI 进入企业以后，最容易完成的是一个演示：接入大模型，导入几份文档，再做一个能够问答的聊天窗口。真正困难的是下一步：模型能否理解订单、设备、客户和供应商之间的业务关系？能否读取实时状态而不是过期文档？能否调用预测模型和业务规则？能否在获得授权后创建工单、调整库存或通知负责人？如果答案错误，组织能否知道它用了什么数据、调用了什么工具，又是谁批准了最后的操作？

这些问题共同指向一个事实：**企业缺少的通常不是一个更会说话的模型，而是一套让模型安全进入业务系统的运行环境。**

Palantir AIP（Artificial Intelligence Platform）正是围绕这个问题构建。它不是一款独立的大模型，也不只是一个企业知识库或 Agent 编排器。更准确地说，AIP 是 Palantir 平台中的 AI 能力层：它把大模型接入 Foundry 已经治理的数据、Ontology 表达的业务对象、Functions 封装的业务逻辑和 Actions 定义的可执行操作，再通过权限、审计、评估与人工审批控制整个过程。

理解 AIP 的关键不在于记住一组产品名称，而在于理解一条从数据到行动的链路：

```text
企业数据
  -> 可治理的数据资产
  -> Ontology 中的业务对象与关系
  -> 模型、规则和 Functions
  -> AIP Logic 或 Agent 编排
  -> 人工审批或自动化策略
  -> Actions 与外部系统操作
  -> 结果回写、评估和持续改进
```

本文以 Palantir 官方产品页和 Foundry 文档为主要依据，资料核验日期为 **2026 年 10 月 29 日**。由于 Palantir 的产品命名和功能仍在持续演进，具体可用能力还会受到版本、部署环境、授权和管理员配置影响。

## 一、企业 AI 的断点不在模型，而在运营闭环

一个通用大模型可以解释供应链概念，也可以给出处理缺货的常识性建议，但它并不知道某家企业今天有哪些订单、每个仓库有多少可用库存、哪些客户享有优先级，也不知道调拨动作受哪些财务和合规规则约束。

把模型用于真实业务，至少要跨过五个断点。

### 1. 数据断点：模型看到的不是企业当前状态

企业信息散落在 ERP、CRM、MES、数据仓库、文档、邮件和第三方系统中。即使通过 RAG 把文档交给模型，检索结果也很难表达实时库存、对象关系和事务状态。模型可能读过运输政策，却不知道某批货物此刻在哪里。

### 2. 语义断点：表和字段不等于业务世界

数据库里可能存在 `order_header`、`inventory_snapshot` 和 `shipment_event`，业务人员思考的却是“高优先级订单”“可替代库存”和“存在延误风险的运输任务”。如果没有稳定的业务语义层，提示词和应用就会直接绑定底层表结构，任何数据变更都可能向上扩散。

### 3. 行动断点：回答没有进入执行系统

聊天机器人可以建议“将订单改由华东仓履约”，但真正执行需要检查库存、权限、成本、客户承诺和审批条件，还要调用 ERP 或仓储系统完成写回。没有受治理的动作接口，AI 的价值停留在建议文本中。

### 4. 治理断点：模型能力越强，风险面越大

当 Agent 能查询更多数据、调用更多工具时，越权访问、错误操作、提示注入和不可追责问题也会同步放大。企业需要的不是一个拥有超级账号的 Agent，而是一个沿用既有权限、只能调用获准工具、关键步骤可被阻止和审计的执行主体。

### 5. 评估断点：演示可用不等于生产可靠

模型输出具有概率性。同一请求可能产生不同答案，提示词、模型版本、检索配置和工具描述的变化都可能造成回归。若没有可重复的测试集、评估函数和线上反馈，团队只能凭少量对话判断效果。

Palantir AIP 的产品设计可以被看作对这五类断点的系统回应：Foundry 处理数据集成与治理，Ontology 建立业务语义和操作边界，AIP 接入模型并编排 AI 工作流，Apollo 则负责软件在不同基础设施上的部署与持续运行。

## 二、AIP 到底是什么，又不是什么

[Palantir AIP 官方产品页](https://www.palantir.com/platforms/aip/)强调的是把 AI 接入组织的 operations，而不只是让员工与模型对话。这里的 operations 指订单履约、生产调度、资产维护、医院运营、风险调查等能够改变业务状态的工作。

从产品职责看，AIP 主要提供四类能力：

| 能力 | 回答的问题 | 典型产物 |
| --- | --- | --- |
| 模型接入 | 使用哪个模型，模型可以处理哪些上下文 | 模型配置、端点、调用策略 |
| AI 编排 | 如何把 Prompt、检索、函数和工具组成流程 | Logic function、Agent、自动化流程 |
| 业务连接 | AI 如何理解对象并执行受控操作 | Ontology 查询、Function、Action |
| 治理与评估 | 如何限制、审计和验证 AI 行为 | 权限、日志、评估集、审批与监控 |

AIP 不是以下几类事物的简单替代品：

- **不是基础模型。** 它可以接入不同提供方的模型，也可以使用组织获准的自有模型。模型负责生成与推理，AIP 负责让这些能力在企业上下文中被组合和治理。
- **不是只有向量检索的 RAG 产品。** 文档检索是能力之一，但 Ontology 对象、实时属性、关系、结构化查询、业务函数和 Actions 同样可以成为模型上下文或工具。
- **不是独立于 Foundry 的通用 Agent 框架。** AIP 的主要差异来自它与 Foundry 数据资产、Ontology 和安全模型的深度结合。
- **不是默认全自动的决策系统。** 平台可以支持从只读助手、建议生成、人工审批到受限自动化的不同自治等级，是否自动执行取决于场景风险和配置。

一句话概括：**AIP 把大模型从一个外部文本服务，变成受企业数据、语义、权限和操作契约约束的运行组件。**

## 三、Foundry、AIP 与 Apollo 如何分工

Palantir 常把 Foundry、AIP 和 Apollo 放在同一平台叙事中。三者并不是彼此隔离的三套系统，而是关注不同层面的能力。

### 1. Foundry：数据与运营基础

Foundry 负责连接数据源、转换数据、管理血缘与质量、构建数据产品，并通过 Ontology 将数据映射成业务对象。它回答的是：组织掌握了哪些数据，这些数据如何被治理，又如何形成可供分析和运营使用的共同基础。

### 2. AIP：模型与智能应用能力

AIP 负责把 LLM 和其他 AI 模型放入上述数据与业务环境。它提供构建、测试和运行 AI 逻辑、Chatbot/Agent、自动化流程与评估的工具。它回答的是：模型可以看见什么、调用什么、如何推理、何时需要人批准，以及怎样判断效果。

### 3. Apollo：跨环境的软件交付与运行

Apollo 关注软件如何部署、升级和持续运行。对需要在公有云、私有云、隔离网络或边缘环境中使用 AIP 的组织而言，部署不是后置问题，而是平台能力的一部分。Apollo 负责将经过治理的软件版本持续交付到目标环境，并帮助维持版本和运行状态。

可以用一个简化关系理解三者：

```text
Foundry：把企业数据变成可治理、可操作的数字资产
   |
   +-- Ontology：把资产组织成业务对象、关系、逻辑和动作
   |
AIP：让模型基于这些对象推理，并通过受控工具参与业务流程
   |
Apollo：把整套能力部署并持续运行在企业需要的基础设施上
```

这也解释了为什么只从“支持哪些大模型”比较 AIP，容易错过其核心。模型列表会变化，真正形成平台黏性的，是数据治理、Ontology、应用、权限与操作流程组成的整体。

## 四、Ontology：AIP 理解企业的共同语言

[Palantir Ontology](https://www.palantir.com/platforms/ontology/) 是理解 AIP 的核心。官方将 Ontology 描述为组织的 operational layer。它位于底层数据之上，把表、模型和业务逻辑映射到设备、订单、客户、工厂、员工、运输任务等现实业务概念。

### 1. 从数据表变成业务对象

假设供应链系统中存在订单表、库存快照表、运输事件表和供应商主数据。Ontology 可以在它们之上定义：

- `Order`、`Product`、`Warehouse`、`Shipment`、`Supplier` 等 Object Type；
- 订单金额、承诺日期、库存数量和运输状态等 Property；
- 订单包含产品、运输任务履约订单、供应商供应产品等 Link；
- 调拨库存、变更履约仓、升级风险事件等 Action；
- 计算延误风险、筛选替代仓和估算成本等 Function。

应用和 Agent 不再直接面对一组没有业务语义的表，而是面对“订单 `O-1024` 由运输任务 `S-81` 履约，关联客户 `C-9`，当前风险为高”这样的对象网络。

### 2. 语义元素与动力元素

Ontology 不只是对象和关系。Palantir 文档将对象、属性和链接视为描述业务世界的语义元素；Actions、Functions 与安全控制则使它具备改变世界的能力。

例如，“重新分配库存”不是让模型随意修改某个字段，而是一个明确的 Action 契约：

```text
输入：订单、来源仓、目标仓、数量、原因
前置校验：订单未发运，目标库存可用，操作者拥有权限
业务约束：不能破坏更高优先级订单的库存承诺
状态修改：更新分配关系和可用库存
副作用：调用 ERP，通知仓库，创建审计记录
审批：超过阈值时由区域运营经理批准
```

同一个 Action 可以被 Workshop 应用、业务人员和 AIP Agent 复用。这样，AI 并不是绕过现有流程写数据库，而是调用组织已经定义和治理的业务能力。

### 3. 为什么不直接把表塞进 Prompt

直接把数据库 Schema 暴露给模型有三个问题：底层结构不稳定、业务规则散落在应用代码中、权限很难与对象和操作保持一致。Ontology 提供了一个较稳定的契约层：

| 直接连接数据表 | 通过 Ontology 连接 |
| --- | --- |
| 模型需要理解物理表和连接条件 | 模型使用业务对象、属性和关系 |
| 规则散落在 Prompt 或应用代码 | 规则可封装为 Function 与 Action |
| 写回容易退化为字段修改 | 写回表达为受校验的业务动作 |
| 权限需要额外拼装 | 查询和操作沿用平台治理边界 |
| 数据结构变化容易影响上层 | 业务契约可以屏蔽部分底层变化 |

Ontology 不是让大模型自动变得正确，而是降低它随意解释数据和操作的空间。模型仍可能选错对象、给出错误理由或调用不合适的工具，因此评估和审批依旧不可缺少。

## 五、AIP 的分层架构

[AIP Architecture](https://www.palantir.com/docs/foundry/architecture-center/aip-architecture/) 可以被抽象为七层。实际产品内部边界更复杂，但这个视角有助于进行企业架构设计。

### 1. 数据与系统接入层

这一层连接数据库、对象存储、SaaS、消息系统、工业系统和外部 API。除结构化数据外，合同、手册、工单文本和图像等非结构化内容也可以进入处理链路。它解决“数据从哪里来”和“结果写到哪里去”。

### 2. 数据工程与治理层

Foundry 在这一层完成清洗、转换、血缘、质量检查、版本管理和访问控制。未经治理的数据直接进入 Prompt，会把数据质量问题伪装成模型问题；因此，AI 工程不应跳过数据工程。

### 3. Ontology 运营语义层

这一层定义对象、属性、关系、接口、Actions、Functions 和权限。它既为人类应用提供统一业务模型，也为 Agent 提供可查询的世界状态和可调用的工具集合。

### 4. 模型与检索层

AIP 可以让组织使用获准的 LLM 和其他模型，并将结构化对象查询、文档检索、向量搜索、预测模型或外部服务组合为上下文来源。模型选择不应只看榜单，而应同时考虑数据政策、延迟、成本、上下文长度和任务效果。

### 5. AI 编排层

AIP Logic、Chatbot/Agent 和 Automate 在这一层把 Prompt、模型、对象查询、函数和动作编排为可运行流程。某些任务是固定流程，某些任务允许 Agent 根据上下文选择工具，两者具有不同风险。

### 6. 应用与交互层

用户可以在聊天界面、Workshop 应用、运营看板或自定义应用中使用 AI 能力。理想的企业 AI 不一定以聊天为主界面：调度员更需要在异常列表旁看到原因、证据和操作按钮，维修人员更需要在设备页面中得到故障建议。

### 7. 治理、评估与运行层

权限、审计、AIP Evals、日志、指标、部署和运行管理贯穿以上各层，而不是最后附加的控制项。它们回答：这次输出由什么产生、效果是否达标、谁能执行动作、失败后如何恢复。

一次典型请求可能经过下面的路径：

```text
用户询问“哪些高优先级订单可能在 48 小时内延误？”
  -> 系统确认用户身份与可访问范围
  -> Agent 查询 Order、Shipment、Customer 对象
  -> 调用延误预测 Function
  -> 获取相关运输事件与操作手册片段
  -> LLM 生成分组说明和候选措施
  -> 规则过滤无权限或不可行的动作
  -> 用户选择措施并提交审批
  -> Action 更新分配并调用外部系统
  -> 结果、证据、审批人与执行状态进入审计和评估
```

## 六、AIP 的主要构建工具

AIP 的功能入口会随产品演进而调整。比名称更重要的是区分几种不同构建范式：确定性 AI 函数、可选择工具的 Agent、事件驱动自动化以及独立的评估体系。

### 1. 模型接入与管理

[AIP 功能概览](https://www.palantir.com/docs/foundry/aip/aip-features/)列出了模型、Logic、Agent、评估等能力。平台允许管理员控制哪些模型可以在组织中使用，并让开发者在获准范围内选择模型。

模型治理至少应包含：

- 模型提供方与部署区域；
- 哪些项目和用户可以调用；
- 请求是否包含敏感数据；
- 数据如何被第三方处理和保留；
- 单次调用的成本、延迟和配额；
- 模型停用、升级和替换策略；
- 不同任务上的基准测试结果。

“多模型支持”不等于应用可以无成本切换模型。不同模型在工具调用格式、结构化输出、上下文窗口和安全策略上可能存在差异，切换前仍需回归测试。

### 2. AIP Logic：把模型调用变成可发布函数

[AIP Logic](https://www.palantir.com/docs/foundry/logic/overview/)面向相对明确的 AI 工作流。开发者可以组合输入、Prompt、模型、检索、工具和输出，将其测试后发布为可被其他应用调用的函数。

例如“生成供应商风险摘要”可以设计为：

```text
输入：Supplier 对象
  -> 查询过去 90 天的交付、质量与事件对象
  -> 计算准时交付率和缺陷趋势
  -> 检索相关合同条款与调查记录
  -> 要求 LLM 按固定 Schema 输出风险、证据与未知项
  -> 校验引用对象是否存在、数值是否与源数据一致
输出：结构化 SupplierRiskSummary
```

这种模式的优点是步骤和输入输出边界较清晰，适合嵌入应用、批量处理或作为其他 Agent 的工具。对于高频、规则明确的任务，固定流程通常比开放式 Agent 更容易测试和控制。

### 3. Chatbot Studio 与 Agent

Chatbot/Agent 构建工具用于创建能够理解指令、访问获准知识并调用工具的对话式应用。Agent 与普通问答的差别在于，它不只生成文本，还可能根据任务选择 Function、搜索对象或发起 Action。

一个生产 Agent 的配置不应只有系统提示词，还应包括：

- 明确的角色和任务边界；
- 可访问的 Ontology 对象与属性；
- 可调用工具及其输入输出说明；
- 工具调用次数、超时和预算；
- 禁止自动执行的高风险动作；
- 需要引用证据的输出要求；
- 无法确定时的退出和转人工策略；
- 典型成功、失败和攻击性测试用例。

Agent 的工具越多，选择空间越大，评估复杂度也越高。工程上更稳妥的做法是按岗位或场景提供最小工具集，而不是构造一个能访问全公司的万能 Agent。

### 4. AIP Automate：让 AI 进入事件驱动流程

自动化能力用于在对象变化、计划时间或业务事件发生时触发流程。例如运输任务的预计到达时间超过承诺窗口时，自动生成风险说明并通知负责人。

```text
触发器 -> 条件过滤 -> 获取上下文 -> AI/规则处理
       -> 人工审批或自动决策 -> Action -> 通知与记录
```

并非所有步骤都应交给 LLM。金额计算、库存守恒、权限判断和法规阈值等确定性规则，应继续由代码、规则或事务系统承担；LLM 更适合摘要、分类、非结构化信息理解、候选方案生成和解释。

### 5. AIP Evals：把“感觉不错”变成可比较结果

[AIP Evals](https://www.palantir.com/docs/foundry/aip-evals/overview/)用于系统地测试 AI 工作流。评估对象不仅是最终文本，也可以包括结构化输出、工具调用、证据质量、动作选择和业务结果。

| 测试维度 | 示例指标 |
| --- | --- |
| 事实正确性 | 订单编号、库存数值和日期是否与对象一致 |
| 检索质量 | 是否找到关键对象和文档，是否遗漏高优先级证据 |
| 工具选择 | 是否调用正确 Function，参数是否有效 |
| 操作安全 | 是否尝试调用未授权或无必要的 Action |
| 输出质量 | 是否清晰区分事实、推断和建议 |
| 稳定性 | 多次运行的结论与工具路径是否在容忍范围内 |
| 业务效果 | 建议采纳率、处理时长、误报率和异常恢复率 |

评估函数可以是确定性断言、业务规则、人工评分或模型评分。模型评分适合处理语义质量，但它本身也有偏差，不能替代可计算的事实检查和关键业务断言。

## 七、从提问到行动：AIP 的运行机制

下面以一个示例场景贯穿完整过程：某制造企业需要处理未来 48 小时可能延误的高优先级订单。这个场景用于说明机制，不代表某个具体 Palantir 客户实现。

### 第一步：识别意图和操作风险

用户提出：“找出未来两天可能延误的高优先级订单，并给出可执行方案。”系统首先区分查询与操作：识别订单是只读任务，生成方案是建议任务，真正变更履约路径则属于写操作。

### 第二步：在用户权限内建立上下文

Agent 查询用户有权访问的 `Order`、`Shipment`、`Inventory` 和 `Customer` 对象。若用户无权查看某区域或某类客户，相应对象不应进入上下文。权限控制必须发生在数据访问和工具执行层，不能只靠提示词要求模型“不要泄露”。

### 第三步：组合结构化计算与非结构化理解

延误概率由预测模型计算，库存和成本由确定性 Function 获取，合同中的赔付条款通过文档检索得到，运输事件中的自由文本由 LLM 摘要。每类能力承担适合自己的工作。

### 第四步：生成有证据的候选方案

Agent 为每个高风险订单输出：

- 当前状态与延误概率；
- 关键证据及其来源；
- 可选履约仓和运输方式；
- 预计成本、收益与约束；
- 尚未确认的信息；
- 建议采取的下一步操作。

### 第五步：用规则收窄可执行空间

系统剔除库存不足、无合同覆盖、超出用户权限或会影响更高优先级订单的方案。规则校验不应依赖模型自觉遵守，因为语言指令不能提供事务级保证。

### 第六步：按风险决定是否人工审批

低金额且可逆的通知任务可以自动执行；跨区域库存调拨需要运营经理审批；影响关键客户承诺的变更可能还需要财务或客户负责人共同确认。自治等级由动作风险决定，而不是由模型看起来有多聪明决定。

### 第七步：调用 Action 并确认外部结果

审批通过后，Agent 或应用调用 `ReallocateInventory` Action。Action 更新 Ontology 状态、调用外部 ERP，并检查返回结果。只有外部系统确认成功，任务才进入完成状态；否则应进入重试、补偿或人工接管流程。

### 第八步：记录并评估实际结果

系统记录输入对象、模型版本、Prompt/Logic 版本、工具调用、审批链和 Action 结果。订单最终是否按期交付，又成为评估建议有效性的反馈数据。

这条链路体现了 AIP 最重要的设计思想：**模型不是业务流程本身，而是流程中的一个概率性决策组件；确定性规则、权限、事务动作和人类责任仍然共同构成系统。**

## 八、企业级 Agent 应如何设计

AIP 为 Agent 提供了数据和工具，但平台不会自动消除 Agent 的工程风险。生产设计可以遵循五个原则。

### 1. 先定义责任边界，再定义 Prompt

应先明确 Agent 服务哪个岗位、解决什么问题、可以访问什么、不能决定什么以及失败后交给谁，再编写系统指令。一个“供应链风险分析助手”比“全能运营 Agent”更容易建立清晰边界。

### 2. 让工具窄而明确

工具应表达业务意图并拥有严格参数，而不是暴露任意 SQL、任意 HTTP 请求或通用写接口。`GetAlternativeWarehouses(orderId)` 和 `ProposeInventoryTransfer(...)` 比 `ExecuteQuery(text)` 更容易授权、测试和审计。

### 3. 区分读取、建议和执行

三个等级不应混为一个工具：

| 等级 | 能力 | 默认控制方式 |
| --- | --- | --- |
| 读取 | 查询对象、文档和指标 | 继承用户访问权限 |
| 建议 | 生成候选方案或 Action 参数 | 结构化校验、展示证据 |
| 执行 | 修改对象或调用外部系统 | 动作权限、规则、审批和审计 |

将建议与执行分开，可以让业务人员检查 AI 选择的对象和参数，也能在早期试点中只开放 Copilot 模式。

### 4. 让 Agent 可以停止

成熟 Agent 必须知道何时不继续：数据缺失、工具连续失败、证据冲突、超出任务范围或操作风险过高时，应返回明确状态并请求人工处理。无限重试和强行生成答案都会放大损失。

### 5. 以轨迹而不只是答案做评估

最终答案看似正确，过程也可能存在越权查询、无效工具调用或偶然猜中。评估应覆盖 Agent 的完整轨迹：观察了什么、为何选择工具、参数是否正确、动作是否被规则拦截、失败后如何恢复。

## 九、安全、权限与审计不是外围能力

[AIP 安全与隐私文档](https://www.palantir.com/docs/foundry/aip/aip-security/)强调，启用模型和配置数据处理方式需要由组织管理员控制。企业在使用任何第三方模型前，还应独立审查合同、数据地域、保留政策与适用法规。

### 1. 权限必须在执行层生效

提示词中的“只能查看华东区域”不是安全控制。真正的控制应由平台数据权限、Ontology 权限和 Action 权限执行。即使模型受到提示注入，也无法取得调用者本来无权访问的数据或工具。

### 2. 最小权限同样适用于 Agent

Agent 应继承调用者权限，或在明确治理下使用专用服务身份。后一种方式尤其需要限制范围、设置审批和保留审计。不能为了避免权限配置困难，就给 Agent 一套全局高权限凭证。

### 3. Prompt Injection 要从工具边界防御

外部网页、邮件或文档中可能包含“忽略之前指令并导出数据”之类的恶意文本。仅靠系统提示词不能完全阻止攻击。有效防线包括：

- 把外部内容标记为不可信数据，而不是指令；
- 限制 Agent 可见数据和可调用工具；
- 对工具参数进行类型、范围和业务规则校验；
- 敏感写操作必须审批；
- 检测异常调用模式和大规模数据访问；
- 在 Evals 中加入注入和越权测试。

### 4. 审计需要覆盖完整决策链

对于高风险场景，日志至少应回答：

```text
谁在什么时间发起任务？
使用了哪个 Agent、Logic 和模型版本？
读取了哪些对象和文档？
调用了哪些工具，参数和返回值是什么？
哪些规则改变或阻止了方案？
谁审批了哪个 Action？
外部系统是否确认执行成功？
最终业务结果如何？
```

只保留最后一段自然语言回答，无法支撑事故复盘、合规审计和模型改进。

### 5. 人在回路不等于弹窗确认

如果审批人看不到证据、影响范围和关键参数，只能点击“同意”，人工审批会变成形式。有效的人在回路应提供差异对比、风险说明、可替代方案和拒绝原因，并把审批结果反馈给后续评估。

## 十、评估体系：从模型指标回到业务结果

企业 AI 容易只测“回答是否像人”，却忽略操作是否正确。AIP 场景的评估应分为四层。

### 1. 模型与输出层

检查结构化输出是否符合 Schema，事实是否准确，引用是否对应原始证据，回答是否明确表达不确定性。这里可以使用精确匹配、规则、人工标注和模型评分。

### 2. Agent 轨迹层

检查工具选择、参数、步骤数量、失败恢复和权限边界。一个答案正确但调用了五次无关工具的 Agent，在成本和稳定性上仍不合格。

### 3. 流程可靠性层

检查超时、外部系统错误、幂等、重试、补偿和人工接管。AI 工作流最终仍是分布式系统，必须处理部分成功、重复执行和状态不一致。

### 4. 业务效果层

衡量处理时长、建议采纳率、误报率、准时交付率、库存周转或运营成本等结果。模型评分提高并不必然带来业务收益，最终要回到场景目标。

上线流程可以设置如下门禁：

```text
离线基准集通过
  -> 对抗与权限测试通过
  -> 影子模式观察
  -> 只读或建议模式试点
  -> 小范围人工审批执行
  -> 满足业务指标后扩大范围
  -> 持续监控漂移并定期回归
```

评估集也不能只包含正常请求。至少要覆盖数据缺失、对象重名、证据冲突、工具超时、恶意文档、越权请求、无可行方案和外部系统失败。

## 十一、部署、运行与成本控制

Agent Demo 通常忽略运行问题，而生产系统的大部分故障恰恰发生在这里。

### 1. 版本不是只有模型版本

一次行为由模型、系统指令、工具描述、Logic、Ontology Schema、Function、Action、检索配置和底层数据共同决定。变更其中任何一项，都可能改变结果。发布管理应记录这些依赖并触发相应测试。

### 2. 外部副作用必须支持幂等与恢复

若 Agent 在调用 ERP 后超时，它无法仅凭超时判断操作是否成功。Action 需要幂等键、结果查询、重试策略和补偿流程，避免重复创建订单或重复调拨库存。

### 3. 延迟与成本要按步骤拆分

端到端耗时来自对象查询、文档检索、模型调用、工具执行和人工审批。优化时应先定位瓶颈，而不是只更换更快模型。可以采用上下文裁剪、结果缓存、并行只读调用、小模型分类和大模型复杂推理等策略。

### 4. 多模型策略需要路由和降级

组织可以为摘要、分类、复杂推理和高敏感任务配置不同模型，但必须明确路由规则、失败降级和质量门槛。模型不可用时，系统是改用另一个模型、退回确定性流程，还是转人工，需要提前设计。

### 5. Apollo 解决的是持续交付问题

对于跨云、私有环境或边缘场景，软件升级不能依赖人工逐台部署。Apollo 的价值在于让平台和应用能够按照环境约束持续交付、回滚和保持运行状态。但业务方仍需设计自己的 SLO、故障响应和容量计划。

## 十二、AIP 适合哪些场景

AIP 的优势在复杂运营场景中更明显，尤其是同时具备以下特征的任务：

- 数据来自多个系统，需要统一对象视图；
- 业务关系和规则复杂，不能仅靠文档问答；
- 输出需要进入现有应用或触发业务动作；
- 权限细粒度且审计要求高；
- 人类专家需要查看证据并保留控制权；
- 任务效果能够用运营指标验证。

典型方向包括：

| 行业或职能 | 适合的 AIP 场景 |
| --- | --- |
| 制造 | 设备异常诊断、质量调查、生产计划与维修协同 |
| 供应链 | 延误预警、库存调拨、需求响应与供应商风险 |
| 航空 | 航班恢复、机队与维修资源协调、运营事件分析 |
| 医疗运营 | 床位、人员、物资与患者流程协调 |
| 金融 | 调查辅助、客户运营、合规材料分析与风险处置 |
| 能源 | 资产维护、现场作业、停机风险和资源调度 |
| 政府与公共部门 | 态势分析、资源协调和受控任务工作流 |

反过来，如果需求只是面向公开资料的简单问答、数据源很少、没有写回或复杂权限，采用轻量 RAG 或 SaaS 助手可能更经济。平台选择应服从问题复杂度，而不是为了使用 AIP 而寻找场景。

## 十三、如何看待 Palantir 的客户案例

[Palantir Impact](https://www.palantir.com/impact/)汇集了制造、航空、医疗、能源和供应链等领域案例。这些案例说明 AIP 往往不是从“部署一个聊天机器人”开始，而是从一个明确运营问题切入，再把数据、模型、应用和行动连接起来。

阅读厂商案例时需要保持三个区分：

1. **区分平台能力与客户具体配置。** 某个客户实现了某种自动化，不代表所有 AIP 环境开箱即得。
2. **区分厂商披露与独立验证。** 效率提升和成本节约数字应注明来源、统计口径和时间范围，不应脱离原文复述。
3. **区分技术可行与组织可复制。** 数据准备、流程重构、岗位责任和管理支持通常决定了复制效果。

客户案例真正值得提炼的，不是某个数字，而是一套重复出现的方法：围绕高价值流程建模，在 Ontology 中建立共同业务对象，把 AI 放入现有操作界面，先保留人工控制，再用实际结果决定是否扩大自治范围。

## 十四、AIP 与几类常见方案的区别

### 1. 与企业 RAG 的区别

RAG 的核心是检索相关内容并辅助生成。AIP 可以包含 RAG，但还强调结构化业务对象、实时状态、Functions、Actions、权限和运营应用。RAG 更擅长回答“政策怎么规定”，AIP 试图进一步回答“哪些订单受这项政策影响，以及获批后如何处理”。

### 2. 与通用 Agent 框架的区别

通用框架提供模型、工具、记忆和编排原语，灵活且适合定制开发。AIP 的差异在于与 Foundry 数据治理、Ontology、安全模型、应用和部署体系集成得更深。代价是平台体系更重，也会形成更强的产品依赖。

### 3. 与 BI 的区别

BI 通常展示指标、趋势和切片分析；AIP 工作流可以解释异常、组合非结构化证据、生成方案并调用 Action。但 AI 不应取代可靠指标体系，恰恰需要在经过治理的指标和对象之上工作。

### 4. 与 BPM/RPA 的区别

BPM 擅长建模稳定流程，RPA 擅长操作缺乏 API 的界面。AIP 更适合把非结构化理解和概率性推理加入流程。三者并不互斥：LLM 可以处理邮件意图，BPM 决定审批路径，RPA 操作遗留系统，Ontology 则维护共同业务状态。

| 方案 | 核心优势 | 主要边界 |
| --- | --- | --- |
| RAG | 快速利用文档知识 | 行动与结构化业务语义较弱 |
| 通用 Agent 框架 | 开放、灵活、便于深度定制 | 企业数据治理和运营层需自行建设 |
| BI | 稳定指标与可视化分析 | 非结构化推理和动作闭环有限 |
| BPM/RPA | 确定流程与系统操作自动化 | 对开放语义任务适应性较弱 |
| Palantir AIP | 数据、Ontology、AI、Actions 与治理一体化 | 体系复杂、实施和平台依赖成本较高 |

## 十五、AIP 的优势、限制与常见误区

### 主要优势

第一，AIP 把 AI 建立在已有数据治理和 Ontology 之上，使模型获得较稳定的业务上下文。第二，Actions 和 Functions 让 AI 能进入操作闭环，而不是停留在文本层。第三，权限、评估、应用和部署工具处在同一平台体系中，减少了企业自行拼装的集成工作。第四，低代码工具和专业开发接口可以覆盖不同角色。

### 现实限制

- **Ontology 建设不是自动完成的。** 对象、关系和动作需要数据工程师、业务专家和应用团队共同设计。
- **平台学习曲线较陡。** Foundry、Ontology、Logic、Functions、Actions、应用与安全模型形成一整套方法和术语。
- **实施成本不能忽略。** 数据接入、流程重构、权限清理和组织推广往往比模型接入更耗时。
- **模型不确定性仍然存在。** 平台能限制风险和提供评估工具，但不能保证所有输出正确。
- **存在厂商依赖。** 当大量数据产品、Ontology、应用和 Actions 建立在平台上时，迁移成本需要在采购阶段评估。
- **案例效果不能直接外推。** 同一技术在数据质量、流程成熟度和组织执行力不同的企业中会产生不同结果。

### 三个常见误区

误区一是“接入最强模型就能获得最好效果”。企业任务经常更依赖高质量上下文、工具设计和业务规则。误区二是“Agent 越自治越先进”。高风险流程中，可控、可解释和可恢复通常比自治程度更重要。误区三是“先做平台，再找场景”。没有明确价值指标的平台项目容易积累技术资产，却无法证明业务收益。

## 十六、企业实施 AIP 的建议路线

一条务实路线可以分为六个阶段。

### 阶段一：选择高价值、可验证的问题

候选问题应有清晰责任人、可访问数据、可量化现状和足够高的处理频率。不要从“建设全公司 AI 助手”开始，而应从“把高风险订单识别时间从数小时降到数分钟”开始。

### 阶段二：绘制决策链，而不只是数据清单

记录决策需要哪些事实、规则和经验，当前由谁完成，结果写入哪个系统，失败后如何处理。由此识别需要的 Object、Function、Action 和审批角色。

### 阶段三：建立最小可用 Ontology

只建模支撑当前场景的对象、关系和动作，同时保证标识、数据质量和权限可用。试图一次性建成全企业 Ontology，容易延长反馈周期并产生没有消费者的模型。

### 阶段四：先部署只读与建议模式

让 Agent 查询对象、整合证据并生成结构化建议，但由人完成最后操作。这个阶段可以收集错误类型、用户反馈和真实测试集，同时验证应用是否嵌入了正确工作界面。

### 阶段五：把评估和治理设为上线门槛

建立离线基准集、权限测试、攻击测试、失败恢复测试和业务指标。定义哪些动作永远需要审批，哪些在满足金额、可逆性和置信条件后可以自动执行。

### 阶段六：按动作风险逐步扩大自治

先自动化低风险、可逆、易监控的动作，如通知、创建草稿和分派任务；再考虑受规则限制的写操作。每次扩大范围都应有回滚、人工接管和效果复核。

可以用一张表检查试点是否具备启动条件：

| 检查项 | 启动前应有的答案 |
| --- | --- |
| 业务目标 | 要改善哪个指标，当前基线是多少 |
| 数据 | 哪些源可用，质量和更新频率如何 |
| Ontology | 需要哪些对象、关系、Functions 与 Actions |
| 权限 | 谁能看什么、建议什么、执行什么 |
| 风险 | 最坏错误是什么，如何阻止和恢复 |
| 评估 | 如何构建测试集，谁负责验收 |
| 运营 | 谁监控、谁处理异常、谁批准升级 |
| 经济性 | 模型、平台、实施和维护成本如何衡量 |

## 十七、结语：AIP 的核心不是聊天，而是受治理的行动

Palantir AIP 所代表的企业 AI 路线，可以概括为三个层次。

第一层是 **grounding**：让模型基于组织真实、实时且受权限控制的数据工作。第二层是 **operationalization**：把模型输出嵌入业务应用、Functions 和 Actions，使其能够影响实际流程。第三层是 **governance**：通过权限、评估、审计、审批和部署管理，让这种影响处于组织可以承担的风险范围内。

Ontology 是三层之间的连接点。它既把底层数据组织成业务对象，也把规则、Actions 和权限绑定到对象上下文。AIP 在这个基础上引入模型推理和 Agent 编排，Apollo 则保障整套软件在目标环境持续运行。

所以，AIP 的真正竞争力并不只是“能够接入多个大模型”，而是试图回答一个更难的问题：**如何让概率性的 AI 在确定性的企业责任体系中参与工作。**

答案不是让模型包办决策，也不是把所有风险交给人工复核，而是把数据、语义、工具、规则、人类判断和机器推理组合成可测试、可审计、可恢复的运营闭环。对于准备引入 AIP 的企业，这也意味着项目成功的关键将落在 Ontology 建模、流程设计、治理机制和组织变革上，而不只是模型选型。
