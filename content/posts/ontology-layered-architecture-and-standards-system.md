一家大型企业往往同时拥有 ERP、MES、PLM、QMS、WMS、设备管理平台、数据仓库和知识图谱。每个系统都保存了大量数据，也都建立了自己的对象、字段、代码和分类体系。

问题并不在于系统没有模型，而在于**每个系统都在用自己的方式描述同一个世界**。

在设备系统中，“设备”可能是一条资产台账；在生产系统中，它可能是一项产能资源；在维修系统中，它是工单的维修对象；在质量系统中，它又是缺陷产生的环境条件。几个系统都使用“设备”这个词，但它们指向的对象范围、身份标识、生命周期和关系并不完全相同。

如果没有统一的语义架构，企业通常会反复遇到以下问题：

- 同名概念含义不同，不同名称却指向同一概念；
- 项目各自建设知识图谱，概念和关系无法复用；
- 数据标准只能规定字段格式，无法解释业务含义；
- 系统集成依赖点对点映射，接口数量持续膨胀；
- 模型只在专家文档中成立，进入应用后无法验证和执行；
- 本体变更缺少影响分析，导致查询、规则和应用悄然失效；
- 大模型能够生成自然语言答案，却缺乏稳定、可追踪的业务语义基础。

因此，企业本体建设不能从“建一份本体文件”开始，而应先回答一个更基础的问题：**企业需要怎样的本体架构，才能让语义在不同领域、系统和应用之间稳定传递？**

本文提出一套“**三层主架构、公共核心衔接、横向标准治理**”的整体方案：

```text
应用本体层：面向具体系统、流程、决策和智能应用
      ↑ 复用、裁剪、约束、映射、反馈
领域本体层：面向稳定业务领域形成共享参考语义
      ↑ 继承、对齐、专门化、公共概念提取
顶层本体层：定义跨领域通用范畴和基础关系
------------------------------------------------
横向能力：术语、标识、元数据、版本、质量、溯源、安全与治理
```

这套架构的目的不是追求一份包罗万象的“终极本体”，而是建立一套可分工、可复用、可验证、可演进的企业语义生产体系。

## 一、先明确建设目标：本体架构要解决什么问题

本体架构的价值不在于概念数量，也不在于模型图是否复杂，而在于它是否降低了跨系统、跨领域和跨应用理解业务的成本。

一个可落地的企业本体体系至少应实现六个目标。

### 1. 建立统一的语义坐标系

不同领域可以保留自己的专业概念，但这些概念必须能够回答：它属于什么基本范畴，与其他领域中的概念是什么关系，能否通过统一标识被引用。

例如，“维修任务”“生产任务”和“检验任务”具有不同业务含义，但都可以对齐到更一般的“计划活动”；“设备”“物料”和“工装”虽然用途不同，但都可能属于具有稳定身份的物理对象。

顶层本体提供的正是这种语义坐标系。

### 2. 形成稳定的领域参考模型

企业不能要求每个应用都直接理解高度抽象的顶层概念。业务真正需要复用的，通常是设备、工单、产品、订单、供应商、缺陷、测量、文档等领域概念。

领域本体负责把顶层范畴转化为专家能够评审、项目能够复用的业务语义骨架。

### 3. 控制应用差异

应用必然存在差异。相同的设备概念，在预测性维护、备件优化、能耗分析和质量追溯中会有不同的属性、约束和查询需求。

架构不应消灭这些差异，而应把差异限制在应用层，避免应用细节反向污染共享领域模型。

### 4. 建立语义互操作机制

传统系统集成经常采用点对点映射。系统数量为 `n` 时，潜在映射关系可能接近 `n × (n - 1) / 2`。本体不能自动消除所有映射工作，但可以提供共享语义中介，让系统优先映射到稳定概念，再通过概念关系实现复用。

### 5. 支撑知识服务与智能应用

一套本体只有被查询、校验、推理和应用调用，才真正进入运行状态。整体架构必须同时考虑：

- 知识图谱如何实例化；
- 数据进入图谱前如何校验；
- 规则和推理如何使用语义；
- 搜索、问答和推荐如何引用概念；
- Agent 如何理解对象、关系、约束和动作；
- 模型版本变化后，上层应用如何保持兼容。

### 6. 让本体成为可治理的企业资产

本体不是一次性交付物。它会随着业务、法规、系统和组织变化持续演进，因此必须拥有责任人、版本、状态、评审记录、发布记录、依赖关系和废弃策略。

> 架构的核心任务，是把“不同团队怎样描述业务”从项目习惯变成企业可治理的公共能力。

## 二、统一基本概念：三层分别是什么

在开始分层前，需要先区分本体、术语表、分类体系、数据模型和知识图谱。

| 产物 | 主要回答的问题 | 典型表达 |
| --- | --- | --- |
| 术语表 | 一个词是什么意思，有哪些同义词 | 术语、定义、别名、来源 |
| 分类体系 | 一个概念属于哪一类 | 上位、下位、相关概念 |
| 数据模型 | 数据如何存储和关联 | 表、字段、主键、外键、类型 |
| 本体 | 世界中有哪些概念，它们之间有什么可计算的语义关系 | 类、属性、关系、公理、约束 |
| 知识图谱 | 现实对象和事实如何按照本体组织 | 实例、事实、来源、时间、证据 |

这些资产相互关联，但不能互相替代。把数据库表直接转换成 RDF，并不意味着已经建立了本体；画出一棵分类树，也不代表已经表达了角色、事件、时间、约束和业务规则。

### 1. 顶层本体

顶层本体描述跨领域稳定、与具体业务无关的基本范畴，例如：

- 物理对象与信息对象；
- 持续存在的实体与发生在时间中的过程；
- 主体、组织、角色和能力；
- 时间、空间、状态和生命周期；
- 质量、度量、数量值和单位；
- 计划、活动、目标和结果；
- 标识、分类、记录和证据。

[ISO/IEC 21838-1](https://www.iso.org/standard/71954.html) 将顶层本体定义为领域中立的高层本体，并强调它对下层领域本体的数据交换、检索、发现、集成和分析能力的支撑作用。

### 2. 领域本体

领域本体描述某个稳定业务领域中的共享概念和关系。例如：

- 设备领域：设备、部件、功能、测点、故障、维修活动；
- 制造领域：产品、工艺、工序、生产任务、资源、批次；
- 质量领域：检验计划、检验特性、测量结果、缺陷、不合格项；
- 供应链领域：供应商、采购订单、交付、库存、物流事件。

领域本体不应依附于某个具体页面或数据库。它的目标是成为多个应用共同引用的参考语义。

### 3. 应用本体

应用本体面向明确场景，对领域本体进行选择、组合、扩展和约束。例如：

- 离心泵预测性维护本体；
- 产品批次质量追溯本体；
- 高风险供应商识别本体；
- 基于设备状态的智能工单推荐本体。

应用本体可以包含系统字段映射、场景特有状态、完整性约束、规则和查询视图，但不应重新定义领域层已经存在的稳定概念。

### 4. 公共核心本体

实践中，顶层和领域层之间往往还需要一组“比顶层具体、比单一领域通用”的公共概念，例如组织、人员、位置、时间、单位、文档、标识和活动。

[Industrial Ontologies Foundry](https://industrialontologies.org/) 的体系中包含顶层本体、核心本体、领域参考本体和应用本体。为了保持三层管理结构，可以把公共核心本体作为顶层体系中的独立模块管理，而不是再增加一个行政层级。

这样既保留三层架构的清晰度，也避免每个领域重复建设时间、空间、组织和标识模型。

## 三、总体架构：三层主干与五类横向能力

完整的本体体系不能只有纵向分层，还需要横向工程能力。

```text
┌─────────────────────────────────────────────┐
│ 应用本体：场景概念、数据映射、约束、规则、查询、动作 │
├─────────────────────────────────────────────┤
│ 领域本体：领域对象、事件、过程、角色、状态、规则     │
├─────────────────────────────────────────────┤
│ 顶层本体：基础范畴、基础关系、公共核心模块           │
└─────────────────────────────────────────────┘
     │          │          │          │          │
   术语标识     元数据      质量验证     版本发布     治理安全
```

### 1. 三层职责矩阵

| 维度 | 顶层本体 | 领域本体 | 应用本体 |
| --- | --- | --- | --- |
| 复用范围 | 全企业、跨行业 | 某业务领域内 | 某系统或场景 |
| 语义稳定性 | 很高 | 较高 | 随应用迭代 |
| 抽象程度 | 高 | 中 | 低 |
| 主要维护者 | 企业架构与语义委员会 | 领域专家与数据架构师 | 产品、项目与应用团队 |
| 主要输入 | 国际标准、企业架构原则 | 业务规范、领域标准、专家知识 | 用户故事、数据源、接口、查询和规则 |
| 主要输出 | 基础类、关系与公理 | 领域参考模型与术语 | 可运行模型、约束、映射和应用接口 |
| 变更频率 | 低 | 中 | 高 |
| 验收重点 | 一致性、通用性、边界清晰 | 业务完整性、复用性 | 场景覆盖、数据可用性、运行效果 |

### 2. 五类横向能力

**术语与标识。** 为每个概念建立永久 IRI、首选名称、别名、定义、来源和责任人，防止“名称相同就认为概念相同”。

**元数据与目录。** 记录本体模块、依赖、版本、许可、成熟度、适用范围和发布地址，使本体能够被发现和复用。

**质量与验证。** 同时验证语法、逻辑一致性、业务完整性、数据约束和能力问题。

**版本与发布。** 区分草稿、候选、正式、废弃等状态，明确兼容性规则和迁移方式。

**治理与安全。** 明确概念所有者、审批流程、访问权限、审计和知识产权要求。

### 3. 分层设计原则

整个体系应遵循以下原则：

1. **稳定性向上集中。** 越稳定、越通用的概念越靠上。
2. **变化向下隔离。** 页面字段、算法输出和系统状态优先留在应用层。
3. **概念只定义一次。** 下层引用和专门化上层概念，不复制定义。
4. **依赖方向单一。** 应用层可以依赖领域层，领域层可以依赖顶层，反向依赖必须通过治理变更处理。
5. **模块小而内聚。** 按语义职责拆分模块，避免所有概念放入一个文件。
6. **形式化程度服从用途。** 需要推理的语义用 OWL 表达，需要数据完整性校验的规则用 SHACL 表达。
7. **每个模型都能被验证。** 本体必须绑定能力问题、示例实例、查询或约束测试。

## 四、顶层本体设计：建立企业共同的世界观

顶层本体是整个体系中变更最谨慎的一层。它不直接追求业务覆盖率，而是提供一致的分类原则和基础关系。

### 1. 顶层本体应回答的问题

顶层本体首先要帮助团队回答这些容易混淆的问题：

- 一个概念代表现实对象、发生过程，还是关于对象的信息记录；
- 角色是对象固有类型，还是对象在特定上下文中承担的身份；
- 状态是对象、属性值、时间切片，还是一次状态变更事件；
- 计划、任务和实际执行过程是否属于同一类事物；
- 测量值、被测质量、单位和测量活动如何区分；
- 文档、文档版本和文档所描述的现实对象是否应使用同一标识；
- “不存在”和“当前数据未知”如何区分。

这些问题一旦在顶层没有明确原则，就会在每个领域重复争论。

### 2. 建议的顶层模块

| 模块 | 核心内容 | 典型问题 |
| --- | --- | --- |
| 实体模块 | 对象、集合、系统、信息对象 | 什么具有独立身份 |
| 过程模块 | 活动、事件、变化、参与关系 | 什么在时间中发生 |
| 主体模块 | 人、组织、系统主体、责任 | 谁发起、执行或负责 |
| 角色能力模块 | 角色、职能、能力、权限 | 对象在上下文中做什么 |
| 时空模块 | 时刻、时间区间、位置、区域 | 何时何地发生 |
| 状态模块 | 状态、阶段、生命周期、转换 | 对象如何演化 |
| 质量度量模块 | 质量、量、数值、单位、测量 | 如何描述和测量特征 |
| 计划目标模块 | 计划、目标、任务、结果 | 预期与实际如何区分 |
| 标识分类模块 | 标识符、名称、代码、类别 | 如何识别和归类对象 |
| 溯源证据模块 | 断言、来源、记录、证据 | 为什么相信一个事实 |

### 3. 顶层关系必须少而稳定

顶层关系不宜追求数量，而应优先稳定表达：

- `is-a`：类型之间的继承；
- `instance-of`：实例与类型的关系；
- `part-of`：整体与组成部分；
- `participates-in`：对象参与过程；
- `has-role`：对象在上下文中承担角色；
- `located-in`：对象或事件所在位置；
- `occurs-during`：过程发生的时间区间；
- `has-quality`：对象具有可描述或可测量质量；
- `realizes`：活动实现计划、能力或功能；
- `about`：信息对象描述现实对象或事件；
- `derived-from`：信息或结论来源于其他信息和过程。

关系名称只是展示层，真正重要的是其定义域、值域、对称性、传递性、函数性及使用约束。

例如，`part-of` 是否允许传递，会直接影响查询结果；“部件属于设备”和“工位属于车间”虽然都可称为组成关系，但生命周期依赖和空间包含的语义可能不同，不应仅凭中文名称合并。

### 4. 顶层本体不应该包含什么

以下内容通常不应进入顶层：

- 某个系统专用的字段和状态码；
- 某个产品线特有的设备分类；
- 只被单个应用使用的算法标签；
- 频繁变化的组织岗位名称；
- 尚未在多个领域证明可复用的概念；
- 为解决一次接口对接而产生的临时映射类。

判断标准不是“这个概念听起来是否重要”，而是“它是否跨领域稳定，并且能够成为多个领域共同依赖的分类基础”。

### 5. 采用外部顶层本体还是自建

企业通常有四种选择：

| 方案 | 优点 | 风险 | 适用情况 |
| --- | --- | --- | --- |
| 完整采用 | 标准基础清晰，外部互操作性好 | 学习成本高，可能与企业语言距离较远 | 行业已有成熟共识 |
| 裁剪采用 | 保留核心思想，降低使用门槛 | 裁剪后兼容性需要重新评估 | 大多数企业级项目 |
| 映射对齐 | 内部保持自己的模型，同时声明映射 | 映射维护成本较高 | 已有稳定企业模型 |
| 完全自建 | 最贴合内部表达 | 容易重复发明概念，外部互操作性弱 | 特殊领域且缺乏可用标准 |

更稳妥的路线通常是：先评估 BFO、DOLCE、TUpper 等体系，选择分类原则和可复用模块，再形成企业顶层模型，并保留与外部标准的映射。不要为了“标准化”而无条件复制，也不要以“业务特殊”为理由拒绝所有外部对齐。

## 五、领域本体设计：建立可复用的业务主干

领域本体是三层架构的核心。顶层本体提供一致性，应用本体产生业务价值，而领域本体负责把二者连接起来。

### 1. 领域不是组织部门，也不是系统边界

领域划分应围绕稳定的业务知识和业务闭环，而不是简单沿用组织架构或系统菜单。

例如，“设备管理”可能横跨资产台账、运行监测、维修、备件、质量和安全多个部门；“供应商”也会同时出现在采购、质量、财务和风险系统中。如果直接按部门建设本体，同一个现实对象仍然会被重复定义。

判断一个领域边界，可以检查：

- 是否拥有一组稳定的核心对象；
- 是否拥有相对完整的业务生命周期；
- 是否由一组专家共同维护语义；
- 是否存在独立的规则、状态和评价方法；
- 是否能够被多个应用复用；
- 与其他领域的交互是否可以通过清晰契约描述。

### 2. 先建立领域地图

企业不应同时把所有领域都建完。更合理的做法是先建立领域地图：

```text
企业公共域
├── 组织与人员
├── 地理与位置
├── 时间与日历
├── 标识与编码
└── 文档与主数据

核心业务域
├── 产品与研发
├── 采购与供应商
├── 制造与生产
├── 质量管理
├── 设备与运维
├── 仓储与物流
└── 销售与服务

支撑域
├── 财务
├── 人力资源
├── 安全环保
└── 风险与合规
```

领域地图用于确定建设顺序、领域责任人和跨领域依赖，不等于最终类层次结构。

### 3. 每个领域应形成模块化参考模型

以设备运维领域为例，可以拆分为：

```text
设备资产模块：设备、部件、位置、型号、制造商
功能结构模块：功能、功能位置、系统、子系统
运行监测模块：测点、传感器、观测、时间序列、阈值
故障诊断模块：异常、故障模式、原因、影响、诊断结论
维修管理模块：维修策略、工单、任务、人员、工具、备件
状态健康模块：运行状态、健康状态、风险等级、剩余寿命
```

模块化的关键不是把文件拆小，而是确保每个模块拥有明确职责、依赖方向和发布边界。

### 4. 领域概念必须有严格定义

每个核心概念至少需要一张概念卡片：

| 字段 | 内容 |
| --- | --- |
| 永久标识 | 不随名称变化的 IRI |
| 首选名称 | 领域内推荐使用的名称 |
| 英文名称 | 对外交流或系统标识使用 |
| 定义 | 必要且充分的自然语言说明 |
| 不包括 | 明确容易混淆但不属于该概念的内容 |
| 上位概念 | 直接继承的概念 |
| 关键关系 | 与其他概念的稳定关系 |
| 示例与反例 | 帮助专家判断边界 |
| 来源 | 标准、制度、专家或系统来源 |
| 所有者 | 对定义负责的角色或组织 |
| 状态与版本 | 草稿、候选、正式、废弃 |

好的定义不能只用近义词改写。例如，“设备是企业使用的设备”没有提供分类条件。更好的定义应说明其身份、用途、生命周期和与相近概念的区别。

### 5. 跨领域概念需要明确归属

跨领域重复建设是最常见的问题。可以使用以下规则确定归属：

1. 谁负责概念的身份和生命周期，谁通常拥有主定义。
2. 其他领域通过关系引用，不复制完整定义。
3. 特定上下文中的角色可以在使用领域定义。
4. 多个领域都需要且含义稳定的概念，上移到公共核心模块。
5. 含义确实不同的同名概念，保留独立标识并显式建立映射。

例如，供应商的主体身份由供应商主数据领域维护；质量领域可以定义“受审核供应商”“高质量风险供应商”等角色或分类，但不应再创建一套独立的供应商身份。

## 六、应用本体设计：让共享语义进入具体场景

应用本体不是领域本体的简化副本，而是共享语义与运行场景之间的适配层。

### 1. 从能力问题开始

应用本体首先应列出系统必须回答的问题，也就是 competency questions。例如，离心泵预测性维护应用可能需要回答：

- 当前哪些泵处于高故障风险状态；
- 哪些异常观测支持这一判断；
- 异常发生在哪个部件和时间区间；
- 该设备历史上发生过哪些相似故障；
- 哪些维修动作对相同故障模式有效；
- 当前诊断结论由哪个模型、哪批数据生成；
- 推荐维修动作需要哪些备件、人员和停机窗口。

这些问题决定应用需要复用哪些领域模块、增加哪些场景概念、建立哪些数据映射和约束。

### 2. 应用层允许包含什么

应用本体可以包含：

- 场景专用的类和关系；
- 对领域类的子类化和组合；
- 系统字段到概念属性的映射；
- API、消息和文件中的语义映射；
- 场景需要的 SHACL 数据约束；
- 告警、评分、推荐和决策规则；
- 查询视图、展示标签和搜索同义词；
- 算法模型、输入特征和结果的溯源；
- 应用专用权限和数据可见范围。

### 3. 应用层不应该重新定义什么

以下做法会破坏分层：

- 因为字段名称不同，就重新创建一个设备类；
- 把系统状态码直接提升为企业统一状态；
- 复制领域类后修改定义，却不声明映射关系；
- 为了方便页面展示，把事件、状态和记录合并为一个类；
- 把算法当前输出标签当成永久领域分类；
- 在应用本体中修改上层概念的语义。

如果应用发现领域模型不够用，应通过变更流程提出扩展建议，而不是静默复制。

### 4. 区分 OWL 语义与 SHACL 约束

[OWL 2](https://www.w3.org/TR/owl2-overview/) 用于表达类、属性、公理和形式语义，适合描述“什么是什么”以及可以推导出的关系。[SHACL](https://www.w3.org/TR/shacl/) 用于描述 RDF 数据图应满足的形状，适合表达接口和数据质量要求。

例如：

```text
OWL 语义：每个振动观测都是一种观测活动。
OWL 语义：参与振动观测的传感器是一种测量设备。

SHACL 约束：每条振动观测必须有且只有一个时间戳。
SHACL 约束：振动速度结果必须带有允许的单位。
SHACL 约束：观测值必须是数值类型。
```

OWL 采用开放世界假设。缺少某个事实，通常表示系统尚不知道，而不是该事实一定不存在。数据接口中的必填、数量和格式要求，应主要由 SHACL、数据库约束或应用校验承担。

### 5. 应用本体必须绑定真实数据验证

一个应用本体至少应通过四类测试：

1. 使用真实样本数据完成实例化；
2. 使用 SPARQL 或应用接口回答能力问题；
3. 使用 SHACL 检出预设的不合格数据；
4. 使用推理机检查逻辑一致性和预期推导。

没有进入实例、查询和验证环节的应用本体，仍然只是设计假设。

## 七、层间契约：三层如何连接而不互相污染

分层本身不能保证架构有效。真正决定体系能否长期演进的是层间契约。

### 1. 五种基本关系

| 关系 | 含义 | 示例 |
| --- | --- | --- |
| 继承 | 下层概念是上层概念的严格子类 | 离心泵 `is-a` 旋转设备 |
| 引用 | 下层直接使用上层概念 | 维修工单引用设备和人员 |
| 组合 | 应用选择多个领域模块形成场景模型 | 预测维护组合设备、观测、故障和维修模块 |
| 映射 | 两个独立模型声明语义对应 | 外部标准设备类与企业设备类对齐 |
| 约束 | 下层缩小上层允许的取值或结构 | 应用要求每次观测必须有单位 |

继承意味着严格的语义包含，不能因为两个类名称相近就建立 `subClassOf`。如果关系只是“大致相似”或“数据可转换”，应使用映射关系并说明置信度和转换条件。

### 2. 公共概念上移规则

应用概念满足以下条件时，可以申请上移到领域层：

- 被两个及以上独立应用使用；
- 定义在不同场景中保持一致；
- 不依赖特定系统字段或算法版本；
- 拥有明确领域责任人；
- 已通过真实数据和能力问题验证。

领域概念满足跨领域复用条件时，可以进一步进入公共核心模块，但需要更严格的兼容性审查。

### 3. 上层概念变更规则

顶层或领域层发生变更时，必须执行依赖分析：

- 哪些本体模块导入该概念；
- 哪些类、关系或 shape 引用了它；
- 哪些 SPARQL 查询依赖旧结构；
- 哪些接口和数据映射会受影响；
- 是否产生逻辑不一致；
- 是否需要数据迁移或兼容映射。

上层概念删除通常不应立即发生。更安全的流程是标记废弃、提供替代概念、保留兼容期、发布迁移说明，最后在主版本升级时移除。

### 4. 禁止循环依赖

建议建立明确依赖方向：

```text
外部标准 → 顶层/公共核心 → 领域参考 → 应用本体 → 实例数据
```

应用需求可以通过治理流程反馈到上层，但不应在技术导入关系中形成领域本体依赖应用本体的循环。

## 八、标准体系：把本体建设从经验变成规范

标准体系不应只是国际标准清单，而应同时覆盖外部技术标准和企业内部工程规范。

### 1. 外部标准技术栈

| 标准或规范 | 在体系中的用途 |
| --- | --- |
| [RDF 1.1](https://www.w3.org/TR/rdf11-concepts/) | 图数据模型、IRI 和三元组基础 |
| [RDFS 1.1](https://www.w3.org/TR/rdf-schema/) | 基础类、属性、继承和定义域值域 |
| [OWL 2](https://www.w3.org/TR/owl2-overview/) | 形式化本体、公理和逻辑推理 |
| [SKOS](https://www.w3.org/TR/skos-reference/) | 分类体系、受控词表和概念映射 |
| [SPARQL 1.1](https://www.w3.org/TR/sparql11-overview/) | RDF 查询和更新 |
| [SHACL](https://www.w3.org/TR/shacl/) | RDF 数据形状和质量约束 |
| [PROV-O](https://www.w3.org/TR/prov-o/) | 实体、活动、主体和来源溯源 |
| [DCAT 3](https://www.w3.org/TR/vocab-dcat-3/) | 本体及数据资产的目录描述 |
| [ISO/IEC 21838-1](https://www.iso.org/standard/71954.html) | 顶层本体要求和下层本体关系 |
| [ISO/IEC 19763-3](https://www.iso.org/standard/76581.html) | 本体注册、管理和演进元模型 |
| [ISO/IEC 24707](https://www.iso.org/standard/66249.html) | Common Logic 逻辑交换框架 |
| [ISO 704](https://www.iso.org/standard/79077.html) | 术语工作中的概念和定义原则 |

这些标准的职责不同。OWL 不负责替代术语治理，SKOS 不适合表达所有复杂逻辑，SHACL 也不应被误当作完整的本体语言。

### 2. 企业内部标准体系

建议形成八类企业标准。

#### 2.1 本体架构标准

规定三层职责、模块划分、依赖方向、公共核心范围、上移和下沉规则。

#### 2.2 建模标准

规定类、对象属性、数据属性、公理、角色、事件、状态、时间和度量的建模方法，并提供正例和反例。

#### 2.3 命名与标识标准

规定 IRI 结构、命名空间、前缀、英文标识、中文标签、别名、语言标签和永久标识策略。

一个可参考的结构是：

```text
https://ontology.example.com/{layer}/{domain}/{version}/{local-name}

layer      = upper | domain | application
domain     = common | asset | manufacturing | quality | ...
version    = 稳定版本标识或通过版本 IRI 单独管理
local-name = 稳定英文标识，不直接使用易变展示名称
```

永久概念 IRI 不应因中文名称变化而改变。版本 IRI 与概念 IRI 应分开管理。

#### 2.4 术语和定义标准

规定首选术语、允许术语、弃用术语、定义写法、同义词、缩写、来源和多语言标签。

#### 2.5 元数据和登记标准

规定本体名称、版本、责任人、许可、状态、依赖、适用范围、发布日期、兼容性和变更记录。

#### 2.6 映射与集成标准

规定等价、上下位、近似、可转换和不可映射关系，并要求记录映射依据、方向、置信度和转换逻辑。

#### 2.7 质量和测试标准

规定语法检查、推理检查、SHACL 校验、能力问题测试、覆盖率指标和发布门禁。

#### 2.8 版本与发布标准

规定版本号、兼容性、发布状态、废弃周期、变更日志、迁移说明和制品格式。

### 3. 标准之间的优先级

发生冲突时，可以按以下顺序决策：

1. 法律法规和强制性行业标准；
2. 企业级架构与主数据规范；
3. 领域标准和正式领域本体；
4. 应用本体和项目规范；
5. 数据源中的历史字段和临时约定。

优先级并不意味着低层内容可以被忽略。历史数据差异仍需映射和保留来源，只是不能反向改变共享语义的定义。

## 九、本体工程生命周期：从需求到持续运营

本体建设应采用可重复的工程流程，而不是依赖少数专家临场建模。

### 1. 需求与范围定义

明确业务目标、使用者、能力问题、数据来源、预期应用和不在本期范围内的内容。

输出物包括项目章程、领域边界、能力问题清单、数据源清单和利益相关方清单。

### 2. 术语采集与概念发现

从标准、制度、业务文档、数据库、接口、日志和专家访谈中采集术语。清理同义词、旧称、缩写和系统代码，区分概念、实例、属性值和记录。

### 3. 复用评估

检查企业现有本体、行业标准和外部本体。对每项候选资产评估：

- 语义是否匹配；
- 形式化程度是否合适；
- 许可是否允许复用；
- 版本是否稳定；
- 社区和维护机制是否可靠；
- 映射成本是否低于自建成本。

### 4. 概念化与模块设计

确定核心对象、过程、角色、状态和关系，划分模块与依赖，形成可供业务专家评审的概念模型。

### 5. 形式化实现

使用 RDF、RDFS、OWL、SKOS 和 SHACL 实现模型。形式化程度应服务于查询、验证和推理，不应为了展示复杂性而增加无用公理。

### 6. 实例化与验证

加载代表性数据，执行能力问题查询、SHACL 校验和推理测试。发现问题后回到概念化阶段修正，而不是只修改实例绕过模型缺陷。

### 7. 专家评审与发布

业务专家评审概念含义，数据专家评审映射，技术专家评审逻辑和性能，治理角色审核标准符合性和兼容性。

### 8. 运行监测与演进

持续跟踪本体使用量、查询失败、映射缺口、数据违规、变更申请和下游依赖。将运行反馈转化为下一版本输入。

> 本体生命周期不是“建模、交付、结束”，而是“需求、建模、验证、发布、使用、反馈、再建模”的闭环。

## 十、治理体系：谁有权定义企业语义

很多本体项目失败，并不是建模能力不足，而是没有回答“谁对定义负责、谁批准变更、谁承担兼容性后果”。

### 1. 建议的治理角色

| 角色 | 主要职责 |
| --- | --- |
| 本体治理委员会 | 批准架构原则、顶层变更和跨领域争议 |
| 首席本体架构师 | 维护总体架构、顶层模型和层间契约 |
| 领域所有者 | 对领域边界、核心概念和业务定义负责 |
| 领域专家 | 提供知识、示例、反例和规则依据 |
| 本体工程师 | 完成形式化建模、映射、推理和测试 |
| 数据架构师 | 负责数据源、主数据和模型映射 |
| 应用负责人 | 提出场景需求并验证应用本体效果 |
| 平台运维人员 | 维护仓库、流水线、目录和运行服务 |

### 2. 变更流程

标准变更流程可以设计为：

```text
提交申请
  → 语义查重
  → 影响分析
  → 专家评审
  → 技术验证
  → 治理批准
  → 候选发布
  → 兼容性观察
  → 正式发布
```

变更申请必须说明业务原因、拟修改内容、示例、受影响模块、兼容性判断和迁移方案。

### 3. 成熟度状态

建议为本体模块和概念设置统一状态：

- **实验中**：允许快速变化，不承诺兼容；
- **草稿**：已形成定义，尚未完成完整评审；
- **候选**：已通过主要测试，进入试用观察；
- **正式**：可被生产应用依赖，变更受兼容性约束；
- **已废弃**：不允许新增依赖，保留替代指引；
- **已归档**：退出运行环境，仅供历史追溯。

[OBO Foundry Principles](https://obofoundry.org/principles/fp-000-summary.html) 对开放性、公共标识、版本管理、文本定义、责任人和协作开发等提出了系统原则，可作为企业内部治理制度的参考。

### 4. 语义争议处理

语义争议不应通过“哪个部门级别更高”解决，而应回到证据：

- 双方是否描述同一个现实对象；
- 对象的身份条件和生命周期是否相同；
- 定义是否能覆盖正例并排除反例；
- 是否存在领域上下文差异；
- 能力问题是否要求区分；
- 合并或拆分会对数据和应用产生什么影响。

必要时允许保留两个概念，但必须使用不同标识，并明确二者的映射关系和适用上下文。

## 十一、质量评价：怎样判断一套本体是否合格

本体质量不能只通过“专家看起来合理”来判断，需要建立可度量的质量门禁。

### 1. 语法质量

- RDF、OWL 和 SHACL 文件能够被标准解析器加载；
- IRI、前缀和语言标签符合规范；
- 不存在未声明或错误引用的资源；
- 发布制品完整且可重复构建。

### 2. 逻辑质量

- 本体整体可满足，不存在非预期不一致；
- 类层次没有异常循环或不可满足类；
- 属性特征不会产生错误推导；
- 等价、互斥和基数公理经过测试。

### 3. 语义质量

- 每个核心概念具有清晰定义；
- 上位概念选择符合分类原则；
- 同名异义和异名同义得到处理；
- 对象、过程、角色、状态和记录没有混淆；
- 示例和反例能够帮助专家稳定判断。

### 4. 业务覆盖质量

- 核心能力问题可以被回答；
- 关键业务对象和生命周期得到覆盖；
- 领域专家确认模型没有重要缺口；
- 跨领域关系能够支持主要业务闭环。

### 5. 数据质量

- 关键数据能够映射到模型；
- SHACL 约束能发现缺失、格式和引用错误；
- 单位、时间、标识和来源完整；
- 冲突事实能够追踪到来源和版本。

### 6. 工程质量

- 模块依赖无循环；
- 版本和变更日志完整；
- 自动化测试能够在流水线执行；
- 发布制品、文档和示例同步；
- 下游应用可以获得迁移说明。

### 7. 建议指标

| 指标 | 计算或检查方式 |
| --- | --- |
| 定义完整率 | 有正式定义的核心概念数 / 核心概念总数 |
| 能力问题通过率 | 可正确回答的问题数 / 能力问题总数 |
| 数据映射覆盖率 | 已映射关键字段数 / 关键字段总数 |
| 约束通过率 | 通过 SHACL 的有效实例数 / 有效实例总数 |
| 复用率 | 直接复用上层概念数 / 应用使用概念总数 |
| 重复概念率 | 确认重复概念数 / 概念总数 |
| 变更可追溯率 | 有申请、评审和记录的变更数 / 总变更数 |
| 兼容性缺陷数 | 发布后发现的非预期破坏性变更数量 |

指标不能替代专家判断，但可以让质量讨论从印象转向证据。

## 十二、技术平台：本体如何成为可运行基础设施

本体平台不等于图数据库。一个完整平台应覆盖设计态、管理态和运行态。

### 1. 设计态

- 可视化和文本化本体编辑；
- 术语采集与概念卡片维护；
- 外部本体检索和导入；
- 模块依赖可视化；
- 示例实例和能力问题管理。

### 2. 管理态

- Git 或同类版本库；
- 合并请求和评审流程；
- 本体注册表和资产目录；
- 版本、状态和责任人管理；
- 差异比较和影响分析；
- 许可、安全和权限管理。

### 3. 运行态

- 三元组存储或图数据库；
- SPARQL 查询服务；
- 推理和规则服务；
- SHACL 校验服务；
- 语义映射和数据转换；
- 搜索、API、事件和 Agent 接口；
- 日志、指标和审计。

### 4. 持续集成流水线

本体代码提交后，流水线至少应执行：

```text
语法解析
  → 命名与元数据检查
  → 模块依赖检查
  → 推理一致性检查
  → SHACL 测试
  → 能力问题回归测试
  → 文档生成
  → 版本制品发布
```

本体一旦被多个应用依赖，就应像公共 API 一样管理。未经测试的概念修改与未经测试的接口修改具有相同风险。

## 十三、贯穿示例：一条“轴承温度高”事实如何穿过三层

以“P-101 离心泵驱动端轴承温度高”为例，可以看到三层分别承担什么职责。

### 1. 顶层本体解释基本范畴

- `P-101` 是具有稳定身份的物理对象；
- 驱动端轴承是该设备的组成部分；
- 温度是轴承具有的可测量质量；
- 温度测量是发生在时间中的观测活动；
- 观测结果是由测量活动生成的信息对象；
- “温度高”判断来源于观测结果、阈值和判断活动。

### 2. 领域本体提供设备运维语义

- 离心泵属于旋转设备；
- 轴承属于旋转设备部件；
- 温度传感器监测轴承测点；
- 温度观测产生带单位的数值结果；
- 高温异常可能指示润滑不足、过载或轴承退化；
- 异常可以触发诊断活动和维修工单。

### 3. 应用本体增加场景规则和数据映射

- `PUMP_MASTER.EQUIPMENT_ID` 映射为设备标识；
- `SENSOR_DATA.VALUE` 映射为观测值；
- 单位必须为摄氏度或可转换温标；
- 连续十分钟超过动态阈值才形成高温异常；
- 异常结合振动特征后计算故障风险；
- 高风险结果触发工单推荐，但需要人工确认后执行。

### 4. 为什么不能全部放在一层

如果全部放在顶层，模型会被离心泵字段和算法阈值污染；如果全部放在应用层，另一个风机诊断应用会重新定义观测、异常和工单；如果只建领域层，又无法表达具体数据库字段和运行约束。

三层架构的价值正是让**稳定语义可以复用，领域知识可以共享，应用差异可以隔离**。

## 十四、实施路线：先建立最小闭环，再逐步扩展

企业本体体系不适合采用“大规划完成后统一上线”的方式。更现实的路线是以重点场景验证架构，再逐步扩大治理范围。

### 阶段一：现状评估与标准基线

主要任务：

- 盘点术语表、数据标准、主数据、知识图谱和现有本体；
- 识别重复概念、语义冲突和高频映射问题；
- 建立领域地图和首批试点范围；
- 发布架构、命名、元数据和版本管理基线；
- 选定工具链和代码仓库。

关键交付物：现状评估报告、领域地图、标准基线、试点计划。

### 阶段二：顶层与公共核心建设

主要任务：

- 评估外部顶层本体；
- 建立实体、过程、角色、时间、空间、状态和度量模块；
- 建立组织、人员、位置、标识、文档等公共核心模块；
- 确定层间契约和导入规范；
- 使用两个以上领域进行交叉验证。

关键交付物：顶层本体、公共核心本体、建模指南、示例和测试集。

### 阶段三：重点领域本体建设

优先选择业务价值高、跨系统问题突出、专家资源可获得的领域。每个领域以能力问题和真实数据验证，形成可独立发布的模块。

关键交付物：领域参考本体、术语集、映射规范、质量报告。

### 阶段四：应用本体与示范场景

围绕一个可以量化价值的场景，完成数据映射、图谱实例化、约束校验、查询和应用集成。

试点不应只展示概念图，而应证明：

- 相同概念能够连接多个数据源；
- 能力问题能够稳定回答；
- 错误数据能够被发现；
- 模型可以被第二个应用复用；
- 变更能够通过流程和测试发布。

### 阶段五：平台化与规模推广

将试点中验证的流程固化到平台和治理制度，扩展到更多领域，并建立本体使用指标、复用指标和兼容性考核。

### 试点选择原则

首个试点最好同时满足：

- 业务痛点明确；
- 涉及两个以上系统；
- 概念和关系具有一定复杂度；
- 数据质量基本可控；
- 有稳定领域专家参与；
- 三到六个月内能够形成可验证结果；
- 成果可以复制到相邻场景。

## 十五、常见风险与控制措施

### 1. 试图一次建完整个企业本体

风险：范围失控、讨论长期停留在抽象层、无法形成应用反馈。

控制：先建立顶层最小骨架和重点领域闭环，用真实场景验证后扩展。

### 2. 顶层本体过于哲学化

风险：业务专家无法参与，项目只剩少数建模人员理解。

控制：每个顶层概念必须绑定领域示例、反例和使用指南。

### 3. 领域本体被数据库结构绑架

风险：一张表变成一个类，一个字段变成一个属性，最终只是物理模型翻译。

控制：先定义业务对象和能力问题，再建立字段映射；明确现实对象与数据记录的区别。

### 4. 应用团队绕过共享模型

风险：为了交付速度复制概念，长期形成新的语义孤岛。

控制：提供易复用的模块、模板和服务，同时把重复概念检查放入发布门禁。

### 5. 只重视模型，不重视实例和查询

风险：本体逻辑上完整，却无法回答真实问题。

控制：每个版本必须绑定样本数据、能力问题查询和回归测试。

### 6. 变更没有兼容性管理

风险：下游查询和应用在升级后失效。

控制：使用语义化版本、依赖分析、废弃周期、替代映射和迁移文档。

### 7. 把大模型生成结果直接当作正式本体

风险：生成内容存在定义漂移、错误继承和虚假来源。

控制：大模型可以辅助术语发现、候选映射和文档生成，但正式概念必须经过来源验证、专家评审和自动化测试。

## 十六、最终交付物体系

一个完整项目不应只交付 `.owl` 或 `.ttl` 文件，而应形成以下资产组合：

| 类别 | 交付物 |
| --- | --- |
| 架构 | 总体架构、分层职责、模块地图、依赖图 |
| 标准 | 建模、命名、定义、元数据、映射、版本和质量规范 |
| 模型 | 顶层、公共核心、领域和应用本体 |
| 术语 | 术语表、同义词、分类体系、代码映射 |
| 数据 | 示例实例、数据映射、转换规则、SHACL shapes |
| 测试 | 能力问题、SPARQL 查询、推理测试、约束测试 |
| 治理 | 组织职责、变更流程、状态模型、评审记录 |
| 发布 | 版本制品、变更日志、兼容说明、迁移指南 |
| 服务 | 查询、校验、推理、目录和应用接口 |
| 运营 | 使用指标、质量报告、问题清单和演进路线 |

这些交付物共同构成本体产品。缺少其中任何一类，都会在后续复用、运行或治理阶段产生明显成本。

---

## 十七、结语：分层的目的不是增加结构，而是管理变化

顶层本体、领域本体和应用本体并不是三份独立文件，而是三种不同的语义责任：

- 顶层本体管理跨领域稳定性；
- 领域本体管理业务共识与复用；
- 应用本体管理场景差异与运行约束。

公共核心模块负责连接高度抽象的顶层与具体领域，术语、标识、元数据、质量、版本和治理机制则横向贯穿整个体系。

真正成熟的本体架构，不是概念最多、逻辑最复杂的架构，而是能够做到：

- 一个概念在正确的层级只定义一次；
- 每项定义都有责任人、来源和使用边界；
- 每个应用差异都能被隔离和解释；
- 每次变更都能被评审、测试和追踪；
- 每份模型都能进入数据、查询、规则和业务流程；
- 每轮应用反馈都能推动共享语义持续演进。

最终，企业获得的不只是一套知识图谱 Schema，而是一套能够让数据、系统、专家和智能应用使用同一种业务语言的语义基础设施。
