讨论 Palantir AIP 时，经常会听到一个问题：**既然 AIP 强调 Ontology，为什么它没有采用 RDF、OWL 和 SPARQL 这一套传统本体技术？**

这个问题抓住了真实的技术差异，却包含一个容易误导后续讨论的前提。AIP 并不是“没有使用本体”。恰恰相反，[Palantir 官方把 Ontology 称为其架构的核心](https://www.palantir.com/docs/foundry/architecture-center/ontology-system)，AIP 中的应用和 Agent 正是通过它理解订单、设备、客户、工厂等业务对象，并调用受治理的业务能力。

真正的问题应该改写为：

> 为什么 Palantir 没有把 RDF/OWL 式的形式本体和逻辑推理机作为 AIP 的主要运行模型，而是发展出一套由对象、关系、函数、动作、实时状态和安全策略共同组成的“运营本体”？

答案不在于哪一种本体更“先进”，而在于两者试图解决的问题不同。传统语义网本体主要回答“世界中的概念如何被精确描述、共享和推理”；Palantir Ontology 还必须回答“组织此刻处于什么状态、谁可以做什么、一个决定怎样安全地改变业务状态，以及改变之后如何回写真实系统”。从知识表示走向生产运营，技术重心自然会发生变化。

本文中的“AIP”指 Palantir Artificial Intelligence Platform。严格来说，Ontology 是 Foundry 与整个 Palantir 平台的基础能力，并非 AIP 独立发明的建模方法；AIP 将大模型和 Agent 接入这一基础。因此，下文分析的是 Palantir 平台为 AIP 提供的本体路线。

## 一、先定义什么是“传统本体”

“本体”一词覆盖范围很广。为了避免把所有语义建模方法混为一谈，本文所说的传统本体，主要指语义网技术栈中的一组典型机制：

- 用 RDF 三元组表达资源及其关系；
- 用 RDFS 或 OWL 定义类、属性、继承、等价、互斥和基数约束；
- 用 IRI 为概念和实体建立可跨系统引用的全局标识；
- 用 SPARQL 查询 RDF 图；
- 用推理机检查一致性或导出隐含事实；
- 在需要封闭式数据校验时，用 SHACL 描述并验证图的形状。

[W3C 的 OWL 2 Primer](https://www.w3.org/TR/owl2-primer/)将 OWL 定义为一种具有形式化语义、用于表达复杂知识的逻辑语言。它可以描述“所有冷链运输都是运输任务”“需要冷链的药品只能由具备冷链能力的运输任务承运”，并由推理机导出未被直接写出的分类关系。它的突出价值是语义明确、标准开放、跨组织交换能力强，而且推理结果由形式语义决定，而不是由某段应用代码临时解释。

这套路线尤其适合以下场景：

- 公共词汇表和行业知识标准；
- 来自多个机构、标识体系不同的开放知识图谱；
- 科研、医药、情报等需要复杂分类和关系推理的领域；
- 强调语义互操作、长期可移植和厂商中立的数据交换；
- 需要回答“根据这些公理还能推出什么”的知识系统。

因此，传统本体并非过时技术。问题在于，OWL 本身是一种声明式知识表示语言，不是事务数据库、工作流引擎、权限系统或应用运行时。W3C 文档也明确说明，OWL 2 不是编程语言，也不是数据库框架。围绕 RDF 当然可以增加校验、事务、规则、流程和访问控制，但这些能力并不是 OWL 核心形式语义自动提供的。

## 二、Palantir 所说的 Ontology 是什么

Palantir 对 Ontology 的定义明显更偏向生产运行。[官方概览](https://www.palantir.com/docs/foundry/ontology/overview)称其为组织的 operational layer，也就是位于数据资产之上的运营层。它把数据集、虚拟表和模型连接到现实中的工厂、设备、产品、订单和金融交易，并包含两组元素：

| 元素 | 典型构件 | 回答的问题 |
| --- | --- | --- |
| 语义元素 | Object、Property、Link、Interface | 业务世界里有哪些对象，它们具有什么属性和关系 |
| 动力元素 | Action、Function、Automation、Dynamic Security | 可以做什么，按什么逻辑做，谁可以做，结果如何改变状态 |

对象、属性和链接仍然承担传统语义建模的职责。例如，`Order` 代表订单，`Warehouse` 代表仓库，订单通过关系连接客户、商品和履约任务。Interface 则提供一种面向对象能力的多态抽象，让不同对象类型可以共享结构和行为契约。

差异主要出现在后半部分。Palantir 不满足于描述“订单关联仓库”，还把“重新分配库存”定义成可执行的 Action，把可用量计算、成本估算和风险预测定义成 Function，再让安全策略决定某个用户或 Agent 能看见哪些对象、读取哪些属性、执行哪些动作。

Palantir 用一个很直观的比喻概括这种设计：对象和关系是企业的“名词”，Actions 是企业的“动词”。只有名词，系统能描述业务；名词、动词、逻辑和安全组合起来，系统才可能参与业务。

这也解释了 Palantir 为何强调 Ontology 不只是一个薄语义层。[Ontology System 文档](https://www.palantir.com/docs/foundry/architecture-center/ontology-system)把它拆成 Language、Engine 和 Toolchain：

1. **Language** 定义对象、属性、链接、动作、自动化以及驱动动作的逻辑；
2. **Engine** 提供查询、订阅、物化、事务写入、批量变更、流和 CDC 等运行能力；
3. **Toolchain** 让开发者通过 OSDK、应用构建工具和 DevOps 机制，把 Ontology 当成应用后端使用。

所以，Palantir 的 Ontology 虽然借用了“本体”这个名字，但其工程边界更接近“语义化的企业运行时”，而不只是一份机器可推理的概念模型。

## 三、一个库存调拨案例：知道是什么，不等于知道怎样做

假设一家制造企业收到高优先级订单 `O-1024`，原定由华东仓发货，但华东仓库存不足。华南仓存在可用库存，运营人员希望重新分配。

传统本体可以精确表达：

```text
Order(O-1024)
hasPriority(O-1024, High)
allocatedTo(O-1024, EastWarehouse)
Warehouse(SouthWarehouse)
hasInventory(SouthWarehouse, Product-A)
```

配合规则或推理，还可以识别 `O-1024` 属于高优先级订单、华南仓属于候选履约仓，甚至发现某些概念定义之间存在矛盾。这些能力很重要，但它们仍未完成一次调拨。生产系统还需要回答：

- 华南仓的“可用库存”是实时值、预测值还是昨日快照？
- 两名操作员同时分配最后 20 件商品时，如何避免超卖？
- 改仓是否会破坏另一个更高优先级订单的承诺？
- 哪个角色可以调拨，超过多少数量需要经理审批？
- 变更怎样以事务方式更新订单、库存占用和履约关系？
- ERP 写回失败时，Ontology 中的状态是否需要回滚或补偿？
- Agent 能否直接执行，还是只能生成方案并等待人工确认？
- 谁在什么时间基于哪些输入批准了这次操作？

在 Palantir 路线中，“重新分配库存”会被建模为一个明确的 Action 契约：输入包括订单、来源仓、目标仓、数量和原因；Function 负责计算候选仓、成本和风险；提交条件检查库存、订单状态与权限；动作更新相应对象和关系，并按配置调用外部系统。应用、自动化流程和 AIP Agent 可以复用同一个动作，而不是分别在界面代码、提示词和脚本里重写规则。

这个例子揭示了核心差异：**知识模型可以说明某个动作在概念上是否合理，运营模型还必须保证它在特定时刻、特定权限和并发条件下能够被正确执行。**

## 四、AIP 没有以传统本体为运行核心的六个原因

公开资料没有给出一份“Palantir 为什么拒绝 RDF/OWL”的架构决策记录，因此不能把下面的分析写成 Palantir 官方表态。更严谨的说法是：从其公开的 Ontology、Action、Security 和 AIP 文档反推，这套产品的目标与传统形式本体的设计中心并不相同。

### 1. 目标从知识表示变成决策与行动闭环

传统本体通常从概念开始：领域中有哪些类，属性的定义域和值域是什么，概念之间有哪些逻辑关系。最终产物往往是一套可共享、可查询、可推理的知识模型。

Palantir 的入口更接近一个运营问题：为什么订单延误，哪些工厂可能停机，怎样重新排产，谁可以批准，以及决定如何回写业务系统。[“Why create an Ontology?”](https://www.palantir.com/docs/foundry/ontology/why-ontology)强调的是把数据、逻辑、动作和安全整合起来，为应用和业务流程提供一致基础。

两条路线可以使用相似的对象与关系，却采用不同的成功标准：

| 维度 | 形式本体的典型关注点 | 运营本体的典型关注点 |
| --- | --- | --- |
| 核心问题 | 概念如何被无歧义地表达 | 业务如何基于共同对象运行 |
| 主要输出 | 公理、分类、关系、推理结果 | 对象状态、决策逻辑、动作与应用 |
| 评价标准 | 一致性、表达力、互操作性 | 实时性、可执行性、安全性、可审计性 |
| 主要用户 | 知识工程师、数据交换系统 | 业务用户、应用开发者、分析师、Agent |
| 变化来源 | 知识模型和事实持续扩展 | 数据流、用户操作和外部系统持续改变状态 |

如果产品目标是运营闭环，那么 Action、Function、权限和状态写回就不能永远作为本体之外的附属组件。Palantir 的选择是把它们提升为一等模型元素。

### 2. 开放世界语义不能直接充当交易完整性规则

OWL 通常采用开放世界假设：系统中没有某条事实，并不意味着该事实为假，只意味着当前未知。例如，知识图谱没有记录某供应商拥有冷链资质，推理机不能仅凭缺失记录断言它没有资质。这很适合不完整、分布式、持续增长的开放知识。

企业交易的默认语义往往更严格。创建冷链订单时，如果系统无法确认承运商资质，通常必须拒绝提交或进入人工审批，而不是把“未知”保留到以后再解释。类似地，如果库存数量、审批人或结算主体缺失，交易系统需要明确失败。

这不是说 RDF 图无法校验。[SHACL](https://www.w3.org/TR/shacl/)正是用于验证 RDF 图是否满足一组 Shapes，例如要求订单必须恰好有一个客户、数量必须为正数。应用也可以在 RDF 存储之上实现封闭世界规则。关键区别在于：**这些校验和事务语义需要额外设计，它们不是 OWL 开放世界推理本身的自然结果。**

Palantir 的对象属性、Action 参数、提交校验和权限策略共同形成操作合同。对 AIP Agent 来说，“缺少必需事实就不能行动”比“缺少事实仍可继续扩展知识”更接近生产环境的风险模型。

### 3. 动作必须成为一等公民，而不是图外的接口说明

传统本体擅长描述实体和关系，但“动作”通常由外部应用、规则引擎、工作流或 API 实现。这样并非错误，却容易在企业里形成断裂：语义模型知道什么是订单，应用代码知道如何改单，权限系统知道谁能改，审计系统再记录改了什么。随着应用增多，同一业务能力会出现多个版本。

[Palantir Action Types](https://www.palantir.com/docs/foundry/action-types/overview)把操作本身建模。一个 Action 可以声明参数、验证规则、对象变更、提交条件、权限和副作用。它既可以被人通过应用触发，也可以被自动化流程或获得授权的 Agent 调用。

这对生成式 AI 尤其重要。若 Agent 只拿到一个通用数据库写权限或几十个缺少业务语义的 API，它必须自行猜测字段、调用顺序和异常处理；若它拿到的是 `ReallocateInventory`、`ApproveWorkOrder` 这类经过治理的动作，允许的操作空间就被压缩为组织认可的能力集合。

动作一等化并不能消除错误，但它把安全边界从提示词中的自然语言要求，移动到可验证、可复用的系统合同中。

### 4. 运行时必须处理实时状态、并发和写回

企业 Ontology 不是静态词汇表。库存、订单、设备状态和风险分数会被批处理、流、CDC、用户编辑与外部系统同时更新。应用还需要搜索、聚合、订阅变化和低延迟读取。

更关键的是写操作。[Palantir 的 Action 一致性文档](https://www.palantir.com/docs/foundry/action-types/consistency-guarantees)说明，对 Ontology 的编辑可以按 ACID 事务提交，并提供与 Action 相关的一致性和隔离语义。这使“扣减库存并更新订单分配”能够作为一次受控状态转换处理，而不是若干彼此独立的图事实写入。

这里必须加一个边界：Action 对 Ontology 编辑的事务保证，不会自动让所有外部副作用也进入同一个分布式 ACID 事务。根据 [Side effects 文档](https://www.palantir.com/docs/foundry/action-types/side-effects-overview)，Webhook、通知或外部 API 调用需要单独考虑失败、重试、幂等和补偿。Palantir 解决的是运营运行时的主要部分，而不是取消分布式系统的基本约束。

传统 RDF 系统也可以支持事务、流和高性能查询；这里不是能力上的绝对“能与不能”，而是产品抽象的重心不同。Palantir 从一开始就把状态变化和应用运行放在 Ontology Engine 的职责内。

### 5. 安全需要随对象、关系和动作动态计算

企业权限很少只是“某人能否访问某张表”。更常见的要求是：区域经理只能查看所属区域的订单；维修人员只能看到自己负责设备的敏感属性；财务审核员能读取金额但不能调整发货；Agent 可以提出调拨方案，却不能执行超过阈值的动作。

这些规则依赖对象属性、关系、用户身份、操作类型和当前状态。它们既约束“看什么”，也约束“做什么”。Palantir 将安全控制与对象、属性、Function 和 Action 一起放进 Ontology，使应用与 AIP 工具调用继承同一组治理边界。

RDF/OWL 可以表达角色、组织、资源及其关系，也可以参与策略推理，但 OWL 推理得到“用户属于某类角色”，不等于生产系统已经完成查询过滤、字段遮蔽、动作授权和审计。后者需要可执行的策略运行时。对 AIP 而言，安全不是知识图谱上的一个标签，而是每次读取和行动都必须执行的约束。

### 6. 平台需要直接交付应用，而不只交付模型文件

如果本体最后仍要由每个团队手工转换成数据库查询、后端接口、前端类型和写回逻辑，语义统一的收益会在应用层大量流失。Palantir 因而为 Ontology 配套对象 API、SDK、应用构建工具、版本管理和发布机制，让对象类型和 Action 可以直接成为应用的开发合同。

这是一种明显的平台化取舍：它牺牲了一部分标准中立性，换取从数据建模到业务应用的短路径。开发者得到的不只是 `.owl` 文件或 SPARQL 端点，而是带类型的对象访问、可调用动作、权限继承和运行状态。

对 AIP 来说，这一点决定了 Ontology 能否真正成为 Agent 的环境。Agent 不仅要“检索与订单相关的事实”，还要获得当前用户可见的订单对象、可调用的 Function、允许执行的 Action，以及每次调用的结构化返回。运营本体正好提供了这套工具表面。

## 五、生成式 AI 放大了运营本体的价值

Palantir 的 Ontology 早于今天的大模型热潮，但生成式 AI 让它的设计价值变得更加明显。原因是，大模型最擅长处理开放语言，企业系统最需要的却是收敛边界。Ontology 正好位于两者之间，把自然语言意图转换为有限、带类型、受权限控制的对象与动作。

### 1. Object 是 Agent 可理解的业务名词

没有语义层时，Agent 看到的是 `ord_hdr`、`wh_avail_qty` 和一组需要临时拼接的主外键。它既要理解数据库结构，又要推断这些字段对应的业务含义。Ontology 把底层结构映射为订单、仓库、设备和客户，使 Agent、应用开发者与业务人员能够围绕同一组对象交流。

这种映射也降低了上层逻辑对物理数据结构的耦合。数据源迁移或字段调整时，只要对象合同保持稳定，Agent 的工具定义和业务应用未必需要同步重写。

### 2. Function 和 Action 是受治理的工具与动词

Agent 的可靠性很大程度上取决于它能使用哪些工具。给模型一个任意 SQL 执行器，能力很强，但权限范围、输入验证和副作用都难以控制；给模型一组经过定义的 Functions 和 Actions，虽然自由度下降，却更接近生产所需的最小授权原则。

例如 Agent 不必自行完成“查库存、判断优先级、更新三张表、调用 ERP、发送通知”的全部步骤，而是先调用 `FindFulfillmentOptions` 获得候选方案，再在用户确认后调用 `ReallocateInventory`。模型负责理解意图、选择工具和解释结果，确定性代码负责业务计算与状态改变。

### 3. Dynamic Security 定义 Agent 的行动空间

一个常见误区是给企业 Agent 配置一个服务账号，再试图在 Prompt 中要求它“不要访问无权限数据”。这不是可靠的安全边界。模型可能受提示注入影响，工具调用也可能因推理错误而越界。

在运营本体中，Agent 应以用户或明确的执行身份调用对象、Function 和 Action。它看到的对象集合和可执行操作受到平台权限约束。这样，Prompt 是行为指导，权限系统才是强制边界。对于高风险动作，还可以要求人工确认、审批或自动化条件，而不是仅依赖模型的一次判断。

因此，AIP 与 Ontology 的关系可以压缩为一条链路：

```text
自然语言意图
  -> 识别相关业务对象
  -> 调用受治理的 Function 获取事实或计算方案
  -> 依据权限选择可用 Action
  -> 人工确认或自动化策略
  -> 事务性修改 Ontology 状态
  -> 外部系统副作用、审计与反馈
```

大模型并没有取代业务模型。相反，模型越有能力调用工具，企业越需要一个明确的对象、动作和权限层来限制其自由度。

## 六、Palantir 并没有抛弃传统本体的思想

如果只看到 Palantir 没有以 OWL 文件和 SPARQL 端点作为产品中心，很容易得出“它只是把数据模型改名为 Ontology”的结论。这同样过于简单。

Palantir 继承了传统本体中至少四个关键思想：

1. **用共享概念消除系统方言。** 不让每个应用分别定义“客户”“订单”和“设备”。
2. **把业务语义与物理存储分离。** 上层依赖稳定对象合同，而不是直接依赖表、列和文件。
3. **用关系表达业务上下文。** 一个订单的意义来自它与客户、商品、仓库、运输任务和责任人的连接。
4. **让模型成为跨团队协作资产。** 对象定义、属性和关系需要被治理、复用、演进，而不是藏在单个应用代码中。

Palantir 的[对象与链接类型参考](https://www.palantir.com/docs/foundry/object-link-types/type-reference)也明确提到，其数据类型系统受到 RDF、OWL 和 XSD 等规范启发。它与传统本体的关系不是彻底割裂，而是把语义建模思想重新组织到企业应用运行时中。

更准确的概括是：Palantir 保留了“共享语义层”的目标，但没有把“形式逻辑表达力最大化”作为首要目标；它把重点转向了状态、行为、安全和软件交付。

## 七、这条路线付出了什么代价

运营本体并非只有收益。它把语义、运行时和开发工具深度结合，也带来几项真实代价。

### 1. 标准互操作性下降

RDF、OWL、SPARQL 和 SHACL 是公开标准，存在多个实现，模型可以跨组织与工具交换。Palantir 的 Object、Action、Function、Interface 和 Dynamic Security 则带有明显的平台语义。即使数据可以通过 API、文件或连接器进出，把一套完整的运营模型原样迁移到另一个平台仍然成本很高。

Palantir 在[互操作性白皮书](https://www.palantir.com/assets/xrfr7uokpv1b/7BxLPkTqJU9QhLTQCjJMo6/eed1457949dc2d1cd6b6e71936c0aa9c/Enabling_Interoperability_and_Embracing_Openness_with_Foundry.pdf)中强调开放 API、数据导出和对开放格式的支持，这有助于降低数据被封闭的风险，但“能够导出数据”不等于“运营语义和运行行为可以无成本移植”。

### 2. 形式推理不是中心能力

如果项目需要复杂的类公理、等价概念、属性链、自动分类或跨知识库推理，OWL 及其推理生态具有直接优势。Palantir 可以通过数据转换、Function、模型和应用逻辑产生派生信息，但程序计算与形式逻辑推理不是同一件事：前者更灵活，后者在可解释的逻辑蕴含和标准语义上更强。

### 3. 平台锁定风险增加

当数据映射、对象模型、动作、权限、应用和 Agent 都建立在同一平台上，开发速度和治理一致性会提高，迁移成本也会随之上升。企业不能只评估最初建模效率，还应评估 API 边界、数据可导出性、关键逻辑是否可移植，以及退出方案。

### 4. “Ontology”一词容易造成沟通错位

知识工程师听到 Ontology，可能期待描述逻辑、IRI、开放世界和自动推理；Palantir 开发者讨论的却可能是对象属性、Action 和 OSDK。双方使用同一个词，却在谈不同层次的系统。项目启动时如果不先明确术语，很容易把产品对象模型误认为完整的形式本体，或反过来因为它不使用 OWL 就否认其语义价值。

这些代价不是否定 Palantir 路线，而是提醒架构选择必须与目标匹配。运营闭环越重要，集成平台的收益越大；跨组织标准交换和形式推理越重要，专有运行时的代价越需要被认真计算。

## 八、更合理的答案可能是分层，而不是二选一

传统本体与运营本体并不必然竞争。大型组织完全可以让两者承担不同职责：

| 层次 | 更适合的技术 | 主要职责 |
| --- | --- | --- |
| 公共语义与行业标准层 | RDF、RDFS、OWL、SKOS | 统一外部词汇、发布可交换概念、跨机构对齐 |
| 知识校验与推理层 | OWL 推理、SHACL、规则系统 | 分类、逻辑一致性、图结构验证、知识发现 |
| 企业运营语义层 | Palantir Ontology 或类似对象运行时 | 映射内部数据、表达当前对象状态、统一权限 |
| 决策与行动层 | Function、Action、Workflow、Agent | 计算方案、审批、事务写回、执行和审计 |

例如，一家制药企业可以用公开的生命科学本体对药物、靶点、疾病和试验术语进行标准化与推理，再把与自身运营相关的产品批次、工厂、质量事件和供应订单映射为 Palantir 对象。研究知识仍以开放标准交换，生产决策则通过受治理的 Action 执行。

这种混合架构需要明确映射边界：

- 哪些概念拥有公开 IRI，哪些对象使用企业内部标识；
- 哪些事实由推理得到，哪些状态以业务系统为权威来源；
- SHACL 校验失败是否阻止数据进入运营层；
- 形式本体中的类如何映射为 Object Type 或 Interface；
- 推理结果更新后，哪些 Action 可以被触发，是否需要人工复核；
- 数据可以导出时，动作、权限和审计合同如何留存。

真正成熟的架构不会因为采用运营本体就重建一套封闭行业词汇，也不会因为已有 OWL 模型就要求推理机承担事务、审批和应用运行的全部职责。

## 九、结论：不是不要本体，而是重新定义本体的工作范围

“为什么 AIP 没有使用传统本体建模”这个问题，最简短的答案是：**因为 AIP 的首要任务不是建立一个可进行形式推理的开放知识库，而是让人和 AI 在企业当前状态之上安全地做出决定并执行行动。**

传统本体围绕概念、公理、互操作与推理建立优势；Palantir Ontology 则把对象和关系与 Functions、Actions、事务运行时、动态安全和开发工具绑定在一起。前者更擅长让机器精确描述、交换和推导世界，后者更强调让人和机器在权限、规则与审计范围内改变世界。

这并不证明 RDF/OWL 不适合企业，也不证明 Palantir 的设计在所有场景都更优。它只说明，一旦目标从“知识是否表达正确”扩展为“业务能否持续、安全、可追责地运行”，仅有形式语义还不够。企业需要在语义开放性、逻辑表达力、实时状态、事务执行、应用效率和平台锁定之间作出权衡。

因此，评价 AIP 的 Ontology 不应只问“它是不是标准本体”，而应继续追问三个更有价值的问题：

1. 它是否把企业数据稳定地映射成业务人员真正使用的对象与关系？
2. 它是否把业务动作、权限、校验和审计变成可复用的系统合同？
3. 它是否保留了与外部标准、数据和其他平台互操作及退出的边界？

能同时回答这三个问题，Ontology 才不只是一个换了名字的数据模型，也不只是停留在概念层的知识图谱，而会成为企业 AI 可以依赖的运营基础设施。
