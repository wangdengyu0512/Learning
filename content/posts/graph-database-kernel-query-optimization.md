图数据库常被概括成一句话：把关系直接存起来，所以多跳查询不再需要 JOIN。这个说法抓住了邻接访问的直觉，却掩盖了真正决定性能的部分。

一条图查询仍然要回答传统优化器熟悉的问题：从哪里开始？先匹配哪条边？过滤条件何时执行？中间结果会膨胀到多大？应该逐边扩展、做哈希连接，还是同时处理多个关系？区别在于，图数据库把“沿边找邻居”变成了一等物理操作，并围绕图拓扑建立了新的统计信息、搜索空间和执行算法。

本文以一条支付风控查询为主线，讨论属性图数据库中的在线模式匹配：

```cypher
MATCH (u:Account {id: $accountId})
      -[:TRANSFER*1..3]->(r:Account)
WHERE r.riskLevel = 'HIGH'
RETURN DISTINCT r.id
```

它要寻找某个账户在 1 到 3 跳转账范围内可达的高风险账户。语句很短，但数据库至少要处理索引定位、变长路径、方向选择、属性过滤、去重和环路语义。本文使用 Cypher 表达示例，讨论的机制同样适用于 Gremlin、GQL 和 SQL/PGQ 等图查询接口。

## 一、图查询没有消灭 JOIN

先把属性图还原成关系，会更容易看见问题的本质。节点与边可以近似表示为：

```text
Account(id, riskLevel, ...)
Transfer(src, dst, amount, timestamp, ...)
```

固定两跳查询在逻辑上接近：

```sql
SELECT DISTINCT a2.id
FROM Account AS a0
JOIN Transfer AS t1 ON t1.src = a0.id
JOIN Account AS a1 ON a1.id = t1.dst
JOIN Transfer AS t2 ON t2.src = a1.id
JOIN Account AS a2 ON a2.id = t2.dst
WHERE a0.id = :account_id
  AND a2.risk_level = 'HIGH';
```

图数据库并没有让这些变量之间的相等约束消失。它改变的是物理访问方式：如果节点记录能直接定位其出边分组，执行器可以从 `a0` 的邻接表中取得 `t1`，再由边端点定位 `a1`，不必每一跳都扫描整个边表并构造通用哈希表。

因此，更准确的表述是：

> 图数据库不是不做连接，而是把常见的端点连接具体化为邻接扩展，并让优化器在邻接扩展、通用连接和多关系算法之间选择。

这也解释了为什么“图数据库擅长多跳”不等于“跳数越多越快”。邻接访问让单次扩展便宜，但扩展次数仍由中间结果规模决定。假设普通账户平均出度为 8，三跳的朴素上界已经是 `8 + 8² + 8³ = 584`；如果第一跳遇到一个拥有 200 万条出边的支付归集账户，查询即使最终只返回 12 个高风险账户，也可能先枚举数百万条边甚至更多路径。

## 二、为什么图模式难以估算

关系优化器依赖选择率和基数估计，图优化器同样如此，而且图数据会放大几个经典难题。

### 1. 度分布高度偏斜

平均出度很容易制造错误安全感。社交网络中的名人、支付网络中的平台账户、知识图谱中的通用实体都可能成为超级节点。平均值为 8，不能说明参数 `$accountId` 对应的节点也只有 8 个邻居。

参数化查询尤其棘手：同一个执行计划面对普通账户和超级节点，运行成本可能相差几个数量级。只按标签和边类型保存一个平均度数，通常不足以支撑稳定的 P99 延迟。

### 2. 拓扑与属性并不独立

优化器经常近似假设谓词相互独立。例如，全局有 1% 的账户为高风险账户，三跳扩展产生 100 万个候选节点，就估算约 1 万个结果。但现实中风险账户可能聚集在特定团簇，也可能刻意避开已知高风险邻居；“可达性”与 `riskLevel` 往往强相关。

同样，边类型、方向、时间和金额之间也存在相关性。`TRANSFER` 的全局分布不能准确描述“近 24 小时、金额大于 1 万、由商户账户发起”的局部分布。

### 3. 环会造成重复匹配

模式中只要出现环，边就不再能独立估算。三角形查询：

```cypher
MATCH (a)-[:KNOWS]->(b),
      (b)-[:KNOWS]->(c),
      (a)-[:KNOWS]->(c)
RETURN a, b, c
```

前两条边产生的 `(a, b, c)` 是否满足第三条边，取决于图的聚集程度，而不只是 `KNOWS` 的总边数。树形假设、独立性假设和均匀性假设会在这里同时失效。

### 4. 变长路径把误差逐跳放大

`*1..3` 不只是三个固定查询的简单并集。执行器还要遵守路径语义：边能否重复、节点能否重复、不同路径是否都需要保留，以及最终是返回路径、端点还是只判断存在性。每一跳的估算误差都会影响下一跳，去重又可能把巨大的路径集合压缩为很少的端点。

### 5. 可选计划数量快速增长

一个包含多个节点变量和边变量的模式，可以从不同锚点开始，沿不同方向扩展，也可以拆成多个子模式后连接。再叠加索引、连接算法和并行策略，候选计划会迅速增长。优化器必须在有限规划时间内剪枝，而不能穷举所有排列。

## 三、存储内核：让邻接成为一等访问路径

查询优化不能脱离存储布局。逻辑上同一张图，可以由完全不同的物理结构承载。

### 1. 节点、边与属性如何落盘

典型属性图内核会维护三类信息：

- 节点记录：内部 ID、标签，以及属性记录或属性区域的引用；
- 边记录：边类型、起点、终点，以及边属性的引用；
- 邻接结构：从节点出发，按方向和类型组织相邻边或相邻节点。

实现并不一定是三个独立文件。记录可以定长或变长，属性可以内联、列式分离或放入独立页，邻接表也可能采用链式记录、CSR 类数组、B+ 树、LSM 结构或压缩块。设计取决于更新频率、图规模和查询负载。

在线事务型图数据库通常重视点查与局部扩展；偏分析型系统则更愿意使用连续、压缩、便于批量扫描和向量化的邻接布局。没有一种布局能同时把随机更新、全图扫描、压缩率和局部遍历都做到最优。

### 2. Index-free adjacency 到底意味着什么

“无索引邻接”常被误读为图数据库不需要索引。它实际强调的是：节点一旦被定位，访问其邻边不必再通过全局二级索引查找 `src = node_id` 的全部边，而可以从节点记录或可直接计算的位置进入邻接结构。

这不意味着起点也能凭空找到。示例中的：

```cypher
(u:Account {id: $accountId})
```

仍然需要标签扫描、属性索引或唯一性约束来定位 `u`。属性过滤、全文检索和向量检索同样需要相应索引。更准确的分工是：

- 属性索引负责找到候选起点或终点；
- 邻接结构负责从已知节点高效取得相邻关系；
- 优化器决定从哪种访问路径进入图，以及何时切换策略。

### 3. 邻接表也需要面向负载设计

如果查询常按方向和边类型过滤，把出边、入边以及不同类型分组，能避免扫描无关关系。若经常求共同邻居，将邻接 ID 排序后做归并或交集会很有效。对于静态大图，差分编码、位图和分块压缩可以减少内存与 I/O；代价是更新和随机定位更复杂。

分布式图数据库还要决定如何分区。按节点哈希分区便于均衡容量，却可能让一次多跳扩展跨越多台机器；按社区切分能保留局部性，但热点社区和超级节点会造成负载不均。此时，网络传输不再只是执行细节，而会进入优化器的成本模型。

存储层最终提供的是一组带成本特征的原语，例如“按内部 ID 取节点”“读取某节点某类型的出边”“判断两个节点之间是否有边”“批量取得一组节点的邻居”。查询优化器的任务，是把逻辑图模式编译成这些原语的组合。

## 四、从查询文本到物理计划

一条图查询通常要经过如下流水线：

```text
查询文本
  → 语法树 AST
  → 名称绑定与类型检查
  → 规范化的图模式 IR
  → 逻辑重写与代价搜索
  → 物理执行计划
  → 流水线或向量化执行器
```

### 1. 图模式 IR 比语法更重要

解析器先把 Cypher、GQL 或其他语言转成 AST；语义阶段再确认变量作用域、标签、边类型和表达式类型。之后，优化器通常不会直接在原始语法树上枚举计划，而会把查询规范化为图模式：节点变量是顶点，关系变量是边，属性条件附着在对应变量上，投影、聚合和路径语义作为额外约束。

这层中间表示让不同语法形式落到同一个优化问题，也让图算子与关系算子能够组合。GOpt 就提供了统一的图中间表示 GIR：上层可接入不同图查询语言，下层则通过物理算子与成本模型接口适配不同执行后端，从而把优化器从单一语言和单一图系统中解耦 [5]。

### 2. 先做等价重写，再比较成本

不依赖具体统计信息的规则可以先执行，例如：

- 合并重复谓词并做常量折叠；
- 把只依赖单个变量的过滤尽量靠近数据源；
- 只读取后续真正需要的属性；
- 把固定长度路径展开为明确的关系模式；
- 在语义允许时，把“只需判断存在”改写成半连接或提前终止的遍历。

“谓词下推”并非越深越好。对变长路径上的 `all(rel IN relationships(p) WHERE ...)`，能否在每次扩展时检查，取决于谓词是否只依赖当前边、路径语义以及实现能力。如果系统先枚举完整路径再过滤，逻辑结果相同，成本却可能完全不同。

### 3. 物理算子不只是 Expand

不同产品名称不完全相同，但常见计划算子大致包括：

- `NodeScan` / `LabelScan`：扫描节点或某标签下的节点；
- `IndexSeek`：通过属性索引取得候选节点；
- `Expand`：一端已绑定时，沿邻接结构绑定边和另一端；
- `ExpandInto`：两端都已绑定时，检查它们之间是否存在目标边；
- `PathExpand`：执行有界或无界的变长路径扩展；
- `HashJoin` / `MergeJoin` / `Apply`：连接两个子计划；
- `Distinct` / `Aggregate` / `Sort`：去重、聚合与排序。

下面这个计划仅用于说明机制，不是任何具体数据库版本的真实输出：

```text
Distinct(r.id)                           estimated: 12
└─ Filter(r.riskLevel = 'HIGH')          estimated: 20
   └─ PathExpand(u, TRANSFER, 1..3, r)   estimated: 2,000
      └─ IndexSeek(Account.id = $id)     estimated: 1
```

表面上它很合理：唯一索引找到一个起点，再向外扩展。但如果 `$id` 是超级节点，`PathExpand` 的实际输出可能是 800 万，计划中的 `2,000` 就会误导后续算法、内存与并行度选择。

## 五、基数估计：计划质量的地基

代价模型需要估计每个算子的输出行数。行数估错，CPU、I/O、网络和内存成本都会随之失真。

### 1. 从简单统计到图摘要

最基础的统计包括：

- 各标签的节点数、各类型的边数；
- 属性的不同值数量、空值比例和直方图；
- 按起点标签、边类型、终点标签分组的平均度；
- 入度与出度的分位数、重尾或高频节点信息。

对单边模式 `(a:A)-[:R]->(b:B)`，可以先用类型化边数估算；多边模式则常通过条件选择率逐步相乘。这个方法便宜，却会忽略路径相关性和环闭合概率。

更精细的方法会保存小型子图的频率、路径摘要、特征值或采样结果。一套面向属性图的通用基数估计框架，通常需要同时描述标签、属性和拓扑约束，而不能只复用关系表的单列直方图 [6]。Amazon Neptune 的 DFE 统计信息也会生成特征集和谓词统计，用于基于成本的计划生成；统计过期或缺失时，优化器的判断能力自然受限 [3][4]。

### 2. 采样与学习型估计

在线采样可以从候选锚点出发，实际探测若干邻接表，再外推模式规模。它比全局平均值更能感知当前参数附近的度分布，但在稀有模式、强偏斜和多跳放大下，方差可能很高。采样预算本身也属于规划成本，不能无限增加 [7]。

学习型方法则尝试从历史查询或图表示中学习联合分布。它们有机会捕捉复杂相关性，但需要处理训练数据偏差、图更新、模型推理开销和最坏情况失准。工程上更常见的方向不是完全替代规则统计，而是让直方图、摘要、采样与学习模型相互兜底。

### 3. 用 Q-error 衡量估算误差

基数估计常用 Q-error：

```text
Q-error = max(estimated / actual, actual / estimated)
```

估算 100、实际 10,000，Q-error 为 100；估算 10,000、实际 100，同样为 100。它对高估和低估对称，也能直观反映数量级误差。

不过，最终结果的估算准确并不代表计划正确。一个计划可能把中间结果从 1 行放大到 800 万行，再经过去重返回 12 行。真正值得关注的是执行计划中**第一次**出现巨大估算偏差的位置，因为之后的行数、算法选择和资源预算往往都已被污染。

## 六、连接顺序：先限制，再扩展

考虑一个更具体的查询：寻找某个用户转账可达、同时绑定了高风险设备的账户。

```cypher
MATCH (u:Account {id: $accountId})
      -[:TRANSFER*1..2]->(r:Account)
      -[:USES]->(d:Device {risk: 'HIGH'})
RETURN DISTINCT r.id
```

至少有三种起点策略：

1. 用唯一索引定位 `u`，向外扩展转账，再检查设备；
2. 用索引找到高风险 `d`，沿 `USES` 反向找到 `r`，再验证它是否从 `u` 可达；
3. 分别生成 `u` 附近账户和高风险设备关联账户，再连接两边的 `r`。

若 `u` 是普通账户，第一种通常很好；若 `u` 是拥有 200 万出边的平台账户，而高风险设备只有几十台，第二种或第三种可能更优。查询语句的书写顺序不应决定执行顺序，选择性与局部度分布才应该决定。

### 1. 左深树、浓密树与混合计划

左深计划每次把一个新关系接到已有结果上，容易流水线执行，搜索空间也较小。浓密计划可以独立优化多个子图，再将子结果连接；它更适合存在多个高选择性锚点的模式，也更容易并行，但需要更大的搜索空间和中间物化。

实际优化器常采用动态规划或级联式搜索：为同一个逻辑子图保留若干具有不同物理属性的低成本计划，剪掉明显劣势方案，再逐步合并子图。对于复杂模式，还会限制枚举宽度、先分解连通分量，或使用启发式规则控制规划时间。

### 2. 方向也是代价选择

边在语义上有方向，不代表物理上只能顺向执行。若内核同时维护入邻接和出邻接，模式 `(a)-[:R]->(b)` 既可以在 `a` 已绑定时读出边，也可以在 `b` 已绑定时读入边。

这正是图优化里最实用的规律之一：**先找选择性强的锚点，再沿低扇出方向扩展**。不过，索引选择性只是第一步。一个属性索引返回 10 个节点，如果每个节点都有百万级入度，后续扩展仍然昂贵；成本模型必须同时看候选数和条件度分布。

## 七、物理执行：Expand、二元连接与 WCOJ

逻辑顺序确定后，执行器还要选择如何完成每一步。图查询并不存在一个对所有模式都最优的算法。

### 1. 邻接扩展适合已绑定端点

当 `u` 已经由唯一索引绑定时，`Expand(u)` 直接读取它的邻接表，成本大致与实际访问的边数相关。它天然适合点查驱动的局部遍历，也可以流水线地产生下游记录，不必先构造完整边表。

如果两个端点都已经绑定，`ExpandInto(a, b)` 可以检查邻接结构中是否存在目标边。实现可能扫描较短的一侧、在有序邻接表中二分，或使用哈希、位图和布隆过滤器做快速排除。

当一批输入节点同时进入算子时，逐行随机访问可能造成大量缓存未命中。批量化执行可以按节点或分区重排请求，向量化读取邻接块，并摊薄函数调用和解释器开销。代价是流水线延迟增加，而且重排必须保持查询语义。

### 2. 二元连接仍然不可替代

当两个子模式都能被高选择性谓词大幅缩小，分别执行后用哈希连接往往比从一端长距离扩展更便宜。排序合并连接适合输入已经按连接键有序的情况；嵌套循环或 `Apply` 则适合外侧很小、内侧能够快速索引查找的情况。

例如，先得到 20 个高风险设备关联账户，再与某个用户两跳内的 500 个账户求交，构造一个小型哈希表就足够了。为了坚持“图查询必须用遍历”而放弃这种计划，反而会损失关系优化器积累多年的工程优势。

### 3. 多路连接为何适合环模式

再看三角形：

```text
R(a, b) ⋈ S(b, c) ⋈ T(a, c)
```

假设三个关系的规模都不超过 `N`。根据 AGM 界，三角形结果在最坏情况下可达到 `N^(3/2)`。但某些传统二元计划会先计算 `R ⋈ S`，产生最多 `N²` 个 `(a, b, c)` 候选，再用 `T` 过滤。这个中间结果可能远大于最终输出的最坏情况界。

Worst-Case Optimal Join（WCOJ）不固定先物化某个二元连接，而是按变量顺序逐层求候选集合交集。例如先选择 `a`，再交汇与 `a` 相容的 `b`，最后对多个约束给出的 `c` 候选做交集。只要底层索引支持高效的前缀查找和集合交，算法就能让运行时间更贴近查询的最坏情况输出界。EmptyHeaded 展示了这种多路连接、压缩集合表示与硬件感知执行在图分析负载中的结合 [8]。

但 WCOJ 不是“图查询专用的万能替代品”。以下场景中，传统计划可能更简单、更快：

- 起点由唯一索引绑定，局部邻接扩展极小；
- 查询是链式或树形，二元连接不会产生灾难性中间结果；
- 属性计算、外连接、排序或复杂聚合占据主要成本；
- 维护多种排列索引的存储与写放大得不偿失。

更现实的方向是混合执行。Free Join 试图在传统二元连接和 WCOJ 之间建立统一抽象，让优化器可以按查询结构选择拆分粒度，而不是在两套互斥执行器之间二选一 [9]。

### 4. 流水线、物化与并行

流水线可以边扩展边过滤，降低首行延迟和峰值内存；但 `Distinct`、全局聚合和排序通常会形成阻塞点。浓密计划、重复使用的子结果和跨机器交换，也可能要求主动物化。

算子融合可以减少中间对象和虚函数调用，例如把“读取邻接边、检查边类型、过滤时间、投影终点 ID”合成一个紧凑循环。向量化则用批次提高 CPU 与内存带宽利用率。两者并不矛盾：系统可以融合批处理算子，也可以对小规模点查保留低延迟的行式路径。

并行扩展还会遭遇数据偏斜。简单地把起点均分给线程，如果某个起点是超级节点，一个线程会承担绝大多数工作。更稳健的调度要能把大邻接表切块、动态窃取任务，并在分布式环境中把计算尽量推向数据所在分区。

归根结底，物理计划的目标不是最少算子，而是最少无效工作：少读无关边、少构造无用路径、少跨网络搬运中间结果，并尽早执行真正有选择性的约束。

## 八、实战：如何诊断一条慢图查询

面对慢查询，最有效的方法不是先猜应该建哪个索引，而是沿执行计划找到中间结果第一次失控的位置。不同产品的命令和指标名称有所差异，下面以 Neo4j 风格术语说明通用方法；其官方文档对 `EXPLAIN`、`PROFILE` 和各类算子有完整定义 [1][2]。

### 第一步：区分计划问题与执行问题

先使用 `EXPLAIN` 查看计划而不实际执行，再在可控环境中用 `PROFILE` 采集真实行数与资源指标。生产环境中的超大查询要谨慎执行 `PROFILE`，因为分析本身仍会跑完整查询。

重点检查：

- 起点使用 `IndexSeek`、标签扫描还是全节点扫描；
- 第一段扩展是顺向还是反向，扇出是否合理；
- 属性和边谓词在哪个算子执行；
- 哪一步出现 `Distinct`、`Sort` 或大规模物化；
- 估算行数与实际行数从哪里开始明显分离；
- `DB Hits`、内存、网络和耗时是否集中在同一个算子。

以下仍是机制示意，不代表特定版本的真实计划格式：

```text
Operator                 Est. rows   Actual rows   DB Hits
----------------------------------------------------------
IndexSeek(Account.id)             1             1         4
PathExpand(TRANSFER*1..3)     2,000     8,240,000  9,100,000
Filter(r.riskLevel)              20        73,500    140,000
Distinct(r.id)                   12            12          0
```

这里真正的问题不在最后的 `Distinct` 返回 12 行，而在 `PathExpand` 首次从估算 2,000 行偏离到实际 824 万行。接下来应检查参数是否命中超级节点、统计信息是否过期、路径是否重复访问同一批节点，以及过滤能否提前。

### 第二步：确认业务需要“路径”还是“存在性”

很多业务问题实际只关心：是否存在一条满足条件的路径，或哪些终点可达，并不关心所有路径本身。如果查询把完整路径绑定为变量，又在末尾 `DISTINCT`，执行器可能不得不生成大量重复路径后才能丢弃。

以下三个问题语义不同：

```cypher
// 返回所有匹配路径
MATCH p = (u:Account {id: $accountId})-[:TRANSFER*1..3]->(r)
RETURN p

// 返回不同终点
MATCH (u:Account {id: $accountId})-[:TRANSFER*1..3]->(r)
RETURN DISTINCT r.id

// 只判断是否存在满足条件的模式
MATCH (u:Account {id: $accountId})
RETURN EXISTS {
  MATCH (u)-[:TRANSFER*1..3]->(r:Account {riskLevel: 'HIGH'})
} AS hasRisk
```

如果引擎能把存在性查询编译为半连接或支持提前终止，第三种形式可能少做大量工作。改写前必须确认产品版本的语法、路径唯一性规则和执行计划，不能假设表面相似的语句必然共享实现。

### 第三步：把有业务意义的约束放进扩展

风控规则通常不只是“任意三跳”。时间窗口、金额、币种和边状态往往都能减少扇出：

```cypher
MATCH p = (u:Account {id: $accountId})
          -[:TRANSFER*1..3]->(r:Account)
WHERE r.riskLevel = 'HIGH'
  AND all(rel IN relationships(p) WHERE
          rel.timestamp >= $windowStart AND rel.amount >= $minAmount)
RETURN DISTINCT r.id
```

语义上，边条件限制了合法路径；物理上，它是否在每一跳扩展时执行，要查看计划。如果系统在生成完整路径后才计算 `all(...)`，仍可能产生巨大的中间结果。有些引擎提供专门的路径模式、量化路径谓词或遍历 API，使这类条件更容易下推，应优先使用该产品可优化的表达方式。

### 第四步：为锚点建索引，不要把索引当提示词

示例查询至少应该保证账户 ID 能唯一定位：

```cypher
CREATE CONSTRAINT account_id_unique IF NOT EXISTS
FOR (a:Account) REQUIRE a.id IS UNIQUE;

CREATE INDEX account_risk_level IF NOT EXISTS
FOR (a:Account) ON (a.riskLevel);
```

唯一性约束不仅加速访问，也向优化器提供“最多一行”的强基数信息。`riskLevel` 索引则增加了从高风险端反向规划的候选路径。

但“存在索引”不等于“必须使用索引”。如果 40% 的账户都是高风险，索引返回大量随机记录，标签扫描或从另一端扩展可能更便宜。索引的价值是增加候选访问路径，最终仍应由选择率、局部度与成本决定。

### 第五步：显式治理超级节点

超级节点不是一个能靠“更新统计信息”彻底消失的问题，它往往是业务模型本身。常见处理包括：

- 把账户按角色分开建模，避免平台账户与普通账户共用同一种无差别扩展；
- 将高频关系按时间或业务维度分桶，使查询只访问相关分片；
- 对超级节点维护专门的压缩邻接、位图或摘要；
- 在在线请求中设置跳数、时间、结果数和资源上限；
- 按起点度数或参数类别准备不同计划，必要时使用自适应重规划；
- 并行执行时切分大邻接表，而不是只按起点数量分配任务。

这里需要克制：为了绕过某条慢查询而复制节点、引入中间节点，可能让写入一致性和其他查询变得更复杂。先确认瓶颈来自数据模型、统计信息、计划选择还是执行实现，再决定是否修改模型。

### 一份可复用的排查清单

1. 用索引或约束把候选锚点缩到多小？
2. 每次扩展的方向、边类型和实际扇出是多少？
3. 第一个“估算行数远小于实际行数”的算子在哪里？
4. 属性条件和路径条件能否在扩展过程中执行？
5. 查询需要所有路径、不同终点，还是只需要存在性？
6. 是否因 `DISTINCT`、排序、聚合或跨分区交换而阻塞？
7. 慢参数是否集中在超级节点或特定数据分布？
8. 冷缓存、热缓存和并发负载下，结论是否一致？

## 九、如何做一场可信的图数据库基准测试

只用一条查询的平均耗时比较产品，几乎一定会遗漏关键变量。图负载对数据分布、参数和缓存非常敏感，基准测试至少要控制以下维度。

### 1. 选择可解释的工作负载

LDBC Social Network Benchmark（SNB）提供社交网络数据生成器以及 Interactive、Business Intelligence 等工作负载，适合观察点查、多跳模式、更新与分析查询的组合 [10]。金融场景可以参考 LDBC FinBench，其数据和查询围绕账户、转账、风险路径等模式构造 [11]。

标准基准的价值不只是有一组查询，还在于它定义了数据生成、参数选择、正确性与审计规则。自建业务基准仍然必要，但应保留同样的可复现性：固定数据版本、数据分布、查询模板、参数集、并发模型和硬件配置。

### 2. 参数必须按难度分桶

同一个模板不能只随机抽几个起点。应按起点度数、谓词选择率、结果规模、路径长度和所在分区分桶，例如：

- 低度、中度、高度和超级节点；
- 命中 0 行、少量结果和大量结果；
- 高风险比例低、中、高的局部社区；
- 单分区局部查询与跨分区查询。

否则，大量容易参数会掩盖少数灾难性长尾。对在线图查询，P50 只能描述常态，P95 与 P99 往往更接近真实容量风险。

### 3. 不要只报告端到端延迟

一份可诊断的报告应同时包含：

- P50、P95、P99 延迟与吞吐量；
- 规划时间和执行时间；
- 各算子的估算行数、实际行数和最大中间结果；
- 存储访问量、缓存命中、CPU、峰值内存和临时落盘；
- 分布式系统的网络字节数、远程请求数与负载偏斜；
- 数据导入时间、索引构建时间和索引占用空间。

还要分开测试冷缓存与热缓存。冷缓存反映存储路径和预热成本，热缓存更接近稳定在线服务；把两者混在同一组数字里，结论不可解释。查询计划、数据库配置和统计信息版本也应随结果保存。

## 十、接下来的优化器会往哪里走

### 1. 图与关系使用统一中间表示

GQL 已成为 ISO 图查询语言标准，SQL/PGQ 也把属性图模式带入 SQL 体系 [12]。语言层正在靠近，内核层同样需要让图模式、关系代数、路径语义和属性表达式进入统一 IR。这样，成熟的规则引擎、代价搜索和分布式执行能力可以复用，同时保留 `Expand`、路径枚举与集合交等图原生算子。

GOpt 展示了模块化图优化器的一种实现：不同语言先进入统一 GIR，后端再注册自己的物理算子和成本模型 [5]。进一步统一图与关系优化时，真正困难的不只是语法翻译，而是保持路径语义，并为图特有算子提供可信的统计与成本模型。

### 2. 传统连接与 WCOJ 混合

链式局部遍历、星形模式、稠密环查询和带复杂属性计算的查询，需要的算法并不相同。未来执行器更可能把邻接扩展、哈希连接、排序集合交、位图和 WCOJ 放在同一个候选空间，根据子图结构和数据分布组合，而不是押注单一算法。

### 3. 自适应执行与参数感知计划

图上的估算误差很难被静态统计完全消除。执行器可以在运行时观察实际扇出：如果第一跳已经比估算大 1,000 倍，就停止沿原计划扩展，改为从另一端建立候选集，或切换到不同连接算法。

这种自适应能力需要解决重规划开销、已完成工作的复用、结果语义和分布式协调。更轻量的方案是按参数特征缓存多份计划，例如根据起点度数分为普通节点与超级节点两类，而不是让所有参数共享同一计划。

### 4. 图、向量与全文检索联合优化

越来越多查询先用向量相似度或全文条件找实体，再沿知识图谱扩展并做结构约束。若各引擎串行执行，第一阶段可能返回过多候选；理想的优化器应同时估计向量阈值、文本选择率和图扩展扇出，在“先语义召回”与“先结构限制”之间选择，并支持两个方向的增量交替执行。

这会把图优化器带回一个熟悉的核心问题：不同访问路径之间如何交换统计信息，如何控制中间结果，以及如何在不确定性下做代价决策。

## 结语

理解图数据库性能，可以沿着一条因果链展开：

```text
数据模型与邻接布局
  → 可用访问路径
  → 图模式与路径语义
  → 基数估计
  → 锚点、方向与连接顺序
  → Expand / 二元连接 / WCOJ
  → 中间结果、资源消耗与尾延迟
```

邻接存储让“从已知节点找邻居”变得便宜，但它不会自动解决超级节点、相关性、环和变长路径带来的组合爆炸。真正高质量的图数据库内核，需要存储结构、统计信息、代价搜索和执行算法彼此配合。

对使用者而言，最有价值的调优原则也很朴素：找到选择性强的锚点，沿低扇出方向扩展，让约束尽早生效，确认业务是否真的需要枚举所有路径，并从执行计划中定位第一次基数失真。只盯着最终返回了多少行，往往看不见数据库已经为那 12 行结果走过了 800 万条中间记录。
