一个负责技术调研的 Agent 接到任务：找出支持某项架构选择的论文，比较方案，生成一份有来源的报告。它可能很快写出流畅但证据不足的结论，也可能搜索几十次、反复修改计划，最后仍没有解决最关键的分歧。

两种结果都暴露出同一个设计问题：系统需要决定每一步投入多少计算、获取什么信息，以及什么证据足以支持下一步行动。

本文围绕一个目标展开：**在明确的成本、时间和执行约束内，提高 Agent 完成任务的概率。** 推理长度、调用次数和 Agent 数量都是可调手段；最终需要观察任务是否完成，以及为此付出了多少资源。

研究为这些选择提供了依据。《AI Agents That Matter》强调将成本纳入 Agent 评估；关于推理时计算扩展的研究讨论如何按问题难度分配预算；ReAct、Reflexion 和 LATS 则分别探索行动反馈、跨尝试反思和搜索的作用。[7](#ref-7) [8](#ref-8) [1](#ref-1) [4](#ref-4) [3](#ref-3)

本文以“检索论文并生成有来源的技术报告”为贯穿案例。涉及阈值、状态结构、控制策略和实验流程的部分是工程建议；教学数字是人为构造的示例。论文中的实验结果只在对应模型、数据集和环境下成立。

## 一、先定义目标：效率与质量应放在同一张表里

### 1. 推理效率有多个维度

一次任务的账单可以按以下口径拆分：

```text
总成本 = 全部模型调用成本
       + 工具和环境成本
       + 验证与重试成本

端到端延迟 = 任务开始到交付结果的实际墙钟时间
```

模型调用成本应按实际计费口径记录，覆盖输入、输出、缓存和服务方可观测的推理用量。系统没有暴露的内部计算，不能通过“回答看起来很短”来估计。检索、代码执行、截图、浏览器操作和评判器调用也应计入对应成本。

并行执行时，各调用耗时之和通常不同于端到端延迟。把三个独立搜索并发发出，可以缩短等待，但不会自动减少请求数量。LLMCompiler 将工具调用组织成可调度的依赖关系，为这种优化提供了研究案例。[6](#ref-6)

### 2. 决策质量要落到完成条件

对技术报告任务，可以在开始前规定：关键结论必须有原始来源；论文标题和年份必须核对；研究结果与工程推断必须区分；来源冲突必须保留；证据不足时明确说明。

这些条件比“报告是否专业”更容易验证。其他任务也应定义对应结果：代码修改需要满足行为要求和相关检查；数据查询需要符合字段、过滤和权限条件；外部操作需要获得可确认的执行结果。

一次正确的中间选择未必保证任务成功，一次结果正确也未必说明过程可靠。因此，建议同时记录结果指标和过程指标：

| 维度 | 建议指标 | 用途 |
|---|---|---|
| 完成质量 | 成功率、约束满足率、引用支持率 | 判断交付是否合格 |
| 资源消耗 | 每任务费用、Token、工具次数 | 解释预算花在哪里 |
| 时效 | P50/P95 延迟、超时率 | 观察典型体验与慢任务 |
| 恢复能力 | 可恢复故障后的成功率、重试代价 | 判断纠错是否有效 |
| 稳定性 | 多次运行波动、按任务类型分层的表现 | 避免平均数掩盖局部退化 |

### 3. 用约束和帕累托前沿组织比较

可以把产品目标写成：在平均成本、尾延迟和硬性约束满足要求的条件下，最大化任务成功率。涉及必须遵守的执行边界时，应直接作为可行动作约束，避免用一个加权分数抵消违规。

如果方案 A 成本更低、质量也不差，方案 B 就没有明显优势；如果 A 更便宜而 B 更可靠，则需要依据产品目标选择。这种比较构成质量与成本的帕累托前沿，也是《AI Agents That Matter》提倡联合评估的核心背景。[7](#ref-7)

另一个有用口径是：

```text
每个成功任务的平均成本 = 所有任务的总成本 / 成功任务数
```

分子包含失败与重试的消耗。例如，100 个任务共花费 200 个成本单位，成功 80 个，则该指标为 2.5。它不同于“只统计成功样本的平均账单”。当成功数为零时，应报告指标不可用，而不是给出一个正常均值。

## 二、先观察执行轨迹，再决定优化什么

假设调研 Agent 用了 18 次搜索、5 次提纲修改和 3 次自我评审。这个数字本身无法说明哪里浪费。真正需要检查的是：每次行动解决了什么未知问题，怎样改变了后续决策。

建议记录任务、步骤、模型和工具的版本，调用的开始与结束时间，输入输出用量，行动目的，证据引用，结果状态，以及停止原因。决策依据可保存为简短结构化摘要；没有必要把完整内部思考过程作为可观测性的前提。

可以用下面这张诊断表读轨迹。它是工程分析框架，并非论文给出的通用故障分类。

| 观察到的现象 | 待检验的原因 | 优先尝试的干预 |
|---|---|---|
| 同一问题多次搜索，来源高度重合 | 没有记录检索结果或未解决问题 | 保存证据索引，明确下一次查询目的 |
| 计划反复改写，事实没有增加 | 缺少完成条件或执行反馈 | 先定义子任务产物，再执行验证 |
| 多个独立请求依次等待 | 调度器没有表达依赖关系 | 对独立读操作并发调度 |
| 文章越长，关键限定条件越模糊 | 状态压缩丢失了条件或出处 | 分离事实、推断与待确认项 |
| 反思后只修改表达，错误仍在 | 缺少外部信号 | 引入规则、测试或原始来源 |
| 成功率上升，但整体费用倍增 | 增益集中在少数难题，所有任务却都升级 | 按任务和步骤分配预算 |

诊断应考虑任务分布。简单检索题、跨来源比较题和证据冲突题可以使用不同策略。先在轨迹中找到成本集中和失败集中的位置，再决定是改路由、改工具，还是增加推理。

## 三、自适应推理：每次加算力都要有明确用途

### 1. 额外计算可以花在不同地方

更长的单条推理、更多独立候选、更深的搜索、更多环境交互和更强的验证器，会产生不同成本。它们解决的问题也不同。

Snell 等人的研究比较了推理时计算分配策略，并发现最优分配与题目难度和已有模型能力有关。其主要实验对象是数学推理，不能直接把结果转换为浏览器 Agent 的固定预算公式。[8](#ref-8)

对于调研任务，缺少一篇论文的实验条件时，打开论文通常比继续推测更有针对性；已有几组互相冲突的证据时，可能需要比较定义与数据范围；对格式明确的引用列表，则可以直接执行结构化检查。这些选择需要根据当前缺口做出。

### 2. 将预算分配拆成任务级和步骤级

任务级路由可以参考是否需要外部信息、依赖深度、验收难度以及错误后果，选择初始模型、工具范围和预算档位。

步骤级路由则根据观察更新预算。例如，读到论文摘要后可以继续获取方法和实验部分；发现引用不支持结论时，可以重新检索；多个独立检查已经通过时，可以结束该子任务。

| 当前状态 | 建议动作 | 再次评估的条件 |
|---|---|---|
| 输入完整、结果可直接验证 | 执行短路径 | 检查失败时升级 |
| 缺少关键外部事实 | 定向检索或读原文 | 得到足够信息或检索无进展 |
| 多条可行路线，走错代价较高 | 生成少量候选并比较 | 找到有证据支持的行动 |
| 关键结论存在冲突 | 交叉核对来源、定义与时间 | 冲突解释清楚或标为未解决 |
| 工具连续失败 | 诊断权限、参数、服务状态 | 出现新条件后再尝试 |
| 完成条件已经通过 | 交付结果 | 不再自动追加润色循环 |

这张表是策略起点。具体阈值要用任务集校准，不能假设模型口头给出的“90% 确信”已经具备统计意义。若使用置信分数路由，需要检查分数与实际正确率的关系，并在分布变化时重新评估。

### 3. 用边际收益解释继续推理的条件

一个便于设计的决策准则是：

```text
继续计算的预期收益
= 预期减少的任务损失
- 新增计算成本
- 新增延迟代价
```

这些量在真实系统中并不可直接获得。工程上可以按任务类型统计“追加一次检索”“升级一次模型”“再做一次验证”的平均收益，形成策略表，再用新日志修正。

例如，关键结论缺少来源时，一次定向检索可能改变报告是否合格；所有事实均已核验后，再让模型泛泛地“想得更深入”，则没有同样明确的目标。

同时要为整个循环设置费用、时间、工具次数和连续无进展次数的上限。用于最后验证和交付的预算应提前保留。预算耗尽时应输出已完成内容和未解决项，不能把“被迫停止”记为成功。

2026 年的 SR²AM 研究将模拟规划、自调节和反应式执行分开，并通过训练学习何时规划、规划多深。它为这种控制思路提供了新的研究实例，但方法包含监督学习和强化学习，不能简化为给现有模型增加一句提示词就能复现。[11](#ref-11)

## 四、规划与搜索：让每一步都对应可检查的状态变化

### 1. 从可验收的子目标开始

“先深入理解，再广泛研究，最后认真总结”难以指导调度。更有效的计划可以写成：列出待回答问题；为每个问题寻找原始来源；提取研究条件和结果；解释冲突；生成报告；检查引用是否支持对应结论。

每一步都有输入、输出和完成条件。计划也可以据此表达依赖：多个研究问题可以并行检索，跨论文比较必须等待相关证据，最终结论检查必须等待报告初稿。

建议详细规划近期步骤，给远期步骤保留调整空间。新观察改变假设、子目标失败或工具不可用时，再重新规划。每轮都重写完整计划会产生额外成本，是否必要应由任务状态变化决定。

### 2. 根据问题结构选择 ReAct、ToT 或 LATS

ReAct 将推理与行动交替组织，行动提供外部观察，再影响后续计划。论文在问答、事实核查和交互任务中评估了这一模式。[1](#ref-1)

Tree of Thoughts 将中间思路作为可探索的单位，允许生成多个分支、评估和回退。原论文的代表任务包括 24 点、创意写作和迷你填字；它展示了搜索的作用，也提醒我们关注任务是否能够定义有用的中间评价。[2](#ref-2)

LATS 进一步将蒙特卡洛树搜索、语言模型价值评估、反思和环境反馈结合，覆盖编程、交互问答、网页导航和数学等实验场景。[3](#ref-3)

| 方法 | 主要增加的能力 | 采用前需要回答的问题 |
|---|---|---|
| ReAct | 用观察不断修正下一步 | 工具结果是否可靠，如何识别无进展循环？ |
| ToT | 比较和回退多个中间方案 | 分支价值是否可评估，搜索是否值得成本？ |
| LATS | 将搜索与环境反馈结合 | 环境能否重置，分支是否可安全执行？ |

调研报告可以探索几组检索词和论证结构，再基于证据筛选。对于会产生真实外部影响的行动，分支搜索需要在模拟环境、只读环境或草稿状态中进行。执行层应明确哪些动作可探索、可回退，哪些只能在满足执行条件后提交。

### 3. 搜索质量受评估能力约束

生成十个方案以后，仍然需要选择最终方案。如果评估器无法判断引用是否支持结论，就可能偏好更长、更流畅的文字。

因此，工程上应先问“候选之间怎样比较”，再决定生成多少候选。能执行测试的代码任务、能检查约束的结构化任务，具有明确的部分验证手段；开放式报告则需要把评价拆成事实支持、覆盖范围、冲突处理和表达质量。

树搜索还应限制分支数与深度，并缓存已经评估过的状态。当新增分支与已有方案高度相似时，应检查搜索是否仍有新信息，而不是只观察候选数量。

## 五、工具与上下文：降低获取信息和维护状态的开销

### 1. 按依赖调度工具

假设调研需要独立核对 ReAct、Reflexion 和 LLMCompiler 三篇论文，可以并发读取。若下一步是比较三者的实验范围，就需要等待这些结果。

LLMCompiler 通过规划器和执行调度机制组织并行函数调用，说明工具并行是可以独立于长篇自然语言推理优化的系统环节。[6](#ref-6)

落地时建议同时设置最大并发数、单调用超时和任务总截止时间。一个来源失败，应单独记录并决定是否替换来源；不能因为其他请求成功而把整组结果标为完整。取消尚未开始的工作也不同于撤销已经提交的外部操作。

缓存适合在明确条件下复用结果。缓存键应覆盖参数、数据版本、身份或权限范围等会改变输出的因素。固定版本论文正文与实时库存查询的有效期显然不同；是否复用要由数据语义决定。

### 2. 用结构化状态承接上下文

完整会话记录适合归档，但下一步决策通常只需要部分信息。建议分开保存当前状态、外部证据和历史执行日志。

下面是报告任务的一个状态示例，字段属于本文的工程设计：

```json
{
  "goal": "比较三种 Agent 推理优化方案",
  "acceptance": ["关键结论有原始来源", "明确实验适用范围"],
  "confirmed_facts": [
    {
      "claim": "某研究在指定基准评估了并行工具调用",
      "source_id": "paper-06",
      "locator": "实验设置章节",
      "scope": "该论文的模型与工具配置"
    }
  ],
  "open_questions": ["论文的费用统计是否包含计划生成"],
  "completed_steps": ["来源定位", "标题年份核对"],
  "next_action": "读取费用统计方法",
  "stop_reason": null
}
```

关键设计是保留出处和限定条件。把“在指定实验环境下更快”压缩成“这种架构更快”，会扩大结论；把尚未解决的冲突写进事实列表，则会影响后续决策。

### 3. 压缩之后仍然要能够回到原文

AgentFold 研究面向长程网页任务的主动上下文管理，在探索过程中折叠历史，并保留所需信息。论文方法包含相应训练；直接对历史做摘要，只能视为借鉴设计思路，不能宣称得到同等能力。[10](#ref-10)

工程上可以将近期操作保留在工作上下文中，把稳定事实写入证据表，把原始材料存入可检索的记录。压缩前后应抽查关键约束、数值、失败原因和证据定位是否保留。

跨任务经验也要区分稳定规则和临时状态。“这个接口曾经超时”不能永久升级为“以后不要调用这个接口”。经验条目应记录适用条件、发生时间与失效条件，否则一次异常可能持续改变未来决策。

## 六、验证与反思：让纠错建立在反馈之上

### 1. 自我检查需要明确检查对象

Reflexion 利用任务反馈生成反思，并通过情景记忆影响后续尝试。它可以使用不同来源的反馈，并不要求更新模型权重。[4](#ref-4)

《Large Language Models Cannot Self-Correct Reasoning Yet》则研究缺少外部反馈的内在自我纠错，发现在其模型和推理任务设置中，自我纠错可能失败，甚至降低表现。该结论描述的是特定实验条件，不能据此断言所有模型在所有任务中都无法自我修正。[5](#ref-5)

这两类研究提示我们先检查反馈来源。对报告任务，反馈可以是某条结论找不到支持段落、年份与原文不符、比较对象采用了不同的数据集。这样的信息能够指向具体修正。笼统地要求“重新检查一下”，缺少同样清晰的诊断目标。

### 2. 按验证能力分层

建议把验证分成三层：

| 层次 | 示例 | 能够确认什么 |
|---|---|---|
| 确定性检查 | 字段完整、类型正确、引用编号存在、数值重算一致 | 已编码的规则是否满足 |
| 环境检查 | 测试运行结果、接口返回、页面实际状态 | 在所观察环境中的执行结果 |
| 语义检查 | 结论是否被来源支持、方案是否遗漏关键条件 | 需要判断的内容质量，仍需校准 |

每层都有边界。链接存在不代表支持对应结论；测试通过不代表覆盖全部需求；另一个模型认同也不等于获得了独立真值。建议用规则和环境结果检查可确定部分，再让语义评判处理剩余问题，并通过人工标注样本检查其误判。

论文《Scaling Test-time Compute for LLM Agents》研究了并行采样、顺序修订、验证与结果合并，强调反思时机和候选多样性的重要性。这支持把“何时触发反思”作为独立实验变量，而非默认每一步都追加反思。[9](#ref-9)

### 3. 给反思设置触发条件和退出条件

可以把验证失败、关键证据冲突、重复动作无进展和工具状态异常设为触发信号。反思输出只需回答四件事：已知失败是什么；现有证据支持什么原因；下一步如何检验；满足什么条件后恢复执行或停止。

不同错误应选择不同动作。参数错误可以修正参数；权限不足需要满足权限条件；暂时性服务故障可以有限重试；证据不足需要继续检索；目标理解错误需要重新解释任务。反复调用同一个失败工具不能替代诊断。

每次重试还应说明相对上次有什么变化。若输入、证据、环境和策略都没有改变，重试是否值得执行应有明确理由。连续无进展达到上限时，交付局部结果与失败说明。

## 七、多 Agent：先评估分工价值，再承担协调成本

多 Agent 可以提供独立候选、并行子任务和交叉检查，但也引入重复上下文、通信与仲裁开销。对于报告任务，一个可检验的分工是：各执行者负责互不重叠的问题，提交结构化证据，由协调者统一处理冲突。

《Multi-Agent Reasoning Improves Compute Efficiency》比较自一致性、自我修订、多 Agent 辩论和混合方法，在 MMLU-Pro 与 BBH 等推理基准上分析计算预算与准确率的关系。研究发现某些协作配置在匹配预算下具有优势。该论文已收录于 ACL 2026 学生研究研讨会，其结果不能直接视为真实工具执行任务的同等收益。[12](#ref-12)

工程选型可以从下面四种组织方式开始：

| 组织方式 | 适合检验的任务特征 | 必须计入的成本 |
|---|---|---|
| 单 Agent 加工具 | 依赖紧密，状态频繁共享 | 主循环、工具和验证 |
| 并行独立候选 | 存在多个解法，结果可有效筛选 | 所有候选与选择器 |
| 按子任务分工 | 输入边界清晰，可独立推进 | 子任务执行、通信与汇总 |
| 交叉审查 | 有具体可检查的关键结论 | 审查、争议处理与返工 |

评价协作效果时，建议给单 Agent 同样的总预算，并为它配置合理的工具、重试和验证策略。否则，增加预算本身就可能解释部分改进。

多样性也应通过结果观察。同一个模型共享相同材料，可能产生相同的错误；更换角色名称不能保证获得独立证据。可以让执行者检索不同来源、检验不同假设，再检查它们是否实际减少了共同错误。

对于高度依赖共享状态的步骤，协调者应维护唯一的任务状态和证据索引。执行者提交的推断仍需标明来源和条件，避免汇总时将多人认同误当成事实确认。

## 八、把策略组合成可运行的决策循环

上述方法需要一个共同的控制入口：维护任务状态，选择行动，分配预算，执行并验证，然后依据反馈继续或停止。

![Agent 决策循环：围绕共享状态进行预算分配、行动执行、验证与停止判断](/blog-assets/agent-reasoning-efficiency/decision-loop.svg)

图中的“验证未通过”不必总是引发更长推理。它可以导致补充信息、修正参数、替换工具或停止。控制器需要区分这些状态。

下面是用于解释控制关系的伪代码，不对应具体 SDK。真实实现需要由执行层落实超时、并发和资源限制。

```text
state = initialize(task, acceptance_conditions)
ledger = create_budget(cost_limit, deadline, step_limit)
ledger.reserve(final_validation_and_delivery)

while ledger.can_continue():
    observation = inspect(state)
    action = choose_action(observation, calibrated_policy)

    if action is unavailable:
        state.stop_reason = "no_valid_action"
        break

    allocation = estimate_and_cap(action)
    if not ledger.reserve_atomically(allocation):
        state.stop_reason = "budget_limit"
        break

    result = execute_with_limits(action, allocation)
    ledger.settle(allocation, result.actual_usage)
    state = update_state_with_evidence(state, result)
    checks = run_required_checks_within_budget(state, ledger)

    if checks.acceptance_passed:
        state.stop_reason = "acceptance_passed"
        break

    if checks.requires_recovery:
        state = attach_recovery_target(state, checks)

    if state.no_progress_count >= configured_limit:
        state.stop_reason = "no_progress"
        break

if state.stop_reason is unset:
    state.stop_reason = ledger.exhaustion_reason()

return finalize_with_reserved_budget(state, ledger)
```

这里有三项实现约束值得单独说明。

**预算必须覆盖控制器本身。** 路由、候选评估、验证和最终生成都是有成本的工作。并行任务应在发出前原子预留预算，完成后按实际用量结算，避免多个执行者同时读取同一份剩余额度。估算不等于硬上限；如果外部服务不能保证费用上界，需要预留缓冲，并明确预算是软约束还是硬约束。

**停止状态必须可解释。** `acceptance_passed`、`budget_limit`、`no_progress` 和工具不可用代表不同结果。最终生成若修改了已验证的内容，需要使用预留预算再检查变更；未经检查的新增结论不能沿用此前的成功标记。

**状态更新必须依据可观察结果。** 工具请求超时可能意味着结果未知，而非确定未执行。控制器应先核对实际状态，再决定重试。这个区分直接影响后续行动是否正确。

可以从规则路由实现第一版控制器。后续若训练路由器，需要准备包含任务状态、备选动作、资源消耗和结果的轨迹，并通过可控实验补充不同动作的反事实比较。只记录最终成功轨迹，无法判断其他预算策略是否更好。SR²AM 提供了训练自调节机制的研究方向，但训练成本和收益仍要结合自己的任务分布评估。[11](#ref-11)

## 九、实验设计：把“看起来更好”变成可检查的结论

### 1. 建立基线与独立验收集

建议基线采用清晰的单 Agent 工具循环，固定模型版本、提示词、工具说明、验收规则和预算。基线应具备任务所需的基本能力，便于判断改进来自哪里。

任务集可覆盖直接查找、多来源比较、关键证据缺失、来源冲突、工具故障和长程任务。开发集用于调阈值与策略，保留集用于最终验收。避免围绕同一批例子反复优化后，再用它们报告泛化能力。《AI Agents That Matter》对成本、保留集和评测标准化的讨论为这种设计提供了依据。[7](#ref-7)

数据量应根据任务多样性、基线波动和希望识别的差异规划。对同一道题重复运行很多次，有助于观察随机性，但不能替代覆盖不同业务情境。

### 2. 同时做累加实验与消融实验

可以按下表逐步加入机制，观察组合表现：

| 版本 | 改动 | 主要检验的问题 |
|---|---|---|
| A | 基线 | 当前质量、费用和延迟是多少？ |
| B | 自适应预算 | 简单任务是否节省资源，难题是否得到帮助？ |
| C | 工具并行与合适的缓存 | 延迟和重复调用是否下降？ |
| D | 结构化状态与可回溯压缩 | 长任务是否减少遗漏与重复检索？ |
| E | 外部验证与条件反思 | 错误修复收益是否覆盖额外成本？ |
| F | 按需分工或交叉审查 | 相同总预算下是否进一步改善？ |

累加顺序会影响观察结果，所以还应针对关键机制做单独加入和移除实验。例如，在同一强基线上分别启用预算路由与状态管理，再检查两者组合是否有额外收益。

公平比较至少包括两组视角：固定预算比较质量，以及达到相近质量时比较费用和延迟。模型、评判器、工具和缓存条件都需要记录；若更换了基础模型，就应明确这是另一项变量。

### 3. 报告完整口径和不确定性

建议报告任务数、每任务运行次数、成功率、费用分布、P50/P95 延迟、失败类型和按难度分层的结果。超时、无法判断和预算耗尽都要进入报告，不能只保留成功样本。

重复尝试的成功率要对应实际产品策略。如果线上只执行一次，不能把离线多次运行中最好的一次当作线上表现；如果线上允许重试，需要把尝试次数、结果选择与全部成本纳入评估。

分析时建议使用同一任务上的配对结果，并给出与抽样结构相匹配的不确定性估计。存在同一任务多次运行时，需要保留任务内相关性。若方案只在特定任务类型上改善，也应按该范围描述结论。

对模型评判器，要固定版本、隐藏方案身份，并使用人工核验样本检查误判。对检索类任务，可以使用固定网页快照进行可复现实验，再用真实网络任务观察外部变化下的表现。两组数据分别报告，避免混淆环境稳定性与策略能力。

### 4. 用一个教学例子检查决策

假设两种方案各完成同一组 100 个任务，每个任务只运行一次，得到以下**人为构造的数字**：

| 方案 | 成功任务 | 全部任务总成本 | 每个成功任务平均成本 | P95 延迟 |
|---|---:|---:|---:|---:|
| 基础方案 | 80 | 200 单位 | 2.50 单位 | 60 秒 |
| 条件验证方案 | 86 | 215 单位 | 2.50 单位 | 75 秒 |

新方案的观察成功率增加了 6 个百分点，成功任务成本相同，但尾延迟上升。是否采用，要看产品对质量和延迟的要求，也要查看配对差异与不确定性。

仅凭这张汇总表，无法判断改进是否稳定，无法知道新增成功是否集中在某类任务，也无法排除其他任务退化。下一步应查看哪些任务从失败变成功、哪些从成功变失败，再定位机制。

## 十、落地顺序：先补齐观察与反馈，再增加决策复杂度

第一阶段建议建立完成条件、预算账本和执行轨迹，得到可复现的基线。这个阶段的产物应是一份能够解释主要失败和成本来源的报告。

第二阶段优先处理明确的重复开销：消除重复查询，调度独立工具调用，完善工具参数，保留关键状态，限制无进展循环。每项改动都应能在轨迹中找到对应证据。

第三阶段针对高频失败增加验证与恢复路径。例如，报告经常扩大论文结论，就加入来源支持检查；数据任务经常漏字段，就加入结构化校验。先确定检查能发现什么，再设计触发反思的条件。

第四阶段再评估自适应模型路由、候选搜索和多 Agent 分工。让这些机制主要覆盖已识别的困难区域，并在固定预算下与强基线比较。如果调用规模足以摊薄训练成本，也可以进一步研究学习式路由与规划控制。

每轮优化建议留下四项结果：哪类任务发生了变化；改变成功率的证据是什么；完整成本和延迟如何变化；下一轮要检验哪个尚未解决的假设。这样，优化过程本身也具备明确的状态、反馈和停止条件。
