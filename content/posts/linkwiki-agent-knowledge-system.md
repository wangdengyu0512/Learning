# LinkWiki：为 AI Agent 构建可链接、可追溯、可持续演化的知识系统

很多 AI 知识库都从同一条流水线开始：解析文档、切分文本、生成向量、写入索引，然后在用户提问时召回几个片段交给大模型。

这条路线很适合快速搭建问答系统，却不天然擅长处理长期知识：

- 十份资料都在讨论同一个概念，应该生成十份摘要，还是合并成一个稳定页面？
- 新资料到来后，应该追加一页、更新旧页，还是保留两个版本？
- 两个来源发生冲突时，系统应该相信谁？
- Agent 如何先了解知识库结构，再决定需要阅读什么？
- 一次任务中发现的新知识，能否沉淀下来供后续任务复用？
- 人工修订过的内容，如何避免在下一次自动生成时被覆盖？

这些问题已经超出了“检索几个相关 Chunk”的范围。它们要求系统理解知识的身份、边界、来源、关系、版本和生命周期。

**LinkWiki** 就是面向这类问题的一种知识组织方式：它把分散的文档、网页、代码、会议记录和业务数据，整理为一组拥有稳定身份、明确用途、相互链接且能够持续更新的知识页面。

如果说传统 RAG 关注的是：

> 这一次提问，应该召回哪些文本？

那么 LinkWiki 更关注的是：

> 这些资料应该被沉淀成什么知识，它们之间是什么关系，未来又该如何继续更新？

本文将从定义、原理、数据模型、处理流程、实际应用和 Agent 集成六个方面，完整拆解 LinkWiki。

---

## 一、什么是 LinkWiki

LinkWiki 可以定义为：

> **一种以语义页面为知识单元、以显式链接为关系骨架、以原始来源为事实依据，并支持增量编译和 Agent 导航的知识系统。**

这个定义包含五个关键词。

### 1. 语义页面

LinkWiki 的基本单元不是固定长度的文本片段，而是围绕一个稳定主题组织的页面。

一页可以对应：

- 一个实体，例如某个系统、产品、组织或项目；
- 一个概念，例如事件驱动、幂等性或上下文工程；
- 一种方法，例如故障排查、部署或数据迁移流程；
- 一组比较，例如两种技术方案的差异与取舍；
- 一项分析，例如针对某个问题形成的跨来源结论。

每页都应该回答一个清晰、可长期复用的问题，而不是简单对应一份输入文件。

### 2. 显式链接

页面之间的关系不只依赖向量相似度，而是通过链接明确表达：

```text
订单服务 ──depends_on──> 库存服务
幂等性 ──applies_to──> 消息消费
新版本方案 ──evolved_from──> 旧版本方案
结论 A ──derived_from──> 调研报告
来源甲 ──contradicts──> 来源乙
```

向量相似度只能告诉我们“两个文本可能相关”，显式链接还能说明“为什么相关”。

### 3. 原始来源

LinkWiki 页面不是凭空生成的。重要事实应该能够回到原始文档、代码路径、会议记录、数据表或外部链接。

来源的作用是：

- 支持事实核验；
- 区分事实与推断；
- 处理版本和时间范围；
- 在结论冲突时保留上下文；
- 在知识过期后重新编译。

### 4. 增量编译

LinkWiki 不是一次性生成的静态站点。新资料进入后，系统需要判断：

- 是否已经存在同一主题的页面；
- 应该创建、更新、合并还是保持不变；
- 哪些关系需要新增或失效；
- 导航索引是否需要调整；
- 人工修改是否仍然有效。

因此，LinkWiki 的写入过程更像编译，而不是简单的文本生成。

### 5. Agent 导航

LinkWiki 同时为人和 Agent 服务。

人可以通过目录、标签和页面链接浏览；Agent 则可以通过搜索、读取、关系遍历和来源核验，逐步构建当前任务需要的上下文。

它不是要求 Agent 一次读取整个知识库，而是让 Agent 能够决定：

- 先看哪个入口；
- 哪些页面可能相关；
- 哪些内容只需要摘要；
- 哪些结论必须回到原始来源验证；
- 什么时候已经获取了足够证据。

## 二、为什么传统 RAG 还不够

LinkWiki 并不是为了取代 RAG。相反，它通常仍然需要全文检索、向量召回和重排序。

问题在于，RAG 主要解决的是查询时的证据定位，而 LinkWiki 还要解决知识写入和长期维护。

### 1. Chunk 是检索单元，不一定是知识单元

一个 Chunk 可能是：

- 半段定义；
- 一个列表的后半部分；
- 同时包含三个主题的段落；
- 脱离标题后无法理解的正文；
- 某次会议中的临时观点；
- 已经失效的旧版本说明。

Chunk 可以被检索，却不一定适合被直接复用。

LinkWiki 会把多个片段重新组织为拥有标题、范围、摘要、正文、来源和关系的知识页面。

### 2. 相似度不能代替关系

“支付服务”和“订单服务”在文本上可能高度相似，但它们究竟是调用关系、上下游关系、替代关系还是共同依赖关系，向量距离无法直接表达。

显式链接能为检索增加结构信息：

```text
找到“支付超时”页面
  ↓
沿 caused_by 查看可能原因
  ↓
沿 handled_by 查看处理模块
  ↓
沿 related_method 查看排查流程
  ↓
沿 source 查看原始事故报告
```

这比单次相似度搜索更接近真实的问题解决过程。

### 3. 单次问答不会自然形成长期知识

传统问答流程通常是：

```text
问题 → 检索 → 回答 → 会话结束
```

即使 Agent 在本次任务中完成了高质量分析，结论也可能只存在于会话记录中。下一次任务仍然要重新检索和推理。

LinkWiki 增加了一条知识沉淀路径：

```text
问题 → 检索 → 分析 → 形成候选知识
                        ↓
                 核验、去重、链接
                        ↓
                 更新长期知识页面
```

### 4. 知识冲突需要治理，而不是交给模型临场猜测

同一个主题可能同时存在：

- 旧版本与新版本；
- 官方说明与实际代码行为；
- 不同部门的口径；
- 多次会议中的不同决策；
- 事实与个人判断。

如果系统只把所有片段一起召回，生成模型只能在回答时临场选择。更可靠的方式，是在知识写入阶段就记录：

- 来源；
- 时间；
- 适用范围；
- 版本；
- 可信度；
- 冲突关系；
- 当前采用的解释。

### 5. 长期知识必须可编辑

一个只能通过重新生成修改的知识库，很难被团队真正信任。

LinkWiki 页面应该允许人工修订，并区分：

- 来源直接支持的事实；
- 模型生成的解释；
- 人工补充的业务上下文；
- 尚待验证的推断；
- 已经废弃但需要保留的历史说明。

这使知识库从“模型输出展示层”变成可共同维护的工作空间。

## 三、LinkWiki 的核心组成

一个完整的 LinkWiki 通常包含七类核心对象。

### 1. Source：原始来源

Source 是未经语义重组的事实材料，例如：

- Markdown、PDF、Word；
- 网页与在线文档；
- Git 仓库和代码文件；
- 数据库记录；
- 聊天和会议记录；
- 工单、日志和事故报告；
- API 返回的数据。

Source 应尽量保持只读。知识页面可以重新生成，但原始证据不能被生成过程悄悄修改。

一个来源至少需要记录：

```text
source_id
source_type
uri
version
created_at
updated_at
owner
access_scope
content_hash
```

### 2. Page：语义页面

Page 是 LinkWiki 的主要知识单元。

一个页面可以使用类似的数据模型：

```ts
interface WikiPage {
  id: string;
  slug: string;
  title: string;
  type: "entity" | "concept" | "method" | "comparison" | "analysis" | "summary";
  description: string;
  body: string;
  aliases: string[];
  tags: string[];
  sourceRefs: SourceRef[];
  version: number;
  status: "draft" | "active" | "deprecated";
  createdAt: string;
  updatedAt: string;
}
```

其中 `description` 不只是页面摘要，还承担检索路由作用：Agent 可以先阅读描述，再决定是否加载完整正文。

### 3. Link：页面关系

Link 用于连接两个页面或页面与来源。

```ts
interface WikiLink {
  from: string;
  to: string;
  type: string;
  description?: string;
  weight?: number;
  evidence?: SourceRef[];
  validFrom?: string;
  validTo?: string;
}
```

常见关系包括：

| 关系 | 含义 |
| --- | --- |
| `related_to` | 一般相关 |
| `belongs_to` | 属于某个系统或分类 |
| `depends_on` | 依赖目标对象 |
| `implements` | 实现某个概念或接口 |
| `derived_from` | 由某个来源或结论推导 |
| `caused_by` | 由目标对象导致 |
| `contradicts` | 两者存在冲突 |
| `evolved_from` | 从旧版本或旧方案演化而来 |
| `applies_to` | 某方法、规则适用于目标对象 |
| `supersedes` | 当前页面或版本替代旧内容 |

关系类型不宜无限扩张。第一版只需要覆盖最有用、最容易理解和验证的关系。

### 4. Index：导航索引

Index 是知识空间的入口，不负责重复页面正文，而负责告诉读者：

- 这个知识空间覆盖什么；
- 有哪些主要主题；
- 哪些页面是关键入口；
- 不同页面之间如何分组；
- 新用户应该从哪里开始。

可以把它理解为 LinkWiki 的路由表。

### 5. Catalog：页面目录

Catalog 是面向机器的页面清单，通常包含：

```text
page_id
canonical_title
aliases
page_type
path
summary
status
version
updated_at
```

编译新资料前，系统需要先查询 Catalog，避免重复创建已有主题。

### 6. Compiler：知识编译器

Compiler 负责把来源转化为页面、链接和更新操作。

它不只是调用一次大模型，而是一条包含调查、规划、生成和校验的流水线。

### 7. Retriever：检索与导航器

Retriever 同时支持：

- 关键词搜索；
- 向量搜索；
- 元数据过滤；
- 页面摘要检索；
- 目录浏览；
- 链接扩展；
- 来源回溯；
- 混合召回和重排序。

它的目标不是一次返回最多内容，而是帮助 Agent 用最小上下文成本找到足够证据。

## 四、LinkWiki 的基本原理

LinkWiki 的实现可以归纳为六条核心原理。

### 原理一：来源是证据，不天然等于页面

假设输入目录中有：

```text
2026-09-01-架构会议.md
2026-09-08-架构会议.md
支付系统设计-v1.pdf
支付系统设计-v2.pdf
支付故障复盘.md
```

最简单的做法是生成五篇摘要，但更合理的页面可能是：

```text
entity/支付系统.md
concept/支付幂等.md
concept/支付状态机.md
method/支付超时排查.md
analysis/支付架构演进.md
```

原始文件只是证据载体，页面应该围绕长期问题组织。

### 原理二：先识别知识身份，再生成内容

创建页面前，系统必须回答：

- 这个主题是否已经存在？
- 当前名称是不是别名？
- 它和已有页面是同一个对象，还是同名不同物？
- 新资料描述的是当前版本，还是历史版本？
- 应该更新原页面，还是创建带限定词的新页面？

例如：

```text
Postgres
PostgreSQL
PG
```

通常应该归一到一个规范主题；但：

```text
Gateway：API 网关
Gateway：支付渠道网关
```

则可能是两个不同实体。

因此，页面匹配不能只比较标题字符串，还需要结合类型、别名、上下文、时间和关系。

### 原理三：页面必须具有单一主要用途

一页内容如果同时介绍系统、解释概念、提供操作步骤、比较方案并给出趋势分析，后续检索和更新都会变得困难。

更好的方式是拆成多页：

```text
系统是什么       → entity
机制为什么成立   → concept
具体怎么操作     → method
两个方案如何选择 → comparison
跨来源结论是什么 → analysis
```

单一用途不等于内容很短，而是页面始终围绕同一个主要读者问题。

### 原理四：链接是有语义的边

普通 Markdown 链接只能表达“跳转到另一页”。结构化 Link 还应该包含：

- 关系类型；
- 关系方向；
- 简短解释；
- 证据；
- 权重；
- 生效时间。

这样才能支持关系检索、反向链接、图谱展示和自动校验。

### 原理五：事实、推断和未知必须分开

一个高质量页面应该区分：

```text
事实：来源明确表达或代码可以直接证明的内容
推断：基于多个事实形成的解释
未知：当前来源无法回答的问题
冲突：多个来源给出不同结论
决策：团队在特定时间选择的方案
```

否则，模型非常容易把合理推断写成确定事实。

### 原理六：增量更新优先于全量重写

知识库每次更新都全量重写，会造成：

- 人工内容丢失；
- 页面路径频繁变化；
- 无意义的文本改写；
- 链接失效；
- 审计困难；
- 版本噪声。

编译器应该输出明确操作：

```text
CREATE     创建新页面
UPDATE     更新已有页面
LINK       新增或更新关系
DEPRECATE  标记旧页面或旧版本失效
NOOP       输入没有带来有效变化
REVIEW     存在冲突，需要人工确认
```

## 五、LinkWiki 的完整处理流程

从一批原始资料到可供 Agent 使用的知识网络，通常要经过九个阶段。

```text
来源接入
  ↓
解析与标准化
  ↓
来源调查
  ↓
主题抽取与归一
  ↓
页面规划
  ↓
页面与链接生成
  ↓
确定性校验
  ↓
发布与索引
  ↓
增量维护
```

下面逐步展开。

### 阶段一：来源接入

首先把外部资料接入统一的来源层。

不同来源需要不同连接器：

```text
文件系统连接器
网页抓取连接器
Git 连接器
数据库连接器
消息连接器
文档平台连接器
对象存储连接器
```

接入时不要急着生成 Wiki，而应先保存来源元数据、访问权限和内容版本。

### 阶段二：解析与标准化

不同格式要被转化成统一的可读表示：

```text
PDF       → 页面、段落、表格、图片说明
Word      → 标题层级、正文、表格
HTML      → 主体内容、标题、链接
代码仓库  → 文件、符号、依赖、配置、测试
会议记录  → 时间、参与人、议题、结论、行动项
数据库    → 记录、字段、主键、更新时间
```

这一阶段尽量采用确定性解析。能够用解析器得到的结构，不要全部交给大模型猜测。

### 阶段三：来源调查

编译器需要先了解输入，而不是立即逐文件生成页面。

调查内容包括：

- 来源类型和数量；
- 时间范围；
- 版本关系；
- 权威程度；
- 主题覆盖；
- 重复资料；
- 明显冲突；
- 信息缺口；
- 权限边界。

这一步相当于建立编译上下文。

### 阶段四：主题抽取与归一

系统从资料中提取候选：

- 实体；
- 概念；
- 方法；
- 可比较对象；
- 分析问题；
- 关系；
- 别名；
- 来源引用。

然后与现有 Catalog 进行匹配：

```text
候选主题
  ↓
标题、别名与关键词初筛
  ↓
语义相似度召回已有页面
  ↓
类型、范围、时间、关系复核
  ↓
得到 canonical page_id 或创建建议
```

### 阶段五：页面规划

在真正生成内容前，先产生页面计划：

```json
{
  "action": "update",
  "pageId": "concept-payment-idempotency",
  "type": "concept",
  "title": "支付幂等",
  "purpose": "解释支付请求重复到达时如何避免重复扣款",
  "sources": ["source-12", "source-18"],
  "relations": [
    {"to": "entity-payment-service", "type": "applies_to"}
  ]
}
```

页面计划让系统在生成正文前先解决“写什么、写到哪里、和谁关联”。

### 阶段六：页面与链接生成

生成页面时应该遵循稳定模板，但不要强迫每页出现无意义的空章节。

概念页通常包含：

```text
定义与边界
工作机制
适用场景
限制与权衡
与相关概念的区别
来源
```

方法页通常包含：

```text
使用时机
前置条件
执行步骤
判断分支
验证方式
失败模式
来源
```

分析页通常包含：

```text
问题
证据范围
假设
分析过程
结论
反例与不确定性
来源
```

链接生成必须保守。只有在关系能够得到来源或正文支持时才创建，不要为了让图谱看起来丰富而发明边。

### 阶段七：确定性校验

大模型生成结果不能直接写入生产知识库。需要经过确定性校验：

- 页面 ID 和路径是否合法；
- 标题、类型、描述是否完整；
- 是否存在重复页面；
- 来源引用是否真实存在；
- 链接端点是否存在；
- 是否出现自链接；
- 是否有重复关系；
- 页面大小是否超限；
- 是否包含敏感信息；
- 当前用户是否有权读取来源和写入目标；
- 更新是否会覆盖人工保护区。

可以把生成结果视为 Draft，把校验后的操作视为 Commit Plan。

### 阶段八：发布与索引

校验通过后再提交：

```text
写入页面
更新版本号
写入链接和反向链接
刷新 Catalog
更新导航 Index
生成全文索引
生成向量索引
记录编译任务与变更日志
```

页面正文、结构化关系和检索索引是三种不同表示，应该分别维护。

### 阶段九：增量维护

来源变化后，不必重建整个 Wiki。

可以根据：

- 来源内容哈希；
- 页面到来源的依赖关系；
- 主题影响范围；
- 页面更新时间；
- 关系变化；
- 人工审核状态；

只重新编译受影响的页面。

这与增量构建系统很相似：来源是输入，页面是产物，来源引用和链接共同构成依赖图。

## 六、LinkWiki 如何组织检索

LinkWiki 的检索不应该只有一个 `search(query)` 接口，而应提供多种互补方式。

### 1. 导航检索

Agent 先读取知识空间的 Index 或目录：

```text
知识空间
├── 核心系统
├── 业务概念
├── 操作方法
├── 架构决策
└── 故障案例
```

适合问题范围还不明确、需要先建立领域地图的场景。

### 2. 关键词检索

适合：

- 精确术语；
- 类名、接口名和配置项；
- 错误码；
- 人名、项目名和产品名；
- 日志中的固定文本。

### 3. 向量检索

适合：

- 用户表达和页面术语不一致；
- 查询是自然语言描述；
- 需要发现语义相近的概念；
- 不知道准确关键词。

### 4. 元数据过滤

常用过滤条件包括：

```text
page_type
workspace
tag
owner
status
version
updated_at
access_scope
source_type
```

### 5. 关系扩展

找到核心页面后，沿链接展开：

```text
当前页面
  ├─ depends_on
  ├─ caused_by
  ├─ related_method
  ├─ contradicts
  └─ source
```

关系扩展不宜无限递归。通常限制在一到两跳，并根据关系类型和权重筛选。

### 6. 来源回溯

当任务需要高可信答案时，Agent 不能止步于 Wiki 页面，而要继续读取原始来源。

推荐采用三级读取：

```text
L0：标题、类型、描述
L1：页面摘要、关键关系、来源列表
L2：完整页面正文
L3：原始证据片段或原始文件
```

这里的重点不是层级名称，而是渐进加载：先用低成本信息判断相关性，再为关键结论加载更深证据。

### 7. 混合排序

最终排序可以综合：

```text
关键词得分
向量相似度
页面类型权重
目录距离
关系距离
页面质量
来源可信度
更新时间
访问频率
用户反馈
```

例如：

```text
final_score =
  0.30 * semantic_score
+ 0.20 * lexical_score
+ 0.15 * relation_score
+ 0.15 * source_quality
+ 0.10 * freshness
+ 0.10 * page_quality
```

具体权重需要通过实际任务评估，而不是凭感觉固定。

## 七、LinkWiki 如何与 Agent 结合

LinkWiki 真正的价值，不只是让人浏览 Wiki，而是成为 Agent 的外部知识空间。

完整结合需要解决三个问题：

1. Agent 如何读取知识？
2. Agent 如何决定读取多少？
3. Agent 如何把新知识写回去？

### 1. 为 Agent 提供最小工具集

第一版不需要几十个工具。下面这组接口已经能覆盖大多数任务：

```text
wiki.list(path)
wiki.search(query, filters)
wiki.read(page_id, level)
wiki.neighbors(page_id, relation_types)
wiki.sources(page_id)
wiki.read_source(source_id, range)
wiki.propose_update(page_id, patch, evidence)
wiki.compile(source_ids, target_scope, instruction)
```

职责分别是：

| 工具 | 用途 |
| --- | --- |
| `list` | 浏览目录或主题空间 |
| `search` | 关键词、向量或混合搜索 |
| `read` | 按摘要或全文层级读取页面 |
| `neighbors` | 沿结构化关系扩展 |
| `sources` | 查看页面的证据来源 |
| `read_source` | 阅读原始证据 |
| `propose_update` | 提交知识更新建议 |
| `compile` | 从一组来源触发知识编译 |

生产环境中，读取工具和写入工具应该使用不同权限。

### 2. Agent 的任务前流程

Agent 接到任务后，不应立刻做一次全库搜索。

更稳健的顺序是：

```text
理解问题
  ↓
判断所属知识空间
  ↓
读取 Index 或搜索页面描述
  ↓
形成候选页面列表
  ↓
加载少量页面摘要
  ↓
决定后续检索计划
```

例如用户问：

> 为什么支付回调偶尔会重复处理？

Agent 可以先定位：

```text
entity/支付回调服务
concept/消息重复投递
concept/支付幂等
method/支付回调重复处理排查
analysis/历史重复扣款事故
```

而不是直接把所有包含“支付”“重复”“回调”的 Chunk 放入 Prompt。

### 3. Agent 的任务中流程

任务执行过程中，Agent 可以循环进行：

```text
读取页面
  ↓
发现信息缺口
  ↓
沿链接或搜索补充
  ↓
回到原始来源核验
  ↓
更新当前结论
```

一个简化的伪代码如下：

```python
plan = agent.plan(user_question)

pages = wiki.search(
    query=plan.search_query,
    filters={"workspace": plan.workspace}
)

context = []
for page in pages[:5]:
    overview = wiki.read(page.id, level="summary")
    if agent.is_relevant(overview, plan):
        context.append(overview)

while agent.has_information_gap(context):
    next_action = agent.choose_retrieval_action(context)

    if next_action.type == "read_page":
        context.append(wiki.read(next_action.page_id, level="full"))

    elif next_action.type == "expand_links":
        context.extend(
            wiki.neighbors(
                next_action.page_id,
                relation_types=next_action.relation_types
            )
        )

    elif next_action.type == "verify_source":
        context.append(
            wiki.read_source(
                next_action.source_id,
                next_action.range
            )
        )

answer = agent.answer(user_question, context)
```

### 4. Agent 的任务后流程

任务结束后，不是所有输出都应该写回 LinkWiki。

需要先判断本次是否产生了长期价值：

```text
只是当前任务的临时结果？
  → 不写入长期知识

发现了可复用的新事实或方法？
  → 形成更新建议

修正了已有页面中的错误？
  → 提交带证据的 Patch

产生了跨来源稳定结论？
  → 创建 Analysis 候选页

只是模型的未经验证推测？
  → 保留在会话，不进入正式 Wiki
```

推荐采用“提议—校验—提交”模式：

```text
Agent 提交候选更新
  ↓
检查证据、权限、重复和冲突
  ↓
低风险更新自动提交
高风险更新进入人工审核
  ↓
更新页面、关系和索引
```

不要赋予普通对话 Agent 直接覆盖核心知识页面的权限。

### 5. 将 LinkWiki 接入 Agent 工具协议

LinkWiki 可以通过多种方式接入 Agent：

- HTTP API；
- SDK；
- Function Calling；
- MCP 工具服务；
- 本地 CLI；
- 工作流节点。

如果使用 MCP，可以将服务能力暴露为：

```text
Resources
  wiki://workspace/index
  wiki://page/{page_id}
  wiki://source/{source_id}

Tools
  search_wiki
  read_wiki_page
  list_wiki_neighbors
  read_wiki_source
  propose_wiki_update
  compile_wiki_sources
```

资源适合被读取，工具适合带参数执行检索、编译和更新。

### 6. 给 Agent 明确的使用规则

仅提供工具还不够，还要在 Agent 指令中声明检索纪律。

例如：

```text
回答业务和项目问题前，优先查询 LinkWiki。
先读取索引和页面摘要，再加载完整正文。
涉及版本、数字、接口、制度或事故结论时，必须核验来源。
不要把没有证据的推断写成事实。
发现页面冲突时，同时保留双方观点并说明适用范围。
除非拥有写入权限，否则只提交更新建议，不直接修改正式页面。
```

这些规则可以显著降低 Agent 找到一页内容后过早下结论的问题。

## 八、LinkWiki 与 Agent Memory 的关系

LinkWiki 和 Agent Memory 经常被混用，但二者并不相同。

### Agent Memory 主要保存什么

- 用户偏好；
- 历史交互；
- 任务经验；
- 个性化事实；
- Agent 自身策略；
- 会话之间需要延续的状态。

### LinkWiki 主要保存什么

- 可共享的领域知识；
- 项目和系统说明；
- 业务概念；
- 方法与流程；
- 跨来源分析；
- 具有出处的事实；
- 页面之间的关系。

两者可以配合：

```text
用户记忆：用户负责支付系统，偏好先看故障时间线
                         ↓
Agent 查询 LinkWiki：支付系统、支付事故、排查方法
                         ↓
根据用户偏好组织答案和操作步骤
```

一个实用边界是：

> **Memory 负责“这个 Agent 或用户经历过什么”，LinkWiki 负责“这个领域有哪些可以共享和复用的知识”。**

当然，经过治理后的经验记忆也可以被编译成 LinkWiki。例如，多次排障记录可以归纳为一篇可复用的方法页，但原始会话本身不应该自动变成正式知识。

## 九、LinkWiki 的典型应用场景

### 场景一：代码仓库知识库

输入：

- 源代码；
- README；
- 架构文档；
- 配置文件；
- API Schema；
- 测试；
- 部署脚本；
- Issue 和变更记录。

生成：

```text
实体页：系统、服务、模块、接口、数据表
概念页：架构模式、核心机制、数据流
方法页：构建、部署、扩展、调试
比较页：旧架构与新架构
分析页：关键调用链和技术债
```

Agent 可以用它完成：

- 新成员代码导览；
- 影响范围分析；
- Bug 定位；
- 修改前上下文收集；
- 架构问答；
- 代码评审辅助。

### 场景二：企业内部知识助手

输入：

- 制度；
- 产品手册；
- SOP；
- 业务文档；
- 培训材料；
- 历史问答；
- 工单和案例。

LinkWiki 可以把“按部门和文件夹存放的资料”重组为“按业务主题组织的知识”。

Agent 回答时不仅能给出结论，还能提供：

- 适用制度；
- 操作流程；
- 例外情况；
- 相关角色；
- 原始依据；
- 最近更新时间。

### 场景三：研究资料整理

输入：

- 论文；
- 报告；
- 网页；
- 实验记录；
- 访谈；
- 数据集说明。

输出可以围绕：

- 研究对象；
- 核心概念；
- 方法；
- 争议；
- 对比；
- 跨论文结论；
- 证据缺口。

这比逐篇论文摘要更适合长期研究，因为新论文可以更新已有主题，而不是继续堆叠孤立笔记。

### 场景四：客服与运维

将产品功能、错误码、工单、事故报告和解决步骤编译为 LinkWiki 后，Agent 可以从现象页进入：

```text
现象
  → 可能原因
  → 相关版本
  → 排查方法
  → 解决方案
  → 历史事故
  → 原始工单
```

这种路径比单纯搜索相似工单更容易复用经验。

### 场景五：个人第二大脑

个人可以把：

- 收藏网页；
- 学习笔记；
- 项目记录；
- 读书笔记；
- 会议纪要；
- 灵感草稿；

整理成按主题持续生长的 Wiki。

关键不是自动生成更多笔记，而是减少重复记录，让一个主题能够不断吸收新材料。

## 十、如何实现一个最小可用的 LinkWiki

第一版不需要先构建复杂知识图谱。可以从下面的最小架构开始。

```text
                   ┌──────────────────┐
                   │ Web / Agent / CLI│
                   └────────┬─────────┘
                            │
                   ┌────────▼─────────┐
                   │ LinkWiki API     │
                   └────────┬─────────┘
                            │
       ┌────────────────────┼────────────────────┐
       │                    │                    │
┌──────▼──────┐     ┌───────▼───────┐    ┌──────▼──────┐
│ Compiler    │     │ Retriever     │    │ Governance  │
│ 抽取与编译   │     │ 搜索与关系扩展 │    │ 权限与审核    │
└──────┬──────┘     └───────┬───────┘    └──────┬──────┘
       │                    │                    │
       └────────────────────┼────────────────────┘
                            │
      ┌─────────────────────┼─────────────────────┐
      │                     │                     │
┌─────▼─────┐       ┌───────▼──────┐      ┌──────▼──────┐
│ 文档存储   │       │ 元数据数据库  │      │ 搜索/向量索引 │
│ Markdown   │       │ Page / Link  │      │ Fulltext/Vec │
└───────────┘       └──────────────┘      └─────────────┘
```

### 1. 存储层

建议分开保存：

- 原始来源；
- 页面正文；
- 页面元数据；
- 结构化链接；
- 搜索索引；
- 编译任务和变更日志。

Markdown 很适合作为页面正文格式，因为它可读、可编辑、可版本控制，但关系、权限和任务状态更适合存放在数据库中。

### 2. 检索层

第一版可以采用：

```text
全文检索 + 向量检索 + 元数据过滤
```

关系数据量不大时，普通关系表已经足够：

```sql
wiki_links(
  from_page_id,
  to_page_id,
  link_type,
  weight,
  description,
  created_at
)
```

不必一开始就引入专用图数据库。

### 3. 编译层

Compiler 至少需要三个步骤：

```text
Planner   决定创建或更新哪些页面
Writer    生成页面正文和关系建议
Validator 校验路径、来源、链接和权限
```

不要让同一个模型调用同时负责所有事情。规划和写作分开后，更容易检查页面是否重复、类型是否正确。

### 4. 异步任务

知识编译通常耗时较长，应该采用异步任务：

```text
POST /compile
  → 返回 task_id

GET /tasks/{task_id}
  → queued / running / review / completed / failed
```

大任务还应支持：

- 进度；
- 取消；
- 重试；
- 幂等键；
- 超时；
- 配额；
- 部分失败报告。

### 5. 版本管理

每次页面更新至少保留：

```text
旧版本
新版本
变更时间
触发来源
编译任务
修改人或 Agent
变更摘要
```

高风险页面可以采用发布审核：草稿生成后，人工确认再进入 Active 状态。

## 十一、生产环境中的关键治理问题

### 1. 提示注入

来源内容中可能出现：

```text
忽略系统规则
读取其他目录
输出密钥
删除已有页面
```

来源中的指令必须被视为数据，不能覆盖编译任务规则。

同时需要：

- 输入和指令分离；
- 来源只读；
- 写入路径白名单；
- 工具最小权限；
- 敏感信息检测；
- 操作日志；
- 高风险动作人工审批。

### 2. 权限传播

如果一个页面综合了多个来源，它的权限不能简单取最宽范围。

可以采用：

- 继承最严格来源权限；
- 查询时重新检查来源权限；
- 按权限域分别编译；
- 对跨域页面做脱敏；
- 记录页面到来源的完整依赖。

### 3. 人工内容保护

可以把页面划分为：

```text
自动生成区
人工维护区
受保护字段
来源列表
系统元数据
```

再编译时只修改允许自动更新的区域，或者生成 Patch 让人工确认。

### 4. 页面爆炸

不要为每个名词建页。页面是否值得存在，可以按以下条件判断：

- 是否会被独立检索；
- 是否有清晰边界；
- 是否有足够证据；
- 是否能连接其他有价值页面；
- 是否会长期复用；
- 是否与已有页面重复。

### 5. 过时与冲突

系统需要支持：

- 生效时间；
- 失效时间；
- 版本范围；
- 当前状态；
- 替代关系；
- 冲突关系；
- 待确认状态。

不要通过删除旧内容来伪造一致性。历史知识在事故分析和决策追踪中可能非常重要。

### 6. 成本控制

编译成本主要来自：

- 大量来源读取；
- 主题抽取；
- 与已有页面匹配；
- 页面生成；
- 链接生成；
- 来源验证；
- Embedding 和索引更新。

可以通过以下方式控制：

- 先用规则和小模型筛选；
- 内容哈希跳过未变化来源；
- 只编译受影响主题；
- 页面摘要优先；
- 限制 Agent 迭代次数；
- 缓存页面匹配结果；
- 批量生成 Embedding；
- 将高成本分析放到离线任务。

## 十二、如何评估 LinkWiki

只评价语言是否流畅，会掩盖大多数知识质量问题。

建议从五个层面建立指标。

### 1. 页面质量

- 标题是否规范；
- 页面是否只有一个主要用途；
- 摘要能否支持检索判断；
- 正文是否自洽；
- 是否存在重复主题；
- 是否混淆事实和推断。

### 2. 证据质量

- 关键事实是否有来源；
- 来源是否真实可访问；
- 引用是否准确支持结论；
- 是否保留冲突；
- 是否明确版本和时间范围。

### 3. 链接质量

- 是否存在断链；
- 是否存在自链接；
- 关系类型是否正确；
- 链接是否有证据；
- 关键页面是否成为孤立节点；
- 一到两跳扩展是否带来有用信息。

### 4. 增量质量

- 相同输入重复编译是否稳定；
- 新资料是否更新了正确页面；
- 是否产生重复页面；
- 是否误删人工内容；
- 过时页面是否正确标记；
- 导航索引是否同步更新。

### 5. Agent 任务效果

- 找到正确页面的比例；
- 平均工具调用次数；
- 获取足够证据所需 Token；
- 回答的事实正确率；
- 来源引用准确率；
- 复杂任务完成率；
- 相比普通 RAG 是否减少重复检索；
- 是否能够正确拒答未知问题。

可以建立一组真实任务作为回归集，例如：

```text
定位某个接口的调用链
解释某项制度的适用范围
根据历史事故给出排查步骤
比较两个版本的架构变化
核验某个数字的原始来源
判断两个页面是否描述同一实体
```

每次更换模型、Prompt、Embedding 或页面策略，都运行同一批任务。

## 十三、常见错误做法

### 错误一：一个来源对应一个页面

结果是 Wiki 退化成摘要目录，跨来源知识无法合并。

### 错误二：只生成正文，不维护 Catalog

下一次编译无法判断页面是否已经存在，重复内容会快速增长。

### 错误三：只在 Markdown 中插链接

缺少结构化关系后，很难实现反向链接、关系过滤、图谱查询和完整性检查。

### 错误四：允许 Agent 直接覆盖正式页面

没有 Draft、Validator、权限和变更记录，任何一次模型错误都可能污染长期知识。

### 错误五：把所有关系都交给模型发明

图谱看起来很丰富，但大量边没有证据，最终会误导检索。

### 错误六：只保留最终结论

没有原始来源、时间和冲突信息，知识库无法审计，也无法在新证据到来时重新判断。

### 错误七：把 LinkWiki 当成向量数据库替代品

LinkWiki 仍然需要搜索和向量召回。它增加的是稳定知识单元、关系、来源和更新机制，而不是取消底层检索。

### 错误八：所有 Agent 共享同样的写权限

读取、提交建议、编译和正式发布应该是不同权限。大多数 Agent 只需要读取和提交候选更新。

## 十四、一个可落地的演进路线

如果要在现有 RAG 系统上逐步建设 LinkWiki，可以分四个阶段。

### 阶段一：从 Chunk 增加 Page

先保留现有向量检索，同时引入语义页面：

- 页面标题；
- 页面类型；
- 一句话描述；
- 正文；
- 来源列表；
- 页面版本。

目标是让知识拥有稳定身份。

### 阶段二：增加 Catalog 和增量更新

建设页面目录和匹配机制：

- 别名；
- Canonical ID；
- 创建、更新和不变判断；
- 变更记录；
- 人工内容保护。

目标是让知识可以长期维护。

### 阶段三：增加结构化链接

从少量高价值关系开始：

```text
belongs_to
depends_on
derived_from
contradicts
evolved_from
applies_to
```

目标是让 Agent 可以沿关系导航。

### 阶段四：形成 Agent 读写闭环

为 Agent 提供：

- 搜索；
- 分层读取；
- 关系扩展；
- 来源核验；
- 更新建议；
- 异步编译。

目标是让任务执行产生的稳定知识可以经过治理后反哺知识库。

这个演进顺序比一开始建设庞大知识图谱更稳健，因为每一步都能独立产生价值。

---

## 十五、总结：LinkWiki 是知识的长期运行时

LinkWiki 的核心不是 Wiki 页面，也不是大模型自动写文档，而是建立一套完整的知识生命周期：

```text
来源进入
  ↓
解析与调查
  ↓
主题抽取和身份归一
  ↓
页面与关系规划
  ↓
内容生成
  ↓
来源、权限和链接校验
  ↓
发布与索引
  ↓
Agent 检索、导航和核验
  ↓
形成候选更新
  ↓
增量编译和持续演化
```

它和传统 RAG 最大的区别，是把知识从匿名片段提升为具有稳定身份的页面，并让页面之间拥有明确关系。

它和普通 Wiki 最大的区别，是将语义抽取、增量编译、混合检索、来源追踪和 Agent 工具调用纳入同一套系统。

它和 Agent Memory 最大的区别，是强调可共享、可验证的领域知识，而不是某个用户或某个 Agent 的个性化经历。

最终，LinkWiki 希望解决的是一个长期问题：

> 当资料越来越多、版本不断变化、Agent 持续参与工作时，如何让知识不只是被搜索一次，而是能够被理解、连接、验证、更新并反复利用？

当页面拥有稳定身份，结论能够回到来源，关系可以被机器遍历，更新经过确定性校验，Agent 就不再只是从文档中临时寻找答案，而是开始在一套持续生长的知识系统中工作。
