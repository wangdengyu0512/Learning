准备 AI 应用开发岗位时，最危险的状态不是“完全不会”，而是每个名词都见过，却说不清它们之间的边界：记忆和 RAG 有什么区别？ReAct 与普通工具调用差在哪里？LangChain 和 LangGraph 是替代关系吗？可插拔 RAG 算不算热更新？Skill、MCP、Function Calling 又分别解决什么问题？

我把目录《腾讯 AI 应用开发一面 · 逐题参考答案》里的起点、记忆系统、Agent 架构、Skill 机制、工程落地、算法题和自测内容重新整理成这篇博客。它不是把 15 个答案机械拼在一起，而是尝试找出这些问题共享的工程主线。

> **资料边界**：原目录中的框架版本、行业动态与基准数据，以 **2026 年 6 月** 为事实基线。本文写于 **2026 年 10 月 7 日**，重点是整理原资料中的机制与判断方法，不把其中的生态清单宣称为本文发布日期的实时状态。

## 先看全局：这 15 道题到底在考什么

题目可以分成五组：

| 主题 | 题号 | 核心问题 |
| --- | --- | --- |
| 记忆系统 | Q1、Q2、Q5 | 什么信息以什么形式进入上下文，并如何跨会话保留与召回 |
| Agent 架构 | Q3、Q4、Q6、Q12 | Agent 按什么控制流行动，何时需要循环、多 Agent 与持久化运行时 |
| Skill 机制 | Q7、Q8 | 如何把流程知识做成按需加载、可版本化的工程资产 |
| 工程落地 | Q9、Q10、Q11、Q13 | 如何创建、配置、切换、部署和运行真实系统 |
| 算法题 | Q14、Q15 | 能否识别状态、不变量与转移，而不是只背模板 |

看似分散的题目，其实都围绕三个约束展开：

- **上下文窗口是稀缺资源**：不能把所有历史、工具定义、知识和流程永久塞进 Prompt。
- **模型是概率组件**：流程边界、状态持久化、权限、重试和终止条件必须由外部系统兜底。
- **架构选择必须服从任务形状**：步骤固定就用工作流，步骤未知才用 Agent；单一实现就不要过度抽象，存在真实变化点才引入工厂与策略。

其中 Q4、Q9、Q12 尤其像三道“边界题”：

- ReAct 的循环思想，不等于某种固定 Prompt 格式；
- 配置热更新，不等于代码热更新；
- LangChain 的高层 API，不等于 LangGraph 的底层运行时。

回答这类题时，最有效的结构不是先背定义，而是：**先下结论，再画边界，最后说明代价与适用条件。**

## 第一部分：记忆系统不是“找个数据库存聊天记录”

### Q1：记忆模块的数据存在哪种介质上？

面试官真正想听的，不是某个数据库名字，而是你是否理解：**记忆是一组不同查询需求对应的分层存储。**

第一层先区分上下文内与上下文外：

- 上下文窗口是工作记忆，模型本轮推理可以直接读取，但容量有限、按 token 计费，而且不会天然跨会话保存。
- 外部存储是长期记忆，需要显式写入，并在未来某次推理前被检索、筛选和重新注入上下文。

第二层再按记忆类型选介质：

| 记忆或状态 | 合适介质 | 擅长什么 | 主要代价 |
| --- | --- | --- | --- |
| 指令、规范、偏好、SOP | 文件 / Markdown | 整体读取、版本管理、人工审计 | 不擅长语义召回，文件过大时上下文成本高 |
| 历史片段、语义事实 | 向量库 | 语义相似检索 | 难以表达精确结构与多跳关系 |
| 用户画像、会话状态、检查点 | 关系型数据库 / KV | 精确查询、事务、明确 schema | 不擅长开放式语义检索 |
| 实体、关系、时间演化 | 知识图谱 | 关系遍历、多跳查询 | 写入前要抽取实体和关系，复杂度与延迟更高 |

高质量回答一定要补一句：**生产系统通常是组合使用，而不是四选一。**

例如，一个客服 Agent 可以把系统规范放在文件中，把会员等级放在 PostgreSQL，把历史投诉片段放在向量库，把“用户—订单—商家—产品”的关联放在图谱中。选型依据不是流行度，而是未来要回答哪类查询。

这里还有一个常见辨析：记忆和 RAG 的检索技术可能相似，但二者的主要分界在写入路径。

- RAG 通常把外部文档经过解析、切分和索引后导入知识库。
- 记忆通常从交互过程中自动抽取事实、偏好、事件和状态。

一句可直接口述的话是：

> 上下文窗口是易失的工作记忆，跨会话内容必须进入外部存储；外部存储按查询类型分工，程序性知识放文件，语义片段进向量库，结构化状态进数据库或 KV，多跳关系进图谱，真实系统通常采用混合架构。

### Q2：如何跨会话压缩对话并保留关键信息？

不能把“压缩”简单理解为让模型写一段摘要。更完整的答案可以分成四档：

1. **滑动窗口**：只保留最近 N 轮，最便宜，但早期关键信息可能直接消失。
2. **递归摘要**：旧消息离开窗口前压成滚动摘要，后续再把新内容合并进去。
3. **结构化事实抽取**：把对话转成原子事实、用户画像、任务状态和关键决策，写入外部记忆。
4. **分层换入换出**：上下文只保留当前活跃信息，其余信息在外部存储中分页，需要时通过检索或工具调用换回。

真正困难的不是“怎么缩短”，而是“保留什么”。一个实用准则是：

> **决策与事实留下，重复表达、中间尝试和已经被否决的过程性 token 丢掉。**

因此，好的压缩结果至少应保留：

- 当前任务目标与约束；
- 已确认的用户偏好；
- 已做出的关键决策及其原因；
- 当前文件、资源或业务状态；
- 未完成事项与下一步；
- 最近一次关键工具结果。

而下面这些内容通常可以降权或删除：

- 重复问答；
- 已被推翻的候选方案；
- 大段可重新获取的工具原始输出；
- 对最终状态没有贡献的中间推理文本。

结构化事实写入还需要冲突消解。面对一条新事实，系统不应该永远只做 append，而应判断：

- `ADD`：这是一个全新的事实；
- `UPDATE`：它修正了旧事实；
- `DELETE`：它使旧事实失效；
- `NOOP`：它只是重复或没有长期价值。

这样可以避免长期记忆变成一个互相矛盾、无限增长的日志垃圾场。

### Q5：用户今天问 A，三天后问 B，系统如何关联？

跨会话关联的核心不是“把全部历史聊天再塞回去”，而是建立稳定的身份、写入与检索链路：

```text
Day 0：用户问 A
  → 识别 user_id / tenant_id
  → 抽取事实、实体、偏好与事件
  → 写入语义记忆、情景记忆或结构化画像

Day 3：用户问 B
  → 以 user_id 限定检索边界
  → 使用向量、关键词、时间与实体等多信号召回
  → 过滤过期、冲突和低相关内容
  → 将少量证据注入上下文
  → 生成与 A 相关联的回答
```

这里至少有四个关键点：

- `session_id` 管单次会话，`user_id` 管跨会话身份，不要混为一谈；
- 记忆沉淀应发生在 A 结束时，而不是等 B 出现后临时翻原始日志；
- 检索不应只依赖向量相似度，还可以组合 BM25、实体匹配、时间衰减和业务过滤；
- 事实存在有效期，用户可能搬家、换公司或改变偏好，因此要支持更新、失效和审计。

如果 A 与 B 字面上毫不相似，但共享同一个实体或存在关系链，知识图谱或实体链接就比纯向量检索更有优势。

最终可以把这三道记忆题收束成一句话：

> 记忆系统的本质不是“存更多”，而是在写入时提炼，在存储时分层，在检索时受身份和时间约束，最后只把当前决策真正需要的信息放回上下文。

## 第二部分：Agent 架构的核心是显式控制流

### Q3：FSM 状态机由哪些部分组成？如何实现？

有限状态机的形式定义是五元组：

- `Q`：状态集合；
- `Σ`：输入或事件集合；
- `δ`：状态转移函数，`δ(state, event) -> next_state`；
- `q0`：初始状态；
- `F`：终态集合。

工程实现通常还要补两个概念：

- **Guard 条件**：事件到达后，只有条件成立才允许转移；
- **Action 副作用**：进入状态或经过转移边时执行的动作。

Agent 的工具调用循环本身就可以画成状态机：

```text
planning
  ├─ can_answer ─────────────→ answering → done
  └─ need_tool → calling → observing
                         ↑         │
                         └─ need_more
                                   └─ enough → answering
```

最轻量的 Python 实现就是一张转移表：

```python
TRANSITIONS = {
    ("idle", "user_input"): "planning",
    ("planning", "need_tool"): "calling",
    ("planning", "can_answer"): "answering",
    ("calling", "tool_result"): "observing",
    ("observing", "need_more"): "calling",
    ("observing", "enough"): "answering",
    ("answering", "finish"): "done",
}


def step(state: str, event: str) -> str:
    key = (state, event)
    if key not in TRANSITIONS:
        raise ValueError(f"非法转移: {state} x {event}")
    return TRANSITIONS[key]
```

状态较少时，字典足够清晰；状态与 guard 增多后，可以使用 `Enum + match`；需要层级状态机、回调和状态图导出时，再引入专门状态机库。

面试中不要只说“有状态和转移”。高分点是说明：**状态机把合法路径、非法路径、重试上限和终止状态都变成可测试的显式结构。**

### Q4：为什么选择 ReAct，而不是纯 Chain 或单轮 Tool Use？

这道题的答案不应是“ReAct 更智能”，而应从任务形状出发。

| 任务形状 | 更合适的方式 | 原因 |
| --- | --- | --- |
| 步骤固定、顺序可枚举 | Chain / Workflow | 成本低、行为稳定、容易测试 |
| 只需调用一次外部能力 | 单轮 Tool Use | 没有必要维护循环 |
| 步骤未知，需要根据观察继续决策 | ReAct Loop | 可以在行动后读取结果，再规划下一步 |

ReAct 的核心是一个反复进行的“推理—行动—观察”循环：

```text
Reason：根据当前状态判断下一步
Action：请求调用工具或执行动作
Observation：读取真实结果
Reason：修正计划、重试或收束答案
```

它的收益是动态决策、错误恢复和多步取证；代价则是更高的 token、延迟与失控风险。因此必须配套：

- 最大迭代次数；
- 工具白名单与参数校验；
- 超时、重试和熔断；
- 明确终止条件；
- 对有副作用动作进行审批或幂等保护。

还要指出一个容易混淆的边界：ReAct 是循环架构，不等于必须把 `Thought / Action / Observation` 原样输出成文本。现代模型可以通过原生工具调用表达 Action，由运行时执行并回填 Observation，循环思想仍然成立。

### Q6：多 Agent 框架怎么设计？如何划分 Agent？

多 Agent 不是“把一个 Agent 复制很多份”。设计时可以沿三条轴拆开讨论：

| 设计轴 | 常见选择 |
| --- | --- |
| 拓扑 | Supervisor 星形、Hierarchical 层级、Swarm / Handoff 网状 |
| 协调 | 中心调度、去中心交接、固定编排 |
| 通信 | 共享状态、结构化消息、事件或任务队列 |

真正决定是否拆 Agent 的，通常是下面四种边界：

- **上下文边界**：不同子任务需要独立上下文，避免互相污染；
- **职责边界**：研究、编码、审查、发布等角色有清晰目标；
- **工具与权限边界**：不同角色只能访问自己的工具和数据；
- **模型能力与成本边界**：高难规划使用强模型，机械执行使用便宜模型。

上下文隔离往往是最有说服力的拆分理由。一个研究子 Agent 可以独立阅读大量资料，只把结构化结论返回协调者，而不把全部搜索过程污染主 Agent 的上下文。

但多 Agent 会引入新的问题：

- 任务分派错误；
- 重复劳动；
- Agent 之间循环交接；
- 共享状态冲突；
- token 与延迟放大；
- 故障定位变难。

因此，步骤固定、强耦合、共享状态很多的任务，通常应该留在单 Agent 或普通工作流中。多 Agent 的判断标准不是“听起来更先进”，而是：**并行与隔离带来的收益，是否大于协调成本。**

### Q12：LangChain 和 LangGraph 有什么区别？

把二者说成竞争对手，通常说明分层没有理解清楚。

- LangChain 更接近高层开发接口：模型、Prompt、工具、检索器、Agent 构建器与中间件，适合快速搭建标准能力。
- LangGraph 更接近有状态工作流运行时：节点、边、条件分支、循环、共享状态、检查点、中断恢复与人工介入。

最重要的边界是：

> **高层 Agent API 可以构建在 LangGraph 运行时之上；一个解决“方便地创建”，一个解决“可靠地运行复杂控制流”。**

选型可以这样回答：

- 标准工具调用 Agent：优先使用高层 Agent API；
- 固定、无循环的数据处理：使用普通链或工作流；
- 需要条件边、循环、断点续跑、人工审批、长时运行：下沉到 LangGraph；
- 只有在复杂性真实存在时才暴露底层图，不要为了“用了图”而把简单任务图化。

`checkpointer` 是这道题的加分点。它把每一步共享状态按 `thread_id` 等键持久化，使流程可以在进程重启后继续，也可以在人工确认点暂停。裸 ReAct 循环如果没有外部检查点，进程终止后通常只能从头再来。

## 第三部分：Skill 是程序性知识的工程化载体

### Q7：Skill 是什么？编码 Agent 的 Skill 如何工作？

一个 Agent Skill 可以理解为一个“技能包”目录：

```text
pdf-form-filler/
├─ SKILL.md
├─ scripts/
│  ├─ inspect.py
│  └─ validate.py
├─ references/
│  └─ field-mapping.md
└─ templates/
   └─ output.json
```

核心文件 `SKILL.md` 通常由两部分组成：

- YAML frontmatter：至少包含 `name` 与 `description`；
- Markdown 正文：描述操作步骤、约束、检查清单和失败处理。

它的关键机制不是“又一段长 Prompt”，而是**渐进式披露**：

1. Discovery：启动时只加载所有 Skill 的名称与描述，形成轻量索引；
2. Activation：任务与描述匹配后，才读取被命中的完整 `SKILL.md`；
3. Execution：按照正文按需读取参考文件、调用工具或运行脚本，脚本代码留在执行环境，只把结果返回上下文。

一个编码 Skill 的典型流程是：

```text
用户请求
  → description 匹配或显式调用
  → 加载 SKILL.md
  → 按 SOP 检查仓库与约束
  → 调用工具、修改代码、运行测试
  → 按验收清单复核
  → 交付结果
```

如果面试题中的“Auto-coder Skill”没有明确指向某个具体产品，正确做法不是假装知道，而是先说明自己按通用 Agent Skill 机制回答，并向面试官确认所指。能主动消除歧义，本身就是工程严谨性的体现。

### Q8：Skill 的核心价值是什么？为什么会出现？

Skill 主要解决两个问题。

第一是**上下文经济**。如果每种流程说明、模板、脚本和参考资料都永久塞在 system prompt 中，上下文会快速膨胀，而且大量内容与当前任务无关。Skill 通过索引化与按需加载，让上下文只承载当前真正需要的规程。

第二是**知识资产化**。团队经验不再散落在某个人的 Prompt、聊天记录或口头传授中，而是变成可以：

- 版本控制；
- Code Review；
- 测试与验收；
- 分发与复用；
- 回滚与审计；
- 持续迭代。

Skill、RAG、MCP、工具调用和微调解决的是不同问题：

| 机制 | 主要回答什么 |
| --- | --- |
| Skill | 应该按什么流程做，即 know-how |
| RAG | 当前需要哪些外部事实 |
| MCP | 如何标准化连接外部系统与能力 |
| Function Calling | 这一次具体调用哪个工具、传什么参数 |
| Fine-tuning | 如何改变模型较稳定的行为模式与能力分布 |

一句最好记的关系是：

> **Skill 定流程，MCP 连系统，Tool 执行动作，RAG 补事实。**

评审规范、发布流程、故障排查手册这类每月都会更新的 SOP，通常比微调更适合做成 Skill；事实型知识库更适合 RAG；数据库、浏览器、工单系统等连接问题则属于 MCP 或具体工具层。

## 第四部分：从概念正确走向可部署、可切换、可维护

### Q9：可插拔 RAG、一键配置切换，算不算热更新？

结论先行：**通常属于配置热更新，不属于代码热更新。**

两者的边界如下：

| 类型 | 变化内容 | 是否需要新代码进入进程 |
| --- | --- | --- |
| 配置热更新 | 参数变化，或在已加载实现集合中切换 | 不需要 |
| 代码热更新 | 新增实现类、替换方法逻辑或加载新模块 | 需要 |

一个可插拔 RAG 通常由策略接口、注册表和工厂组成：BM25、向量检索、混合检索与不同重排器都已经加载到进程中，配置只决定当前选择哪一套组合。

完整链路应该是：

```text
配置中心发布新配置
  → 客户端 watch 收到变化
  → 校验配置与依赖
  → 工厂创建新的 RAG pipeline
  → 预热连接、模型与索引
  → 原子替换当前引用
  → 旧实例继续服务在途请求
  → drain 完成后释放旧资源
```

高分回答要继续说明生产细节：

- 新配置先校验，创建失败时保留旧实例；
- 支持灰度发布，不要一次推全量；
- 保留配置版本和一键回滚；
- 在途请求继续持有旧引用，避免切换瞬间被中断；
- 新增检索策略仍需正常发版，因为它超出了“已加载实现集合”。

因此，“页面上一键切换”只是操作入口，真正的工程能力在后面的创建、预热、原子切换、优雅释放与回滚链路。

### Q10：工厂模式的优点是什么？

工厂模式解决的是“对象应该怎么创建”，不是“对象运行时应该执行哪种算法”。它的主要价值包括：

- 创建与使用解耦，调用方只依赖抽象接口；
- 新增实现时尽量不修改已有调用代码，符合开闭原则；
- 高层模块依赖抽象而非具体类，符合依赖倒置；
- 鉴权、默认参数、连接池、重试等创建逻辑集中收口；
- 测试时更容易替换为 mock 或 fake 实现。

在 LLM 应用里，模型 Provider、Embedding、Retriever、Reranker 和存储后端都很适合用工厂创建。例如：

```python
_REGISTRY: dict[str, type["Retriever"]] = {}


def register(name: str):
    def wrapper(cls):
        _REGISTRY[name] = cls
        return cls
    return wrapper


@register("bm25")
class BM25Retriever:
    pass


@register("vector")
class VectorRetriever:
    pass


def create_retriever(config: dict):
    retriever_type = config["type"]
    retriever_class = _REGISTRY[retriever_type]
    return retriever_class(**config.get("params", {}))
```

这里还要辨析工厂与策略：

- 工厂负责“创建谁”；
- 策略负责“使用哪种可替换行为”；
- 可插拔 RAG 通常是二者组合：策略接口定义检索行为，工厂根据配置创建具体策略。

也不要滥用模式。如果系统永远只有一个实现、看不到真实变化点，却提前铺三层抽象，得到的只是额外复杂度。

### Q11：本地或私有化部署要考虑什么？配置放在哪里？

回答本地部署时，可以先抓住核心动机：**数据不出域。** 围绕这个目标，再展开完整清单。

| 维度 | 需要回答的问题 |
| --- | --- |
| 模型推理 | 模型、精度、量化、显存、并发、上下文长度和推理引擎如何选 |
| 数据边界 | 文档、向量、日志、对话与备份是否全部留在客户环境 |
| 依赖交付 | 数据库、Redis、向量库、对象存储是否提供离线镜像 |
| 可观测性 | 没有公网 SaaS 时，日志、指标、链路与告警如何内置 |
| 安全合规 | 模型 license、组件许可证、密钥、审计、漏洞修复如何处理 |
| 运维升级 | 离线安装、容量评估、版本升级、数据库迁移和失败回滚怎么做 |

模型显存估算不能只看参数量，还要考虑精度、KV cache、并发与上下文长度。开发机上追求易用性，生产环境更关注批处理、显存利用率、吞吐和稳定性；资源不足时可以考虑量化，但要验证质量损失。

配置管理建议分层回答：

- 本地单机：`.env` 与类型化配置对象；
- 容器或集群：ConfigMap、配置中心或等价的集中配置设施；
- API Key、数据库密码、证书：Secret、Vault 或专门密钥系统；
- 代码仓库：只保留配置模板和默认值，不提交真实密钥。

此外，配置必须有作用域、版本和刷新边界。并非配置中心发生变化，应用内所有单例都会自动重建；需要明确哪些对象支持刷新、谁负责重建、失败时如何回退。

### Q13：第一个项目的后台是怎么搭建的？

这是一道项目经历题，不能只报技术栈。建议使用“场景—决策—结果—反思”的结构：

- 场景：服务什么用户、流量规模、数据量和主要约束是什么；
- 决策：为什么选择某个框架、协议、数据库与部署方式；
- 结果：延迟、QPS、稳定性或成本改善了多少；
- 反思：遇到过什么故障，如何定位并修正。

一个典型 AI 对话后台可以这样组织：

```text
Client
  → API Gateway / Auth
  → FastAPI async API
      ├─ Agent / RAG 编排
      ├─ Model Provider
      ├─ PostgreSQL + pgvector
      ├─ Redis session / cache / lock
      ├─ Object Storage
      └─ Task Queue + Worker
  → SSE 流式返回
```

每个技术选择都要能解释：

- FastAPI + ASGI 适合大量等待模型、数据库和网络 IO 的请求；
- SSE 适合服务端向客户端单向推送 token，比 WebSocket 更轻；
- PostgreSQL 管业务数据，数据规模合适时可用 pgvector 统一向量与业务数据；
- Redis 管会话、缓存、限流或短时状态；
- 文档解析、索引构建等慢任务放进任务队列；
- Docker Compose 适合较小规模交付，规模扩大后再考虑 Kubernetes。

还要主动暴露异步系统的典型坑：如果在 `async` 路由里直接调用阻塞式 SDK，事件循环会被卡住，表现为并发上升后所有请求延迟一起恶化。修复方式是使用真正的异步客户端，或把阻塞调用隔离到线程池。

项目题最有说服力的不是“用了很多组件”，而是一个可验证的结果，例如首 token 延迟、P95 延迟、工具调用成功率或单位请求成本的前后变化。数字必须来自自己的真实经历，不要照抄示例。

### Q14：最长有效括号

这道题的主推解法是栈。关键不是“括号题用栈”这句口诀，而是建立一个不变量：

> 栈中存下标，栈底始终表示最后一个无法参与当前有效区间的位置。

初始化时压入哨兵 `-1`。遇到左括号时压下标；遇到右括号时先弹栈：

- 弹完为空，说明当前右括号没有匹配对象，把它的下标压入，作为新的无效边界；
- 弹完不为空，说明从新栈顶之后到当前位置都是有效区间，长度为 `i - stack[-1]`。

```python
def longest_valid_parentheses(s: str) -> int:
    stack = [-1]
    answer = 0

    for index, char in enumerate(s):
        if char == "(":
            stack.append(index)
            continue

        stack.pop()
        if not stack:
            stack.append(index)
        else:
            answer = max(answer, index - stack[-1])

    return answer
```

复杂度是时间 `O(n)`、空间 `O(n)`。如果追问空间优化，可以给出双向计数法：从左到右统计左右括号，右括号过量时清零；再从右到左对称扫描，补上左括号过量的情况，空间降为 `O(1)`。

如果追问动态规划，可以定义 `dp[i]` 为“以下标 i 结尾的最长有效括号长度”，再根据 `s[i - 1]` 是左括号还是右括号分别转移。

面试时最佳策略通常是：主写栈法，解释哨兵与不变量，再口述 DP 和双向计数两条备选路线。

### Q15：股票交易系列

正确的第一步不是写代码，而是澄清约束：

- 只允许一次交易？
- 可以交易无限次？
- 最多 k 次？
- 是否有冷冻期或手续费？

不同约束对应不同状态机。

仅一次交易时，一次遍历维护历史最低价：

```python
def max_profit_once(prices: list[int]) -> int:
    min_price = float("inf")
    answer = 0

    for price in prices:
        min_price = min(min_price, price)
        answer = max(answer, price - min_price)

    return answer
```

允许无限次交易时，可以贪心累加所有正向日差，也可以用两个状态统一表达：

- `hold`：当天结束时持有股票的最大利润；
- `cash`：当天结束时不持股的最大利润。

```python
def max_profit_unlimited(prices: list[int]) -> int:
    hold = float("-inf")
    cash = 0

    for price in prices:
        previous_hold = hold
        previous_cash = cash
        hold = max(previous_hold, previous_cash - price)
        cash = max(previous_cash, previous_hold + price)

    return cash
```

这个状态机的真正价值是扩展性：

| 约束 | 状态如何扩展 |
| --- | --- |
| 最多两次或 k 次 | 增加交易次数维度 |
| 冷冻期 | 增加刚卖出与可买入状态 |
| 手续费 | 在买入或卖出转移中扣除 fee |

股票题与 Agent FSM 看似无关，底层却是同一个抽象：**定义状态，识别事件，写出合法转移，并明确初始态与终态。**

## 把 15 道题压缩成一套面试回答模板

面对系统设计或概念辨析题，可以稳定使用下面的五步：

1. **结论**：先用一句话回答“是什么”或“选哪个”；
2. **边界**：说明它与相邻概念在哪里分开；
3. **机制**：按数据流、状态流或控制流讲实现链路；
4. **取舍**：说明收益、成本、失败模式和不适用场景；
5. **落地**：给出自己项目中的组件、指标或故障案例。

例如回答“为什么使用 ReAct”时：

- 结论：因为任务步骤无法预先枚举，需要根据工具结果继续决策；
- 边界：固定流程用 Chain，单次查询用 Tool Use；
- 机制：Reason → Action → Observation 循环；
- 取舍：能动态修正，但增加 token、延迟和失控风险；
- 落地：设置迭代上限、超时、工具白名单和终止条件。

再例如回答“可插拔 RAG 是否是热更新”时：

- 结论：是配置热更新，不是代码热更新；
- 边界：只能在已加载实现中切换；
- 机制：配置推送 → 工厂重建 → 原子替换 → 旧实例 drain；
- 取舍：切换快，但新增实现仍要发版；
- 落地：灰度、校验、回滚、监控和资源释放。

一旦形成这种回答结构，就不需要逐字背诵长答案。

## 结语

这套题最值得学习的，不是某个框架在某个版本里的 API，而是一组可以迁移的工程判断：

- 先根据查询类型决定记忆介质；
- 先根据任务形状决定 Chain、Tool Use 还是 Agent Loop；
- 先找到上下文、职责和权限边界，再决定是否拆多 Agent；
- 把流程知识做成可版本化资产，而不是继续堆长 Prompt；
- 把模型的不确定性包在显式状态、持久化、权限和回滚机制中；
- 算法题和系统设计题都从状态、不变量、边界与转移开始。

真正成熟的 AI 应用工程师，不是知道最多名词的人，而是能在约束条件下说明：**为什么选它、它解决什么、它不解决什么，以及失败以后系统如何恢复。**
