企业在评估智能体产品时，很容易遇到一个看似简单、实际上比较错位的问题：已经有 WorkBuddy，是否还需要建设企业 AI 底座？

如果只看产品页面，二者都会出现智能体、模型、Skill、连接器、知识、安全、审计和运行等关键词，于是容易得出两个相反但都过于草率的结论：一种认为买了 WorkBuddy 就不再需要底座；另一种认为 WorkBuddy 只是聊天工具，与企业平台建设无关。

问题的关键不是功能名称是否重复，而是它们处于什么层级、管理什么状态、承担什么责任。

本文中的“企业 AI 底座”不是某个厂商的同名产品，而是《[企业级智能体统一底座：从四类断裂面到六项平台能力](/posts/enterprise-agent-unified-foundation)》提出的厂商中立架构。它要求企业统一管理运行、调度、数据、生态、安全和持续进化六项能力，使 Agent 能够进入真实业务系统，受控地执行长任务，并在故障后恢复和验收。

本文的结论先放在前面：

> WorkBuddy 与企业 AI 底座不是同一抽象层级。WorkBuddy 主要是员工侧的 AI 工作台；WorkBuddy Enterprise 是覆盖办公、研发、组织管理和智能体托管的平台产品，与企业 AI 底座有明显交集；企业 AI 底座则是企业为全部智能体、数据和业务执行链路定义的总体架构与治理责任。多数情况下，二者适合形成“总体架构约束产品、产品承载部分能力”的上下层协同，而不是非此即彼。

## 一、先校准比较对象：WorkBuddy 不是一个单一层级

截至 2026 年 10 月 27 日，腾讯公开材料中至少需要区分三个相关对象。

| 对象 | 官方公开定位 | 在本文中的层级 |
| --- | --- | --- |
| WorkBuddy | 覆盖办公、代码开发和设计创意的全场景 AI 办公工作台 | 员工入口、桌面执行环境和生产力应用 |
| WorkBuddy Enterprise | 面向企业的一站式 AI 智能体平台，覆盖研发编码、通用办公、云端托管、统一身份和安全治理 | 组织级 AI 平台产品 |
| WorkBuddy Managed Agents | 云端托管的智能体运行服务 | 产品线中的 Agent 托管运行组件 |

腾讯对 WorkBuddy 的公开描述强调自然语言下达任务、自主拆解规划、工具执行、本地文件读写、领域专家、云端助理和多 Agent 项目空间。[1] 这些能力首先解决的是“员工如何直接使用 AI 完成工作”。用户看到的是任务入口、文件和工具，以及可以交付的文档、表格、代码或分析结果。

WorkBuddy Enterprise 的范围更大。官方页面列出统一身份、组织管理、企业 Skill、企业专家、企业智能体、企业模型配置、安全与操作审计、OpenAPI、连接器，以及共享云、专享和企业私有化等不同形态；文档中心将其定义为面向企业的一站式 AI 智能体平台。[2][3]

Managed Agents 又比普通工作台更靠近运行层。官方称其为云端托管的智能体运行服务，并将它与 WorkBuddy、CodeBuddy 一起放入产品矩阵。[2][4] 这意味着讨论“WorkBuddy 能否替代企业 AI 底座”时，不能只拿个人工作台与总体架构比较，也不能把产品矩阵中的所有能力都默认算进任意版本。

正确的问题应该拆成三层：

1. WorkBuddy 能否作为企业员工统一使用 AI 的工作入口？
2. WorkBuddy Enterprise 能覆盖企业 AI 底座中的哪些公共能力？
3. 对核心业务状态、可靠副作用、异常恢复和企业语义，企业还需要承担哪些不可外包的责任？

## 二、企业 AI 底座解决的不是“有没有 Agent”，而是“Agent 如何进入生产”

工作台关注用户能否方便地下达任务并得到结果；企业 AI 底座关注这些任务进入组织和业务系统后，能否持续、受控、可解释地运行。

前文将企业智能体落地中的问题归纳为四类断裂面：

| 断裂面 | 典型问题 | 底座责任 |
| --- | --- | --- |
| 连接面 | Agent 知道目标，却没有正确身份、通道或工具 | 统一身份、能力契约、系统连接与结果查询 |
| 行为面 | 外部内容被误当成指令，或动作超出授权边界 | 强制授权、审批、隔离、审计和敏感动作保护 |
| 认知面 | 数据含义不一致，经验无法跨任务复用 | 业务事实、语义、本体、规则和分层记忆 |
| 运行面 | 长任务中断，不知道做到哪一步，也不敢直接重试 | 状态持久化、幂等、恢复、终态核验和依赖治理 |

对应的平台能力包括统一运行框架、统一调度管理、统一数据基座、统一生态链接、统一安全管理和统一持续进化。其管理对象不只是提示词和模型，还包括任务状态、执行实例、工具调用、审批凭证、业务回执、知识版本、授权证据和经验资产。

AIOS 将调度、上下文、记忆、存储和访问控制等服务从 Agent 应用抽离到运行内核，为“应用与运行底座需要分层”提供了研究参照。[5] MemGPT 则从上下文窗口限制出发，说明长期交互需要独立的分层记忆和上下文管理机制。[6] 两项研究都采用了操作系统类比，但它们仍只是企业底座的局部参照，不能独自覆盖组织身份、业务语义、交易一致性和监管责任。

因此，企业 AI 底座不是一个更大的聊天页面，也不是简单堆叠模型网关、向量数据库和 Agent 框架。它本质上是一套共同契约：所有受管智能体如何获得身份，如何读取事实，如何申请动作，如何保存进度，如何确认结果，以及如何留下可追溯证据。

## 三、二者的关系：一条路径从员工入口向下，一条路径从企业系统向上

WorkBuddy 的产品路径从知识工作和员工体验出发，再向下补充组织管理、模型、连接器、安全和托管运行。企业 AI 底座的架构路径则从业务系统、数据和治理责任出发，再向上支撑工作台、数字员工和行业应用。

两条路径正在中间汇合，但起点不同。

```text
[员工与业务应用层]
  WorkBuddy 工作台       行业 Agent / 数字员工 / 业务应用
           |                         |
           +-------------+-----------+
                         v
[组织级 Agent 平台层]
  WorkBuddy Enterprise -- Managed Agents
           |              其他自研或第三方 Agent 平台
           +-------------------------+
                         v
[企业 AI 底座共同契约]
  运行与恢复 | 调度与资源 | 数据与语义
  连接与能力契约 | 身份、安全与审计 | 评测与持续进化
                         |
                         v
[企业事实与执行系统]
  办公与协同 | ERP / CRM / SCM / 财务
  生产、设备与现场系统 | 模型、算力与存储
```

图中的“企业 AI 底座共同契约”不一定全部由企业自研。它可以由 WorkBuddy Enterprise、云服务、自研平台和既有中间件共同实现。关键是企业必须明确每项责任由谁承担，并能获得相应的接口、日志、状态和服务承诺。

如果企业主要目标是提高文档、研究、设计、开发和日常协作效率，WorkBuddy 可能已经覆盖最有价值的上层体验。若企业还要让 Agent 修改订单、调整排产、发起付款或处置设备告警，则必须继续回答底层状态与责任问题。

## 四、六项能力逐项映射：有交集，但不能只看功能名称

下面的映射基于腾讯截至核对日的公开产品材料。它表示公开可见的能力交集，不代表完成了产品验收，也不把营销描述转换为技术保证。

| 企业 AI 底座能力 | WorkBuddy 产品线的公开覆盖 | 仍需重点核验的企业责任 |
| --- | --- | --- |
| 统一运行框架 | 自主拆解、工具执行、云端持续任务、多 Agent 项目空间、Managed Agents | 任务状态模型、断点续作、幂等、未知结果处理、补偿和业务终态验收 |
| 统一调度管理 | 云端托管、模型配置、企业 Credit 池、专属服务实例等 | 队列与优先级、资源隔离、容量上限、故障切换、SLA 和成本归因 |
| 统一数据基座 | 本地文件、腾讯文档、知识库、连接器和企业上下文 | 主数据、指标口径、时态事实、数据血缘、本体、冲突处理与失效传播 |
| 统一生态链接 | 腾讯生态原生集成、第三方连接器、OpenAPI、Skill | 能力契约、身份委托、异步回执、接口版本、限流和跨系统事务边界 |
| 统一安全管理 | 统一身份、组织管理、企业安全与操作审计、私有化和网络隔离选项 | 最小权限、审批绑定、数据分类、密钥托管、沙箱、提示注入防护和审计导出 |
| 统一持续进化 | 专家、Skill、流程和项目空间复用，以及组织效能分析 | 离线评测、回归门禁、版本发布、经验准入、灰度、回滚和责任归属 |

这张表最重要的信息不是“有”或“没有”，而是同名能力可能具有不同深度。

例如，“支持连接器”可以只表示 Agent 能调用一个 API，也可以表示平台已经管理身份委托、接口版本、限流、异步回执、去重和终态查询。二者都可以称为连接器，但进入采购、财务和生产系统时，风险完全不同。

同样，“支持长期任务”可能表示任务关闭客户端后仍在云端运行，也可能进一步包括检查点、租约接管、外部副作用核对和跨版本恢复。前者是有价值的用户体验，后者才是关键业务运行时需要验证的工程能力。

## 五、最大边界不在办公任务，而在核心业务闭环

WorkBuddy 公开展示的优势集中在文档、表格、代码、研究、设计、资料整理和办公协同。这些任务当然也可能复杂，但多数成果可以在提交前由人检查，失败后通常可以重新生成，副作用相对可控。

WorkArena 以 ServiceNow 企业软件中的常见知识工作任务评估 Web Agent，WorkArena++ 又将范围扩展到需要规划、检索、计算、逻辑推理和上下文理解的组合式工作流。[7][8] 这类研究说明，知识工作并不等于简单问答或机械点击；工作台要产生实际价值，确实需要规划、工具操作和结果交付能力。同时，它们也提示企业应在真实软件和完整工作流中评估产品，而不是只测试孤立提示词。

企业核心流程不同。采购、订单、库存、排产、财务、设备和客户服务包含持续变化的业务状态。Agent 一旦执行写操作，就可能产生不可简单撤销的后果。

以“识别延期订单，生成并提交交期调整方案”为例，表面上它只是查询数据、分析原因、生成方案和调用接口四步。进入生产后至少还要处理以下问题：

1. 查询期间库存和排产数据发生变化，方案依据的是哪个时间点？
2. 同一订单是否已经被其他人或其他 Agent 调整？
3. 提交接口超时，究竟是失败，还是已经成功但响应丢失？
4. 用户重新点击后，系统如何避免重复提交？
5. 哪些金额、客户等级或交期变化需要人工审批？
6. 审批通过后，执行的是否仍是原方案和原数据版本？
7. 最终应以“接口返回成功”还是“订单、排产和通知均达到目标状态”为完成标准？

这就是“能调用工具”与“可靠完成业务”的差异。

τ-bench 使用领域 API、业务政策和最终数据库状态验收任务，并通过 `pass^k` 衡量 Agent 多次运行的一致性。[12] ToolSandbox 加入状态依赖、信息不足、多轮澄清以及中间和最终里程碑评估。[13] AppWorld 则通过状态测试确认任务结果，同时检查是否产生任务之外的意外修改。[14]

这些研究共同说明，企业不能只验收函数名、参数格式和单次成功演示。至少要区分四层结果：

| 层次 | 要回答的问题 |
| --- | --- |
| 调用成功 | 请求是否到达工具，参数是否通过校验？ |
| 步骤成功 | 该步骤是否产生预期输出？ |
| 任务成功 | 多个步骤是否共同满足用户目标？ |
| 业务终态正确 | 数据库、审批、通知和外部系统是否达到正确且一致的状态？ |

WorkBuddy Enterprise 可能承载这条流程的入口、专家、连接器和托管 Agent，但订单语义、审批规则、状态核验和异常补偿仍需要企业与产品共同设计。采购一个平台不会自动消除业务系统原有的一致性责任。

## 六、工作台的知识能力，不等于企业数据基座

文件读写、知识库检索和连接器访问能够显著提高员工效率，也是 WorkBuddy 的重要价值。但企业数据基座需要处理的对象比“把资料放进上下文”更广。

它至少应区分以下几类信息：

- **任务状态**：当前步骤、等待条件、重试次数、审批和执行回执。
- **业务事实**：订单、客户、设备、物料、合同和指标在特定时间的真实状态。
- **业务语义**：字段含义、对象关系、指标口径、生命周期和约束。
- **正式规则**：权限、政策、阈值、合规要求和审批条件。
- **执行经验**：过去任务中验证有效的方法、失败条件和适用范围。
- **用户偏好**：表达方式、常用模板和非强制性的个性化选择。

这些信息的权威性和生命周期不同。正式规则不能被一次对话随意覆盖，业务事实不能由模型记忆代替，用户偏好也不应获得业务授权的效力。

MemGPT 证明了分层记忆和虚拟上下文对长交互有价值，但它没有替企业定义哪个系统是订单事实源、冲突时谁优先、数据何时失效。[6] CRMArena 把账户、订单、知识文章和工单等相互关联的对象放进专业 CRM 任务，说明 Agent 进入企业工作后，必须理解对象关系并遵守业务规则。[11]

因此，WorkBuddy 的知识、文件和连接器能力可以成为企业数据消费层的重要组成部分，但企业仍需管理事实来源、语义契约、版本、权限和血缘。否则，Agent 可能检索到很多内容，却无法判断哪一条是当前有效、可用于执行的事实。

## 七、云端持续运行，不自动等于可恢复的生产运行时

腾讯公开材料显示，WorkBuddy 的云端助理可以在关闭客户端后继续完成任务，Managed Agents 则被定位为云端托管的智能体运行服务。[1][2][4] 这说明产品线已经明显超出传统聊天助手，开始承担持续执行和托管运行职责。

但对关键业务而言，仍应进一步核验“持续运行”的语义：

1. 任务进度保存在会话文本里，还是结构化检查点中？
2. 执行实例故障后，能否由另一个实例接管？
3. 模型、Skill 或连接器升级后，旧任务按哪个版本继续？
4. 工具超时后，系统会重试、查询结果，还是等待人工确认？
5. 已经产生外部副作用的步骤如何去重？
6. 长时间等待审批或外部事件是否占用执行资源？
7. 最终失败时能否导出完整轨迹、证据和未完成动作？

OSWorld 在真实操作系统、文件和跨应用工作流中进行执行式评估，揭示了桌面 Agent 在 GUI 定位和操作知识上的能力缺口。[9] 2026 年发布的 OSWorld 2.0 又把评估推进到长流程、动态环境、跨来源推理和隐式状态推断；论文观察到 Agent 会丢失约束、忽略任务中途出现的信息、在应该询问时猜测，并跳过验证。[10]

这些结果不能直接代表 WorkBuddy 的表现，因为论文评测的是特定模型和 Agent 实现。但它们给出了合理的采购方法：不要用短演示推断长任务可靠性，而要使用包含中断、状态变化、信息不足和结果核验的真实任务测试。

## 八、多 Agent 是组织方式，不是可靠性保证

WorkBuddy 项目空间公开支持多 Agent 并行推进，把同一目标拆给多个 Agent 并汇总结果。[1] 这种能力适合研究、方案比较、内容生产和可并行的信息处理，也能让团队复用专家、Skill 与连接器。

但是，把一个 Agent 改成多个 Agent 会增加交接点。任务分解错误、角色认知不一致、信息丢失、重复劳动和错误终止都可能随之增加。

《Why Do Multi-Agent LLM Systems Fail?》从多个框架的执行轨迹中归纳出 14 种失败模式，并将其分为系统设计问题、智能体间失配和任务验证三类。[15] 这意味着多 Agent 的验收重点不能只是“是否并行”和“是否最终生成一份汇总”，还应包括：

- 子任务是否覆盖总体目标，是否存在遗漏和重叠；
- 交接时是否保留事实来源、约束和置信度；
- 不同 Agent 发生冲突时由谁裁决；
- 汇总 Agent 是否重新验证，而不是机械拼接；
- 达到预算、时间或质量阈值后如何停止；
- 某个 Agent 失败时能否局部恢复，而不是全任务重做。

多 Agent 项目空间是上层协作体验；统一调度、状态交接、预算控制和验收机制才是底座责任。前者可以由 WorkBuddy 提供，后者需要根据任务重要性验证其实现深度。

## 九、安全治理不能停留在“有权限和审计”

WorkBuddy Enterprise 官方页面公开了统一身份、组织管理、企业安全与操作审计、专属网络访问和企业私有化等选项。[2] 这些能力是企业部署的重要基础，也说明它与普通个人工具存在实质差异。

但 Agent 安全比传统应用多了一层：模型读取到的数据本身可能包含诱导其行动的恶意指令。权限正确并不意味着行为一定正确，因为 Agent 可能在合法权限内执行错误动作。

AgentDojo 在邮件、电子银行和旅行预订等工具环境中评估不可信数据中的提示注入攻击。[17] Agent Security Bench 进一步覆盖系统提示、用户输入、工具使用、记忆检索、记忆投毒和后门等攻击面。[18] 这些研究不证明某个商业产品存在同样缺陷，但说明企业需要把安全控制落实到执行链路，而不是只写在系统提示词中。

对高风险动作，建议至少形成以下控制链：

```text
用户或任务身份
  -> 数据访问授权
  -> 工具与动作授权
  -> 参数和业务规则校验
  -> 必要时人工审批
  -> 隔离环境执行
  -> 结果与副作用核对
  -> 不可抵赖的审计记录
```

采购时需要确认的不只是“是否有审计”，还包括审计能否关联用户、Agent、模型、Skill、工具、参数摘要、审批、业务对象、结果和版本；企业能否导出并保存日志；安全策略由谁配置；被阻断后是否有清晰的申诉和恢复路径。

## 十、哪些能力适合采购，哪些责任必须保留

企业没有必要因为强调底座就把所有组件都自研。成熟产品通常能更快提供员工入口、办公套件集成、模型接入、专家与 Skill 管理、组织账号、托管运行和运营界面。重复建设这些通用能力，成本高且难以形成差异化。

更合理的策略是按责任而不是按软件模块划分“买”和“建”。

| 能力或责任 | 更适合的策略 | 原因 |
| --- | --- | --- |
| 员工 AI 工作入口、文件与办公协同 | 优先采购 | 体验、生态适配和持续迭代成本高 |
| 通用专家、Skill 市场和办公模板 | 优先采购并治理 | 通用性强，但需准入和版本管理 |
| 模型接入、基础托管和通用审计 | 采购为主 | 规模效应明显，可通过合同和接口约束 |
| 企业身份、组织和权限映射 | 与现有 IAM 集成 | 权威身份必须由企业掌握 |
| 核心业务对象、指标和规则 | 企业主导 | 属于业务语义和长期数字资产 |
| 写操作、审批、幂等和补偿 | 企业与平台共同设计 | 责任跨越 Agent 平台和业务系统 |
| 关键任务终态和验收标准 | 企业定义 | 只有业务所有者能定义“真正完成” |
| 风险等级、审计留存和应急处置 | 企业保留最终责任 | 涉及合规、内控和事故责任 |

对于只处理低风险知识工作的场景，可以采用“WorkBuddy 为主、轻量治理”的方式快速推广。对于跨系统但以查询和草拟为主的场景，可以让 WorkBuddy Enterprise 承载入口、专家和连接器，同时增加企业数据与权限适配层。对于会写入 ERP、财务、生产或客户系统的场景，则应把底座契约、状态机和验收机制放在产品之上，不能只依赖自然语言编排。

## 十一、用一组 PoC 问题检验真实边界

产品选型不应只比较功能清单。建议选择一条同时包含查询、分析、写入、审批和异常恢复的真实业务链路，用下表进行 PoC。

| 验收维度 | 测试场景 | 需要留存的证据 |
| --- | --- | --- |
| 身份与权限 | 用户换部门、权限过期、跨租户访问、代办任务 | 身份映射、授权决策、拒绝记录 |
| 数据与语义 | 两个系统数据冲突、规则更新、历史时点查询 | 来源、时间戳、版本、冲突处理结果 |
| 连接器 | 接口限流、版本变化、异步完成、返回未知 | 契约版本、重试策略、结果查询与回执 |
| 长任务恢复 | 客户端关闭、实例退出、模型不可用、网络中断 | 检查点、接管记录、恢复时间、重复副作用检查 |
| 写操作可靠性 | 请求超时后重复提交、审批后数据变化 | 幂等键、审批绑定、终态核验、补偿记录 |
| 多 Agent | 子任务遗漏、结果冲突、某角色失败 | 分解计划、交接证据、裁决和局部恢复记录 |
| 安全 | 文档中夹带提示注入、越权工具调用、敏感数据外发 | 拦截、审批、沙箱和审计日志 |
| 稳定性 | 同一任务重复执行 8 至 20 次并加入扰动 | 完成率、`pass^k`、错误类型和结果差异 |
| 运维 | 模型、Skill、连接器升级后回归 | 版本清单、评测结果、灰度和回滚记录 |
| 成本 | 正常、失败、重试和人工介入分别计费 | Token、Credit、工具、算力和人工成本 |

单次成功不能证明生产可靠性。2026 年的 Agent 可靠性研究建议从一致性、鲁棒性、可预测性和安全性四个维度建立指标，而不是把所有行为压缩成平均成功率。[16] 对企业而言，这四个维度可以翻译为：重复运行是否稳定，输入和环境变化时是否保持目标，失败是否可解释且有界，以及错误是否会造成不可接受的副作用。

PoC 结果还应进入合同和上线门禁。若产品不能暴露任务状态、审计证据或结果查询接口，企业就应降低其可执行动作范围；若只能保证办公内容生成，就不要把它直接放进交易和生产控制链路。

## 十二、最终判断：不是“买还是建”，而是“谁对哪一层负责”

回到最初的问题：博客中的企业 AI 底座和 WorkBuddy 有什么区别？

第一，**目标不同**。WorkBuddy 首先解决员工如何使用 AI 完成办公、研发和创意工作；企业 AI 底座首先解决全部 Agent 如何接入企业系统并被统一治理。

第二，**抽象层级不同**。WorkBuddy 是用户可见的工作台，WorkBuddy Enterprise 是组织级平台产品，Managed Agents 是托管运行组件；企业 AI 底座则是跨产品、跨业务域的目标架构和共同契约。

第三，**责任边界不同**。产品可以提供身份、连接器、托管、审计和部署能力，但企业仍要定义业务事实、语义、审批、终态、风险和事故责任。

第四，**二者存在明显交集**。WorkBuddy Enterprise 已经覆盖企业 AI 底座中的若干平台能力，尤其适合承载员工入口、办公生态、组织能力资产和通用 Agent 运行。把它简单归为“上层聊天工具”是不准确的。

第五，**交集不等于完全替代**。在订单、库存、财务、生产等核心业务中，连接器可用、任务持续运行和界面显示成功，都不能替代幂等、状态恢复、规则执行、业务终态验证与可追溯证据。

因此，更稳妥的企业路线是：用企业 AI 底座定义责任和验收标准，用 WorkBuddy Enterprise 等产品实现其中适合采购的部分，再通过身份、数据、业务能力和运行证据把它接入企业现有体系。

最终需要避免的不是选错某个产品，而是没有分层：把工作台当底座，会低估核心业务责任；把所有能力都归为底座自研，又会错失成熟产品带来的体验和交付速度。真正可持续的架构，是让产品能力能够替换和演进，而企业的业务语义、治理规则与责任边界始终清晰。
