采购 Agent 把十份供应商材料交给模型，用户等了很久才看到第一段结果。另一项任务很快开始输出，却逐字生成得很慢。增加并发之后，显卡更忙了，任务完成时间反而更长。

这几种现象发生在同一个模型服务上，却不一定来自同一个瓶颈。理解它们，需要把一次生成拆成输入处理、逐步解码、排队和外围调用。

**推理性能的目标应当由任务体验和资源约束共同定义。** 本文介绍容量估算与实验方法，使用标准 Transformer 的简化模型。公式和示例不代表任何具体硬件的性能承诺；不同模型结构、推理后端和版本应重新测量。

## 一、一次模型请求经历哪些阶段

```text
请求进入
  → 鉴权、限流与排队
  → 分词和输入准备
  → Prefill：处理输入上下文
  → Decode：逐步生成后续 Token
  → 输出处理与返回
```

对于使用因果注意力和 KV Cache 的自回归模型，Prefill 处理已知输入并建立后续解码所需的缓存；Decode 利用已有状态生成后续 Token。输入处理和解码的并行程度、访存方式与计算需求不同。[1]

长输入可能增加 Prefill 工作量；长输出会延长 Decode 占用。实际服务还包含调度等待、网络传输、分词、内容处理与工具往返，所以用户感知的慢不能只归因于 GPU。

采购任务如果先检索、再调用模型、再查 ERP、最后再次调用模型，完整任务耗时还包括这些串行依赖。优化单次模型请求，不一定等比例缩短业务任务。

## 二、先把“快”拆成可以测量的指标

| 指标 | 本文采用的口径 | 用途 |
| --- | --- | --- |
| TTFT | 客户端发出请求到收到首个内容 Token | 判断开始响应是否及时 |
| 端到端延迟 | 发出请求到完整输出到达 | 判断任务何时完成 |
| TPOT | 首个 Token 后的生成时长除以后续 Token 数 | 描述平均逐 Token 生成速度 |
| ITL | 相邻输出 Token 到达的时间间隔 | 观察生成过程中的停顿 |
| 输出吞吐 | 单位时间内服务完成的输出 Token 数 | 描述聚合生成能力 |
| 有效请求吞吐 | 单位时间内满足质量与延迟要求的完成数 | 连接技术容量与业务体验 |

若一次输出共有 N 个 Token，且 N 大于 1，本文用以下近似口径：

```text
TPOT =（最后一个 Token 到达时间 - 第一个 Token 到达时间）/（N - 1）
```

网络流式分块不一定与 Token 一一对应。测量客户端 ITL 时，应明确是在统计 Token 间隔还是网络块间隔；两者不能混用。外部 API 也可能只暴露部分时间指标。

报告平均值还不够。对于交互体验，需要同时查看中位数和尾部延迟，并保留样本量、请求失败率和超时处理口径。一个很高的 Token 吞吐，可能伴随大量超时任务。

## 三、显存预算至少分成三个部分

```text
显存需求
  ≈ 模型权重
  + KV Cache
  + 激活、临时工作区与运行时开销
```

仅用模型参数量乘以权重精度，只能粗估权重占用，不能判断服务能接多少并发。

例如，假设模型有 80 亿参数，权重按每参数 2 字节存储，原始权重约为 160 亿字节，即约 14.9 GiB。这还没有包含缓存、计算工作区、量化元数据和框架预留。

多卡部署也不能简单将总量除以 GPU 数量。一部分状态可能被切分，一部分被复制，通信与内存布局还有额外成本。需要按所用并行方式和模型结构测量各卡峰值。

## 四、推导 KV Cache 的容量

对一个假设的标准多层注意力模型，如果每层保存 Key 和 Value，缓存的简化估算为：

```text
KV 字节数
  ≈ 2 × 层数 × KV 头数 × 每头维度
      × 已缓存 Token 总数 × 每个元素字节数
```

“已缓存 Token 总数”是所有活动序列的输入与已生成输出占用之和。不能只看请求数：一个 32K 上下文请求和一个 1K 请求的占用差别很大。

假设一个教学模型有 32 层、8 个 KV 头、每头 128 维，缓存使用 2 字节元素，则每 Token 的缓存约为：

```text
2 × 32 × 8 × 128 × 2 = 131072 字节 = 128 KiB
```

当一个序列缓存 8192 个 Token 时，约占 1 GiB。16 条同等长度且未共享缓存的活动序列，原始 KV 占用约为 16 GiB。

这只是简化估算。分块分配、前缀共享、滑动窗口、KV 量化，以及 MLA 等不同注意力结构都会改变计算方式。估算的作用是判断数量级，最终容量仍要以目标模型和后端为准。[1]

## 五、批处理为什么同时影响效率与等待

把多个请求组合执行，可以提高设备利用率。但如果为了凑大批次而等待，请求开始时间会变晚；长请求占据资源时，短请求的尾部延迟也可能恶化。

连续批处理允许服务在生成过程中动态调度活动请求。vLLM 的优化文档讨论了分块 Prefill 与批处理调度参数，说明调度选择需要在输入处理、解码延迟和吞吐之间取舍。[1]

分块 Prefill 可以把长输入拆成较小片段参与调度，但它不意味着每一种工作负载都会更快。较小的分块可能改善其他请求的生成体验，也可能改变长输入自身的完成时间。

调优时应固定请求分布，再逐项改变参数。只用几十个很短的提示测试，无法推导采购长文档分析的容量。

## 六、前缀缓存解决的是重复输入计算

多个请求可能共享系统提示、工具描述或同一份供应商手册。支持前缀缓存的引擎可以在满足匹配条件时复用已计算的前缀状态，减少重复的输入处理。[2]

它不会自动省掉新输出的解码，也不等于“相似文本”都能命中。分词结果、模板顺序、模型和其他配置变化，都可能影响可复用范围。

压测应分别测冷缓存和热缓存，并记录请求之间的前缀相似结构。始终重复同一个问题得到的热缓存结果，不能直接代表真实生产流量。

多租户部署还要核验缓存隔离策略。敏感输入的复用、清理和潜在侧信道应按服务风险控制；不要为了提高命中率，把不该跨租户复用的状态放入同一无边界缓存。

## 七、量化与并行都需要收益验证

降低权重或 KV Cache 的存储精度，可以改变显存占用，但速度收益取决于内核、硬件支持、请求形态和数据转换开销。体积更小，不自动等于每次请求更快。[1]

对于采购任务，不能只比较通用文本质量。还应检查供应商编号、金额、结构化参数和长上下文引用是否发生退化。

| 手段 | 希望改善的约束 | 必须同时检查 |
| --- | --- | --- |
| 权重量化 | 权重显存与带宽占用 | 业务质量、内核支持、实际延迟 |
| KV 量化 | 长上下文缓存容量 | 长文本质量、缓存精度与兼容性 |
| 张量并行 | 单实例模型容量与计算 | 卡间通信、每卡内存、实际吞吐 |
| 数据并行 | 总请求处理能力 | 单副本容量、路由和负载偏斜 |
| 推测解码 | 自回归解码效率 | 候选接受率、额外计算、实现约束 |

每个优化都应与明确的瓶颈对应。模型装不下、缓存不够、排队过长和网络慢，需要不同处理方式。

## 八、用排队视角理解容量拐点

当请求到达速度长期超过处理能力，等待队列会持续增长。即使没有报错，用户也会因等待而超时。

在稳定系统中，Little 定律可写为：

```text
系统内平均请求数 L = 平均到达率 λ × 平均停留时间 W
```

它描述平均量的关系，不能直接推导 P99 延迟，也不适用于无限积压而没有稳定状态的测量窗口。[3]

提高允许并发，可能先提升吞吐，随后让缓存压力和排队明显增长。容量规划应找到满足延迟目标的运行区间，并保留余量，而不是把刚好不崩溃的最大并发作为日常配置。

可以根据输入和输出预算做准入控制，对超长任务采用异步队列，并设置租户配额。超时后要确认请求是否还在服务端占用资源，否则客户端重试可能继续放大负载。

## 九、设计一次可解释的压测

以下是实验方案，不含真实硬件跑分。先记录模型标识、权重版本、后端版本、硬件、精度、并行方式和所有调度参数。

| 维度 | 建议分组 | 需要回答的问题 |
| --- | --- | --- |
| 输入长度 | 短问答、中等材料、长文档 | Prefill 对延迟的影响 |
| 输出长度 | 短结构化结果、长分析 | Decode 对占用的影响 |
| 负载 | 逐步提高到达率与并发 | 容量何时出现拐点 |
| 缓存 | 冷缓存、代表性热缓存 | 优化收益是否依赖重复前缀 |
| 输出方式 | 流式与非流式 | 指标口径是否一致 |
| 质量 | 同一组固定采购任务 | 性能提升是否损害有效完成率 |

固定并发的闭环压测中，请求变慢会降低新请求产生速度，因此可能掩盖外部流量继续到达时的积压。还应使用按计划到达的负载，记录实际发送偏差和排队时间。

每组保存原始请求级记录：输入与输出 Token 数、请求时间、首响应时间、完成时间、错误类型和质量判定。把预热阶段与正式测量分开，并报告测量时长和失败样本。

不要把失败请求静默丢弃后再宣布延迟降低。它们应计入错误率或服务目标失败，并明确是否还产生了计算费用。

## 十、只使用外部 API 时仍能做哪些工作

没有 GPU 也可以建立有效的请求画像：

- 统计每类任务的输入长度、输出长度和串行调用次数。
- 测量客户端 TTFT、端到端延迟、失败率与限流等待。
- 对比上下文裁剪、工具描述压缩和结果缓存的效果。
- 记录每个有效完成任务包含多少次模型请求和重试。
- 将供应商可见指标与客户端指标分开，避免猜测服务端瓶颈。

成本比较应围绕有效任务。一次请求便宜但需要反复修复参数的模型，可能让完整任务更贵。比较时应记录质量门槛、请求计费、人工接管和重试成本，并按使用时的实际价格计算。

## 十一、把调优决策写成实验结论

一份有用的结论可以写成：“在这组采购任务、这个输入长度分布和这个服务版本下，配置 B 满足既定质量门槛，并在目标到达率下改善了尾部延迟；冷缓存长文档仍存在瓶颈。”

这比一个脱离负载条件的 Token 每秒数字更容易复现，也更适合指导部署。服务性能最终要回到具体任务、明确口径和可重复的测量环境。
