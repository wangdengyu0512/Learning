一位线材工程师收到一份需求：制作一条连接控制柜与传感器的线束，已知接口类型、长度、电流和安装环境，参考资料包括一张旧版 DWG、一个 Excel 接线表，以及几段写在邮件里的工艺要求。

如果把任务简单描述成“让 AI 画一张 CAD 图”，看起来并不复杂：模型识别需求，生成几条线、几个连接器和一些文字，再导出 DXF。但当图纸真的要交给工程师审核，甚至进入生产环节时，问题会迅速暴露：

- 图中的 `J1` 究竟是文字，还是一个连接器的业务标识？
- `PIN 1` 指的是物理孔位、逻辑信号，还是接线表中的行号？
- 线规、端子和连接器是否兼容？
- 图纸中的长度是成品总长、裁线长，还是两个测量基准之间的距离？
- 接线表、总装图和 BOM 是否来自同一份设计数据？
- AI 自动补充的物料型号，有没有真实依据？
- 企业规则更新后，为什么同一份输入得到了不同结果？
- 如果图纸有问题，能否追溯到输入文件、规则版本和人工确认记录？

这些问题说明，线材 CAD 的难点从来不只是“生成图形”，而是把需求、图纸、业务对象、企业规则和工程输出组织成一条可信链路。

> **工程 AI 的目标，不应该是让大模型直接书写 DXF，而应该是让模型提出候选设计，由领域模型约束语义，由规则快照控制风险，再由确定性程序生成可编辑、可校验、可追溯的工程图。**

本文以 OrbitStudio 当前的线材 CAD 能力为参考，拆解一条从 DWG/DXF 导入、线束语义识别，到规则校验和确定性出图的完整技术主线。

```text
自然语言 / Excel / PDF / DWG / DXF
              ↓
         需求与图纸解析
              ↓
      CadDrawingIR 几何事实
              ↓
 EngineeringSemanticOverlay
              ↓
   WireHarnessDesign 设计数据
              ↓
      DrawingCommandPlan
              ↓
    冻结规则快照并校验
              ↓
       确定性生成 DXF
              ↓
   预览、人工确认、受控交付
```

> **内容边界**：本文根据 OrbitStudio 在 2026 年 10 月 9 日的本地代码和架构文档整理。文中部分代码经过简化，用于解释设计思路，不等同于完整接口声明。当前实现已经覆盖 CAD 中间表示、线材领域包、语义增强、规则治理和确定性 DXF 生成等关键骨架，但企业真实物料、正式工艺阈值、样图准确率和原业务系统集成仍需结合客户数据完成。

## 一、先纠正一个误区：线材 CAD 不是“画几条线”

从视觉上看，一张线束图可能只包含连接器、导线、文字、尺寸和表格。但从制造角度看，它同时承载了多组相互约束的信息。

### 1. 图形只是最终表达，设计数据才是核心

一份可用于加工的线材图，通常至少需要表达：

- 连接器型号、物理孔数和实际使用针位；
- 针位、信号与导线之间的连接关系；
- 导线规格、线规或截面积、颜色和条纹色；
- 总长、分支长度、剥线长度及其测量基准；
- 端子、压接、焊接、管形端头或裸端等端部处理；
- 主干、分支、包覆、屏蔽和固定方式；
- 线号、标签及其安装位置；
- 单件 BOM、物料单位和数量；
- 导通、错接、短路、尺寸、外观等检验要求；
- 图号、修订、单位、比例和审批信息。

因此，真正的设计对象不是一堆 CAD 图元，而是一份统一的线束设计数据：

```text
WireHarnessDesign
   ├─ 连接器与物理针位
   ├─ 导线与连接拓扑
   ├─ 端子与兼容范围
   ├─ 主干、分支与路径
   ├─ 包覆与环境约束
   ├─ 尺寸与公差
   ├─ BOM
   ├─ 工艺要求
   └─ 检验要求
```

总装图、接线表、接口详图和 BOM 应当是这份设计数据的不同投影，而不是四套互相独立的结果。

### 2. “文件合法”不等于“工程正确”

一个 DXF 文件能够被 AutoCAD 或其他 CAD 软件打开，只能说明它大概率满足文件格式要求，不能说明它已经具备可制造性。

例如，下面这些图都可能在格式上完全合法：

- 图中画了两只连接器，但没有说明观察方向；
- 接线表写着 `J1-1 → J2-4`，总装图却连接到了 `J2-5`；
- BOM 中出现了端子，但没有说明端子与线规是否兼容；
- 图上标注长度为 `1000 mm`，却没有给出测量起点和终点；
- 一只 12 孔连接器只使用 4 个孔位，图纸却把“已接线 PIN 数”当成“外壳总孔数”；
- AI 根据记忆填写了某个料号，却没有查询企业物料库或厂商资料。

所以，线材 CAD 至少需要两组校验：

| 校验层级 | 主要问题 |
| --- | --- |
| 文件与几何校验 | DXF 能否打开、单位是否正确、图层与实体是否合法、包围盒是否合理 |
| 领域与制造校验 | 接线是否一致、选型是否兼容、尺寸是否有基准、BOM 是否完整、工艺是否有依据 |

前者由通用 CAD 能力负责，后者必须由线材领域模型和企业规则负责。

## 二、系统边界：AI 是设计助手，不是正式业务系统

工程系统最危险的设计之一，是让 AI 直接覆盖正式数据。

在线材场景中，更稳妥的边界是：原有线材软件继续负责正式编号、正式设计数据、业务状态、最终编辑和归档；AI 平台负责需求解析、历史图纸识别、候选选型、字段映射、CAD 草稿和校验报告。

```text
原有线材软件
  ├─ 正式图号与版本
  ├─ 正式业务状态
  ├─ 最终人工编辑
  └─ 生产归档

AI 工程平台
  ├─ 参数候选
  ├─ 语义识别候选
  ├─ 方案与物料建议
  ├─ CAD 草稿
  ├─ 规则校验
  └─ 证据与审计
```

两者之间通过新修订、导入草稿或受控接口交接，而不是由 AI 绕过正式系统直接修改生产数据。

### 1. 哪些事情适合交给模型

模型擅长处理概率性任务：

- 理解自然语言需求；
- 识别 Excel 和文档中的字段别名；
- 从历史案例中总结相似设计；
- 提出查询计划、字段映射或绘图计划候选；
- 解释异常并形成待确认清单。

### 2. 哪些事情必须保持确定性

下列工作不能只依赖模型“看起来合理”的输出：

- DWG/DXF 的底层解析；
- 单位和坐标转换；
- 稳定 ID 与引用完整性；
- 权限和知识范围裁决；
- 规则生命周期与版本冻结；
- 图纸命令 Schema 校验；
- DXF 文件写入；
- 哈希、审计和状态迁移。

可以把责任边界压缩成一句话：

> **模型负责提出候选，领域层负责判断候选是否合法，确定性程序负责产生真实工程资产。**

## 三、整体架构：治理、工程运行时和 CAD 转换各司其职

OrbitStudio 没有把所有能力塞进一个“CAD Agent”，而是将系统拆成多个责任层。

```text
┌────────────────────────────────────┐
│ Hub / Engineering CAD Workbench    │
│ 查询、规则、出图、企业知识、治理    │
└─────────────────┬──────────────────┘
                  │
┌─────────────────▼──────────────────┐
│ Knowledge Governance / SA Java     │
│ 知识库、权限、修订、任务、发布治理  │
└─────────────────┬──────────────────┘
                  │
┌─────────────────▼──────────────────┐
│ Engineering Runtime / Python       │
│ CAD IR、领域包、语义、规则、出图    │
└────────────┬────────────────┬──────┘
             │                │
┌────────────▼──────┐  ┌──────▼──────────────┐
│ ODA Converter     │  │ Storage Projection  │
│ DWG → 规范化 DXF │  │ SQL / 向量 / 图谱   │
└───────────────────┘  └─────────────────────┘
```

### 1. Hub：面向用户的工程工作台

Hub 负责提供查询、规则、出图和企业知识维护入口。它展示业务结果，但不成为 CAD 领域规则的真源，也不直接读取工程运行时数据库。

### 2. Knowledge Governance：权限和修订控制

治理层负责：

- 当前用户能够访问哪些知识库；
- 哪些文件修订处于 `READY` 状态；
- 哪个领域包版本绑定到哪个知识库；
- 哪些规则已经发布；
- 哪个任务可以生成、修改或发布图纸。

这里有一条重要原则：**权限先于检索。** 系统不能先从所有资料中检索，再在结果层过滤；可访问范围必须在查询和语义投影之前确定。

### 3. Engineering Runtime：领域能力的运行位置

Python 工程运行时承载：

- CAD 中间表示；
- DXF 确定性解析；
- 线材语义增强；
- 工程查询；
- 字段映射；
- 规则评估；
- Drawing Plan 与 Patch；
- 确定性 DXF 编译。

它采用模块化单体组织：统一入口启动，通用能力集中管理，不同工程领域通过 Domain Pack 扩展，而不是每新增一个领域就复制一套服务。

### 4. ODA Converter：只解决格式规范化

DWG 是复杂的二进制格式，工程运行时不会让模型解析 DWG，也不会把 ODA 转换器和业务语义混在一起。

ODA Converter 的职责很窄：

```text
DWG → 受控、规范化的 DXF
```

转换后的 DXF 再由工程运行时解析成统一中间表示。

## 四、第一条关键分界：CadDrawingIR 只记录几何事实

面对 CAD 文件，系统首先要回答一个问题：什么是文件中可以确定的事实，什么是后续推断出来的业务含义？

OrbitStudio 使用 `CadDrawingIR/v1` 作为二维 CAD 的权威中间表示。它可以被定义为：

> **绑定到不可变图纸修订的、格式无关且领域中立的二维 CAD 几何事实快照。**

### 1. 为什么需要中间表示

如果查询、预览、线材识别和 AI 都直接理解 DWG/DXF 语法，系统会产生多个问题：

- 每个上层功能都要重复处理 CAD 格式细节；
- DWG 和 DXF 会形成两套逻辑；
- 解析器升级后很难比较前后差异；
- 业务语义与文件结构紧密耦合；
- 上层模型可能误把解析失败当成“图中不存在”。

引入 IR 后，上层只依赖统一合同：

```text
DWG ── ODA ──> 规范化 DXF ─┐
                           ├─> CadDrawingIR/v1
DXF ───────────────────────┘
                                  │
                                  ├─> 几何查询
                                  ├─> 图纸预览
                                  ├─> 数据投影
                                  └─> 领域语义增强
```

### 2. CadDrawingIR 记录什么

当前 IR 顶层主要保存：

- 图纸修订身份；
- 原始格式；
- 插入单位；
- 图层定义；
- Model Space 与 Paper Space Layout；
- 二维图元及其坐标；
- 图元和整图包围盒；
- 解析器版本；
- ODA 规范化来源；
- DXF 原始属性。

强类型几何包括：

- 直线；
- 圆；
- 圆弧；
- 二维多段线；
- 文字；
- 块引用。

暂未强类型支持的图元也不能静默丢弃，而应保留一个带有来源类型和原始属性的 `unsupported` 信封。否则，“解析器不支持”会被错误解释成“原图中不存在”。

### 3. CadDrawingIR 不记录什么

下面这些内容不能写成 IR 的固有事实：

- 这段文字代表连接器；
- 这条线代表导线；
- 这个块是端子；
- 两个图元构成一条电气连接；
- 该物料符合企业标准；
- 该图纸已经通过人工审核。

例如，IR 可以确定“坐标 `(120, 80)` 处有一段内容为 `J1` 的文字”，但不能仅凭这段文字断言它一定是一只连接器。

```text
CadDrawingIR 事实：
  Text(content="J1", x=120, y=80)

可能的领域解释：
  Connector(connector_id="J1")
```

这两个层次必须分开。

### 4. 不可变修订是可追溯性的基础

图纸导入过程可以表示为：

```text
uploaded
   ↓
converting
   ↓
parsing
   ↓
enriching
   ↓
indexing
   ↓
ready
```

其中：

- DXF 在 `parsing` 阶段生成 IR；
- DWG 先在 `converting` 阶段转成 DXF，再进入 `parsing`；
- `ready` 之前的修订不能成为默认查询版本；
- 失败修订可以保留错误和中间产物，但不能覆盖当前可用修订；
- 新版本产生新 Revision，而不是原地改写历史数据。

不可变修订使系统能够回答：“这个语义结果究竟来自哪一份原始图纸？”

## 五、第二条关键分界：Semantic Overlay 负责解释业务语义

CAD IR 解决了统一几何事实的问题，但工程师真正关心的是：图里有哪些连接器、针脚和导线，它们之间是什么关系。

这些信息进入 `EngineeringSemanticOverlay`。

### 1. Overlay 是叠加在图纸上的领域解释

同一份图纸可以被不同领域包分别解释：

```text
                  ┌─> wire_harness Overlay
CadDrawingIR ─────┼─> electrical_schematic Overlay
                  └─> future_domain Overlay
```

Overlay 需要记录：

- 图纸修订 ID；
- 领域包 ID 和版本；
- 语义 Schema 版本；
- 规则快照；
- 语义对象；
- 对象关系；
- 置信度；
- 来源证据；
- 候选或已发布状态。

因此，升级领域包时不会原地改写旧结果，而是针对同一个图纸修订产生新的 Overlay。历史语义仍然可以回放和比较。

### 2. 线材领域中的核心对象

项目中的 `wire_harness` 领域包定义了线材设计的核心对象：

```python
class HarnessPin:
    pin_id: str
    connector_id: str
    cavity: str
    signal: str | None

class HarnessWire:
    wire_id: str
    from_pin_id: str
    to_pin_id: str
    gauge_awg: int | None
    cross_section_mm2: float | None
    color: str | None
    length_mm: float | None

class HarnessConnector:
    connector_id: str
    part_number: str | None
    pins: tuple[HarnessPin, ...]
```

完整模型还包括：

- `HarnessTerminal`：端子及适用线规范围；
- `HarnessBundle`：主干或导线集合；
- `HarnessWrap`：包覆材料及起止位置；
- `HarnessRoute`：线束路径；
- `HarnessEnvironment`：温度、电压、电流和防护条件；
- `HarnessBomItem`：设计对象到受控物料的映射；
- `WireHarnessDesign`：统一设计聚合。

### 3. 关系比对象列表更重要

只识别出 `J1`、`J2` 和 `W1` 还不够，系统还需要构建连接拓扑：

```text
Connector J1
   └─ contains_pin → Pin J1:1
                         ↑
                         │ connects_from
                         │
                       Wire W1
                         │
                         │ connects_to
                         ↓
Connector J2
   └─ contains_pin → Pin J2:4
```

线材图中的业务价值主要存在于关系里：

- 连接器包含哪些针脚；
- 导线从哪个针脚出发；
- 导线连接到哪个针脚；
- 导线使用什么端子；
- 哪些导线属于同一主干；
- 主干使用什么包覆；
- 哪个 BOM 条目代表哪个设计对象。

这也是为什么系统同时需要关系查询和图谱投影，而不能只做全文检索。

### 4. 不确定数据必须输出诊断，不能强行补齐

工程语义识别最重要的品质不是“尽量多识别”，而是“知道什么时候不能确定”。

当前测试特别覆盖了这些情况：

- 端点缺失或存在歧义时，不猜测连接关系；
- 相同连接器代号出现在不同 Layout 时，不随意合并；
- 两个物理块使用同一代号时，保留歧义；
- 缺少颜色或线规时，保留可确认的导线，同时输出字段缺失诊断；
- BOM 被识别出来时，不能掩盖另一张未识别的接线表；
- 信号名碰巧类似连接器代号时，不能污染连接器身份；
- 不可识别行应形成 `extraction_issue`，并关联原始图元和证据。

也就是说，系统宁可返回：

```text
状态：incomplete
原因：第三列端点含义不明确
影响：无法确认该行是否为三端连接
证据：Layout-2 / entity-184
```

也不应生成一条看似完整、实际错误的导线。

## 六、Domain Pack：让线材知识成为可治理的软件资产

很多 AI 项目会把行业知识写进 Prompt：告诉模型什么是连接器、如何理解 PIN、什么情况下选择某种线规。原型阶段这样做很快，但进入工程系统后会立即遇到治理问题。

- 哪个 Prompt 才是最新版本？
- 查询 Agent 和出图 Agent 是否使用同一套定义？
- 企业修改了“孔位”的叫法后，哪些能力需要更新？
- 某条规则导致误判时，如何回滚？
- 历史图纸当时使用了哪一版业务模型？

OrbitStudio 将行业能力组织成 `EngineeringDomainPack`。`wire_harness` 是第一个参考实现。

### 1. 一个领域包不只是一些提示词

线材领域包包含：

- 领域 Manifest；
- 语义 Schema；
- 术语和字段基线；
- Semantic Enricher；
- Query Extensions；
- Field Mapping Provider；
- Rule Compiler 与 Evaluator；
- Drawing Composer；
- 图谱节点和边定义；
- 企业可扩展 Facet；
- 业务可读内容投影。

当前 `wire_harness` 领域包声明支持：

```text
semantic_enrich
query_execute
fieldmap_propose
validate
drawing_generate
patch_propose
```

它还声明可使用结构过滤、语义检索、图定位、图遍历、几何计算和原始资产获取等查询算子。

### 2. 四层模型避免“企业规则污染平台核心”

```text
平台通用工程模型
  ↓
线材行业基线模型
  ↓
企业扩展模型
  ↓
项目 / 任务实例
```

#### 平台通用层

负责修订、证据、权限、规则生命周期、绘图命令、任务和审计，不理解某个具体企业的物料编码。

#### 线材行业基线层

定义 Connector、Pin、Terminal、Wire、Bundle、Wrap、Route、Environment 等行业通用对象和关系。

#### 企业扩展层

维护：

- 企业字段别名；
- 内部物料编码；
- 图层命名规范；
- 必填字段；
- 连接器和端子兼容矩阵；
- 工艺与检验规则；
- 审批要求。

#### 项目实例层

保存本次线材设计的具体连接器、针位、长度、颜色、物料和人工确认结论。

这样的分层允许平台升级通用能力，同时保留企业自己的正式标准。

### 3. 字段别名也是领域能力

线材领域包内置了基础字段映射，例如：

```text
图号       → drawing_number
版本       → revision
线号       → wire_id
线径       → gauge_awg
导体截面积 → cross_section_mm2
长度       → length_mm
主色       → color
条纹色     → stripe_color
连接器     → connector_id
针位 / 孔位 → cavity
端子       → terminal_id
包裹材料   → material
```

但企业可能把同一个概念称为“位号”“腔位”“孔号”或内部缩写，因此行业基线只能提供骨架，企业叫法必须通过受控扩展维护，而不是散落在各个 Prompt 里。

## 七、统一设计数据：让图纸、接线表和 BOM 说同一种语言

多源输入最终需要汇聚成 `WireHarnessDesign`。

其核心结构可以简化为：

```python
class WireHarnessDesign:
    schema_version = "wire_harness_design/v1"
    design_id: str
    drawing_number: str | None
    revision: str | None
    title: str | None

    connectors: tuple[HarnessConnector, ...]
    terminals: tuple[HarnessTerminal, ...]
    wires: tuple[HarnessWire, ...]
    bundles: tuple[HarnessBundle, ...]
    wraps: tuple[HarnessWrap, ...]
    routes: tuple[HarnessRoute, ...]
    environments: tuple[HarnessEnvironment, ...]
    bom: tuple[HarnessBomItem, ...]
```

### 1. 模型本身就执行一部分一致性检查

例如：

- 端子 AWG 范围必须位于合法区间且上下界有序；
- 截面积范围必须为正数；
- 包覆结束位置必须晚于起始位置；
- 环境最低温度不能高于最高温度；
- 路径至少包含两个点；
- BOM 数量必须大于零；
- 导线端点必须引用有效针脚；
- 同一连接器中不能出现重复孔位。

这些属于领域不变量，应该由模型直接保护，而不是等待最后出图时才发现。

### 2. 输入不要求用户预先完成所有设计

用户可以只提供功能需求：

```text
需要一条 24V 传感器延长线，长度约 3 米，设备端为 M12，
控制柜端接端子排，现场有油污和轻微振动。
```

系统需要区分三类信息：

| 类型 | 示例 | 处理方式 |
| --- | --- | --- |
| 用户明确约束 | 24V、3 米、M12 | 作为设计输入 |
| 可由规范或物料库确定 | 导体规格、护套候选 | 查询并给出依据 |
| 无法安全确定 | M12 编码、针位方向、端子排编号 | 集中请求确认 |

不能因为用户没有给出完整料号，就直接从模型记忆里编造一个物料；也不能把工程建议伪装成已经确认的事实。

### 3. 一份设计数据生成多个一致的视图

```text
                 ┌─> 总装图
                 ├─> 接口详图
WireHarnessDesign├─> 接线表
                 ├─> BOM
                 ├─> 工艺说明
                 └─> 检验要求
```

这样才能执行交叉校验：

- 接线表中的每条导线是否都在总装对象中存在；
- BOM 中的端子是否被某条导线使用；
- 图纸标注的线规、颜色和长度是否与设计对象一致；
- 配对座是采购物料，还是客户设备上已经存在的对象；
- 批量数量是否被误写成单件 BOM 用量。

## 八、不要让模型写 DXF：让它生成 Drawing Plan

这一设计是整条链路中最关键的安全边界。

大模型可以生成 JSON、文本和结构化计划，但不应该直接书写裸 DXF 内容。DXF 包含版本、段、实体、handle、subclass marker 和大量格式细节，让模型直接生成会带来三个问题：

1. 文件语法可能不完整；
2. 业务对象与图元之间缺少稳定映射；
3. 修改只能重写整个文件，难以审计差异。

OrbitStudio 引入 `DrawingCommandPlan/v1`：

```python
class DrawingCommandPlan:
    schema_version = "drawing_command_plan/v1"
    plan_id: str
    tenant_id: str
    kb_id: str
    unit: DrawingUnit
    layers: tuple[DrawingLayerCommand, ...]
    commands: tuple[DrawingCommand, ...]
    evidence: tuple[SourceEvidence, ...]
    rule_snapshot_id: str | None
```

当前基础命令包括：

- `LineCommand`；
- `CircleCommand`；
- `TextCommand`。

领域包的 Drawing Composer 将 `WireHarnessDesign` 转换为绘图命令。模型可以参与设计和布局候选，但最终计划必须满足：

- 图层 ID 唯一；
- 命令 ID 唯一；
- 所有命令引用已声明图层；
- 单位合法；
- 命令数量在受控范围内；
- 计划关联来源证据；
- 服务端绑定租户与知识库范围。

### 1. 浏览器提交的是候选，不是权限事实

前端示例中可以编辑一个不包含权限字段的候选计划：

```json
{
  "schema_version": "drawing_command_plan/v1",
  "plan_id": "candidate-plan-001",
  "unit": "mm",
  "layers": [
    {"layer_id": "wire", "name": "E-WIRE", "color_index": 3}
  ],
  "commands": [
    {
      "kind": "line",
      "command_id": "wire-W1",
      "layer_id": "wire",
      "start": {"x": 0, "y": 0},
      "end": {"x": 100, "y": 0}
    }
  ],
  "evidence": []
}
```

但是 `tenant_id`、`kb_id`、scope 和 capability 不能由浏览器自行声明。它们由服务端根据当前身份和授权重新绑定。

这是典型的“候选与权威分离”：

```text
浏览器候选输入
      ↓
服务端补充身份与权限范围
      ↓
领域 Schema 与业务规则校验
      ↓
权威 DrawingCommandPlan
```

### 2. 修改通过 Patch，而不是覆盖文件

图纸修改被表达为 `DrawingPatchPlan/v1`：

```python
class DrawingPatchPlan:
    patch_id: str
    base_plan_id: str
    remove_command_ids: tuple[str, ...]
    upsert_commands: tuple[DrawingCommand, ...]
    evidence: tuple[SourceEvidence, ...]
```

Patch 的优势是：

- 明确基于哪个计划修改；
- 能准确表示新增、更新和删除；
- 可以保留修改证据；
- 可以在应用前做影响分析；
- 不会直接覆盖并发产生的新版本；
- 应用后形成新的 Candidate Plan。

例如，“将 W1 的终点向右移动 10 mm”不需要让模型重写整个 DXF，只需更新命令 `wire-W1`。

## 九、规则快照：同一张图为什么必须绑定同一组规则

假设企业今天规定最小线规为 24 AWG，下周调整为 22 AWG。如果出图任务每次都读取“最新规则”，那么同一个设计在不同日期重新生成时，会得到不同结论，而且无法解释差异来自哪里。

因此，正式校验不能只引用规则 ID，而必须冻结 `RuleSetSnapshot`。

### 1. 规则先治理，再执行

规则具有生命周期：

```text
candidate → reviewed → published
```

只有已发布规则可以进入正式快照。候选规则即使由 AI 从文档中提取出来，也不能直接阻断生产出图。

规则还需要区分严重级别：

- `warning`：允许继续，但必须提示；
- `blocking`：校验失败，禁止生成正式输出。

典型规则包括：

- 导线线规必须落在端子兼容范围内；
- 连接器孔位不能重复；
- 导线端点必须存在；
- 必填 BOM 物料不能缺失；
- 长度必须具有公差或明确说明；
- 特定环境下必须使用指定护套；
- 关键待确认项存在时只能保持草稿状态。

### 2. Drawing Work 是受治理的状态机

出图不是一次无状态函数调用，而是一个持久化 Work：

```text
Candidate
   │
   ├─ 可选：应用 Drawing Patch
   │
   ↓
绑定并冻结 RuleSetSnapshot
   ↓
执行领域规则校验
   ├─ 失败 → Rejected
   │          └─ 保存违规项，不写 DXF
   │
   └─ 通过 → Generated
              ├─ DXF 输出引用
              ├─ SHA-256
              ├─ 实体数量
              └─ 语义指纹
```

实现中的状态不变量非常明确：

- `candidate` 不能携带最终校验和输出；
- `generated` 必须拥有通过的校验结果和输出；
- `rejected` 必须拥有失败校验，并且不能存在生成结果；
- 规则快照的租户、知识库和计划引用必须完全匹配；
- 阻断规则失败时，不允许先写文件再告诉用户“有问题”。

这种状态机把“AI 生成草稿”和“系统认可输出”分成了两个阶段。

### 3. 生成服务不等于发布服务

当前 Drawing Workflow 的职责是把候选变成经过治理的确定性资产，它本身不自动发布为正式图纸修订。

这条边界很重要：

```text
生成成功 ≠ 审核通过 ≠ 正式发布 ≠ 允许生产
```

生成、审核、发布和归档应该是不同的权限动作。

## 十、确定性编译：把计划写成可编辑 DXF

当 Drawing Plan 通过规则校验后，系统使用 `ezdxf` 进行确定性编译。

核心过程可以简化为：

```python
def compile(plan, output_path):
    document = ezdxf.new("R2018", setup=True)
    document.header["$INSUNITS"] = unit_code(plan.unit)

    for layer in plan.layers:
        document.layers.add(
            layer.name,
            color=layer.color_index,
            linetype=layer.line_type,
        )

    modelspace = document.modelspace()

    for command in plan.commands:
        if command.kind == "line":
            modelspace.add_line(command.start, command.end)
        elif command.kind == "circle":
            modelspace.add_circle(command.center, command.radius)
        elif command.kind == "text":
            modelspace.add_text(command.text, height=command.height)

    document.saveas(output_path)
```

这里最关键的不是 `ezdxf` API，而是输入已经被约束为一个合法、可审计的命令计划。

### 1. 文件哈希和语义指纹解决不同问题

生成结果同时记录：

- `sha256`：针对最终文件字节；
- `semantic_fingerprint`：针对绘图命令的语义序列；
- `entity_count`：实体数量；
- `plan_id`：来源计划；
- `output_ref`：受控输出引用。

文件哈希用于确认字节是否一致，语义指纹用于确认计划表达是否一致。

两个 DXF 文件可能因为非业务元数据不同而具有不同文件哈希，但仍表达同一组工程命令；反过来，文件都能打开也不代表语义相同。

### 2. 输出路径也必须受控

实现要求结果引用位于受控命名空间，例如：

```text
local://generated/candidate.dxf
```

调用方不能通过输出参数让生成器覆盖任意业务文件。文件系统边界也是工程安全的一部分。

### 3. DXF 自检至少包含什么

生成之后应检查：

- DXF 版本与单位；
- 必需段和 EOF；
- 图层与实体类型；
- 实体数量；
- EXTMIN、EXTMAX 与实际包围盒；
- 关键几何是否为非零长度；
- 文字是否落在合理位置；
- 文件是否能够重新读取；
- 图纸、接线表和 BOM 是否保持一致。

如果需要 DWG，可以在 DXF 验证通过后调用 ODA 转换，但 DWG 交付仍需要额外的往返语义检查。

## 十一、可制造性不是“图元越多越好”

AI 生成图纸时容易追求视觉丰富度：增加护套、热缩、屏蔽、端子、局部视图和标注，让图看起来更像“专业 CAD”。但在线材设计中，丰富度应该按可制造性衡量，而不是按图元数量衡量。

一条简单的三芯延长线应该简洁但完整；一条多分支、高速或屏蔽线束才需要更多局部视图和专用工艺。

不能为了让图面复杂而添加实际不存在的结构。

### 1. 加工图的最低内容基线

| 内容 | 最低要求 |
| --- | --- |
| 标题与图框 | 图号、名称、修订、单位、比例或不按比例声明 |
| 总装外形 | 主干、真实分支、端部外形、代号和物料序号 |
| 接口详图 | 型号、物理孔数、已用和未用针位、观察方向、PIN 1 依据 |
| 接线表 | 两端代号与针号、信号、线规、颜色、端子 |
| 尺寸 | 总长、分支长、端部处理尺寸、公差和测量基准 |
| 端部加工 | 压接、焊接、管形端头或裸端做法及依据 |
| BOM | 线缆、壳体、接触件和实际存在的辅材 |
| 工艺与标识 | 装配顺序、方向、固定、防护、屏蔽和线号位置 |
| 检验 | 导通、错接、短路、尺寸、外观和端接检查 |

### 2. 不适用项也应有结论

如果某条线束不需要屏蔽，不应简单让“屏蔽工艺”一栏消失，而可以记录：

```text
屏蔽：不适用
原因：当前信号类型与环境要求不需要屏蔽结构
依据：设计输入 REV-A / 环境约束 E-03
```

明确“不适用”比字段缺失更有审计价值。

## 十二、工程工作台：把查询、规则和出图放进同一闭环

OrbitStudio 的工程 CAD 工作台包含五类能力入口：

```text
Query | Rules | Drawing | Enterprise | Governance
```

### 1. Query：查询工程对象，而不是只搜文本

查询计划可以组合：

- 结构化过滤；
- 语义检索；
- 图定位；
- 图遍历；
- 几何计算；
- 原始资产获取。

例如用户询问：

```text
查找 J1 连接的 PIN，以及这些 PIN 对应的线材规格。
```

高层流程不是把问题直接翻译成 SQL 或 Cypher，而是：

```text
自然语言问题
   ↓
模型提出 EngineeringQueryPlan 候选
   ↓
服务端重新生成当前身份可访问范围
   ↓
领域层校验算子、字段、预算和企业术语
   ↓
执行查询并返回对象、关系和证据
```

如果信息不足，系统应返回 `need_clarification`，而不是盲目执行。

### 2. Rules：规则从候选走向发布

工作台支持：

- 提交结构化规则候选；
- 从自然语言中提取规则候选；
- 审核和发布；
- 创建跨知识库 Rule Binding；
- 冻结规则快照；
- 查看违规项和来源证据。

前端只是治理入口，真正的字段、关系和规则边界仍由领域模型裁决。

### 3. Drawing：查看每次生成的真实状态

Drawing Work 需要展示：

- Work ID 和 Plan ID；
- 当前状态；
- 命令数量；
- 提交人；
- 领域包版本；
- 规则校验结果；
- 失败原因；
- 输出引用；
- 实体数量；
- 文件哈希。

这样用户看到的不只是“下载 DXF”按钮，而是一条完整的生成证据链。

### 4. Enterprise：行业模型和企业标准分离

平台提供线材行业基线，租户管理员维护企业术语和后续可扩展的企业规则。普通工程师直接使用已经生效的企业知识，不需要理解内部的模型版本、迁移和投影细节。

企业维护界面也不应退化成“万能 JSON 编辑器”。每种可维护内容都应由领域包声明强类型表单和校验策略。

## 十三、测试重点：工程系统要证明自己不会乱猜

线材 CAD 的测试不能只验证“接口返回 200”，而要验证领域不变量、证据完整性和重复执行稳定性。

### 1. 领域模型测试

需要覆盖：

- 重复孔位被拒绝；
- 无效端点被拒绝；
- 端子线规范围合法；
- 包覆起止位置有序；
- 路径至少包含两个点；
- BOM 引用真实设计对象；
- 环境温度上下界有效。

### 2. 图纸识别变体测试

真实工程图不会使用统一模板，因此要测试：

- 表头位于不同位置；
- 单位出现在标题或表格末尾；
- 合并单元格；
- 多个 Layout；
- 中英文和 DXF 转义字符；
- 重复位号；
- 表格中存在页脚和说明行；
- BOM 与接线表同时存在；
- 缺失颜色、线规或端点；
- 第三列含义模糊；
- 未识别表格不能被静默忽略。

测试的目标不是保证“每一行都被识别”，而是保证系统在不能识别时给出明确诊断，并且绝不伪造连接。

### 3. 确定性测试

同一输入重复执行，应保证：

- 对象 ID 稳定；
- 关系数量稳定；
- 命令顺序稳定；
- 语义指纹稳定；
- 不同运行之间不共享脏状态；
- 相同代号在不同 Layout 中不会被错误合并。

### 4. 出图门禁测试

必须验证：

- 未发布规则不能进入正式快照；
- 不相关领域包的规则不会误生效；
- 快照范围不匹配时拒绝生成；
- 阻断规则失败时不产生 DXF；
- 规则通过后生成的文件可以重新读取；
- 输出只能写入受控命名空间；
- 生成状态、校验状态和输出结果保持一致。

工程系统最重要的测试，不是证明它能成功，而是证明它在不确定和失败时能够安全停止。

## 十四、当前边界：技术骨架完成，不等于生产标准已经完成

一套平台可以实现完整的 CAD IR、领域包和出图工作流，但仍不能宣称“已经自动生成可直接生产的所有线束图”。

当前能力骨架解决了：

- DWG/DXF 到统一 CAD IR；
- 几何事实与领域语义分层；
- 线材对象和连接拓扑建模；
- 证据化语义识别；
- 字段映射和工程查询；
- 规则候选、发布和快照；
- Drawing Plan 与 Patch；
- 校验通过后确定性生成 DXF；
- 工作台中的查询、规则和出图治理。

但生产落地仍依赖企业提供和确认：

- 正式物料主数据；
- 连接器、端子和导线兼容矩阵；
- 压接高度、拉脱力、耐压等受控阈值；
- 企业图框、字体、图层和符号规范；
- 历史样图及标注数据；
- 原线材软件的数据接口；
- 正式审核和电子签核流程；
- DWG 版本、字体、外部参照和代理对象策略；
- 真实业务场景下的识别准确率和验收标准。

尤其需要警惕三种错误表述：

1. **“文件生成成功，所以可以生产。”**
2. **“模型给出了料号，所以完成了选型。”**
3. **“识别到大部分字段，所以剩余字段可以自动猜测。”**

工程平台必须准确区分“技术链路可运行”“企业数据已接入”“真实样图已验收”和“正式生产已批准”。

## 十五、从线材 CAD 可以抽象出的通用工程 AI 方法

线材只是第一个领域。它背后的架构可以迁移到电气原理图、流体图、工艺图和其他二维工程场景。

### 1. 表示、语义和使用方式必须分离

```text
表示层：文件里有什么
语义层：这些内容在某个领域中代表什么
使用层：谁可以查询、修改、校验和发布
```

混在一起，系统会变成特定场景的功能堆叠；分开后，通用 CAD 核心和领域能力才能独立演进。

### 2. AI 输出应该是候选协议，不是最终副作用

```text
LLM Candidate
      ↓
Schema Validation
      ↓
Domain Validation
      ↓
Rule Evaluation
      ↓
Deterministic Side Effect
```

无论是查询、字段回填、规则抽取还是图纸修改，都可以复用这条模式。

### 3. 证据是一等数据，不是回答末尾的备注

工程结果必须能够关联：

- 文件；
- 修订；
- CAD 图元；
- 文本片段；
- 规则；
- 领域包版本；
- 人工确认记录。

没有证据的“高置信度”并不可靠。

### 4. 快照比“始终读取最新配置”更适合工程任务

出图、仿真、校验和发布都应绑定不可变快照。这样才能复现历史结果，并解释规则变化带来的差异。

### 5. 安全失败比勉强完成更重要

当针位方向、关键接口、尺寸基准或安全参数不明确时，正确行为是保持草稿并提出澄清问题，而不是追求任务完成率。

## 结语：真正的 AI CAD 是一条可信设计链路

如果只看最终界面，线材 CAD 的结果可能只是一个可下载的 DXF 文件。但文件背后真正重要的是一条完整链路：

```text
输入需求与历史资料
   ↓
不可变文件修订
   ↓
领域中立的 CadDrawingIR
   ↓
带版本和证据的 Semantic Overlay
   ↓
统一 WireHarnessDesign
   ↓
候选 DrawingCommandPlan
   ↓
RuleSetSnapshot 与阻断校验
   ↓
确定性 DXF 编译
   ↓
人工确认、发布与归档
```

判断一套工程 AI 系统是否真正可信，可以追问三个问题：

1. **领域规则是否集中在强类型模型和领域包中，而不是散落在 Prompt、页面和临时代码里？**
2. **同一个图纸修订能否绑定明确的领域包、企业模型和规则快照，并在未来复现？**
3. **任意识别、推荐、修改和出图结果，能否追溯到原始证据、执行身份和人工决策？**

如果答案是否定的，那么系统可能只是一个能够生成 CAD 文件的 Demo。

如果答案是肯定的，它才开始具备工程平台的雏形：AI 负责理解和提出候选，领域模型维护业务真相，规则系统控制风险，确定性程序产生真实资产，工程师保留最终决定权。

这不是用 AI 替代 CAD，也不是用 Agent 替代工程师。

它真正改变的是：过去依赖人工抄录、个人经验和反复核对的线材设计过程，开始被重构为一条**结构化、可验证、可回退、可持续演进的数字工程闭环**。
