凌晨两点，一个采购 Agent 收到请求：为项目购买 20 台显示器，预算不超过 3 万元，必须使用合格供应商，并在审批通过后下单。

Agent 完成检索、询价与审批，向 ERP 发出创建订单的请求。ERP 已经落单，响应却在网络中丢失。Worker 等到超时后重启，恢复程序看到“上次调用失败”，于是又创建了一张订单。

这时，模型可能完全理解了用户意图，工具服务也一直可用，重启机制甚至按设计正常工作。但业务已经失败：同一份采购需求产生了两份承诺。

这个假设案例暴露出 Agent 上线时需要一起回答的三个问题：**什么结果值得承诺，什么证据允许新版本接管真实任务，故障后凭什么恢复执行。** 只有把三者连接起来，监控数据才能变成发布和恢复决策。

本文以采购 Agent 为贯穿案例。论文用于解释问题与机制；任务口径、发布门槛和演练方案是基于这些机制提出的工程设计。文中数字均为教学假设，不是论文实验结果或生产实测。

## 一、为什么离线高分还不能证明系统可靠

### 1. 任务成功必须有外部证据

τ-bench 在用户、Agent、工具和业务规则共同构成的环境中评测任务，并通过比较交互结束后的数据库状态与目标状态判断完成情况。[1] 这给生产系统一个直接启发：验收应该落在业务事实，而不能只检查 Agent 最后有没有说“已完成”。

采购任务至少涉及五项事实：订单属于正确项目，数量与规格符合请求，价格没有超出授权范围，供应商符合规则，并且审批在写入前已经生效。还需要检查是否存在额外的重复订单。仅仅确认“查得到一个订单”会漏掉最后一种失败。

数据库终态也有边界。最终金额正确，并不能证明过程中没有越权；一张后来取消的违规订单仍然可能产生业务影响。因此，本文建议同时保留**结果验收**与**过程约束检查**。τ-bench 提供了结果验收的研究依据，生产审计还需要按自身业务补充过程证据。

### 2. 平均成功率会掩盖重复运行的不稳定

τ-bench 提出 `pass^k`，关注同一任务多次运行能否全部成功。[1] 它与常见的 `pass@k` 回答不同问题：后者关心多次尝试中至少一次成功，前者关心重复交付是否稳定。

假设某个任务每次独立执行的成功概率固定为 90%，那么：

```text
执行 5 次至少成功一次：1 - (1 - 0.9)^5 = 99.999%
执行 5 次全部成功：0.9^5 ≈ 59.05%
```

这只是帮助理解指标的概率示例。实际任务难度不同，重复运行也可能相关，不能把整套测试的平均成功率直接取五次方，冒充实测 `pass^5`。

对生产采购系统而言，“试五次总能成一次”尤其危险：如果每次重试都可能创建真实订单，增加尝试次数会同时扩大副作用。

### 3. 可靠性需要看到失败如何发生

《Towards a Science of AI Agent Reliability》将可靠性分解为一致性、鲁棒性、可预测性与安全性，并提出十二项指标。[2] 它提示我们：能力分数之外，还要关心输入轻微变化、工具故障或环境变化后表现是否稳定，以及失败的严重程度。本文引用其研究框架，不把特定评测环境的结论直接当作企业生产指标。

《Why Do Multi-Agent LLM Systems Fail?》提出的 MAST 则把失败分为系统设计、Agent 间不一致和任务验证三类，共十四种模式。[3] 它研究的是多 Agent 系统，不能据此推断所有单 Agent 的故障分布；但它支持一个重要诊断方向：失败来源需要沿着任务执行过程查找。

据此，可以把采购系统的验收问题拆成三个层面：

| 层面 | 需要回答的问题 | 示例检查 |
| --- | --- | --- |
| 决策与业务语义 | 目标和约束是否理解正确 | 规格、预算、供应商与审批条件 |
| 执行与状态一致性 | 动作是否按预期发生 | 订单唯一、回执可关联、恢复不重复写入 |
| 服务交付 | 用户是否在承诺时间内得到结果 | 按时完成、明确失败、及时接管 |

这是一种面向工程的组织方式，不是上述论文共同提出的标准。它的价值是防止团队用一个“成功率”同时替代三类不同的验证。

## 二、先把用户承诺写成可以验收的任务契约

SLO 是服务级别目标，SLI 是衡量目标的指标。Google SRE 的实践强调，指标要围绕用户体验选择，并用于指导可靠性投入与发布决策。[6]

在选定 99% 或 99.9% 之前，应先定义任务服务的边界。本文只讨论一类受支持的请求：输入完整、属于支持的采购品类、已经取得必要审批，且通过准入检查的自动下单任务。审批之前的等待由另一项端到端指标记录。

为这类任务定义一份示例契约：

| 契约项 | 本文的示例定义 |
| --- | --- |
| 进入服务的时点 | 准入通过、任务持久化并向用户确认接收 |
| 完成时限 | 接收后的 10 分钟以内 |
| 成功条件 | ERP 中存在且仅存在一份对应采购结果，内容正确，并通过过程约束检查 |
| 结果证据 | 外部订单 ID、动作身份、验收结果及授权记录 |
| 无法自动完成时 | 在时限内给出真实状态，并按条件转人工 |
| 统计规则 | 人工接管及时记录，但不算自动完成成功 |

把人工接管单列非常关键。如果原先承诺自动下单，却把所有失败都转人工并算作成功，那么自动完成率会失去意义。可以另设“及时接管率”，评估服务是否妥善兜底。

拒绝也需要按任务契约解释。若服务承诺是“审核请求并给出合规处理结果”，正确拒绝可能是成功；若任务已经通过准入、服务承诺是执行订单，内部故障后返回拒绝就不能算成功。分类规则必须在观察结果之前确定。

对于上述自动下单任务，可以把验收条件写成：

```text
任务按时成功 =
    业务结果正确
    AND 关键过程约束满足
    AND 没有额外重复副作用
    AND 完成时间不晚于约定截止点
```

验收器应优先读取 ERP、审批服务等权威状态。模型评审可以辅助处理开放式语义，但金额、权限、订单唯一性等可精确判断的条件，应通过结构化规则验证。验收器本身也要有版本，并用人工复核检查漏判与误判。

## 三、长任务的 SLO，难点在分母和结算时点

### 1. 未完成的任务不能从统计里消失

假设某段时间接收了 100 个任务，其中 80 个完成、20 个卡住。如果只计算已经结束的任务，系统可能报告 100% 成功。恰恰最需要关注的任务没有进入分母。

本文采用按接收时间归组、到约定截止点结算的办法。每个任务在接收时生成 `accepted_at` 与 `deadline_at`，截止点到达后才能进入这组指标的最终结算。

```text
合格任务集合 = 符合预先定义的准入和统计规则的任务
已结算集合 = 合格任务中，deadline_at 已到达的任务
按时有效完成率 = 已结算集合中按时通过验收的任务数 / 已结算任务数
```

例如，观察 09:00—10:00 接收的一批任务，每个任务的时限都是 10 分钟。到 10:10，这批任务才全部到达结算点。若当时仍有任务卡住，它们必须计为超时失败。

对于持续滚动的 30 天看板，可以按最近 30 天到达截止点的任务计算；按接收批次分析版本表现时，则要等待该批次成熟。两种视图都合理，但它们的时间轴不同，必须在图表与查询中写清楚。

### 2. 恢复成功不能抹去曾经超时

某个任务第 18 分钟终于完成，业务状态可以更新为“最终完成”，但“是否在第 10 分钟前完成”仍然为否。建议分别保存：

```text
met_deadline: false
final_outcome: completed
completed_at: 实际完成时间
```

这样既能衡量用户体验，也能评估补救效果。如果把所有补救后的任务都改回按时成功，事故就会随着恢复从报表中消失。

后续对账发现重复订单时，原有的正确性判断可能需要修订。修订应保留原结算值、修订原因和生效时间。事实纠错与抹去超时是两回事，不能靠冻结错误数据来追求“口径稳定”。

### 3. 主指标、诊断指标与安全事件分别负责什么

| 类型 | 示例 | 用于什么决策 |
| --- | --- | --- |
| 主 SLI | 按时有效完成率 | 是否兑现业务承诺、是否消耗错误预算 |
| 自动化效果 | 人工接管比例、每个有效任务成本 | 是否把困难转给人工、成本是否可接受 |
| 提前发现问题的信号 | 最老任务年龄、队列积压、未知动作数量及年龄 | 在任务截止前发现异常 |
| 安全事件 | 未审批写入、重复下单、越权访问 | 按严重度立即止损和调查 |

结果型 SLI 有结算延迟，所以队列年龄等信号很有价值。但队列恢复正常，并不意味着已发生的业务失败可以消除。

主 SLI 应从完整任务事实和验收记录计算。采样 Trace 用于解释单次执行过程，不能直接承担完整分母。任务 ID、动作 ID 与订单 ID 放进可查询记录；聚合指标只按受控的场景、版本和错误类别分组。

## 四、错误预算怎样变成真实的行动规则

假设上述任务的 SLO 为 30 天内按时有效完成率达到 99%。某个已结算窗口有 10,000 个任务，则允许的失败数量为：

```text
允许失败数 = 10,000 × (1 - 0.99) = 100
实际失败 70 个时，已使用预算 = 70 / 100 = 70%
```

这是固定窗口的示例。滚动窗口中分母、失败数和允许失败数都会变化，“剩余预算”不是月初发放后只减不增的账户余额。

Google SRE 用燃烧率描述当前失败速度相对目标容忍速度的倍数：[7]

```text
燃烧率 = 某观测窗口内的失败率 / (1 - SLO)
```

目标为 99%，近期失败率为 5%，燃烧率就是 5。对按任务计数的 SLO，估计何时耗尽预算还需要考虑未来任务量；采购业务有明显峰谷，不能直接按自然时间线性推算。

Google SRE 的多窗口方法同时使用长窗口和短窗口，分别确认问题的持续影响和是否仍在发生。[7] 本文建议把这一思路映射为以下操作约定，具体阈值由流量、任务周期和响应成本确定：

| 观察到的情况 | 对应行动 |
| --- | --- |
| 长、短窗口均显示持续快速消耗 | 呼叫值班，限制影响范围，调查当前变更 |
| 较慢但持续的预算消耗 | 创建修复任务，暂停扩大相关灰度 |
| 未知动作明显积压 | 限制相关写入并启动对账，不等待业务 SLI 结算 |
| 已确认越权或重复下单 | 立即按业务严重度止损，不以预算余额为放行理由 |

低流量任务需要额外小心。一个失败就可能使分钟级比例达到 100%，因此应同时展示计数、窗口内任务量和任务年龄。严重安全事件独立触发处置，不应被最小样本量规则压住。

错误预算最后必须对应负责人可以执行的动作：谁暂停灰度、谁决定恢复、需要看哪些证据。如果没有这些约定，SLO 只是另一个报表指标。

## 五、一次 Agent 发布需要通过哪些验证

### 1. 先定义这次发布究竟改变了什么

本文建议为每个任务绑定一份执行配置清单，记录应用、工作流、提示模板、模型配置、工具契约、策略、检索数据和验收器的版本。例如：

```json
{
  "release_id": "purchase-2026-10-22-r2",
  "workflow_version": "purchase-v4",
  "prompt_version": "planner-v12",
  "model_configuration": "model-config-v7",
  "tool_contract_version": "erp-v3",
  "policy_version": "purchase-policy-v9",
  "retrieval_snapshot": "supplier-index-v18",
  "validator_version": "order-check-v5"
}
```

这使事故调查能够回答“哪些任务使用了同一组行为配置”。对于无法固定版本的外部模型或数据源，应保存可获得的标识与时间信息，并承认无法完全复现的部分。

长任务跨越部署时，运行中的任务应继续使用兼容的执行逻辑，或通过经过验证的迁移切换。恢复程序不能默认把旧任务的历史直接交给新工作流解释。

### 2. 离线评测要覆盖重复运行和恢复路径

从 τ-bench 与可靠性研究可以推导出一套面向本文场景的验证矩阵：[1][2]

| 验证维度 | 怎么构造用例 | 需要检查的结果 |
| --- | --- | --- |
| 业务正确性 | 正常订单、复杂约束、需要拒绝的请求 | 权威状态和策略检查都通过 |
| 重复运行稳定性 | 同一输入多次独立执行 | 成功率、全部成功比例和失败类型 |
| 输入与环境扰动 | 等价改写、字段顺序变化、支持范围内的接口差异 | 关键业务约束仍成立 |
| 故障鲁棒性 | 超时、限流、鉴权失败、Worker 中断 | 有界重试、明确失败或合规接管 |
| 恢复正确性 | 外部已成功但本地缺失回执 | 不重复写入，能关联已存在结果 |

每次离线执行需要重置测试环境，避免前一次订单污染下一次结果。对关键失败要核查轨迹与权威状态，不能把另一个模型的打分当作最终业务证据。

这些维度用于指导测试设计，不是论文已经替采购系统验证过的发布标准。

### 3. 影子执行必须隔离写入

影子流量可以比较新旧版本的检索、计划与工具参数。但对真实用户请求执行两遍下单，会把验证过程本身变成事故来源。

建议在写入边界截断影子执行，将写调用发送到隔离环境或模拟器。影子结果能够支持“新版本选择了什么”的比较；真实写入、并发和恢复行为，还需要单独验证。

### 4. 灰度需要稳定分组和成熟样本

Google SRE 的灰度实践强调通过受控发布观察新版本表现。[8] 应用于本文案例时，可以按任务或租户稳定分组，让同一任务及其重试留在同一版本，并保留同期对照组。

比较时至少对齐任务类型、难度和观察时段。新版本碰巧只收到简单任务，或只运行在 ERP 低负载时段，都会使成功率比较失真。主指标还必须等待任务到达结算点，不能只统计先完成的简单任务。

“灰度跑了 100 个任务，零失败”也不足以证明失败率低于 0.1%。在独立同分布的伯努利假设下，零失败时失败概率的单侧 95% 上界为：

```text
上界 = 1 - 0.05^(1/n)
n = 100 时，上界约为 2.95%
```

这是根据零失败概率 `(1 - p)^n` 推导的统计示例。在该假设下，约 3,000 个独立样本零失败，才把上界压到约 0.1%；它仍不能覆盖未出现过的业务场景。共享故障、相同模板与同一租户的相关性还会削弱独立性假设。

因此，扩大灰度需要组合证据：成熟任务的表现、分场景结果、关键恢复用例，以及安全事件。若反复查看数据并随时决定放行，还应预先定义观察节点或采用适合序贯观察的方法，避免把普通固定样本结论用于任意停止规则。

## 六、超时之后，为什么不能直接重试

回到开篇的采购事故。调用超时至少对应三种外部事实：请求没有到达，请求到达但尚未完成，以及请求已经成功但回执丢失。调用方单凭超时无法区分它们。

本文建议把动作状态与任务状态分开管理。任务可能仍在执行，而某次写入的结果已经进入未知状态：

```text
PREPARED：动作身份和意图已持久化
DISPATCHED：已尝试向外部系统发送
CONFIRMED：有权威证据证明动作成功
REJECTED：有明确证据证明请求被拒绝且未产生目标副作用
UNKNOWN：是否产生副作用尚无法确认
```

从 `DISPATCHED` 发生超时或进程中断时，应按证据进入 `UNKNOWN`。`CONFIRMED` 也只是说明动作发生了，是否满足任务要求仍需业务验收。

### 1. 幂等键必须指向同一个业务动作

《Implementing Linearizability at Large Scale》提出 RIFL，通过唯一 RPC 身份、完成记录及其生命周期管理，支持故障下的重复请求识别。[4] 其机制说明：可靠去重需要请求身份与已完成结果共同参与。

映射到采购系统，可以在首次发送前持久化一个稳定的 `action_id`，并让它关联任务、操作类型和参数摘要。随后所有恢复尝试都使用这个身份。不能在 Worker 重启后换一个新键，也不能把参数不同的新业务意图塞进同一个键。

但发送幂等键不等于整个系统已具有 exactly-once 保证。接收方还需要确保：

1. 去重检查与业务写入具有所需的原子性，或等价的正确性保证。
2. 同一个键与不同参数的冲突能够被拒绝。
3. 已完成结果可以查询或在重复请求中返回。
4. 去重记录的保存时间覆盖调用方可能重试和恢复的时间范围。

RIFL 的结果建立在其系统协议与假设之上，不能直接推广为任意 ERP API 的保证。第三方接口的能力要逐项核实。

### 2. 查询不到，不一定意味着可以重试

对于 `UNKNOWN` 动作，恢复流程应先按动作身份查询外部结果：

| 查询结果 | 建议处置 |
| --- | --- |
| 找到唯一且匹配的结果 | 关联外部 ID，确认动作，再做业务验收 |
| 找到结果但参数不匹配 | 停止自动执行，按数据冲突调查 |
| 查询服务不可用 | 保持未知，退避核对或转人工 |
| 暂时查不到 | 判断读一致性、请求是否仍在飞行，以及接收方的幂等能力 |

如果查询读取的是有延迟的副本，“不存在”可能只是暂时不可见；即使此刻确实不存在，原请求也可能仍在执行。只有接收方提供可靠去重，或能够确定原尝试已终止且不会稍后提交，才具备安全重试的条件。

当外部系统既不支持稳定去重，也无法按动作身份核查结果时，应把这种限制显式暴露到产品与运维流程。高影响写入可以转人工核对，不能宣称已经自动保证不重复。

## 七、回滚版本、补偿业务和恢复数据要分别设计

### 1. 代码回滚改变后续执行，已发生动作需要业务处理

把程序从新版本切回旧版本，不会自动撤销 ERP 中已经创建的订单。事故期间可以先限制相关写入、继续接收迟到回执并开展对账，再判断已发生的动作是否需要冻结、取消或其他补偿。

《Sagas》研究将长事务组织为一系列子事务，并在失败时用补偿事务处理已经完成的部分。[5] 对采购场景的工程启发是：补偿必须按业务语义设计。取消订单可能产生费用，已发货订单可能需要退货；补偿也可能失败，需要自己的状态记录与重试规则。

因此，应分别检查代码和状态版本的兼容性、未完成任务的续跑方式，以及已发生动作的补偿条件。

### 2. 数据库恢复不能重置外部世界

假设任务库恢复到昨晚 23:00，而 ERP 保留了今天上午已经创建的订单。本地历史中的“尚未下单”，已经不是完整的业务事实。如果恢复后直接重放任务，系统可能再次采购。

RTO 表示期望恢复服务所需的时间目标，RPO 表示可接受的数据丢失时间窗口。本文建议把恢复验收分成两个里程碑：恢复查询与核对能力，以及完成影响区间对账后恢复自动写入。进程启动只能证明其中很小的一部分。

对于本地记录丢失的区间，可以结合外部审计、订单业务关联键、持久化消息或独立保留的动作记录重建已发生事实。但这些来源必须事先具备可检索性和足够保留时间；如果无法重建，就要保留未决任务清单，进入人工处置。

恢复写入前，至少需要知道哪些任务已确认完成、哪些仍然未知、哪些允许重试、哪些需要补偿。未知状态的数量和年龄应继续可见。

## 八、把恢复能力变成一场可以重复执行的实验

以下是一份针对开篇故障的演练设计，未在本文中实际执行。目标是验证：在外部写入成功、本地未收到回执时，系统能否恢复任务而不重复下单。

实验环境需要一个支持按动作身份去重和查询的模拟 ERP、一份持久化动作账本，以及能够控制进程中断和响应丢失的故障注入点。所有写入都发生在隔离环境。

| 步骤 | 故障或操作 | 验收条件 |
| --- | --- | --- |
| 1 | 正常提交一次采购 | 形成一个动作身份与唯一外部订单 |
| 2 | ERP 提交后丢弃响应 | 本地将结果视为未知，不直接判定无副作用 |
| 3 | 结束并重启 Worker | 恢复后沿用原动作身份 |
| 4 | 按动作身份查询结果 | 关联已存在订单，不新增订单 |
| 5 | 延迟查询可见性或重复发送回执 | 暂时查不到不触发无保护重试，重复回执不重复推进业务 |
| 6 | 将本地数据恢复到较旧快照 | 对账未结束前限制自动写入 |
| 7 | 让任务超过截止点后再恢复成功 | 保留超时失败，同时记录最终完成 |

还应加入一个反例：让去重记录先于恢复窗口过期，检查系统能否发现保证条件已失效并停止自动重试。这样才能验证实现是否真正依赖了声明的前提。

演练记录应包含发现时间、限制写入时间、恢复查询时间、完成对账时间、恢复写入时间、重复订单数，以及未决动作数量和最老年龄。检查终态之外，还要核查动作身份是否变化、是否发生未经许可的写入，以及补偿是否留下审计记录。

事故或演练结束后，改进项要进入下一次发布验证。例如，“接口增加按动作身份查询能力”应对应新的核对用例；“恢复时保留原动作身份”应对应跨重启的重复提交检查。这样，恢复经验才能持续改变发布质量。

## 九、把这些机制放进同一条运营流程

可以用下面的关系检查系统是否形成闭环：

```text
业务承诺
  → 任务契约与验收证据
  → SLI、错误预算与安全事件
  → 发布放行 / 限制流量 / 暂停写入
  → 外部事实核对、恢复与补偿
  → 回归用例与下一次发布验证
```

对已经有 Trace、但缺少运营机制的团队，建议先实现完整任务台账与结果验收，再给高影响动作补齐稳定身份和未知状态核对，然后接入发布对照与故障演练。这个顺序能让每一步都有可观察的验证结果。

以开篇采购任务为验收题：ERP 已落单、回执丢失、Worker 重启后，系统应该能回答“原动作是什么、外部发生了什么、当前允许做什么”，并把这次任务是否按时完成如实记录下来。能给出这些证据，才有依据继续扩大自动化范围。
