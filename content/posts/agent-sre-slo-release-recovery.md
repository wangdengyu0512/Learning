监控面板显示 HTTP 成功率为 99.9%，模型 API 也没有明显报错，但采购人员仍然抱怨任务经常卡住。还有一些任务返回“完成”，ERP 中却没有正确订单。

这说明监控正在描述局部组件，用户关心的业务结果尚未进入服务目标。Trace 能帮助解释一次失败，但持续运营还需要决定什么算失败、何时告警、是否暂停发布，以及如何恢复。

**可靠性工作从可观察的用户结果开始，再把结果连接到可执行的运营决策。**

## 一、先定义服务边界和责任

一个采购 Agent 可能依赖检索服务、模型 API、工作流运行时、审批系统与 ERP。某个组件可用，并不意味着整条任务链可用。

先把产品提供的能力说清楚：用户提交符合条件的采购需求后，系统在约定时间内完成正确且获批的订单，或返回明确、可处理的拒绝与接管状态。

这里至少有三种结果：自动完成、按规则拒绝、需要人工处理。是否把后两者纳入服务成功，取决于产品承诺；不能在事故发生后临时改变口径。

Google SRE 的 SLO 实践强调从用户体验选择服务指标，并让目标服务于可靠性决策。[1] 对 Agent，这意味着不能只把“接口返回 200”当成任务成功。

## 二、区分 SLI、SLO 和响应规则

| 概念 | 含义 | 采购示例 |
| --- | --- | --- |
| SLI | 实际测量服务表现的指标 | 合格任务中在时限内正确完成的比例 |
| SLO | 指标在指定窗口中的目标 | 30 天内达到某个业务认可的比例 |
| 错误预算 | 目标允许的失败空间 | 目标对应的允许失败任务量 |
| 响应规则 | 指标偏离后要采取的行动 | 暂停扩大灰度、调查依赖或回滚 |

SLO 要包含对象、分母、成功定义、时间窗口和数据来源。一个没有分母定义的“成功率 99%”，在实现中很容易被各团队计算成不同结果。

业务安全约束应单独表达。越权和重复采购不能因为“错误预算还有余额”就被接受，可以设置立即处置的事件规则，与一般可用性目标同时运行。

## 三、给长任务设计不会失真的分母

Agent 任务可能持续数分钟，也可能等待一天审批。如果只统计已经完成的任务，卡住的任务会消失在分母里，成功率反而提高。

一种方案是按任务进入服务的时间组成队列，待预先约定的截止时间到达后结算结果。未完成且超过截止时间的任务计入时限失败，稍后恢复成功可以另记最终完成状态，但不抹去原来的超时事实。

本文示例采用如下口径：

```text
分母：在观察队列中、满足准入条件且已到结算截止点的任务
分子：这些任务中，在截止点前完成全部业务验收条件的任务
```

人工审批等待可以有独立计时：用户总等待时间反映完整体验，系统处理时间用于定位平台责任。若某项 SLO 排除人工等待，暂停与恢复事件必须可审计，并同时展示端到端等待。

用户取消、无效输入、被策略拒绝和内部崩溃也需要预定义归类。不能把内部错误包装成“用户取消”，也不能无限扩大“不支持场景”来提高成功率。

## 四、用一组指标覆盖任务全程

| 指标 | 观察问题 | 适合的数据来源 |
| --- | --- | --- |
| 任务有效完成率 | 用户目标是否按时实现 | 任务事实表与验收结果 |
| 确认响应延迟 | 用户多久知道任务已被接收 | 接入时间与持久化确认 |
| 系统处理时长 | 平台处理本身是否拖延 | 状态事件与运行时记录 |
| 未知动作滞留时间 | 外部副作用是否长期无法核对 | 动作账本与核对记录 |
| 人工接管比例 | 自动化是否在扩大人工负担 | 接管事件与结果 |
| 每个有效任务成本 | 可靠性改善是否付出过高代价 | 调用、计算与人工统计 |
| 安全异常数量 | 是否出现越权或重复副作用 | 审计与业务对账 |

用户或任务 ID 应放进可检索事件与 Trace，避免把它们当作无限增长的指标标签。聚合指标可以按场景、适配器版本和有限的错误类别划分。

不能只依赖采样 Trace 统计全部任务成功率。采样用于诊断时，需要另有完整任务事实或计数机制支持 SLI，防止关键失败未被采样。

## 五、把错误预算算清楚

假设业务选择 30 天、99% 的任务有效完成率目标，某个已经结算的窗口中有 10,000 个合格任务：

```text
允许失败数 = 10000 × (1 - 0.99) = 100
```

如果实际失败 70 个，按这一固定样本计算还剩 30 个失败的空间。滚动窗口中，任务会进入和离开窗口，预算也会变化；它不是月初分配后不再变化的余额。

燃烧率用于观察当前失败速度相对目标有多快：

```text
燃烧率 = 观测失败率 / (1 - SLO)
```

目标是 99%，某段窗口失败率为 5%，燃烧率就是 5。若流量和失败比例维持不变，这表示消耗预算的速度约为目标允许速度的五倍。[2]

对按请求计数的 SLO，这个时间推算依赖流量分布。采购任务在工作日集中，不能只按自然时间线性外推。

## 六、告警要同时考虑速度、持续时间和处置能力

一个失败任务可能让低流量服务的分钟失败率瞬间达到 100%。只用单个短窗口，容易造成频繁告警；只看长窗口，又可能错过正在扩大的事故。

Google SRE 工作手册介绍了多窗口燃烧率告警，用较长窗口确认消耗规模、较短窗口判断问题仍在持续。[2] 实际阈值应根据服务目标、任务量和响应成本配置，不必照搬示例数值。

长任务的完成指标有天然滞后。因此还需要观察队列最老任务年龄、Worker 心跳、持续 UNKNOWN 的动作数量和依赖失败等前置信号。它们用于提前诊断，不能直接替代最终业务 SLI。

每个告警应附带可执行入口：影响范围、相关任务查询、值班责任人和初步操作。没有处置动作的信息可以进入看板或工单，避免把所有波动都升级为即时呼叫。

## 七、发布的对象比代码更多

Agent 的行为可能因提示模板、模型版本、工具 Schema、权限规则、检索配置或数据索引改变。

建议为一次任务记录配置清单：

```json
{
  "application_version": "app-42",
  "workflow_version": "purchase-v3",
  "prompt_version": "purchase-plan-8",
  "model_configuration": "model-config-12",
  "tool_schema_version": "erp-tools-5",
  "policy_version": "purchase-policy-7",
  "retrieval_configuration": "retrieval-9"
}
```

外部模型不一定提供不可变权重版本。能够固定的部分应固定，无法固定的部分应记录提供方返回的标识、配置和观测时间，避免宣称具有不存在的完全可复现性。

一次发布尽量保持可归因的变更范围。若模型、提示、索引和权限同时修改，即使发现退化，也很难识别原因。

## 八、让灰度发布对应真实业务边界

可按场景、租户或任务分组逐步扩大流量。分组应稳定，运行中的任务通常继续使用其兼容的工作流版本，避免在恢复时突然切换控制逻辑。

灰度门槛需要同时看业务成功率、延迟、未知动作和安全护栏。小流量中“尚未出现错误”不是安全证明，还需要离线回归和定向故障用例。

影子流量适合比较检索和规划输出，但不能让影子执行器再次向生产 ERP 创建订单。具有写入副作用的步骤应使用模拟目标、只读预览或明确隔离的测试环境。

回滚也需要兼容性。回退代码无法自动撤销已经创建的订单，也不能恢复已被不可逆迁移删除的数据。数据库和工作流演进应保留回退窗口，外部副作用则进入核对与补偿。

## 九、故障期间先阻止影响扩大，再恢复任务

遇到重复采购风险时，可按以下顺序处置：

1. 限制相关适配器的新写入，保留查询与核对能力。
2. 确定受影响时间、版本、租户与动作集合。
3. 对结果未知的动作查询 ERP，关联已发生的订单。
4. 按业务规则冻结、取消或补偿重复结果。
5. 验证修复后，以受控范围恢复写入。

暂停新写入不能保证已经派发的请求停止。隔离期间仍需持续处理迟到回执，并查询外部事实。把所有任务一律重试，可能扩大原来的重复副作用。

事故记录应区分已确认影响和待调查范围。某张订单金额代表潜在承诺还是实际付款，也需要按业务事实判断，不能混为一谈。

## 十、恢复目标必须覆盖外部系统

RTO 描述希望在多久内恢复服务，RPO 描述可以接受多大的数据丢失窗口。二者是恢复规划目标，需要通过演练验证，而不是只写在文档中。

假设恢复了昨晚的任务数据库，今天上午创建的 ERP 订单却仍然存在。若平台不知道这些动作已经发生，恢复后可能再次创建订单。

因此，恢复范围应包括动作账本、工作流历史、审批记录、外部幂等记录、必要证据与密钥配置。索引可以从事实重建，也需要估算重建时间及重建期间的服务方式。

| 故障 | 恢复关注点 | 验证条件 |
| --- | --- | --- |
| Worker 进程丢失 | 接管与检查点 | 原动作身份不变 |
| 任务数据库恢复到旧时间点 | 外部动作核对 | 不把已完成采购再次派发 |
| 检索索引不可用 | 重建与直接查询降级 | 高影响动作仍获取权威依据 |
| 模型服务不可用 | 排队、限流、替代或接管 | 任务不会无限重试积压 |
| 凭据或授权服务故障 | 安全恢复与权限校验 | 不因降级放开写入权限 |

备份成功只能证明备份任务完成。恢复演练还要检查数据是否可读、应用是否兼容、外部状态能否核对，以及恢复后的任务是否满足业务约束。

## 十一、最小实践：演练一个失去回执的采购任务

在隔离测试环境准备一个具有幂等能力的模拟 ERP、持久化任务表和可查询的动作记录。以下步骤是实验设计，不是已执行报告。

先让 ERP 创建订单但不返回响应，观察动作进入 UNKNOWN；随后重启 Worker，验证恢复流程能找到原订单。再恢复一份较旧的本地数据快照，检查外部动作核对如何防止重复执行。

实验记录至少包括：故障注入时间、发现时间、限制写入时间、恢复时间、未知动作数量、重复订单数量和未恢复任务清单。

为了验证告警，还可以让一批任务超过截止点，确认它们进入 SLI 分母并计为失败。然后恢复任务，检查系统是否同时保留“曾经超时”和“最终完成”两种事实。

演练结束后，应形成具体改进项，例如增加按动作键查询接口、修复超时覆盖成功的状态转换，或补充恢复后对账。每项改进对应可再次运行的验证条件。

## 十二、让服务目标进入日常决策

服务目标需要有责任人和定期复核节奏。预算消耗过快时，可以暂停扩大灰度、减少非必要变更，优先修复主要失败来源；持续富余时，也可以重新评估目标是否合适。

采购高峰、业务类型和自动化范围变化后，原来的 SLO 可能不再代表用户体验。调整时应保留历史口径，解释新旧差异，避免在可靠性下降时悄悄降低标准。

可运营的 Agent 系统能够把一个用户抱怨追到具体任务，把任务失败转成可度量的服务问题，再把修复和恢复结果反馈到下一次发布决策。
