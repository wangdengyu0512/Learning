假设一个财税 Agent 收到这样的问题：

> 这张增值税专用发票能否抵扣？如果可以，需要哪些证据；如果不可以，是哪项条件不满足？

大模型可以根据文字描述生成一段回答，向量数据库也可以召回发票抵扣政策。但要稳定地完成判断，系统还需要理解一组更精确的问题：

- 当前对象究竟是增值税专用发票、普通发票，还是其他扣税凭证；
- 销售方和购买方是否为合法纳税主体，各自在交易中承担什么角色；
- “可抵扣”是发票的固有类型，还是在特定用途、期限和业务状态下产生的资格；
- 缺少认证记录意味着“不符合条件”，还是仅仅意味着“系统暂时不知道”；
- 哪些条件适合逻辑推理，哪些条件必须检查当前数据，哪些条件应交给外部规则服务计算。

这些问题仅靠数据库表结构或 Prompt 很难长期维护。数据库可以保存发票、企业和认证记录，却不会自然说明这些对象在业务上意味着什么；JSON Schema 可以检查接口字段，却不会推出“增值税专用发票也是增值税发票”；大模型能够理解自然语言，却无法保证每次都遵守同一套概念边界和业务约束。

本体要解决的正是这一层问题：**把领域中的概念、关系、约束和公理写成共享、显式、形式化的语义规范，让机器不仅能保存事实，还能分类、推理、校验和对齐知识。**

对 Agent 而言，本体不是一张更复杂的关系图，而是机器理解领域的“世界观”：世界中有哪些对象，它们可以处于什么状态，彼此存在什么关系，哪些结论能够从已有事实中推出，以及哪些动作在当前状态下允许发生。

## 一、什么是本体：从术语表走向形式化语义

本体常被定义为“对共享概念化的显式、形式化规范”。这句话包含四个关键要求：

| 关键词 | 含义 | 工程产物 |
| --- | --- | --- |
| 概念化 | 选择领域中重要的对象、关系和规则 | 概念模型、类层级、关系模型 |
| 共享 | 让业务专家、系统和 Agent 使用共同含义 | 术语定义、命名规范、评审记录 |
| 显式 | 把隐含知识写成可以检查的定义 | 公理、约束、规则和注解 |
| 形式化 | 使用机器可解释的语言表达 | RDF、RDFS、OWL、SHACL |

一份术语表可以解释“纳税人”“发票”“抵扣”分别是什么意思，一棵分类树可以说明专用发票属于增值税发票，但本体还要继续表达：

- 增值税普通发票和增值税专用发票是否互斥；
- 发票的销售方必须是什么类型的主体；
- 哪些对象可以参与开票、认证和申报过程；
- 满足哪些逻辑条件的对象可以被自动归类为某种凭证；
- 某个事实来自制度文件、业务系统，还是模型推导；
- 当前实例缺少必要数据时，系统应如何报告。

因此，本体不是“高级词典”，也不只是画一棵类树。它是对领域语义作出的一组可计算承诺。

### RDF 三元组：最小知识表达

RDF 使用“主语、谓词、宾语”组成三元组：

```text
主语 Subject + 谓词 Predicate + 宾语 Object
```

例如：

```turtle
@prefix tax: <https://example.org/tax/> .
@prefix xsd: <http://www.w3.org/2001/XMLSchema#> .

tax:inv-001
    a tax:VATSpecialInvoice ;
    tax:amount "1000.00"^^xsd:decimal ;
    tax:hasSeller tax:company-A .
```

这里表达了三个事实：`inv-001` 是增值税专用发票，金额为 1000 元，销售方是 `company-A`。RDF 提供图数据模型，但它本身并没有定义 `VATSpecialInvoice` 的完整含义，也不会检查金额是否缺失。概念语义主要由 RDFS 和 OWL 表达，实例形状主要由 SHACL 校验。

## 二、OWL 本体的核心组成

在 OWL 体系中，最常用的建模元素包括类、个体、属性和公理。理解这些元素的职责，是从数据库建模转向语义建模的第一步。

### 1. Class：类与概念

类表示一类可以拥有实例的事物，例如：

- `Invoice`：发票；
- `VATInvoice`：增值税发票；
- `Taxpayer`：纳税人；
- `InvoicingProcess`：开票过程。

常见类关系包括：

- `rdfs:subClassOf`：子类关系；
- `owl:equivalentClass`：两个类具有相同的逻辑外延；
- `owl:disjointWith`：两个类不能拥有共同实例。

如果定义 `VATSpecialInvoice` 是 `VATInvoice` 的子类，那么任何专用发票实例都可以被推理为增值税发票。这个结论不需要应用代码再次判断。

### 2. Individual：个体与现实对象

个体是类的具体实例。例如：

- `inv-001` 是某张具体发票；
- `company-A` 是某个具体企业；
- `filing-2026-10` 是某次具体申报活动。

“发票”是类，“2026 年 11 月 4 日开具的编号为 001 的发票”是个体。类表达可重复实例化的类型，个体表达现实世界中的具体对象。

### 3. ObjectProperty：对象之间的关系

对象属性连接两个资源，例如：

- `hasSeller`：发票具有销售方；
- `hasPurchaser`：发票具有购买方；
- `belongsToLedger`：凭证属于账套；
- `producedBy`：凭证由某个业务过程产生。

对象属性可以声明 `domain` 和 `range`，即定义域和值域：

```turtle
tax:hasSeller a owl:ObjectProperty ;
    rdfs:domain tax:Invoice ;
    rdfs:range tax:Taxpayer .
```

这项声明的逻辑含义是：凡是出现在 `hasSeller` 主语位置的对象，都可以被推出是 `Invoice`；凡是出现在宾语位置的对象，都可以被推出是 `Taxpayer`。

需要特别注意：**OWL 中的 domain 和 range 是推理规则，不是数据库字段校验。** 如果一条数据把未声明类型的对象放在 `hasSeller` 主语位置，推理机通常会补充它的类型，而不是直接报告“类型错误”。如果目标是检查当前数据是否符合输入规范，应使用 SHACL。

### 4. DatatypeProperty：对象到字面量的属性

数据属性把对象连接到字符串、数字、日期等字面量，例如：

- `amount`：金额；
- `issueDate`：开票日期；
- `invoiceNumber`：发票号码；
- `taxpayerIdentifier`：纳税人识别号。

数据类型通常使用 XML Schema Datatypes，例如 `xsd:string`、`xsd:decimal`、`xsd:date` 和 `xsd:dateTime`。

### 5. AnnotationProperty：解释和治理信息

注解属性面向人和治理流程，通常不参与领域推理。常见内容包括中文标签、概念定义、同义词、来源标准、维护责任人和版本信息。

一个只有类名而没有定义、来源和边界说明的本体，很快就会退化成另一份难以治理的代码表。

### 6. Axiom：让知识能够被推导

公理描述领域中始终成立的逻辑关系。例如：

```text
增值税专用发票 是 增值税发票 的子类
增值税普通发票 与 增值税专用发票 互斥
每张发票的销售方只能是纳税主体
影响轴承的机械故障 等价于 轴承相关故障
```

公理的价值不是让模型“看起来严谨”，而是让推理机能够自动分类、发现矛盾，并减少散落在应用代码中的重复判断。

### TBox 与 ABox：概念规范和现实事实

语义系统通常把知识区分为两个层次：

- **TBox**：类、属性、公理等概念层知识，描述世界可能如何组织；
- **ABox**：具体个体及其事实，描述当前世界中实际知道什么。

本体主要定义 TBox，知识图谱通常同时包含 TBox 和大量 ABox。对 Agent 来说，TBox 是相对稳定的领域世界观，ABox 则是不断变化的世界状态。

## 三、本体、ER、JSON Schema 与知识图谱有什么不同

这些技术经常同时出现在企业架构中，但它们解决的问题并不相同。

| 模型 | 核心问题 | 主要能力 | 典型用途 |
| --- | --- | --- | --- |
| ER / 关系模型 | 数据怎样存储和关联 | 主外键、事务、完整性 | 业务数据库 |
| JSON Schema | 一个报文结构是否合法 | 类型、必填、枚举、格式 | API 入参和消息校验 |
| OWL 本体 | 领域中的事物意味着什么 | 分类、蕴含、等价、互斥、一致性检查 | 共享语义、知识推理 |
| SHACL | 当前 RDF 图是否满足数据形状 | 基数、类型、取值、路径和条件校验 | 数据质量、运行时护栏 |
| 知识图谱 | 当前拥有哪些实体、关系和事实 | 图查询、关联分析、知识服务 | 搜索、分析、RAG、Agent |

可以用一句话概括：

> ER 关心“数据怎么存”，JSON Schema 关心“消息长什么样”，本体关心“领域里的东西意味着什么、能推出什么”，SHACL 关心“当前这批图数据是否合规”。

本体也不替代数据库。发票系统仍然需要关系数据库处理高并发写入、事务和结算一致性；本体提供的是跨系统的语义解释。一个本体概念可能映射到多张表，一张表中的字段也可能映射到不同的领域角色。

知识图谱与本体同样不是同义词。知识图谱可以没有严格本体，只保存实体和关系；本体也可以只定义概念规范，而不承载海量业务实例。工程上更常见的组合是：用本体约束知识图谱的语义，用图数据库保存事实，再由查询、推理和校验服务对外提供能力。

## 四、从能力问题开始：本体建模七步法

本体建模最常见的失败方式，是先打开 Protégé 画一棵庞大的类树，几个月后才发现它不能回答真正的业务问题。更稳妥的做法，是先定义模型必须具备的能力，再逐步增加语义承诺。

### 第一步：明确范围和能力问题

能力问题（Competency Questions）是本体必须回答的问题，也是后续查询和测试的来源。以财税本体为例，第一阶段可以只回答：

1. 一张凭证属于哪类税务凭证？
2. 某张发票的销售方和购买方是谁？
3. 一张发票是否具备申请抵扣的必要信息？
4. 哪些凭证与某次申报活动相关？
5. 某个抵扣结论依据了哪些事实和规则？

能力问题需要尽量具体，并明确时间、组织、状态和证据边界。“理解所有财税知识”不是可验收的范围，“识别缺少购买方信息的专用发票”才是。

### 第二步：复用已有本体和行业标准

复用对象可以包括 BFO、DOLCE、SUMO 等顶层本体，时间、组织、单位等通用词汇，国家标准、行业标准和监管术语，以及企业已经治理过的主数据和指标口径。

复用不是直接导入所有外部类。团队应先判断许可证、维护状态、表达能力、版本策略和本地业务边界，再选择直接引用、局部复用或建立映射模块。

### 第三步：建立领域术语清单

术语清单至少应记录：

| 字段 | 示例 |
| --- | --- |
| 首选名称 | 增值税专用发票 |
| 唯一标识 | `VATSpecialInvoice` |
| 正式定义 | 符合特定法规和开具要求的增值税发票类型 |
| 上位概念 | 增值税发票 |
| 同义词 | 专票 |
| 来源 | 法规、标准或企业制度 |
| 负责人 | 税务领域专家 |
| 状态 | 草案、已审核、已废弃 |

这一步的重点不是收集越多词越好，而是消除同名异义和异名同义，并把每个术语的定义依据保留下来。

### 第四步：构建类层级

类层级可以自顶向下、自底向上，或采用混合方式。一个轻量的凭证分类可以是：

```text
凭证
├── 税务凭证
│   ├── 发票
│   │   └── 增值税发票
│   │       ├── 增值税专用发票
│   │       └── 增值税普通发票
│   └── 完税凭证
└── 会计凭证
    ├── 原始凭证
    └── 记账凭证
```

类层级必须表达真实的“是一种”关系。销售方不是发票的一种，开票也不是发票的一种；前者是角色或参与方，后者是过程。仅仅因为两个词经常一起出现，不代表它们应该处于同一分类树中。

### 第五步：定义属性、定义域和值域

围绕能力问题定义必要关系，例如：

```text
发票 --hasSeller--> 纳税人
发票 --hasPurchaser--> 纳税人
发票 --generatedBy--> 开票过程
申报活动 --usesEvidence--> 税务凭证
抵扣结论 --supportedBy--> 证据
```

如果一个对象需要独立身份、生命周期、来源或更多关系，就不应把它压缩成字符串。例如，销售方不应只是 `sellerName` 文本，因为企业还可能有纳税人识别号、组织关系、风险状态和历史名称。

### 第六步：添加公理、规则和 SHACL 约束

三类机制各有分工：

- OWL 表达稳定的概念语义和可蕴含关系；
- SHACL 检查当前 RDF 图的结构和取值；
- 规则语言或应用服务处理多条件业务判断和外部计算。

不要为了“形式化程度高”而把所有业务逻辑都塞进 OWL。税率计算、时间窗口、外部验真和频繁变化的政策条件，往往更适合由版本化规则服务处理。

### 第七步：灌入实例、推理验证和迭代

至少执行四类测试：

1. **一致性测试**：本体是否存在不可满足类或逻辑冲突；
2. **能力问题测试**：SPARQL 查询能否回答最初的问题；
3. **SHACL 测试**：错误数据能否被准确拦截；
4. **回归测试**：本体变更后，已有推理和查询是否保持预期行为。

建模不是一次性交付。每次新增概念或公理，都意味着扩大了系统的语义承诺，应经过评审、测试和版本发布。

## 五、一个可运行的极简财税本体

下面用一个最小示例串起类、属性、公理和实例。示例只用于说明建模机制，不代表完整的税务法规或真实抵扣规则。

```turtle
@prefix tax: <https://example.org/tax/> .
@prefix owl: <http://www.w3.org/2002/07/owl#> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .
@prefix xsd: <http://www.w3.org/2001/XMLSchema#> .

tax:ontology a owl:Ontology .

# Classes
tax:Taxpayer a owl:Class .
tax:Invoice a owl:Class .
tax:VATInvoice a owl:Class ;
    rdfs:subClassOf tax:Invoice .

tax:VATSpecialInvoice a owl:Class ;
    rdfs:subClassOf tax:VATInvoice ;
    owl:disjointWith tax:VATNormalInvoice .

tax:VATNormalInvoice a owl:Class ;
    rdfs:subClassOf tax:VATInvoice .

# Object properties
tax:hasSeller a owl:ObjectProperty ;
    rdfs:domain tax:Invoice ;
    rdfs:range tax:Taxpayer .

tax:hasPurchaser a owl:ObjectProperty ;
    rdfs:domain tax:Invoice ;
    rdfs:range tax:Taxpayer .

# Datatype properties
tax:amount a owl:DatatypeProperty ;
    rdfs:domain tax:Invoice ;
    rdfs:range xsd:decimal .

tax:issueDate a owl:DatatypeProperty ;
    rdfs:domain tax:Invoice ;
    rdfs:range xsd:date .

tax:invoiceNumber a owl:DatatypeProperty ;
    rdfs:domain tax:Invoice ;
    rdfs:range xsd:string .

# Individuals
tax:company-A a tax:Taxpayer .
tax:company-B a tax:Taxpayer .

tax:inv-001 a tax:VATSpecialInvoice ;
    tax:invoiceNumber "001" ;
    tax:amount "1000.00"^^xsd:decimal ;
    tax:issueDate "2026-11-04"^^xsd:date ;
    tax:hasSeller tax:company-A ;
    tax:hasPurchaser tax:company-B .
```

推理机从这些显式事实中可以得到：

```text
inv-001 是 VATSpecialInvoice
inv-001 是 VATInvoice
inv-001 是 Invoice
company-A 是 Taxpayer
company-B 是 Taxpayer
```

后面几个结论不必重复写入每个业务系统。只要类层级和关系语义成立，推理机就可以生成这些隐含知识。

如果同一个实例又被声明为 `VATNormalInvoice`，由于两个类互斥，本体将不一致。这里检查的是逻辑矛盾，而不是简单的字段格式。

### 用 SPARQL 回答能力问题

例如，查询所有专用发票及其交易双方：

```sparql
PREFIX tax: <https://example.org/tax/>

SELECT ?invoice ?seller ?purchaser ?amount
WHERE {
  ?invoice a tax:VATSpecialInvoice ;
           tax:hasSeller ?seller ;
           tax:hasPurchaser ?purchaser ;
           tax:amount ?amount .
}
ORDER BY ?invoice
```

如果查询引擎使用了推理后的图，还可以查询上位类 `Invoice`，同时命中专用发票和普通发票实例。

## 六、为什么还需要 SHACL

OWL 采用开放世界假设：图中没有记录某个事实，不代表这个事实为假，只代表当前不知道。

假设 `inv-002` 没有 `hasPurchaser`：

```turtle
tax:inv-002 a tax:VATSpecialInvoice ;
    tax:amount "800.00"^^xsd:decimal .
```

OWL 不会自然把它判定为“不合格发票”，因为在某个可能的世界中，购买方可以存在，只是当前图没有记录。对于“当前数据必须显式包含购买方”这样的封闭式校验，需要使用 SHACL。

```turtle
@prefix tax: <https://example.org/tax/> .
@prefix sh: <http://www.w3.org/ns/shacl#> .
@prefix xsd: <http://www.w3.org/2001/XMLSchema#> .

tax:VATSpecialInvoiceShape
    a sh:NodeShape ;
    sh:targetClass tax:VATSpecialInvoice ;

    sh:property [
        sh:path tax:invoiceNumber ;
        sh:minCount 1 ;
        sh:maxCount 1 ;
        sh:datatype xsd:string ;
        sh:minLength 1 ;
        sh:message "专用发票必须有且仅有一个非空发票号码"@zh
    ] ;

    sh:property [
        sh:path tax:amount ;
        sh:minCount 1 ;
        sh:maxCount 1 ;
        sh:datatype xsd:decimal ;
        sh:minExclusive 0 ;
        sh:message "发票金额必须是大于零的十进制数"@zh
    ] ;

    sh:property [
        sh:path tax:hasSeller ;
        sh:minCount 1 ;
        sh:maxCount 1 ;
        sh:class tax:Taxpayer ;
        sh:message "专用发票必须关联一个销售方纳税人"@zh
    ] ;

    sh:property [
        sh:path tax:hasPurchaser ;
        sh:minCount 1 ;
        sh:maxCount 1 ;
        sh:class tax:Taxpayer ;
        sh:message "专用发票必须关联一个购买方纳税人"@zh
    ] .
```

这份 Shape 会检查当前图中是否真的存在必要三元组，并生成可定位到具体节点和属性的验证报告。

### OWL 与 SHACL 的职责边界

| 问题 | OWL | SHACL |
| --- | --- | --- |
| 专用发票是否属于增值税发票 | 适合 | 通常不负责 |
| 普通发票与专用发票是否互斥 | 适合 | 可检查，但不是核心职责 |
| 当前发票是否显式填写购买方 | 不适合做缺失报告 | 适合 |
| 金额是否只能出现一次 | 开放世界下不等于表单校验 | 适合 |
| 金额是否大于零 | 通常交给数据约束 | 适合 |
| 概念组合是否造成逻辑不一致 | 适合 | 通常不负责全局逻辑一致性 |

一句实用的判断是：

> OWL 说明“在任何符合本体的世界中，什么语义成立”；SHACL 检查“眼前这张 RDF 图，是否满足应用要求的数据形状”。

两者不是竞争关系。生产系统通常先进行必要推理，再根据约定对原始图或推理闭包执行 SHACL；具体顺序必须写入数据处理契约，否则同一份 Shape 在不同系统中可能得到不同结果。

## 七、SWRL 与业务规则：不要把所有逻辑塞进本体

一些业务结论需要组合多个条件。例如，可以把抵扣资格简化为：

```text
对象是增值税专用发票
+ 发票状态有效
+ 销售方是合法纳税人
+ 业务用途允许抵扣
+ 仍在允许期限内
+ 未被重复抵扣
→ 可以申请抵扣
```

SWRL 可以表达类似的条件推导，但工程上需要谨慎。完整业务规则通常还涉及日期计算、外部验真、政策版本、金额计算、优先级和冲突处理。无限制地混用 OWL 与规则会增加推理复杂度，部分组合甚至无法保证通用推理过程终止。

更可靠的分工是：

- 用 OWL 表达稳定分类和关系语义；
- 用 SHACL 检查输入事实是否完整、类型和取值是否合规；
- 用受限规则引擎处理可解释的条件推导；
- 用应用服务完成外部查询、时间计算和复杂数值逻辑；
- 把规则版本、输入证据和结论来源写回知识图谱。

这样既保留语义推理能力，也能控制在线执行的性能和可解释性。

## 八、顶层本体：为什么要区分对象、过程、角色和信息实体

领域模型规模变大后，一个常见问题是不同团队使用不同的基础范畴。例如，有人把“开票”当成发票类型，有人把“纳税人”当成永久身份，有人把电子文件和它所承载的业务凭证视为同一个对象。

BFO、DOLCE 等顶层本体提供了一套更稳定的基础分类。以 BFO 的核心区分为例：

- **Continuant**：在时间中持续存在的对象，例如企业、人员、设备和文档；
- **Occurrent**：在时间中发生的过程或事件，例如开票、付款、申报和审核。

这个区分可以帮助模型明确：

- 发票信息对象不等于开票过程；
- 企业不等于它在交易中承担的销售方角色；
- 纳税申报表不等于申报行为；
- 付款指令不等于实际付款事件；
- 会计凭证不等于记账过程。

角色也应与主体本身区分。同一个企业在一笔交易中是销售方，在另一笔交易中可能是购买方。把 `Seller` 永久建成 `Enterprise` 的本质子类，会让模型难以表达这种情境变化。更合理的方式是引入交易参与或角色分配：

```text
Enterprise --bearsRole--> SellerRole
SellerRole --realizedIn--> Transaction
Transaction --produces--> Invoice
```

但顶层本体并非项目的必选项。如果应用只服务一个边界清晰的小场景，轻量上层概念就足够。只有在跨财税、制造、供应链等多领域对齐，或者对长期治理和概念严谨性要求较高时，引入 BFO 等顶层本体的收益才会明显超过成本。

## 九、本体如何增强 RAG

传统向量 RAG 主要根据文本相似度召回内容。它擅长找到“说法相近”的段落，却不天然理解严格的类型边界和关系路径。

用户询问“这张发票能否抵扣”时，证据可能分散在发票结构化数据、交易双方主体信息、费用用途、认证与历史抵扣记录，以及当前有效的税务制度文档中。这些信息之间不是简单的文本相似关系，而是一条有类型约束的证据链。

一个本体增强 RAG 流程可以设计为：

```text
用户问题
  ↓
实体识别与实体链接
  ↓
映射到本体概念和关系
  ↓
按类型、组织、时间和状态限定范围
  ↓
沿知识图谱关系查询结构化事实
  ↓
按本体术语扩展向量检索
  ↓
规则推理与 SHACL 证据校验
  ↓
大模型基于证据生成答案
```

本体在这里承担四项职责：

1. **术语归一化**：把“专票”“增值税专用发票”等表达映射到同一概念；
2. **查询扩展**：根据上下位关系，把对“发票”的查询扩展到具体子类；
3. **关系导航**：沿销售方、交易、用途、申报等明确路径获取证据；
4. **结果过滤**：使用类型、状态和规则排除语义上不成立的候选结果。

向量检索、图查询和本体推理不是替代关系。向量检索擅长非结构化文本召回，图查询擅长精确关系和多跳路径，本体推理擅长分类和隐含知识。生产级 RAG 往往需要三者配合。

## 十、本体如何约束 Agent 的工具调用

问答系统生成错误答案的主要后果是误导；Agent 一旦调用真实工具，错误可能直接改变业务状态。因此，Agent 比普通问答系统更需要显式语义和运行时约束。

工具可以被描述为一种可调用能力：

```text
能力：验证发票真实性
输入类型：发票
必要参数：发票号码、开票日期、金额
前置条件：调用主体具有验真权限
输出类型：验真结论
可能状态：真实、可疑、无法验证
证据来源：税务验真服务
```

本体可用于描述工具接受和产生的业务对象，SHACL 可用于在调用前检查参数图：

1. Agent 将自然语言请求解析成候选对象和意图；
2. 本体判断对象类型是否与工具输入类型匹配；
3. SHACL 检查必要参数、数据类型和基数；
4. 策略层检查身份、权限和风险等级；
5. 工具执行并返回结构化结果；
6. 输出 Shape 校验结果结构；
7. 执行事实、证据和状态变化写入图中。

这使工具选择不再只依赖模型对工具描述的语言相似度，而是增加类型匹配、前置条件和结果契约。

需要强调：本体和 SHACL 不能替代权限系统、事务机制和人工审批。它们提供的是语义层护栏，真正的高风险操作仍应由授权、幂等、审计、回滚和策略引擎共同控制。

## 十一、多智能体协作：共享词汇只是起点

多个 Agent 协作时，最容易被低估的问题不是消息能否传输，而是消息中的概念是否被一致理解。

例如，采购 Agent 输出“供应商已冻结”，财税 Agent 需要知道：

- 冻结的是供应商主数据、付款、采购下单，还是全部业务关系；
- 冻结作用于哪个法人、工厂和时间范围；
- 冻结是风险建议、已审批决定，还是系统已经执行的状态；
- 哪类 Agent 有权解除冻结。

本体可以为 A2A 通信提供共享标识、类型和关系，使能力发现和任务路由具备语义基础。但稳定的多 Agent 协议还需要消息版本、输入输出 Shape、来源、时间、置信度、权限、幂等键、审计信息，以及失败和补偿语义。

共享本体解决“双方说的是不是同一件事”，协议和运行时则解决“这件事怎样可靠地发生”。

## 十二、本体与 WAM：从静态世界观到动态行为

在世界行为模型（World Action Model，WAM）中，本体定义世界中存在哪些实体、状态、能力和关系，实例图保存当前世界快照，行为模型描述状态如何变化。

可以把系统拆为四层：

| 层次 | 回答的问题 | 示例 |
| --- | --- | --- |
| 本体层 | 世界中有哪些类型和关系 | 发票、纳税人、申报、证据 |
| 状态层 | 当前有哪些事实 | 发票有效、尚未抵扣 |
| 行为层 | 什么动作可以改变状态 | 验真、申请抵扣、撤销申报 |
| 治理层 | 谁在什么条件下可以执行 | 权限、审批、风险策略、审计 |

一个“申请进项税抵扣”行为可以表示为：

```text
行为：申请进项税抵扣
执行者：获得授权的财税 Agent 或业务人员
对象：增值税专用发票

前置条件：
- 发票真实性已验证
- 发票状态有效
- 用途满足当前政策规则
- 尚未被重复抵扣
- 证据数据通过 SHACL 校验

效果：
- 创建抵扣申请
- 关联发票、申报期和证据
- 发出审批或申报命令

后置条件：
- 系统记录本次执行结果
- 成功后更新抵扣状态
- 失败时保留原因和补偿状态
```

OWL 可以判断对象类型和能力归属，SHACL 可以检查当前状态是否具备必要事实，规则服务可以评估政策条件，工作流和事务系统负责执行动作。这样，本体不只是知识检索的 Schema，而是行为系统中类型检查和状态判断的一部分。

## 十三、工程工具栈与 Profile 选择

常见工具可以按职责划分：

| 职责 | 工具或技术 |
| --- | --- |
| 本体编辑 | Protégé、WebProtégé、TopBraid Composer |
| 逻辑推理 | HermiT、Pellet、ELK |
| SHACL 校验 | PySHACL、Apache Jena SHACL、TopBraid SHACL API |
| RDF 存储 | Apache Jena Fuseki、GraphDB、Stardog、RDF4J |
| 查询 | SPARQL 1.1 |
| 序列化 | Turtle、JSON-LD、RDF/XML、N-Triples |
| 版本与测试 | Git、CI、SPARQL ASK、SHACL 回归用例 |

OWL 2 还提供不同 Profile，以在表达能力和计算成本之间取舍：

- **OWL 2 EL**：适合大型分类体系和高效类层级推理；
- **OWL 2 QL**：适合本体驱动的数据访问和查询重写；
- **OWL 2 RL**：适合基于规则的 RDF 推理和物化；
- **OWL 2 DL**：表达能力更强，但需要更谨慎地控制复杂度。

如果项目重点是大规模产品、设备或凭证分类，可以优先评估 OWL 2 EL；如果主要在关系数据库上做本体驱动查询，可以评估 QL；如果希望在三元组库中执行规则式推理，可以评估 RL。不要默认选择表达力最强的 Profile，应该从数据规模、更新频率、查询延迟和必须使用的逻辑构造反推选择。

一个轻量起步组合是：

```text
Protégé
+ Turtle
+ 受控的 OWL 2 EL / RL 子集
+ SHACL
+ PySHACL 或 Apache Jena
+ Fuseki
+ SPARQL
+ Git 与 CI
```

## 十四、六个常见建模误区

### 1. 把本体做成数据库表的翻版

类等于表、属性等于字段，只能得到 RDF 版数据字典。建模时应回到能力问题，识别跨系统稳定存在的业务对象、角色、事件和语义关系。

### 2. 把所有信息都建成字符串

`sellerName = "甲公司"` 方便写入，却失去了主体身份、组织关系、历史名称、风险状态和跨源对齐能力。需要被关联、治理和追踪的对象应拥有稳定 IRI。

### 3. 用 OWL 模拟必填校验

开放世界下，“没有记录”不等于“不存在”。必填、唯一、格式和取值范围应由 SHACL 或应用校验负责。

### 4. 把 domain 和 range 当成输入约束

它们通常触发类型推导，而不是报告字段错误。只有当推导结果与其他互斥公理冲突时，推理机才会发现不一致。

### 5. 一开始就构建巨型本体

概念越多不代表价值越高。过多公理会增加评审、推理、测试和演化成本。优先完成一个能够回答 10 到 20 个核心能力问题的最小本体。

### 6. 忽略标识、来源和版本

没有稳定命名空间、定义来源、废弃策略和版本记录，本体很快会出现同义类、断裂映射和不可追踪规则。语义资产需要像代码和 API 一样治理。

## 十五、一条可执行的落地路线

本体项目可以按五个阶段推进。

### 阶段一：建立最小语义内核

- 选择一个明确业务场景；
- 编写 10 到 20 个能力问题；
- 建立核心术语表；
- 定义 20 到 50 个核心类和必要关系；
- 只添加能够服务能力问题的公理。

### 阶段二：建立数据质量门禁

- 为关键实体编写 SHACL Shape；
- 准备正例和反例数据；
- 在数据入库和 Agent 调用前执行校验；
- 将验证报告转成可理解的业务错误。

### 阶段三：接入推理和语义查询

- 选择与负载匹配的 OWL Profile 和推理机；
- 将能力问题转成 SPARQL 测试；
- 记录显式事实和派生事实的来源；
- 对推理时间和结果膨胀建立基线。

### 阶段四：增强 RAG 和 Agent

- 建立实体链接与概念映射；
- 组合向量检索、图查询和规则过滤；
- 用本体描述工具输入输出类型；
- 用 SHACL 检查工具参数和执行结果；
- 对高风险动作保留权限、审批和人工确认。

### 阶段五：治理和持续演化

- 为本体、Shape 和规则建立版本；
- 在 CI 中运行解析、一致性、SHACL 和 SPARQL 回归测试；
- 评估变更对数据映射、查询、Agent 和接口的影响；
- 记录废弃周期和迁移路径；
- 由领域专家和工程团队共同评审语义变更。

每一阶段都应交付可以运行和测试的资产，而不是只交付概念图或会议文档。

## 结语：本体是 Agent 的认知基础设施

本体论建模的目标，不是用复杂术语重新包装数据建模，而是把领域中长期稳定的概念和规则变成机器可以共同理解、推导和检验的语义资产。

在一套完整的 Agent 系统中，各层职责可以清晰分工：

- 数据库负责可靠存储和事务；
- 知识图谱负责连接实体、关系和证据；
- OWL 负责概念分类、语义蕴含和一致性；
- SHACL 负责实例数据与运行时状态校验；
- 规则服务负责可版本化的业务判断；
- RAG 负责获取非结构化知识；
- Agent 负责基于目标组织推理、工具和行动；
- WAM 负责描述动作怎样改变世界状态。

真正有效的本体不一定庞大，但必须能够回答明确的能力问题，产生可解释的推论，发现真实的数据问题，并能安全地进入检索、决策和执行链路。

当多个系统和 Agent 对“什么是什么、什么与什么相关、什么条件下可以做什么”使用同一套机器可读定义时，本体才真正成为领域世界观，而不只是知识图谱中的一份 Schema。
