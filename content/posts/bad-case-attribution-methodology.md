# Bad Case 归因方法论：从错误样本到可验证根因

一个线上问答系统给出了错误答案。排查时，检索团队发现召回文档不够理想，Prompt 团队认为指令约束不够强，模型团队怀疑基础模型能力不足，业务团队则将问题归为“复杂问题”。每一种解释似乎都说得通，却没有一种解释足以指导下一步行动。

这正是 Bad Case 分析中最常见的困境：团队看到了失败，也收集了很多相关线索，但还没有完成归因。

真正有用的归因，不是给错误贴一个标签，也不是找到一个看起来可疑的模块，而是建立一条可以验证的证据链：

```text
失败现象
  → 偏差首先出现的位置
  → 可能导致偏差的机制
  → 可证伪的根因假设
  → 受控干预
  → 结果是否按预期改变
  → 修复后是否稳定且无明显回归
```

本文将 Bad Case 归因定义为：

> 从可观察的失败现象出发，通过错误切片、链路分解、候选假设和受控干预，找到能够稳定解释失败、可以被工程修复，并能通过回归测试验证的主导原因。

它适用于分类、搜索、推荐、RAG、LLM 应用、Tool-Using Agent 和 Multi-Agent 系统。不同系统的组件不同，但核心闭环相同：

```text
发现 → 复现 → 分组 → 定位 → 假设 → 干预 → 回归
```

> 资料口径：本文根据截至 **2026 年 10 月 30 日**可访问的公开论文整理。论文提供方法启发，但文中的工程流程、证据等级和报告模板是面向实际研发流程的综合设计。

## 一、先分清四个容易混淆的概念

归因混乱通常不是算法问题，而是讨论对象没有对齐。至少要区分 Bad Case、错误现象、失败位置和根因。

### 1. Bad Case：一次失败观测

Bad Case 是在特定输入、系统版本、配置和运行环境下出现的一次不符合预期的结果。它是调查入口，不是原因。

一条完整的 Bad Case 至少应保存：

- 原始输入与业务上下文；
- 期望结果或判定规则；
- 实际输出与完整 Trace；
- 模型、Prompt、索引、工具和代码版本；
- 时间、租户、权限、实验桶等环境信息；
- 自动评测结果与人工判定；
- 是否可以重复触发。

如果只保存一张错误答案截图，后续通常既无法复现，也无法判断失败发生在哪个版本。

### 2. 错误现象：最终错成什么

错误现象描述用户看到的结果，例如：

- 答案事实错误；
- 引用与结论不一致；
- 工具执行失败；
- 未完成任务；
- 延迟或成本超出预算；
- 泄露敏感信息。

它适合做影响统计，却不应直接充当根因。“幻觉”“答非所问”“任务失败”描述的是表现，而不是机制。

### 3. 失败位置：偏差首先在哪里出现

失败位置回答系统执行链上的第一个可观察偏差。例如，一个 RAG 答案事实错误，偏差可能最早出现在：

- Query 理解错误；
- 过滤条件生成错误；
- 目标文档未被召回；
- Reranker 将正确证据排到上下文之外；
- 上下文已经充分，但生成阶段没有使用；
- 答案正确，但引用映射阶段绑定了错误来源。

“最先出现偏差”比“最终哪个模块报错”更重要。后续模块可能只是继承了上游错误。

### 4. 根因：改变后能够稳定改变结果的因素

根因应当具有可干预性和可验证性。一个合格的根因陈述通常包含四部分：

```text
在条件 C 下，机制 M 导致组件 A 产生偏差 B；
当对 A 或 M 实施干预 I 时，失败率显著下降，且关键对照切片未恶化。
```

例如，“检索有问题”过于宽泛；下面的描述更接近可验证根因：

> 对含产品别名的售后问题，查询改写没有将旧型号映射到当前知识库实体，导致目标文档无法进入 Top-20。加入版本化别名字典后，该切片 Recall@20 从 61% 提升到 93%，答案正确率从 54% 提升到 86%，其他产品切片无显著回归。

因此要牢记：

```text
相关线索 ≠ 失败位置 ≠ 根因
模型解释 ≠ 因果结论
修复后变好一次 ≠ 根因已经验证
```

## 二、为什么只看错误样本会误导归因

Bad Case 分析天然容易产生确认偏差。工程师知道这条样本失败了，便会在 Trace 中寻找任何“看起来不对”的地方，并把它解释成原因。

### 1. 错误样本里出现的特征，正确样本里也可能大量存在

假设 100 条错误样本中有 70 条是长问题。如果只看错误集，很容易得出“长问题导致失败”。但若全量数据中长问题的错误率为 10%，短问题的错误率为 18%，真实高风险群体反而是短问题。

归因必须同时看分子与分母：

```text
Support(S)       = 切片 S 的样本数 / 全部样本数
ErrorRate(S)     = 切片 S 的错误数 / 切片 S 的样本数
ErrorCoverage(S) = 切片 S 的错误数 / 全部错误数
Lift(S)          = ErrorRate(S) / 全局错误率
```

- `Support` 防止把极小样本的偶然现象当规律；
- `ErrorRate` 衡量该切片有多危险；
- `ErrorCoverage` 衡量修复它能覆盖多少错误；
- `Lift` 衡量该切片相对基线是否异常。

一个切片可能错误率很高但覆盖很低，也可能覆盖很多错误却只是因为流量巨大。两者的修复优先级不同。

### 2. 多个组件可能同时表现异常

一条 Agent Trace 中可能同时存在规划冗余、工具参数错误、重试过多和最终答案不完整。它们不一定是四个独立根因，可能是一条传播链：

```text
实体识别错误
  → 选择了不合适的工具
  → 参数无法通过校验
  → 无效重试
  → Token 预算耗尽
  → 最终答案不完整
```

如果逐项统计，会重复计算同一失败；如果只修复最后的“答案不完整”，上游问题仍会以另一种形式出现。

### 3. 生成式系统具有随机性

同一输入可能一次成功、一次失败。对单次 Trace 归因，可能只是解释随机采样结果。应在相同版本与近似环境下重复运行：

```text
ReproRate = 相同条件下失败次数 / 重复运行次数
```

稳定失败、条件性失败和低概率偶发失败需要不同策略：

| 类型 | 典型表现 | 调查重点 |
|---|---|---|
| 稳定失败 | 多次运行都在同一位置偏离 | 规则、数据、能力或确定性缺陷 |
| 条件性失败 | 只在特定产品、语言、权限或上下文触发 | 交互条件与数据切片 |
| 随机失败 | 相同条件下轨迹波动较大 | 采样、模型不确定性、竞态和外部服务 |

### 4. 事后解释容易把修复方案写成根因

“增加 Prompt 约束”“更换模型”“扩大 Top-K”是干预方案，不是根因。一个方案有效，可能是因为它绕开了问题，而不是找到了问题。例如增大 Top-K 改善答案，不代表根因一定是召回不足，也可能是 Reranker 或上下文组织对证据位置敏感。

归因报告必须分别记录：事实、假设、干预和结论，不能把四者混写。

## 三、用三轴分类替代单一错误标签

一个扁平标签很难同时服务产品统计、工程定位和机理分析。更实用的方法是为每条 Bad Case 维护三组正交标签。

### 1. 现象轴：用户看到了什么

现象标签面向质量与业务影响，例如：

- 正确性：事实错误、推理错误、遗漏约束；
- 相关性：答非所问、过度展开；
- 完整性：漏步骤、漏字段、任务未完成；
- 可信度：无依据结论、错误引用、不确定性表达失真；
- 效率：延迟过高、无效调用、Token 超预算；
- 安全性：越权、隐私泄露、危险操作。

### 2. 位置轴：偏差首先出现在哪里

位置标签应映射真实系统拓扑，而不是套用一套通用名词。常见层级包括：

```text
输入与上下文
→ 解析 / 路由 / 规划
→ 检索 / 记忆 / 数据访问
→ 工具选择 / 参数构造 / 执行
→ 状态更新 / 多 Agent 通信
→ 推理 / 生成
→ 后处理 / 引用 / 安全校验
→ 展示与反馈
```

### 3. 机制轴：为什么产生偏差

机制标签描述可泛化的失败模式，例如：

- 数据缺失、错误、过期或污染；
- 分布外输入或覆盖不足；
- 表示、排序或阈值不合适；
- 指令冲突、约束丢失或上下文干扰；
- 规划错误、状态丢失或终止条件错误；
- 工具契约不清、参数模式不匹配；
- 权限、网络、超时或竞态；
- 模型能力不足或随机性过高；
- 评测器误判、期望本身错误。

三轴组合后，一条记录可以表示为：

```text
现象：引用错误
位置：引用映射
机制：文档分块后 source_id 未稳定继承
```

这样既能统计“用户受到了什么影响”，也能定位“工程上应该修改哪里”，还可以跨模块聚合“哪种机制最常见”。

### 4. 分类树必须保留 Unknown 和 Multi-cause

强迫分析者为每条样本选择一个已知标签，会制造虚假的确定性。建议保留：

- `Unknown`：证据不足，尚不能定位；
- `Non-reproducible`：当前环境无法稳定复现；
- `Expected behavior`：评测规则或用户预期有误；
- `Multi-cause`：多个必要条件共同导致失败；
- `External dependency`：外部系统是主导因素。

分类体系的目标不是做到 100% 可归类，而是暴露团队目前还解释不了什么。

## 四、建立系统因果链，而不是只画组件列表

组件列表告诉我们系统由什么构成，因果链则描述信号如何传播。归因前，应为系统建立最小可观测图：

```text
输入特征与业务上下文
  → 中间决策
  → 组件输入输出
  → 外部依赖结果
  → 最终输出
  → 评测判定
```

图中的每个节点至少要有：

- 可追踪的输入和输出；
- 版本与配置；
- 时间戳和调用关系；
- 对应的局部质量指标；
- 能够替换、屏蔽或回放的干预接口。

如果一个中间节点不可观测，团队只能根据最终结果猜测；如果不可回放，就很难做受控实验。可观测性并非归因后的平台建设，而是可靠归因的前置条件。

对于含环路的 Agent，不要只保存最终 DAG。应保存事件序列和状态快照：

```text
step_id, parent_step_id, actor, action, observation,
state_before, state_after, latency, tokens, error
```

这使分析者能够找到“第一次偏离预期”的步骤，而不是被后续连锁错误淹没。

## 五、七步归因闭环

### 第一步：确认判定标准，排除假 Bad Case

调查前先问：它为什么被判错？判定来自确定性规则、标准答案、人工 Rubric，还是 LLM Judge？

需要优先排除：

- 标准答案错误或已经过期；
- 多个答案均合理，但评测只接受一种表达；
- Judge 存在位置、长度或模型家族偏差；
- 用户预期超出产品承诺边界；
- 外部事实在采集后发生变化。

CheckList 提出的能力矩阵与三类测试很适合校验判据：最小功能测试验证基本能力，不变性测试检查不应改变结果的扰动，方向性期望测试检查变化方向是否合理。[2]

### 第二步：复现并冻结现场

把 Case 固化为可回放包：

```yaml
case_id: BC-2026-0042
input: 原始输入
expected: 判定规则或参考答案
actual: 实际结果
versions:
  app: commit_sha
  model: model_snapshot
  prompt: prompt_version
  index: index_snapshot
environment:
  tenant: tenant_id
  permissions: permission_snapshot
  experiment: bucket_id
trace: trace_uri
```

对生成式任务重复运行若干次，并记录结果分布。无法复现不等于问题不存在，但结论的证据强度必须下降。

### 第三步：形成错误切片，而不是逐条救火

单条 Case 很难区分系统性缺陷与偶然噪声。应寻找共享属性形成切片，例如：

- 输入结构：长度、语言、实体数、约束数；
- 业务属性：产品、场景、租户、权限；
- 系统状态：模型版本、索引版本、工具版本；
- 轨迹属性：调用步数、重试数、上下文长度；
- 语义主题：问题意图、知识域、所需推理类型。

Slice Finder、SliceLine 和 Domino 的共同启发是：可以自动发现表现显著变差、规模足够且具有可解释性的子群，而不必完全依赖人工枚举。[3][4][5] 自动切片只负责生成调查候选，最终仍要检查统计显著性、重复发现和业务含义。

为避免“切片挖掘等于过拟合”，至少应执行三项检查：

1. 设置最小样本量和置信区间，不按几个样本的 100% 错误率决策；
2. 在独立时间窗或留出集上确认同一切片仍然异常；
3. 与匹配的成功样本对比，确认区别不只是流量结构或版本混杂。

### 第四步：定位第一次偏差

从最终失败沿 Trace 反向检查，直到找到最早一个不符合局部预期的节点：

```text
最终答案错误
← 生成是否得到充分证据？
← 上下文是否包含正确证据？
← Reranker 是否保留目标文档？
← Retriever 是否召回目标文档？
← Query 与过滤条件是否正确？
← 输入是否被正确解析？
```

每个节点都应使用局部 Oracle，而不是凭感觉判断。例如：

- 检索节点：目标证据是否进入 Top-K；
- 工具参数节点：参数是否满足 Schema 和业务约束；
- 规划节点：计划是否覆盖完成任务的必要子目标；
- 生成节点：给定充分证据时能否得到正确答案；
- 引用节点：每项主张能否映射到支持它的来源。

反向定位找到的是**故障边界**，还不是根因。它只是把调查空间从整个系统缩小到一个组件或接口。

### 第五步：提出可证伪的候选假设

一个好假设必须能够预测干预结果。建议使用统一句式：

```text
由于 [机制]，在 [触发条件] 下，[组件] 会产生 [局部偏差]；
如果实施 [干预]，则 [局部指标] 和 [端到端指标] 应按 [方向] 改变。
```

同一现象至少保留两个竞争假设，防止过早锁定。例如，目标文档未进入最终上下文，可能因为：

- H1：Embedding 对领域缩写表示不足；
- H2：元数据过滤条件错误地排除了文档；
- H3：召回正常，但 Reranker 对长文档存在位置偏差；
- H4：文档在索引快照中缺失或版本过期。

为每个假设列出支持证据、反对证据、最小验证实验和预期结果。不能被实验推翻的描述，不是工程假设。

### 第六步：通过受控干预区分相关性与原因

最有价值的归因手段是只替换一个环节，观察失败是否随之改变。

常见干预包括：

| 干预 | 做法 | 能回答的问题 |
|---|---|---|
| Oracle 替换 | 用人工正确的中间结果替换某节点输出 | 下游在理想输入下能否成功 |
| 组件交换 | 固定其他条件，只更换 Retriever、模型或工具 | 差异是否由该组件主导 |
| 输入反事实 | 只修改一个属性，其余保持不变 | 哪个触发条件改变了结果 |
| 消融实验 | 移除记忆、反思、Reranker 或某类上下文 | 该机制是否真正贡献质量 |
| 回放实验 | 将历史 Trace 输入新版本组件 | 修复能否覆盖真实失败 |
| Shadow 实验 | 生产流量并行执行但不影响用户 | 在线分布下是否仍然成立 |

影响函数可用于追踪哪些训练样本最影响某个预测，为数据归因提供候选线索，但它依赖模型与近似条件，不能直接替代删除数据、重训或对照实验。[6]

对包含多个因素的复杂问题，可以设计阶乘实验或分层消融，估计交互效应。若只有 `A+B` 同时存在时才失败，就不应强行指定唯一根因；应记录必要条件组合及其适用边界。

### 第七步：修复、回归并沉淀知识

修复通过当前 Case 只是开始。完整验证应覆盖：

1. 原始 Case 是否稳定通过；
2. 同一错误切片中的相邻 Case 是否改善；
3. 对照切片是否没有明显下降；
4. 成本、延迟、安全指标是否仍在预算内；
5. 多次运行的成功率是否提高；
6. 线上分布与长期指标是否支持离线结论。

最后，把生产失败转化为四类资产：

- 回归 Case：防止同类问题再次出现；
- 分类规则：提高后续自动聚类与路由效率；
- 根因知识：记录触发条件、证据和适用边界；
- 监控指标：在用户报告之前发现复发。

到这里，归因才真正闭环。

## 六、用证据等级管理归因结论

团队经常用“已定位”描述不同成熟度的判断，导致决策者误以为猜测已经被证实。可以为每条根因候选设置证据等级：

| 等级 | 含义 | 允许使用的表述 |
|---|---|---|
| E0 | 尚未调查或只有现象描述 | 未知 |
| E1 | 有相关线索，但无稳定复现 | 疑似、候选 |
| E2 | 可复现，且与匹配对照存在稳定差异 | 高相关、待干预验证 |
| E3 | 受控干预支持因果假设 | 根因得到实验支持 |
| E4 | 生产修复有效，回归和长期监控均通过 | 已验证根因 |

升级证据等级时应保留原始实验，而不是覆盖旧结论。一个 E3 假设可能在更大流量上失效，届时需要降级并说明新发现。

### 对照样本怎样选

最有价值的对照不是随机成功样本，而是“除怀疑因素外尽可能相似”的成功样本。可以按以下顺序选择：

1. 同一输入在另一次运行中成功的 Trace；
2. 同一用户意图、实体和环境下的成功 Case；
3. 通过倾向得分、最近邻或分层匹配得到的成功样本；
4. 人工构造的最小对比样本或 Contrast Set。

Contrast Sets 通过对原样本做小而有意义的修改，检验模型局部决策边界是否符合预期。[7] 它特别适合回答：“只改变这个条件，结果是否应该改变？”

### 如何避免把相关性写成因果性

归因结论至少应回答：

- 时间顺序：候选原因是否发生在失败之前？
- 可复现性：相同条件下能否重复观察？
- 特异性：它是否也大量出现在成功样本中？
- 剂量关系：因素增强时失败概率是否系统变化？
- 机制合理性：是否能够解释信号传播路径？
- 干预响应：改变它时结果是否按预测改变？
- 替代解释：其他假设是否已被对照实验排除？

这不是要求每次都完成严格的科学因果推断，而是要求结论强度与证据强度匹配。

## 七、RAG Bad Case 的分层归因

RAG 的最终答案同时受知识库、检索和生成影响，只看答案正确率很难指导修复。更有效的做法是把链路拆成五层。

### 1. 知识与索引层

先判断目标事实是否存在于系统可访问的知识快照中：

- 文档是否缺失、过期或权限不可见；
- OCR、解析和表格抽取是否正确；
- Chunk 是否切断了必要上下文；
- 元数据、实体和版本字段是否正确；
- 增量更新是否真正进入线上索引。

若知识库中根本没有正确证据，继续调 Retriever 或 Prompt 通常只是绕开问题。

### 2. 查询理解层

检查用户问题是否被正确规范化、改写和过滤：

- 实体、时间和版本是否识别正确；
- 指代是否被会话上下文正确消解；
- 多意图问题是否需要拆分；
- Query Expansion 是否引入错误含义；
- 元数据过滤是否过严或过松。

### 3. 召回与排序层

分别计算 Retriever 与 Reranker 的局部指标：

```text
Context Recall@K：必要证据是否进入候选集
MRR / nDCG：高价值证据是否排在前面
Context Precision：进入上下文的内容中有多少真正相关
```

若证据进入召回集但未进入最终上下文，根因更可能位于排序、去重或上下文预算，而不是向量模型。

### 4. 生成与证据使用层

使用 Oracle Context 是最关键的诊断实验之一：人工提供充分且无噪声的证据，再观察模型能否正确作答。

- Oracle Context 下仍失败：重点调查指令遵循、推理、上下文理解或输出格式；
- Oracle Context 下成功：问题主要位于知识、检索或上下文组织；
- 加入无关文档后才失败：模型可能对噪声或证据冲突敏感；
- 答案正确但无引用：调查引用生成和主张映射，而不是事实生成。

### 5. 端到端判定层

RAGChecker 将诊断进一步拆成 Retriever 与 Generator 的细粒度指标，强调正确性、忠实性、上下文相关性等维度之间的区别。[9] ARES 则使用合成数据与少量人工标注来训练评判器，评估上下文相关性、答案忠实性和答案相关性。[10]

这两类方法的工程启示不是“选一个总分”，而是用组件指标定位：系统究竟没有找到证据、没有使用证据，还是基于证据生成了不受支持的主张。

### 一个 RAG 归因矩阵

| 目标证据 | Oracle Context | 实际答案 | 优先调查方向 |
|---|---|---|---|
| 知识库中不存在 | 不适用 | 错误 | 数据采集、更新与权限 |
| 存在但未召回 | 成功 | 错误 | Query、过滤、Retriever |
| 已召回但未入上下文 | 成功 | 错误 | Reranker、去重、预算 |
| 已入上下文 | 失败 | 错误 | 推理、指令、模型能力 |
| 已入上下文 | 成功 | 正确但引用错 | 引用映射与后处理 |

RGB Benchmark 还从噪声鲁棒性、拒答、信息整合和反事实鲁棒性等角度揭示 RAG 的不同失败机制。[11] 因此，“检索到了正确文档”不是 RAG 成功的充分条件。

## 八、Tool-Using Agent 的归因

工具型 Agent 的最终失败通常跨越“想做什么、选什么工具、怎样调用、怎样理解结果、何时结束”多个阶段。可以按以下局部契约逐层检查。

### 1. 意图与规划

- 是否理解任务目标和不可违反的约束；
- 是否遗漏必要子任务或依赖关系；
- 计划是否可执行，而非只有抽象步骤；
- 环境变化后是否及时重规划。

### 2. 工具发现与选择

- 正确工具是否出现在候选集中；
- 工具描述是否足以区分相似能力；
- Agent 是否选择了能力与风险相匹配的工具；
- 是否错误地用语言生成代替确定性工具执行。

### 3. 参数构造与调用

- 参数是否满足类型、格式和业务约束；
- 是否漏传租户、时区、分页或幂等键；
- 失败后重试是否修正参数，而不是重复相同调用；
- 高风险动作是否经过确认与权限校验。

### 4. Observation 理解与状态更新

- 是否区分空结果、权限拒绝、超时和真正不存在；
- 是否从长输出中提取了关键字段；
- 是否把工具返回写回正确的任务状态；
- 是否因旧记忆或摘要覆盖了新证据。

### 5. 终止与结果交付

- 完成条件是否已经满足；
- 是否在未完成时提前终止；
- 是否陷入无效重试或循环；
- 最终答复是否准确反映真实执行状态。

工具增强 LLM 的失败 taxonomy 研究说明，错误不只发生在“工具调用失败”这一点，还覆盖任务规划、工具选择、参数、执行反馈和响应生成等不同阶段。[13] 工程上应把每阶段写成可测试契约，否则最终结果错误时只能笼统归为“Agent 不稳定”。

### 最有效的 Agent 干预实验

```text
固定计划，替换工具选择     → 判断工具路由是否主导失败
固定工具，注入正确参数     → 判断参数生成是否主导失败
固定 Observation，重放后续 → 判断结果理解与后续决策是否有误
注入正确中间状态           → 判断状态丢失是否造成传播
强制停止或扩大预算         → 判断终止策略与资源预算的影响
```

对每种实验同时观察局部成功和端到端成功。正确参数若仍不能完成任务，说明参数错误只是一个可见症状，后续还存在其他必要缺陷。

## 九、多 Agent 系统：归因对象从步骤扩展到协作关系

多 Agent 系统增加了角色、通信、委派和共享状态，同一个错误可能由单个 Agent 能力不足，也可能由协作结构本身造成。

MAST 基于 7 个多 Agent 框架的 1600 余条标注 Trace，归纳出 14 种失败模式，并将其聚合为三类：系统设计问题、Agent 间失配和任务验证问题。[12] 这说明多 Agent 归因不能只统计“哪个 Agent 最后输出了错误内容”。

### 1. 系统设计问题

重点检查：

- 角色划分是否与任务结构匹配；
- 是否存在职责空白或重复劳动；
- 路由和委派是否把任务交给了正确能力；
- 通信拓扑是否导致关键信息丢失；
- 共享记忆是否有明确的写入和冲突解决规则；
- Token、时间和工具预算是否分配合理。

### 2. Agent 间失配

重点检查：

- 不同 Agent 是否对目标和完成条件理解一致；
- 上游交付格式是否满足下游输入契约；
- 一个 Agent 的假设是否被下游误当成事实；
- 冲突意见是否被真正解决，而非由最后发言者覆盖；
- 中间结果是否在摘要和转述中失真。

### 3. 任务验证问题

重点检查：

- 是否有 Agent 负责检查最终结果；
- 验证者是否获得了原始证据，而不只是生成者的摘要；
- 验证规则能否发现真实错误；
- 发现错误后能否路由回具体责任步骤；
- 系统是否把形式通过误认为任务完成。

### 多 Agent 的关键反事实

多 Agent 归因需要围绕协作关系做干预：

```text
单 Agent 基线 vs 多 Agent 系统  → 多 Agent 结构是否真正有增益
固定角色，改变通信拓扑          → 信息传播是否是主导因素
替换某个 Agent 的中间输出       → 该角色是否是失败传播源
隐藏 Agent 身份并交换输出        → 验证者是否存在角色偏见
给验证者原始证据而非摘要        → 错误是否由信息压缩造成
```

如果复杂协作结构没有稳定超过单 Agent 基线，首先应调查系统设计，而不是继续增加 Agent 数量。

## 十、如何决定先修哪个根因

归因完成后，团队往往面对几十个候选问题。只按出现次数排序，会忽略高风险低频错误；只按错误率排序，又容易追逐极小切片。

可以用以下维度建立优先级：

```text
Priority ≈
  Impact × Frequency × ErrorCoverage × Confidence × Fixability
  -------------------------------------------------------------
                    RegressionRisk
```

其中：

- `Impact`：对正确性、收入、安全和用户信任的影响；
- `Frequency`：在真实流量中的发生频率；
- `ErrorCoverage`：修复后预计覆盖的错误比例；
- `Confidence`：根因证据等级；
- `Fixability`：在当前资源与架构下的可修复程度；
- `RegressionRisk`：对其他能力、成本和延迟的潜在副作用。

这不是一个需要精确计算的小数公式，而是防止遗漏关键维度的决策框架。安全与合规问题通常设置硬门槛，不应被较低频率抵消。

建议把工作队列分成三类：

| 队列 | 条件 | 行动 |
|---|---|---|
| 立即修复 | 高影响，E3/E4，修复路径明确 | 进入版本计划并设置回归 Gate |
| 继续实验 | 高影响但只有 E1/E2 | 补对照、回放或 Shadow 实验 |
| 观察与积累 | 低覆盖、低置信度或不可复现 | 加强监控，等待更多样本 |

## 十一、归因平台需要哪些能力

Bad Case 归因不是靠一个可视化页面完成，而需要数据、实验、评测和知识管理共同支撑。

### 1. Case Store：保存可复现现场

将输入、期望、输出、Trace、版本和判定绑定为不可变记录。敏感数据要有脱敏、权限与保留周期，不能为了调试复制到无治理的表格。

### 2. Trace Explorer：定位第一次偏差

支持按时间、父子调用、Agent、工具和状态查看轨迹；能够比较成功与失败 Trace，并将局部输出发送到相应 Evaluator。

### 3. Slice Engine：发现系统性错误

支持结构化属性、语义聚类和轨迹特征切片，同时展示样本量、错误率、覆盖率、Lift 和置信区间。自动生成的切片需要在留出时间窗验证。

### 4. Replay 与 Intervention Harness：执行受控实验

能够冻结上游输入、替换中间结果、切换组件版本、批量重放历史 Trace。没有这层能力，团队很容易把每次线上发布都当成昂贵的归因实验。

### 5. Eval Registry：管理判据和局部指标

记录每个 Evaluator 的版本、适用任务、人工一致性和已知偏差。确定性检查优先于 LLM Judge；使用 Judge 时，应保留 Rubric、模型快照和原始评分理由。

Robustness Gym 将测试组织为可复用的切片、评测与报告流程，为持续鲁棒性检查提供了一个重要思路。[8] 工程平台也应让一次分析规则可以被后续版本重复执行。

### 6. Attribution Knowledge Base：管理证据而非只存结论

每项根因记录都应包括：适用切片、系统版本、支持与反对证据、干预实验、证据等级、修复版本、回归集和失效边界。这样后续出现相似问题时，团队能复用证据，而不是只搜到一句“此前通过改 Prompt 解决”。

## 十二、最常见的失败做法

### 1. 看到一个 Case 就立即改 Prompt

Prompt 是最容易修改的环节，却不一定是偏差来源。先用 Oracle 和组件替换定位故障边界，再决定修改位置。

### 2. 只看错误样本，不看成功对照

这会把高频但无区分度的特征误判为原因。任何切片都应同时报告成功和失败的分母。

### 3. 用一个根因标签覆盖整条传播链

“模型问题”“检索问题”粒度太粗，无法映射到实验和 Owner。应记录第一偏差、传播路径和最终影响。

### 4. 把模型自评当作事实

让出错模型解释“自己为什么错”可以生成候选假设，但它可能合理化并不存在的过程。自评必须与 Trace、局部指标和干预实验交叉验证。

### 5. 只修原始样本，不修失败机制

为单个 Case 添加例外规则可能让回归集变绿，却不改善相邻样本。修复后必须检查同切片和最小对比样本。

### 6. 用总指标掩盖局部退化

总体准确率提升可能同时伴随某个语言、产品或高风险场景大幅下降。发布门禁应同时包含总体指标、关键切片和安全硬指标。

### 7. 分类体系一次定死

Taxonomy 应随系统架构和新错误演化。定期合并无区分度标签、拆分过粗标签，并复审 Unknown 中的新模式。

### 8. 修复上线后立即关闭问题

离线回放通过只支持 E3。还需要线上 Shadow、灰度、长期监控和回滚准备，才能升级为 E4。

## 十三、把归因变成团队运行机制

### 每日：新错误分诊

- 校验是否是真 Bad Case；
- 补齐版本、Trace 和业务影响；
- 标记三轴标签与证据等级；
- 将相似 Case 合并到已有问题簇；
- 高风险问题立即进入应急流程。

### 每周：错误簇与实验评审

- 查看覆盖最高和 Lift 最高的切片；
- 评审竞争假设及反对证据；
- 为高优先级问题指定最小验证实验；
- 复查修复是否只改善单个 Case；
- 将 E3 问题安排到 Shadow 或灰度。

### 每个版本：归因驱动的发布门禁

- 运行固定回归集与近期生产回放集；
- 比较总体、关键切片和多次运行稳定性；
- 检查成本、延迟和安全副作用；
- 对新失败进行版本 Diff；
- 确认每个已知高风险根因都有监控或回滚策略。

Owner 不应只按最终失败模块分配。建议分别明确：Case Owner 负责证据完整，Component Owner 负责局部实验，Fix Owner 负责修复与回归，Quality Owner 负责判据和发布门禁。

## 十五、论文方法与工程问题的对应关系

| 工程问题 | 可借鉴的方法 | 代表论文 |
|---|---|---|
| 如何系统检查和复现错误 | 声明式错误分析、可测试规则 | Errudite [1] |
| 如何从“准确率”转向能力测试 | 能力矩阵、最小测试、不变性、方向性测试 | CheckList [2] |
| 如何自动发现高风险子群 | 数据切片、切片评分、语义错误簇 | Slice Finder / SliceLine / Domino [3][4][5] |
| 如何追踪训练数据影响 | 影响函数 | Koh & Liang [6] |
| 如何验证局部决策边界 | 最小语义改动与对比集 | Contrast Sets [7] |
| 如何持续执行鲁棒性测试 | 模块化切片与测试报告 | Robustness Gym [8] |
| 如何分解 RAG 失败 | Retriever / Generator 细粒度诊断 | RAGChecker / ARES / RGB [9][10][11] |
| 如何分析多 Agent 协作失败 | MAST taxonomy 与 Trace 标注 | MAST [12] |
| 如何分析工具调用链 | 工具增强 LLM 失败 taxonomy | Winston & Just [13] |

这些论文解决的是不同层次的问题。切片发现告诉我们“哪里集中出错”，影响函数提供“哪些训练样本可能相关”，专项 Taxonomy 帮助描述“错误如何发生”，而受控干预才进一步回答“改变什么会让结果改变”。不能用其中任何单一方法替代完整归因闭环。

## 结语：归因的终点是可验证的改变

Bad Case 的价值不在于证明系统曾经出错，而在于帮助团队把失败转化成更可靠的系统能力。

成熟的归因流程应当做到：

- 用现象、位置和机制三轴描述错误，而不是依赖一个含糊标签；
- 同时观察错误样本与匹配成功样本，避免只看相关线索；
- 沿系统链路找到第一次偏差，区分源头与传播结果；
- 为竞争假设设计可证伪的对照和干预实验；
- 用证据等级约束结论强度；
- 在修复原始 Case 后，验证同切片收益与其他切片回归；
- 将每次失败沉淀为回归、监控、分类规则和根因知识。

最终，团队应当能够回答的不只是“这条 Case 为什么错”，而是更严格的四个问题：

```text
它在什么条件下错？
偏差最早在哪里出现？
什么干预能够稳定改变结果？
如何证明修复没有把错误转移到别处？
```

只有当这四个问题都有证据支持，Bad Case 才从一次失败记录，变成了可复用、可验证的工程知识。
