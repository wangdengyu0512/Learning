客户提出一个看似简单的要求：“这批货能不能提前三天交付？”

销售需要确认客户诉求，仓库需要核对可用库存，计划人员需要检查产能，采购需要判断物料到货时间，负责人还需要决定是否接受额外成本。得到一个可行方案以后，相关人员必须修改计划、确认资源、通知客户，并持续跟踪执行结果。

如果让智能体参与这项工作，企业需要解决的问题就从“模型能否给出建议”延伸到了“谁可以作出承诺、哪些操作经过授权、执行中断后如何继续、怎样证明任务已经完成”。这些问题共同构成企业智能体操作系统的设计起点。

本文承接《从理解企业到自主运行：基于世界行为模型的企业级 AI 操作系统》，沿用 **Data OS、Agent OS、Agent Workforce** 的总体划分，重点展开 Agent OS 如何把业务目标组织成受控的执行过程。[1]

本文中的 Agent OS 和世界行为模型（World Behavior Model，WBM）是面向企业场景的工程架构概念。下文提出的模块、状态、接口契约和实施阶段属于设计建议，不代表仓库已实现相应后台能力。案例中的企业、订单、日期、数量、成本与岗位规则均为虚构示例。

## 一、建设背景：企业为什么需要智能体操作系统

### 1. 业务任务天然包含多种约束

假设客户要求将订单 SO-2026-1022 的 100 件产品，从 10 月 30 日提前到 10 月 27 日交付。销售希望尽量满足客户，但企业还需要保证质量、控制额外费用，并维护其他订单的交付承诺。

这项任务至少涉及四类判断。

第一类是事实判断：客户究竟要求提前发货还是提前到货，库存是否可用，哪些物料尚未到齐。第二类是可行性判断：调整生产顺序后，质量检验和运输是否来得及。第三类是授权判断：谁能调整优先级，谁能批准加急费用，谁能对客户作出新承诺。第四类是结果判断：计划是否真正修改，资源是否确认，货物是否按约定送达。

这些判断的责任和证据来源不同。企业需要让系统明确记录每一次判断的依据，并将允许执行的动作限制在对应的授权范围内。

### 2. 从一次调用走向持续运行

一次模型调用可以生成计划，一次工具调用可以提交变更，但业务任务可能持续数小时甚至数天。在这段时间内，人员会补充信息，系统会发生故障，业务状态也会不断变化。

因此，平台需要保存任务进度，识别等待原因，恢复中断执行，并及时发现已经失效的计划。智能体可以更换执行节点，模型服务可以切换，业务任务的身份、已完成动作和待处理事项仍应连续可查。

**企业智能体操作系统的建设目标，是让智能体在明确的业务边界内持续承担任务，并为每项结果提供可核验的执行证据。**

### 3. 用任务质量评价建设价值

第一阶段就应确定业务验收方式。例如，试点需要缩短交期调整的方案准备时间，同时避免未经批准的订单变更，保证写操作结果可追踪，并把异常交给指定人员处理。

这些指标会反过来决定数据接入范围、工具能力和治理机制。如果试点只要求辅助评估交期，就不必一开始接入全部财务系统；如果试点允许修改交期，则执行授权、版本校验和结果核验必须同时具备。

## 二、概念与边界：企业智能体操作系统管理什么

### 1. 工作定义

本文将企业智能体操作系统定义为：**围绕企业任务提供智能体编排、持久执行、工具访问、身份授权、过程追踪和结果验收的公共平台。**

这里的“操作系统”强调共享运行机制。它可以由既有工作流、模型服务、数据平台和业务接口组合实现，不预设必须独立采购一套产品，也不要求替换现有企业软件。

平台的基本管理对象包括任务、计划、智能体版本、执行实例、工具调用、审批记录、上下文引用和业务产物。这些对象之间应有稳定的标识关联，支持从一个业务结果反查完整执行过程。

### 2. 与其他系统的责任划分

| 系统或能力 | 主要职责 | 与 Agent OS 的协作方式 |
| --- | --- | --- |
| ERP、CRM、WMS 等业务系统 | 保存和维护订单、客户、库存等权威业务记录 | 接受受控业务命令，返回可核验的处理结果 |
| Data OS | 统一业务语义，提供有来源和权限约束的数据与知识 | 按任务提供事实、规则和证据，更新业务状态视图 |
| 智能体开发平台 | 配置模型、提示词、技能和工具，支持开发调试 | 将经过验证的智能体版本发布到运行环境 |
| 工作流引擎 | 执行明确的流程步骤、等待、分支和补偿 | 承载确定性流程，与动态规划和智能体运行结合 |
| Agent Harness | 管理单次或连续的模型与工具执行循环 | 为 Agent OS 提供状态、上下文、暂停恢复等执行基础 |
| Agent Workforce | 定义数字岗位、业务职责、协作规则和交付标准 | 提供岗位配置，由 Agent OS 调度和执行 |

业务系统继续拥有业务事实的最终解释权。Agent OS 可以记录“修改订单的动作已提交”，但订单是否已经生效，需要查询负责该订单的业务系统。

### 3. 人员责任需要随系统一起设计

业务负责人定义任务价值、可接受风险和完成标准；数据负责人维护事实口径与规则效力；平台团队维护运行能力和故障处理；智能体维护者负责配置版本与评测；授权管理者维护访问范围和审批策略。

数字岗位需要绑定现实中的责任人。遇到无法自动处理的业务冲突时，平台必须知道向谁升级，以及多长时间未处理后需要进一步提醒。

## 三、总体架构：连接企业认知、任务执行与数字岗位

### 1. 保持三层体系，明确各层交付物

原文将 Data OS、Agent OS 与 Agent Workforce 连接起来，并用 WBM 描述企业对象、状态、行为及约束。[1] 本文据此采用以下职责分工。

| 层次 | 回答的问题 | 对外提供的主要产物 |
| --- | --- | --- |
| Agent Workforce | 谁负责什么业务目标，按什么标准交付 | 数字岗位、业务流程模板、升级规则、验收条件 |
| Agent OS | 目标如何被组织、执行、恢复和验收 | 任务计划、运行状态、工具调用、审批与执行证据 |
| Data OS | 当前事实是什么，规则是什么，依据在哪里 | 业务对象、状态快照、知识片段、规则版本与来源 |
| 跨层共享的 WBM 契约 | 对象有哪些动作，动作在什么条件下有效 | 对象标识、状态定义、动作语义、前置条件与结果约束 |

WBM 在这里作为跨层共享的语义契约，不另设一个包揽所有计算和存储职责的系统层。

### 2. Agent OS 内部的主要模块

| 模块 | 主要职责 | 提前交付案例中的作用 |
| --- | --- | --- |
| 请求与事件入口 | 认证、输入校验、事件去重、任务创建 | 接收销售请求，关联订单和发起人 |
| 任务与计划管理 | 目标解析、依赖关系、计划版本、验收条件 | 组织库存核查、产能评估、方案审批和执行 |
| 智能体注册与路由 | 管理能力、版本、运行限制和执行资格 | 选择有相应业务权限的分析岗位 |
| 运行内核 | 调度、模型循环、状态持久化、暂停恢复 | 保存进度，等待审批，恢复被中断的执行 |
| 上下文服务 | 按权限装配事实、规则、历史与任务资料 | 提供订单状态、库存口径与有效制度 |
| 工具执行入口 | 工具发现、参数校验、授权和结果记录 | 受控调用订单、库存与排产接口 |
| 治理与观测 | 审计、成本、告警、权限撤销和运行控制 | 追踪交期变更，限制费用与资源消耗 |
| 验收与反馈 | 校验交付物、核对业务状态、形成改进样本 | 区分计划生效与货物最终交付 |

逻辑模块并不要求各自成为独立微服务。试点阶段可以共享进程和数据库，先通过清晰的接口与数据所有权建立边界，再依据负载和隔离需求拆分部署。

### 3. 一次请求如何经过各层

销售提交请求后，入口创建任务并记录发起身份。Agent OS 从 Data OS 获取必要事实，依据 WBM 动作契约生成候选计划，再调用相应数字岗位完成分析。

方案通过验收和审批以后，工具执行入口向业务系统提交变更。业务系统返回处理结果，Agent OS 回查关键状态，将执行证据关联到任务。后续事件触发跟踪步骤，最终由验收规则或业务负责人确认任务结果。

贯穿整个过程的身份、任务标识和证据引用，使不同模块可以围绕同一个业务目标协同工作。

## 四、企业认知基础：WBM 如何支撑智能体行动

### 1. 从一个业务域建立最小模型

针对提前交付场景，首批建模对象可以限定为客户订单、订单行、库存批次、生产任务、采购到货、运输安排和审批记录。

模型还需要表达对象关系。例如，订单行由哪些库存或生产任务满足，生产任务消耗哪些物料，一次资源调整可能影响哪些其他订单。这些关系决定分析的范围，也决定执行后的核验范围。

每个状态需要清晰口径。“库存充足”应说明是账面库存、扣除冻结后的可用库存，还是已经为本订单预留的库存；“交期满足”应说明是计划发货、实际发货，还是客户到货。

### 2. 把动作写成可校验的契约

以“修改订单承诺日期”为例，可以定义如下动作契约。

| 契约项 | 示例内容 |
| --- | --- |
| 目标对象 | 订单 SO-2026-1022，当前版本 v17 |
| 输入 | 新承诺到货日期、已批准方案、变更原因 |
| 前置条件 | 订单可变更，方案仍有效，授权与审批覆盖本次参数 |
| 执行约束 | 不覆盖并发变更，不超出批准费用，不破坏受保护订单的承诺 |
| 预期结果 | 订单承诺日期更新，版本递增，关联方案与变更记录可查 |
| 核验方式 | 查询订单权威记录及关联的资源确认状态 |
| 异常处理 | 版本冲突后重新评估；结果未知时先查单；无法满足约束时交人工处理 |

动作契约把模型生成的候选行为转化为平台能够检查的业务命令。模型提出动作以后，授权、参数约束和状态更新由受控程序落实。

### 3. 上下文应携带来源和有效范围

任务上下文至少应区分事实、规则、推断和历史经验。事实附带对象版本和查询时间；规则附带生效范围与版本；推断标明假设和缺失信息；历史经验说明适用条件。

当库存数据超过允许的新鲜度，系统应重新查询；当合同存在两个无法确认效力的版本，任务应等待确认；当某项信息对发起人不可见，系统应通过合适的授权流程取得结论或交由有权限的岗位处理。

上下文中的来源标记也应保留到最终方案中，让审批者能定位关键依据。

### 4. 明确方案推演的依据

交期方案可以由规则引擎、排程服务或人工确认结果支撑。语言模型适合整理约束、提出候选方案和解释差异；具体的产能计算、费用汇总和时间校验，应调用可复算的计算能力。

如果企业暂时没有可靠的排程模型，就将产能确认设置为人工步骤。系统应明确记录“等待计划负责人确认”，避免把缺少证据的预测当成执行依据。

## 五、运行内核：一个智能体如何稳定执行任务

### 1. 分开管理岗位、任务和执行实例

一个数字岗位可以同时服务多个业务任务，同一个任务也可能经历多次运行。建议至少分开管理以下对象。

| 对象 | 作用 | 示例 |
| --- | --- | --- |
| Agent Definition | 定义可发布的智能体能力与配置版本 | 库存分析员 v3 |
| Task | 保存业务目标、约束、负责人和验收条件 | 完成订单提前交付的协调与跟踪 |
| Plan | 保存步骤、依赖、方案版本与适用条件 | 提前交付方案 v2 |
| Run | 记录某次实际执行及其恢复位置 | 库存分析第 2 次运行 |
| Tool Invocation | 记录一次逻辑业务动作及其调用尝试 | 为订单预留 40 件成品 |
| Artifact | 保存可验收的产物及证据引用 | 可行性报告、批准方案、系统回执 |

任务不能随着模型会话结束而消失。执行实例失败以后，可以通过新的运行继续推进原任务，已确认的业务动作和审批关系仍属于同一任务链路。

智能体配置发布后应有不可变的版本标识。运行记录需要关联所用模型配置、提示词、工具定义和规则版本，以便分析行为变化。模型服务本身可能存在非确定性，保存版本信息也不能保证逐字重现历史输出。

### 2. 建立明确的状态与退出条件

可以将任务主状态设计为以下几类。

| 状态 | 含义 | 典型后续处理 |
| --- | --- | --- |
| 待调度 | 已受理，等待资源或前置条件 | 调度执行，或在截止时间后升级 |
| 执行中 | 正在分析、调用工具或核验结果 | 保存进展，推进下一步骤 |
| 等待输入 | 缺少必要信息或业务确认 | 收到输入后检查其适用性并恢复 |
| 等待审批 | 已提交确定方案，尚未获得批准 | 批准后重新核验，拒绝后调整或结束 |
| 待核对 | 外部动作结果未知或执行证据冲突 | 查询权威系统，必要时交人工处理 |
| 部分完成 | 已有动作生效，剩余目标未满足 | 继续执行、补偿或接受部分交付 |
| 已完成 | 已满足约定的业务验收条件 | 保存验收证据，结束任务 |
| 已失败 | 目标无法完成且恢复策略已结束 | 记录原因和剩余影响，交接责任人 |
| 已取消 | 已停止后续执行并交接未决事项 | 保留已生效动作与处置记录 |

等待状态需要同时记录等待对象、截止时间和升级责任人。平台不应仅显示一个长期不变的“处理中”。

“已取消”意味着停止当前任务的继续推进，并不表示历史业务变更已自动撤销。存在仍在执行的外部动作时，应先进入取消处理阶段，核对影响并将必要的后续处置转交给明确的任务或人员，再结束原任务。

### 3. 将执行进度持久化

每一步至少保存输入引用、执行状态、产物引用和下一步条件。关键状态变更与待发送事件可以在同一数据库事务中写入，再由可靠投递机制发送，减少“状态已更新但后续步骤未被唤醒”的问题。

任务领取可以使用有期限的租约，并配合执行代次或防护令牌，阻止旧执行节点继续推进本地状态。外部系统若不支持同类控制，仍需要幂等键、版本检查和结果核对来保护业务动作。

服务恢复时，平台根据持久记录判断应该继续分析、等待审批、查询外部结果，还是执行尚未开始的步骤。恢复逻辑需要识别已经完成的动作，避免从头重放所有工具调用。

### 4. 控制运行预算与资源范围

每次运行应配置时间上限、模型调用预算、工具调用次数和可使用的执行环境。长任务按步骤检查预算，在无法继续时说明已完成内容和剩余工作。

需要执行代码时，可以提供隔离环境，限定文件访问、网络出口和资源额度。业务系统凭证由受控工具层按需使用，模型上下文只接收完成任务所需的信息。

运行预算耗尽以后，任务可以等待追加资源、采用经过验证的降级方案，或交由人工继续。降级也需要满足原有验收条件。

### 5. 让业务验收决定任务完成

运行结束、工具成功和业务完成是不同层次的状态。

在提前交付案例中，“方案已获批”“执行计划已生效”“货物已发出”“客户已收货”分别对应不同里程碑。创建任务时就应指定本次任务覆盖到哪个里程碑。

如果任务目标是完成计划调整，订单、资源和生产计划核验通过即可验收；如果目标是实现提前交付，平台还需要跟踪物流与收货事件。等待期间可以释放模型和工作节点，以事件驱动方式继续任务。

## 六、任务编排与协作：从业务目标到跨部门执行

### 1. 将自然语言转换为任务契约

“尽快交付”需要进一步明确为可判断的目标。对于案例任务，契约可以约定：100 件产品于 10 月 27 日到货，保持既定质量要求，额外费用不超过批准额度，不延误受保护订单，并持续跟踪到收货确认。

无法从输入或已有记录确定的信息，应作为待确认项。例如，客户允许分批到货与否，可能直接改变方案空间。平台应在执行相关动作之前取得明确答案。

### 2. 用依赖关系组织协作

库存核查、产能评估和采购到货评估可以并行进行；方案比较依赖这些评估结果；业务执行依赖方案批准和执行前复核；客户承诺依赖资源确认。

每个节点应有输入、输出、超时、失败处理和完成判定。调度器只在依赖满足时推进，避免由智能体之间的自由对话隐式决定业务状态。

对于固定审批、费用计算和状态校验，采用明确流程。对于方案探索、非结构化信息整理和异常原因分析，可以允许动态规划，但新增步骤仍需通过权限、预算和依赖校验。

### 3. 按资格选择执行者

路由首先检查岗位是否具备所需能力、业务范围和工具权限，再比较负载、历史质量、延迟与成本。

一个价格更低的模型或空闲的智能体，未必具备处理某类合同或某家工厂数据的资格。资格约束应在路由阶段明确，执行阶段再次校验。

当多个智能体属于不同团队或系统时，委派接口仍应传递任务标识、授权范围、截止时间、产物要求和取消约定。接入某种通信协议以后，这些业务约束仍需逐项实现。

### 4. 让交接产物可以验收

库存分析岗位的产物不应只有“库存可以满足”的结论，还应包含可用数量、仓库范围、对象版本、查询时间、预留情况和证据来源。

协调岗位据此判断该结果是否足以支持方案。过期数据需要重查，缺少关键证据的结果需要补充，不同岗位的结论存在冲突时，应定位到具体事实或约束。

例如，库存岗位发现有 40 件成品，计划岗位却认为这些成品属于另一订单。此时需要核对预留记录和优先级规则；通过多个智能体投票无法解决事实归属问题。

### 5. 将计划修改视为版本变更

如果采购到货延迟，平台可以生成新计划，但应记录它修改了哪些步骤、影响哪些产物、是否改变费用和承诺。

依赖旧计划的审批和下游动作需要重新检查适用性。已经执行的动作继续保留，未执行的动作按照新计划调度，不能用覆盖历史记录的方式掩盖方案变化。

## 七、工具与业务系统接入：让行动产生可靠结果

### 1. 建立描述业务语义的工具目录

工具目录需要说明输入输出、访问范围、操作副作用、超时语义、幂等支持、查询方式和失败处理。只描述函数名称与参数类型，难以支撑长期业务执行。

例如，“预留库存”应明确预留期限、释放方式、并发冲突响应和查询凭证。平台才能判断调用失败后是否可以重试，以及任务取消后如何处理已有预留。

查询、修改、消息通知和资金相关动作应分别配置治理规则。对外通知同样会产生业务影响，需要确认接收对象、发送内容和授权范围。

### 2. 为每次动作执行检查链路

建议按以下顺序执行工具动作：解析候选调用，校验参数，检查身份与作用域，检查业务前置条件，核验审批，记录调用意图，提交外部请求，保存回执，查询结果并判断下一步。

审批和执行之间可能经过很长时间，因此执行前仍需重新读取关键状态。订单版本、库存可用量、规则效力或授权发生变化时，平台应停止原动作并重新评估。

版本检查最好由业务系统在更新操作中原子执行。例如，要求“仅在订单仍为 v17 时更新”，由服务端拒绝已经变化的对象。客户端先查询再无条件写入，仍可能覆盖查询之后发生的并发变更。

### 3. 区分失败与结果未知

假设库存系统已完成预留，但回执在网络中丢失。Agent OS 看到的是超时，无法据此判断库存是否已经预留。

建议在外部调用前持久化业务动作标识，并在重试时复用同一幂等键。幂等键应标识同一个逻辑动作，不能每次重试生成一个新键。业务系统还需要约束该键的作用域、保留时间和参数一致性。

收到超时后，平台优先通过业务动作标识查询结果；只有确认未生效并符合重试条件，才重新执行。外部系统不支持幂等和查询时，应转入待核对状态，安排人工或专用对账流程。

这套设计的目标是控制重复副作用并能核对结果。跨系统执行能否达到相应保证，取决于各业务接口提供的实际能力。

### 4. 管理部分成功与补偿

库存预留成功、生产计划调整失败，是跨系统执行中需要预先设计的情况。任务应记录哪些步骤已生效，以及剩余目标为何无法继续。

对于可撤销的预留，可以执行释放；对于已经发送的客户通知，可以发出经批准的更正；对于已经发生的运输费用，需要记录损失并交由负责人处理。

每个补偿动作也需要授权、幂等控制和结果核验。补偿的含义是处理既有影响，是否能恢复原状态需要逐项判断。

### 5. 核对业务结果并更新状态视图

工具返回成功以后，应回查关键对象与关联条件。订单日期修改成功，但生产计划没有落实，不能判定整个方案已经生效。

Agent OS 保留命令和执行证据，业务系统维护权威状态，Data OS 更新面向分析的状态视图。在视图存在延迟时，验收应读取满足新鲜度要求的权威数据，并记录查询时间和版本。

## 八、数字员工与人机协同：建立可运营的岗位体系

### 1. 为每个数字岗位编写职责说明

数字岗位需要明确服务对象、可接受任务、所需能力、允许动作、输出要求、运行时间和升级责任人。

| 岗位 | 核心职责 | 交付物 | 人员责任 |
| --- | --- | --- | --- |
| 交付协调员 | 整理目标、组织评估、跟踪方案执行 | 完整方案与任务进展 | 业务负责人确认目标和例外处理 |
| 库存分析员 | 核对可用量、预留及调拨条件 | 带版本和来源的库存评估 | 仓储负责人维护可用量口径 |
| 计划分析员 | 核对产能、工序及其他订单影响 | 可执行的排产评估 | 计划负责人确认关键调整 |
| 采购分析员 | 核实到货承诺与加急条件 | 物料可达性与费用依据 | 采购负责人确认供应商承诺 |

岗位配置可以复用工具和模型，但每个岗位的授权范围、业务规则和验收条件需要独立明确。

### 2. 员工工作台应围绕任务展开

员工需要看到系统理解的目标、当前进度、已完成事项、等待原因和下一步预计动作。需要补充信息时，应指出缺少哪项内容，以及它会影响什么判断。

交付结果应支持从结论查看依据，从执行状态查看业务回执。员工也应能修改目标或申请取消，系统据此评估对已执行动作的影响。

### 3. 审批工作台应展示实际决策

审批页面至少展示方案版本、涉及对象、费用上限、影响范围、关键假设、计划执行的动作和有效期限。

审批者批准的是这一组明确内容。方案改变以后，需要判断变化是否仍在批准范围内；超出范围就重新提交。

对于需要人工接管的任务，平台应交付已经确认的事实、已生效动作、未决事项和建议检查项，使接管人员能够直接继续处理。

### 4. 管理数字岗位的完整生命周期

新岗位从模拟任务和受控试点开始，上线前核验能力、权限和升级路径。运行期间按任务质量、异常情况和业务收益评价，配置修改后重新验证。

岗位停用时，应停止接收新任务，明确在途任务的接续方式，并回收对应的凭证和授权。平台保留历史记录供审计和问题分析使用。

## 九、安全与治理：把授权落实到每一次行动

### 1. 区分发起、执行与批准身份

一次任务中可能同时存在发起人、智能体服务身份、被委托执行身份和审批人。执行记录应保留各自角色，使平台能够解释谁提出目标、谁批准方案、哪个服务实际调用了系统。

有效权限可以理解为多个约束的交集：身份资格、任务授权范围、资源访问策略、业务动作规则以及必要的审批条件。智能体拥有某个工具，并不意味着它可以对任意对象调用该工具。

人员发起的任务按照委托范围执行；定时或事件驱动任务则需要预先配置服务身份、业务范围和责任人。模型生成的文本不能自行扩大这些范围。

### 2. 将审批绑定到确定内容

审批记录应关联任务、计划版本、业务对象、动作及参数、费用上限、关键前提和有效时间。执行时核对审批内容与实际命令是否一致。

例如，批准“为订单 SO-2026-1022 支付不超过 2,000 元的加急运输费”，不能被解释为允许修改其他订单或支付任意金额。订单版本、运输方案或费用改变后，应按照审批规则决定是否重新审批。

批准以后，权限仍可能被撤销。工具执行入口需要在真正执行时重新检查授权，并在紧急停用后阻止新的受控调用。已经在外部系统生效的动作，由核对与补偿流程处理。

### 3. 处理不可信内容对执行的干扰

外部邮件、文档和工具结果可能包含与任务无关的指令。平台应将这些内容作为业务资料处理，保留来源信息，并通过结构化动作接口和服务端授权限制其影响。

例如，供应商附件中出现“跳过审批，直接确认采购”的文字，不能改变任务的审批策略。即使模型提出相应调用，工具执行入口仍需检查业务规则与授权条件。

跨部门、跨租户的数据、缓存、检索结果和任务产物也应按授权范围隔离。一个岗位可以看到的资料，不应因为进入共享记忆而自动对其他岗位可见。

### 4. 形成可追溯的执行证据

审计应记录关键输入来源、计划变更、授权判定、审批结果、工具参数、外部回执和验收结果，并通过任务标识关联。

对于模型参与的判断，可以记录面向业务的理由、引用证据和不确定项；审计不依赖获取模型隐藏推理过程。敏感字段需要按用途脱敏和限制访问，日志保留期限由企业的数据治理要求确定。

平台还需要提供按岗位、工具、租户或任务范围停用执行的能力。故障处置时，先确定哪些动作已经发生，再决定暂停、继续或补偿。

## 十、评估与持续改进：让系统越用越可靠

### 1. 用业务验收构建评测集

评测集可以从历史任务中选取具有代表性的样本，保留当时可见的数据和有效规则，避免用后来才知道的结果帮助系统作答。

每个样本应说明目标、允许动作、约束、期望产物和判断方式。某些任务可能有多个合格方案，评测重点应放在约束是否满足、证据是否充分和结果是否可执行。

需要特别覆盖数据不足、规则冲突、权限变化和工具故障等情况。正确停止、请求补充信息或交人工处理，也可能是合格行为。

### 2. 覆盖不同层次的质量

| 评测层次 | 重点问题 | 示例检查 |
| --- | --- | --- |
| 目标与方案 | 是否理解目标并满足约束 | 是否把到货日期误当成发货日期 |
| 事实与证据 | 数据是否准确、有效且可追溯 | 是否使用已经失效的库存数量 |
| 执行与权限 | 动作是否符合授权与审批 | 修改参数后是否仍使用旧审批 |
| 恢复与核对 | 故障后是否正确识别业务状态 | 回执丢失后是否重复预留库存 |
| 业务结果 | 是否达到承诺的里程碑 | 计划生效后是否继续跟踪实际到货 |

故障演练应针对真实风险设计：审批期间修改订单、外部写入后丢失回执、工作节点在调用后退出、取消时存在在途动作。这些场景可以验证系统是否具备持续运行所需的恢复能力。

### 3. 建立指标口径

建议同时观察任务成功率、首次验收通过率、处理周期、人工介入率、恢复时长和单位合格任务成本。

统计时应明确任务纳入条件、终态分类和时间窗口。等待中的任务不能直接当成成功；取消、超时和部分完成应独立展示。对于持续跟踪的任务，还应分开衡量方案生成时间与业务完成时间。

人工审批原本就是流程要求时，应将正常审批与异常救援分开统计。否则，人工介入率下降可能掩盖审批缺失，或者错误评价一个运行正常的高风险流程。

### 4. 将经验沉淀纳入版本管理

记忆可以分成当前任务状态、具有明确适用范围的偏好、经审核的业务经验和由权威系统维护的事实。事实更新应回到相应数据来源，经验总结则附带来源、适用条件和失效机制。

例如，“某运输路线上次只用了一天”可以作为方案分析的参考，不能直接成为新的交付保证。企业需要区分一次事件、统计规律和正式业务承诺。

模型、提示词、工具描述、路由规则和经验库变更后，应经过离线评测、小范围发布和运行观察。发现质量下降时，回退配置版本，并核对受影响的在途任务；配置回退不会自动撤销已发生的业务动作。

## 十一、完整案例：客户要求提前交付，系统如何完成协调

### 1. 固定示例条件与责任范围

以下以 2026 年 10 月 22 日创建的任务为例。客户要求将 100 件产品的到货日期从 10 月 30 日提前到 10 月 27 日，不接受分批到货。

当前可用成品为 40 件，剩余 60 件需要生产。计划评估表明，在物料按承诺到货且产能确认的条件下，可以在 10 月 25 日完成生产与检验。运输服务给出的方案是在 10 月 26 日发运、10 月 27 日到货，额外费用为 1,800 元。负责人对本任务可批准的费用上限为 2,000 元。

这些数字是本例的假设输入。实际使用时，每项条件都需要来自相应业务系统、合同或责任人的确认。

本次任务覆盖到客户收货。因此，“方案执行完成”只结束计划调整阶段，整体任务仍需等待交付证据。

### 2. 从请求到收货的完整链路

| 阶段 | 系统动作 | 需要保留的证据 | 推进条件 |
| --- | --- | --- | --- |
| 受理 | 确认订单、数量、到货时间与客户限制 | 原始请求、发起人、任务契约 | 目标与权限范围明确 |
| 事实获取 | 查询库存、订单版本、产能与物料到货 | 数据版本、查询时间、来源 | 关键事实可用，无未决冲突 |
| 并行评估 | 库存、计划、采购岗位分别评估 | 各岗位的结论、假设与证据 | 结果符合交接要求 |
| 方案比较 | 比较可用方案的成本、时间和风险 | 候选方案与约束检查结果 | 至少一个方案满足业务条件 |
| 人工审批 | 提交指定版本的方案及执行动作 | 审批人、参数范围、有效时间 | 方案获得必要批准 |
| 执行前复核 | 再次确认订单、资源、规则与授权 | 最新状态与检查结果 | 关键前提仍然成立 |
| 业务执行 | 预留库存、落实生产和运输、修改承诺 | 业务动作标识、系统回执 | 所需动作生效且关联一致 |
| 客户确认 | 根据授权发送新承诺并记录反馈 | 通知内容、接收对象、发送结果 | 通知或确认条件满足 |
| 持续跟踪 | 接收生产、发运、运输与收货事件 | 事件来源、异常处置记录 | 收货达到任务约定 |
| 最终验收 | 核对数量、日期、费用和其他约束 | 验收结果与责任人 | 所有完成条件满足 |

### 3. 执行顺序由业务依赖决定

在本例中，平台先确认或预留必要资源，再落实生产与运输安排。只有这些前提成立，才修改订单承诺并向客户发出经授权的确认。

具体系统可能要求不同顺序。例如，库存预留需要关联正式计划编号，或运输订舱具有取消费用。实施时应据实际接口和合同约束设计步骤，并在审批材料中说明费用与不可逆影响。

### 4. 库存预留超时以后如何恢复

假设库存系统已经预留 40 件成品，但 Agent OS 没有收到回执。运行节点随后退出。

新的执行节点读取到该动作处于已提交、结果待确认状态，先使用原业务动作标识查询库存系统。查到预留成功后，记录回执并推进后续步骤；确认未执行且允许重试时，使用原幂等键重试；仍无法确定时，进入待核对状态。

在结果未确认以前，后续生产或订单变更步骤不会把这 40 件视为已经安全落实。工作台显示的是具体等待原因，并将核对责任交给指定人员。

### 5. 审批后库存发生变化怎么办

另一个分支中，审批等待期间库存从 40 件下降到 20 件。执行前复核发现原方案前提不成立，平台暂停相关动作，重新计算生产数量、交期与费用。

如果新方案超出 2,000 元上限，或影响其他订单，就生成新计划版本并重新审批。如果原方案已经部分执行，则同时记录已预留资源与已经发生的费用，供负责人决定继续还是补偿。

### 6. 任务结束时交付什么

最终产物包括任务目标、批准方案、关键状态变化、执行回执、异常处理、实际费用和收货证据。

若 10 月 27 日已完成收货且满足其他约束，可以判定目标完成。若只完成发运，系统继续跟踪；若出现运输延误，则启动异常处理并如实记录结果。业务完成状态始终由约定的证据决定。

## 十二、建设路线与价值验收：从试点走向规模化运行

### 1. 选择可以验证结果的首批场景

优先评估业务价值、数据质量、动作风险、流程稳定性和结果可验证性。首个场景可以限定到一家工厂、一类订单和一组明确动作，使数据与责任范围可控。

如果核心数据缺少统一口径，先完成相关 Data OS 能力；如果业务系统无法核对写入结果，先补齐接口或采用人工执行。平台应按照依赖逐步开放自动执行范围。

### 2. 按能力成熟度推进

| 阶段 | 核心交付 | 验收重点 |
| --- | --- | --- |
| 场景定义 | 任务契约、业务对象、责任人、基线指标 | 业务负责人能判断什么结果算合格 |
| 辅助分析 | 上下文服务、候选方案、证据展示 | 事实与计算可核验，缺失信息能被识别 |
| 受控执行 | 工具接入、审批、持久状态、结果核对 | 越权动作被阻止，中断与未知结果有处理路径 |
| 岗位协作 | 标准产物、任务依赖、分歧升级和版本管理 | 多岗位能正确交接，计划变化可追踪 |
| 持续运营 | 评测发布、指标看板、故障演练与成本核算 | 质量变化可发现，故障可恢复，收益可持续衡量 |
| 扩展复用 | 新业务域、新组织、新系统接入 | 复用部分有证据，新规则与权限重新验证 |

阶段推进不以智能体数量为依据。一个能够稳定完成真实任务、正确处理异常的数字岗位，已经可以形成有效的能力基础。

### 3. 最小系统需要具备什么

第一套允许真实写操作的系统，至少需要任务持久化、智能体版本管理、受控工具入口、身份与审批、结果核对、异常接管和执行记录。

多智能体自由协作、复杂自动规划和跨业务域记忆可以按场景需要逐步增加。对首批任务没有直接帮助的能力，不必成为试点前置条件。

部署上可以从少量服务开始，将任务状态、执行事件和业务动作记录组织清楚。随着负载增加，再分别扩展模型调用、执行节点、工具连接器与分析存储。

### 4. 用可比较的数据评估价值

试点前记录同类任务的处理时间、人工投入、异常率与成本。试点后按相近业务条件比较，并单独说明订单复杂度、业务量和流程变化的影响。

成本应覆盖模型与工具调用、运行设施、人工复核、维护投入及异常处理。收益应使用可核验的时间节省、费用减少或业务改善，避免将同一项收益重复计算。

对提前交付场景，可以分别观察方案准备周期、计划调整成功率、实际准时到货率和单项合格任务成本。平台运行指标与经营指标共同反映系统价值。

### 5. 将运营责任落实到日常工作

业务团队定期复盘未完成任务与客户结果，数据团队处理事实和口径问题，平台团队处理运行与恢复问题，智能体维护者依据评测发布改进版本。

新增工厂或业务域时，重新确认业务对象映射、动作语义、审批范围和验收条件。复用已有运行机制可以降低建设成本，但每个新范围都需要完成必要验证。

建议首批项目评审提交六项具体材料：任务契约、责任矩阵、最小业务模型、工具动作契约、异常恢复方案，以及业务验收记录。它们共同回答平台要承担什么工作、依赖哪些条件，以及企业如何判断它已经具备上线资格。
