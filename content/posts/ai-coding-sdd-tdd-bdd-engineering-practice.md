AI Coding 最容易制造一种错觉：代码生成速度提高了，研发效率就自然提高了。

在个人实验或原型阶段，这个判断往往成立。开发者给出一句需求，Agent 在几分钟内创建页面、接口和数据库表，一个可以演示的版本很快就出现了。但当代码进入真实团队，问题也会一起出现：需求中的关键边界被模型自行补全；不同开发者用不同提示词得到完全不同的实现；测试是在代码完成后“顺手补上”的；规格、代码和验收标准逐渐分离；Pull Request 看起来改动完整，却没有人能快速证明它真的满足业务要求。

这不是模型不够强，而是软件工程中原本由需求分析、架构设计、测试、评审和发布流程承担的约束，被压缩进了一段临时对话。模型获得了更大的执行能力，团队却没有同步建立新的控制系统。

因此，AI Coding 的下一阶段并不是寻找一个更长的 Prompt，而是建立一条可审查、可执行、可验证的工程链路：

```text
业务意图
  ↓
Specification：明确要做什么、为什么做、什么算完成
  ↓
BDD：把关键业务规则变成可讨论、可执行的示例
  ↓
Plan / Tasks：把方案拆成边界明确的实现任务
  ↓
TDD：用失败测试驱动最小实现
  ↓
Review / CI：用自动化证据和人工判断共同把关
  ↓
Metrics：判断交付是否真的更快、更稳定、更经济
```

本文以 OpenSpec、GitHub Spec Kit 和 Superpowers 为代表，讨论如何把 Spec-Driven Development（SDD）、Behavior-Driven Development（BDD）和 Test-Driven Development（TDD）组合起来，并以“订单退款审批”功能为案例，给出一套适合团队逐步采用的 AI Coding 工程化方法。

> **资料边界**：本文在 **2026 年 10 月 12 日**核对了 OpenSpec、GitHub Spec Kit、Superpowers 与 Cucumber 的官方文档。相关工具仍在快速演进，命令名称和默认工作流应以各项目最新文档为准。文中的代码、目录和配置为工程示例，不代表这些项目的固定接口。

## 一、AI Coding 的主要风险不是“写错代码”，而是“正确地实现了错误理解”

传统开发中，需求从产品经理流向开发和测试，信息也会损失。但人通常会在会议、评审和联调中主动追问：谁可以操作？失败后如何恢复？是否需要幂等？旧数据怎么办？

Agent 的危险之处在于，它很少因为需求缺少这些信息而停下来。只要 Prompt 看起来足够完整，它就会根据训练数据中的常见模式补齐空白，并生成一套局部合理的实现。

例如，需求只有一句话：

> 为订单系统增加退款审批，小额退款自动通过，大额退款需要人工审批。

这句话至少隐藏了以下问题：

- “小额”的阈值是多少，是否按币种、渠道或商户配置？
- 判断依据是订单金额、申请退款金额，还是累计退款金额？
- 部分退款能否多次发起？
- 审批通过后，调用支付渠道失败怎么办？
- 相同幂等键的重复请求应该返回什么？
- 哪些角色可以审批，申请人能否审批自己的申请？
- 审批规则变更后，存量申请使用旧规则还是新规则？
- 自动审批是否也需要审计日志？
- 退款成功、审批通过和支付渠道受理是不是同一个状态？

如果这些问题没有被显式回答，Agent 依然可以生成 Controller、Service、Repository 和页面。问题只会从“需求不确定”转化为“代码中的隐含决策”，并在测试、联调或生产阶段重新暴露。

所以，AI Coding 的第一个工程原则是：

> **不要让模型通过写代码来替团队做产品决策。**

模型可以帮助发现问题、比较方案、生成草稿，但业务规则、风险边界和验收标准必须成为显式资产。SDD 的价值正是把这些容易散落在对话中的信息，转换成团队和 Agent 共同使用的执行契约。

## 二、SDD 不是“多写几份 Markdown”，而是建立意图到实现的追踪链

Spec-Driven Development 经常被误解为“先让 AI 写一份 PRD，再让它照着开发”。如果只是增加文档数量，SDD 不但不会提效，还可能制造大量很快过期的文本。

有效的规格必须承担三个责任。

### 1. 把决策和假设分开

规格应明确区分：

- 已确认的业务规则；
- 当前采用的技术决策；
- 尚未确认、需要人工回答的问题；
- 暂时不做的非目标；
- Agent 根据代码库观察得到的事实。

如果把这些内容混在一起，模型生成的一条“合理建议”很容易在下一轮对话中变成“既定事实”。

### 2. 让每项要求可以被验证

“系统应当安全”“页面体验要好”“接口性能要高”都不是可执行规格。更有效的表达应该包含条件、行为和可观察结果：

```text
当同一用户使用相同幂等键重复提交退款申请时，
系统不得创建第二条退款记录，
并应返回第一次申请的退款单号和当前状态。
```

这条要求既可以被业务评审，也可以被测试自动化，还可以在代码评审时追踪到具体实现。

### 3. 在需求、任务、测试和代码之间保留映射

一条完整的追踪链可以表示为：

```text
REQ-007 幂等退款申请
  ├─ SCN-007-1 相同幂等键重复请求
  ├─ TASK-014 增加幂等记录与唯一约束
  ├─ TEST-UNIT-032 幂等服务单元测试
  ├─ TEST-INT-011 并发请求集成测试
  └─ src/refund/idempotency-service.ts
```

有了这条链，团队才能回答：某个需求是否有实现任务，某个任务为什么存在，某个测试保护哪条业务规则，以及一次代码删除会影响哪些验收条件。

SDD 真正改变的不是文档格式，而是事实来源：**代码仍然描述系统现在如何运行，规格则描述系统为什么应该这样运行。** 两者都不能单独取代对方。

## 三、OpenSpec、Spec Kit 与 Superpowers 分别解决什么问题

这三个项目经常被放在一起比较，但它们并不完全处于同一层。OpenSpec 和 Spec Kit 主要组织规格与变更流程，Superpowers 更侧重通过 Skills 约束 Agent 的工作方式。实际落地时，不必机械地三选一。

### 1. OpenSpec：围绕“变更”组织轻量规格

[OpenSpec 官方文档](https://github.com/Fission-AI/OpenSpec/blob/main/docs/README.md)将目标概括为：让开发者和 AI Coding Assistant 在写代码前先对“要构建什么”达成一致。它的核心对象不是一份覆盖整个系统的巨型需求文档，而是一次具体变更。

其日常流程可以概括为：

```text
Explore（可选）
  → Propose
  → Review / Correct
  → Apply
  → Archive
```

扩展工作流还可以加入 `verify`、`sync` 等步骤。归档不只是移动文件，还会把已经交付的变化合并回主规格，使“当前系统规格”和“本次变更提案”保持区别。

OpenSpec 适合以下环境：

- 已有代码库中的增量开发；
- 团队希望低成本引入 SDD；
- Claude Code、Codex、Cursor 等多种工具并存；
- 不希望所有小改动都经过重型阶段门；
- 希望通过变更提案控制本次工作的边界。

它的优势是轻量，但也意味着团队要自己补充架构原则、测试标准、审批规则和 CI 门禁。OpenSpec 可以告诉 Agent 本次要改什么，却不会自动替组织建立完整的软件治理体系。

### 2. GitHub Spec Kit：阶段化、可治理的 SDD 工作流

[GitHub Spec Kit](https://github.com/github/spec-kit)提供了更完整的阶段模型。其核心链路是：

```text
Constitution
  ↓
Specify
  ↓
Clarify（按需）
  ↓
Plan
  ↓
Tasks
  ↓
Analyze（按需）
  ↓
Implement
  ↓
Converge
```

其中最有团队价值的并不是某一条命令，而是三个结构化控制点。

第一，**Constitution** 用来保存项目级不可随单个需求改变的原则，例如技术栈、架构边界、测试底线、安全要求和兼容性策略。

第二，**Specify、Plan、Tasks 分离**。业务规格先回答用户需要什么，技术计划再回答系统如何实现，任务列表最后回答开发顺序与验证方式。这种分离可以减少 Agent 在写需求时过早锁定实现方案。

第三，**Converge** 用当前代码反向检查 `spec.md`、`plan.md` 和 `tasks.md`，识别缺失、部分完成、相互冲突或超出规格的实现，并把剩余工作追加为可追踪任务。官方模板明确强调：任务勾选不是完成证据，当前行为是否满足规格才是判断依据。

Spec Kit 更适合：

- 跨模块或跨团队功能；
- 有明确架构、安全、合规要求的项目；
- 需要人工阶段评审的企业环境；
- 从零建设的新系统；
- 遗留系统改造和较长周期的复杂工作。

代价也很直接：规格、计划和任务如果没有控制粒度，很容易膨胀。团队需要为小改动设计简化路径，而不是要求修改一行配置也执行完整流程。

### 3. Superpowers：把工程纪律做成 Agent Skills

[Superpowers](https://github.com/obra/superpowers)把重点放在 Agent 应该如何工作。其基础流程包含：

```text
brainstorming
  → using-git-worktrees
  → writing-plans
  → subagent-driven-development / executing-plans
  → test-driven-development
  → requesting-code-review
  → finishing-a-development-branch
```

这套方法的核心不是生成更多文档，而是把容易被模型忽略的纪律写成可触发的 Skill：实现前先澄清和设计；在隔离工作区中操作；计划必须落到文件、接口、测试和验证命令；生产代码之前先看到测试失败；任务完成后请求评审；声明完成之前必须运行验证。

它适合解决另一个常见问题：团队已经有 Jira、PRD、ADR 和测试规范，但不同开发者使用 Agent 时，执行过程仍然高度随机。此时真正缺少的是 Agent 行为标准，而不是另一套需求管理工具。

### 4. 选型时不要问“哪个最好”，要问“我们缺少哪一层”

| 维度 | OpenSpec | GitHub Spec Kit | Superpowers |
| --- | --- | --- | --- |
| 主要对象 | 变更规格与增量 | 完整 SDD 阶段与产物 | Agent 行为与工程 Skills |
| 流程重量 | 低到中 | 中到高 | 中到高，可按 Skill 组合 |
| 适合任务 | 日常功能、缺陷、重构 | 复杂功能、跨团队项目 | Agent 深度参与的实施过程 |
| 项目级治理 | 需要团队补充 | Constitution 较适合承载 | 可写入 Skills 和规则文件 |
| TDD 约束 | 可集成 | 可在原则、计划和任务中定义 | 核心工作流直接强调 |
| 主要风险 | 规格过轻、验证不足 | 产物膨胀、流程仪式化 | 上下文和执行成本较高 |

一种实用组合是：

- 用 OpenSpec 管理多数日常变更，或用 Spec Kit 管理高风险、长周期功能；
- 用 BDD 把关键业务规则变成验收场景；
- 借鉴 Superpowers，把探索、计划、TDD、评审和完成前验证做成 Agent Skills；
- 用 CI/CD 和代码评审执行最终质量门禁；
- 用效能与质量指标判断这套流程是否值得继续。

## 四、端到端案例：给订单系统增加退款审批

下面用一个接近真实业务的例子说明这套链路如何运转。

### 1. 不要从生成代码开始，先探索系统事实

面对“增加退款审批”的需求，Agent 的第一项任务不应是创建 `RefundController`，而应是读取现有代码并建立事实清单：

```text
已确认事实
- 订单服务已经支持整单退款，但目前由客服后台直接触发。
- 支付渠道通过 payment-adapter 模块统一封装。
- order 表只有 PAID、REFUNDED 两个相关状态。
- 当前接口使用 X-Request-Id 做请求追踪，但没有业务幂等约束。
- 管理后台已经接入 RBAC，存在 finance_operator 和 finance_manager 角色。

待确认问题
- 自动审批阈值按申请金额还是订单金额计算？
- 是否允许部分退款和多次退款？
- 人工审批通过是否立即调用支付渠道？
- 支付渠道超时后由谁重试？
- 申请人能否审批自己的退款？

风险
- 订单状态不足以表达“审批通过但渠道处理中”。
- 重复请求可能导致重复退款。
- 支付调用和本地事务无法组成数据库事务。
```

这里的关键是把**代码库事实、业务疑问和技术风险分开**。Agent 可以帮助发现它们，但不能擅自把疑问变成决定。

### 2. 把需求写成有边界的规格

经过产品、开发和测试确认后，可以形成如下简化规格：

```markdown
# 退款审批规格

## 目标
在不改变现有支付渠道适配层的前提下，为已支付订单增加部分退款审批，
降低小额退款处理时间，同时保证大额退款经过财务复核。

## 角色
- customer_service：创建退款申请、查看状态
- finance_manager：审批或拒绝人工审批申请
- system：执行规则判断、调用支付渠道、记录审计日志

## 业务规则
- REQ-001：单次退款金额必须大于 0，且不得超过订单剩余可退金额。
- REQ-002：累计退款金额不得超过订单实付金额。
- REQ-003：退款金额小于等于 500 元时自动审批。
- REQ-004：退款金额大于 500 元时进入人工审批。
- REQ-005：申请人不得审批自己创建的退款申请。
- REQ-006：审批通过只代表允许执行退款，不代表支付渠道已经退款成功。
- REQ-007：同一订单、同一幂等键只能创建一条退款申请。
- REQ-008：所有自动与人工审批结果都必须记录规则版本和审计事件。

## 非目标
- 本次不支持跨币种退款。
- 本次不修改支付渠道的对账流程。
- 本次不自动重试支付渠道明确返回的业务拒绝。
```

这份规格没有提前规定使用哪种消息队列或表结构，但已经约束了实现不能绕过的行为。

### 3. 用 BDD 示例消除规则歧义

Cucumber 官方将 BDD 分为 **Discovery、Formulation、Automation**：先通过具体示例发现业务规则，再把示例写成团队共同认可的结构化表达，最后将其自动化。BDD 不是把测试用例改写成 Given-When-Then，而是先借助示例完成共同理解。

例如，针对自动审批规则，可以写出：

```gherkin
Feature: 退款审批

  Rule: 小额退款自动审批

    Scenario: 退款金额等于自动审批阈值
      Given 订单 ORD-1001 已支付 1000 元
      And 订单尚未发生退款
      When 客服申请退款 500 元
      Then 系统应创建退款申请
      And 审批状态应为 APPROVED
      And 执行状态应为 PENDING
      And 审计日志应记录当前规则版本

    Scenario: 累计退款金额超过订单实付金额
      Given 订单 ORD-1002 已支付 1000 元
      And 订单已经成功退款 800 元
      When 客服申请退款 300 元
      Then 系统应拒绝创建退款申请
      And 返回错误码 REFUND_AMOUNT_EXCEEDED
```

再看“申请人不能审批自己申请的退款”：

```gherkin
Scenario: 财务经理审批自己创建的申请
  Given 用户 U-21 同时拥有客服和财务经理角色
  And 用户 U-21 创建了退款申请 RF-9001
  When 用户 U-21 审批退款申请 RF-9001
  Then 系统应拒绝本次审批
  And 返回错误码 SELF_APPROVAL_FORBIDDEN
  And 退款申请状态仍为 PENDING_APPROVAL
```

具体示例会迫使团队面对文字规格中容易忽略的问题：500 元是否包含边界？审批状态和执行状态是否分离？权限按角色判断还是按申请人与审批人的身份关系判断？

### 4. 技术计划应该记录关键决策，而不是复述需求

基于规格和现有系统，可以形成技术计划：

```text
领域模型
- RefundRequest：退款申请与审批生命周期
- RefundExecution：支付渠道执行状态
- RefundPolicy：按规则版本判断审批路径

状态拆分
- approval_status：PENDING / APPROVED / REJECTED
- execution_status：NOT_STARTED / PENDING / SUCCEEDED / FAILED

一致性策略
- 数据库事务只负责保存退款申请和 Outbox 事件。
- 支付调用由异步消费者执行。
- 渠道调用使用 refund_request_id 作为外部幂等标识。

数据约束
- (order_id, idempotency_key) 建立唯一约束。
- 保存 policy_version、applicant_id、approver_id 和审计时间。

兼容性
- 旧的直接退款接口暂时保留，但内部改为创建“已审批”的退款申请。
- 通过配置开关逐步迁移客服团队。
```

一个合格的 Plan 应重点记录以下内容：

- 哪些决策是实现者不能自行更改的；
- 哪些模块会被修改；
- 数据和接口契约如何变化；
- 哪些风险需要专门测试；
- 如何发布、观察和回滚。

“创建 Service”“增加 Repository”“补充单元测试”不算技术计划，因为这些话没有减少任何实现歧义。

### 5. 任务必须小到可以独立验证，又大到值得单独评审

任务拆分可以采用纵向切片，而不是先把所有表建完，再写所有接口，最后统一补测试：

| 任务 | 交付结果 | 验证方式 |
| --- | --- | --- |
| TASK-001 | 剩余可退金额规则 | 领域单元测试覆盖零值、边界和累计退款 |
| TASK-002 | 自动/人工审批策略 | 参数化测试覆盖 499、500、501 元 |
| TASK-003 | 创建退款申请接口 | API 契约测试和数据库集成测试 |
| TASK-004 | 自审批禁止规则 | 权限测试和审计事件断言 |
| TASK-005 | Outbox 与异步执行 | 集成测试验证事务提交和重复消费 |
| TASK-006 | 管理后台审批页 | 组件测试与关键 E2E 场景 |
| TASK-007 | 旧接口兼容层 | 回归测试证明旧调用方行为不变 |

每个任务都应包含：

- 对应的规格编号；
- 要修改或新增的文件范围；
- 预期接口或行为；
- 先编写的失败测试；
- 测试命令和通过标准；
- 不允许顺手修改的范围。

这样做的目的不是让计划替代代码，而是让 Agent 在开始工作前知道“哪些决定已经做完，哪些选择仍然开放”。

---

## 五、把 TDD 变成 Agent 的执行协议，而不是一句“请补充测试”

很多团队声称在 AI Coding 中使用 TDD，实际流程却是：Agent 先写完实现，再生成一批能通过的测试。这是 Test-After Development，无法证明测试曾经捕获过缺失行为，也很难发现实现和测试是否在重复同一种错误理解。

真正的 TDD 循环仍然是 Red、Green、Refactor，但在 Agent 场景中需要增加证据要求。

### 1. Red：失败必须与目标行为相关

以自动审批阈值为例，先写测试：

```ts
describe("RefundPolicy", () => {
  it.each([
    [499, "APPROVED"],
    [500, "APPROVED"],
    [501, "PENDING_APPROVAL"],
  ])("routes %i yuan to %s", (amount, expected) => {
    const policy = new RefundPolicy({ autoApproveLimit: 500 });

    expect(policy.decide(amount)).toBe(expected);
  });
});
```

然后必须运行测试并观察它因为缺少目标能力而失败。以下情况都不算有效 Red：

- 测试因为语法错误失败；
- 测试环境没有启动；
- Fixture 缺失；
- 导入路径错误；
- 断言根本没有执行。

Agent 在报告中应记录测试命令、失败测试名称和关键失败原因，而不是只说“测试按预期失败”。

### 2. Green：只实现当前行为需要的最小代码

```ts
type ApprovalDecision = "APPROVED" | "PENDING_APPROVAL";

export class RefundPolicy {
  constructor(private readonly config: { autoApproveLimit: number }) {}

  decide(amount: number): ApprovalDecision {
    return amount <= this.config.autoApproveLimit
      ? "APPROVED"
      : "PENDING_APPROVAL";
  }
}
```

此时不应顺手增加币种换算、分级审批、复杂规则 DSL 或后台配置页面。规格中的非目标和任务边界，就是控制 Agent 过度实现的重要手段。

### 3. Refactor：保持行为不变地改善结构

只有测试通过后，才可以进行命名调整、重复消除、职责拆分和性能优化。重构完成后，应重新执行：

- 当前任务的目标测试；
- 受影响模块的回归测试；
- 必要的静态检查和类型检查。

### 4. 防止 Agent 为了通过测试而“作弊”

Agent 有时会选择最短路径满足当前断言，例如硬编码测试数据、降低断言强度、删除已有测试或在生产代码中识别测试环境。团队应把以下规则写入项目级规范：

```text
- 不得删除、跳过或弱化已有测试来使新实现通过。
- 不得在生产逻辑中根据测试环境返回特殊结果。
- 修复缺陷前必须先增加能够复现该缺陷的测试。
- 测试替身只能用于明确的外部边界，不得 Mock 被测核心行为。
- 对安全、权限、幂等和事务保护，测试必须证明保护失效时会失败。
```

对于关键规则，还可以使用变异测试或有意弱化实现来检查测试是否真的能失败。测试覆盖率只能说明哪些代码被执行过，不能证明断言足够有效。

### 5. TDD 与 BDD 的职责不同

BDD 和 TDD 经常被混为一谈。二者可以连接，但关注层次不同：

- BDD 通过示例澄清“业务希望看到什么行为”；
- TDD 通过快速反馈驱动“代码内部如何最小化实现该行为”；
- BDD 场景通常稳定、数量较少，表达领域语言；
- TDD 测试通常更细，允许随着内部设计重构。

一个 BDD 场景可能对应多个单元和集成测试，但不应把每个私有函数测试都暴露成业务场景。

## 六、团队定制的重点不是改模板，而是定义不可越过的边界

直接安装工具只能得到默认流程。要在团队中稳定运行，必须把组织经验转换为四类资产。

### 1. 项目 Constitution：长期稳定的工程原则

Constitution 或项目规则文件适合保存不会随单个需求频繁变化的约束。例如：

```markdown
## 架构原则
- 领域层不得依赖 Web 框架和数据库实现。
- 跨服务写操作必须显式定义一致性与补偿策略。
- 公共 API 的破坏性变更必须提供迁移窗口。

## 测试原则
- 缺陷修复必须先增加回归测试。
- 核心业务规则必须有不依赖网络和数据库的单元测试。
- 数据库约束、事务和并发行为必须使用真实数据库验证。
- E2E 只覆盖关键用户路径，不承担全部边界测试。

## AI 操作边界
- 未经人工确认不得执行破坏性数据库迁移。
- 未经人工确认不得升级框架主版本。
- 不得修改与当前规格无关的模块。
- 声明完成前必须提供实际运行过的验证命令和结果。
```

规则应当短、明确、可检查。把整个内部 Wiki 塞进 Agent 上下文，只会提高成本并稀释真正重要的约束。

### 2. Spec 模板：强制暴露业务空白

推荐的规格模板至少包含：

```text
背景与目标
角色与权限
业务规则
用户场景与验收标准
边界条件和失败行为
数据、安全、性能与兼容性要求
非目标
待确认问题
发布与回滚要求
```

模板字段不是越多越好。判断一个字段是否值得保留，可以问：它是否曾经阻止过返工、缺陷或错误决策？如果没有，可能只是文档装饰。

### 3. Skills：把高频工程动作做成可重复流程

团队可以把以下能力沉淀为 Skills：

- `explore-codebase`：读取入口、依赖、测试和变更历史，输出事实与疑问；
- `write-feature-spec`：按领域模板生成规格草稿并标记未决问题；
- `plan-with-tdd`：把每项任务拆成 Red、Green、Refactor 和验证步骤；
- `review-spec-compliance`：逐条检查实现与需求映射；
- `review-code-quality`：在规格符合后检查可维护性、安全和性能；
- `verify-before-completion`：运行测试、类型检查、构建和差异检查；
- `prepare-release-evidence`：生成发布说明、风险、观测项和回滚步骤。

需要特别注意：**Skill 文件存在，不代表 Agent 一定会正确执行。** 团队还需要通过样例任务和行为测试确认 Skill 是否会在正确时机触发、是否会越权、是否能在失败后停止并报告。

### 4. Definition of Done：把“完成”变成证据集合

AI Coding 环境中的完成定义可以包含：

```text
[ ] 所有规格要求都有任务或明确的不实施说明
[ ] 关键验收标准已映射到自动化测试
[ ] 新测试曾因目标行为缺失而失败
[ ] 相关单元、集成和端到端测试通过
[ ] 类型检查、静态检查和构建通过
[ ] 数据迁移、权限和兼容性风险已检查
[ ] 实现没有超出规格边界
[ ] 变更说明包含验证命令、结果和剩余风险
```

这份清单的价值在于把“Agent 说完成了”改造成“流水线和评审者能够独立复核完成证据”。

---

## 七、流程分级：不要让一行配置修改背负完整 SDD

SDD 最常见的失败方式是流程一刀切。为了避免遗漏，团队给所有任务增加同样的文档和评审步骤，最后开发者绕过流程，规格也沦为事后补写。

更合理的方式是按风险和复杂度分级。

### S 级：局部、低风险、行为明确

适合文案、样式、小范围配置和已有模式下的简单修复。

最小流程：

```text
问题说明
  → 回归测试或验证步骤
  → 实现
  → 相关测试与构建
```

### M 级：标准业务功能

涉及新的业务行为、接口或数据字段，但边界仍在单个服务或团队内。

标准流程：

```text
Explore
  → Spec + BDD Examples
  → Plan + Tasks
  → TDD Implementation
  → Spec Review + Code Review
  → CI Verification
```

### L 级：高风险或跨边界变更

涉及支付、权限、隐私、数据迁移、公共 API、跨服务一致性或多团队协作。

增强流程：

```text
Discovery Workshop
  → Spec + Threat Model + ADR
  → Architecture Review
  → Phased Plan
  → Isolated Implementation
  → BDD / TDD / Contract Tests
  → Security and Migration Review
  → Progressive Delivery
  → Production Verification
```

任务等级应由风险决定，而不是由代码行数决定。修改十行权限代码可能是 L 级，增加一个内部报表页面可能只是 M 级。

---

## 八、团队落地：从三人试点到组织级规范

不要在第一天就发布几十页 AI Coding 规范。更有效的路径是选一个真实项目，用数据验证哪些规则确实减少了返工。

### 第一阶段：建立基线

先记录当前状态：

- 从需求确认到合并的周期；
- PR 首次评审通过率；
- 平均返工轮次；
- 测试阶段发现的需求遗漏；
- 生产缺陷和回滚次数；
- 开发者在编码、等待和修复上的时间分布。

没有基线，团队很容易把“感觉生成更快”误认为端到端效能提高。

### 第二阶段：选择试点

选择一个中等复杂度、风险可控、能够在两到四周内完成的功能。参与者最好包括产品、开发和测试，而不是只让一名开发者独自试用工具。

试点只引入最关键的三项变化：

1. 编码前必须完成可评审的 Spec；
2. 每条关键业务规则必须有具体示例；
3. Agent 声明完成前必须提供真实验证结果。

### 第三阶段：把有效实践自动化

经过一到两个试点后，把重复出现的经验沉淀为：

- 仓库内的 Constitution 或 Agent Rules；
- Spec、Plan、Task 模板；
- BDD 场景示例库；
- TDD 和完成前验证 Skill；
- PR 模板和评审清单；
- CI 中的测试、安全、兼容性和迁移门禁。

自动化顺序很重要：先证明一条规则确实有价值，再把它固化进工具。否则，团队只是在自动化未经验证的流程偏好。

### 第四阶段：建立维护机制

AI Coding 规范本身也是代码，需要版本、负责人和反馈闭环：

- 谁可以修改项目级规则？
- Skill 更新是否需要测试？
- 旧项目如何获得新规则？
- 某条规则频繁被绕过，是培训问题还是规则本身不合理？
- 如何比较不同模型和工具下的执行效果？
- 如何回滚导致交付速度下降的规则？

没有维护机制，规则文件会不断增长，互相冲突，最终成为 Agent 和开发者都不愿阅读的历史堆积。

## 九、用什么指标证明 AI Coding 体系真的提效

AI Coding 最不应该使用的核心指标是代码行数、提交次数和 Prompt 数量。这些指标容易采集，却与用户价值和交付质量没有稳定关系。

建议从四个维度建立指标。

### 1. 流动效率

- 从规格确认到生产可用的端到端周期；
- 从开始编码到首次可评审 PR 的时间；
- 评审、测试和等待占总周期的比例；
- 单个功能的返工轮次；
- 在制品数量和任务阻塞时间。

### 2. 规格质量

- 开发开始后新增的关键需求数量；
- Spec Review 发现的歧义数；
- 验收阶段发现的需求遗漏率；
- 规格要求与自动化测试的映射覆盖率；
- 实现超出规格范围的变更比例。

### 3. 交付质量

- 首次评审通过率；
- 变更失败率；
- 生产逃逸缺陷；
- 缺陷平均恢复时间；
- 测试不稳定率；
- 因 AI 生成代码导致的回退或重写比例。

### 4. 成本与体验

- 单个功能的模型调用成本；
- 人工评审和修复时间；
- 开发者对认知负荷和工具体验的评价；
- 不同任务等级下的投入产出比；
- 因上下文膨胀和重复生成造成的浪费。

最终应比较的不是“AI 写一段代码需要几分钟”，而是：

> **从一个业务意图进入团队，到正确、可维护、可观察的功能到达生产环境，总共需要多少时间、成本和返工。**

如果生成速度提高了 50%，但评审时间翻倍、返工增加、线上缺陷上升，那么系统层面的研发效能并没有改善。

## 十、常见失败模式：为什么有了规格和测试仍然会失控

### 1. 规格由 AI 生成后无人评审

AI 可以快速生成结构完整的文档，但格式完整不等于业务正确。关键规则必须由有决策权的人确认，未决问题必须显式保留。

### 2. 规格包含过多实现细节

如果业务规格提前指定类名、表名和框架 API，Agent 会把当前方案误当成不可改变的需求，后续重构也会变得困难。业务行为、技术决策和任务实现应分层保存。

### 3. 任务按技术层横向切分

“先写全部数据库，再写全部后端，再写全部前端”会导致很长时间没有可验证结果。优先按用户行为纵向切片，让每个任务形成最小闭环。

### 4. 测试和实现由同一个上下文一次生成

同一 Agent 可能让测试重复实现中的错误假设。高风险功能可以让一个上下文生成业务示例，另一个上下文实现，再由独立评审或测试 Agent 检查规格符合性。

### 5. 只做代码质量评审，不做规格符合性评审

代码可以很整洁，却实现了错误行为。评审应先问“是否满足规格”，再问“实现质量如何”。Superpowers 的两阶段评审思路在这里很有参考价值。

### 6. 规则文件越来越长

规则应按全局、仓库、模块和任务分层，并按需加载。已经能由编译器、Linter 或 CI 强制的规则，不必继续消耗模型上下文反复说明。

### 7. 把 SDD 变成新的瀑布流程

规格不是一次冻结、之后不得修改的合同。实现中发现新事实时，应返回规格或计划阶段更新决策，并保留变更记录。SDD 的目标是持续对齐，不是禁止学习。

## 十一、一套可以直接采用的最小实践

如果团队还没有任何 AI Coding 规范，可以从下面这套最小流程开始。

### 开发前

```text
1. Agent 先读取相关代码和测试，输出事实、疑问与风险。
2. 人工回答影响业务行为的问题。
3. Agent 生成短规格，必须包含验收场景和非目标。
4. 人工确认规格后，Agent 才能生成技术计划和任务。
```

### 开发中

```text
1. 每次只执行一个边界明确的任务。
2. 先写测试并运行，确认因目标行为缺失而失败。
3. 编写最小实现，使测试通过。
4. 重构后运行相关测试。
5. 发现规格冲突时停止实现，回到规格阶段。
```

### 开发后

```text
1. 逐条检查规格、场景、任务、测试与代码映射。
2. 运行单元、集成、端到端、类型检查和构建。
3. 单独执行规格符合性评审与代码质量评审。
4. PR 中记录验证命令、结果、风险和回滚方式。
5. 合并后观察生产指标，并把新知识更新回规格与规则。
```

这套流程不依赖某个特定产品。OpenSpec、Spec Kit 和 Superpowers 的价值，在于帮助团队把其中不同部分自动化和标准化，而不是代替团队做判断。

---

## 十二、结语：AI Coding 的真正壁垒是可验证的工程上下文

Prompt 决定一次生成的质量，工程体系决定团队能否长期稳定地交付。

OpenSpec 展示了如何围绕一次变更建立轻量规格；Spec Kit 展示了如何用 Constitution、Specify、Plan、Tasks 和 Converge 组织更完整的 SDD 流程；Superpowers 展示了如何把探索、计划、TDD、评审和验证做成 Agent 必须遵循的 Skills。BDD 让业务规则通过示例变得可讨论，TDD 则让代码在快速反馈中逐步形成。

这些方法最终指向同一件事：把原本依赖资深工程师经验、临场追问和人工记忆的知识，转换成 Agent 能读取、流程能执行、测试能验证、团队能持续改进的工程资产。

成熟的 AI Coding 团队不会把目标定为“让 AI 写更多代码”，而会建立下面这个闭环：

```text
意图可表达
  → 决策可追踪
  → 任务可执行
  → 行为可验证
  → 变更可审查
  → 结果可度量
  → 经验可复用
```

当这条链路建立起来，模型能力提升会直接放大团队产出；如果链路不存在，更强的模型只会更快地产生更大范围的不确定性。
