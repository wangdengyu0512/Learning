# 把“检索 + LLM”拆成一条可定位、可优化的工程系统

很多团队搭建 RAG（Retrieval-Augmented Generation，检索增强生成）时，第一版通常非常顺利：文档切块、生成向量、写入向量库，用户提问后取回若干片段，再交给大模型组织答案。

真正困难的是第二步：

- 答案错了，究竟是没有检索到正确证据，还是模型没有正确使用证据？
- 换了 Embedding 之后效果没有提升，问题是不是根本不在向量模型？
- 已经用了 Hybrid Search 和 Reranker，为什么还是会漏掉关键事实？
- 上下文窗口越来越长，为什么塞入更多文档，效果反而可能下降？
- 面对 GraphRAG、Agentic RAG、视觉检索等方案，如何判断它们解决的是不是当前问题？

如果系统只能输出最终答案，而中间过程不可见，那么每次失败都只能靠“再调一调 Prompt”“多取几个 Chunk”“换一个模型”碰运气。

更有效的理解方式，是把 RAG 看成一条逐级收窄的工程漏斗：

```text
源文档
  ↓
解析与分块
  ↓
嵌入并写入索引
  ↓
查询理解与查询改写
  ↓
第一阶召回：尽量不要漏
  ↓
第二阶重排：尽量减少噪声
  ↓
上下文组装
  ↓
基于证据生成、引用或拒答
  ↓
最终答案
```

这条链路中的每一段，都有不同的目标、指标、成本和失败方式。只有把它们拆开，RAG 才会从一个 Demo 变成真正可治理的工程系统。

> **资料说明**：本文根据目录内六个章节整理与重写，前沿技术与数据沿用原始材料截至 **2026 年 6 月** 的时间口径。

## 一、RAG 的本质：把知识从模型权重里搬出来

大模型的知识主要储存在参数中，也就是所谓的“参数化记忆”。这种知识有三个天然限制：

1. **更新慢**：知识发生变化后，模型不会自动知道；
2. **溯源难**：模型很难说明某个结论具体来自哪份文档；
3. **私有知识缺失**：企业制度、内部手册和实时业务数据通常不在训练语料中。

微调可以改变模型的行为和表达方式，却不适合频繁更新大量事实知识。把整本手册直接塞进 Prompt，也会带来高成本、长延迟、噪声增加，以及关键信息在长上下文中被忽略等问题。

RAG 选择了第三条路：**知识保留在模型外部，回答时只取回与当前问题有关的少量证据。**

因此，RAG 改变的并不只是 Prompt，而是知识的存放位置和更新方式：

- 模型权重负责语言能力、推理模式和通用知识；
- 外部索引负责可更新、可检索、可追踪的业务知识；
- 生成阶段负责把问题与证据组织成答案。

可以把它类比为开卷考试。但这个类比有一个重要边界：考生知道自己正在引用哪本书，而大模型只是根据上下文计算下一个 Token 的概率。即使正确证据已经放在面前，它仍可能抄错、漏抄，或者用参数中的旧知识覆盖新证据。

所以必须记住一句话：

> **检索质量决定答案质量的上限，但完美检索并不保证完美回答。**

## 二、先把系统分成两条路径：索引侧与查询侧

一个完整的 RAG 系统至少包含两条时间尺度不同的路径。

### 1. 索引侧：离线的写路径

```text
文档 → 解析 → 分块 → 嵌入 → 写入索引
```

索引侧负责把原始知识变成可检索单元。它通常在文档新增、修改或删除时运行，不需要为每次提问重复执行。

### 2. 查询侧：在线的读路径

```text
问题 → 查询理解/嵌入 → 召回 → 重排 → 上下文组装 → 生成
```

查询侧需要在用户等待时间内完成，因此对延迟和成本更敏感。

两条路径的交汇点是索引。这里有两个经常被忽略的工程约束：

- 文档向量和查询向量必须位于兼容的向量空间中；
- 源文档的增、删、改必须同步反映到索引中。

如果一份政策已经从源系统删除，但对应向量仍留在索引里，用户仍可能检索到旧政策。此时问题不在 Prompt，也不在大模型，而在索引写路径没有正确处理删除事件。

这正是分阶段建模的价值：同样是“答案错误”，可能需要修复的是文档生命周期，而不是生成模型。

## 三、RAG 的主线：从保召回到提精度

RAG 的检索链路通常不是一步完成，而是一个由宽到窄的漏斗。

### 第一阶：廉价召回，宁可多捞

第一阶面对整个语料库，首要目标是 **Recall——不要让正确证据漏在门外**。这一阶段必须足够快，因此通常使用可预计算的向量检索和倒排检索。

### 第二阶：昂贵精排，压低噪声

第一阶返回的候选往往“相关但不够准确”。第二阶使用更昂贵的模型逐条判断 Query 与候选文档的细粒度关系，首要目标是 **Precision——把真正有用的证据推到前面**。

这两个阶段不能相互替代：

- 召回不足时，正确证据没有进入候选，重排再强也无米下锅；
- 只有召回、没有重排时，大量噪声进入上下文，会抬高成本并干扰生成；
- 直接用昂贵的重排模型扫描全库，则会因为逐文档前向计算而无法承受。

因此，成熟的检索链路往往是：

```text
查询改写 → Hybrid 召回 → Rerank 精排 → 少量高质量上下文
```

## 四、Dense 与 BM25 应该互补，而不是二选一

### 1. Dense Retrieval：擅长语义，弱于精确字形

Dense 检索把 Query 和文档分别编码成定长向量，再根据点积或余弦相似度寻找近邻。

它的优势是可以处理同义改写。例如用户问“住宿能报多少”，文档写的是“差旅住宿费用报销上限”，两者字面不同，但语义接近。

它的代价也来自“压成一个向量”：一整段文字被压缩成一个语义点，本质上是有损的。它容易丢失：

- 型号、编号和表单名，如 `SKU-7741`、`1099-MISC`；
- 罕见术语和训练分布外词汇；
- 一段文本中的细粒度限定关系。

Dense 向量像一张语义缩略图：能看出主题，却未必读得清其中的小字。

### 2. BM25：擅长精确词项，弱于同义表达

BM25 根据 Query 与文档之间的词项重叠打分，综合考虑词频、逆文档频率和文档长度。

它不真正理解语义，却能精准捕捉编号、专有名词和罕见 Token。只要文档中明确出现 `1099-MISC`，BM25 就有机会把它强力召回。

但如果用户和文档没有字面重叠，即使表达的是同一件事，BM25 也可能接近零分。

### 3. Hybrid Search：用两条路线覆盖彼此盲区

| 检索方式 | 强项 | 典型盲区 |
|---|---|---|
| Dense | 同义改写、语义相近 | 精确编号、罕见 Token、细粒度字形 |
| BM25 | 专有名词、编号、字面命中 | 同义表达、词面不重叠 |

Hybrid Search 同时运行两路检索，再融合结果。常见的 RRF（Reciprocal Rank Fusion）不是直接相加原始分数，而是根据各路排名计算融合分数：

```text
RRF(doc) = Σ 1 / (k + rank_i(doc))
```

原因是 BM25 分数与向量相似度不在同一尺度上，直接相加相当于把不同单位的数值混在一起。RRF 放弃原始置信度，只保留排名，以换取跨检索器的稳定性。

## 五、为什么已经 Hybrid 了，还需要 Reranker

第一阶检索通常使用 Bi-encoder：Query 与文档分别编码，在线只需比较两个向量。它速度快、文档向量可缓存，但 Query 和文档在编码过程中从未真正“见面”。

Reranker 通常使用 Cross-encoder：把 Query 与候选文档拼接后共同送入模型，让两者逐 Token 交互。它更容易判断：

- 否定关系；
- 数值到底修饰哪个对象；
- 条件、范围与例外；
- “主题相似”与“真正回答当前问题”的区别。

例如两个片段都在讨论差旅费用，但只有一个明确说明“一线城市住宿上限为 800 元”。向量相似度可能认为它们都很像，而 Cross-encoder 更有机会识别数值与对象之间的准确归属。

代价是每个候选都要单独执行一次前向计算，因此 Reranker 只能处理第一阶产生的小规模候选集。

> **Bi-encoder 解决规模问题，Cross-encoder 解决精度问题。**

## 六、查询改写：很多召回失败，从入口就开始了

用户的自然语言问题通常很短、很口语化，也可能同时包含多个意图。即使索引和检索器都没有问题，一个表达不充分的 Query 也可能把检索带偏。

常见的入口优化包括：

### HyDE

先让 LLM 生成一段“假设答案”，再嵌入这段答案去检索。它利用了“答案式陈述”和文档正文通常位于更相近的向量区域这一特点。

### Multi-query

把一个问题改写成多种不同措辞，并行检索后取结果并集，用措辞多样性提高召回。

### Query Decomposition

把多意图问题拆成若干子问题。例如：

```text
“出差住宿和交通的报销上限分别是多少？”
```

可以拆成：

```text
1. 出差住宿报销上限是多少？
2. 出差交通报销上限是多少？
```

单个向量很难同时准确表达多个独立意图，拆开后每个子查询都更容易命中对应证据。

## 七、分块不是预处理细节，而是检索系统的入口设计

很多 RAG 项目把 Chunking 当成一个固定参数，例如“每 500 Token 切一段”。但分块决定了什么内容能够成为独立的检索单元，是整个漏斗的入口闸门。

分块存在一个无法同时取胜的三难：

1. **Recall**：片段要足够大，避免完整答案被切散；
2. **Precision**：片段要足够小，避免多个主题混在一起，导致向量被稀释；
3. **Context Budget**：片段不能太大，否则 Top-K 很快耗尽上下文并引入噪声。

| 策略 | 优点 | 风险 |
|---|---|---|
| 固定大小分块 | 简单、稳定、易批处理 | 可能切断句子、表格和逻辑边界 |
| 递归/结构感知分块 | 尊重标题、段落、表格等结构 | 依赖较干净的文档结构 |
| 语义分块 | 在话题变化处切分，主题更集中 | 计算成本更高，阈值需要调优 |

对事实型问答，可以从较小片段开始；对分析和长推理任务，则需要更大的上下文单元。无论使用哪种策略，都应根据真实问题集评估，而不是迷信统一的 Chunk Size。

表格尤其需要特殊处理。若把“住宿费上限”和“一线城市 800 元”切进两个 Chunk，检索系统即使找到了数字，也可能不知道数字修饰的对象。更合理的做法是保留表头、行列关系和所在章节，必要时先转换为结构化 HTML 或其他可保留语义关系的形式。

## 八、证据已经找对，模型为什么仍然会答错

把证据放进 Prompt，只是在改变生成概率，而不是建立逻辑上的强制约束。模型仍可能：

- 使用参数中的旧知识覆盖新政策；
- 把不同片段中的数字和对象错误拼接；
- 面对证据不足时继续猜测；
- 忽略位于长上下文中间的关键证据。

工程上可以使用三个 Grounding 杠杆。

### 1. Grounding Prompt

明确要求模型只依据给定上下文回答，证据不足时不要补写未知事实。这是成本最低的基础约束。

### 2. Citation

要求每个关键结论附带 Chunk ID、页码或文档位置，并在生成后校验引用是否真的支持该结论。引用不只是展示功能，也是一种抑制无依据生成的机制。

### 3. Abstention

给模型一条明确的拒答路径。当检索置信度过低、证据覆盖不足或材料互相冲突时，允许系统回答“当前资料不足以确定”。

但 Grounding 也不是越强越好。阈值过高、提示过于保守，会导致本来可以回答的问题被拒绝。系统需要在“减少幻觉”和“避免过度拒答”之间寻找业务可接受的平衡点。

## 九、评估必须拆成四个指标

端到端正确率只能告诉你系统坏了，却不能告诉你坏在哪里。要让 RAG 可调试，应分别观察检索侧与生成侧。

| 阶段 | 指标 | 回答的问题 |
|---|---|---|
| 检索侧 | Context Recall | 回答问题需要的证据是否被完整取回？ |
| 检索侧 | Context Precision | 取回的内容是否大多有用，并排在前面？ |
| 生成侧 | Faithfulness | 答案中的论断是否都能由上下文支持？ |
| 生成侧 | Answer Relevance | 答案是否真正回应了用户的问题？ |

这四个指标可能彼此解耦。

例如，系统可能得到很高的 Faithfulness 和 Answer Relevance，却仍被用户投诉答案错误。原因可能是检索只拿到了一份不完整的证据：模型忠实地回答了问题，也没有凭空编造，但它是**基于残缺上下文，忠实地答错**。此时真正欠债的是 Context Recall。

反过来，证据完整但 Faithfulness 很低，说明问题更可能发生在生成阶段，应该检查 Grounding、引用校验和上下文组织，而不是继续扩大召回数量。

## 十、把常见故障映射回漏斗

| 症状 | 优先检查 | 可能根因 | 优化方向 |
|---|---|---|---|
| 命中数字，却丢失数字所属条件 | Context Recall | Chunk 太小或表格被切断 | 增加 Overlap、结构感知分块 |
| 正确片段存在，却排不进前列 | Context Precision | Chunk 太大、主题混杂 | 缩小片段、重排、改善索引语义 |
| 型号或编号总是检索错 | Context Recall | Dense 丢失精确字形 | 加入 BM25，采用 Hybrid |
| 正确证据进入候选，但没进入最终上下文 | Rerank 日志 | Top-K 截断或重排不准 | 调整候选规模与 Reranker |
| 证据完整，答案仍张冠李戴 | Faithfulness | 生成未扎根 | 加强 Grounding、Citation 校验 |
| 证据不足，模型仍强行回答 | Faithfulness | 没有拒答机制 | 增加 Abstention 与置信阈值 |
| 答案忠实，却答非所问 | Answer Relevance | 查询理解或生成偏题 | 查询改写、意图识别、约束输出 |
| 已删除文档仍被引用 | 索引新鲜度 | 删除事件未同步到索引 | 修复索引增删改生命周期 |
| 单点事实很准，跨文档归纳总漏 | Context Recall | 平铺 Top-K 不适合全局问题 | GraphRAG、分层摘要或多轮检索 |

排查时最有价值的第一步，通常不是换模型，而是打印并保存每一阶的产物：

```text
原始 Query
→ 改写后的 Query
→ Dense 候选
→ BM25 候选
→ 融合后的候选与名次
→ Rerank 前后排序
→ 最终送入模型的上下文
→ 带引用的答案
```

没有这条观测链路，就没有真正意义上的可定位和可优化。

## 十一、前沿方案是漏斗上的不同补丁

面对不断出现的新方法，最实用的问题不是“它是不是更先进”，而是：

> **它修改了漏斗的哪一段？它解决的是否正是当前系统的主要瓶颈？**

### Contextual Retrieval：修索引侧的上下文丢失

在 Chunk 写入索引前，为它补充一小段定位信息，例如所属文档、章节、主题和指代对象，再进行向量化与 BM25 索引。它解决的是 Chunk 脱离原文后语义不完整的问题，与后续 Rerank 可以叠加。

### GraphRAG / LazyGraphRAG：改变检索单元

传统 RAG 检索平铺 Chunk，适合单点事实，却不擅长“总结全部文档的共同主题”或“寻找跨部门政策冲突”这类全局、多跳问题。

GraphRAG 将语料组织为实体—关系图和社区摘要，检索对象不再只是局部片段。LazyGraphRAG 则试图降低全量建图和预摘要的成本，把更多计算推迟到查询阶段按需完成。

### Agentic RAG：把一次性漏斗变成反馈循环

普通 RAG 是一次性的：检索一次，然后无论结果好坏都继续生成。Agentic RAG 在外层加入控制循环：

```text
检索 → 自评证据质量 → 改写/再次检索/调用外部工具/拒答 → 生成
```

它适合多跳、高风险或证据不稳定的任务，代价是更多延迟、Token 和系统复杂度。

### Late Interaction 与视觉检索：改变嵌入单元

ColBERT 一类 Late Interaction 方法不再把整段文本压成单向量，而是保留 Token 级多向量，提升细粒度匹配能力。

面对扫描件、图表、多栏布局和复杂表格 PDF，视觉文档检索则直接把页面图像作为检索对象，减少“OCR → 解析 → 分块”链路中的信息损失。

### 长上下文与 RAG：不是替代关系，而是查询路由

长上下文适合答案分散、难以被少量片段覆盖，并且总材料仍能放入窗口的任务；RAG 适合答案集中在少量证据中、需要低成本和可溯源的任务。

更合理的架构是在漏斗之前增加路由：

```text
当前问题的答案是否集中在少量可检索片段？
  ├─ 是：走 RAG
  ├─ 否，但材料总量可控：走长上下文
  └─ 复杂/多跳/高风险：走多轮或 Agentic 流程
```

更多上下文不等于更好。无关内容增加后，信噪比下降，关键证据也可能被埋在长输入中间。工程目标应该是提供**最小但充分的证据集**，而不是把窗口尽量塞满。

## 十二、一个可落地的 RAG 优化顺序

### 第一步：建立基线数据集

收集真实问题，并为每个问题标注期望答案、支撑文档、证据片段、是否允许拒答，以及问题属于事实型、归纳型、多跳型还是精确编号型。

### 第二步：让中间链路可观测

记录 Query 改写、各路召回结果、融合排名、重排分数、最终上下文、引用和答案。必要时为每个请求生成 Trace ID。

### 第三步：先修 Recall

确认正确证据能进入第一阶候选。优先检查：

- 分块是否破坏结构；
- 索引是否新鲜；
- Dense 与 BM25 是否互补；
- Query 是否需要改写或分解；
- Metadata Filter 是否误杀正确结果。

### 第四步：再修 Precision

在召回基本合格后，再优化融合策略、Reranker、候选数量、最终上下文数量、证据顺序、去重和冲突处理。

### 第五步：最后修生成

如果证据已经正确且完整，再调整 Grounding Prompt、引用校验、拒答策略、结构化输出和生成参数。

### 第六步：按问题类型路由

不要强迫所有问题走同一条链路。单点事实、跨文档总结、多跳推理、视觉 PDF 和超长材料，本来就需要不同的检索单元与执行策略。

---

## 结语：不要再问“RAG 好不好”，要问“哪一阶在欠债”

RAG 最重要的工程价值，不是给 LLM 外接了一个向量数据库，而是把知识问答拆成了一条可观测的系统：

- 分块决定答案能否成为完整的检索单元；
- Dense 与 BM25 共同决定第一阶召回上限；
- Reranker 决定噪声能否在进入生成前被压下去；
- Grounding、引用和拒答决定模型是否正确使用证据；
- 分阶段指标决定一次失败能否被准确定位；
- Graph、Agent、视觉检索和长上下文路由，则在不同位置扩展这条主干。

当答案出错时，不要立刻换 Embedding，也不要先把 Top-K 从 5 调到 50。先问四个问题：

1. 正确证据是否存在于索引中？
2. 它是否进入了第一阶候选？
3. 它是否在重排后进入了最终上下文？
4. 模型是否忠实地使用了这份上下文？

能回答这四个问题，才算真正拥有了一套 RAG 系统，而不只是一个“检索 + LLM”的演示程序。
