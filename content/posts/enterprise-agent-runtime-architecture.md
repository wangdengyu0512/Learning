企业级智能体要持续参与业务，需要在任务执行过程中获得可信数据、受控权限、稳定资源和可恢复状态。模型提供理解、推理与规划能力，运行底座负责把这些能力组织成可管理、可核验的执行过程。

这也是企业级 Agent OS 的核心定位：在业务应用、模型服务与企业系统之间，提供共同遵循的运行契约，并在执行时落实身份、权限、状态、资源和质量约束。

本文主要参考 GNex 技术洞察的《智能体为什么需要操作系统》，沿用原文从四类运行问题推导六项公共能力的思路，进一步整理职责边界、总体架构与执行机制。[1] 文中的架构图与工程约束是对这一思路的展开，用于说明设计关系。

## 一、从四类运行问题理解底座的必要性

智能体从独立交互进入企业流程后，会同时面对连接、行为、认知和运行四方面的要求。它们共同决定任务能否持续推进，以及执行结果能否被业务接受。

| 问题维度 | 核心缺口 | 运行底座需要建立的能力 |
| --- | --- | --- |
| 系统接入 | 身份传递、接口语义、异步回执与写入机制缺乏一致约定 | 统一接入与能力注册，让调用具备明确的身份、输入、输出和执行语义 |
| 行为约束 | 权限与业务规则未落实到实际执行路径 | 在动作执行前强制校验身份、授权、参数和前置条件 |
| 认知积累 | 数据、规则、任务状态与历史经验缺乏清晰归属 | 管理知识来源、有效范围与版本，让经验经过验证后复用 |
| 运行恢复 | 任务依赖临时上下文，故障后难以确认进度和外部结果 | 持久化状态、协调资源、核对副作用，并支持接续执行 |

这些问题具有跨应用的共性。分别在各个智能体中实现，会使权限口径、恢复行为和审计证据难以保持一致。抽取公共能力的价值，是让不同业务应用共享可验证的运行规则。

因此，底座设计需要回答一个共同问题：**任务每前进一步，系统凭什么允许它继续，又如何确认这一步实际产生了什么结果？**

## 二、Agent OS 的定位与职责边界

本文将 Agent OS 定义为面向企业智能体的公共运行与治理体系。“操作系统”强调任务管理、资源分配、访问控制和故障恢复等职责；具体实现可以由多个服务与既有平台共同承担。

### 1. 业务定义目标，底座保障执行

业务应用负责定义任务目标、领域规则、完成标准和人工责任。运行底座负责把这些要求转化为执行约束，并贯穿任务创建、调度、调用、等待、恢复与验收。

| 组成 | 主要职责 | 与运行底座的边界 |
| --- | --- | --- |
| 业务应用 | 定义目标、业务规则与交付标准 | 提供任务约定，保留业务判断与责任归属 |
| 模型服务 | 理解信息、生成计划、提出候选动作 | 输出接受校验，执行权限由外部机制控制 |
| 智能体开发框架 | 组织模型交互、工具调用与推理循环 | 可参与运行期执行，但需接入组织级治理约束 |
| Agent OS | 管理任务生命周期、资源、状态与执行治理 | 对公共执行规则及其落实负责 |
| 企业数据与业务系统 | 保存权威事实，执行受控业务操作 | 保留数据主权、事务边界与最终状态解释权 |

### 2. 统一规则，分布式执行

公共治理需要一致的身份语义、策略版本、能力定义和审计口径。运行实例则可以按组织、租户、环境和资源要求进行隔离部署，并通过多副本承担并发与故障切换。

因此，本文将组织级统一落实为共享契约和治理规则。控制服务可以高可用部署，执行节点可以横向扩展，状态存储可以按隔离要求划分。

### 3. 在真实动作发生的位置落实约束

安全策略只有覆盖实际执行路径才有意义。模型产生的调用请求，需要经过受控的执行入口；凭据、网络访问与运行环境也应受到约束，防止绕开该入口直接访问资源。

策略服务负责给出判断，执行组件负责落实判断。审批、审计和质量校验需要与具体任务、计划版本及动作关联，才能形成完整的责任链。

## 三、六项公共能力构成总体架构

参考文章将公共能力归纳为统一运行框架、统一调度管理、统一数据基座、统一生态链接、统一安全管理和统一持续进化。[1] 这六项能力共同覆盖任务执行所需的过程、资源、认知、连接、治理与改进。

![企业级 Agent OS 总体架构：业务入口连接公共运行底座，底座包含六项能力，并通过受控接口访问模型、企业系统与基础设施。](/images/enterprise-agent-runtime/architecture.svg)

图 1：企业级 Agent OS 总体架构。六项能力按职责划分；实际部署时可以组合实现，并复用已有基础设施。

### 1. 统一运行框架：管理任务推进过程

运行框架把目标、计划、动作和结果组织为明确的任务生命周期。关键节点设置质量校验，明确何时继续、等待、重试、终止或交由人工处理。

其核心对象包括任务、执行实例、计划版本、动作记录与验收结果。每个对象具有稳定标识，确保一次重试、一次重新规划与一次新的业务动作能够被正确区分。

运行框架还需要保留决策摘要、所用依据、工具调用及核验记录。可追溯性建立在可观察的输入、动作和结果上，无需依赖模型内部推理过程的完整暴露。

### 2. 统一调度管理：协调执行资源

调度层负责队列、优先级、并发配额、资源分配、超时控制与故障转移，并为执行实例提供适当的隔离环境。

任务状态与执行进程分离后，资源可以释放、替换和重新分配。接续执行仍需核对持久化进度与外部操作结果，避免把进程恢复误当成业务恢复。

模型路由也属于资源管理的一部分。切换模型时需要重新检查能力要求、数据使用边界与工具调用契约，并验证输出质量，确保切换后的执行仍满足任务约定。

### 3. 统一数据基座：组织事实、知识与记忆

数据基座为智能体提供一致的业务语义、可信来源和受控访问入口。对象标识、关系、状态、规则及有效时间共同决定信息如何解释和使用。

运行中的任务状态、长期业务知识与可复用经验需要分别维护。前者服务于恢复与协调，后两者服务于理解和后续决策，更新流程与有效性要求各不相同。

已有数据平台可以继续承载数据处理与存储。Agent OS 重点补齐智能体使用数据时需要的权限、语义、上下文组织和证据关联。

### 4. 统一生态链接：提供一致的能力入口

连接层统一注册模型、工具、服务与智能体，维护能力描述、接口契约、版本和可用状态，使上层能够按任务要求发现并调用能力。

连接契约需要覆盖输入输出、身份传递、异步回执、超时含义、幂等条件与错误分类。仅统一调用格式，仍不足以判断动作是否执行成功、能否重试以及如何核对结果。

连接层与安全层共同形成受控执行入口：连接层处理协议与执行语义，安全层判断调用是否获准，业务系统负责其内部校验和状态变更。

### 5. 统一安全管理：执行治理并形成证据

安全管理贯穿身份绑定、最小授权、租户隔离、审批、敏感信息保护、工具访问和行为审计。

一次授权判断应同时考虑发起主体、执行身份、目标资源、具体动作、参数、环境和有效时间。外部内容进入上下文后仍属于输入数据，不能据此改变系统权限或审批要求。

观测与审计也在这一职责下形成统一规范：运行组件产生事件，平台关联任务、动作与外部回执，分别支持故障定位、运行分析和责任追溯。日志与证据本身也需要访问控制、脱敏和留存管理。

### 6. 统一持续进化：将反馈转化为受控改进

持续进化把任务结果、人工纠正和运行异常转化为候选改进，覆盖知识、规则、提示词、工具契约与执行流程。

候选内容需要经过证据检查、质量评估和版本管理，再进入受控发布。运行期可以在既有授权范围内调整计划；涉及共享策略、权限或公共知识的变更，则进入独立的治理流程。

这样既保留任务执行的适应能力，也使跨任务复用的改进具备来源、适用范围和回退路径。

## 四、把六项能力组织成运行闭环

总体架构说明能力放在哪里，执行链路说明它们如何共同发挥作用。任务应沿明确的状态与证据推进，从创建到结束都有可解释的条件。

![任务执行与治理流程：任务约定进入计划生成和动作校验，按需审批后经执行入口调用目标系统，核验结果；未知结果进入核对与恢复，关键阶段持久化状态和证据。](/images/enterprise-agent-runtime/execution.svg)

图 2：任务执行与治理流程。执行前校验决定动作能否发生，执行后核验决定任务能否继续或完成。

### 1. 先建立任务约定

任务创建时，需要明确目标、范围、授权、输入依据、资源预算、完成标准和退出条件。这份约定同时约束规划、执行与验收。

任务状态至少要区分待执行、运行中、等待审批、等待外部结果、核验中、已完成、已失败、已取消和已移交。动作记录还应单独表达结果未知，避免把通信异常直接归入执行失败。

### 2. 计划经过校验后才能进入执行

模型提出候选计划，运行框架检查步骤依赖、输入完整性与完成条件，策略组件判断动作是否处于授权范围。

需要人工确认的动作进入等待状态。审批记录应绑定计划版本、动作范围、关键参数与有效期。计划或关键事实发生变化后，需要重新判断原审批是否仍然有效。

执行前还要再次检查当前权限、资源版本和前置条件，使审批时的判断与实际执行时的状态保持衔接。

### 3. 结果核验决定下一次状态迁移

工具返回值需要结合执行回执与权威状态进行解释。对于改变外部状态的动作，应通过可核验的证据确认实际结果，再决定继续、补偿或关闭任务。

任务完成由预先定义的验收条件决定。产出文本、调用返回成功和业务目标达成，应分别记录；只有满足任务约定的交付结果，才能进入完成状态。

### 4. 状态和证据贯穿全程

任务进度、动作标识、审批引用、执行回执、核验结果与组件版本共同构成恢复依据。观测记录负责解释执行过程，结构化状态负责驱动后续行为。

两者通过稳定标识关联，既能定位异常，也能明确恢复时允许从哪里继续。

## 五、可靠性设计围绕外部副作用展开

任务可以重新调度，模型可以重新生成输出，外部系统中已经发生的变更却需要单独处理。可靠性设计必须识别这几类行为的区别。

| 机制 | 需要保证的性质 | 设计边界 |
| --- | --- | --- |
| 状态持久化 | 关键进度与动作意图可被后续执行者读取 | 本地状态与外部变更之间可能存在未确认区间 |
| 幂等控制 | 同一逻辑动作的重复请求不产生重复业务效果 | 依赖稳定标识、参数约束和目标系统支持 |
| 未知结果核对 | 通信失败后仍能确认原动作的实际状态 | 未确认前限制后续依赖动作和盲目重试 |
| 并发控制 | 多个执行者不会基于过期状态重复推进 | 需要状态版本、租约或执行令牌配合校验 |
| 补偿处理 | 部分执行后能够按规则修复业务状态 | 补偿本身是新动作，可能失败且未必能完全逆转 |
| 超时与预算 | 单个任务的等待、调用和资源消耗有界 | 达到限制后保存状态，并明确终止或移交方式 |
| 降级与切换 | 依赖不可用时仍有受控的处理路径 | 切换后的能力、权限和质量要求仍需满足 |

幂等应约束业务副作用：同一逻辑操作重放时，外部效果保持在约定范围。模型生成内容可能变化，因此需要把候选输出与获准执行的动作分别管理。

恢复过程应先读取结构化状态，再核对未确认的外部操作，随后重新检查权限、审批与业务前置条件，最后恢复执行上下文。只有满足恢复条件的步骤才能继续。

配置回退与业务补偿也需要分别处理。恢复旧版模型、提示词或策略，只会改变后续执行；已经完成的业务变更仍需通过受控操作处理。

## 六、让知识与经验形成可治理的反馈

认知积累需要把运行记录转化为可验证、可维护的资产。信息是否值得长期保留，取决于来源可靠性、适用范围、有效时间和后续验证结果。

![知识与经验反馈架构：执行轨迹和人工反馈进入候选提炼，经过证据与权限检查、回归评估、版本化发布，形成知识、规则和能力资产；运行时按权限与版本加载，结果再次进入反馈。](/images/enterprise-agent-runtime/feedback.svg)

图 3：知识与经验反馈闭环。运行产生候选经验，治理流程决定哪些内容可以成为共享资产。

| 信息类型 | 核心用途 | 管理要求 |
| --- | --- | --- |
| 权威业务事实 | 支撑当前状态判断 | 保留来源、版本与时间，使用前检查有效性 |
| 业务知识与规则 | 解释对象、约束和处理依据 | 明确维护责任、生效范围与冲突处理方式 |
| 任务状态 | 协调执行与恢复进度 | 随状态迁移更新，保证读取与更新的一致性 |
| 长期记忆与偏好 | 延续主体相关的信息 | 明确归属、访问权限、保留期限及删除机制 |
| 候选经验与标准能力 | 改进后续执行 | 证据校验、评估、审核与版本发布后复用 |

反馈流程可以组织为“采集—提炼—校验—评估—发布—观察”。提炼后的内容应保留证据引用，并明确哪些条件下有效、哪些情况下需要重新核对。

共享资产还应支持失效、撤回和回退。事实变化、规则调整或评估退化后，系统能够停止加载受影响版本，并追踪哪些任务曾使用相关内容。

持续进化的效果需要通过任务结果验证。知识数量、记忆规模与调用次数可以用于运行分析，质量是否改善仍要看成功率、错误复发、人工介入和资源消耗的变化。

## 七、按职责拆分部署与建设路径

六项公共能力可以按控制、执行、状态三个部分组织部署。三者共享契约，同时保留明确的扩展和故障隔离边界。

| 部分 | 主要职责 | 部署关注点 |
| --- | --- | --- |
| 控制部分 | 身份策略、能力注册、版本发布、配额与调度决策 | 高可用、配置一致性、变更审计与隔离边界 |
| 执行部分 | 任务运行、模型调用、工具执行与结果核验 | 多副本、资源隔离、弹性扩展与受控出站访问 |
| 状态部分 | 任务进度、动作记录、知识索引与审计证据 | 一致性、备份恢复、访问控制与数据生命周期 |

控制服务暂时不可用时，需要预先定义哪些动作可以在有效策略与授权范围内继续，哪些必须暂停。授权状态无法确认的动作应停止执行，并记录原因。

建设顺序可以沿能力依赖逐步推进：

1. **建立运行契约。** 明确任务、动作、身份、授权、完成标准和审计标识，使不同组件能够准确交换执行含义。
2. **打通受控执行。** 接入必要的数据与工具，让权限检查、审批、回执和核验覆盖完整调用链。
3. **补齐可靠性机制。** 建立状态持久化、未知结果核对、恢复、补偿与资源预算控制。
4. **扩展公共治理。** 完善租户隔离、能力注册、版本管理、统一观测和容量管理。
5. **形成反馈机制。** 将运行结果纳入评估，把经过验证的改进发布为共享知识或标准能力。

每个阶段都应有可验收的任务结果和运维责任。已有身份平台、数据平台、工作流与监控系统可以继续复用，新增能力通过明确接口接入。

## 八、用可验证的结果验收底座

参考文章从接入、约束、积累和恢复四个方向提出验收要求。[1] 在工程实施中，可以把这些要求转化为证据和统计口径。

| 验收维度 | 核心问题 | 需要提供的证据 |
| --- | --- | --- |
| 接入完整性 | 身份、查询、执行与异步反馈是否贯通 | 能力契约、授权记录、调用回执与结果核验记录 |
| 约束有效性 | 未授权动作能否在产生副作用前被阻断 | 策略判断、审批绑定、执行拦截和审计关联记录 |
| 认知可维护性 | 共享信息是否可信、可更新、可撤回 | 来源、适用范围、版本、评估与发布记录 |
| 运行可恢复性 | 中断和依赖故障后能否有序接续或退出 | 状态恢复、未知结果核对、补偿与移交记录 |
| 交付质量 | 任务是否满足预先约定的完成标准 | 权威状态检查、质量评价与最终验收结果 |
| 运行经济性 | 成功交付所需资源是否可控 | 模型、工具、基础设施及人工介入成本 |

指标需要固定任务范围、时间窗口和失败处理规则。端到端成功率以达到完成标准的任务为分子；自主完成率需说明正常审批与人工接管的统计方式；单位成功任务成本应包含失败尝试消耗，成功任务数为零时单独报告。

权限验证应同时观察未授权操作的拦截率与合法操作的误拦截率。恢复验证应覆盖状态丢失、重复事件、依赖中断和外部结果未确认等故障条件，并检查是否出现重复副作用。

验收责任也需要落实到人：业务负责人维护目标与完成标准，平台负责人维护运行规则和恢复机制，系统负责人维护接口契约与权威状态，知识负责人维护共享资产的有效性。

## 结语

企业级 Agent OS 的价值，在于让智能体执行始终处于可管理的系统关系之中：目标有约定，能力有入口，动作有授权，过程有状态，结果有核验，经验有治理。

围绕这组要求，运行框架、调度管理、数据基座、生态链接、安全管理与持续进化形成共同的运行底座。业务应用据此表达目标与规则，模型能力据此参与规划和行动，企业则获得可持续维护的执行体系。
