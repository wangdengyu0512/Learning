# 多 Agent 怎样工作：从 Workflow 到数字团队的八种 Work Mode

> 多 Agent 的关键不是系统里有多少个模型，而是任务如何流动、控制权如何转移、状态由谁维护，以及系统凭什么判断工作已经完成。

假设线上支付接口突然出现大量超时。一个 Agent 可以读取告警、查询日志、检查最近发布、分析数据库、搜索历史事故、提出修复方案并执行测试。但把所有事情塞进一个上下文，会很快遇到三个问题：信息越来越杂，调查无法真正并行，读取日志、修改代码和执行发布也很难使用同一套权限。

另一种设计是建立一个故障处理团队：协调 Agent 负责制定计划，日志 Agent、代码 Agent 和数据库 Agent 并行调查，修复 Agent 根据证据生成补丁，评审 Agent 检查风险，测试 Agent 验证结果，最后由人类批准发布。

这并不意味着第二种设计天然更好。它增加了模型调用、消息传递、状态合并和故障恢复的复杂度。如果任务只需要固定的三步处理，普通 Workflow 往往更可靠；如果一个 Agent 加几个工具就能完成，引入多个 Agent 反而是在为组织结构付费。

因此，设计多 Agent 系统时，首先不应该问“需要几个 Agent”，而应该问：**这个任务需要什么工作模式？**

本文把 Work Mode 定义为五件事的组合：

```text
Work Mode
  = 任务依赖关系
  + 控制权归属
  + 通信方式
  + 状态所有权
  + 终止机制
```

接下来将沿着这五个维度，拆解八种常见模式，并说明它们何时有效、为什么失败，以及如何组合成一套可治理的生产系统。文中框架与产品能力依据截至 **2026 年 10 月 16 日**的公开官方资料整理。

## 一、先区分 Workflow、Agent 与 Multi-Agent

多 Agent 最容易被误解的地方，是把“调用了多个模型”当成“存在多个 Agent”。

### 1. Workflow：路径主要由代码决定

一个固定工作流可以包含多个模型节点：

```text
提取需求 → 生成大纲 → 撰写正文 → 检查格式
```

如果节点、顺序和分支都是开发者预先定义的，模型只负责完成当前步骤，那么它仍然更接近 Workflow。它可以并行，可以循环，也可以在不同节点使用不同模型，但控制权主要在代码里。

Google Agent Development Kit 将 `SequentialAgent`、`ParallelAgent` 和 `LoopAgent` 归为 Workflow Agents。这类组件按照预定义逻辑控制执行顺序，本身不依赖 LLM 动态决定控制流。

### 2. Agent：路径可以由模型在运行时决定

Agent 不只是一次模型调用。它通常拥有目标、指令、工具、状态和一个执行循环：

```text
观察当前状态
    ↓
判断下一步行动
    ↓
调用工具或其他 Agent
    ↓
读取执行结果
    ↓
继续、修正、交接或结束
```

当模型能够根据中间结果决定下一步查什么、调用哪个工具、是否需要追问或何时停止时，系统才开始具有 Agent 特征。

### 3. Multi-Agent：多个自治边界共同完成目标

多 Agent 系统至少包含两个相对独立的执行单元。它们通常具有不同的职责、上下文、工具、权限或生命周期，并通过消息、共享状态或任务协议协作。

这里的“独立”不是必须使用不同模型，也不是必须部署成不同服务。真正重要的是边界：

- 谁负责什么结果；
- 谁能看到哪些信息；
- 谁能使用哪些工具；
- 谁能把任务交给谁；
- 谁承担最终输出责任。

因此，“并行调用三个提示词”不一定是多 Agent；而一个进程里的三个执行单元，只要拥有清晰的职责、状态和控制权边界，也可以构成多 Agent 系统。

## 二、判断 Work Mode 的五个维度

模式名称只是标签。真正决定系统行为的，是下面五个维度。

### 1. 任务依赖：顺序、并行还是动态生成

先画任务依赖图，而不是先画 Agent 组织图。

- 如果任务 B 必须使用任务 A 的结果，二者是顺序依赖。
- 如果 A、B、C 可以独立完成，它们适合并行执行。
- 如果只有完成 A 后才知道是否需要 B 和 C，任务图需要动态扩展。
- 如果多个角色要围绕同一份状态持续协商，任务图可能是循环或事件驱动的。

很多失败的多 Agent 项目，根源不是模型能力不够，而是把强依赖任务错误地拆成并行，把固定流程错误地包装成自治团队。

### 2. 控制权：谁决定下一步

控制权通常有四种位置：

- **代码控制**：状态机、DAG 或规则引擎选择下一个节点。
- **中央控制**：Manager 或 Orchestrator 分解任务并调度 Worker。
- **局部转移**：当前 Agent 通过 Handoff 把控制权交给另一个 Agent。
- **分布式控制**：多个 Agent 根据共享状态、事件或发言规则自行协调。

控制越集中，系统越容易审计；控制越分散，局部自治和扩展性越强，但全局行为越难预测。

### 3. 通信：传对话还是传任务

Agent 之间可以传递完整历史、摘要、结构化任务单、工具结果或共享状态引用。不同方式的成本和风险完全不同。

直接转发完整对话最容易实现，却会导致上下文膨胀和敏感信息扩散。生产系统通常更适合传递经过裁剪的任务包：目标、约束、已有证据、未解决问题和期望输出格式。

### 4. 状态：谁拥有事实，谁能修改

状态至少分为三层：

- **会话状态**：用户说过什么，当前活动 Agent 是谁。
- **任务状态**：子任务、依赖、进度、重试次数和预算。
- **业务状态**：数据库记录、代码变更、订单、审批或发布状态。

模型上下文不是可靠的状态数据库。关键状态应由应用维护，Agent 只读取执行当前任务所需的视图。涉及并行写入时，还必须定义 reducer、锁、版本号或冲突合并规则。

### 5. 终止：什么叫做完成

“Agent 觉得完成了”通常不是足够可靠的终止条件。可用的终止信号包括：

- 固定步骤已经执行完；
- 结构化输出通过 Schema 校验；
- 测试、查询或规则检查达到阈值；
- 评审者明确接受结果；
- 达到最大轮次、时间或费用预算；
- 任务升级给人类并进入等待状态。

如果没有终止协议，任何带循环、交接或讨论能力的架构都可能变成一台持续消耗 Token 的机器。

## 三、模式一：Sequential Pipeline，顺序流水线

顺序流水线是最简单的工作模式：前一个节点的输出成为后一个节点的输入。

```text
需求分析 Agent
      ↓
方案设计 Agent
      ↓
实现 Agent
      ↓
测试 Agent
```

### 它怎样工作

控制权通常在代码或 Workflow 引擎中。每个 Agent 只负责一个阶段，不决定全局路径。上游输出通过结构化接口交给下游，最后一个节点生成最终结果。

这种设计适用于阶段稳定、顺序明确的任务，例如文档生产、数据处理、合同审查或代码生成流水线。它的最大优势是可预测：执行到哪里、为什么失败、应该从哪里重试，都比较清楚。

### 它为什么会失败

流水线会放大上游错误。如果需求分析 Agent 漏掉一个约束，后面的设计、实现和测试可能都建立在错误前提上。另一个常见问题是损失信息：上游用自然语言概括结果时，下游真正需要的证据、置信度或异常项可能已经丢失。

因此，流水线节点之间不应该只传一段“看起来完整”的文字，而应传递稳定字段，例如：

```json
{
  "conclusion": "连接池耗尽导致请求排队",
  "evidence": ["trace-182", "metric-db-pool-usage"],
  "confidence": 0.86,
  "open_questions": ["为什么发布后连接未释放"],
  "status": "needs_verification"
}
```

### 终止条件

最后一个节点完成并通过验收，或者任一关键节点进入明确的失败、拒绝或人工接管状态。

## 四、模式二：Parallel Fan-out/Fan-in，并行分发与汇总

当多个子任务互不依赖时，可以从一个协调节点向外分发，再统一汇总。

```text
                    ┌→ 日志调查 Agent ───┐
故障目标 → 任务拆分 ├→ 代码变更 Agent ───┼→ 证据汇总
                    └→ 数据库 Agent ─────┘
```

### 它怎样工作

Fan-out 阶段为每个 Worker 生成边界清晰的任务，Worker 在独立上下文中并行执行。Fan-in 阶段并不是简单拼接文本，而是完成去重、冲突识别、证据排序和结论合并。

Anthropic 在多 Agent Research System 的工程复盘中描述了类似结构：Lead Agent 根据问题启动多个 Subagent 并行探索，再综合结果。它适合搜索空间大、不同方向可以独立调查、且覆盖面比单条推理深度更重要的任务。

### 它为什么会失败

第一类问题是假并行。两个任务表面不同，实际上都依赖同一个未完成前提，结果只能重复等待或产生矛盾假设。

第二类问题是写冲突。多个 Agent 可以并行读日志，却不应该在没有隔离机制时同时修改同一个文件、工单或数据库记录。

第三类问题是汇总失真。汇总 Agent 可能为了生成流畅结论而抹掉不一致意见。正确做法是保留 `evidence`、`confidence`、`conflicts` 和 `unknowns`，把分歧作为状态处理，而不是作为文风问题处理。

### 终止条件

所有必需分支完成，或部分分支达到超时后按照降级规则汇总。系统应提前定义最小可接受结果，而不是无限等待最慢的 Worker。

## 五、模式三：Router + Specialists，路由与专家

Router 读取请求并选择最适合的专家。它通常只负责分类和转发，不持续管理任务。

```text
用户请求 → Router
              ├→ 账户 Agent
              ├→ 退款 Agent
              ├→ 技术支持 Agent
              └→ 人工服务
```

### 它怎样工作

Router 可以使用规则、轻量分类模型或 LLM。它的输出最好不是自由文本，而是受约束的路由决策：目标 Agent、置信度、路由原因和是否需要人工确认。

这种模式适合意图边界相对稳定、不同专家拥有明显不同工具或知识的系统，例如企业服务台、客服中心和多产品助手。

### Router 与 Manager 的区别

Router 通常做一次选择，专家接手后独立完成任务。Manager 则持续拥有全局目标，可以连续调用多个 Worker、比较结果并决定下一步。

如果一个请求同时涉及账单解释、退款审批和账户权限，单次路由往往不够。此时应该由 Manager 编排多个子任务，或者先路由到一个领域 Manager。

### 它为什么会失败

- 专家能力描述模糊，Router 无法区分；
- 请求本身跨越多个领域，却被强制单选；
- 低置信度仍然自动执行高风险操作；
- 新增专家后没有回归测试旧路由边界；
- Router 只依据关键词，没有读取真正影响决策的上下文。

### 终止条件

专家返回最终结果，或者返回 `cannot_handle`、`needs_clarification`、`needs_human` 等显式状态，由上层流程继续处理。

## 六、模式四：Manager + Workers，主管与执行者

Manager 始终面对用户并保留控制权，Worker 作为专业工具被调用。

```text
用户 ↔ Manager
        ├→ 检索 Worker
        ├→ 数据分析 Worker
        └→ 写作 Worker
```

OpenAI 官方的多 Agent 编排指南把这种方式描述为 Manager pattern：中央 Agent 通过工具调用专业 Agent，并负责统一生成最终答案。它与 Handoff 的核心差别，是对话控制权有没有转移。

### 它怎样工作

Manager 负责理解目标、拆分任务、选择 Worker、维护进度和综合结果。Worker 不直接面向用户，只返回当前子任务的结果。对于需要统一语气、统一政策和集中 Guardrail 的系统，这种结构很实用。

Manager 最重要的能力不是“比 Worker 更聪明”，而是维护全局约束：哪些任务已经完成、哪些证据相互冲突、预算还剩多少、什么时候必须停止。

### 它为什么会失败

Manager 很容易成为认知和性能瓶颈。如果所有原始日志、搜索页面和 Worker 思考过程都回流到中央上下文，系统最终仍会退化成一个超载的单 Agent。

更好的做法是让 Worker 返回压缩后的结构化结果，把大对象放在外部存储，只在消息中传引用。Manager 应维护任务账本，而不是背诵全部工作过程。

另一个风险是过度委派。Manager 可能为一个简单问题创建多个 Worker，导致成本高于直接回答。需要用策略约束何时允许委派、并行数上限和单任务预算。

### 终止条件

Manager 根据验收标准决定完成，也可以由代码在预算耗尽、任务失败或人工审批时强制终止。

## 七、模式五：Dynamic Orchestrator-Worker，动态编排

固定 Manager 通常面对已知类型的 Worker；动态 Orchestrator 则会根据中间结果创建新的任务，并不断调整计划。

```text
目标
 ↓
生成初始计划
 ↓
创建并分配子任务
 ↓
读取新证据与进度
 ↓
修改计划、追加任务或停止
```

Anthropic 将这一类结构称为 Orchestrator-Workers：中央 LLM 动态拆分任务，把子任务交给 Worker，再综合结果。Microsoft Agent Framework 的 Magentic orchestration 也采用专门的 Manager 维护共享上下文、管理进度并动态选择下一位参与者。

### 它适合什么任务

- 深度研究，事先不知道需要调查多少方向；
- 复杂故障，证据会不断改变调查路径；
- 大型代码迁移，子任务取决于扫描结果；
- 数据分析，后续步骤取决于异常模式；
- 需要动态寻找外部专家的跨系统任务。

### 它为什么会失败

动态规划最大的风险不是某一步答错，而是任务树失控：重复创建近似任务、不断追逐边缘问题、发现新信息后忘记原始目标，或者 Worker 数量随着深度指数增长。

Orchestrator 必须维护一个显式任务账本：

```text
task_id
parent_task_id
objective
owner
dependencies
status
attempts
budget
acceptance_criteria
evidence_refs
```

创建新任务前，应进行去重和价值判断；继续探索前，应估算新增信息价值是否值得成本。规划可以由模型提出，但并发上限、总预算、权限和超时应该由代码强制执行。

### 终止条件

所有关键问题达到验收标准，或者剩余不确定性已低于业务阈值。若达到预算仍无法收敛，应输出当前证据、未解决问题和建议的人工行动，而不是伪造确定答案。

## 八、模式六：Handoff，控制权交接

Handoff 不是“向专家问一个问题”，而是把当前任务或会话的主导权交给另一个 Agent。

```text
用户 → 分诊 Agent → 退款 Agent ↔ 用户
                    ↓
                 风控 Agent
```

OpenAI 官方文档将 Handoff 与 Manager pattern 并列：Manager pattern 中中央 Agent 保留控制权；Handoff 中专业 Agent 接管执行，并成为当前活动 Agent。

### 它怎样工作

交接通常包含两个部分：

1. 控制状态发生变化，例如 `active_agent` 从分诊 Agent 变为退款 Agent。
2. 新 Agent 获得完成任务所需的上下文，但不一定获得全部历史。

好的交接消息应该说明：

- 为什么交接；
- 当前目标是什么；
- 已经完成了什么；
- 还有哪些问题；
- 哪些证据可信；
- 新 Agent 可以执行哪些动作；
- 完成后应该返回、继续交接还是直接结束。

### 它为什么会失败

最典型的故障是踢皮球：Agent A 认为任务属于 B，B 又认为缺少条件应该交还 A。另一种问题是上下文泄露，系统把完整历史连同不必要的个人信息和内部数据一起转交。

因此需要维护 Handoff 图和次数限制，禁止未定义的环路；交接前执行上下文过滤；高风险交接要求结构化理由和策略检查。

### 终止条件

当前活动 Agent 完成目标，或者交接到人工角色。系统还应区分“任务完成”和“等待外部输入”，避免把等待审批误判为成功。

## 九、模式七：Generator-Critic-Judge，生成、评审与裁决

这类模式通过角色分离建立质量闭环：Generator 负责提出结果，Critic 根据标准发现问题，Judge 或确定性验证器决定是否接受。

```text
Generator → Critic → 修订
     ↑          ↓
     └── 未通过 ┘

通过 → Judge / Tests → 输出
```

### 它怎样工作

Critic 不应该只收到一句“请检查质量”，而应拿到具体 Rubric，例如事实是否有证据、代码是否通过测试、方案是否覆盖性能和安全约束。能够用程序验证的内容，应优先交给测试、Schema、静态分析或业务规则，而不是再调用一个模型表达意见。

Judge 也不一定是第三个 Agent。它可以是测试套件、评分模型、规则引擎、人类审批者，或者这些机制的组合。

### 它为什么会失败

- Generator 和 Critic 使用相同信息，产生相关性错误；
- Critic 擅长挑语言问题，却无法验证事实；
- 每轮反馈都引入新要求，循环无法收敛；
- Judge 只看最终文字，不检查证据和执行结果；
- 多数投票被错误地当成事实证明。

独立意见只有在信息源、方法、模型或工具确实存在差异时才有价值。让三个同模型、同提示词、同上下文的 Agent 投票，常常只是把同一种偏差复制三次。

### 终止条件

达到明确分数阈值、确定性检查通过或最大修订轮次耗尽。达到轮次上限但仍不合格时，状态应该是失败或人工复核，而不是强制发布“最后一版”。

## 十、模式八：Group Chat、Swarm 与 Blackboard

前面的模式都能清楚指出当前控制者。群体协作模式则让多个 Agent 围绕共享会话或共享工作区持续协作。

```text
              共享任务空间
        ┌────────┼────────┐
        ↓        ↓        ↓
   产品 Agent  架构 Agent  测试 Agent
        ↑        ↓        ↑
        └──── 状态与消息 ────┘
```

这不是单一实现，而是一组相关形式：

- **Group Chat**：多个 Agent 读取同一段对话，由规则或 Manager 选择下一位发言者。
- **Swarm**：Agent 根据局部判断把工作交给其他 Agent，控制权沿网络流动。
- **Blackboard**：Agent 不必直接对话，而是在共享任务板上发布事实、假设、问题和候选方案。

### 它适合什么任务

当问题需要多轮协商、角色之间会相互影响，而且无法提前确定严格顺序时，共享协作空间很有价值。例如架构评审、跨专业诊断、复杂计划制定和仿真推演。

### 它为什么会失败

共享会话会快速膨胀，Agent 容易重复观点、迎合群体结论或失去自己的专业边界。没有强约束的群聊还会把“讨论活跃”误认为“任务推进”。

Blackboard 通常比完整群聊更容易治理，因为它迫使参与者写入结构化对象，例如：

```text
Fact       已验证事实
Hypothesis 待验证假设
Question   未解决问题
Proposal   候选方案
Decision   已确认决策
Action     待执行动作
```

不同类型拥有不同修改权限和生命周期，系统也能更容易检测冲突、重复和停滞。

### 终止条件

决策规则必须独立于“大家不再发言”。可以使用任务板清空、关键问题关闭、主席 Agent 裁决、投票达到阈值或人类确认。无论采用哪种方式，都必须设置最大轮次和无进展检测。

## 十一、八种模式放在一起比较

| Work Mode | 控制权 | 任务关系 | 上下文方式 | 最适合 | 主要风险 |
| --- | --- | --- | --- | --- | --- |
| Sequential Pipeline | 代码或固定流程 | 强顺序依赖 | 阶段间传递 | 稳定业务流程 | 上游错误传播 |
| Parallel Fan-out/Fan-in | 协调器 | 独立子任务 | Worker 隔离 | 检索、分析、调查 | 冲突与汇总失真 |
| Router + Specialists | Router 后转移 | 单路径为主 | 专家独立 | 分类与服务分流 | 路由错误 |
| Manager + Workers | 中央 Manager | 可组合子任务 | 中央摘要 | 统一入口与综合 | Manager 过载 |
| Dynamic Orchestrator | 动态规划器 | 运行时生成 | 任务级隔离 | 开放式复杂任务 | 任务树失控 |
| Handoff | 当前 Agent 转移 | 阶段式接管 | 裁剪后传递 | 专家接手长对话 | 循环与信息泄露 |
| Generator-Critic-Judge | 评审者或验证器 | 反馈循环 | 结果与证据 | 质量门禁 | 无限修订、伪验证 |
| Group Chat/Swarm/Blackboard | 共享或分布式 | 动态协作 | 共享空间 | 多方协商 | 噪声、从众、难终止 |

这张表不是让系统八选一。真实应用通常是组合：代码控制外层 Workflow，Manager 在局部动态委派，独立任务并行执行，高风险阶段使用 Handoff 和人工审批，输出再经过评审循环。

## 十二、一个完整案例：软件故障排查与修复团队

回到开头的支付超时事件。目标不是让一群 Agent 自由讨论，而是在 30 分钟内定位原因、提出可验证修复，并禁止未经批准的生产变更。

### 1. 外层使用确定性 Workflow

```text
告警接入
  ↓
事件分类
  ↓
调查与诊断
  ↓
修复与验证
  ↓
人工审批
  ↓
发布、监控或回滚
```

事件状态、审批和发布流程由代码控制。即使模型输出异常，也不能跳过人工审批直接修改生产环境。

### 2. Router 完成事件分流

Router 根据服务、错误类型、影响范围和告警等级，把事件路由到支付领域的 Incident Manager。如果置信度过低，或者同时涉及安全与资金风险，则并行通知人工值班人员。

### 3. Manager 建立调查计划

Incident Manager 创建三个初始任务：

- 日志 Agent：分析错误日志和分布式 Trace；
- 变更 Agent：检查最近代码、配置和依赖变更；
- 数据库 Agent：检查连接池、慢查询和锁等待。

这些任务没有写权限，可以安全并行。

### 4. Fan-out/Fan-in 汇总证据

三个 Agent 返回结构化报告。Manager 不只读取结论，还检查证据引用、时间范围、置信度和冲突。

假设日志 Agent 发现超时集中在数据库调用，变更 Agent 发现当天修改了连接释放逻辑，数据库 Agent 发现连接池持续达到上限。三条证据相互支持，Manager 将“连接泄露”提升为高置信度根因假设。

### 5. 动态追加验证任务

Manager 创建一个新的 Reproduction Agent，在隔离环境中复现连接未释放问题。这个任务不是预先固定的，而是由调查结果触发，属于动态 Orchestrator-Worker 行为。

### 6. Handoff 给修复 Agent

根因通过复现后，控制权交给 Fix Agent。交接包只包含相关代码、复现步骤、证据引用、修改权限范围和验收标准，不传递全部日志上下文。

### 7. Generator-Critic-Judge 完成质量门禁

Fix Agent 生成补丁后：

- Review Agent 检查资源释放、异常路径和回归风险；
- Test Agent 执行单元测试、集成测试和压力测试；
- 确定性策略检查变更范围是否越权；
- 未通过则返回修订，最多两轮。

### 8. 人类批准真实副作用

即使所有检查通过，生产发布仍需要值班工程师批准。发布系统拥有部署权限，调查和修复 Agent 没有。部署后，监控规则根据错误率、延迟和连接池指标决定继续观察或自动回滚。

这个案例展示了一个重要原则：**多 Agent 不应该替代 Workflow，而应该被嵌入受约束的 Workflow。**确定性的外壳负责权限、预算和状态，一小部分真正需要判断的节点再交给 Agent。

## 十三、通信契约：不要让 Agent 只靠聊天协作

Agent 之间最脆弱的接口，是一段没有 Schema 的自然语言。它既难校验，也难区分事实、猜测和建议。

可以为委派定义统一任务信封：

```json
{
  "task_id": "INC-1024-T3",
  "objective": "验证连接泄露是否由最近发布引入",
  "inputs": ["commit:8f31a2", "trace:payment-timeout-182"],
  "constraints": {
    "read_only": true,
    "deadline_seconds": 180,
    "max_tool_calls": 12
  },
  "acceptance_criteria": [
    "指出具体代码路径",
    "提供可复现证据",
    "区分事实与假设"
  ],
  "return_schema": {
    "status": "completed|blocked|failed",
    "findings": [],
    "evidence": [],
    "uncertainties": [],
    "recommended_next_actions": []
  }
}
```

至少要在协议中表达五类内容：目标、输入、约束、验收标准和返回 Schema。涉及交接时，再增加交接原因、当前活动角色和下一步责任。

事实也应该带来源和状态。`数据库连接池已满`、`可能存在连接泄露`、`建议回滚`分别是事实、假设和行动建议，不能被压缩成一句没有边界的总结。

## 十四、生产治理：把自治关进工程边界

### 1. 预算不是提示词，而是运行时约束

应该在代码层限制：

- 最大 Agent 数量；
- 最大并行度；
- 每个任务的模型调用和工具调用次数；
- 最大 Handoff 次数；
- 最大评审轮次；
- 总 Token、费用和执行时间。

提示词里的“请控制成本”不能代替计数器、超时和熔断器。

### 2. 权限跟随角色，而不是跟随模型

同一个模型可以扮演不同 Agent，但每个角色必须获得独立的工具白名单和凭证。调查 Agent 只读，修复 Agent 只能修改隔离分支，发布 Agent 才能触发部署，高风险动作必须经过审批。

这既减少误操作，也防止提示注入沿 Agent 链路扩大权限。

### 3. 并行写入必须有冲突策略

如果多个 Agent 修改同一对象，需要使用分支、乐观锁、版本号、事务或专门的合并 Agent。最简单的策略通常是“并行读、串行写”：调查可以并行，产生真实副作用的动作集中执行。

### 4. Trace 要能够还原因果链

一次运行至少应回答：

- 谁创建了这个任务；
- 为什么选择这个 Agent；
- Agent 看到了哪些输入；
- 调用了哪些工具；
- 哪个结果触发了下一步；
- 发生过哪些重试、交接和失败；
- 每条分支消耗多少时间和费用；
- 最终结论依赖哪些证据。

OpenAI Agents SDK 的 tracing 将 Agent 运行、模型生成、工具调用、Handoff 和 Guardrail 等事件组织到 Trace 与 Span 中。无论使用哪个框架，生产系统都应该具备同等粒度的可观测性。

### 5. Eval 必须评估协作过程

只判断最终答案“看起来是否正确”不够。多 Agent 评测至少需要覆盖：

- Router 的路由准确率；
- 子任务拆分的完整性和重复率；
- Worker 的任务完成率；
- Handoff 的成功率和循环率；
- 汇总结果对原始证据的忠实度；
- 评审循环的收敛率；
- 端到端成功率、延迟和成本；
- 人工接管率与越权操作率。

最重要的基线不是另一个多 Agent 方案，而是单 Agent 和固定 Workflow。只有在同一任务集上确实提升成功率、覆盖面或处理速度，新增复杂度才有工程价值。

## 十五、如何选择：从最简单的结构开始

可以按照下面的顺序判断。

### 第一步：流程能否预先写清楚

如果步骤和分支基本固定，优先使用代码 Workflow。模型负责节点内部的语义任务，不负责随意改变业务流程。

### 第二步：一个 Agent 是否已经足够

如果工具数量少、上下文可控、任务无法并行，也不需要权限隔离，单 Agent 往往是更好的起点。

### 第三步：寻找引入多 Agent 的真实收益

只有出现下面至少一种需求时，才值得继续拆分：

- 独立子任务可以并行；
- 不同工作需要不同上下文；
- 工具和权限必须隔离；
- 单个上下文无法容纳探索过程；
- 需要独立验证或利益分离；
- 不同团队或系统拥有独立生命周期。

### 第四步：选择最小可用模式

- 固定阶段依赖：Sequential Pipeline；
- 独立子任务：Parallel Fan-out/Fan-in；
- 单一领域分流：Router + Specialists；
- 统一入口、多个专家：Manager + Workers；
- 路径事先未知：Dynamic Orchestrator-Worker；
- 专家需要接管：Handoff；
- 结果需要反复验证：Generator-Critic-Judge；
- 多方持续协商：Group Chat 或 Blackboard。

### 第五步：最后才组合模式

不要一开始就建设包含路由、群聊、动态生成 Worker 和多层评审的复杂系统。先让最小模式在真实任务上可测量地工作，再根据失败证据增加新的协调机制。

## 十六、常见反模式

### 1. 用角色名称代替能力边界

三个 Agent 使用相同模型、相同工具、相同上下文和相同目标，只改角色名称，不会自然产生专业分工。

### 2. 所有 Agent 共享全部上下文

这会失去上下文隔离的主要收益，还可能扩大隐私和提示注入风险。

### 3. 让 Agent 用自由文本分配任务

如果任务没有 ID、状态、验收条件和预算，系统很难去重、重试、审计和终止。

### 4. 多个 Agent 同时写同一资源

并行适合探索，不天然适合副作用。没有并发控制的多 Agent 写操作，本质上是分布式竞态。

### 5. Manager 既执行又评审自己

如果同一个上下文负责提出方案、验证证据和裁决结果，角色分离只是表面结构。

### 6. 把投票当成正确性证明

多个 Agent 的一致意见可能来自同一种模型偏差。事实验证需要独立数据、工具和可执行检查。

### 7. 没有退出机制

任何循环、Handoff、动态委派和群聊模式，都必须定义最大轮次、无进展检测、预算耗尽和人工接管。

### 8. 没有与简单基线比较

如果单 Agent 加工具就能达到相同结果，多 Agent 只是在增加延迟、成本和故障面。

## 十七、上线前检查清单

### 任务与模式

- [ ] 任务是否存在清晰、可独立验收的子任务？
- [ ] 是否区分了固定 Workflow 与模型自主决策？
- [ ] 所选 Work Mode 是否对应真实的任务依赖？
- [ ] 多 Agent 是否比单 Agent 基线带来可测量收益？

### 控制与状态

- [ ] 是否明确谁拥有当前控制权？
- [ ] 是否明确谁维护会话、任务和业务状态？
- [ ] 并行写入是否有版本和冲突合并策略？
- [ ] Handoff 是否有允许路径和次数上限？

### 通信与证据

- [ ] Agent 之间是否使用结构化任务协议？
- [ ] 是否区分事实、假设、建议和未知项？
- [ ] 关键结论是否携带来源和证据引用？
- [ ] 上下文是否遵循最小必要原则？

### 安全与终止

- [ ] 每个角色是否拥有最小工具权限？
- [ ] 真实副作用是否具备幂等、审批和回滚机制？
- [ ] 是否设置调用、时间、费用和并行度预算？
- [ ] 是否定义成功、失败、阻塞和人工接管状态？

### 观测与评测

- [ ] Trace 是否能还原完整委派和因果链？
- [ ] 是否记录每个 Agent 的延迟、成本和失败原因？
- [ ] 是否分别评估路由、交接、汇总和端到端结果？
- [ ] 是否能识别重复任务、循环委派和无进展讨论？

## 结语：先设计组织，再增加 Agent

多 Agent 看起来像模型能力问题，真正落地时却更接近工作流设计、组织设计和分布式系统设计。

Sequential Pipeline 解决阶段依赖，Parallel Fan-out/Fan-in 解决并行探索，Router 解决分流，Manager 解决集中协调，Dynamic Orchestrator 解决未知路径，Handoff 解决责任转移，Generator-Critic-Judge 解决质量闭环，Group Chat 与 Blackboard 解决多方协商。每种模式都对应一种具体的任务结构，也带来一种新的失败方式。

成熟的系统不会追求让 Agent 获得无限自治，而是把不确定性放在真正需要判断的位置：外层用代码守住状态、权限、预算和终止条件，内层让 Agent 处理语义理解、动态规划和开放式探索。

最终需要回答的不是“系统里有几个 Agent”，而是：

> 每个 Agent 为什么存在，它拥有什么责任和权限，它如何证明工作已经完成，以及当它犯错时，系统如何阻止错误继续传播？

能清楚回答这些问题，多 Agent 才从一场模型群聊，变成一支可以工作的数字团队。
