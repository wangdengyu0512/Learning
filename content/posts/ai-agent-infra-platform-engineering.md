一个采购助手已经能够理解需求、查询库存、比较供应商，并在获得授权后创建采购申请。演示时，整个过程只需要几分钟；投入生产之后，问题变得具体起来：执行一半时 Worker 重启，任务从哪里继续？供应商接口已经创建了申请，但响应超时，重试是否会重复下单？新版本上线时，等待人工审批的旧任务应该由谁接手？模型供应商限流之后，增加 Pod 能否改善吞吐？

这些问题决定了 AI Agent 能否成为可靠的业务服务。

Agent Infra 平台的职责，是把计算、网络、存储、交付和运维能力组织成一套稳定的运行环境。业务团队可以在清晰的接口与约束下开发 Agent，平台负责让任务有边界地执行、让变更可验证、让故障可定位、让恢复过程可重复。

本文以企业采购助手为贯穿案例，给出一套可分阶段实施的参考设计。讨论重点是应用与 Agent 运行基础设施；模型训练平台不在范围内，自建模型推理服务仅讨论与容量、路由和故障隔离有关的接口。文中的架构、指标目标与流程属于设计建议，示例数值不代表生产实测结果。

## 一、先定义平台要承诺什么

### 从服务存活走向任务可靠

传统应用的可用性往往从请求成功率开始衡量。采购助手的请求则可能只负责创建任务，真正的执行发生在之后：查询资料、调用模型、执行工具、等待审批，再提交采购申请。

因此，一次 HTTP 202 只能证明入口接受了请求，无法证明采购流程已经完成。平台至少需要分别描述三种结果：

| 层次 | 要回答的问题 | 典型证据 |
| --- | --- | --- |
| 服务可用性 | 请求能否被接受，结果能否被读取 | 接入成功率、读取延迟、流式连接状态 |
| 执行可靠性 | 任务是否在约定时间内到达正确终态 | 任务状态、超时率、恢复成功率、重复副作用数 |
| 业务质量 | 采购建议是否正确，申请是否满足要求 | 规则校验、抽样评测、人工复核、业务验收 |

Infra 直接负责前两层，为第三层提供版本、轨迹和评测接入能力。模型效果与业务规则需要应用团队共同负责，不能把所有质量问题都解释成基础设施故障。

### 明确团队边界与服务等级

平台团队负责集群、应用交付、网关、运行状态、观测和恢复能力；Agent 框架团队负责决策循环、工作流和上下文组织；业务团队负责工具语义、权限规则、结果验收与业务补偿。即使这些职责由同一支团队承担，也应保留接口和责任边界。

每个接入平台的服务都应登记负责人、依赖、服务等级、数据等级、SLO 和应急入口。核心采购提交链路与离线采购报告可以使用不同的保障等级。前者需要优先保障正确提交与结果可核对，后者可以接受较长排队时间。

建设目标也应具有明确口径：发布耗时从哪一刻开始计算，恢复时间是否包含发现故障的时间，任务成功率怎样处理用户取消和人工等待。口径不清晰，平台看板就很难指导工程决策。

## 二、总体架构：把控制、执行与状态分开

建议将平台划分为控制面、执行面和共享状态服务，并以统一交付与观测能力贯穿它们。

![AI Agent Infra 平台参考架构](/blog-assets/agent-infra/platform-architecture.svg)

控制面管理服务目录、环境、发布版本、配置、租户配额和策略。执行面承接请求、调度任务、运行 Agent，并调用模型与工具。状态服务保存任务事实、检查点、结果和必要的业务关联。

这三个部分的故障影响应尽量分离。例如，控制台暂时不可用时，已经获得有效配置的 Worker 应尽可能继续工作；新的高风险授权不能因为控制面不可达而自动放行。哪些配置可以使用最近一次有效版本、哪些操作必须等待实时校验，需要逐项定义。

采购助手的一次执行可以拆成以下步骤：

1. 网关完成身份认证、租户识别、配额检查和请求去重。
2. 任务服务持久化任务及发布版本，返回可查询的任务标识。
3. 调度器将就绪任务交给具有相应能力的 Worker。
4. Worker 加载检查点，调用模型与工具，记录步骤结果。
5. 遇到人工审批时持久化等待状态，释放执行资源。
6. 审批事件触发后续执行，最终写入终态和结果。

这里最重要的约束是：**请求连接的生命周期、Pod 的生命周期和任务的生命周期必须能够独立变化。** 用户关闭页面不一定意味着取消任务，Worker 重启也不应自动丢弃已接受的任务。

对于任务创建与入队之间的一致性，可以在同一数据库事务内写入任务记录和待投递事件，再由投递器发布到队列。投递器可能重复发送，因此消费者仍然需要去重。这样可以把“任务已经接收却永远没有入队”的风险转化为可扫描、可重试、可报警的投递积压。

## 三、Kubernetes 底座：从副本数推导真实可用性

### 可用性取决于故障域与剩余容量

将服务设置为三个副本，只能描述期望数量。三个副本是否落在不同节点、不同可用区，数据库是否位于同一故障域，以及故障后的剩余节点能否承载流量，决定了实际恢复能力。

生产设计应同时考虑应用副本布局、控制平面可用性、网络与存储依赖，以及故障后的资源余量。对核心无状态服务，可以使用跨可用区拓扑分散和节点级反亲和设计；对于有状态服务，还需要验证数据复制与故障切换行为。

假设服务均匀分布在三个可用区，丢失一个可用区后剩余容量约为原来的三分之二。在流量不变且分配均匀的简化模型下，原先 70% 的资源利用率会升至约 105%。部署跨区并不能弥补容量不足。实际预算还要考虑热点、启动延迟、调度约束和外部依赖限额。

### 探针与中断策略需要匹配任务语义

启动探针回答应用是否完成初始化，就绪探针回答实例能否接收新流量，存活探针用于发现进程是否陷入需要重启才能恢复的状态。把模型供应商暂时不可用直接映射成存活探针失败，可能引发大量无效重启。

PodDisruptionBudget 可以限制符合条件的自愿驱逐，但它不阻止硬件故障，也不直接约束 Deployment 或 StatefulSet 自身的滚动更新。滚动更新仍需配置对应工作负载的更新策略。[1]

对执行长任务的 Worker，退出流程需要由应用实现：先停止领取新任务，再等待当前安全步骤完成，提交检查点与任务状态，最后释放任务租约。优雅退出期限只能提供一个时间窗口，无法保证任意长度任务都执行完毕；强制终止之后仍应依赖持久状态恢复。

### 弹性伸缩需要业务信号

网关可以结合请求并发、延迟与 CPU 进行伸缩。异步 Worker 更适合观察就绪队列长度、最老任务等待时间、执行槽位和有效处理速率。等待人工审批的任务不应被计入可执行积压。

如果瓶颈是模型供应商每分钟请求数或 Token 限额，扩容 Worker 可能放大限流。扩缩容决策必须与模型并发限制、数据库连接池和工具服务容量协调，同时设置最大副本数、冷却窗口和租户公平调度。

有状态组件优先选择团队能够可靠运维的方案。是否采用托管数据库、托管队列或自建集群，应依据恢复验证、成本和控制需求决定。应用运行在 Kubernetes 上，并不意味着所有依赖都必须部署在同一个集群。

## 四、Agent 执行基础设施：让恢复具有明确语义

### 用状态机管理任务

采购助手可以采用以下任务状态：

```text
已接受 → 待执行 → 执行中 → 成功 / 失败 / 已取消 / 已超时
                    ↓
              等待审批或外部事件
                    ↓
                  待执行
```

状态迁移需要受控。例如，任务进入成功终态后，不应被迟到的超时事件改写。可以通过条件更新、状态版本号或等价并发控制保证迁移的合法性。

任务记录至少需要包含租户、业务请求标识、任务标识、发布版本、工作流版本、当前步骤、状态版本、截止时间、重试次数、取消标记和检查点位置。执行尝试应具有独立标识，便于区分同一任务的多次恢复。

### 租约保证接管，栅栏机制限制旧执行者

Worker 领取任务时获得有期限的租约，并持续续约。租约过期后，调度器允许其他 Worker 接管。但旧 Worker 可能只是网络暂时中断，仍在执行。

因此，仅有租约还不够。状态写入可以携带单调递增的栅栏令牌，由数据库或接收端拒绝过期执行者的写入。外部工具如果无法校验令牌，则需要业务幂等键、结果查询或专门的工具代理进一步控制风险。

任务恢复的目标应是从已确认的步骤继续。一次模型调用已完成且输出已被接受时，可以持久化该结果，减少恢复时重新采样导致的分支变化。具体保留哪些输入与输出，需要结合数据权限和保留期限决定。

### 检查点解决进度，幂等解决重复副作用

考虑这样的时序：采购系统已经创建申请，Worker 尚未保存成功结果就退出。接管者只能看到“调用结果未知”。如果直接重试，可能重复创建申请；如果直接跳过，又可能漏掉实际未成功的操作。

建议为每个业务动作生成稳定的操作标识，例如由租户、采购业务单号和动作序号组成。同一操作的重试复用该标识，接收方以唯一约束或幂等协议返回原结果。新的合法业务动作必须使用新的标识。

对于不支持幂等的工具，平台先查询业务结果；仍无法确定时，将任务置于待核对状态，转交人工或补偿流程。不要仅凭本地检查点宣称整个跨系统过程具有“恰好执行一次”的保证。

| 故障位置 | 恢复依据 | 处理动作 |
| --- | --- | --- |
| 任务提交前失败 | 请求幂等键 | 客户端重试，返回已有任务或创建任务 |
| 工具执行前失败 | 步骤状态与检查点 | 重新执行该步骤 |
| 工具成功但回执丢失 | 业务幂等键与结果查询 | 核对原操作，避免重复副作用 |
| 状态已提交但消息未确认 | 任务版本与消费去重记录 | 确认已完成状态，结束重复投递 |
| 业务结果无法判定 | 操作记录与外部业务凭据 | 暂停自动重试，进入核对流程 |

### 把工具执行限制在可管理的环境内

对于代码执行、浏览器自动化和文件处理，平台应提供独立执行环境、CPU 与内存限制、执行时限、受控网络出口和临时凭证。隔离强度需要与代码可信度匹配，普通进程或普通容器本身不能自动满足所有不可信代码场景。

权限应绑定调用者、租户、工具与动作，并在执行前验证。模型生成的参数只是一项输入，不能修改平台授权。日志与网页内容同样属于待处理数据，不能成为自动提升权限的依据。

## 五、CI/CD 与 IaC：把环境和发布变成可审查的变更

### 为资源定义清晰的所有者

基础设施即代码首先解决资源来源可追溯的问题。网络、集群、数据库、权限和监控资源应通过版本化模块管理，环境差异通过明确参数表达。

可以让 Terraform 管理云资源与基础依赖，让 Kubernetes 声明式交付工具管理应用对象。关键是同一资源只有一个明确的期望状态管理者，避免 Terraform、GitOps 控制器和人工脚本同时改写同一对象。

IaC 变更流程应包含格式与静态检查、计划预览、风险检查、受控执行和结果核对。计划生成后如果代码、状态或依赖发生变化，应重新验证，不能把较早的计划当作当前执行依据。

状态文件和计划文件可能包含敏感信息；将变量标记为 sensitive 主要影响展示，不能据此认为数据不会落入状态。应限制访问、加密存储、保留版本、使用适当的状态锁，并避免把状态文件加入代码仓库。[2]

### 环境管理需要完整生命周期

开发、测试、预发和生产可以共享模块，但应明确凭证、配额、网络和数据边界。临时环境需要负责人、用途、过期时间和回收策略，否则自助创建只会把人工申请变成资源堆积。

生产数据进入测试环境前需要脱敏。临时环境也不能默认继承生产模型密钥、工具写权限和真实采购提交能力。预发环境可以使用工具模拟器或专用测试账户，验证副作用流程时则需要明确的测试业务空间。

### 构建一次，按环境晋级

标准流水线建议包括代码检查、单元与集成测试、工具契约测试、镜像构建、依赖检查、制品登记、预发验证、灰度发布和上线后观察。

同一应用制品应通过不可变摘要标识，在环境之间晋级，避免每个环境重新构建出不同内容。环境配置独立版本化，并在发布记录中关联。

Agent 的一次发布还需要包括模型路由、Prompt、工作流、工具 Schema 和评测集版本。以下是平台自定义发布清单示例，不是 Kubernetes 内置对象：

```yaml
releaseId: procurement-agent-20261021-01
artifacts:
  imageDigest: "<CI 写入的不可变镜像摘要>"
  workflowVersion: purchase-v7
  promptVersion: purchase-review-v12
  toolSchemaVersion: procurement-tools-v4
  modelRouteVersion: model-route-v3
  configVersion: production-config-v18
validation:
  evaluationSuite: procurement-regression-v6
  checkpointCompatibility: verified
  toolContractTests: passed
```

模型路由版本能够记录平台配置，但若供应商的模型别名在后台发生更新，它不能保证供应商内部实现完全不变。应尽可能记录实际响应的模型标识，并持续执行回归评测。

验收时应抽取一次真实发布，验证能否从运行任务定位到镜像、配置、工作流和评测结果，而不只是检查流水线是否显示绿色。

## 六、应用 Infra：让配置、网关与流量策略相互配合

### 配置中心要区分普通参数与执行契约

日志等级、界面文案和部分限流参数可以动态生效；工具定义、Prompt 与工作流结构则可能改变任务语义。后一类配置适合在任务创建时固定版本，后续迁移通过显式流程完成。

配置发布应经过 Schema 校验、兼容性检查、小范围验证和版本留存。客户端使用最近一次有效配置时，应暴露配置版本与更新时间，并定义缓存失效后的行为。

密钥与普通配置分开管理。租户密钥、工具令牌和数据库凭证通过专门的秘密管理能力下发，支持轮换和访问审计。

### 网关负责接入治理，任务系统负责执行事实

统一网关应提供认证、租户识别、路由、限流、配额、请求大小控制和访问审计。模型接入代理可以进一步统一供应商凭证、模型路由、费用归集和限流响应处理。

对于流式响应，需要明确首个有效输出超时、连接空闲超时、代理缓冲与断线恢复方式。对于异步任务，网关返回任务标识后，执行结果应由任务状态服务提供，不能依赖某个网关实例内存。

外部输入中的租户标识不能直接成为可信身份。网关应从认证结果建立租户上下文，下游继续验证访问边界；控制面和运行时也需要最小权限的服务身份。

### 服务发现与流量治理需要共同约束重试

集群内服务可通过 Kubernetes Service 和 DNS 进行发现。跨集群访问需要额外设计命名、路由、身份和故障切换策略。是否采用服务网格，应由跨服务策略一致性、身份与流量治理需求决定，同时评估数据面开销和排障复杂度。

每条调用链应有总时间预算，单次调用预算小于剩余任务预算。重试应设置次数上限、退避和抖动，并明确由哪一层负责。如果三层分别允许最多三次总尝试，极端情况下可能将一次请求放大为 27 次底层调用。

模型降级也需要业务约束。降级目标必须满足工具调用协议、上下文长度和质量要求；数据驻留或租户许可不允许的供应商不能进入候选集。发送给用户的部分流式输出无法简单撤回，因此中途切换模型还需要定义结果拼接或重新开始的体验。

## 七、灰度发布：同时管理流量与在途任务

### 灰度单位要符合状态边界

对于无状态接口，可以按请求分流；对于采购助手，更适合在任务创建时分配发布版本，并让后续步骤保持一致。仅靠入口按比例路由，无法保证异步 Worker 消费到相同版本。

任务队列、调度器与 Worker 应支持按版本或兼容能力领取任务。处于等待审批状态的任务可能持续数天，旧 Worker 的保留时间、工作流兼容期和检查点迁移方式必须一起设计。

### 自动放量需要证据与样本约束

可以从内部租户开始，逐步扩大到少量用户，再增加覆盖范围。每个阶段同时观察基础服务错误率、任务执行成功率、关键工具失败率、延迟、成本和质量评测。

Argo Rollouts 的分析机制可以依据指标决定继续、暂停或中止发布。[3] 但平台还需要补充样本量、观察时长和数据新鲜度约束。没有足够流量、指标服务不可用或评测尚未完成时，应保留为未得出结论，不能当作通过。

对会执行写操作的 Agent，影子验证应使用录制回放、模拟工具或受控测试账户，防止复制真实业务副作用。对照版本和候选版本还应尽量比较相近的任务类型，避免把流量组成变化误判为版本变化。

### 回滚是一组有边界的恢复动作

| 变更类型 | 主要恢复动作 | 必须验证的限制 |
| --- | --- | --- |
| 应用镜像 | 停止新版本接单，切回稳定版本 | 旧版本是否兼容当前配置和数据 |
| Prompt 或模型路由 | 恢复旧配置，固定新任务版本 | 已输出结果无法自动撤回 |
| 工作流结构 | 将新任务切回旧版本 | 在途任务是否可由旧运行时接管 |
| 数据结构 | 使用兼容读写或前向修复 | 不把删除数据视为普通回滚 |
| 已执行采购动作 | 查询业务结果并执行补偿 | 撤销需要业务权限和可撤销条件 |

数据库变更可以先扩展兼容字段，让新旧版本并存，再迁移数据，最后在确认兼容窗口结束后收缩旧结构。对无法恢复的外部副作用，需要明确的业务补偿，不能承诺通过镜像回退消除影响。

一次发布只有在流量恢复、任务状态可核对、数据兼容且指标回稳后，才算完成恢复。仅将灰度权重改为零，只完成了其中一部分。

## 八、可观测性与 SLO：让每个告警指向可验证的用户影响

### 统一关联标识，控制数据规模

建议在日志与链路中关联服务、环境、租户、任务、执行尝试、工作流版本和发布版本。任务跨进程或跨队列运行时，显式传递追踪上下文；长时间挂起后可以使用关联标识或 Span Link 连接不同阶段，避免依赖一条无限增长的 Trace。

OpenTelemetry 的 GenAI 语义约定覆盖模型相关遥测；核验时官方页面已指向独立的 GenAI 规范仓库，该仓库将相关总览标为 Development。[4] 实施时应固定采用的约定版本，建立兼容映射，并区分标准字段与平台自定义字段。

采购助手需要记录模型延迟、输入输出 Token、工具执行结果、重试原因和步骤耗时，但不应默认完整收集所有 Prompt、采购资料和凭证。敏感内容需要脱敏、访问控制、保留期限与删除机制。

任务标识、用户标识等高基数字段适合用于日志和链路检索；常规指标标签应使用有界维度。按每个任务生成时间序列，会迅速提高存储和查询成本。核心 SLI 应使用完整事件或专门聚合数据计算，避免直接从有偏抽样的 Trace 推导成功率。

### 为不同执行阶段定义不同 SLI

| SLI | 建议口径 | 需要提前约定的问题 |
| --- | --- | --- |
| 任务接收成功率 | 成功持久化的有效请求数 / 有效请求总数 | 合同内请求被容量限制拒绝是否计失败 |
| 任务及时完成率 | 在承诺时限内成功的任务数 / 已到评估期限的合格任务数 | 超期仍运行的任务必须进入失败统计 |
| 交互延迟达标率 | 在阈值内产生首个有效输出的请求数 / 合格交互请求数 | 区分有效输出与连接握手或心跳 |
| 工具副作用正确率 | 经核对无重复、无遗漏的操作数 / 应核对操作总数 | 检测窗口与结果未知如何处理 |

人工等待可以从平台执行时间中单独扣除，但端到端用户等待时间仍应保留。用户取消、格式错误、业务规则拒绝等分类要预先约定，避免事后改变口径。若平台承诺包含供应商调用，供应商故障通常仍会影响用户侧 SLO，应在内部归因时另行标记。

示例：为任务接收设置 30 天 99.9% 的事件成功率目标，那么错误预算为该窗口合格事件总数的 0.1%。请求量变化时，不能直接把这一预算等同于固定停机分钟数。

### 用错误预算消耗率组织告警

错误预算消耗率可以写成：

```text
消耗率 = 当前错误比例 / (1 - SLO 目标)
```

目标为 99.9%，当前错误比例为 1%，消耗率就是 10。在流量和错误比例保持相近的简化条件下，这意味着预算消耗速度为允许水平的十倍。

Google SRE 给出了基于消耗率和多窗口组合的告警方法。[5] 平台可以使用长窗口判断影响是否持续、短窗口确认故障是否仍在发生，并将高消耗率事件交给值班人员，慢性消耗转为工作项。低流量服务还需要合成探测、最小样本量和任务级检查，避免少数请求造成误导。

告警内容应直接包含受影响服务、用户影响、起始时间、最近发布、依赖状态、相关链路和操作手册。平台应持续统计误报、重复告警与无行动告警，减少值班人员手动关联信息的时间。

## 九、容量与成本：从任务模型推导资源需求

### 先算执行并发，再讨论副本数

在系统稳定且统计范围一致时，可以用“平均在系统中的任务数约等于任务到达率乘以平均停留时间”进行初步估算。

假设采购助手每秒到达 2 个任务，每个任务平均占用执行槽位 30 秒，则平均需要约 60 个执行槽位。如果单个 Worker 可在资源约束内承载 10 个槽位，并希望平均槽位利用率控制在 60%，则初步估计需要 10 个 Worker。

这是平均负载下的起点，尚未覆盖长尾、突发、重试、节点启动时间和故障余量。人工审批等待若不占用执行槽位，应单独统计；如果计算端到端在途任务数，则要把等待时间纳入停留时间。

### 分别核对每一种瓶颈

假设每个任务平均调用模型 4 次、每次约消耗 3000 个输入与输出 Token。在每秒 2 个任务的负载下，约产生每分钟 480 次模型调用和 144 万个 Token。这个估算只用于说明方法，实际还需区分输入与输出配额、模型、区域和供应商的计费方式。

因此，容量评估应分别覆盖 Worker 槽位、CPU、内存、数据库连接、队列吞吐、模型请求额度、Token 额度及工具服务限制。任何一个限制都可能成为全链路瓶颈。

自建推理服务时，还需要单独分析显存、并发序列、上下文长度和推理阶段的资源消耗。使用外部 API 时，应把采购配额与供应商故障时的备用容量一起纳入计划。

### 把成本控制放在执行前和执行中

平台可以设置租户预算、任务 Token 预算、工具调用次数上限、最大步骤数和执行时限，并对低优先级任务实施排队或延后。预算耗尽时需要返回明确状态，不能将任务静默丢弃。

并行子任务可能同时消费预算，因此严格的预算限制需要额度预留或原子记账。考虑到用量回报可能存在延迟，平台也应定义允许的短暂超额与结算方式。

核算时同时观察总成本、单次成功任务成本、失败任务消耗和重试放大。如果更便宜的模型显著增加重试和人工返工，总体成本可能上升。优化效果需要结合质量与成功率评估。

## 十、容灾与应急：验证任务是否真的恢复

### 让恢复目标覆盖状态与外部事实

恢复时间目标 RTO 描述多久恢复服务，恢复点目标 RPO 描述最多可接受丢失多少时间范围内的数据。它们应按服务等级分别定义，并通过演练验证。

采购助手的恢复对象不仅包括数据库，还包括任务记录、检查点、队列或可重建事件、发布版本、配置、权限和外部采购单号。若数据库恢复到较早时刻，而外部采购系统已经完成提交，恢复后的任务可能再次执行，因此必须进行业务对账。

同样，已经向用户确认接受的任务如果因恢复点回退而丢失，就违反了相应的持久化承诺。可以通过更强的复制或持久化事件记录改善保障，但需要同步评估跨区延迟、成本和可用性取舍。

多集群能够隔离部分故障，却不会自动消除共享数据库、统一身份服务或模型供应商的单点。跨区切换前，还要避免两侧同时对同一任务执行写操作。

### 从受控演练验证完整恢复链路

| 演练场景 | 重点观察 | 恢复验收 |
| --- | --- | --- |
| 执行中 Worker 被终止 | 租约、检查点、接管耗时 | 任务可继续，副作用无重复 |
| 单个可用区不可用 | 剩余容量与依赖可达性 | 关键 SLO 和恢复时间满足约定 |
| 模型持续限流 | 背压、重试、队列增长 | 无重试风暴，积压可在目标时间内消化 |
| 错误配置逐步下发 | 灰度门禁、配置缓存、回退 | 影响范围受控，实例版本可核对 |
| 从备份恢复状态 | 数据一致性与外部对账 | 已接收任务可解释，无静默丢失 |

演练应明确假设、范围、负责人、停止条件和恢复手册，从小范围开始。成功标准需要描述用户结果，而不仅是 Pod 已恢复运行。

应急流程可以按“发现与定级、指定负责人、控制影响、恢复与核对、复盘改进”组织。优先使用经过验证的止损动作，例如暂停接单、关闭高风险工具、限制受影响租户或回切稳定版本。

复盘应把改进落实到平台能力：补充一个发布门禁、完善一条诊断查询、提供一个可回退操作，或修正一项容量模型。持续统计同类故障复发率，才能判断机制是否有效。

## 十一、智能运维：让 AI 使用证据，按约束执行

### 先建设诊断所需的数据入口

当“任务超时率升高”触发告警时，运维 Agent 应能够读取服务目录、SLO、近期变更、调用链、队列状态和依赖错误。输出需要区分已观察事实、推测原因、支持证据和待验证项。

例如，它可以发现超时任务集中于某个模型路由版本，队列增长先于 CPU 上升，模型限流错误与发布时间接近。这些信息支持“供应商额度或路由策略异常”的候选解释，但仍需检查请求额度和发布差异，不能仅凭时间相关性断言根因。

把日志、工单和运行手册接入知识检索时，应保留来源、更新时间和适用版本。历史操作不能因为曾经有效就直接用于当前环境。

### 从辅助分析逐步走向受控执行

第一阶段提供告警摘要、流水线失败分析和排障建议；第二阶段允许调用预定义只读查询；第三阶段开放有限的、可验证和可回退的处置动作。

例如，自动扩容动作需要满足实例上限、租户配额、模型额度和数据库连接预算，并验证真正瓶颈是 Worker 容量。执行后检查队列等待时间是否改善、依赖错误是否恶化，未满足预期时停止继续扩容。

授权与执行策略应由平台独立判断。运维 Agent 不能自己批准自己的权限升级。生产数据删除、无法撤销的业务写操作和跨区域数据移动，应进入相应的变更与授权流程。

工具接口适合暴露“查询发布差异”“暂停指定服务放量”“按上限扩容”等明确动作。每个动作都有参数 Schema、权限范围、前置条件、超时、幂等规则、验证步骤和审计记录。

### 用回放评测检验真实效果

历史故障可以构建诊断评测集，但回放时应隔离事后复盘结论，避免把答案泄漏给模型。评价维度包括候选根因准确率、证据引用正确率、误操作率、诊断耗时和恢复耗时。

对于自动处置，还需要统计“建议看似合理但未改善系统”的比例。平台应保存执行前后的观测快照、工具参数、决策依据和操作结果，使每次处置都可以被复核。

## 十二、技术选型与建设路线：以能力验收推动平台成熟

### 技术选型应回答具体问题

| 能力 | 可以评估的方向 | 架构评审重点 |
| --- | --- | --- |
| 资源管理 | Terraform、云平台资源模板 | 状态安全、模块复用、漂移和恢复 |
| 应用交付 | GitOps 控制器、渐进式发布控制器 | 状态一致性、门禁、回退和维护成本 |
| 网关与流量 | Kubernetes 网关实现、必要时引入服务网格 | 协议支持、租户策略、流式行为、排障复杂度 |
| 任务运行 | 持久化工作流引擎、具有检查点的 Agent 运行时 | 恢复语义、版本兼容、幂等边界 |
| 可观测性 | OpenTelemetry 与日志、指标、链路后端 | 数据成本、关联查询、采样和敏感数据治理 |
| 配置与密钥 | 统一配置服务、独立秘密管理 | 版本、缓存行为、轮换与访问审计 |

候选方案先用采购助手的真实场景进行验证：终止 Worker、模拟工具响应丢失、保留旧任务并发布新版本、制造模型限流，再检查恢复证据。把验证结果写入架构决策记录，说明适用规模、已知限制和替换成本。

避免为抽象的“统一”建立过重平台。若多个团队使用不同 Agent 框架，可以优先统一身份、工具协议、任务元数据、遥测和交付接口，让框架差异保留在适当边界内。

### 分阶段交付可用能力

| 阶段 | 核心交付物 | 验收方式 |
| --- | --- | --- |
| 基础标准化 | 服务目录、环境模板、IaC 模块、标准流水线 | 新服务能按模板部署，资源与发布可追溯 |
| 应用治理 | 配置、网关、流量策略、灰度门禁、统一观测 | 一次异常发布能被发现、中止并完成恢复 |
| 执行可靠性 | 任务状态、检查点、幂等工具、容量与容灾机制 | 长任务跨故障恢复，业务副作用可核对 |
| 平台产品化 | 自助入口、配额、操作手册、智能诊断与受控处置 | 减少人工交接，并以真实事件证明效率提升 |

阶段可以交叉推进，但自动化处置依赖于清晰的服务目录、可靠的观测数据和可验证的操作接口。基础能力缺失时，增加一个运维聊天入口很难稳定缩短恢复时间。

平台最终应提供一条清晰的自助路径：业务团队登记服务，选择环境和运行模板，声明依赖与 SLO，提交发布版本，经过验证上线，并在同一入口查看任务、成本和故障信息。

衡量建设成效，可以持续跟踪环境交付时间、变更交付时间、变更失败率、故障恢复时间、重复事故数、任务超期率、单次成功任务成本，以及需要平台人员手动介入的次数。为这些指标建立基线，再用真实发布与故障数据检验改进。

对于采购助手，一套成熟的 Infra 平台应能在 Worker 故障后继续任务，在发布失败后恢复接单，在供应商限流时控制积压，并解释每一个采购动作是否真正发生。平台能力正是在这些可重复验证的行为中形成的。
