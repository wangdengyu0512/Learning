同一张工单，第一次被分给网络组，第二次被分给应用组；同一段设备故障描述，换个说法就变了紧急程度；接口明明要求 JSON，偶尔却多出一段解释。遇到这些现象，团队很容易把问题归结为“模型太随机”，然后尝试把 temperature 调到 0。

这个调整可能改善其中一部分问题，却不能回答全部问题。逐字相同的答案可能一直是错的；格式正确的 JSON 可能包含虚构字段值；十个候选答案可能共享同一个错误。要让模型进入可依赖的业务流程，必须先说清楚：哪些东西需要保持不变，哪些变化是合理的，哪些结果有资格被系统接受。

本文把“稳定输出”拆成可测试的目标，再结合相关研究讨论可实现的保证。论文用于说明已研究的方法和边界，文中的工单示例、系统架构、验收指标与实施顺序均为工程设计建议，不是论文已验证的统一配方。参考文献核对日期为 2026 年 10 月 24 日。

## 一、先定义稳定，才能判断方案是否有效

考虑一张工单：“应用页面打开很慢，连续刷新后偶尔出现超时。”

如果我们要求每次解释文字完全一致，目标是文本复现。如果只要求每次得到相同的负责团队，目标是决策一致。如果要求输出总能被程序解析，目标是结构合规。如果希望在证据不足时避免错误派单，目标则进一步涉及可靠性。

这些目标可以分别定义。

| 维度 | 需要固定的条件 | 检查什么 | 不能据此推出什么 |
| --- | --- | --- | --- |
| 文本可复现 | 输入、版本和声明的运行条件 | 输出字节或 token 序列是否相同 | 答案正确 |
| 结构合规 | 输出协议及其版本 | 语法、字段、类型和枚举是否合规 | 字段值真实 |
| 语义一致 | 事实与任务含义保持不变 | 改写后结论是否相容 | 对新事实也应维持旧结论 |
| 决策可靠 | 证据、业务规则与风险要求 | 接受的结果是否满足验收条件 | 模型每次都能回答 |

“含义保持不变”需要认真定义。“页面慢”和“页面慢且所有用户均无法登录”不能直接放进同义改写测试，后者增加了影响范围与症状。系统如果因此升级工单，可能恰恰是正确反应。

ParaRel 研究通过表达相同事实关系的不同提示来衡量模型预测的一致性，并把一致性与准确性区分开来。[2] 它支持一个基本判断：评估模型时，既要看答案是否正确，也要看它是否对无关的表达变化过度敏感。该研究的原始实验对象主要是预训练掩码语言模型，不能直接把实验数值视为现代聊天模型的表现。

对工单系统，本文采用如下稳定性目标：**在证据与规则版本不变时，语义等价的请求应产生相容的路由结果；证据不足时，系统应进入明确的待补充状态；已经提交的同一请求，应能够返回已保存的结果。** 解释文字可以变化，关键决策和状态转换必须受到检查。

## 二、输出的变化来自哪些层次

### 1. 采样只是不确定性的一个来源

自回归模型根据输入 x 和已经生成的前缀，计算下一个 token 的条件概率：

```text
p(y_t | x, y_1, ..., y_(t-1))
```

采样解码按照经过处理的概率分布抽取 token；贪心解码选择当前分数最高的 token。Self-Consistency 的一个关键做法，就是用多条采样推理路径代替单条贪心路径，再聚合最终答案。[4]

温度通常用于缩放 logits。对于正温度 T，常见表达是：

```text
p_i(T) = exp(z_i / T) / Σ_j exp(z_j / T),  T > 0
```

较低温度使分布更集中，但这里的公式不能直接代入 T = 0。接口中 temperature 为 0 的语义，应以具体实现为准；讨论工程保证时，需要确认它是否使用贪心选择，以及是否还有其他会影响候选 token 的处理步骤。[1][4]

即便每一步都选最高分 token，也不代表求得了整条序列概率最高的答案，更不代表求得了事实最正确的答案。“选择过程确定”和“所选内容正确”是两个问题。

### 2. 数值计算也可能改变生成路径

假设两个候选 token 的分数极为接近。运行配置改变了浮点运算顺序，导致很小的数值差异，最高分候选就可能发生变化。自回归生成会把这个变化写入后续上下文，最终文本差异因此可能远大于最初的数值扰动。

NeurIPS 2025 论文《Understanding and Mitigating Numerical Sources of Nondeterminism in LLM Inference》研究了贪心解码条件下的这类问题，包括批大小、GPU 数量以及硬件类型变化带来的影响。[1] 这说明：消除随机采样之后，仍需考虑数值计算与运行环境。

固定随机种子主要控制使用相应随机数生成器的过程，不能自动固定全部浮点运算、服务调度与依赖版本。对托管接口，如果使用者无法控制底层运行配置，就应把逐字复现当成需要实测的服务属性，而不能只根据请求参数推断。

### 3. 输入相同，实际送入模型的上下文未必相同

在工程排查中，建议把一次输出建模为以下因素的共同结果：

```text
输出 = F(
  用户输入,
  系统提示与历史上下文,
  检索证据与工具结果,
  模型和分词器版本,
  解码配置,
  运行配置
)
```

这是用于定位问题的抽象，不是对模型内部机制的完整数学描述。

如果用户输入没有变化，但检索库更新了、工具返回的新状态不同了，或者对话历史多了一条消息，就不能把结果变化全部归因于随机性。诊断之前，应保存实际送入模型的消息、证据快照和配置标识。

## 三、实现可复现：先控制条件，再定义回放

### 1. 建立可比较的运行记录

针对工单分类，可以为每次调用保留以下记录。示例中的版本号和标识均为假设值。

```json
{
  "request_id": "req-1042",
  "task_version": "ticket-routing-v3",
  "model_revision": "model-build-17",
  "tokenizer_revision": "tokenizer-build-4",
  "prompt_version": "prompt-v8",
  "schema_version": "schema-v2",
  "policy_version": "routing-policy-v5",
  "evidence_snapshot": "snapshot-20261024-001",
  "decoding": {
    "mode": "greedy",
    "max_output_tokens": 256
  }
}
```

这些字段不构成某家厂商的 API 请求格式，而是一份建议的审计记录。自建推理服务还可以记录引擎、驱动、硬件与相关计算配置；托管服务则记录服务商实际提供的版本信息。拿不到的字段应明确标为未知。

先在固定条件下重复执行，再单独改变批大小、并发度或环境。如果一开始就混合改变多个因素，很难判断哪个因素导致结果波动。数值确定性的进一步优化可能影响性能，具体代价需要在实际工作负载上测量。[1]

### 2. 区分重新生成与返回已有结果

如果产品要求“同一张工单重复提交时必须得到同一个结果”，可以通过持久化结果与请求幂等机制满足这一要求。它与“重新运行模型必定生成同样的文本”是不同的服务保证。

建议区分两种键。

| 键 | 用途 | 建议约束 |
| --- | --- | --- |
| 请求幂等键 | 识别同一次业务请求的重复提交 | 同一键绑定同一请求内容，内容不同时拒绝复用 |
| 计算缓存键 | 在条件相同时复用已验证的计算结果 | 包含任务、输入、模型、提示、证据、规则和权限范围等版本信息 |

缓存键不能只对用户输入求哈希。来自不同租户、不同权限范围或不同知识快照的请求，可能不应该共享答案。缓存本身也需要有效期和失效机制。

建议只回放已经通过验收并成功提交的结果，保存其决策记录编号。旧结果可以用于审计，但在知识或规则更新后是否继续用于新请求，应由明确的产品规则决定。

这里的关键选择是：**需要复盘旧决策时读取历史，需要基于新事实决策时产生新版本。** 把两种需求混在一个“永远不变”的缓存里，会掩盖该发生的更新。

## 四、约束输出空间：让模型在明确的协议内工作

### 1. 提示词要求与解码约束的区别

“请只输出 JSON”是一条自然语言指令。语法约束解码则在生成过程中限制下一步允许选择的 token，使其符合指定语言或结构。《Grammar-Constrained Decoding for Structured NLP Tasks without Finetuning》研究了这类方法在结构化 NLP 任务中的应用。[3]

工程中需要区分约束层次：合法 JSON、满足指定 Schema、满足业务规则，并不是同一件事。不同实现支持的 Schema 子集、引用方式和约束能力也不同，应以实际实现为准。

对工单路由，可以先设计一个有限决策空间：

```json
{
  "status": "decided",
  "category": "network",
  "priority": "P2",
  "evidence_ids": ["obs-31", "obs-32"],
  "missing_fields": []
}
```

这是一个假设已有足够观测证据的输出示例，并非根据开篇那一句症状描述即可得出的结论。

协议可以规定 category 仅允许 network、application、database、unknown；status 仅允许 decided、needs_info、review。进一步规定 decided 状态必须有可核验的证据，needs_info 状态必须列出缺少的信息。

枚举和字段类型有机会在解码阶段限制，证据是否存在、是否有权访问、是否真的支持结论，则需要后续检查。输出被截断、请求超时或约束构造失败，也需要作为独立的接口失败处理，不能算成已获得合规结果。

### 2. 结构约束后的验证分工

建议按以下顺序检查候选结果：

| 检查层次 | 工单示例 | 适合的实现方式 |
| --- | --- | --- |
| 语法检查 | JSON 是否完整 | 解析器 |
| 协议检查 | 枚举、必填字段、类型 | Schema 验证器 |
| 引用检查 | obs-31 是否存在于本次授权证据中 | 标识匹配与权限检查 |
| 规则检查 | 哪些可观测条件允许 P1 | 版本化规则引擎 |
| 语义检查 | 证据是否足以支持“网络故障” | 专用验证器、模型辅助或人工复核 |

最后一层通常更难自动化，应报告验证器自身的误判率。模型生成的解释即使写得很完整，也不能替代原始观测记录。

结构约束的价值在于缩小输出空间、明确接口边界。它不会赋予模型未知的事实，也不会自动解决任务定义含糊的问题。[3]

## 五、候选聚合与验证：让额外计算服务于明确目标

### 1. Self-Consistency 聚合的是答案

Self-Consistency 生成多条推理路径，抽取最终答案，再选择支持最多的答案；其原始研究在多项算术与常识推理任务上报告了改进。[4] 它为“生成多个候选，再比较结果”提供了重要依据。

在工单系统中，应用这一思路需要先定义答案等价类。network、网络问题和网络组可能需要映射到统一类别；但“网络故障已确认”和“需要排查网络故障”不能因为都包含“网络”而被合并。

以下是一个假设的投票结果，不代表真实实验：

```text
候选 1：network
候选 2：application
候选 3：network
候选 4：network
候选 5：unknown

network 支持率 = 3 / 5
```

3/5 描述这组候选的支持比例，不能直接解释成“有 60% 概率正确”。候选共享模型、输入与证据，可能高度相关。即使支持率达到 5/5，也可能只是同一个错误被重复表达。

如果每次调用都会重新采样，投票结果本身还可能变化。因此，应同时测量聚合前后的准确率和重复运行一致性，不能用准确率改进代替确定性证明。

### 2. 自由文本需要单独定义一致性判断

工单标签容易比较，长文本解释则很难靠字符串相等判断。《Universal Self-Consistency for Large Language Model Generation》使用语言模型从候选中选择最一致的响应，将这一思路扩展到自由文本生成任务。[5]

这引入了一个额外评估环节：负责选择的模型也可能偏好更流畅、更长或位置更靠前的答案。因此，在采用这种方案前，应评测候选顺序变化、表达长度变化和关键事实冲突是否影响选择。

对业务输出，建议优先把待比较的内容分解为明确字段、事实主张或决策类别，再决定是否需要模型评审整段文本。

### 3. 验证器与多数票解决不同问题

《Training Verifiers to Solve Math Word Problems》训练验证器对候选解答评分，再从多个候选中选择答案。[6] 这一研究支持“生成与选择分开设计”的思路，但其数学任务结果不能直接视为工单验证器的效果。

对于能够形式化验证的任务，可以优先采用程序检查：算术交给计算器，数据引用交给查询结果，类型与字段交给验证器。对于语义判断，则需要专门的标注集来检验验证器是否会接受错误结论。

本文建议将投票结果作为辅助信号，把是否接受输出交给统一的验收规则。若证据冲突、票数接近或验证失败，输出 review 或 needs_info，而不是不断重采样直到出现一个看起来顺眼的结果。

## 六、证据与不确定性：让系统知道何时可以接受答案

### 1. 引入外部证据，也要记录证据的变化

RAG 将检索得到的非参数化知识与生成模型结合。Lewis 等人的原始研究在知识密集型任务中评估了这种设计。[7] 该研究为外部知识增强提供了依据，但没有证明任何接入检索的系统都能获得稳定且正确的回答。

对工单系统，建议把证据分为两类：一类是相对稳定的故障手册和路由规则；另一类是会随时间变化的监控、日志与服务状态。二者都应带有来源、版本或观测时间。

例如，用户只说“页面很慢”，不足以支持直接归因。系统可以查询请求延迟、错误日志和依赖状态，再决定是否满足某条路由规则。若查询失败，应返回缺少的证据项，不能把“没有查到”解释为“故障不存在”。

为了复现一次决策，建议保存实际提供给模型的片段及其顺序，而不只是保存检索查询。为了判断当前故障，则需要重新取得新观测。历史回放与实时诊断应有明确的入口和版本边界。

### 2. 四种看起来像概率的数字

| 数字 | 实际描述的对象 | 使用前需要注意什么 |
| --- | --- | --- |
| token 概率 | 下一个 token 的条件分布 | 与整个答案是否正确不是同一事件 |
| 候选支持率 | 某次采样中支持某答案的比例 | 候选可能共享偏差，不能直接当正确概率 |
| 模型自报置信度 | 模型对自身结果的评估 | 需要在目标任务上验证校准情况 |
| 经校准的分数 | 在指定任务与数据条件下修正后的置信估计 | 新领域与分布变化可能影响有效性 |

Kadavath 等人的研究考察模型评估自身答案是否正确、以及是否知道答案的能力，在特定设置下得到积极结果，同时指出跨任务校准仍有困难。[9] 因此，“请给出 0 到 1 的置信度”可以提供一个待评估的特征，不能直接成为生产系统的可信阈值。

### 3. 校准温度与采样温度的目标不同

Guo 等人的工作研究分类模型的概率校准，并评估了温度缩放等后处理方法。[8] 温度缩放通常在独立校准数据上学习参数，使预测置信度与实际正确频率更接近。

虽然它也会缩放 logits，但与生成时为了调整随机性而设置温度的目标不同。对固定分类 logits 使用正的标量温度缩放，不会改变最大分数类别的排序；它主要调整概率分布，而不是自动修正分类错误。[8]

如果工单任务已有清晰的类别和标签，可以单独设计分类置信度与校准流程。对开放文本，首先要定义“正确”对应什么可标注事件，例如路由正确、关键事实都受到支持，或结果通过特定验收规则，然后才能讨论那个事件的概率。

建议将数据划分为训练或开发集、校准集和最终测试集，避免反复在最终测试集上选择阈值。阈值一旦上线，还应按故障类型、来源渠道和时间段监测接受率与错误率。

### 4. 共形预测提供集合层面的统计保证

共形预测可以利用校准数据构造预测集合。适用条件下，其覆盖保证可以写为：

```text
P(Y_new 属于 C(X_new)) ≥ 1 - α
```

这里是对校准数据和新样本随机性而言的边际覆盖保证，依赖交换性等条件；它不等于每个输入都具有同样的条件正确率，也不保证集合只有一个元素。[10]

对于有限类别的工单路由，预测集合可能同时包含 network 和 application。本文建议将这种情况用于触发补充诊断，而不是强行选出一个类别。

还要注意：只在集合为单元素时自动接受，并不能直接从边际覆盖保证推出“所有被接受样本的错误率不超过 α”。这种选择性决策需要另行评估或使用相应的风险控制方法。对自由文本任务，预测空间与评分函数也要专门设计，不能直接照搬分类集合。[10]

## 七、把生成、验证和业务提交连接起来

下面是一套面向工单系统的参考流程。它是一项组合设计，具体效果需要通过下一节的实验验证。

```text
接收工单与请求标识
        ↓
核对请求内容、访问范围和版本
        ↓
查找同一请求已提交的结果 ── 命中 → 回放结果
        ↓ 未命中
获取证据，保存快照与观测时间
        ↓
生成结构受约束的候选决策
        ↓
解析、协议、引用与业务规则校验
        ↓
必要时增加候选并进行聚合、验证
        ↓
按验收规则选择状态
        ├── decided：保存并提交路由结果
        ├── needs_info：返回待补充信息
        └── review：进入人工处理队列
```

流程中最重要的边界，是候选生成与业务提交之间的验收环节。模型可以提出 category 和 priority，系统需要决定这些字段是否有资格驱动路由。

下面的 Python 风格伪代码只表达职责分配，不是可以直接运行的 SDK 示例。

```python
def route_ticket(request, versions):
    # 相同幂等键必须绑定相同的请求内容与访问范围。
    previous = load_committed_result(request.idempotency_key)
    if previous is not None:
        assert_same_request(previous, request)
        return previous.result

    evidence = collect_authorized_evidence(request)
    snapshot = save_evidence_snapshot(evidence)

    candidate = generate_constrained_candidate(
        request=request,
        evidence=snapshot,
        versions=versions,
    )

    checks = validate_candidate(candidate, snapshot, versions)
    decision = apply_acceptance_policy(candidate, checks, versions)

    # 原子保存结果；同一键的并发请求只能提交一个有效结果。
    # 若另一个请求先提交，核对请求一致性并返回已提交结果。
    return commit_once_or_load_existing(
        request=request,
        decision=decision,
        evidence_snapshot=snapshot.id,
        versions=versions,
    )
```

实际实现还要处理请求处理中断、并发竞争、证据过期和存储失败。如果路由动作要调用外部系统，结果记录与外部动作之间需要可靠的任务交接，并让下游接受幂等标识；数据库中只有一份结果，不能单独证明外部动作只执行了一次。

重试也应有明确目的。解析失败可以触发有限修复；证据缺失应补充查询；事实冲突应进入复核。建议给每类失败配置次数、时间和成本预算，达到预算后返回明确状态。

再次考虑开篇的工单。仅有“页面慢、偶发超时”时，流程可以稳定地进入 needs_info，并指出需要时间窗口、受影响范围和相关监控。补充证据后，产生一个新版本的决策。这里的稳定体现为处理规则可解释、状态转换可追溯，而不是第一次猜出的路由永远不变。

## 八、用实验分别证明一致性和正确性

### 1. 测试集应覆盖不该变化和应该变化的情况

建议按以下维度组织测试用例。

| 用例类型 | 改变什么 | 保持什么 | 观察目标 |
| --- | --- | --- | --- |
| 重复调用 | 调用次数 | 完整输入、证据与配置 | 文本与决策复现 |
| 同义改写 | 句式、语序和措辞 | 事实、范围与任务意图 | 语义一致性 |
| 事实反转 | 故障范围、时间或观测事实 | 其余背景 | 能否正确更新结论 |
| 证据不足 | 删除关键观测 | 原有任务 | 能否进入补充信息状态 |
| 证据冲突 | 引入相互矛盾的观测 | 来源可追溯 | 能否识别冲突并复核 |
| 环境扰动 | 批大小、并发或硬件 | 请求与模型版本 | 运行条件敏感性 |
| 版本回归 | 模型、提示、规则或知识版本 | 固定评测样本 | 改进与退化的分布 |

同义改写需要抽样人工核对，避免测试数据生成时引入事实变化。事实反转测试则用于发现另一种失败：系统为了保持一致，忽略了本应改变答案的新信息。

测试“生成是否稳定”时，应绕过结果缓存；测试“重复请求是否回放”时，应单独检验缓存与幂等流程。否则，缓存命中率可能被误报为模型稳定性。

### 2. 避免用一个百分比覆盖全部问题

对同一问题执行 K 次，取得标准化后的决策 d_1 到 d_K。一个直观的描述指标是两两决策一致率：

```text
两两决策一致率 = 相同决策的无序调用对数量 / [K × (K - 1) / 2]
```

K 必须至少为 2。决策应明确是否同时包含状态、类别和优先级；请求错误不能被当作一种“所有结果都一样”的成功决策，应单独记录失败率。这个指标不需要正确标签，也因此不能说明决策正确。

当系统允许拒答或转人工时，还应计算：

```text
自动接受率 = 自动接受请求数 / 全部有效评测请求数

选择性错误率 = 自动接受但错误的请求数 / 自动接受请求数
```

如果没有自动接受的请求，选择性错误率应记为不适用，不能记为 0 并宣称系统完美。只报告很低的错误率而不报告接受率，同样可能掩盖一个几乎拒绝所有请求的系统。

建议至少同时报告以下指标：

| 指标 | 回答的问题 |
| --- | --- |
| 文本完全匹配率 | 是否逐字复现 |
| 关键字段一致率 | 实际决策是否一致 |
| 结构合规率与请求失败率 | 接口是否可用 |
| 全样本任务准确率 | 整体完成任务的质量如何 |
| 自动接受率与选择性错误率 | 自动处理了多少，其中错了多少 |
| 分类型错误率 | 是否在少数重要场景集中失败 |
| P50、P95 延迟与每个正确自动处理结果的成本 | 收益是否值得资源投入 |

所有指标都要写清分母和失败处理方式。比较系统时，建议在相近接受率或相同错误预算下比较，同时展示接受率与错误率的变化曲线。

### 3. 逐项增加机制，再做独立消融

可以先建立一组递进实验：

| 实验组 | 配置 | 主要观察 |
| --- | --- | --- |
| A | 当前基线 | 原始质量、波动与成本 |
| B | A + 固定版本与声明的解码配置 | 重复调用变化 |
| C | B + 结构约束 | 格式与字段合规 |
| D | C + 候选聚合 | 准确率、一致性和成本变化 |
| E | D + 验证与不确定性处理 | 自动接受率与接受后的错误 |

这组实验适合观察逐步建设的结果，但相邻差异不一定代表某项机制在所有组合中的独立收益。还应补充 C 加验证但不加聚合等消融组，判断某个环节是否值得保留。调整接受阈值时，要避免因为拒答增多而把错误率下降全部归因于推理能力提升。

可以先做小规模预实验估计波动，再根据目标误差和成本决定样本量。最终比较应使用相同问题集，按问题或工单实体分组统计；同一工单的多次调用与改写不应被当成完全独立的业务样本。建议报告置信区间，并保留配对结果以检查哪些问题发生了变化。

本文章节中的数字、字段值和投票示例用于解释设计，没有实际执行上述实验，也没有提供虚构的准确率提升结果。

## 九、根据目标选择最小可行方案

不同任务不必同时引入全部方法。

| 首要问题 | 建议优先建设 | 进一步增加的条件 |
| --- | --- | --- |
| 输出偶尔不能解析 | 明确协议、约束解码与解析校验 | 业务字段仍不可靠时加入语义验证 |
| 同一请求重复执行结果不同 | 固定可控条件、保存版本、实现结果回放 | 确需重新生成复现时研究数值与运行配置 |
| 改写后分类变化明显 | 清晰标签定义、改写测试与边界样本 | 基线不足时评估任务微调、聚合或验证 |
| 无证据也给出确定结论 | 证据引用检查、needs_info 和 review 状态 | 有标注数据后评估校准与风险阈值 |
| 自动流程产生错误动作 | 提交前验收、幂等、审计与恢复机制 | 扩大自动化范围前验证分场景错误预算 |

若工单分类、路由与优先级规则已经足够明确，还可以将问题拆得更小：模型抽取可核验的事实，程序根据规则生成类别和优先级。这个设计是否优于直接让模型做决策，需要在同一测试集上比较，尤其检查信息抽取错误会如何传播。

对固定业务，训练或微调也是可评估选项，但需要积累代表性的正确样本、边界样本和一致性样本。ParaRel 的研究包含改善一致性的训练方法，为这一方向提供了参考。[2] 推理协议、验证和结果记录仍应保留，因为训练改进本身不构成接口合规或业务正确性的绝对保证。

可以从三个具体交付物开始实施：一份明确状态与字段的输出协议，一套包含重复调用、改写和事实变化的评测集，一条保留证据与版本的提交记录。随后只为已测量的失败增加对应机制。

当产品要求变化时，这些交付物也能帮助团队做出具体选择：需要更强的复现，就收紧运行条件或明确回放规则；需要更高的自动接受率，就改善证据和模型能力；需要更低的接受后错误率，就完善验证与选择策略。每个目标都应对应一个可观测指标和一条明确的系统责任。

## 参考文献与阅读顺序

以下按正文编号排列。年份区分预印本首次提交与正式发表；原文地址用于核查方法、实验对象与适用条件。

**[1] Jiayi Yuan, Hao Li, et al. Understanding and Mitigating Numerical Sources of Nondeterminism in LLM Inference. NeurIPS, 2025.**

研究贪心解码下的数值不确定性及运行配置变化。适合回答“为什么关闭采样后仍不能简单宣称完全可复现”。

原文：`https://proceedings.neurips.cc/paper_files/paper/2025/file/f80094a824ba5912d4a2de169c404a40-Paper-Conference.pdf`

**[2] Yanai Elazar, Nora Kassner, et al. Measuring and Improving Consistency in Pretrained Language Models. TACL, 9: 1012–1031, 2021.**

提出 ParaRel，研究意义保持不变的提示改写下的预测一致性，并探索改进方法。

原文：`https://aclanthology.org/2021.tacl-1.60/`

**[3] Saibo Geng, Martin Josifoski, Maxime Peyrard, Robert West. Grammar-Constrained Decoding for Structured NLP Tasks without Finetuning. EMNLP, 2023.**

研究语法约束与输入相关文法在结构化 NLP 任务中的应用。本文核对的 arXiv 版本最后修订于 2024 年。

原文：`https://arxiv.org/abs/2305.13971`

**[4] Xuezhi Wang, Jason Wei, et al. Self-Consistency Improves Chain of Thought Reasoning in Language Models. arXiv, 2022; ICLR, 2023.**

研究采样多条推理路径并聚合最终答案的方法。阅读时应区分任务表现提升与重复运行确定性。

原文：`https://arxiv.org/abs/2203.11171`

**[5] Xinyun Chen, Renat Aksitov, et al. Universal Self-Consistency for Large Language Model Generation. arXiv, 2023.**

利用语言模型选择多个候选中最一致的响应，将候选聚合思路扩展到自由文本任务。

原文：`https://arxiv.org/abs/2311.17311`

**[6] Karl Cobbe, Vineet Kosaraju, et al. Training Verifiers to Solve Math Word Problems. arXiv, 2021.**

在数学文字题中训练验证器、评估候选并选择解答，为生成与验证分离提供实验依据。

原文：`https://arxiv.org/abs/2110.14168`

**[7] Patrick Lewis, Ethan Perez, et al. Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks. NeurIPS, 2020.**

将参数化生成模型与检索知识结合，研究知识密集型 NLP 任务中的效果。

原文：`https://arxiv.org/abs/2005.11401`

**[8] Chuan Guo, Geoff Pleiss, Yu Sun, Kilian Q. Weinberger. On Calibration of Modern Neural Networks. ICML, 2017.**

讨论现代分类网络的概率校准与温度缩放。研究对象与开放式语言生成不同，迁移时需要重新定义评分与校准目标。

原文：`https://arxiv.org/abs/1706.04599`

**[9] Saurav Kadavath, Tom Conerly, et al. Language Models (Mostly) Know What They Know. arXiv, 2022.**

研究语言模型评估自身答案与知识边界的能力，讨论校准及跨任务推广的限制。

原文：`https://arxiv.org/abs/2207.05221`

**[10] Anastasios N. Angelopoulos, Stephen Bates. A Gentle Introduction to Conformal Prediction and Distribution-Free Uncertainty Quantification. arXiv, 2021.**

介绍共形预测及不确定性集合。本文核对版本最后修订于 2022 年，阅读时应重点理解边际覆盖与适用假设。

原文：`https://arxiv.org/abs/2107.07511`

如果目标是改善已有接口，建议先读 [1] 和 [3]；如果重点是推理质量，接着读 [4]、[5]、[6]；如果需要建立拒答与风险指标，再结合 [8]、[9]、[10]。每次引入方法，都应记录它实际改善的指标、增加的成本，以及仍未覆盖的失败场景。
