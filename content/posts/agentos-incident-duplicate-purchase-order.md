> 本文是一篇基于当前仓库 AgentOS 架构设计的故障推演，不是真实生产事故披露。业务背景、时间线、日志、订单号和处置过程均为模拟，用于说明设计约束缺失时可能出现的故障。文中的错误实现是假设场景，修复方案对应架构草案提出的稳定动作标识、结果未知与恢复核对机制，不代表这些后台能力已经交付。

## 一、事故现场：任务成功了，订单却多了一张

上午 10:12，采购人员在 ERP 中发现，同一条采购需求生成了两张订单：供应商相同、物料相同，数量都是 100 件，每张金额都是 20,000 元。

这条需求原本交给了采购 Agent。它读取需求、选择已有供应商、生成采购方案，在人工批准后调用 ERP 创建订单。AgentOS 的任务页面显示“已完成”，最终回复附带了一张有效订单的编号。

从这个页面看，业务似乎已经顺利结束。直到采购人员按需求编号查询 ERP，另一张订单才浮现出来。

打开执行记录，只能看到一个看似合理的过程：第一次工具调用超时，系统自动重试，第二次调用成功。

**事故的关键在于，第一次调用虽然超时，ERP 中的订单已经创建成功。** 恢复流程又创建了一张订单，而任务验收只检查了第二次返回的订单是否存在。

在这个模拟场景中，核对最终确认只有这一条需求受到影响，两张订单均未进入供应商履约。多出的 20,000 元代表重复采购的潜在承诺，不能直接记为已经发生的资金损失。事故的处置目标是冻结重复订单、保留正确订单，并确认没有其他超时任务存在相同问题。

## 二、事故前的系统：一条采购任务怎样执行

这套 AgentOS 沿用 Data OS、Agent OS、Agent Workforce 三层设计。采购数字员工承担业务目标，Data OS 提供需求、供应商和规则，AgentOS 负责把计划变成受控执行。

为了看清事故，只需要保留下面这条链路。

![采购任务执行链路：从业务需求、审批到工具网关和 ERP，并分别保存执行记录与订单事实](/blog-assets/agentos-incident/execution-chain.svg)

这里有三种容易混淆的身份。

| 对象 | 在案例中的含义 | 重试时是否变化 |
| --- | --- | --- |
| Task | 完成采购需求 PR-2048 的任务 | 不变 |
| Attempt | 创建订单节点的一次执行尝试 | 每次重试新建 |
| 逻辑业务动作 | 为这次已批准的采购方案创建订单 | 语义未变时不变 |

一个任务可以有多个业务动作，一个业务动作也可以经历多次技术尝试。把这两种数量混在一起，后面就会出现问题。

模拟实现中，工具网关已经记录请求参数、调用标识和返回结果，Worker 也支持从持久化状态恢复。开发者认为，失败的工具调用重新执行一次即可；为了便于追踪，每次尝试都会生成新的请求标识，并将它用作 ERP 的幂等键。

本文假设 ERP 支持按租户和幂等键去重：同一个键和相同参数再次提交，会返回原有结果。但它允许一条采购需求拆分为多张订单，所以不会仅凭需求编号拒绝第二次创建。

这意味着，外部系统具备去重能力，平台却没有给它一个能够跨重试保持不变的身份。

另外，AgentOS 的执行记录与 ERP 的订单分属两个存储边界。ERP 提交订单、本地保存成功回执，这两个动作没有共同的数据库事务。两者之间存在一个必须被恢复流程处理的间隙。

## 三、事故时间线：订单已经落库，成功响应没有回来

下面用相对时间还原事故，避免给模拟案例附上看似真实的发生日期。

| 时间 | 发生的事情 | 当时可确认的状态 |
| --- | --- | --- |
| T+0 秒 | 人工批准采购方案，任务开始执行 | 允许按批准参数创建一张订单 |
| T+1 秒 | Attempt A 发出创建请求，幂等键为 req-A | AgentOS 已记录请求发出 |
| T+2 秒 | ERP 提交订单 PO-7311 | ERP 中已存在订单 |
| T+11 秒 | 返回链路发生故障，调用方等待超时 | AgentOS 没有取得订单号 |
| T+12 秒 | 恢复逻辑把超时归类为可重试失败 | 本地记录为失败，外部结果未核对 |
| T+15 秒 | Attempt B 使用新键 req-B 再次提交 | ERP 识别为另一笔创建请求 |
| T+16 秒 | ERP 创建 PO-7312 并返回成功 | 同一需求关联两张订单 |
| T+17 秒 | AgentOS 保存 PO-7312，任务结束 | 本地只关联第二张订单 |
| T+12 分钟 | 采购人员查询需求，发现重复订单 | 业务核对暴露异常 |

![事故时序：ERP 第一次提交成功后响应丢失，AgentOS 使用新幂等键重试并创建第二张订单](/blog-assets/agentos-incident/incident-sequence.svg)

事故窗口出现在 T+2 秒到 T+11 秒之间。ERP 已经完成写入，AgentOS 却只能观察到请求没有按时返回。

超时描述的是调用方的等待结果。它没有证明请求是否到达、事务是否提交，也没有证明服务器是否仍在处理。如果直接把它写成“创建失败”，就把一段不确定的外部事实转换成了一个过于确定的本地判断。

这次事故也不要求 Worker 崩溃才会发生。普通的超时重试已经足够触发；如果 Worker 在收到响应后、保存结果前退出，同样需要面对“外部可能成功，本地没有回执”的恢复问题。

## 四、先止损：暂停自动写入，查清订单实际发生了什么

发现重复订单后，第一步是暂停受影响采购动作的自动重试，并拦截这些动作的新建订单派发。查询、核对和审计读取继续保留。已经发出的请求仍可能完成，所以开关生效后还要追踪在途调用。

随后，从异常动作扩展排查范围：查询同一适配器版本下发生过超时、Worker 接管或多次执行的创建订单任务。范围从可能引入错误策略的版本上线时间开始；如果无法确定起点，就扩大核对窗口，不能只查收到反馈后的十几分钟。

核对使用租户、采购需求、供应商、物料、数量、金额和执行时间定位候选订单，再用 ERP 的请求记录与业务关联字段确认。参数相同只能帮助筛选，不能单独证明重复，因为两笔合法采购也可能完全一样。

本案例中，两张订单都尚未进入履约。处置流程选择保留 PO-7311，并按 ERP 的撤销流程处理 PO-7312，同时更正 AgentOS 的任务关联。选择哪张订单必须结合实际流转状态，不能简单规定“永远删除后一张”。

如果订单已经被供应商接受或关联收货、发票，撤销就需要相应业务责任人判断。补偿动作本身也要有授权、执行记录和结果确认；直接修改 AgentOS 的任务状态无法撤回 ERP 中已经发生的事情。

止损结束的条件是：在途请求已核对、影响范围已确认、重复订单已处置或有人负责跟进。此时可以保留自动写入限制，继续完成根因修复。

## 五、排查：两次工具调用，对应同一个业务动作

排查从两个问题开始：Agent 是否规划了两次采购？运行时是否重复执行了同一次采购？

先查看计划和审批记录。计划中只有一个创建订单节点，审批也只批准了采购 100 件物料。模型执行记录里没有第二个独立采购决策。第二次请求来自运行时的超时恢复分支。

再把工具网关记录与 ERP 请求记录按调用标识连接起来，得到下面这组简化证据。

```text
# 以下为模拟日志；ERP 与网关记录经事后关联后并列展示
10:00:01 gateway task=T-2048 attempt=A call=C-A
         demand=PR-2048 idempotency_key=req-A event=request_sent
10:00:02 erp     request=req-A order=PO-7311 event=committed
10:00:11 gateway call=C-A error=read_timeout state=failed
10:00:15 gateway task=T-2048 attempt=B call=C-B
         demand=PR-2048 idempotency_key=req-B event=request_sent
10:00:16 erp     request=req-B order=PO-7312 event=committed
10:00:17 runtime task=T-2048 state=completed order=PO-7312
```

日志显示，第一次超时前 ERP 就已提交 PO-7311。两次请求具有不同的幂等键，却指向同一计划节点和同一份批准参数。这个组合把问题定位到了业务动作身份和恢复策略。

原来的监控为什么没有提前报警？因为工具层的一次超时被后续成功覆盖，任务指标只记录最终完成；验收程序则读取 PO-7312，确认其供应商、数量和金额正确后就通过了。

这些检查能够证明返回的订单有效，却没有证明这次动作只产生了预期的一张订单。

追踪系统因此需要保留 `task_id`、逻辑动作标识、`attempt_id`、`tool_call_id`、审批引用和外部业务编号之间的关联。一条 Trace 能帮助还原请求路径，但业务动作可能跨多次恢复和多条 Trace，稳定的业务关联仍然需要单独保存。

## 六、根因：恢复流程丢失了业务动作的身份

网络故障触发了事故，真正允许重复采购发生的是四个设计缺口。

**第一，状态模型把结果未知压缩成了失败。** 超时之后，系统立即进入通用重试分支，没有留下等待外部核对的状态。

**第二，幂等键绑定了 Attempt。** 每次技术尝试都创建新键，ERP 正确地把它们当成不同请求处理。只要重试就换键，幂等接口就无法帮助识别重复业务动作。

**第三，恢复依据只有本地步骤状态。** 本地找不到成功结果，就从创建订单步骤重新开始，没有先确认 ERP 是否已完成写入。

**第四，任务验收只检查成功回执。** 在本案例“批准生成一张订单”的约束下，还应该确认需求与订单的对应关系，并阻止未核对的动作直接进入完成状态。

四个缺口组成了完整因果链：响应丢失 → 本地判失败 → 更换键重试 → 外部再次写入 → 第二次成功掩盖第一次副作用。

把超时从 10 秒改成 30 秒只能改变触发概率；增加退避可以减轻压力，也不能改变请求的业务身份。修复必须落到动作标识、状态迁移和外部确认契约上。

## 七、修复：把“重跑一步”改成“恢复一个业务动作”

### 7.1 为已批准动作保存稳定身份

任务计划确定创建订单动作后，平台为其分配 `logical_action_id`，在首次派发前持久化。它不由模型在每次恢复时重新生成。

```text
action_key = tenant_id + task_id + logical_action_id

Attempt A → action_key=tenant-7:T-2048:create-order-1
Attempt B → action_key=tenant-7:T-2048:create-order-1
```

实际实现需要使用无歧义编码。参数摘要另行保存，并规范化币种、数量和明细字段。同一个键携带不同参数时应拒绝执行，而不是覆盖原记录。

动作记录还应关联审批版本、外部订单号和执行状态。技术重试改变 Attempt，保持动作键和批准参数不变。

这只能约束同一逻辑动作的重复执行。如果用户重复提交需求，产生了两个 Task，还需要入口幂等或业务唯一性规则。本案例允许真实的拆单业务，因此不能粗暴地给需求编号加上“只能有一张订单”的全局约束。

### 7.2 增加结果未知与查询确认路径

![修复后的动作状态：执行中遇到超时进入结果未知，查询确认后成功、安全重试或转人工核对](/blog-assets/agentos-incident/recovery-state.svg)

写入超时、连接中断，或者恢复时发现已发出请求却没有最终回执，都应进入 `outcome_unknown`。依赖该结果的后续写操作暂停，任务页面显示“执行结果待确认”。

恢复程序按稳定动作键查询 ERP。确认已经成功，就保存原订单号并继续验收；确认仍在执行，就继续等待并查询；无法确认，就保留未知状态并转人工核对。

**一次“查询无结果”不等于“确定未执行”。** 查询可能存在可见性延迟，原请求也可能仍在处理。只有源系统能够保证同键并发去重，并且仍处于约定的幂等有效期内，或能够提供足以排除迟到提交的未执行证明，才可以按契约重新提交。

本案例选择复用 ERP 的同键去重能力，但必须验证它覆盖并发请求、参数冲突和恢复时间窗口。仅仅看到接口文档中有一个“幂等键”字段还不够。

### 7.3 把恢复能力写入工具契约

创建订单工具除了参数 Schema，还要声明下面这些能力。

| 契约项 | 必须明确的问题 |
| --- | --- |
| 幂等范围 | 按哪个租户、动作和键去重，是否覆盖并发请求 |
| 保留时间 | 幂等记录保存多久，过期后如何核对 |
| 结果查询 | 能否按动作键查回执，查询是否有可见性延迟 |
| 错误语义 | 哪些错误确定未写入，哪些属于结果未知 |
| 补偿能力 | 什么阶段可撤销，谁授权，如何确认撤销结果 |

如果 ERP 没有幂等能力，平台内部的唯一键只能拦截平台已知的重复派发，无法填补外部提交后本地崩溃的窗口。此时需要源系统提供稳定业务编号查询、唯一性约束等支持；能力不足时，自动恢复停在人工核对。

### 7.4 约束并发接管、审批和完成条件

Worker 接管时使用租约与版本条件更新，工具网关在派发前验证有效执行权，降低两个 Worker 同时推进同一动作的风险。但已经送达 ERP 的旧请求仍可能完成，所以这层控制必须与外部幂等共同工作。

动作意图要在请求发出前持久化。恢复时保留原动作键，补查回执；本地状态更新也不能让迟到的超时处理覆盖已经确认的成功。事件与派发的一致性需要持久化派发记录等机制配合，但这些机制同样不能替代 ERP 端的去重。

审批绑定具体动作和参数摘要。若恢复过程中改了供应商、数量或金额，就要创建新的动作版本并重新判断授权；执行新版本前，还必须核对旧动作，避免旧采购已经成功后又追加一笔。

最后，验收根据本次批准的采购方案检查订单归属、参数和预期数量。只有外部事实已确认、异常已处理，任务才能进入完成状态。

## 八、验证：在最容易重复下单的位置主动制造故障

修复验收不能只运行一次正常采购。应在测试环境使用可控的 ERP 模拟服务注入故障，再在集成环境验证真实 ERP 的幂等和查询契约。下面是建议的验收用例，不是本文已执行的测试报告。

| 故障注入 | 预期行为 | 关键断言 |
| --- | --- | --- |
| ERP 提交后丢弃响应 | 进入未知状态，查回原订单 | 同一动作仍只有一个订单 |
| 收到成功后、本地保存前终止 Worker | 接管后按原动作键恢复 | 关联原订单，保持原审批引用 |
| 重复投递任务或并发接管 | 平台拦截重复派发，外部同键去重 | 不产生第二个业务副作用 |
| 查询短暂返回无结果 | 保持未知，按契约等待或同键恢复 | 不因一次空结果换键重试 |
| 原请求在超时后才提交 | 查询与重提仍遵循同键契约 | 迟到提交不产生额外订单 |
| 重试时改变采购数量 | 检测参数冲突 | 不沿用旧审批直接执行 |
| 超过幂等有效期仍无法确认 | 转人工核对 | 不自动创建新订单 |

断言需要同时查看 AgentOS 的动作记录与 ERP 的订单事实。只验证“任务最终成功”，仍然可能让同样的错误通过测试。

观测指标也应补上结果未知动作的数量、滞留时间、核对完成时长和业务差异数量。按适配器和版本聚合指标，具体任务与动作标识放在可检索的事件记录中。未知状态不是坏数据，它是需要被持续处理的真实运行状态。

整改可以按责任落地：运行时负责状态与恢复路径，工具平台负责能力契约和动作键传递，ERP 集成负责核验源系统去重保证，业务负责人负责补偿规则和验收标准。每项整改都应附上可重现的故障用例及通过条件。

恢复自动写入前，要完成存量未知动作核对、关键故障用例验证，再按受控范围逐步放开。若业务差异重新出现，就暂停扩大范围，保留核对通道。

这次推演最终留下一个具体的设计要求：当 AgentOS 在超时后继续任务时，它必须能回答，上一笔采购是否已经发生，证据在哪里，以及接下来的执行为何不会再创建一张订单。
