假设我们要让一组智能体修复一个线上缺陷：同一个业务请求重试后，系统偶尔生成两条工单。

分析智能体检查调用链，实现智能体修改代码，测试智能体构造并发场景，审查智能体判断补丁是否符合接口约定。分工看起来很合理，但很快就出现三个问题：分析智能体把问题归因于调用方重试，测试智能体却在单次调用中复现了重复创建；实现智能体仍然使用旧版接口文档；两个智能体同时修改了同一个模块。

此时，再增加一个“负责协调的智能体”还不足以说明系统该如何工作。我们需要明确：谁有资格接手任务，哪些信息必须随任务交接，不同结论如何核验，并发修改如何提交，以及什么时候应该停止尝试。

**本文设计的协作网络，以任务契约组织分工，以版本化状态传递上下文，以可核验证据和提交协议处理冲突。** 路由、共享与消解通过同一条执行闭环连接起来。

本文面向基于大语言模型的多智能体系统，适用于研发协作、研究分析以及需要工具执行的复杂任务。文献核验日期为 **2026 年 10 月 22 日**。研究依据以文末编号标注；架构、字段、评分公式和执行流程是本文综合提出的参考设计，未经本文独立基准测试。案例与配置值均用于解释机制。

## 一、先定义成功，再决定如何分工

### 1.1 复杂任务的难点在依赖关系中

在本文的任务模型里，一个复杂任务至少包含部分这样的特征：需要跨领域知识，存在多个相互依赖的步骤，中间结论可能被新证据推翻，最终结果需要通过测试或外部事实核验。

因此，任务是否完成不能仅由最后一个智能体宣布。对于重复工单问题，我们需要先约定可检查的验收条件：相同业务请求的并发提交只产生一个有效工单；响应丢失后的重试可以定位原结果；不同业务请求仍然可以分别创建工单；接口行为保持在约定范围内。

验收条件决定了后续要找什么证据、安排什么角色、执行什么测试。缺少它，路由器只能根据“看起来像后端问题”挑选角色，审查器也只能评价答案是否有说服力。

MAST 研究将观察到的失败模式归入系统设计、智能体间失配和任务验证等类别。[1] 这为本文提供了一个分析起点：诊断失败时，应检查任务是否被定义清楚、交接是否失真、验证是否真正发生，不能把所有问题都归结为模型能力不足。

### 1.2 为多智能体执行设置准入条件

本文建议在任务入口设置一次轻量判断：是否存在能够独立推进的工作，是否需要不同工具或权限，是否值得保留独立判断，以及预期收益是否足以覆盖协调成本。

例如，调用链调查与并发测试设计可以同时推进；修改补丁与验证最终补丁则存在先后依赖。对于流程固定的格式转换，直接使用确定性的程序或工作流即可。对于范围很小的代码修改，保留一个执行智能体和必要的检查也可能足够。

这一步的输出是执行模式，而不是预设一个固定规模的团队。本文的路由空间包含单智能体、串行协作、并行调查与执行后审查等模式，允许任务在运行中改变模式。

### 1.3 将质量、成本与时延同时写入目标

一个可执行的目标可以表述为：在权限、费用和截止时间约束下，提高满足验收标准的概率。

成本统计要包含规划、检索、上下文准备、执行、核验和失败重试。时延统计则覆盖从接收任务到最终交付的整个区间。并行执行时，多个任务的耗时不能简单相加；应结合依赖链、排队和可用容量计算完成时间。

本文同时设置两个不可被评分抵消的边界：权限不足时不派发；验收未通过时不标记成功。高分、低价或高自报置信度，都不能越过这两条边界。

## 二、总体架构：任务图、协作图与共享状态

### 2.1 三种对象分别表达什么

**任务图表达“工作如何依赖”。** 节点是具有输入、输出和验收条件的子任务，边表示前置条件。一次调度使用一个明确版本的有向无环图；发现新问题后，可以追加调查任务并形成新版本，避免在原图中不断添加无法终止的回边。

**协作图表达“执行者如何通信”。** 节点是智能体实例，边表示允许发生的消息交接或状态订阅。角色描述职责，实例承担一次具体执行，同一个角色可以由不同模型和工具组合实现。

**共享状态表达“目前已记录什么、认可什么”。** 它保存任务状态、证据索引、候选结论、版本信息与未解决的冲突。本文将模型生成的结论先记录为主张；是否被采纳由后续核验决定。

此外，系统记录产物的派生关系：某份测试报告验证哪个补丁，某个补丁依据哪些接口和证据。这组关系支持失效传播，不能完全由任务图替代。

### 2.2 一个可实施的参考架构

```text
用户目标、约束、验收条件
          │
          ▼
规划器 ──► 任务图与调度器 ◄──► 能力注册表、预算账本
                │
                ▼
             路由决策
                │
                ▼
           上下文装配服务
                │
      ┌─────────┼─────────┐
      ▼         ▼         ▼
   分析实例   实现实例   测试实例
      └─────────┼─────────┘
                ▼
           候选结果与产物
                │
                ▼
       验证器、冲突处理器
                │
          条件提交或补充任务
                │
                ▼
       共享状态与持久事件记录
                │
       通知依赖任务、重新调度

贯穿执行：权限校验、版本校验、工具调用记录、资源计量
```

这些是逻辑组件，不要求一开始就部署为多个服务。最小实现可以使用一个调度进程、一组执行进程、关系数据库和产物存储。模型负责需要语义判断的步骤，程序负责状态迁移、预算预留、权限检查和版本比较。

尤其不能把“模型给出的下一步计划”直接当作调度器状态。计划是一项提议，调度器只有在检查依赖、权限与预算后，才能将其转化为可执行任务。

### 2.3 为什么选择分层调度与按需通信

本文采用任务级协调者管理依赖和预算，执行者按授权并行推进，跨任务的产物与证据通过共享状态交接。

与完全中心化的消息转发相比，这种结构允许执行者按引用读取大体量资料；与完全去中心化的协商相比，它保留了可定位的任务所有权和终止责任。代价是必须认真处理调度器恢复以及共享状态的可用性。

对于 n 个智能体，如果每一轮都让每个智能体向其余所有智能体发送一条消息，该轮有向消息数为 n(n−1)。这只是给定通信规则下的数量关系，实际 token 成本还取决于消息长度和历史是否被重复附带。

AgentPrune 将通信表示为时空消息传递图，并研究裁剪冗余通信。[3] 本文据此把通信关系视为需要评估的设计变量，但不直接复用其裁剪算法：只有任务依赖、证据需求或冲突处理需要某条通信边时，才建立相应交接。

## 三、路由分发：从匹配角色到选择可执行方案

### 3.1 先有任务契约，再谈匹配能力

“调查重复工单问题”仍然过于宽泛。下面给出一个简化的任务契约，数值仅作示例：

```json
{
  "task_id": "repair-042/diagnose",
  "graph_revision": 3,
  "goal": "定位相同业务请求产生重复工单的条件",
  "required_capabilities": ["code_search", "trace_analysis"],
  "required_permissions": ["repo:read", "trace:read:redacted"],
  "depends_on": ["repair-042/scope"],
  "input_refs": ["incident:042@v2", "repo:commit-a1"],
  "acceptance": [
    "提供可定位到代码或日志的证据",
    "区分已验证事实与待验证假设",
    "给出可以区分候选根因的验证方法"
  ],
  "output_schema": "diagnosis.v1",
  "max_attempts": 2,
  "budget": {"total_tokens": 12000, "wall_time_seconds": 180}
}
```

契约中，目标解释任务意义，能力与权限限定候选者，输入引用约束分析对象，验收条件决定结果能否进入下一步。输出结构还应约定证据引用、未知项与失败原因，使接收者能够明确区分“发现问题”和“已经证明问题”。

工具权限由执行平台检查，不能仅靠提示词要求智能体自律。实例是否能读取某份资料，取决于其实际授权以及资料范围，而不是它声明自己扮演什么角色。

### 3.2 能力注册表需要记录可验证信息

本文建议把注册信息分成四组：职责与领域、可调用工具、实际权限、运行表现。运行表现包括按任务类别统计的验收通过率、常见失败原因、时延、成本和当前负载。

“擅长数据库”只能作为召回候选者的标签。真正影响派发的，应当包括它是否可以访问目标数据库的脱敏元信息，是否具备对应工具，以及在相近任务上完成过什么可核验工作。

历史通过率还需要保留样本量和任务难度分布。一个只处理过五个简单任务的实例，不能因为全部通过，就被当作比长期处理困难任务的实例更可靠。没有足够历史时，使用保守先验或明确规则，并标记估计不确定性。

### 3.3 分四层做出决策

MasRouter 将协作模式、角色分配和模型选择组织为级联决策。[2] 本文沿用这一问题分解思路，并增加运行时实例与状态约束：

| 决策层 | 需要回答的问题 | 案例中的选择 |
| --- | --- | --- |
| 协作模式 | 这一步适合独立执行还是多方协作 | 两路独立调查，之后统一核验 |
| 角色组合 | 需要哪些职责和工具 | 调用链分析、并发测试 |
| 实例与模型 | 哪个候选具备权限、容量和合适能力 | 从可用池中选择实例及模型 |
| 执行上下文 | 接手前需要哪些资料与版本 | 事件说明、目标提交、相关日志 |

最后一层会反过来影响前面的决策。如果某候选者虽然能力很强，却无法访问关键资料，就应被过滤；如果接手需要重新加载大量背景，则应把交接成本纳入比较。

### 3.4 先过滤硬约束，再比较预期价值

一个便于解释的起点是：

```text
候选集 = 满足能力、授权、数据范围和可用容量的执行方案

score(a, t, s)
  = wq × 预估验收通过率
  − wc × 归一化预估成本
  − wl × 归一化预估完成时延
  − wh × 归一化上下文交接成本
  − wr × 归一化失败后恢复代价
```

这里的 a 是包含角色、实例、模型和上下文准备方式的执行方案；t 是任务；s 是当前系统状态。这是本文的启发式设计，不是对 MasRouter 公式的转述，也不构成最优性保证。

各项需要统一尺度，并根据任务优先级校准权重。通过率来自历史评估或专门预测器，不能直接替换为模型说出的“我有 95% 把握”。计算成本时还要避免把同一笔上下文费用重复计入多个项。

对于任务图，局部最高分不一定带来最好的整体完成时间。本文建议优先处理关键依赖链上的任务，并为稀缺工具保留容量。例如，不能让多个非关键调查占满测试环境，导致最终验收一直等待。

### 3.5 路由之后还需要接单与恢复协议

派发时，调度器先预留预算，再以条件更新领取任务，记录实例、尝试编号、租约与递增的执行代次。实例可以报告三类结果：接受、缺少输入、能力或权限不满足。

缺少输入应触发补充资料；能力不足才需要重新选择执行者。若每次上下文缺失都换一个智能体，团队只是在重复支付接手成本。

运行中区分工具暂时不可用、输出结构错误、任务理解偏差和证据不足。恢复动作可以分别是有限重试、结构修复、重新澄清任务契约、追加核验任务。每次重试都要消耗任务级预算，并共享整个任务树的尝试上限。

智能体超时后，调度器也不能立即假定它停止运行。新的执行代次需要让旧实例失去提交权限；涉及外部动作时，还需要工具侧配合去重或拒绝过期写入。这些约束在第五章进一步展开。

## 四、上下文共享：传递足够信息，并保留信息的来历

### 4.1 共享对象要有明确的生命周期

本文把上下文相关对象分为五类，并为它们设置不同的共享方式：

| 对象 | 内容 | 共享策略 |
| --- | --- | --- |
| 任务契约 | 目标、约束、验收条件 | 发给承担相关子任务的每个实例 |
| 执行状态 | 任务状态、所有权、预算、版本 | 从权威状态服务读取 |
| 证据与产物 | 日志、文档、代码、测试结果 | 保存不可变引用，按需获取 |
| 局部工作记录 | 当前探索摘要、候选假设、工具进度 | 默认局部保留，交接时提取必要部分 |
| 跨任务经验 | 适用条件、处理步骤、验证结果 | 审核后入库，检索时检查适用性 |

局部记录不要求保存或广播模型内部的完整推理过程。任务交接需要的是可检查的结论摘要、依据、已经做过的操作和未解决问题。

G-Memory 使用 insight、query 和 interaction 三层图组织协作经验，并通过检索关联较高层次的经验与交互轨迹。[4] 本文借鉴的是“经验应能追溯到具体任务与证据”的组织思路，不把跨任务记忆等同于实时共享状态，也不认为引入图存储就自动解决并发一致性。

### 4.2 共享存储与进入模型窗口是两件事

即使多个智能体能够读取同一个存储，它们也未必在本轮输入中看到同一条信息。因此，系统需要一个上下文装配步骤，把可访问的资料转换成本次任务实际使用的输入。

本文采用这样的流程：先根据任务与身份过滤资料，再按依赖关系取回必要对象，随后检索补充证据，最后在 token 预算内选择或压缩内容。权限过滤发生在召回和内容装配阶段，而不是把越权资料放入提示词后要求模型忽略。

对于任务硬约束、接口定义和当前未决冲突，设置必须保留的内容。日志和大型文档可以使用片段，但要携带来源定位及版本；摘要保留回到原文的路径。若必须内容已经超过预算，应调整任务粒度或执行方案，不能静默丢掉验收条件。

### 4.3 一个可交接的上下文包

```json
{
  "context_id": "ctx-042-07",
  "task_id": "repair-042/implement",
  "contract_revision": 3,
  "read_set": [
    {"ref": "api:create-ticket", "version": 5},
    {"ref": "claim:root-cause", "version": 4}
  ],
  "repo_commit": "commit-a1",
  "accepted_facts": [
    {
      "claim_id": "claim-23",
      "summary": "并发测试已复现重复创建",
      "evidence_refs": ["artifact:run-17/log", "artifact:run-17/test"]
    }
  ],
  "open_conflicts": ["conflict:request-key-scope"],
  "constraints": ["保持已确认的响应契约"],
  "requested_output": "patch-with-verification.v1",
  "access_scope": "project:ticket-service"
}
```

这里使用对象级版本集合描述读到了什么。一次全局事件编号可以帮助定位处理进度，但它并不自动证明模型实际读取了哪些对象，也不保证外部工具数据与内部状态处于同一快照。

对于外部系统的读取，补充查询时间、对象版本或 ETag；对于代码与测试产物，记录内容哈希或提交标识。无法固定版本的来源，需要标记其可变性，并在提交前重新核验关键条件。

### 4.4 优先压缩重复信息，谨慎压缩约束和分歧

假设资料里有两条记录：“旧接口文档要求按用户去重”和“当前实现按租户与请求标识去重”。摘要不能把它们压缩成“接口已经支持去重”。后一种写法抹掉了差异，也让下游失去发现问题的机会。

本文为摘要要求四类信息：当前认可的事实、仍待验证的主张、发生过的变更、尚未消解的冲突。每一条关键事实都应能返回证据引用；摘要只作为读取优化，原始证据仍然保存。

资料过期也需要沿派生关系传播。接口从 v5 更新到 v6 后，系统把依赖 v5 的补丁或报告标记为“需要复核”，根据实际变更范围决定重新执行哪些检查。并非任何版本变化都必须重跑全部任务，但不能在没有检查的情况下继续把旧验证当作有效。

### 4.5 为不同数据选择不同的一致性要求

本文建议对任务领取、共享预算扣减和结果采纳使用原子状态更新；证据上传采用不可变对象加元数据登记；搜索索引和非关键通知允许异步更新，但消费者处理前仍要回查权威版本。

这样，向量检索可以帮助找到相似资料，却不承担“这个任务现在归谁”或“预算是否还足够”的裁决职责。

从计算机体系结构视角讨论多智能体记忆的论文，将共享与分布式记忆、缓存共享和访问控制列为关键问题，并强调一致性挑战。[5] 它是一篇立场性论文。本文提出的对象版本、读集和失效传播属于工程设计选择，不是该论文已经验证的通用实现。

## 五、冲突消解：先识别冲突对象，再选择处理机制

### 5.1 四种冲突不能使用同一种办法

| 冲突类型 | 典型表现 | 本文采用的处理方向 |
| --- | --- | --- |
| 事实或证据冲突 | 两个实例对根因、接口含义给出不同判断 | 比较证据范围，设计区分性验证 |
| 方案或目标冲突 | 一个方案优先快速恢复，另一个优先彻底重构 | 按明确约束与目标比较，必要时由目标所有者决策 |
| 状态或产物冲突 | 两个实例修改同一对象，或基于旧版本提交 | 对象版本校验、三方合并、重新验证 |
| 资源或动作冲突 | 重复创建资源、并发占用同一测试环境 | 租约、执行代次、幂等协议与资源调度 |

事实冲突适合补充证据，版本冲突适合提交协议。让模型讨论哪份过期修改“更合理”，并不能替代对文件基线和实际变更的检查。

系统也需要先排除假冲突。例如“旧版本存在重复创建”和“新版本未复现”可能同时成立。判断冲突时，必须比较同一对象、相同时间或版本、相同条件下的主张。

### 5.2 把分歧变成结构化对象

本文建议把主张与冲突分别存储。主张包含对象、范围、内容、证据与状态；冲突引用多个主张，并记录影响范围和处理动作。

```json
{
  "conflict_id": "conflict-042-03",
  "kind": "evidence_disagreement",
  "subject": "duplicate-ticket/root-cause",
  "scope": {"repo_commit": "commit-a1"},
  "claim_refs": ["claim:retry-only", "claim:concurrent-insert"],
  "evidence_refs": ["trace:batch-07", "artifact:run-17/log"],
  "affected_tasks": ["repair-042/implement"],
  "status": "needs_verification",
  "next_action": "reproduce_single_request_concurrency"
}
```

结构化记录让冲突能够被检索、分配和追踪。冲突消解后也保留原始主张与裁决依据，防止后续无法解释某个结论为何改变。

StateFuse 在标准 OpSet/CRDT 合并基础上研究面向智能体的冲突保留、不可变历史和读取时解析。[8] 其论文明确限制了结果范围：主要证据支持冲突可见性、弃答和可审计纠正，不能据此宣称普遍提高答案准确率。

因此，本文只借鉴“不要在记录层提前抹掉争议”的原则。存储收敛描述多个副本如何得到一致记录；哪条业务主张正确，仍然要通过证据或规则判断。

### 5.3 用区分性验证处理事实争议

面对两个候选根因，先把各自可检验的预测写出来：

- 若问题只来自调用方重试，那么单次请求中不应出现重复创建。
- 若服务内部存在并发检查与写入窗口，那么受控并发可能在没有调用方重试时复现问题。

这两条预测告诉测试智能体应该构造什么实验。系统可以同时保留两个解释，直到新的日志或测试缩小范围。

多智能体辩论的早期研究报告了在部分推理与事实性任务上的收益。[6] 后续《Debate or Vote》在其评估设置中发现，多数投票能够解释大量收益。[7] 本文据此把讨论设计为有界步骤：先独立形成判断，再交换证据，必要时追加验证；没有新的区分性信息时停止重复讨论。

投票可以帮助选择候选答案，但本文不允许它覆盖失败的测试或越过任务硬约束。多个角色如果共享同一条错误资料，增加票数并不会给出新的证据。

对于只能依靠专家判断的开放问题，保留评价标准、不同方案的代价和未决条件。如果关键目标冲突缺少授权范围内的决策依据，就把具体争议交回目标所有者，并让不受影响的任务继续执行。

### 5.4 用条件提交处理共享状态冲突

设两个实例都读取了对象 v12，并分别提出变更。本文采用“读取版本 + 候选变更 + 条件提交”的协议：只有当前对象版本仍满足前置条件，候选变更才可以被采纳。

实现时，版本比较与更新必须在同一个原子操作中完成。先查询版本、再无条件更新，中间仍然可能插入其他写入。涉及多个对象的不变量时，还要在合适的事务中统一检查；不能只保护其中一行。

PostgreSQL 的事务隔离文档说明，不同隔离级别提供不同保证，并要求应用正确处理相应的并发失败与重试。[9] 本文的条件提交需要在所选数据库与隔离设置下实现，不能仅凭“使用事务”就假定所有读取条件都会保持有效。

冲突之后按数据语义处理：追加证据可以保留多个版本；局部且互不影响的修改可以尝试合并；修改同一行为的补丁则必须重新分析并验证。代码的文本合并成功，也不等于组合后的行为正确。

### 5.5 租约到期以后，旧执行者必须失去写入资格

任务租约解决的是“在一定时间内把任务分配给谁”。它不能保证超时实例已经停止。网络恢复后，旧实例仍可能提交结果或继续调用工具。

本文在每次重新领取任务时增加执行代次，例如从 7 增加到 8。状态服务只接受当前代次的提交；如果外部资源支持 fencing token，也将代次传递给资源端，由真正接受写入的一方拒绝过期操作。

只在协调者内存中检查代次是不够的。外部动作在检查之后仍可能延迟执行，因此需要资源端能够执行的约束，或使用具备等价保护的工具网关和业务协议。无法提供这种保护时，就必须显式承认动作可能处于未知状态。

### 5.6 超时重试需要业务幂等协议

假设创建工单的请求已成功，但响应在网络中丢失。执行者看见的是超时，业务系统中却可能已经有了工单。直接再次创建可能重复执行动作。

AWS 关于幂等 API 的工程文档讨论了用调用方提供的请求标识表达意图，以及迟到请求和相同标识不同意图等问题。[10] 本文据此要求：同一个逻辑动作跨重试复用幂等标识，执行端检查作用域与参数一致性，并能够返回既有结果或明确的处理中状态。

幂等标识不应随尝试编号变化；两个真正不同的业务动作也不能复用同一个标识。执行端还需要定义去重记录的保留时间，以及记录过期后的行为。

对于不支持幂等或结果查询的外部工具，响应丢失后先进入“动作结果未知”状态。系统尝试对账或人工确认，在确定安全恢复方式前阻止有风险的再次执行。内部事件日志无法替外部系统承诺恰好一次执行。

## 六、把三类机制连接成一条执行闭环

### 6.1 区分任务状态与外部动作状态

本文使用以下简化任务状态机：

```text
等待依赖 ──► 可调度 ──► 已领取 ──► 执行中 ──► 待核验 ──► 已完成
                ▲          │           │          │
                │          └─租约失效──┘          ├─输入变化──► 待复核
                │                                 ├─证据不足──► 等待补充
                └────────预算允许且满足恢复条件─────┘

任何非终态均可按规则进入：失败、取消、需要外部决策
```

外部工具调用另有自己的状态：尚未发出、已发出、成功、明确失败、结果未知。任务超时不直接把已发出的动作改成失败；任务取消也不等于撤销已产生的外部效果。

任务图推进时，只有“已完成且验证仍有效”的前置节点才能解锁下游。若上游证据被撤回，则根据派生关系对下游执行选择性复核。

### 6.2 调度与提交的关键步骤

下面是协议级伪代码，用来表达事务边界，不是可以直接部署的实现：

```text
dispatch(task):
    检查任务依赖、截止时间和取消状态
    按硬约束过滤候选执行方案
    估算上下文准备成本并选择候选

    原子操作：
        确认任务仍可领取
        预留预算和必要容量
        增加执行代次，写入所有权与租约

    装配带来源、权限范围和版本读集的上下文
    派发当前代次；若失败，按恢复规则释放或结算预留

submit(task, attempt, candidate):
    将候选产物保存为不可变对象
    核验输出结构、证据引用及验收条件
    对候选产物哈希生成验证记录

    原子操作：
        确认任务未取消，提交代次仍有效
        检查所依赖对象的版本及前置条件
        确认验证记录对应待采纳产物
        采纳结果，更新任务状态，结算预算
        写入待发布事件

    异步发布事件；消费者按事件标识去重
```

模型核验和工具执行可能耗时较长，不应把数据库事务一直保持到它们结束。因此，本文先执行核验，再在短事务中重查前置条件。若核验期间关键输入发生变化，结果进入复核流程。

这也意味着“验证通过”必须绑定到具体产物。补丁又改了一行后，之前的测试报告不能自动成为新补丁的验收证明。

### 6.3 消息用于通知，状态用于决定

本文采用至少一次事件投递作为可恢复的设计起点，并要求消费者能够处理重复消息。事件通知“某个结果已提交”，消费者处理时读取权威状态，确认该结果仍有效。

任务状态更新与待发布事件在同一事务中记录，随后由发布进程转发。这样可以避免状态已完成但通知因进程退出而丢失。这个设计仍然需要消费去重、重放与失败队列，不能把消息系统接入本身当作恢复能力。

协调者恢复后，从持久任务状态、租约和工具调用记录继续推进：尚未执行的任务可以重新领取；结果未知的外部动作先核对；已经提交的候选不会因重复通知再次结算预算。

### 6.4 三个反馈关系形成闭环

**上下文影响路由。** 某候选者缺少访问权限，或交接成本过高，会改变任务分配。

**冲突影响任务图。** 证据分歧会生成新的核验任务，并阻止依赖争议结论的步骤进入提交。

**验证改变共享状态。** 被证实或被推翻的主张更新采纳状态，触发下游复核，也为后续路由提供可统计的运行表现。

这三个反馈关系必须同时受到预算和终止条件约束。否则，系统会不断发现需要更多信息的理由，却无法在可接受时间内交付结果。

## 七、贯穿案例：修复并发创建导致的重复工单

以下过程是按本文机制推演的示例，不代表已经对某个真实仓库完成修复或测得性能提升。

### 7.1 把验收条件转化为任务图

首先固定目标代码版本、接口约定、日志范围和复现条件。规划器生成三条初始分支：调用链调查、接口与数据约束检查、并发复现设计。

这些任务都使用同一版任务契约，但获得不同的上下文包。分析实例读取调用链与相关代码；测试实例读取接口约束和测试环境；接口检查实例核对请求标识的业务范围。

实现任务等待“可复现条件”和“已确认接口约束”就绪，再产生候选补丁。最终审查依赖补丁、针对该补丁的测试报告以及行为变化说明。

### 7.2 第一次分歧触发补充验证

分析实例提出“调用方重试导致重复”，测试实例提交“一次入口调用触发两次并发内部创建”的记录。冲突处理器先检查它们是否讨论同一代码版本和请求范围，再生成区分性测试。

测试在受控并发下观察到两个执行路径都先检查“记录不存在”，随后都执行插入。该结果支持调查检查与写入之间的竞争窗口，但仍需排除测试本身重复发送请求等干扰。

在证据完成核验后，系统采纳相应根因说明，并保留先前关于重试的主张，因为重试仍然可能是另一条触发路径。

### 7.3 过期上下文阻止错误补丁提交

实现实例准备按旧接口说明生成请求标识。提交时，读集显示它依赖接口 v4，而当前任务契约已采用 v5，其中明确了租户范围。

系统把候选补丁转入复核，不允许它直接解锁最终验收。上下文服务提供 v4 到 v5 的相关差异，实现实例只需重新检查受影响逻辑，而无需重读全部日志。

由此可以看到，过期检测发生在状态提交边界；模型是否主动记住“资料可能更新”，不再是唯一防线。

### 7.4 两个补丁合并后重新验证组合行为

实现实例修改创建流程，另一个被授权的修复实例调整重试行为。即使两份补丁可以无文本冲突合并，也要在合并后的代码上验证请求标识是否保持稳定、错误分支是否重复触发动作。

测试设计覆盖相同请求的并发提交、成功后响应丢失再重试、不同请求分别创建，以及相同标识携带不同参数的处理。具体唯一性约束和事务范围需要根据业务定义决定，这里不把某一种数据库索引视为所有系统的通用补丁。

最终交付包含采纳的补丁哈希、对应测试结果、验证过的环境范围、仍然存在的限制和恢复说明。任务只有在这些材料对应同一产物时才能完成。

### 7.5 用一条交互时序串起整个过程

```text
协调者       分析/测试实例      上下文服务       验证与状态服务
  │ 派发独立调查  │                │                 │
  ├─────────────►│ 获取版本化资料  │                 │
  │              ├───────────────►│                 │
  │              │ 提交不同主张与证据                │
  │              ├─────────────────────────────────►│
  │◄───────────────────────────────产生区分性核验任务┤
  │ 派发补充验证  │                │                 │
  ├─────────────►│─────────────────────────────────►│
  │◄────────────────────────────────────采纳根因记录┤
  │ 派发实现与审查，提交候选补丁                      │
  ├────────────────────────────────────────────────►│
  │◄──────────────────────────检查读集、产物哈希和测试┤
  │ 输入过期则复核；验证有效则条件提交                 │
  └────────────────────────────────────────────────►│
```

## 八、评估方案：在相同资源条件下判断是否值得协作

### 8.1 对照实验要控制什么

本文建议至少包含四组：使用相同工具的单智能体；固定角色与固定流程的多智能体；允许全量共享上下文的方案；本文提出的动态路由、按需上下文和分级冲突处理方案。

所有组使用相同任务集合、资料范围和验收规则。固定模型版本及工具环境，记录不同组实际使用的模型、预算与并发容量。比较路由机制时，还要报告候选模型池是否相同，防止把更强模型的能力当作路由收益。

设置两种互补比较：在相同总预算上限下比较成功率；在达到相近质量要求时比较成本和时延。如果某方案因超出预算而中止，应计入该组结果，不能从失败样本中删掉。

辩论机制另设“独立回答后投票”的对照，以区分增加采样次数与交换意见分别带来的收益。该设计直接回应《Debate or Vote》提出的比较问题。[7]

### 8.2 为指标明确分母与判定依据

| 指标 | 本文建议的定义 | 用途 |
| --- | --- | --- |
| 任务成功率 | 在预算与时限内通过全部必要验收的任务数 / 总任务数 | 衡量最终交付 |
| 总成本 | 包含失败尝试在内的模型、工具和资源费用 | 避免只统计最终成功路径 |
| 端到端时延 | 从接收到完成或终止的时间，报告中位数和尾部值 | 观察排队、重试与长任务 |
| 交接遗漏率 | 标注的必要交接项中，未进入有效上下文的比例 | 检查共享机制 |
| 冲突检测精确率与召回率 | 对标注或注入冲突分别统计正确告警与漏检 | 避免把告警数量当作能力 |
| 冲突处理正确率 | 被处理冲突中，满足预定义裁决或安全终止条件的比例 | 检查消解效果 |
| 过期结果错误采纳率 | 已知前置条件失效的提交中，被错误接受的比例 | 检查一致性边界 |
| 重复外部效果率 | 一个逻辑动作产生多次不应发生效果的比例 | 检查重试协议 |

“安全终止”应与“问题已解决”分别报告，不能把弃答包装为准确回答。重复工作也要与刻意设计的独立复核分开计数，否则会鼓励系统删除有价值的交叉验证。

### 8.3 消融实验回答哪个机制有用

分别移除动态路由、上下文筛选、读集校验和证据核验，观察质量、成本和失败模式变化。对于存在交互的机制，还需要测试组合：上下文裁剪过度可能增加核验次数，而强核验也可能掩盖路由质量下降。

结果应按任务类型、依赖深度和冲突密度分层展示。对同一批任务进行配对比较，多次运行记录随机波动与区间估计。开放式答案可以辅助使用模型评审，但关键结论仍需可核对事实、可执行检查或人工复核支持。

训练路由器和总结长期经验时，评估任务不能泄漏到训练或记忆库中。经验检索的收益应在固定数据切分下单独评估。

### 8.4 注入故障，检查协议能否守住边界

本文建议注入以下故障：证据过期、错误摘要、工具超时、结果已生效但响应丢失、消息重复、旧执行者迟到提交、预算并发争用，以及同一接口的冲突补丁。

每个故障都要有明确预期。例如，旧执行者迟到提交应被拒绝；重复消息不得重复结算预算；验收报告对应旧补丁时不得直接完成任务；外部动作结果未知时应进入核对流程。

这些检查关注系统是否遵守约定，不能替代对模型任务能力的评估。两类结果应同时报告，才能解释一个方案为何可靠，或者究竟失败在什么环节。

## 九、从最小实现走向自适应网络

### 9.1 第一阶段：固定流程，建立可追溯执行

先选择一种边界明确、可以验收的任务，使用少量固定角色。实现任务契约、结构化交接、不可变产物、工具调用记录和统一验收。用数据库保存任务状态与预算，保留必要的恢复流程。

此时路由可以只是规则：满足条件进入并行调查，否则单实例执行。第一阶段要回答的是任务能否被稳定交接和验收，而非路由策略是否足够复杂。

### 9.2 第二阶段：补齐共享状态与冲突协议

加入对象版本、读集、执行代次、条件提交、冲突记录与外部动作核对。对生产中出现的交接失真和并发问题增加针对性约束，再接入按需检索和增量上下文。

长期记忆在这一阶段也需要写入门槛：只有结果经过验收、适用条件明确且来源可追溯，经验才进入可复用集合。被推翻的经验保留历史，但从默认检索视图中撤回。

### 9.3 第三阶段：根据真实轨迹优化路由与通信

当任务、候选方案、成本与验收结果已经稳定记录，再训练或校准路由器。新策略先在离线轨迹和受控任务上评估，再逐步扩大使用范围。

动态通信结构、跨任务记忆和模型选择可以分别优化，并保留固定策略作为可比较的回退路径。未经核验的自报成功，不进入路由效果统计；系统没有明确处理结果的任务，也不应被自动当成正样本。

### 9.4 需要持续研究的边界

本文架构仍然有几类难点。首先，历史路由数据只记录实际选择过的方案，很难直接知道其他候选是否更好。其次，开放任务可能缺少可靠的自动裁决器，新增一个审查智能体不能自动填补这项缺口。再次，外部系统的可变数据与不可逆动作，限制了内部状态协议能够提供的保证。

这些问题决定后续工作的方向：为路由建立受控探索数据，为冲突建立可核验评价集，为记忆建立纠错与撤回机制，并明确每一种工具在超时、取消和重试时的业务语义。

下一轮迭代可以从一组真实任务开始，逐项记录任务在哪一步被交错了、哪个必要事实没有交接、哪次提交使用了过期输入、哪项分歧缺少决定性证据。这些记录会告诉我们，下一笔工程投入应该放在模型能力、路由决策、共享状态还是验证协议上。
