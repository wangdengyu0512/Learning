# 把 RAG 从 Demo 推到生产：Milvus 生产化设计指南

做一个 RAG Demo 往往只需要四步：**文档分块、生成向量、写入向量库、检索 Top-K**。

但“能够返回答案”和“能够稳定、安全、持续地返回正确答案”之间，隔着一整套生产设计。Demo 中被默认值掩盖的问题，会在真实系统里集中暴露：多个客户的数据混在一起、产品型号搜不准、刚上传的文档查不到、权限过滤后召回率突然下降、换了嵌入模型却没有报错但结果全部失真……

在 Milvus 上把 RAG 推向生产，核心不是再写一遍向量检索代码，而是认真设计四个面：

1. **租户隔离**：一次查询究竟允许看到谁的数据；
2. **检索质量**：如何同时处理语义问题和精确关键词；
3. **新鲜度与一致性**：刚写入或更新的数据何时可见；
4. **元数据过滤**：如何按租户、时间、来源和权限缩小搜索范围，同时不把召回率拖垮。

这四件事不是彼此独立的配置项，而是一条相互牵制的决策链。本文将从数据模型开始，给出一套完整的生产化设计方法。

> **版本说明**：本文根据目录内材料整理，原材料的产品状态说明截至 **2026 年 6 月**。具体 API、配额和版本能力在上线前应以项目实际使用的 Milvus 版本为准。

## 一、为什么 Demo 能跑，生产却容易出问题

Demo 通常只有一个用户、一份相对静态的语料，以及一条简单的 Dense Vector Search 链路。它天然绕过了生产环境的复杂性：

```text
文档 → 分块 → Embedding → 写入 Milvus → Dense Top-K → LLM
```

到了生产环境，这条链路会多出一系列约束：

- 数据属于不同客户、部门或用户，必须隔离；
- 查询中既有自然语言，也有错误码、型号、函数名和工单号；
- 文档会持续新增、修改和删除；
- 查询必须叠加时间、来源、语言、ACL 等条件；
- 检索结果需要引用原文、去重、扩展上下文和整篇删除；
- 嵌入模型会升级，索引和 Collection 也需要迁移；
- 召回率、延迟、成本和一致性不可能同时取最大值。

因此，生产化的本质不是“把 Demo 部署到服务器”，而是把 Demo 中没有做出的决策逐一补齐。

## 二、先设计数据：一个 Chunk 就是一行 Entity

RAG 在 Milvus 中最常见的数据粒度是：**一个 Chunk 对应一行 Entity**。

一份生产可用的 Schema，至少要回答三个问题：

1. 这段内容如何参与向量检索？
2. 它属于谁，允许被哪些查询看到？
3. 命中后，如何回到原文并执行文档级操作？

一个典型的字段设计如下：

| 字段 | 用途 |
|---|---|
| `pk` | Chunk 主键，用于 upsert 和精确定位 |
| `dense_vector` | 语义向量，处理改写、近义表达和自然语言问题 |
| `sparse_vector` | 稀疏向量，可用于精确词项检索 |
| `text` | Chunk 原文，供 BM25 分词、Rerank 和 LLM 使用 |
| `parent_doc_id` | 指向原始文档，用于整篇删除、去重和邻块扩展 |
| `tenant_id` | 租户边界，通常也是每次查询必须携带的过滤条件 |
| `timestamp` | 时间范围过滤和数据生命周期管理 |
| `source` | 数据来源过滤，例如 Wiki、工单、手册、CRM |
| `acl_tags` | 部门、角色、用户组等权限标签 |
| `model_version` | 标记向量由哪个嵌入模型生成，防止新旧空间混用 |
| `$meta` | 保存低频、稀疏、结构不稳定的扩展元数据 |

### 1. 为什么必须保留 `parent_doc_id`

如果只保存 Chunk ID，而没有原始文档 ID，会失去两个关键能力：

- **整篇删除**：文档被撤回时，无法方便地删除它对应的全部 Chunk；
- **邻块扩展**：命中一个小块后，无法回查同一文档的前后块来补足上下文。

因此，`parent_doc_id` 并不是装饰字段，而是文档级生命周期管理和 Small-to-Big Retrieval 的基础。

### 2. 高频过滤字段不要全部塞进 JSON

Milvus 的 Dynamic Field 很适合保存不稳定的扩展属性，但它不应成为所有元数据的“杂物间”。

像 `tenant_id`、`timestamp`、`source` 这类高频过滤维度，应该定义为显式标量字段，并建立合适的标量索引。否则，每次查询都要为 JSON 路径解析和通用过滤付出额外成本。

一个实用原则是：

> **稳定且高频过滤的字段显式建列；低频、稀疏、未来可能变化的字段再放入 `$meta`。**

## 三、多租户设计：隔离强度与扩展能力无法兼得

多租户 RAG 最大的安全风险，不是查询变慢，而是**把租户 B 的内容召回到租户 A 的上下文中**。一旦这些内容被送给 LLM，就已经构成数据泄漏。

Milvus 中常见的多租户组织方式可以分为四档：

| 隔离方式 | 隔离强度 | 扩展能力 | 适用场景 |
|---|---:|---:|---|
| Database per tenant/business | 最强 | 最低 | 少数强隔离的大业务线或大客户 |
| Collection per tenant | 强 | 较低 | 数百到数千个、需要独立索引和独立删除的客户 |
| Partition per tenant | 中 | 中 | 租户不多、共用同一 Schema 的场景 |
| Partition Key | 较弱 | 最强 | 数千到海量中小租户，是 SaaS RAG 的常见选择 |

选择时要记住一条主线：

```text
可扩展性：Partition Key > Partition > Collection > Database
隔离强度：Database > Collection > Partition > Partition Key
```

租户数量越多，通常越需要向 Partition Key 方案移动；但越靠近这一端，越依赖应用层保证隔离。

### Partition Key 不是自动安全边界

假设把 `tenant_id` 设为 Partition Key，查询必须始终携带类似下面的条件：

```python
expr = 'tenant_id == "tenant_a"'
```

该等值条件既用于触发分区裁剪，也是应用层的租户边界。如果漏掉它，查询可能退化为更大范围的扫描，并召回其他租户的数据。

更重要的是，RBAC 通常只能保护 Database 或 Collection 等较粗粒度资源，无法替应用层区分同一个 Partition-Key Collection 内的单个租户。因此：

> **在 Partition Key 多租户架构中，`tenant_id` Filter 应当像用户鉴权一样被集中注入、强制校验和自动化测试，绝不能依赖业务开发者手写。**

建议在检索网关统一完成以下动作：

1. 从可信身份上下文中读取租户 ID，而不是接受前端自由传值；
2. 自动把租户条件与业务过滤条件合并；
3. 禁止没有租户条件的普通检索请求；
4. 对跨租户检索单独授权、审计和限流；
5. 建立“租户 A 永远无法召回租户 B 文档”的回归测试。

对于少数超级大客户，可以采用混合架构：**大客户单独使用 Collection 或 Database，长尾小租户共享 Partition-Key Collection**。这样既保留规模能力，也能满足大客户的物理隔离、审计和独立删除要求。

## 四、检索质量：不要停留在 Dense-Only

纯 Dense 检索擅长理解“意思相近”，却不擅长所有问题。

例如下面这些内容，往往更依赖字面匹配：

- 产品型号：`BGE-M3`；
- 错误码：`ERR_CONNECTION_RESET`；
- API 或函数名：`hybrid_search`；
- 工单号、合同号、版本号；
- 人名、缩写和罕见专有名词。

Dense Embedding 可能会把它们泛化为“某种模型”“某种网络错误”或“某个检索接口”，从而错过用户真正想找的精确条目。

生产级检索更适合采用两路召回：

- **Dense 路**：负责语义、改写和跨表达匹配；
- **Sparse/BM25 路**：负责关键词、型号、代码标识符和罕见 Token。

整体链路可以设计为：

```text
                         ┌─ Dense / HNSW / COSINE ─┐
用户 Query → 查询预处理 ─┤                         ├→ RRF/Weighted 融合
                         └─ Sparse/BM25 / IP ──────┘
                                      ↓
                              候选 Top 50~100
                                      ↓
                           Cross-Encoder 精排
                                      ↓
                              Final Top 5~10
                                      ↓
                                     LLM
```

### 1. 融合排序和模型精排不是一回事

这两个阶段经常被统称为 Rerank，但它们解决的是不同问题。

**第一阶段：融合排序**

Dense 相似度与 BM25 分数不在同一量纲，不能简单相加。融合器负责把两条召回列表合并成一个候选排序：

- **RRF**：只看每条结果在各列表中的名次，不依赖原始分数尺度；
- **Weighted Ranker**：对各路分数归一化后加权，可以控制 Dense 与 Sparse 的话语权。

如果还没有稳定的离线评测集，RRF 往往是更稳妥的起点，因为它不需要先解决分数归一和权重调参问题。只有当评测显示某一路长期偏强或偏弱时，再考虑 Weighted Ranker。

**第二阶段：交叉编码器精排**

ANN 负责快速召回，但它毕竟是粗排。Cross-Encoder 会把 Query 与每个候选文本一起输入模型，重新判断相关性。它更准，但成本也更高，因此应该只处理几十到一百个候选，而不是全库文档。

于是，生产链路通常遵循：

> **宽召回、窄精排、再把更窄的上下文交给 LLM。**

### 2. 三个 Top-K 不要混为一谈

RAG 中至少有三类容易混淆的旋钮：

- `ef` 或 `nprobe`：控制向量索引愿意搜索多少候选，影响召回率与延迟；
- Retrieval Top-K：给 Reranker 的候选宽度，常见为 50～100；
- Final-K：最终送入 LLM 的内容条数，常见为 5～10。

系统过载时，可以优先降低 `ef`、`nprobe` 或召回候选数来控制检索成本；不要通过无限增加 LLM 上下文来掩盖低召回。把更多低质量 Chunk 塞进 Prompt，不会修复检索，只会增加 Token 成本并稀释关键信息。

## 五、一致性与新鲜度：看得见和查得快是两件事

用户上传文档后立刻提问，却检索不到刚写入的内容，是 RAG 上线时非常常见的问题。

这里需要区分两个维度：

1. **可见性**：这次查询是否允许看到刚写入的数据；
2. **索引状态**：数据是仍在 Growing Segment 中被暴力扫描，还是已经 Sealed 并建立索引。

这两件事相互独立。

### 1. 一致性级别如何选

| 一致性 | 特征 | 适用场景 |
|---|---|---|
| Bounded | 允许秒级滞后，吞吐和尾延迟更友好 | 离线批量灌库、日常只读检索 |
| Session | 同一客户端可读到自己刚写入的数据 | 用户上传后立即提问、灌库后立即自测 |
| Strong | 尽量读取全局最新视图，成本最高 | 少量对全局最新状态有严格要求的场景 |

默认 Bounded 不等于 Read-Your-Writes。如果业务语义是“用户刚上传的文档必须立刻能问”，应在相应链路使用 Session，而不是把偶发查不到误判为 Embedding 或索引 Bug。

### 2. Session 也不代表已经完成索引

Session 解决的是“能不能看到”，不保证数据已经进入性能最优的索引状态。新数据可能仍位于 Growing Segment 中，以 Brute-Force 方式参与检索。

因此，灌库后的严格验收通常还需要：

- 等待写入完成；
- 必要时执行 Flush；
- 等待 Segment 进入可预期状态；
- 确认索引构建完成后再做性能和召回验收。

不要把“数据不可见”和“数据可见但尚未索引”混成一个问题：前者应该检查一致性，后者应该检查 Segment 与索引状态。

## 六、元数据过滤：条件越严，不一定越快

关系数据库给人的直觉是：`WHERE` 条件越严格，通过的行越少，查询通常越快。

但在向量检索中，尤其使用 HNSW 等图索引时，情况可能相反。

HNSW 依靠图上的邻居关系不断接近查询向量。如果 Filter 极其严格，图上绝大多数节点都会被排除，搜索过程可能无法顺利从一个有效节点走到下一个有效节点。结果是：

- 延迟升高；
- 找不够 Top-K；
- 召回率明显下降；
- 最危险的是系统仍然返回结果，却漏掉真正相关的内容。

例如下面的条件叠加后可能只剩不到 1% 的数据：

```text
tenant_id == 当前租户
AND department == 当前部门
AND timestamp >= 最近 7 天
AND acl_tags 包含当前用户权限
```

这时不能继续无脑沿用低过滤比场景下的索引参数。

### 1. 标量索引要与字段特征匹配

可参考以下思路：

| 字段特征 | 常见索引方向 |
|---|---|
| 低基数枚举，如 `source`、`language`、状态 | BITMAP |
| 高基数等值查询，如普通 `tenant_id`、文档 ID | INVERTED |
| 时间、数值范围，如 `timestamp` | Range / STL_SORT 类 |

凡是高频参与 Filter 的字段，都应该有明确的索引策略。否则标量过滤本身可能退化为扫描，抵消向量索引带来的收益。

### 2. 高选择性过滤需要联动调整

对于通过率极低的过滤条件，可以综合考虑：

- 使用 Milvus 的可迭代过滤策略；
- 提高 HNSW 的搜索努力，但同时接受更高延迟；
- 对极高选择性场景考虑 IVF 类索引；
- 先预过滤出很小的候选集合，再直接扫描；
- 对极小租户或极小数据集直接使用 Brute-Force；
- 按大租户、小租户采用不同的检索策略。

关键不是寻找一个“全局最优索引”，而是先测量不同查询的 Filter Selectivity，再基于真实分布选策略。

## 七、更新与模型迁移：最危险的是“不报错但结果错”

生产语料不会静止不变。文档会更新、撤回，Embedding 模型也会升级。

### 1. Upsert 不是原地覆盖

在 Milvus 中，可以把 Upsert 理解为按主键执行“旧记录删除 + 新记录插入”。删除通常通过 Tombstone 标记完成，旧数据需要等待 Compaction 和垃圾回收才能真正释放。

因此，大批量 Upsert 后可能出现一段时间的：

- 存储占用增加；
- 检索成本上涨；
- 新数据仍处于 Growing Segment；
- 性能短暂波动。

文档级删除应优先按 `parent_doc_id` 批量执行，而不是在应用层逐个 Chunk 删除。

### 2. 换 Embedding 模型通常要走蓝绿迁移

向量维度在建表时确定。新模型一旦改变向量维度，就不能直接在原 Collection 上修改，只能创建新 Collection。

推荐流程如下：

```text
创建 v2 Collection
        ↓
使用新模型重算全部文档向量
        ↓
回填数据并重建索引
        ↓
完成离线检索评测和线上影子验证
        ↓
查询流量切换到 v2
        ↓
保留 v1 一段时间用于回滚
```

这里有一条必须写进发布规范的铁律：

> **Query 与 Document 必须由同一套 Embedding 模型生成。**

如果文档已经切到新模型，而在线查询仍使用旧模型，两边向量位于不同的语义空间。相似度计算依旧能够执行，系统也依旧会返回 Top-K，但结果没有语义意义，而且通常不会报错。

建议增加两道护栏：

- 每条向量保存 `model_version`；
- 检索服务在执行搜索前校验 Query 模型版本与目标 Collection/字段版本一致。

如果要做两套模型 A/B Test，可以考虑在同一 Collection 中维护多个向量字段；如果维度、索引策略或生命周期差异较大，则使用双 Collection 通常更清晰。

## 八、一个完整案例：多租户 SaaS 客服知识库

假设要建设一个 SaaS 客服 RAG：

- 数千到数万个中小租户；
- 每个租户有自己的产品文档、工单和 FAQ；
- 查询中包含自然语言，也包含错误码、版本号和产品型号；
- 用户可以上传文档后立即提问；
- 默认只检索最近 90 天、当前用户有权限查看的内容。

可以做出如下设计。

### 1. 租户隔离

- 长尾租户共享一个 Partition-Key Collection；
- `tenant_id` 设为 Partition Key；
- 检索网关从身份系统注入租户条件；
- 超级大客户或强合规客户单独使用 Collection/Database；
- 建立跨租户泄漏回归测试。

### 2. Schema

显式字段至少包括：

```text
pk
parent_doc_id
tenant_id
timestamp
source
acl_tags
text
dense_vector
sparse_vector
model_version
```

低频扩展属性放入 `$meta`。

### 3. 标量索引

- `timestamp`：Range / STL_SORT 类；
- `source`、`language` 等低基数字段：BITMAP；
- 高基数等值字段：INVERTED；
- `tenant_id` 同时承担 Partition Key 路由和安全过滤职责。

### 4. 检索栈

- Dense + BM25/Sparse 双路召回；
- 先用 RRF 融合；
- 候选 Top 50～100；
- Cross-Encoder 精排；
- Final Top 5～10 进入 LLM；
- 结合文档 ID 做去重和邻块扩展。

### 5. 一致性

- 普通检索使用 Bounded；
- 用户上传后立即提问的同会话链路使用 Session；
- 批量灌库验收时区分可见性检查与索引就绪检查。

### 6. 更新与迁移

- 单个 Chunk 变更使用 Upsert；
- 整篇撤回按 `parent_doc_id` 批量删除；
- 监控 Tombstone、Compaction 和 Segment 状态；
- Embedding 升级采用新 Collection 回填、验证、切流和回滚；
- 使用 `model_version` 防止新旧语义空间混用。

### 7. 最需要压测的风险

这套系统中，`tenant_id + 最近 90 天 + ACL` 可能形成高选择性过滤。它会反过来影响 HNSW 召回、`ef` 设置和 Retrieval Top-K。因此压测不能只测“无 Filter 的平均延迟”，而要覆盖：

- 大租户与小租户；
- 热门租户与长尾租户；
- 低过滤比与高过滤比；
- 刚写入数据与已完成索引的数据；
- 自然语言查询与精确标识符查询。

## 十、结语

把 RAG 从 Demo 推到生产，真正困难的地方从来不是“把向量存进 Milvus”，而是围绕真实业务做出一系列彼此关联的取舍：

- 用什么数据层级隔离租户；
- 哪些字段必须在写入时进入 Schema；
- 如何让语义召回与精确词召回互补；
- 何时需要 Session，何时 Bounded 已经足够；
- Filter 如何影响图索引的可达性和召回率；
- 文档与模型更新时，怎样避免系统在不报错的情况下返回错误结果。

如果只记住一句话，可以是：

> **生产级 RAG 不是一次向量搜索，而是一条带有安全边界、混合召回、精排、一致性和生命周期管理的检索流水线。**

设计 Milvus 时也不要逐项孤立优化。租户 Filter 会改变过滤比，过滤比会影响索引与召回参数，一致性会影响更新流程，模型升级会推翻向量字段和索引。只有把这些决策放到同一条真实查询链路中一起验证，RAG 才算真正从 Demo 走向生产。
