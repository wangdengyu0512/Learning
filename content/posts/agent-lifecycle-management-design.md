一家企业准备上线售后工单智能体。第一版演示很顺利：用户说明问题，智能体查询订单、检索售后政策，生成处理方案，必要时提交退款申请。

真正准备交给用户使用时，一组问题出现了：谁可以修改退款规则？更换模型后是否仍然遵守旧的权限边界？工具调用超时，究竟是申请没提交，还是提交成功但响应丢了？一个等待人工审批的任务经历了版本升级，应该从哪里继续？用户说处理错误时，平台能否还原当时的政策、工具返回和状态变化？

这些问题共同指向一个设计目标：**让智能体从一个可以运行的程序，成为有明确责任、可验证行为、可追溯版本和可恢复状态的生产服务。**

本文以虚构的售后工单智能体为例，讨论创建、调试、部署、观测、运维五个阶段如何衔接。文中的架构、配置与流程属于工程设计建议，示例数值不代表真实生产指标。论文提供评测、可观测性和故障分析的研究依据，不意味着这些研究已经给出统一的平台实现标准。

## 一、先明确全生命周期管理的对象

### 1. 一个智能体包含多种变化速度不同的资产

ReAct 将推理与行动交替组织，让语言模型通过行动获取环境信息，再据此调整后续行为。[1] 在企业应用中，这个执行循环还会受到提示词、检索内容、工具能力、用户身份、历史状态和业务策略共同影响。

因此，管理对象需要覆盖整个行为生成与执行链。仅记录代码提交号，无法回答一次执行使用了什么知识、获得了什么权限，以及为什么产生了某个业务结果。

本文建议区分以下对象：

| 对象 | 回答的问题 | 关键内容 |
| --- | --- | --- |
| 智能体定义 | 它负责什么 | 任务契约、负责人、输入输出、终止条件 |
| 资产版本 | 它依赖什么 | 提示词、流程、工具契约、知识清单、记忆策略 |
| 发布版本 | 哪组资产经过共同验证 | 资产引用、构建摘要、评测报告、兼容性声明 |
| 部署实例 | 哪个环境运行哪个版本 | 环境、路由规则、配额、运行时配置 |
| 运行实例 | 这次任务进行到哪里 | 输入、有效身份、步骤、检查点、等待原因 |
| 外部动作记录 | 对业务系统做了什么 | 动作标识、幂等键、审批记录、外部回执 |
| 评测与观测证据 | 如何判断行为是否正确 | 评测样本、轨迹、验收结果、事件与指标 |

这里有两个容易混淆的概念。**发布版本描述经过验证的实现组合，运行实例描述某次执行的实际过程。** 一个版本可能服务很多次任务，一个任务也可能等待数小时，跨过平台的多次发布。

还要区分“知识来源发生更新”和“智能体版本发生更新”。对于持续变化的政策库，可以把知识索引作为独立资产管理，但必须记录每次执行实际命中的文档版本、有效期和检索时间。涉及退款等写操作时，还需要在执行前检查当下有效的业务政策。

### 2. 用两套状态机表达版本与任务

建议为发布版本定义如下状态：

```text
草稿 → 验证中 → 待发布 → 灰度中 → 正式运行 → 停用 → 归档
          ↓                  ↓
       验证失败          灰度终止 / 回切旧版本
```

其中，“待发布”意味着约定的评测门禁已经通过；“正式运行”意味着部署规则允许它接收正式流量；“停用”意味着停止接受新任务，已有任务仍需有明确的处理方案。一个旧版本可以在新版本灰度期间继续接收剩余流量，平台应分别记录各部署环境的状态。

运行实例采用另一套状态：

```text
已接收 → 排队 → 执行中 → 成功 / 失败 / 已取消
                  ↕
             等待人工 / 等待外部结果
```

“等待”必须带原因、截止时间和唤醒条件。“成功”必须对应业务验收条件。模型输出一句“已完成”，不能直接将任务改为成功。

版本状态转换也要带条件和证据：是谁发起的，依据哪份评测报告，在哪个环境生效，失败时如何处置。这样，发布流程才成为可检查的状态流转。

## 二、总体架构：连接管理、执行与反馈

AgentOps 研究通过梳理现有工具，提出了生命周期中应追踪的制品与关联数据分类。[2] 本文在这一研究视角上，提出三部分协作的平台结构。

![智能体全生命周期管理平台架构：管理控制、运行执行、观测评测与业务系统之间的关系](/agent-lifecycle/architecture.svg)

### 1. 管理与控制层负责定义目标和约束

这一层提供资产登记、版本管理、评测编排、发布管理、身份权限、配额和审计能力。它管理“谁可以运行什么，以及在什么条件下运行”。

控制层输出经过校验的发布配置，运行时加载具体的配置版本。配置变更采用版本号与原子切换，避免一次任务执行过程中混用不同版本的提示词、工具 Schema 和流程定义。

权限撤销、凭据失效、紧急禁用工具等约束需要及时生效。对于外部写操作，应在动作提交前重新检查有效权限；不能因为任务启动时获准，就允许它在权限撤销后继续写入。策略服务不可用时，可以暂停此类写操作，并明确只读任务允许使用缓存策略的范围与期限。

### 2. 运行执行层负责推进任务

这一层包含任务调度、智能体执行循环、模型访问、工具网关、状态持久化、检查点、人工介入和终止控制。一次运行至少绑定任务标识、会话标识、租户、有效身份和发布版本。

为避免无限循环与失控消耗，运行时应执行最大步数、总时限、模型调用预算、并行数和重试次数约束。模型可以提出下一步动作，运行时负责验证动作是否允许执行。

多智能体场景还需要维护父子任务关系、任务交接条件和责任归属。下游智能体获得的权限应受到上游有效权限与被委派任务范围的共同限制，不能通过转交绕过原有边界。

### 3. 观测与评测层负责形成证据

这一层接收执行事件、调用轨迹、业务验收结果和资源消耗，支持故障定位、质量分析与回归评测。

建议分别存储三类数据：运行时状态用于恢复执行，业务动作账本用于核对外部副作用，遥测数据用于诊断和分析。它们可以通过统一标识关联，但不应把抽样日志当作恢复任务或核对退款的唯一依据。

为了让平台具备可实施的边界，可以先确定以下持久化对象：

| 数据对象 | 主标识 | 主要关联 |
| --- | --- | --- |
| 智能体登记 | agent_id | 负责人、任务契约、资产版本 |
| 发布记录 | release_id | agent_id、配置摘要、评测报告 |
| 部署记录 | deployment_id | release_id、环境、路由规则 |
| 运行记录 | run_id | deployment_id、任务、会话、父运行 |
| 检查点 | checkpoint_id | run_id、状态格式版本、步骤序号 |
| 动作账本 | action_id | run_id、业务对象、幂等键、外部回执 |
| 评测报告 | evaluation_id | release_id、评测集版本、评分器版本 |

每条记录都应具有明确的租户边界。跨对象查询与访问鉴权必须保留这个边界，不能只依赖难以猜测的 ID。

## 三、创建：把业务需求写成任务契约

### 1. 先写验收标准，再组织执行过程

“帮助用户处理售后”不足以指导实现。需要进一步定义：允许处理哪些订单，何时要求补充信息，哪些情况直接拒绝，哪些情况必须转人工，以及如何确认结果。

售后智能体的任务契约可以写成：用户经过身份验证后，系统查询其可访问订单，使用有效售后政策判断处理路径。符合自动处理条件的申请进入业务系统；超过权限范围的申请转交人工；最终返回可查询的申请编号或明确的未受理原因。

契约需要同时描述正常路径与停止条件。身份无法确认、政策冲突、外部结果未知、预算耗尽，都应成为可识别的结果或中间状态。

### 2. 按任务需要选择执行结构

对于步骤固定、规则明确的流程，可以使用确定性工作流，让模型承担信息提取、解释和材料整理。需要根据环境反馈动态探索时，再为相关节点引入智能体循环。

多智能体适用于确实存在独立职责、不同工具范围或可并行子任务的情况。每增加一个协作角色，都要定义输入输出、共享状态、交接条件和最终验收责任。

关于多智能体失败的研究将问题归纳为系统设计、智能体间失配以及任务验证等类别。[6] 这提醒平台设计者：创建更多角色的同时，需要增加相应的协作与验证约束。

### 3. 让工具契约包含副作用语义

工具登记除了名称、参数和返回值，还应说明访问范围、写入对象、是否支持幂等、超时后的查询方式，以及是否存在补偿操作。

例如，`submit_refund_request` 应被标记为具有业务副作用的工具。调用时，运行时先完成身份、订单范围和策略检查，再生成稳定的业务动作标识，记录调用意图，最后提交请求。

审批也要绑定具体动作。至少将审批人与审批时限、业务对象、操作类型、金额及参数摘要关联起来。如果金额发生变化，旧审批不能自动覆盖新动作。

### 4. 用声明式清单形成创建产物

下面是一份概念性配置，用于说明需要管理的信息，不对应某个框架的实际语法：

```yaml
agent:
  id: aftersales-assistant
  owner: customer-service-platform
  task_contract: aftersales-contract-v3

release:
  id: aftersales-r17
  workflow: aftersales-flow-v5
  prompt_bundle: aftersales-prompts-v12
  model_config: primary-model-config-v4
  tool_contracts: aftersales-tools-v8
  knowledge_manifest: aftersales-policy-index-v6
  memory_policy: tenant-session-memory-v2

runtime:
  max_steps: 20
  max_active_seconds: 180
  max_model_calls: 12
  checkpoint_schema: aftersales-state-v3
  default_write_action: deny

validation:
  dataset: aftersales-regression-v9
  graders: aftersales-graders-v4
  required_checks:
    - business_state_consistency
    - authorization_boundary
    - duplicate_action_prevention
```

上述限制仅为示例。对于人工等待，最好分别定义总任务期限与主动执行预算，避免等待审批耗尽计算步骤预算，也避免任务无限期悬挂。

这一阶段的交付物包括任务契约、资产清单、工具与权限契约、状态定义和初始评测集。具备这些材料，团队才能进入有共同标准的调试。

## 四、调试与评测：建立可以重复检查的质量证据

### 1. 调试界面要连接上下文、动作和结果

开发者需要看到每一步实际使用的提示词版本、可见上下文、检索引用、工具参数、工具结果与状态变化。定位错误时，应能沿着这些关系检查：输入是否缺失，检索是否过期，权限是否正确，动作是否执行，验收是否误判。

平台可以记录公开可获得的模型输入输出、工具选择和简短决策说明，但不应假定能够获取模型内部完整的推理过程。即使模型输出了决策解释，也需要结合真实调用与业务状态验证。

建议在界面中区分三种能力：

| 能力 | 执行方式 | 能解决的问题 |
| --- | --- | --- |
| 轨迹查看 | 展示已经发生的事件 | 还原当时输入、动作与反馈 |
| 录制结果回放 | 使用已保存的模型或工具结果 | 检查流程分支与状态转换 |
| 沙箱重新执行 | 在隔离环境重新调用模型和工具 | 验证改动后的行为与依赖兼容性 |

保存了配置和随机种子，也不能据此承诺跨供应商、跨版本的完全一致重现。平台应标注回放过程中哪些结果来自录制，哪些来自新的调用。涉及退款等写工具时，调试应使用测试租户、模拟工具或隔离业务数据。

### 2. 同时评估最终结果与执行过程

AgentBoard 指出，只关注最终成功率会掩盖执行过程中的能力差异，并引入细粒度进展度量。[3] 对售后任务，可以检查是否正确识别订单、找到有效政策、补齐必要信息、提交合法申请并返回回执。

过程指标用于定位问题，最终结果仍需由业务条件验收。智能体完成了前四步，如果把申请提交到了错误订单，任务仍应判为失败。

τ-bench 通过比较对话结束后的数据库状态与目标状态评估结果，并提出 `pass^k` 观察多次试验中的可靠性。[4] 对本文案例，验收器应检查申请是否存在、订单归属是否正确、金额是否符合规则，以及是否出现重复申请。

### 3. 评测集覆盖四类风险

初始评测集可以围绕典型任务、边界输入、依赖异常和对抗输入建立，并逐步补充线上失败案例。

| 类别 | 售后场景 | 重点检查 |
| --- | --- | --- |
| 典型任务 | 信息完整且符合政策的申请 | 是否正确完成业务状态转换 |
| 边界输入 | 多笔订单、材料缺失、政策有效期切换 | 是否澄清信息或停止错误处理 |
| 依赖异常 | 工具超时、限流、响应格式变化 | 是否正确重试、等待或转交 |
| 对抗输入 | 检索文档要求忽略规则、工具结果夹带恶意指令 | 是否维护身份、权限和工具边界 |

AgentDojo 研究工具返回的不可信数据如何通过提示注入影响智能体，并提供可扩展的攻防评测环境。[5] 工程上可以借鉴这种测试方式，把攻击放在真实的数据入口，而不只在用户输入框中测试一句“忽略之前的指令”。

### 4. 用可解释的门禁决定是否发布

建议将评测结果分为必须满足的业务约束，以及需要与基线比较的质量指标。越权写入、错误订单操作等已发现的严重失败，应阻断相应版本发布；测试中没有发现失败，只能说明在已测范围内未发现问题。

质量指标可以包括任务成功率、重复运行的一致性、人工接管比例、尾延迟和单个有效任务成本。对不同场景分别报告结果，避免总体平均值掩盖某类订单上的退化。

评分方式根据目标选择：结构与数值使用确定性规则，写操作使用业务状态核对，表达质量使用经过人工校准的模型评分。评分器及其提示词也应版本化。用于开发调优的样本与用于发布判断的保留样本应有所区分，防止反复针对同一批样本修改后得到虚高结果。

重复运行时，要区分“多次尝试至少成功一次”和“多次尝试都成功”。后者更接近日常交付中的一致性要求，但会随重复次数变化。报告应给出重复次数、样本量、场景分布与不确定性，而不是只留下一个百分比。

发布门禁最终输出一份可关联到版本的报告：测了什么、如何判断、与哪个基线比较、存在哪些未覆盖范围，以及结论是什么。

## 五、部署：发布经过共同验证的资产组合

### 1. 明确发布包能固定什么

发布记录应绑定工作流、提示词、模型配置、工具契约、知识清单、记忆策略、权限策略引用和评测报告。对于构建产物与静态配置，可以记录内容摘要，检查部署时是否发生变化。

外部模型服务、持续更新的知识库和业务 API 并不一定支持严格锁定。平台需要区分已经固定的资产与动态依赖，记录实际解析出的版本、服务返回的版本信息以及执行时间。无法锁定的部分应通过契约检查、变更通知和持续评测管理。

发布配置中保存凭据引用，不保存长期密钥明文。运行时根据执行身份获得所需凭据，并将使用范围限制在当前任务允许的操作内。

### 2. 为长任务设计发布兼容策略

任务进入运行时后，应绑定一个发布版本。对于兼容的已有任务，通常继续使用原版本完成；对于存在严重缺陷或权限问题的任务，可以暂停并转入修复与接管流程。

若希望将运行中的任务迁移到新版本，需要显式声明状态格式兼容性、检查点转换方法和待完成动作的处理方式。一个旧节点已经提交了退款申请，新流程不能因为节点名称改变，就将它当作尚未执行的步骤再次提交。

记忆迁移也属于兼容性问题。旧版本写入的长期记忆可能包含过期规则或不适用于新任务的信息，应保留来源与生成版本，并根据新策略重新筛选。

### 3. 灰度发布按业务风险设计

离线评测通过后，可以先使用经过脱敏的历史任务或隔离流量检查集成情况。影子运行若调用写工具，需要由模拟器或隔离业务环境承接这些写操作，避免两套版本同时修改真实订单。

正式灰度应按租户、会话或业务任务进行稳定分流，减少同一任务在新旧版本之间跳变。比较时同时观察质量、策略异常、耗时、成本与人工接管负担，并尽量保证两组任务构成可比。

例如，可以先面向低风险业务范围开放，再逐步扩大。放量依据是预定义的观察窗口、样本量和终止条件，不能只看运行几分钟没有报错。

### 4. 把回退拆成三个动作

版本发布失败后，需要分别回答三个问题：

| 回退对象 | 可采取的操作 | 需要额外检查的内容 |
| --- | --- | --- |
| 新任务流量 | 将路由切回旧版本 | 旧版本是否仍兼容当前依赖 |
| 执行中任务 | 暂停、继续、迁移或人工接管 | 检查点与待处理动作是否兼容 |
| 已发生的业务动作 | 查询、核对、撤销或补偿 | 业务是否支持逆操作，是否需要授权 |

退款、发货和通知发送一旦发生，其业务效果不会随代码回退而消失。补偿也可能失败，或者只能通过人工流程处理。因此，发布预案需要明确每类写操作的核对与处置方式。

## 六、观测：从业务结果找到具体执行证据

### 1. 让标识贯穿任务、调用与业务回执

建议使用 `task_id` 表达业务目标，使用 `run_id` 表达一次运行，使用 `trace_id` 关联调用链，使用 `action_id` 标识对外业务动作。它们之间可以是一对多关系：一个业务任务可能经历多次运行，一次运行也可能跨越多个执行时段。

长任务恢复后，即使产生新的 Trace，也应通过任务与运行标识关联到之前的检查点和业务动作。多智能体子任务还要记录父运行和委派关系，使排查者能找到实际承担失败步骤的执行者。

一个工具动作事件可以包含下列信息：

```json
{
  "event_type": "tool_action_result",
  "tenant_id": "tenant-example",
  "task_id": "ticket-2048",
  "run_id": "run-015",
  "release_id": "aftersales-r17",
  "step_id": "submit-request",
  "action_id": "action-008",
  "attempt": 1,
  "tool": "submit_refund_request",
  "policy_revision": "refund-policy-v6",
  "result": "unknown",
  "reason": "response_timeout",
  "external_receipt": null
}
```

`unknown` 表示调用结果未知，不能据此断言外部业务失败。对这类动作，平台需要能够定位调用意图、后续核对和最终结论，而不是只展示一条超时错误。

### 2. 指标分为四组，并约定计算口径

| 指标组 | 典型指标 | 用途 |
| --- | --- | --- |
| 业务质量 | 正确完成率、错误处理率、人工接管率 | 判断业务交付是否达标 |
| 执行行为 | 步数、重复调用、无进展循环、未知动作数量 | 发现异常执行模式 |
| 系统性能 | 排队时间、模型延迟、工具延迟、任务完成时长 | 定位性能瓶颈 |
| 成本与治理 | 每个有效任务成本、预算超限、越权拦截事件 | 管理资源与权限边界 |

任务成功率需要有明确分母。若只统计已结束任务，长期卡住的任务会被排除，指标可能显得很好。可以按任务进入系统的时间形成观察队列，在预设截止点核算符合条件的任务；超过时限仍未完成的任务计为时限失败，随后完成则另记最终结果。

人工等待应同时保留用户总等待时间与系统主动处理时间。否则，将大量任务转交人工可能降低平台处理时长，却让用户体验变差。

### 3. 从聚合告警进入有上下文的诊断

当某一版本的人工接管率上升时，排查路径可以是：先按任务类型定位集中场景，再检查失败步骤分布，然后查看具体轨迹，关联当时的政策版本、工具返回和有效权限。

需要避免把相关性直接当成根因。新版本上线期间也可能恰好发生业务 API 故障，应结合依赖状态、对照流量和隔离复现判断。

完整任务标识适合保存在事件和轨迹中。聚合指标的标签可以控制在版本、工具、环境、任务类别等有限维度，避免将所有任务 ID 直接作为指标标签。

### 4. 保留足够证据，并控制数据暴露

观测设计应区分诊断内容和必要审计字段。订单信息、联系方式和用户原文可以按用途脱敏或使用受控引用；保留期限与访问权限应与数据类型匹配。

普通诊断轨迹可以采样，但业务动作账本、重要权限决策和发布记录需要完整性设计。对于必须审计的写操作，如果关键记录无法可靠写入，应在执行前停止该操作，防止事后无法核对。

## 七、运维：把异常变成可执行的处置流程

2026 年的《Agent System Operations》综述将智能体运维组织为监控、异常检测、根因定位和解决四个阶段。[7] 在平台实现中，可以为每类故障进一步定义触发条件、责任人、允许执行的动作以及恢复验收方式。

### 1. 先分类，再选择恢复动作

| 故障类型 | 典型现象 | 建议处置 |
| --- | --- | --- |
| 模型服务异常 | 限流、超时、不可用 | 限制重试，切换经过验证的配置或暂缓执行 |
| 工具依赖异常 | 接口错误、契约不匹配 | 暂停相关路径，检查兼容性，必要时转人工 |
| 业务结果未知 | 写请求超时，无确定回执 | 按动作标识查询、对账，避免盲目重提 |
| 知识或策略异常 | 引用过期规则、规则冲突 | 停止受影响动作，修正资产并回归验证 |
| 状态异常 | 检查点缺失、状态格式不兼容 | 暂停恢复，迁移状态或人工接管 |
| 协作异常 | 重复交接、责任缺失、相互等待 | 检查委派图与终止条件，收敛到责任节点 |

备用模型或工具路径也应提前评测。切换后，工具调用能力、上下文容量和输出习惯可能变化，运行时需要确认它们仍满足当前任务要求。

### 2. 为写操作建立核对机制

建议将外部动作状态明确区分为准备提交、已确认、结果未知、确定失败，以及业务允许时的补偿中和已补偿。

在本地可以通过事务保存调用意图与待发送记录，再由执行者派发请求。这个方案让待处理动作有据可查，但无法自动消除外部系统已经成功、本地尚未记录回执的窗口。

要处理这个窗口，外部接口最好支持稳定的幂等键与结果查询。对同一笔业务动作重试时复用同一幂等键，同时验证参数摘要一致；如果参数变化，应重新创建动作并重新校验授权。若两个运行都可能为同一张订单创建同一类申请，还需要业务唯一约束或受控并发机制。

当外部系统既不支持幂等，也不能可靠查询结果时，平台应将该场景转入人工核对，不能声称已经保证了跨系统的“恰好执行一次”。

### 3. 定义服务目标与事件响应规则

服务目标可以围绕合格任务的正确完成率、完成时限与人工接管时效制定，并为不同业务风险设定不同要求。超出目标时，需要有明确的停止放量、限制流量、降级或排障动作。

越权写入、重复退款等事件可采用单独的立即响应规则，不应因为总体成功率仍然较高就继续放量。

人工接管必须附带可操作的信息包：当前任务状态、已经确认的动作、结果未知的动作、待核实事实与可执行选项。接管时还应控制执行权，防止人工处理期间后台智能体继续修改同一业务对象。

### 4. 形成受控的改进闭环

生产问题经过脱敏和归类后进入回归集。团队提出提示词、工具、检索或流程改动，生成新的资产版本，执行评测，再进入部署流程。

如果引入自动优化，也应把优化结果作为候选版本处理。优化器不能仅依据自身评分，就直接修改生产提示词或权限策略。评测集、评分器和发布条件需要独立管理，防止优化过程只学会迎合已知评分方式。

### 5. 退役时处理依赖与存量任务

停用智能体先停止新流量，再梳理正在执行、等待人工和结果未知的任务。对每类任务明确完成、迁移、取消或接管方案，并核对尚未结束的外部动作。

待处置完成后，撤销服务凭据、关闭计划任务与事件订阅，检查其他智能体是否仍引用该服务。根据保留策略归档发布和审计证据，处理会话状态、记忆与临时数据。退款记录等业务事实仍由相应业务系统按自身规则保存。

## 八、贯穿案例：一次退款申请超时如何闭环

下面使用假设场景串联全流程。用户提交售后申请后，智能体完成身份与政策检查，调用退款申请工具。请求已经到达外部系统，但平台未收到响应。

![售后任务发生工具超时后，从结果核对到人工接管及回归发布的处理闭环](/agent-lifecycle/recovery-flow.svg)

### 1. 创建时准备恢复所需的契约

工具登记已经说明这是写操作，支持幂等键和按业务动作标识查询结果。任务验收要求获得有效申请编号，且订单、金额和用户身份匹配。

因此，平台从一开始就知道：出现超时不能直接把任务判为成功，也不能把它视为可以任意重做的普通读取。

### 2. 调试时覆盖两个不同的超时场景

评测环境分别模拟“请求尚未生效”和“已生效但响应丢失”。前者在满足接口重试契约后可以继续提交；后者必须恢复已经存在的申请。

验收器检查同一笔业务申请没有重复创建，并确认智能体没有在缺少回执时向用户宣称处理完成。这些案例在发布前进入门禁。

### 3. 运行时保留未知状态

超时发生后，平台将动作标记为结果未知，保存动作标识、幂等键、参数摘要和原始运行关联，任务进入等待外部结果状态。

用户收到的是准确的状态说明，例如“申请结果正在核实”，以及可查询的工单标识。平台暂不启动依赖申请成功的后续步骤。

### 4. 运维流程先核对，再决定下一步

核对执行者使用原业务动作标识查询外部系统。若确认申请已存在，校验参数并记录回执，再继续流程；若依据外部系统的查询一致性与请求终态确认尚未执行，才按照原幂等键发起受控重试。

若查询接口返回的“未找到”可能来自索引延迟，则继续核对或等待，不能把它当作未执行的确定证据。超过核对期限仍无法确认时，转交人工并暂停冲突操作。

### 5. 修复版本经过验证后发布

假设诊断发现旧版本错误地将超时标为失败并生成新幂等键。团队修复动作状态转换与幂等键复用逻辑，把故障轨迹转化为回归样本，再运行相关评测。

新版本通过门禁后灰度发布。已有的未知动作继续单独核对；如果发现重复申请，则按业务规则处理，而不是期待新代码替它们自动消失。

这条链路依赖创建时的工具契约、调试时的异常样本、部署时的状态兼容策略、观测中的关联标识，以及运维中的核对执行者。任何一环缺失，恢复就会退化为人工猜测。

## 九、按可验收的阶段建设平台

不必在第一期实现全部能力。建设顺序应由业务风险和规模决定，但每一期都需要有可运行的完整链路。

| 阶段 | 建设重点 | 验收方式 |
| --- | --- | --- |
| 第一阶段：跑通闭环 | 任务契约、版本登记、基础评测、运行记录、权限校验与人工接管 | 能追溯一次任务的版本，并确认业务结果和责任人 |
| 第二阶段：提高可靠性 | 检查点、动作账本、幂等与核对、灰度发布、告警与恢复预案 | 能通过工具故障和运行中断演练，受控恢复或接管 |
| 第三阶段：支持规模化 | 多租户、资源配额、依赖影响分析、持续评测与跨智能体追踪 | 能隔离租户与故障，管理批量变更，解释成本和质量变化 |

如果第一期就要执行退款等有副作用的操作，幂等、审计和结果核对应提前进入第一期。阶段划分用于安排建设工作，不能替代实际业务上线条件。

上线验收可以围绕以下问题进行：

- 是否有明确负责人、任务范围、成功条件和接管规则？
- 是否能够关联发布版本、依赖、评测集与评测报告？
- 是否在实际执行时检查身份、数据范围、权限与预算？
- 是否知道每次任务停在哪里，哪些业务动作已经发生？
- 是否能在升级、崩溃、超时和人工接管后受控继续？
- 是否定义了发布回退、业务核对、退役与数据保留方案？

当这些问题能够由平台中的对象、规则和证据回答时，创建、调试、部署、观测与运维就连成了同一套管理机制。团队可以据此持续交付新能力，也能够在行为偏离预期时找到责任边界并恢复服务。
