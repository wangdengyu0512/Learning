# 把 Nacos 当成一个按数据类型切换一致性的系统

很多人第一次接触 Nacos，会把它记成两句话：

- Nacos 是注册中心；
- Nacos 也是配置中心。

这足以把项目跑起来，却不足以解释生产环境里真正棘手的问题：

- 为什么 Nacos 既被说成 AP，又被说成 CP？
- 为什么同一个集群里，临时实例在网络分区时还能注册，配置写入却可能被拒绝？
- 为什么实例进程已经死了，调用方仍可能继续请求它？
- 为什么控制台里的配置已经更新，应用日志也收到了通知，业务代码读到的还是旧值？
- 为什么从 Nacos 1.x 升到 2.x 后，`8848` 明明能连，客户端却一直注册失败？
- 为什么扩容 Nacos 节点时，服务列表反而可能短暂抖动？
- 为什么“注册中心高可用”和“配置中心强一致”可以由同一套 Nacos 同时满足？

这些现象并不分散。它们都可以沿着同一条主线解释：

> **Nacos 不是一个全局固定为 AP 或 CP 的系统，而是根据数据类型，把不同数据路由到不同的一致性路径。临时实例走 AP，持久实例与配置走 CP。**

在服务实例这一侧，真正的分流开关是 `ephemeral`：

```text
一条数据进入 Nacos
        ↓
判断数据类型 / ephemeral
        ↓
┌───────────────────────────┬───────────────────────────┐
│ ephemeral=true            │ ephemeral=false / 配置   │
│ 临时实例                  │ 持久实例与配置            │
├───────────────────────────┼───────────────────────────┤
│ AP                        │ CP                        │
│ Distro                    │ Raft / 多数派提交         │
│ 内存状态                  │ 持久化状态                │
│ 客户端心跳                │ 服务端探活或配置持久化    │
│ 异步复制、最终一致        │ 强一致、分区时可能拒写    │
└───────────────────────────┴───────────────────────────┘
```

只要抓住这条分流线，Nacos 的数据模型、健康检查、服务发现、客户端容灾、配置刷新、CAP 取舍和生产故障就不再是一堆孤立知识点，而会变成同一套设计的不同结果。

> 版本说明：本文根据指定目录中的 Nacos 深入教程整理，以 Nacos 2.x、Spring Cloud Alibaba 2023.x 为主要基线，源资料的前沿信息截至 2026 年 6 月。本文未联网核验 2026 年 10 月之后的版本变化；涉及默认值、端口、兼容矩阵、注解刷新行为和 3.x 能力时，应以实际部署版本的官方文档与配置为准。示例主要用于表达机制，未连接真实 Nacos 集群执行。

## 一、Nacos 首先解决了什么问题

在没有注册中心时，`order-service` 要调用 `user-service`，通常只能把后者的地址写进配置：

```text
user-service = 10.0.0.12:8080
```

但服务实例不是静止的：

- 扩容会增加地址；
- 缩容会删除地址；
- 容器重建会更换 IP；
- 进程崩溃会让地址失效；
- 多机房部署还要考虑就近访问。

如果每次变化都靠人工改配置并重启调用方，服务数量一多，系统就无法维护。

注册中心因此像一本“实时电话簿”：

```text
服务提供者启动
    ↓ 注册自己的 IP:Port
注册中心维护实例列表
    ↓ 查询 / 订阅
服务消费者获得可用地址
    ↓
负载均衡并发起调用
```

但注册中心接手地址管理后，也给自己制造了一个新问题：

> **生产中的注册中心本身是一个集群。一本电话簿被复制到多个节点后，这些副本如何保持一致？**

如果所有实例变化都等待全部节点强一致确认，列表会更准确，但网络分区或选主期间可能无法注册；如果允许各节点继续接收变化，系统更可用，但不同节点短时间内可能看到不同列表。

Nacos 的关键设计，不是替所有数据选择同一个答案，而是先问：**这条数据更怕不可用，还是更怕不一致？**

- 无状态微服务实例可以重试其他节点，更怕注册中心整体不可用；
- 配置和固定身份节点一旦产生分歧，业务含义可能直接出错，更怕不一致。

于是，两类数据进入两条不同的协议路径。

## 二、先建立数据模型：服务到底由什么坐标定位

很多“发现不到服务”和“读不到配置”的故障，不是协议问题，而是坐标没有对齐。

### 2.1 服务发现的五级模型

Nacos 的服务发现可以按五层理解：

```text
namespace
  └─ group
      └─ service
          └─ cluster
              └─ instance
```

| 层级 | 作用 | 默认值或关键点 |
| --- | --- | --- |
| namespace | 环境或租户隔离 | 常见默认空间为 `public`；代码通常使用 namespace ID |
| group | 同一 namespace 内的业务分组 | 常见默认值为 `DEFAULT_GROUP` |
| service | 逻辑服务，如 `order-service` | 与 namespace、group 一起唯一定位服务 |
| cluster | 服务内部按机房、地域或可用区细分 | 常见默认值为 `DEFAULT`；不参与服务唯一定位 |
| instance | 一个具体进程 | `ip:port`，带权重、元数据、健康状态和 `ephemeral` |

真正唯一定位一个服务的是：

```text
namespace + group + service
```

`cluster` 和 `instance` 是服务内部的进一步划分，不是“找哪个服务”的外部坐标。

这条规则可以直接变成排障顺序。当 A 能发现服务、B 却报 `no available server` 时，优先核对：

1. 两边连接的 `server-addr` 是否真的是同一套 Nacos；
2. namespace ID 是否一致；
3. group 是否一致；
4. service name 的拼写和大小写是否一致；
5. 最后再看 cluster、订阅、健康状态和网络。

不要一上来就怀疑负载均衡或 Distro。坐标不一致时，两边看到的本来就是两个逻辑世界。

### 2.2 namespace 是隔离边界，不只是标签

假设 dev 和 prod 下都有一个 `order-service`：

```text
namespace=dev  + group=DEFAULT_GROUP + service=order-service
namespace=prod + group=DEFAULT_GROUP + service=order-service
```

它们不是同一个服务，也不应该互相发现。

namespace 的价值，是允许同一套 Nacos 集群承载多个逻辑环境，同时避免同名服务串台。代价是：一旦客户端填错 namespace，现象通常不是显式报错，而是“注册成功但别人看不到”或“配置存在但应用读不到”。

### 2.3 配置中心的三级定位

配置中心复用了 namespace 和 group，但最后一层换成 `dataId`：

```text
namespace + group + dataId
```

在常见的 Spring Cloud Alibaba 约定中，dataId 可理解为：

```text
${prefix}-${profile}.${file-extension}
```

例如：

```text
order-service-dev.yaml
│             │   └─ file-extension
│             └──── profile
└────────────────── prefix，通常来自 spring.application.name
```

因此，一条配置读不到时，不要只盯着 dataId 全字符串，还要拆开核对：

- `spring.application.name` 是否符合预期；
- 激活的 profile 是否符合预期；
- 扩展名是 `properties`、`yaml` 还是其他格式；
- namespace 和 group 是否与控制台中的配置一致。

服务发现和配置中心共用 namespace、group，也意味着一个错误可能同时制造两类症状：

- 服务发现侧：找不到实例；
- 配置中心侧：拉不到配置。

## 三、`ephemeral`：一个布尔值背后的系统分流

同样是一个 `ip:port`，临时实例和持久实例的生命周期语义完全不同。

| 维度 | 临时实例 `ephemeral=true` | 持久实例 `ephemeral=false` |
| --- | --- | --- |
| 默认性 | 常见微服务默认路径 | 需要显式选择 |
| 健康判定 | 客户端主动上报心跳 | 服务端主动探活 |
| 存储 | 主要保存在内存状态中 | 持久化，可在重启后恢复 |
| 失联行为 | 超时后标记不健康并最终删除 | 探活失败只标记不健康，不自动删除 |
| 一致性路径 | AP，Distro，异步复制 | CP，Raft，多数派提交 |
| 典型场景 | 可随时扩缩的无状态服务 | 有固定身份、需要人工管理的节点 |

### 3.1 为什么无状态服务默认适合临时实例

现代微服务实例通常被当成“可替换资源”：

- 它崩了可以重新拉起；
- 地址可能变化；
- 负载均衡器可以选择其他实例；
- 调用失败可以重试；
- 运维通常不希望手动清理每一个已经消失的容器。

对这类实例，可用性比瞬时一致更重要。网络分区发生时，与其让整个注册中心拒绝注册和查询，不如让各分区继续工作，接受列表短暂不一致。

这就是 AP 路径的业务依据。

### 3.2 为什么固定身份节点更适合持久实例

某些节点不是“死了就从世界里消失”的临时进程，例如：

- 被运维登记和审计的固定网关；
- 某些数据库或中间件节点；
- 有明确资产身份、需要人工确认后才能删除的组件。

这类节点即使暂时不可达，也可能只应该被标记为不健康，而不是自动从注册表中删除。

因此，持久实例把“是否删除”的决定留给运维或显式 API，并使用更强的一致性路径管理状态。

### 3.3 Spring Cloud Alibaba 中的表达

```yaml
spring:
  application:
    name: order-service
  cloud:
    nacos:
      discovery:
        server-addr: 127.0.0.1:8848
        namespace: 3a8d2f1c-xxxx-xxxx-xxxx-xxxxxxxxxxxx
        group: DEFAULT_GROUP
        cluster-name: BJ
        ephemeral: true
```

这里几个字段分别回答不同问题：

- `name`：我是什么服务；
- `namespace` 与 `group`：我属于哪个逻辑空间；
- `cluster-name`：我属于哪个机房或地域分组；
- `ephemeral`：我的生命周期和一致性语义是什么。

`ephemeral` 不是“是否临时展示”的 UI 字段，而是会影响健康检查、存储方式、删除行为和一致性协议的系统级选择。

## 四、健康检查：为什么是 5s、15s、30s

临时实例依赖客户端心跳维持存在感。源资料给出的典型时间线是：

```text
正常运行
  └─ 客户端约每 5s 上报一次心跳

最后一次心跳 t0
  ├─ t0 + 15s：标记为 unhealthy
  └─ t0 + 30s：从临时实例内存状态中删除
```

这三个时间点对应三个不同目的：

- **5s 心跳**：持续证明客户端还活着；
- **15s 不健康**：尽快让消费者避开可疑实例；
- **30s 删除**：给短暂网络抖动留恢复窗口，避免一次丢包就彻底删除实例。

“标记不健康”和“删除”必须分开。因为分布式系统里的心跳丢失，既可能意味着进程真的死了，也可能只是：

- 网络瞬时抖动；
- 客户端发生长时间 GC；
- CPU 饱和导致调度延迟；
- Nacos 节点短暂不可达；
- 容器网络或负载均衡链路异常。

如果第一次怀疑就删除，系统会频繁上下线；如果永不删除，注册表又会积累大量僵尸实例。两阶段处理是在灵敏度和稳定性之间折中。

### 4.1 为什么实例死后，调用方仍可能继续打它

从服务端视角看，临时实例约 30s 后已经删除。但调用方不是每次请求都实时访问 Nacos，它通常持有本地服务列表缓存。

真实链路是：

```text
实例崩溃
  ↓
服务端等待心跳超时
  ↓ 15s
标记 unhealthy
  ↓ 30s
从服务端临时状态删除
  ↓
变更通知到客户端 / 客户端下一次刷新
  ↓
客户端本地列表更新
  ↓
负载均衡器不再选择该实例
```

所以，“服务端已经删除”和“所有调用方都不再访问”不是同一个时刻。

真正的故障窗口是：

```text
服务端检测延迟 + 通知或刷新延迟 + 调用方重试策略
```

这也说明，实例抖动不能只靠缩短心跳解决。生产治理通常还需要：

- 调用超时；
- 有边界的重试；
- 熔断与隔离；
- 合理的客户端刷新机制；
- 幂等设计；
- 对长 GC、网络和容器事件的监控。

### 4.2 持久实例为什么不自动删除

持久实例由服务端主动探活。探测失败时，Nacos 可以把它标记为不健康，但不会替运维做“这个资产已经永久不存在”的决定。

因此，持久实例下线后仍留在列表里不是 bug，而是它的生命周期契约：

> **健康状态可以由系统判断，资产是否删除需要显式决定。**

## 五、服务发现的 AP 路径：Distro 如何工作

Distro 面向临时实例，目标不是让所有节点在每一瞬间完全相同，而是在高频变化下保持可用，并最终收敛。

可以把它理解为三件事：

1. 数据按规则分配 owner；
2. 写入先由 owner 处理；
3. owner 再把变化异步复制到其他节点。

### 5.1 owner 是算出来的，不是人工配置的

源资料用下面的简化表达说明 owner 选择：

```java
int target = distroHash(serviceName) % healthyNodeCount;
boolean responsible = targetFallsInCurrentNodeRange(target);
```

概念上可以理解为：

```text
对服务名做哈希
      ↓
对健康节点数取模
      ↓
落到某个节点负责的区间
      ↓
该节点成为这部分数据的 owner
```

一次注册请求可以到达任意 Nacos 节点。如果接收节点不是 owner，它会把请求转给 owner；owner 完成本地处理后，再把变化异步扩散到其他节点。

```text
Client
  │ 注册 service-X
  ▼
Node A（入口，不是 owner）
  │ 转发
  ▼
Node B（service-X 的 owner）
  │ 本地完成
  ├────────异步复制────────► Node A
  └────────异步复制────────► Node C
```

关键点在“异步”：请求不需要等待所有副本确认后才成功。因此吞吐和可用性更好，但其他节点看到变化会有时间差。

### 5.2 为什么临时实例需要这种设计

临时实例的特点是：

- 数量大；
- 上下线频繁；
- 心跳频繁；
- 状态天然有时效性；
- 消费方可以通过重试容忍少量旧地址。

如果每次心跳、注册、注销都等待多数派提交，高频瞬态数据会给共识协议带来不必要的压力；在网络分区期间，注册中心还可能整体拒绝变化。

Distro 选择的是：

> **先保证注册与查询继续可用，再通过异步复制和校验让副本收敛。**

### 5.3 异步复制失败后如何补偿

异步复制不保证一次送达，因此系统还需要校验机制。源资料描述的常态路径是：

- 节点周期性广播自己负责数据的 checksum；
- 对端比较 checksum；
- 只拉取需要更新或删除的差异；
- 不在每轮同步中传输全部数据。

这相当于给“快速但可能漏”的异步复制加上一层“慢一点但会纠偏”的反熵机制。

| 场景 | 同步方式 | 目的 |
| --- | --- | --- |
| 常态运行 | checksum 比对，只传差异 | 节省网络与序列化成本，修补漏同步 |
| 新节点冷启动 | 从健康节点拉全量快照 | 防止空节点直接对外返回空列表 |

### 5.4 为什么新节点必须先全量同步

一个刚加入集群的节点没有历史数据。如果它空着就开始接查询，消费者可能拿到空服务列表。

“稍旧”与“全空”不是同一种错误：

- 稍旧列表通常还能调用大多数实例；
- 空列表会让服务直接表现为完全不可用。

因此，新节点要先从健康对端拉取全量快照，完成预热后再对外提供服务。

### 5.5 为什么扩缩容可能引发列表抖动

owner 的计算依赖健康节点数：

```text
owner = hash(serviceName) % healthyNodeCount
```

当节点数变化时，大量服务会重新映射到新的 owner。随后会发生：

```text
节点数变化
  ↓
owner 大规模重新分配
  ↓
新 owner 缺少部分历史状态
  ↓
checksum 比对与数据拉取
  ↓
重建窗口中出现短暂缺失或不一致
  ↓
变化被推送到客户端
  ↓
消费者看到列表忽多忽少
```

因此，Nacos 集群扩缩容不是“多加一台机器就结束”。生产上应考虑：

- 低峰期操作；
- 分批变更；
- 观察节点数据同步和订阅推送；
- 为调用方保留重试与缓存兜底；
- 避免一次把节点数改得过大。

## 六、从 Nacos 1.x 到 2.x：UDP 与 gRPC 的变化

实例列表发生变化后，服务端要尽快通知订阅者。

在源资料的简化模型中：

| 维度 | Nacos 1.x | Nacos 2.x |
| --- | --- | --- |
| 主要推送通道 | UDP 推送 | gRPC 长连接 |
| 可靠性 | UDP 本身不可靠，需要轮询补偿 | 双向长连接，通知更可靠 |
| 连接模型 | HTTP 请求与额外推送机制 | 一条长连接复用多类交互 |
| 容量特征 | 短连接和轮询开销较高 | 连接复用，适合更多实例 |
| 关键端口 | 主要关注 8848 | 还要关注主端口偏移出的 gRPC 端口 |

可以把变化画成：

```text
Nacos 1.x
Server ──UDP 推送──► Client
Server ◄─HTTP 轮询── Client

Nacos 2.x
Server ◄════ gRPC 双向长连接 ════► Client
```

2.x 的收益不只是“换了协议名”，而是把注册、心跳、订阅通知等高频交互放进可复用的长连接，减少重复建连和空轮询开销。

### 6.1 最常见的升级陷阱：只开了 8848

源资料强调，2.x 的 gRPC 端口通常按主端口偏移计算：

```text
主端口       8848
客户端 gRPC  9848 = 8848 + 1000
节点间 gRPC  9849 = 8848 + 1001
```

于是会出现一种极具迷惑性的故障：

- 浏览器能打开控制台；
- `telnet 8848` 成功；
- HTTP 健康检查正常；
- 但 2.x 客户端不断报连接失败，无法注册。

第一排查方向不是 8848，而是：

- 9848 是否监听；
- 防火墙、安全组、容器端口和 Service 是否放通；
- 反向代理或四层负载均衡是否转发 gRPC；
- 客户端与服务端版本是否匹配。

### 6.2 升级顺序为什么要先服务端、后客户端

源资料给出的兼容结论是：2.x 服务端可兼容 1.x 客户端，但 2.x 客户端需要 gRPC，不能直接依赖 1.x 服务端提供对应能力。

因此更安全的顺序是：

```text
先升级 Nacos 服务端
  ↓ 验证旧客户端仍可用
再分批升级客户端
  ↓
观察注册、订阅和连接指标
```

升级中最危险的做法，是先把所有客户端升级，再发现服务端还没有对应协议能力。

---

## 七、客户端缓存：Nacos 挂了，调用为什么还能继续

服务消费者通常不会在每次业务请求前同步查询 Nacos。客户端会在内存和本地文件中保留服务列表快照。

简化后的取数顺序可以理解为：

```text
需要服务列表
  ↓
是否启用人工 failover 数据？
  ├─ 是：读取 failover
  └─ 否
       ↓
Nacos 服务端是否可达？
  ├─ 是：读取服务端结果，并更新 snapshot
  └─ 否：读取本地 snapshot 兜底
```

这带来两个同时成立的结论：

1. **Nacos 短时不可用，不一定让已有调用立即中断。**
2. **使用旧快照期间，客户端无法知道最新拓扑变化。**

假设整个 Nacos 集群暂时不可达：

- 已运行的 `order-service` 仍可能根据本地 snapshot 调用已知的 `user-service`；
- 新启动的 `user-service` 无法完成正常注册传播；
- 已下线实例可能仍留在旧列表中；
- 新实例也无法被已有消费者发现；
- 整个调用拓扑冻结在最后一次成功同步附近。

所以，客户端缓存是容灾能力，不是无限期替代注册中心的方案。

> **缓存把“服务端故障”从立即中断变成了数据逐渐过期。故障持续越久，拓扑失真越严重。**

---

## 八、配置中心：从长轮询到 gRPC 通知

服务发现传播的是实例列表，配置中心传播的是配置内容。两者都需要“变更尽快到客户端”，但历史实现路径并不完全相同。

### 8.1 经典长轮询为什么是 29.5s

短轮询的问题是，大多数请求都在问“变了吗”，答案却总是“没有”，浪费连接和服务器资源。

经典长轮询模型是：

```text
Client                               Server
  │                                    │
  │── 请求：当前 MD5，超时 30s ──────►│
  │                                    │ 挂起请求
  │                                    │
  │       配置变化时立即返回            │
  │◄──────── dataId 变化通知 ─────────│
  │                                    │
  │── 拉取最新配置 ───────────────────►│
  │                                    │
  │── 立即发起下一轮长轮询 ───────────►│
```

如果期间没有变化，服务端大约在 29.5s 时返回“无变化”，客户端随后立即发起下一轮。

为什么不是完整的 30s？

> 留出约 0.5s 给网络传输和客户端调度，避免客户端先达到 30s 超时，把正常的“无变化”响应误判为请求失败。

服务端也不是让一个工作线程傻等 29.5s。经典实现利用异步请求能力挂起连接，释放处理线程；只有超时或配置变化时才恢复响应。

### 8.2 为什么用 MD5，而不是每次传完整配置

客户端发起监听时会带上自己当前配置的 MD5。服务端只需比较摘要：

```text
clientMD5 == serverMD5  → 内容未变化
clientMD5 != serverMD5  → 通知客户端重新拉取
```

这样，变更检测与内容传输被拆开：

- 判断是否变化只比较摘要；
- 真有变化时才下载完整内容。

### 8.3 2.x 中通知方式发生了什么变化

源资料指出，2.x 起配置变更通知也可以并入 gRPC 长连接。服务端不必完全依赖 HTTP 长轮询来等待变化，而可以通过长连接发送配置变化通知。

但两个思想仍然值得保留：

- 通知只负责告诉客户端“可能变了”；
- 客户端仍要确认版本或摘要，并拉取实际配置。

因此，无论底层通知是长轮询还是 gRPC，都可以把配置发布链路拆成五步：

```text
① 控制台或 API 发布配置
        ↓
② 服务端持久化并记录变更
        ↓
③ 唤醒长轮询或发送 gRPC 通知
        ↓
④ 客户端拉取最新内容
        ↓
⑤ 应用内监听器处理，刷新相应 Bean
```

前四步主要由 Nacos 完成，第五步发生在你的 Spring 应用内部。大量“配置已发布但业务没生效”的问题，恰恰出在最后一步。

---

## 九、配置已到客户端，为什么业务代码还是旧值

Nacos 负责把变化送到应用，但“哪个对象要重新读取配置”属于 Spring 容器的刷新边界。

在源资料采用的 Spring Cloud Alibaba 基线中，可以这样理解：

| 注入方式 | 配置变化后的典型行为 |
| --- | --- |
| 只有 `@Value` | Bean 不重建，字段可能仍是旧值 |
| `@Value` 与 `@RefreshScope` 位于相应 Bean | Bean 在刷新时重建并重新注入 |
| `@ConfigurationProperties` | 在对应基线中支持刷新，具体行为需按版本核验 |

一个典型的可刷新 Bean：

```java
@RestController
@RefreshScope
public class FeatureController {

    @Value("${feature.rate:0}")
    private int rate;

    @GetMapping("/feature/rate")
    public int rate() {
        return rate;
    }
}
```

故障现象通常是：

```text
Nacos 控制台已更新
  ↓
客户端日志显示收到配置变化
  ↓
新内容已经拉到应用
  ↓
Bean 没有进入刷新边界
  ↓
字段仍保留初始化时的旧值
```

因此，排查“配置不生效”要分层：

1. 控制台中的 namespace、group、dataId 是否正确；
2. 客户端是否收到变化通知；
3. 客户端是否成功拉到新内容；
4. 环境变量和本地配置是否覆盖远端值；
5. 绑定配置的 Bean 是否支持刷新；
6. 业务代码是否在启动时把值复制进了另一个普通对象或静态字段；
7. 新值是否需要额外初始化、连接重建或缓存失效才能真正影响行为。

`@RefreshScope` 只能解决“重建 Bean 并重新注入”这一层，不能自动保证任意第三方连接池、线程池和静态单例都正确热更新。

## 十、灰度、回滚与配置持久化

配置的风险往往比代码发布更集中：一次错误配置可能在几秒内影响所有实例。因此配置中心不只需要“能发布”，还需要控制变更半径。

### 10.1 灰度发布

灰度或 beta 发布的核心不是创建另一个 dataId，而是限制推送对象：

```text
正式配置：risk.switch=off
       │
       ├─ 普通实例继续读取 off
       │
       └─ 指定两台金丝雀机器读取灰度值 on
```

一个安全流程可以是：

1. 选择两台金丝雀实例；
2. 按 IP 发布 beta 配置；
3. 观察业务指标、错误率和日志；
4. 验证通过后转为全量正式配置；
5. 验证失败则停止灰度或回退。

灰度期间，其余实例仍读取正式版本的旧值。

### 10.2 历史版本与回滚

每次发布都应该留下可追溯版本。发生错误时，回滚不应依赖人工重新拼写旧配置，而应从历史版本恢复。

但回滚也不是万能的：如果新配置已经触发不可逆操作，例如数据迁移、任务投递或外部调用，恢复旧值只能阻止后续影响，不能自动撤销已发生的副作用。

### 10.3 单机与集群存储

源资料给出的典型部署认知是：

| 部署形态 | 配置存储 | 适用场景 |
| --- | --- | --- |
| standalone | 内嵌 Derby | 本地开发、演示和测试 |
| cluster | 外置 MySQL | 生产集群，多节点共享配置状态 |

生产中一旦使用外置数据库，数据库本身就进入 Nacos 的可用性链路，需要考虑：

- 高可用与备份；
- 连接池容量；
- 慢 SQL；
- 磁盘与事务日志；
- 恢复演练；
- Nacos 与数据库之间的网络延迟。

不能一边宣称“Nacos 是高可用集群”，一边让所有节点依赖单机 MySQL。

---

## 十一、把 AP 与 CP 放进同一张图

现在可以把前面的机制收口为一张完整路径图：

```text
                         Client SDK
                             │
                    HTTP / gRPC 接入
                             │
                       Nacos Server
                             │
              按数据类型与 ephemeral 分流
                 ┌───────────┴───────────┐
                 │                       │
                 ▼                       ▼
        临时实例 ephemeral=true    持久实例 / 配置
                 │                       │
                 ▼                       ▼
           Distro · AP              Raft · CP
        内存状态、异步复制        持久化、多数派提交
        客户端心跳与超时删除      服务端探活或配置存储
                 │                       │
                 ▼                       ▼
       分区时两侧继续提供服务      只有多数派一侧允许写入
       恢复后异步收敛              少数派等待追平日志
```

### 11.1 5 节点集群被切成 3 + 2 时

| 数据类型 | 3 节点一侧 | 2 节点一侧 | 网络恢复后 |
| --- | --- | --- | --- |
| 临时实例，AP/Distro | 可继续注册与查询 | 也可继续注册与查询 | 异步同步并最终收敛 |
| 持久实例与配置，CP/Raft | 拥有多数派，可继续提交 | 无多数派，写入受限或失败 | 追平已提交日志 |

这就是 Nacos “支持 AP/CP”的准确含义：

> **不是把整个集群从 AP 模式切成 CP 模式，而是让不同数据在同一时刻走不同协议。**

### 11.2 为什么注册中心通常优先 AP

注册中心返回一个稍旧的列表，后果通常是：

- 偶尔调用到刚下线实例；
- 通过超时、重试和熔断切换到其他实例；
- 新实例晚几秒被发现。

而注册中心在网络分区时整体拒绝服务，后果可能是：

- 新实例无法注册；
- 消费者无法查询；
- 大规模扩缩容和故障恢复停摆；
- 服务网格的动态拓扑被冻结。

因此，对高频变化的临时实例，短暂不一致通常比不可用更容易被业务系统吸收。

### 11.3 为什么配置更需要 CP

配置的错误不是“少一个地址”，而可能是：

- 两台机器计算价格使用不同费率；
- 部分实例开启高风险功能，部分没有；
- 权限开关在不同节点上不一致；
- 数据格式和下游协议产生分裂。

同一 dataId 在不同 Nacos 节点上同时接受相互冲突的写入，恢复后很难仅靠“最后同步”安全解决。因此配置更适合多数派提交和强一致语义。

## 十二、选型：Nacos 不应该和所有产品用同一把尺子比较

### 12.1 注册中心维度

| 方案 | 一致性倾向 | 主要特点 | 更适合什么情况 |
| --- | --- | --- | --- |
| Nacos | 临时实例 AP，持久数据可走 CP | 注册与配置二合一，Spring Cloud Alibaba 集成好 | Java/Spring Cloud Alibaba 体系，希望减少中间件数量 |
| Eureka | AP | 客户端心跳、自我保护，体系简单 | 已有遗留系统；新项目需评估维护状态与生态 |
| Consul | CP/Raft | 健康检查、多数据中心、服务网格能力 | 多语言、多数据中心、Mesh 诉求明显 |
| ZooKeeper | CP/ZAB | 临时节点、顺序节点、协调能力强 | 分布式协调；不宜只因“能放临时节点”就直接当注册中心 |

不能只问“谁更强”，而要问：

- 网络分区时，注册是否必须继续？
- 是否强依赖 Spring Cloud Alibaba？
- 是否需要多数据中心和服务网格？
- 团队是否具备额外中间件的运维能力？
- 注册中心是否还要承担配置中心职责？

### 12.2 配置中心维度

| 方案 | 主要特点 | 更适合什么情况 |
| --- | --- | --- |
| Nacos | 注册与配置一体化，支持通知、灰度和历史版本 | 已经使用 Nacos 注册，希望降低系统复杂度 |
| Apollo | 权限、审计和配置治理体系更强 | 大组织、细粒度权限、严格审计流程 |
| Spring Cloud Config | Git 作为配置源，模型直接 | 配置变更频率低、团队强依赖 Git 流程 |
| Consul KV / etcd | 通用 K/V | 已重度使用对应基础设施，并愿意自建配置治理体验 |

对一个小型 Java/Spring Cloud 团队，如果既需要注册又需要配置，没有强审计诉求，一套 Nacos 往往比“Eureka + Apollo”更简单。

但当权限、审计、审批和复杂组织治理成为核心约束时，Apollo 的治理能力可能比“一体化”更重要。

## 十三、生产前必须拧紧的螺丝

默认配置往往只保证“容易启动”，不保证适合生产。

### 13.1 保护阈值

源资料特别提醒 `protect-threshold`。它表达的是健康实例占总实例的比例阈值。

当健康占比低于阈值时，Nacos 可能返回全部实例，包括被标记为不健康的实例。逻辑是：

```text
只返回少量健康实例
  ↓
所有流量挤到这几个实例
  ↓
剩余健康实例也被压垮
  ↓
雪崩
```

保护模式选择的是另一种风险：与其确定性压垮少数健康实例，不如把流量摊开，赌一部分“被判不健康”的实例仍能处理请求。

阈值不是越大越好。它会把不健康实例重新暴露给调用方，必须结合：

- 调用超时；
- 重试预算；
- 熔断；
- 实例规模；
- 健康检查误判率；
- 业务是否允许失败请求。

### 13.2 端口与网络

至少明确检查：

- 控制台与 OpenAPI 端口；
- 客户端 gRPC 端口；
- 节点间通信端口；
- 安全组和防火墙；
- Kubernetes Service、Ingress 或 LoadBalancer 的协议转发；
- NAT、代理和连接空闲超时；
- TLS、鉴权与 token 配置。

“端口监听”不等于“端到端可用”。应该从真实客户端网络路径验证。

### 13.3 JVM 与容量

容量规划不能只看配置条数，还要看：

- 注册实例数量；
- 服务数量；
- 客户端长连接数；
- 心跳和订阅变更频率；
- 配置大小；
- 推送风暴；
- 扩缩容时的数据重分配；
- GC 停顿；
- 集群节点间网络。

生产监控至少应覆盖：

- JVM 堆、GC 和线程；
- CPU、负载、磁盘与网络；
- 注册实例与服务数量；
- 客户端连接数；
- 配置发布和通知延迟；
- 数据库连接池与 SQL 延迟；
- 节点健康与选主状态；
- 注册、查询、订阅和配置接口错误率。

### 13.4 外置数据库

如果集群配置依赖 MySQL，数据库就是关键依赖。应确认：

- 多副本与故障转移；
- 备份是否可恢复；
- 连接上限是否匹配 Nacos 节点数；
- Schema 与 Nacos 版本是否匹配；
- 升级前是否做兼容检查；
- 数据库故障时，配置读取与发布分别会发生什么。

### 13.5 认证与升级

不要把内网等同于安全边界。生产环境应明确：

- 是否开启认证；
- 默认账号与密钥是否已更换；
- namespace、group 和配置权限如何划分；
- 控制台是否暴露到不必要的网络；
- 审计日志是否满足要求；
- 升级是否经过兼容矩阵和回滚演练。

---

## 十四、高频故障：沿数据链路反向排查

### 14.1 调用到已下线实例

```text
实例崩溃
  ↓
心跳超时检测需要时间
  ↓
服务端标记不健康并删除
  ↓
客户端列表尚未刷新
  ↓
负载均衡仍选中旧地址
  ↓
超时、重试、抖动
```

排查：

1. 实例是否优雅注销；
2. 最后心跳时间和健康状态；
3. 服务端何时删除；
4. 客户端何时收到推送；
5. 本地 snapshot 是否过旧；
6. 调用超时和重试是否放大流量；
7. 是否发生长 GC 或网络抖动。

### 14.2 扩容后服务列表忽多忽少

因果链：

```text
健康节点数变化
  ↓
Distro owner 重新计算
  ↓
大量数据重新归属
  ↓
新 owner 拉取与重建状态
  ↓
短暂不一致被推送到客户端
```

对策是低峰、分批、观察同步，而不是在抖动时继续快速加节点。

### 14.3 服务注册成功，但其他人发现不到

优先检查：

```text
server-addr
  ↓
namespace ID
  ↓
group
  ↓
service name
  ↓
cluster 与订阅条件
  ↓
实例健康状态
```

最常见的误区是把 namespace 显示名当作 ID，或者一端使用 `public`，另一端使用自定义 namespace。

### 14.4 Nacos 2.x 客户端连不上，但 8848 正常

优先检查 9848/9849、gRPC 转发、版本兼容和升级顺序。

不要只做 `curl 8848` 就宣布网络正常，因为那只能证明 HTTP 路径的一部分可达。

### 14.5 配置改了不生效

按五段链路逐层定位：

```text
发布是否成功
  ↓
服务端是否持久化
  ↓
客户端是否收到通知
  ↓
客户端是否拉到新内容
  ↓
Spring Bean 是否刷新并真正影响业务
```

如果日志已经明确收到新配置，就不要继续盯着 Nacos 控制台；应转向 Spring 刷新边界、属性覆盖关系和业务对象缓存。

### 14.6 Nacos 全挂，但调用一开始没受影响

这是 snapshot 容灾在工作，不代表系统没有风险。

继续观察：

- 新实例无法被发现；
- 已下线实例无法及时移除；
- 重启后的消费者是否还有可用快照；
- 故障持续多久；
- 本地快照是否跨版本兼容；
- 拓扑失真是否已经影响流量。

## 十五、把 Nacos 记成四条链，而不是一堆名词

### 15.1 临时实例注册链

```text
实例启动
  ↓
注册到任意 Nacos 节点
  ↓
请求转发给 Distro owner
  ↓
owner 更新内存状态
  ↓
异步复制到其他节点
  ↓
通过 gRPC 通知订阅客户端
  ↓
客户端更新服务列表
```

### 15.2 临时实例故障链

```text
实例停止心跳
  ↓
约 15s 标记不健康
  ↓
约 30s 删除临时状态
  ↓
变化推送到客户端
  ↓
客户端刷新本地列表
  ↓
调用方停止选择旧地址
```

### 15.3 配置发布链

```text
控制台 / API 发布
  ↓
服务端持久化
  ↓
长轮询唤醒或 gRPC 通知
  ↓
客户端比较版本 / MD5
  ↓
拉取最新内容
  ↓
Spring 刷新相应 Bean
  ↓
业务代码读取新值
```

### 15.4 故障容灾链

```text
Nacos 暂时不可达
  ↓
客户端无法获得新拓扑
  ↓
读取本地 snapshot
  ↓
已有调用继续
  ↓
拓扑逐渐过期
  ↓
故障过久后风险持续增大
```

这四条链覆盖了绝大多数面试题和线上排障题。遇到问题时，只要先判断它属于哪条链，再找链路在哪一跳断了，就不容易陷入“盲目改参数”。

## 十六、自测：你是否真正理解了这条分流线

先合上文章作答，再回来核对。

### 16.1 概念题

1. 唯一定位一个服务需要哪些坐标？cluster 参与吗？
2. 临时实例和持久实例的健康分别由谁判定？
3. 临时实例最后一次心跳后，典型情况下何时标记不健康、何时删除？
4. `pay-service-test.yaml` 可以拆成哪三部分？
5. 服务发现和配置中心复用了哪两个隔离维度？

### 16.2 原理题

6. Distro 如何决定一个服务数据的 owner？
7. 常态同步为什么只传差异？新节点为什么要先拉全量？
8. 2.x 用什么替代了 1.x 的 UDP 推送与轮询补偿组合？
9. Nacos 全部不可达时，已运行服务为什么可能仍能调用？此时看不到什么？
10. 配置长轮询为什么在约 29.5s 返回，而不是顶满客户端 30s 超时？
11. 配置通知已收到，但普通 `@Value` 字段仍是旧值，最可能缺少什么刷新边界？

### 16.3 场景题

12. 一个固定网关停机后仍要保留在注册表中，由运维手动删除。应注册为临时实例还是持久实例？
13. Java/Spring Cloud 新项目同时需要注册和配置，团队小且没有强审计诉求，为什么一套 Nacos 可能比 Eureka + Apollo 更合适？
14. 一个高风险开关只想先给两台机器验证，应使用什么发布方式？其他实例此时读到新值还是旧值？
15. 2.x 客户端注册失败，但 8848 可达，第一排查方向是什么？
16. “注册中心在网络分区时仍可用，配置必须强一致”，一套 Nacos 能否同时满足？

### 16.4 参考答案

1. `namespace + group + service`；cluster 不参与服务唯一定位。
2. 临时实例由客户端心跳维持，持久实例由服务端主动探活。
3. 源资料中的典型值是约 15s 标记不健康、约 30s 删除。
4. `pay-service`、`test`、`yaml`，分别对应 prefix、profile 和扩展名。
5. namespace 与 group。
6. 对服务名做哈希，再结合健康节点数映射到 owner 区间。
7. 差异同步节省带宽并修补异步复制遗漏；新节点若空着服务会返回空列表，所以要先全量预热。
8. gRPC 双向长连接。
9. 客户端使用本地 snapshot；此时无法感知新的上下线变化，拓扑被冻结。
10. 为网络往返和调度留余量，避免客户端先超时。
11. 常见原因是承载 `@Value` 的 Bean 没进入 `@RefreshScope`；具体刷新行为要按依赖版本核验。
12. 持久实例，因为失败后只标不健康、不自动删除。
13. 注册与配置二合一、Spring Cloud Alibaba 集成成本低，也少维护一套中间件；若有强权限审计诉求则应重新评估 Apollo。
14. 灰度或 beta 发布；未被选中的实例继续读取正式旧值。
15. 检查 9848/9849、gRPC 网络链路和版本兼容。
16. 可以。临时实例走 Distro/AP，配置走 CP 路径，两者在同一集群并存。

## 十七、最后的心智模型

不要把 Nacos 记成“注册中心 + 配置中心”两个功能列表，也不要把它粗暴贴成 AP 或 CP。

更有解释力的模型是：

> **Nacos 是一个根据数据生命周期与业务容错预期，选择不同一致性路径的系统。**

- 临时实例变化快、可替换、允许短暂旧列表，所以走 Distro/AP；
- 持久实例有固定身份，不应因短暂失联被自动删除，所以走 CP 侧；
- 配置错误的语义成本高，需要持久化和强一致，所以也走 CP 侧；
- 客户端通过 gRPC 接收变化，同时用本地 snapshot 抵抗服务端短时故障；
- Spring 是否真正使用新配置，取决于应用内的刷新边界；
- 生产故障通常不是单点机制失效，而是检测延迟、异步传播、缓存和重试叠加后的结果。

最终，你只需要记住这张最小图：

```text
                         ephemeral?
                    ┌────────┴────────┐
                    │                 │
                  true          false / config
                    │                 │
              Distro · AP         Raft · CP
              内存、异步复制      持久化、多数派
              心跳、自动删除      探活/配置、不自动丢
                    │                 │
             可用性优先           一致性优先
```

当你能用这张图解释下面五件事，Nacos 的主干就真正建立起来了：

1. 临时实例为什么会自动消失；
2. 持久实例为什么下线后仍存在；
3. 网络分区时两类数据为什么命运不同；
4. Nacos 全挂时已有调用为什么还能短暂继续；
5. 配置已经送到客户端，为什么业务代码仍可能没有刷新。

这比背几十个配置项更重要。配置项会随版本变化，而数据类型、生命周期、一致性、传播和缓存之间的因果关系，才是能迁移到其他分布式系统的知识。
