一家零售企业同时经营门店、电商和经销渠道。每个渠道都有自己的订单系统，仓库也有独立的软件。业务增长之后，问题开始集中出现：门店显示有货，线上却不能下单；客户付款成功，仓库才发现库存已经被另一渠道占用；集团想分析订单取消原因，各部门交来的数据口径又不一致。

如果只看局部，可以分别提出采购新系统、增加接口、建设数据平台等方案。但管理层还需要回答更大的问题：谁有权承诺库存？跨渠道订单由谁协调？哪些能力应该统一，哪些差异应当保留？预算有限时，先改哪一部分，才能让业务尽快受益？

企业架构工作就在这些问题之间建立联系：把业务目标、组织责任、信息定义、应用协作与技术能力放到同一张决策地图中，说明为什么改变、改变什么、怎样分步实施，以及如何判断改变是否有效。

本文以 **TOGAF Standard, 10th Edition（第十版）**为依据。官方出版页面注明，该版本于 2025 年 5 月应用了第一号技术勘误；本文查阅日期为 2026 年 10 月 22 日。[1] 文中的零售企业、系统名称、数值目标和实施周期均为教学假设，不代表行业基准。阶段安排、工作表和治理建议是对方法的示例应用，不应理解为 TOGAF 要求所有企业采用的固定模板。

**一、从企业需要作出的决策，理解企业架构**

企业架构的价值，要从企业面临的变化来判断。

假设零售企业准备开展“线上下单、门店发货”。这句话看似只是一个新功能，实际上会牵动销售归属、门店作业、库存分配、客户承诺和售后结算。如果技术团队提前选定一套订单产品，却没有解决门店是否愿意发货、占用库存如何释放等问题，系统可能上线了，业务仍然运行不起来。

因此，架构工作的起点应当是一组需要跨部门共同决定的问题：目标客户需要怎样的服务？现有能力缺在哪里？哪些责任和规则必须调整？什么约束不能突破？

为了方便协作，本文采用以下职责划分。实际企业可以调整岗位名称，关键是明确决策范围。

| 工作层次 | 主要关注的决策 | 案例中的问题 |
|---|---|---|
| 企业架构 | 跨业务、跨组织和跨系统的整体方向及演进关系 | 是否建立共享的订单履约协调能力，分几步形成 |
| 解决方案架构 | 某项业务变化所需的完整实现方案 | 线上下单、门店发货涉及哪些应用和交互 |
| 系统架构 | 单个系统内部的结构、机制与质量要求 | 库存预留如何处理并发、超时和重复请求 |

这三层之间存在反馈。例如，系统团队验证后发现某种实时同步方案无法满足成本约束，企业架构就应当重新评估服务承诺或迁移顺序。整体方向需要接受实施证据的检验。

在本案例中，第一轮工作的范围可以限定为“直营渠道的订单履约”，暂时不包含海外渠道和供应商结算。这样既能覆盖真正的跨部门问题，也给调查、决策和交付设定了边界。

**二、TOGAF 提供怎样的一套工作方法**

TOGAF 第十版由基础内容与系列指南共同构成。基础内容提供框架的核心概念和方法，系列指南进一步讨论业务能力、价值流、敏捷实践以及架构能力建设等具体主题。[1][5]

可以沿着四个问题理解这套框架：

- **工作怎样开展？** 使用 ADM（Architecture Development Method，架构开发方法）组织架构活动。
- **结果怎样表达？** 使用架构内容相关概念描述模型、要求、决策和交付物。
- **经验怎样复用？** 通过架构资产的分类、维护和复用，减少重复分析。
- **谁来持续推动？** 建立架构角色、决策机制和治理能力。[2]

企业使用时仍然需要选择范围、确定参与者、裁剪活动。对一家正在整合多套订单系统的企业而言，系统责任和迁移风险可能最紧迫；对一家正在进入新市场的企业而言，业务能力和组织运作方式可能需要先得到澄清。

TOGAF 的框架本身不会自动生成企业的正确答案。企业需要用自身的业务证据填充分析过程，并让能够承担后果的人参与决策。

本文采用这样的阅读顺序：先理解四个架构域，再学习 ADM 如何组织工作，最后把设计结果连接到交付物、项目实施与持续治理。

**三、四大架构域：同一个变化的四个观察角度**

TOGAF 覆盖业务架构、数据架构、应用架构和技术架构四个主要架构域。在 ADM 中，业务架构对应 B 阶段，数据架构与应用架构共同属于 C 阶段的信息系统架构，技术架构对应 D 阶段。[3]

下面用订单履约案例解释四个架构域如何联系起来。

| 架构域 | 本案例需要回答的问题 | 示例设计结果 |
|---|---|---|
| 业务架构 | 谁向客户承诺交付？如何分配订单？异常由谁处理？ | 订单履约能力图、发货责任、异常处理流程 |
| 数据架构 | 怎样定义可售库存？订单、预留和发货之间是什么关系？ | 核心数据定义、数据责任和状态变化规则 |
| 应用架构 | 哪些系统接单、协调履约、占用库存和执行发货？ | 应用职责边界、交互关系和接口约定 |
| 技术架构 | 怎样支撑上述协作，并满足运行与恢复要求？ | 集成方式、身份认证、可观测性和部署方案 |

业务架构先回答“企业需要具备什么能力”。例如，库存承诺是一项业务能力：企业能够对客户判断并承诺某件商品是否可以在指定地点和时间交付。

业务流程则描述在具体情境下如何完成工作。线上订单可能依次经过资格检查、库存预留、支付确认和履约分配；门店订单的操作顺序可能不同。同一能力可以支持多个流程，一条流程也会使用多项能力。官方业务能力指南将能力描述为企业做什么；价值流指南则关注为利益相关者创造价值的整体过程。[7][8]

数据架构需要进一步澄清“库存”究竟是什么。账面库存、物理在库、已预留和可承诺数量可以不同。本文案例中的可承诺数量暂按“可参与销售的数量减去有效预留，再减去安全缓冲”计算。这个公式只是案例假设，企业还应明确在途、质检、损坏、退货等状态是否参与计算。

应用架构据此分配责任。渠道系统负责接收订单，履约协调应用负责选择履约路径，库存预留服务负责接受或拒绝预留，仓储系统负责实际出库。责任明确之后，才能设计接口和事件。

技术架构再回答这些交互如何可靠运行。例如，跨系统事件是否允许延迟，重复请求如何识别，积压如何发现，故障时如何保持库存预留记录可核对。具体实现仍需要解决方案和系统设计继续细化。

四个架构域形成的联系可以写成一条可检查的推导链：

**减少付款后缺货取消 → 建立一致的库存承诺规则 → 明确预留数据及其责任方 → 约束应用的预留入口 → 验证并发、故障和恢复行为。**

安全、成本和可用性需要贯穿这条链。本案例在业务层确定库存调整权限，在数据层规定敏感字段的访问要求，在应用层限定调用权限，在技术层实现身份验证、密钥管理和审计留存。

**四、ADM：让架构设计形成可执行的变化**

ADM 包含预备阶段、A 至 H 阶段，以及贯穿全过程的需求管理。其结构覆盖架构愿景、各领域架构、解决方案与迁移、实施治理和架构变更。[3]

阅读时可以沿阶段理解工作顺序，实施时则需要根据问题反馈和迭代。例如，迁移评估发现数据质量不足，就可能返回数据架构补充约束。官方也提供了将 ADM 与敏捷迭代结合的指南。[5]

下面各段先概括阶段关注点，再展示本文案例可以怎样开展工作。列举的交付结果允许合并维护，并不意味着每一项都要成为独立文档。

**预备阶段（Preliminary）：先让架构工作具备决策条件。**

这一阶段关注架构能力、治理安排、原则以及方法的配置。[3] 在本案例中，应先确定业务发起人、参与范围和决策责任：运营负责人确认履约目标，渠道负责人确认销售规则，仓储负责人确认作业约束，技术负责人组织方案验证。

团队还需要约定三个基本原则：库存预留必须能追踪到订单；库存调整必须有责任来源；进入试点的业务必须具备对账和恢复方案。每个原则都写出理由、适用范围及实施影响，避免只有一句口号。

建议保留一页工作约定，说明谁参与、谁批准、哪些争议需要升级，以及当前允许作出哪些决策。没有决策权的人可以完成分析，但无法替代业务负责人接受经营取舍。

**A 阶段：架构愿景（Architecture Vision）。**

这一阶段形成架构愿景，明确范围、利益相关者和工作授权。[3] 案例中的愿景可以是：在指定直营渠道建立可追踪的库存预留与履约协调能力，减少付款后因缺货取消的订单。

“提升体验”还不足以指导设计。团队需要明确观察什么：付款后缺货取消率如何计算，哪些订单属于分母，哪些原因属于缺货，取消原因由谁归类。假设试点区域过去八周的观测值为 1.2%，业务提出将其降到 0.5% 以下。该目标是待验证假设，并不代表某种系统改造必然能够实现。

A 阶段应当使相关方对问题、范围、预期价值和主要风险形成一致理解。架构工作说明书可以据此明确活动、责任和验收安排。

**B 阶段：业务架构（Business Architecture）。**

本案例先梳理从客户下单到收到商品的价值过程，再识别库存承诺、订单分配、拣货发运和异常处理等能力。

现状调查可能发现：各渠道都能接受订单，却没有共同认可的库存承诺责任方；订单无法发货后，客服、门店和仓库互相转交。目标业务设计就需要补上责任与规则：谁接受预留，谁可以释放预留，超时由谁处理，门店无力履约时由谁重新分配。

这一步需要业务负责人确认。把责任争议留到接口联调阶段，会迫使开发团队在缺少业务授权的情况下作出经营决策。

本案例的阶段结果包括业务能力差距、目标流程、责任分配，以及需要后续系统支持的业务规则。

**C 阶段：信息系统架构（Information Systems Architectures）。**

C 阶段包含数据架构和应用架构。[3] 两者可以根据问题相互推进。本案例先给订单、订单明细、库存位置、预留和发货单建立明确的身份与关系，再确认应用如何创建和使用它们。

例如，一条订单明细允许拆成多次发货，就不能假设订单明细与发货单永远一一对应。预留成功、已释放、已消费也需要不同的业务含义，否则对账时无法解释数量为什么变化。

然后明确应用责任：渠道系统不能绕过预留入口修改有效预留；仓储系统的实际出库需要关联业务依据；协调应用遇到超时，必须能够查询已有操作的结果。

数据责任可以按实体、字段和状态变化进一步划分。商品描述由商品系统维护，库存实物数量由仓储执行事实支撑，预留承诺由约定的预留机制维护。这种划分不要求把所有数据都存进同一个数据库。

本案例的阶段结果包括数据定义、关系模型、应用协作图，以及最关键的接口与事件约束。

**D 阶段：技术架构（Technology Architecture）。**

技术设计从业务语义继续推导。渠道看到的库存展示可以存在一定延迟，但接受订单所依赖的预留结果需要明确的成功、失败或待确认状态。否则，页面显示正常仍可能掩盖履约风险。

本案例需要验证的能力包括请求身份识别、重复请求处理、事件投递与补偿、跨系统追踪、故障恢复和业务对账。团队可以通过原型检验最危险的假设，例如旧仓储系统能否提供足够准确的库存变动记录。

技术选择还要考虑现有团队能否运营。一项方案即使在功能上成立，如果缺乏监控、值守和恢复能力，也不宜直接承载关键业务。

本案例的阶段结果是技术方案、关键质量要求和验证证据。产品型号或部署规格只在影响关键决策时进入企业架构层面的描述。

**E 阶段：机会与解决方案（Opportunities and Solutions）。**

E 阶段关注如何将架构差距转化为工作包，识别实施方式和必要的过渡架构；F 阶段则进一步形成有优先级、可协调的迁移计划。[3][4]

对于本案例，可以识别五个工作包：统一数据定义与标识、建设预留能力、改造渠道调用、建设履约协调能力、建立对账与异常处理机制。每个工作包都应注明解决哪些差距、依赖什么，以及完成后形成什么可用能力。

企业还要比较购买产品、改造现有应用和自行开发等选择。比较依据应包括适配程度、实施成本、运行成本、迁移风险及长期维护责任。

此时可能确定一个过渡架构：先让某一区域的线上订单进入共享预留机制，其他业务继续按现有方式运行，同时用明确的库存分区或额度规则约束两者之间的竞争。

**F 阶段：迁移规划（Migration Planning）。**

本案例中，渠道改造依赖标识统一和预留接口，试点放量依赖对账能力与异常处理值守。因此，不能简单按照功能清单的书写顺序安排项目。

团队需要估计工作量、成本和风险，与项目管理、业务运营及交付团队协调资源，并确定每一批次的进入和退出条件。架构路线图表达能力如何逐步形成；实施与迁移计划进一步明确如何组织这些变化。两者需要衔接，实际项目排期还会继续细化。[4][6]

例如，试点可以要求连续两周完成约定范围的日常对账，并验证重复请求、超时和人工修复场景，再决定扩大范围。这里的“两周”只是案例安排，真实窗口应根据业务周期和风险确定。

**G 阶段：实施治理（Implementation Governance）。**

G 阶段关注实施治理，包括符合性评估及相关治理活动。[4] 本案例的检查应当落到具体证据：调用方是否真正使用约定的预留入口，接口是否满足幂等要求，业务状态能否对账，故障演练是否验证了恢复能力。

当团队需要偏离目标方案时，应记录理由、影响、替代控制措施、责任人和复查日期。例如，某旧渠道暂时只能批量同步，可以限定其试点范围并采用单独的库存额度，但不能假定它已经具备实时共享预留的能力。

架构契约用于明确架构相关的约定与责任，可以与企业已有交付机制衔接。[6] 本案例可以据此约定实施范围、质量要求、验收证据和变更处理责任。

**H 阶段：架构变更管理（Architecture Change Management）。**

H 阶段关注架构变更及其管理。[4] 本案例上线后需要观察，缺货取消是否下降，人工处理负担是否增加，新的业务渠道是否改变原先假设。

如果变化只是一个局部参数调整，可以走已有变更流程；如果企业新增跨区域履约，库存归属、组织责任和应用协作都发生变化，就需要重新评估工作范围，决定是否启动新一轮 ADM。判断依据是影响程度和治理约定。

**需求管理：让每一次变化都能追踪到设计和验收。**

需求管理贯穿 ADM。[3] 本案例可以为“付款前必须获得有效库存预留”赋予一个稳定编号，关联到业务规则、预留数据、应用接口、技术验证和上线验收。

当业务提出“部分客户可以后补库存”时，团队就能够识别哪些规则、模型、实现与指标受到影响，再由相关负责人共同决定是否接受变化。

**五、从现状到目标：让分析能够支持取舍**

了解 ADM 之后，还需要解决一个实际问题：访谈、图表和系统清单怎样转化为决策依据？TOGAF 的相关技术包括利益相关者管理、差距分析、风险与能力评估等。[4] 以下是本文建议的应用方式。

先记录利益相关者真正关心的事情。渠道负责人可能关注转化率，仓储负责人关注作业负荷，客服负责人关注解释和处理异常的时间，财务负责人关注投资与持续成本。这些目标可能冲突，需要写出冲突发生的具体情境。

例如，渠道希望尽量少拒绝订单，仓库希望减少无法发货的任务。双方可以共同讨论可承诺规则与异常处置，而不只是争论库存数字应该显示得更高还是更低。

然后建立足以支撑决策的基线架构。对本案例，调查重点包括订单入口、库存修改入口、关键标识、责任分配和异常记录。没有必要为与本轮问题无关的系统补齐所有内部设计。

基线描述要区分“设计上如此”和“实际运行如此”。应用清单声称只有仓储系统调整库存，运行记录却可能显示渠道也能直接写入。遇到这种差异，应当记录证据和待确认事项，避免把陈旧图纸当成现实。

目标架构应明确预期能力和约束，并让各领域保持一致。差距分析则说明从当前状态达到目标，需要保留、改变、新增或退出什么。下面是一张案例工作表。

| 观察到的现状 | 目标要求 | 差距与处理方式 | 验收证据 |
|---|---|---|---|
| 同一商品在渠道与仓库的标识不同 | 在试点范围能够准确关联商品和库存位置 | 建立映射与异常校验 | 抽样、全量校验及未匹配记录处理结果 |
| 多个渠道独立预留同一份库存 | 对共享库存采用共同认可的预留规则 | 改造调用入口与库存分配规则 | 竞争请求与重复请求的验证结果 |
| 超时请求靠人工猜测是否成功 | 能依据业务标识查询最终结果 | 增加状态查询与对账机制 | 超时、断网和重试场景记录 |
| 取消原因主要依赖自由文本 | 能稳定统计缺货相关取消 | 统一原因分类并抽查质量 | 指标口径及分类准确性检查 |

差距需要有负责人和证据来源。假设“取消主要由库存同步延迟造成”，应当检查取消订单的样本，排除商品下架、地址错误、门店拒单等原因。如果根因判断错误，目标架构也可能解决错问题。

方案评估可以采用少量明确维度：业务效果、实现成本、持续成本、交付风险、退出成本和组织准备度。评分用于显露分歧，权重由相关方讨论；不能用看似精确的总分掩盖某项不可接受的限制。

例如，统一购买一套大型业务套件可能减少部分接口，却需要较长的业务迁移时间；渐进改造可能更快形成试点能力，却要长期承担一段时间的混合运行成本。选择应当留下业务条件与验证依据，方便条件变化后重新评估。

**六、交付物：让不同角色能够使用架构结果**

TOGAF 的架构内容涉及交付物、制品和构建块等概念。[4] 可以结合案例把它们区分开来。

- **交付物（Deliverable）**：约定要交付并接受评审的工作成果。例如，本轮订单履约架构定义文档。
- **制品（Artifact）**：针对某个方面形成的架构表达。例如，应用目录、应用与业务能力映射矩阵、系统交互图。
- **构建块（Building Block）**：可以组合到架构或解决方案中的能力单元。例如，库存预留能力。[9]

一份交付物可以包含多个制品。图表则可以描述构建块及其关系。视图（View）呈现面向特定关注点的架构内容，视点（Viewpoint）规定组织和解释这类视图的约定。[9] 在本案例中，业务负责人需要看到能力与责任，实施团队需要看到应用交互；两者基于同一套事实，采用不同的表达。

对于构建块，架构构建块（ABB）侧重需要的能力，解决方案构建块（SBB）侧重实现这些能力的具体组成。[9] 案例中的 ABB 可以定义为“支持可追踪预留与释放的库存承诺能力”；SBB 则可以是选定产品的预留模块、适配组件及其具体配置。两者的映射不必是一一对应。

本文建议第一轮工作重点维护以下成果。这些说明是便于使用的职责划分，文档结构可参考官方模板，并按企业情况裁剪。[6]

| 成果 | 在案例中帮助解决什么问题 |
|---|---|
| 架构愿景 | 本轮为什么做、面向谁、预期改善什么 |
| 架构工作说明书 | 工作范围、参与责任、交付安排与批准条件是什么 |
| 架构定义文档 | 基线、目标和过渡状态怎样组织，各部分如何协作 |
| 架构需求规格 | 实施必须满足哪些要求，如何判断满足 |
| 架构路线图 | 哪些变化分批形成哪些能力，批次之间如何依赖 |
| 实施与迁移计划 | 如何协调资源、项目、时间和切换活动 |
| 架构契约与符合性记录 | 交付约定是什么，实施证据与约定是否一致 |

**架构定义文档与架构需求规格要相互关联。** 在本案例中，前者可以描述“各渠道通过指定入口申请库存预留”；后者写清“使用同一业务标识重试预留，不应产生第二笔有效占用”，并说明验证条件。结构描述和可验证要求共同帮助团队完成交付。

**架构路线图需要表达能力变化。** “第三季度完成平台一期”还不足以支持判断。如果写成“指定区域的线上订单已使用共享预留，并能完成日常对账”，业务方才能理解这笔投入带来了什么。

架构知识还需要持续维护。TOGAF 使用企业连续体帮助理解和分类从通用到组织特定的架构与解决方案资产，架构存储库则用于组织和保存相关资产。[9] 对本案例，可以将共享的接口模式、企业库存规则、实际应用模型及评审记录关联起来，说明各自适用范围和版本。

本文建议为每项重要资产至少记录责任人、状态、版本、适用范围和更新时间。目标方案经过评审，并不意味着已经部署；项目完成，也不意味着所有旧路径都已退出。资产状态必须反映这些差异。

工具可以从现有文档库、版本库和工作跟踪系统起步。是否引入专门的架构管理工具，应由模型规模、关系查询需求、维护能力与协作成本决定。

**七、架构治理：让决策、执行与证据保持一致**

架构治理要服务于实际决策。本文建议根据影响范围分配决策权：业务负责人决定服务承诺和业务规则，企业架构负责人协调跨域一致性，交付团队决定授权范围内的实现细节，跨部门争议进入能够承担经营后果的治理机制。

在本案例中，“是否允许同一库存同时被两条预留路径占用”需要业务与技术共同决定；某个内部函数如何命名，通常可以由团队自己处理。治理范围清楚，才能让评审时间用于真正重要的问题。

可以把检查安排在三个关键时点：项目立项时确认目标与依赖，重大方案确定时确认跨系统影响，上线或扩围前确认实施证据。这些检查可以嵌入已有流程，并根据风险调整深度。

一次有效的例外处理，至少应该回答：偏离了哪项要求，为什么暂时无法满足，有什么风险，采取了什么补偿措施，由谁接受，什么时候复查。

例如，旧渠道无法支持实时预留，团队决定暂时给它分配独立库存额度。记录中需要明确额度归属、调整规则、对账方式和退出条件。否则，“临时措施”会在扩围后继续生效，却没有人知道它已经改变了目标架构的假设。

架构决策记录也应写出被考虑的方案、选择理由和重新评估的触发条件。假设方案依赖每日订单不超过某个验证规模，当业务量明显增长时，就有依据重新检查容量和协作方式。

衡量架构工作的效果，可以同时观察三个层面：

- **业务结果**：付款后缺货取消是否减少，客户等待是否改善，人工处理负担是否下降。
- **交付表现**：跨团队依赖是否提前暴露，因架构问题导致的返工是否减少，试点与扩围是否有可靠依据。
- **治理健康度**：关键资产是否有维护者，例外是否按期复查，重大变更能否找到决策理由。

这些是本文建议的观察维度。指标还需要明确分母、窗口、数据质量和责任人。业务改善可能同时受到促销策略、人员培训与商品结构变化影响，评价时应保留这些背景。

**八、裁剪落地：第一轮可以怎样启动**

TOGAF 提供配置和应用方法的空间，官方系列指南也涵盖敏捷实践。[1][5] 企业需要根据决策需求确定投入深度。下列 90 天安排是本文为案例提出的启动方案，目标是完成一轮能够支持试点的架构工作；实际开发和迁移周期需要单独估算。

| 时间 | 主要工作 | 应当形成的决策或成果 |
|---|---|---|
| 第 1—15 天 | 确认发起人、范围、目标、责任与工作方式 | 是否开展本轮工作，如何衡量价值 |
| 第 16—30 天 | 访谈、数据抽样、系统与关键路径调查 | 已有证据支持的基线及主要差距 |
| 第 31—45 天 | 比较业务规则与目标方案，验证关键假设 | 目标业务与应用协作方式，技术可行性证据 |
| 第 46—60 天 | 识别工作包、依赖与过渡架构 | 试点方案、迁移批次及成本风险判断 |
| 第 61—75 天 | 协调资源与验收，开展试点准备 | 工作承诺、符合性要求与上线条件 |
| 第 76—90 天 | 对已具备条件的范围开展验证或受控试点 | 是否进入下一批，哪些假设需要调整 |

时间段可以重叠，部分工作也可能反复。若关键数据质量或旧系统接口未达到条件，第 90 天的正确结果可能是调整路线图，而不是强行上线。

对于人员较少的团队，可以合并角色与文档，但应保留责任、需求、决策依据和实施证据。对于集团企业，可以先明确必须统一的规则与接口，再允许各业务单元在边界内选择自己的实现方式。

与敏捷交付结合时，可以将跨团队决策放在适当的提前量内，把已确认的要求转为团队能够验证的交付条件，并让迭代发现反馈到架构模型。没有必要假设每个冲刺都完整执行一轮 ADM，也不应假设架构方向确定后永远不会调整。

例如，第一轮迭代验证旧系统能否提供可靠库存记录；第二轮验证预留与重试；后续迭代再验证订单协调与异常处置。每一轮都在减少下一项决策的不确定性。

如果团队已经有完整的立项、需求、测试和变更流程，可以把相关架构信息放入这些流程，避免为同一事实创建多个互相矛盾的维护入口。

**九、贯穿案例：把订单履约升级拆成能够验证的几步**

现在把前面的分析连接成一个完整方案。假设企业有三套渠道订单应用、两套仓储应用，各渠道分别维护库存展示和预留逻辑。第一轮仅覆盖一个区域的直营线上订单。

业务愿景是减少付款后因缺货取消的订单，同时让预留、出库和释放能够追踪。目标业务能力包括统一的库存承诺、跨系统履约协调和异常处理；业务责任需要同步落实到渠道、仓储、客服与运营。

在目标应用协作中，渠道先取得有效预留，再按业务规则继续支付和履约。支付失败、用户取消和预留超时都需要对应的释放规则；仓储执行发货后，需要提供可核对的结果。具体调用顺序与事务设计由解决方案进一步验证。

这一方案的核心信息关系可以用一张追踪表表达：

| 业务诉求 | 架构要求 | 实施工作 | 验证证据 |
|---|---|---|---|
| 减少付款后缺货取消 | 在约定业务路径中，付款资格依赖有效预留 | 预留能力与渠道流程改造 | 业务路径测试、试点订单原因分析 |
| 避免重复占用库存 | 同一业务操作能够被稳定识别 | 请求标识、状态查询与幂等处理 | 超时后重试与并发请求测试 |
| 缩短异常处理时间 | 能追踪订单、预留与出库之间的关系 | 关联标识、查询与对账能力 | 异常样本回放、人工处置记录 |
| 控制迁移风险 | 每批次的库存责任与切换条件明确 | 分批接入、路由控制与恢复安排 | 切换演练、对账结果与批准记录 |

迁移可以分成四批。批次不等于固定月份，其顺序来自依赖关系。

**第一批：建立可解释的现状。** 统一试点范围的商品、位置和订单标识，补齐取消原因分类及对账。完成后，企业至少能够解释主要异常发生在哪里。这一批本身就有价值，也为后续验证提供基线。

**第二批：让限定范围具备可靠预留。** 在一个区域、有限渠道和明确库存范围内引入预留能力。旧业务与新业务之间需要显式的库存边界，避免同一份库存被两种机制独立承诺。完成后，试点范围能够追踪库存承诺，并处理重试、取消和超时。

**第三批：形成履约协调能力。** 在预留可靠的基础上，增加履约分配、拆单和异常转派。此时需要与仓储、门店和客服一起验证实际作业，不能只检查接口返回成功。

**第四批：扩大覆盖并退出旧路径。** 按渠道和区域逐步接入，确认数据、责任和作业条件具备后，再关闭被替代的预留入口。保留必要的历史查询和追溯能力，并更新应用清单与运维责任。

每一批形成的状态都需要能够独立运作。过渡架构应当说明哪些新旧组件共存、如何分担责任、有哪些临时约束，以及何时退出。它需要与目标架构同样认真地检查。

恢复方案也要保护业务事实。如果新流程已经接受订单并占用库存，出现故障后不能只切回旧版本而忽略这些有效承诺。案例中的恢复步骤可以包括暂停新增试点订单、保留已有承诺记录、核对处理中订单，再按照预先验证的规则恢复服务。

试点评价需要同时观察结果和代价。假设取消率下降，但人工修复数量明显增加，就应分析是否把系统问题转移给了运营。评估还应记录订单量、促销活动、商品结构及观察窗口，避免把样本变化误认为架构收益。

当业务决定进入更多区域时，团队带走的成果应该包括可用能力、明确责任、可复用接口与验证证据，以及仍需处理的例外。下一轮架构工作可以在这些事实之上继续推进。

**十、常见误区与适用边界**

企业采用 TOGAF 时，可以用下面几个问题检查工作是否仍然服务于业务。

**文档能否帮助作决定？** 一张系统关系图如果无法说明关键责任、依赖和风险，就需要继续补充信息。图画得完整与否，应当由读者的决策需要来判断。

**目标是否有业务负责人？** 如果缺货取消目标只有技术部门签字，却没有人确认库存规则和门店作业要求，方案仍缺少实施条件。

**统一的范围是否有依据？** 案例要求共享库存的预留规则一致，但不同渠道仍可以保留各自的界面与营销流程。统一到什么程度，应当由业务价值、耦合关系与运营成本共同决定。

**设计深度是否匹配风险？** 影响集团数据定义和跨系统交易的变化，需要足够的整体分析；一个边界清楚的局部页面调整，可以在现有约束下直接推进。团队需要根据影响选择方法中的活动。

**目标架构是否考虑了迁移？** 如果目标方案只有最终形态，却没有数据准备、混合运行、异常处理和退出条件，实施团队仍然缺少关键依据。

**架构能力是否有人维护？** 一轮项目可以产生文档和系统，持续的企业架构能力还需要有人维护责任、规则和资产，并处理下一次变化。

本文所讨论的方法，适合帮助团队组织跨部门、跨系统的变化决策。具体数据库设计、分布式事务实现、容量验证和操作规程，仍需要相应专业工作继续完成。采用时应当明确每项决定由谁作出、依靠什么证据，以及后续由谁验证。

| 架构开发方法 | Architecture Development Method，ADM | 组织架构开发、实施治理和变更活动的方法 |
| 基线架构 | Baseline Architecture | 用于本轮比较与分析的当前架构描述 |
| 目标架构 | Target Architecture | 希望形成的架构状态 |
| 过渡架构 | Transition Architecture | 通往目标过程中可识别的中间架构状态 |
| 差距分析 | Gap Analysis | 比较基线与目标，识别需要的变化 |
| 利益相关者 | Stakeholder | 对架构或变化结果有关注与利益关系的人或组织 |
| 交付物 | Deliverable | 约定交付并接受评审的成果 |
| 制品 | Artifact | 描述架构某个方面的模型、目录、矩阵或图 |
| 架构构建块 | Architecture Building Block，ABB | 对所需能力及其约束的描述 |
| 解决方案构建块 | Solution Building Block，SBB | 用来实现所需能力的具体组成 |
| 工作包 | Work Package | 在规划中组织一组相关变化的工作单元 |
| 架构路线图 | Architecture Roadmap | 描述架构如何分批演进及其依赖关系 |
| 架构存储库 | Architecture Repository | 保存、组织和维护架构资产的机制 |

**附录二：可以直接使用的工作记录**

以下字段是本文建议的精简模板，用于将讨论连接到责任与验证；企业可以合并到已有系统中。

- **架构原则记录**：编号、名称、原则陈述、业务理由、实施影响、适用范围、批准者、例外处理方式。
- **利益相关者记录**：角色、关注点、需要参与的决策、影响范围、沟通方式、确认状态。
- **差距记录**：现状证据、目标要求、差距说明、候选处理方式、关联工作包、责任人、验收证据。
- **需求追踪记录**：需求编号、业务来源、优先级、约束、关联架构元素、实施任务、验收条件、变更历史。
- **迁移批次记录**：本批形成的能力、前置依赖、涉及系统与数据、进入条件、退出条件、恢复方案、业务责任人。
- **架构例外记录**：偏离要求、申请理由、风险、补偿措施、接受者、生效范围、复查日期、关闭条件。

召开试点评审前，可以要求团队用这些记录回答五件事：为什么做，当前证据是什么，接受了哪些取舍，如何判断实施成功，以及出现偏差时由谁处理。
