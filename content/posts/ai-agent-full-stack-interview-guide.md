准备 AI Agent 方向的面试，最容易陷入一种“看过很多概念，却不会做选择”的状态：知道 Transformer、RAG、ReAct、Function Calling 和多智能体，却回答不好“这个场景为什么要用它”“为什么不用另一个方案”“上线以后出问题怎么定位”。

我整理的《AI Agent 全栈工程师面试通关》目录，真正想训练的不是背诵能力，而是把一条完整的因果链讲清楚：**LLM 的限制，为什么催生 RAG；RAG 和工具调用，为什么需要 Agent 循环；Agent 进入生产后，为什么又必须补上可观测性、评估、安全和可靠性。**

这篇文章把目录中的六个页面压缩成一张面试地图，适合在系统学习前建立全局认识，也适合面试前快速复盘。

## 先记住一句话：Agent 是什么

可以先用一个足够工程化的定义开始：

> 把 LLM 当成一个非确定、无状态、按 token 计费、会产生幻觉并且不会主动执行函数的组件；Agent 则是把它放进一个能够感知环境、选择动作、调用工具并持续循环的系统。

这个定义比“Agent 是一个聪明的聊天机器人”更有用，因为它会自然引出面试中最常见的追问：

- 非确定，如何保证输出结构稳定、操作不会失控？
- 无状态，如何管理短期上下文和长期记忆？
- 按 token 计费，如何控制长上下文、重试和多 Agent 带来的成本？
- 会幻觉，如何用检索、工具和评估减少错误？
- 能产生副作用，如何做权限、审批、幂等、回滚和审计？

回答 Agent 问题时，不要只停留在模型能力。面试官真正想看的是：你能不能把模型的不确定性，转换成系统层面的约束和取舍。

## 一、第一层：把 LLM 当成“会算账的组件”

### 1. 注意力、上下文和 KV cache

自注意力让每个 token 可以关注序列中的其他 token，换来了强大的上下文建模能力，也带来了随序列长度增长的计算和显存成本。上下文越长，不只是输入费用增加，推理延迟、显存占用和并发能力也会受到影响。

KV cache 的价值在于：自回归生成时，不必反复计算已经生成 token 的 Key 和 Value，而是缓存并复用历史结果。它减少了重复计算，却不是免费的——缓存会随上下文长度线性消耗显存。因此，长上下文、高并发场景下，面试官继续追问 MQA 或 GQA 时，核心答案应落在：**通过共享或分组共享 K/V，降低 KV cache 的显存开销。**

这也解释了为什么“模型支持很大的上下文窗口”并不等于“应该把所有资料都塞进 Prompt”。成本、延迟和模型对长文本中间位置的利用能力，仍然需要一起考虑。

### 2. 采样参数不是越多越专业

`temperature`、`top_p`、`top_k` 和各种 penalty，本质上是在调节概率分布的确定性、多样性和重复倾向。面试时不要只背参数定义，要从任务目标出发：

- 信息抽取、分类、路由和工具参数生成，更重视稳定性，应采用低随机性配置。
- 文案、头脑风暴和创意生成，需要适度多样性，可以放宽采样范围。
- 结构化 JSON 场景通常不应随意使用 `frequency_penalty`，因为字段名和固定结构本来就需要重复，惩罚可能导致漏字段或破坏格式。
- 不同模型厂商暴露的参数并不完全一致，回答时要说明“以具体模型 API 的能力为准”，不要把某一家接口的参数当成通用事实。

一个好的面试答案，往往是“任务目标 + 参数选择 + 失败风险”，而不是单独说一个数字。

### 3. 幻觉、结构化输出和 Function Calling

幻觉不是简单的“模型知识不够”，而是模型在概率生成过程中倾向于产出语言上合理、事实却不可靠的结果。常见的缓解手段包括：提供可信上下文、要求引用证据、让模型在证据不足时拒答、采用结构化输出、把事实核验交给工具，以及通过离线和线上评估持续监控。

但要注意：Prompt 里写“不要编造”并不能构成可靠性保证。结构化输出可以约束格式，却不自动保证字段内容正确；Function Calling 也不是模型直接执行函数。真实流程是：

1. 模型根据工具描述生成调用意图和参数；
2. 应用服务校验名称、参数、权限和业务规则；
3. 应用服务真正执行函数；
4. 执行结果回写上下文，模型再决定下一步或组织最终回答。

因此，工具调用的安全边界必须在模型之外。尤其是删除数据、发起付款、发送消息、修改工单等高风险动作，应增加最小权限、幂等键、审批或人工确认、可回滚设计和审计日志。

## 二、第二层：RAG 不是默认答案，而是规模决策

当面试官问“为什么用 RAG”时，完整回答不应只是“因为模型不知道企业内部知识”。更重要的是比较三条路线：RAG、长上下文和微调。

- **RAG** 适合知识经常变化、需要引用来源、数据规模较大或需要按权限检索的场景；代价是检索链路更复杂，召回错误会直接影响回答。
- **长上下文** 适合资料规模可控、任务需要完整阅读文档的场景；代价是 token 成本、延迟和长文本利用率问题。
- **微调** 更适合稳定的行为模式、输出风格或领域任务能力；它不是实时知识库，知识更新和事实溯源并不方便。

### 1. 一条生产级 RAG 链路

可以把 RAG 画成下面这条链路：

```text
用户问题
  → 查询理解与改写
  → 文档过滤 / 权限过滤
  → 混合召回
  → 去重与重排
  → 上下文组装
  → 模型生成
  → 引用、校验与评估
```

每一环都可能成为故障点：

- **切分**：块太大，检索不够精确；块太小，上下文不完整。可以根据文档结构、语义边界和问答类型选择切分策略，必要时使用父子块。
- **Embedding 与向量库**：向量检索擅长语义相似，但不一定擅长精确匹配实体、编号和关键词。索引结构选择还要结合数据规模、更新频率、召回率、延迟和内存成本。
- **混合检索**：将关键词检索和向量检索结合，再用 RRF 等方法融合排序，通常比单一检索更稳健。
- **Rerank**：用更精细的模型对候选文档重新排序，可能提高相关性，但会增加延迟和推理成本。
- **上下文组装**：不是把召回结果全部拼进去，而是去重、压缩、保留证据链，并控制 token 预算。
- **生成**：要求模型基于证据回答，缺乏证据时明确拒答，同时保留可追溯引用。

### 2. 如何定位“RAG 答得不对”

这是非常典型的面试题。不要直接说“换一个更强的模型”，而应先区分两个问题：**召回没找到，还是找到了但生成没用好。**

可以按以下顺序诊断：

1. 固定一批带标准答案和标准证据的测试问题，复现错误。
2. 查看查询改写结果、过滤条件和召回候选，确认正确文档是否进入候选集。
3. 若没有召回，检查切分、Embedding、关键词召回、索引更新、权限过滤和查询改写。
4. 若召回了但排位靠后，检查融合策略、Rerank 模型和候选数量。
5. 若正确证据已经进入上下文，检查上下文长度、证据位置、Prompt 约束、引用规则和模型是否忽略证据。
6. 将结果拆成检索指标与生成指标，避免用一个“准确率”掩盖真正的瓶颈。

RAG 评估至少要覆盖检索相关性、上下文覆盖、答案忠实度和答案正确性。上线后还要结合用户反馈、版本灰度、延迟和成本监控，形成从离线数据集到线上反馈的闭环。

## 三、第三层：Agent 是循环，不是名词堆砌

一个最小 Agent 可以抽象为：

```text
读取上下文
  → LLM 决定下一步
  → 解析动作
  → 调用工具或访问环境
  → 获得观察结果
  → 写回上下文
  → 继续或结束
```

这条循环是 Agent 的核心。只要流程可以被提前确定，优先使用普通代码或 Workflow 往往更简单、更可控；只有当下一步需要根据环境和中间结果动态决定时，Agent 的自主循环才真正有价值。

### 1. Agent 与 Workflow 的边界

Workflow 是开发者预先定义步骤和分支，适合审批、固定格式转换、明确的多步骤业务流程。Agent 允许模型在运行时选择工具和路径，适合目标明确但实现路径不确定、需要探索或处理大量例外的任务。

面试回答“为什么要用 Agent”时，可以用三个标准检查：

- 任务路径是否真的不可预先编排？
- 工具调用和自主决策带来的收益，是否大于额外的成本、延迟和失控风险？
- 是否有足够的观测、终止条件、权限控制和人工兜底？

如果答案是否定的，选择 Workflow 并不是保守，而是更成熟的工程判断。

### 2. ReAct、Plan-and-Execute 与 Reflection

- **ReAct** 把推理、行动和观察交替组织起来，适合需要根据工具结果动态调整的任务；代价是调用次数和延迟可能上升。
- **Plan-and-Execute** 先生成计划，再按计划执行，适合步骤较多、希望先获得全局结构的任务；但环境变化后，原计划可能需要重新规划。
- **Reflection** 通过自检、批评和修订提高质量，适合草稿生成、代码修改、复杂研究等任务；代价是额外 token 和调用，且“自我反思”不等于真实正确。

这些模式不是越复杂越好。真正的取舍是：质量提升是否能够覆盖新增的 token、延迟、失败面和调试难度。

### 3. 记忆、多智能体和 MCP

短期记忆服务于当前任务，例如对话历史、工具结果和当前计划；长期记忆保存跨会话可复用的信息，但必须考虑过期、冲突、隐私和删除机制。记忆系统不是简单地“把所有历史都存起来”，而是要设计写入、检索、更新、压缩和遗忘策略。

多智能体适合角色之间确实存在不同专业能力、权限边界或并行任务的场景。它可能带来并行效率和职责隔离，也会带来通信成本、上下文同步、错误传播、调度复杂度和总 token 增长。把一个 Agent 拆成多个 Agent，不会自动增加智能。

MCP 的价值在于标准化模型与外部工具、资源之间的连接方式。面试中应讲清楚：协议解决的是接入和发现的一致性，不会自动解决工具权限、数据治理、业务幂等或安全审计。

## 四、第四层：全栈工程化决定 Demo 能不能活下来

AI Demo 和生产系统的差别，通常不在“能不能调用模型”，而在于能不能稳定、可观测、可评估、可控地服务真实用户。

### 1. 流式、延迟和成本

聊天场景通常需要流式输出，以改善首 token 时间（TTFT）和用户感知延迟。SSE 适合服务端向浏览器单向推送文本事件，WebSocket 更适合双向、长连接和实时交互。选型要结合通信方向、连接管理、代理兼容性和故障恢复，而不是把 WebSocket 当成更高级的默认答案。

成本优化可以从三处着手：

- **减少不必要的输入和输出**：压缩上下文、限制历史、控制输出长度。
- **缓存与模型路由**：对重复请求复用结果，对简单任务使用更便宜、更快的模型。
- **批处理与调用治理**：合并适合异步处理的任务，限制重试和 Agent 最大步数。

当账单突然上涨时，应先通过 trace 按模型、用户、路由、任务类型和版本拆分，检查 token 数、调用次数、重试比例、上下文长度和缓存命中率，而不是凭直觉直接降模型。

### 2. 可观测性与评估

一次用户请求应当能够串起完整 trace，并把模型调用、检索、重排、工具执行和数据库访问记录为不同 span。至少要记录：输入输出摘要、模型版本、token 数、成本、延迟、错误、重试、工具参数和结果状态；敏感数据则必须脱敏或受控访问。

评估需要分层：

- **离线评估**：用固定 golden set 检查回归、检索质量、答案正确性和结构化输出。
- **线上评估**：观察真实流量中的成功率、用户反馈、P95/P99 延迟、成本和人工接管率。
- **LLM-as-judge**：适合辅助大规模比较，但要校准评审标准，并用人工样本验证偏差。

没有评估的 Agent 迭代，往往只是“感觉变好了”；没有 trace 的评估，也很难知道究竟是哪一个环节改变了结果。

### 3. 安全与可靠性

Prompt 注入不仅可能来自用户输入，也可能来自被检索的文档、网页或工具返回值。生产系统应把指令、用户内容和外部数据分层处理，采用权限过滤、工具白名单、最小权限、输出校验和敏感操作审批，避免让不可信文本直接改变系统行为。

可靠性方面，需要重点防范：

- 重试风暴：失败重试叠加，导致流量和成本进一步上升；
- 重复副作用：重复发消息、重复扣款或重复创建记录；
- 超时级联：一个慢工具拖垮整条 Agent 链路；
- 结构化输出失败：模型返回格式不符合下游契约；
- 无限循环：Agent 没有明确的步数、预算和终止条件。

对应的工程手段包括指数退避、重试上限、熔断、超时、幂等键、结构化校验、降级、人工接管和全链路审计。

## 五、第五层：综合系统设计题怎么答

当题目是“为十万名内部员工设计一个企业知识与操作助手”时，可以按以下骨架展开，而不是直接画一个大模型框：

1. **需求边界**：先区分只读问答和写操作，明确用户、知识类型、敏感动作和成功指标。
2. **接入层**：身份认证、租户与组织权限、限流、会话管理和流式接口。
3. **知识层**：文档解析、分块、Embedding、关键词与向量混合检索、Rerank、权限过滤和引用。
4. **Agent 层**：优先用 Workflow 覆盖确定流程；只在需要动态决策时引入 Agent，并限制工具、步数和预算。
5. **工具层**：统一工具描述与调用协议，执行前做参数校验和权限校验，高风险动作走审批或人工确认。
6. **可靠性层**：超时、重试、幂等、熔断、降级、队列和回滚。
7. **观测评估层**：trace/span、成本、延迟、错误率、检索指标、答案指标和线上反馈。
8. **数据治理**：多租户隔离、敏感信息脱敏、审计、保留期限和数据删除。

最后补充容量和成本估算：并发量、峰值请求、平均输入输出 token、工具调用次数、缓存命中率、P99 延迟和模型路由策略。系统设计的加分点通常不是组件越多，而是你能说明每个组件解决什么问题、增加了什么代价，以及如何验证它确实有效。

## 六、面试前的使用方法：从熟悉感变成判断力

这套内容可以按两种方式使用：

- **时间紧**：先看每章结尾的面试题检索，答不上来的问题再回正文补概念。
- **系统准备**：按“LLM/Prompt → RAG → Agent → 工程化 → 综合自测”的顺序学习，每章结束后自己画图、做题和复述。

建议把每个知识点整理成四句话：

1. 它解决什么问题？
2. 它是怎么工作的？
3. 它的代价和失败模式是什么？
4. 什么情况下不应该使用它？

此外，还应该准备两到三个自己的项目故事，用 STAR 结构讲清背景、目标、技术取舍、量化结果和失败复盘。不要只说“准确率提升了”，要说明数据集、评估口径、样本量、基线和提升来自哪里；不要只说“用了 Agent”，要说为什么固定 Workflow 不够，以及你如何限制 Agent 的成本和风险。

## 最后的判断标准

AI Agent 全栈工程师的“全栈”，不是把前端、后端、模型和数据库名词都背一遍，而是能够把问题从用户体验一路拆到系统实现，再从系统指标反推方案取舍。

一场好的面试回答，应该同时包含四个维度：

- **原理**：知道模型、检索和 Agent 循环为什么这样工作；
- **选择**：能在 RAG、长上下文、微调、Workflow、Agent 和多 Agent 之间做判断；
- **工程**：能处理流式、成本、延迟、评估、安全和可靠性；
- **结果**：能用可验证的指标证明方案有效，并诚实说明失败和边界。

如果只能记住一个结论，那就是：**不要把 AI Agent 面试准备成名词清单，要把它准备成一套“限制 → 方案 → 代价 → 验证”的推理过程。** 当你能沿着这条链路回答问题，模型换代、框架更名或工具更新，都不会轻易动摇你的基本判断力。
