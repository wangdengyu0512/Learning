> Agent 可观测性的核心，不是多装一个监控面板，而是把一次非确定、多步骤的运行，还原成一条可以查询、归因、比较和重建的因果链。

一个差旅助理 Agent 收到请求：帮我找一趟合适的航班，并完成预订。

从服务端看，这次请求很正常：接口返回 200，根任务状态是 `OK`，最终也生成了一段自然语言回复。但是用户随后发现，这次任务的模型费用是平时的 3 倍，而且航班没有真正订上。

传统监控可以告诉我们接口没有崩溃，日志也能证明模型和工具都被调用过，却很难直接回答下面这些问题：

- Agent 为什么连续调用了 9 次模型，而正常情况只有 5 次？
- 第一次错误发生在模型、检索、工具还是编排层？
- 为什么某次工具失败没有让根任务变成失败？
- 哪几次调用消耗了最多 Token？
- 如果任务被转交给另一个 Agent，怎样把两段执行过程连接起来？
- 修复后，怎样证明同类问题不会再次出现？

这些问题不是单靠日志、APM 或离线评测能够解决的。我们需要观察的，不只是一次请求的结果，而是 Agent 在运行过程中形成的完整决策轨迹。

这就是 Agent 可观测性要解决的问题。

## 一、为什么 Agent 让传统可观测性失效了

传统 Web 服务通常有一个相对稳定的执行路径：请求进入控制器，调用若干服务和数据库，最后返回响应。即使系统跨越多个进程，调用关系也大多由代码提前确定。

Agent 不一样。

它的下一步动作可能由模型在运行时决定：先检索资料，还是先向用户追问；调用哪个工具；工具失败后要不要重试；要不要把任务交给另一个 Agent；什么时候停止。相同输入也可能因为模型采样、外部数据和工具状态不同，走出不同路径。

因此，Agent 同时引入了四类传统系统不突出的复杂性：

1. **控制流具有运行时不确定性。** 程序只提供候选动作，模型决定下一步走向。
2. **失败经常是语义失败。** HTTP 请求成功，不代表答案正确，更不代表任务完成。
3. **成本沿执行路径累积。** 每一次推理、检索、重试和子 Agent 调用都可能增加 Token 与外部 API 成本。
4. **中间状态决定最终结果。** 一次错误检索或工具输出，会污染后续所有推理，但最终节点本身未必报错。

传统 APM 的四个黄金信号仍然重要，但它们只能描述系统是否健康，不能完整解释 Agent 为什么做出某个决定。

| 问题 | APM | Eval | Agent 可观测性 |
| --- | --- | --- | --- |
| 服务是否报错、变慢 | 擅长 | 不擅长 | 可以补充 |
| 最终回答质量如何 | 不擅长 | 擅长 | 记录并关联评分 |
| 哪一步开始偏离正确路径 | 通常不够 | 通常只给结果分 | 擅长 |
| Token 和成本花在哪里 | 粗粒度 | 不是主要目标 | 逐步骤归因 |
| 多 Agent 调用关系 | 只能看到服务调用 | 通常不关注 | 通过 Trace 还原 |

可以把三者的边界概括为：

- **APM** 关心系统是否正常运行；
- **Eval** 关心 Agent 的表现是否足够好；
- **可观测性** 关心这一次运行究竟经历了什么。

它们不是互相替代的关系。一个生产级 Agent，通常三者都需要。

![Agent 可观测性、Eval 与 APM 的关系](/blog-assets/agent-observability/fig-1-1.svg)

## 二、核心模型：一次 Agent 运行就是一棵 Trace 树

理解 Agent 可观测性，最重要的不是先记住某个产品，而是先建立 Trace 和 Span 的数据模型。

### 1. Trace：一次完整运行

Trace 表示一次端到端任务。例如：

```text
用户提出差旅需求
    → Agent 理解意图
    → 检索差旅政策
    → 搜索航班
    → 调用预订 Agent
    → 生成最终回复
```

这些步骤共享同一个 `trace_id`，因此可以在后端被还原成一条完整执行链。

### 2. Span：树上的最小工作单元

Span 表示一个有开始和结束时间的工作单元，例如：

- 一次模型调用；
- 一次向量检索；
- 一次工具执行；
- 一次 Guardrail 检查；
- 一次子 Agent 调用；
- 一次在线质量评分。

每个 Span 至少需要包含：

- `trace_id`：属于哪一次完整运行；
- `span_id`：当前工作单元的唯一标识；
- `parent_span_id`：是谁调用了当前 Span；
- 开始时间、结束时间和状态；
- 操作名称与操作类型；
- 与该步骤相关的属性和事件。

没有 `parent_span_id` 的 Span 是根节点。其余 Span 通过父子关系组成一棵树。

### 3. 一棵典型的 Agent Trace

```text
invoke_agent: travel_assistant
├── chat: understand_request
├── retriever: travel_policy
├── chat: make_plan
├── execute_tool: search_flights
│   └── http: flight_api
├── invoke_agent: booking_agent
│   ├── chat: validate_booking
│   └── execute_tool: create_order
└── chat: final_response
```

这棵树比线性日志多表达了一层关键含义：**因果关系**。

我们不仅知道 `create_order` 发生过，还知道它属于 `booking_agent`，而 `booking_agent` 又是由 `travel_assistant` 在某个具体决策点调用的。如果预订失败，可以沿着父子链逐级回溯，而不是在数千条日志中依靠时间戳猜测关联关系。

## 三、一个 Span 到底应该记录什么

“把每一次模型调用记下来”只是起点。真正可用的 Agent Span，至少要覆盖身份、性能、用量和业务上下文四类信息。

### 1. 身份与版本

建议记录：

- Agent 名称与版本；
- 模型供应商、模型名称和模型版本；
- Prompt 模板版本；
- 工具名称与工具版本；
- 部署环境、服务名称和发布版本；
- 会话、线程或业务任务 ID。

版本信息决定了 Trace 能不能用于回归分析。没有模型、Prompt 和 Agent 版本，工程师只能看到“这次错了”，却无法判断错误属于哪个发布批次。

### 2. 性能与状态

建议记录：

- Span 开始和结束时间；
- 总耗时；
- Time to First Token；
- 是否流式输出；
- 状态码、异常类型和错误信息；
- 工具超时、重试次数和退避时间。

对流式输出而言，首 Token 时间往往比总耗时更接近用户感受到的等待时间。一个请求可能总共运行 20 秒，但 1 秒内开始输出，用户体验和等待 15 秒后才看到第一个字完全不同。

### 3. Token 与成本

每个模型 Span 应独立记录：

- 输入 Token；
- 输出 Token；
- 缓存命中或缓存 Token；
- 推理 Token，如果模型能够提供；
- 模型调用次数。

成本通常不是一个稳定的协议字段。模型价格会变化，还可能区分输入、输出、缓存、批处理和不同服务等级。更可靠的做法是：Span 上报标准化的用量，观测后端根据带版本的价格表计算成本。

### 4. Prompt、Completion 与工具 I/O

为了调试语义错误，我们往往还需要：

- 完整渲染后的消息列表；
- 模型响应；
- 工具参数和返回值；
- 检索查询与候选文档；
- 重排结果；
- 路由候选和最终选择；
- Guardrail 的判定结果。

但这些内容体积大、基数高，而且经常包含个人信息、业务数据甚至凭证。它们不应该被当作普通 Metric Label，也不应该无条件发送到第三方平台。

一个实用的分层策略是：

| 数据 | 默认策略 |
| --- | --- |
| Trace/Span ID、操作类型、耗时、状态 | 全量保留 |
| Token、模型、工具名、版本 | 全量保留 |
| Prompt 和 Completion | 脱敏后采样保留 |
| 工具原始响应 | 按工具风险分级 |
| 检索文档正文 | 尽量存引用与哈希，必要时保存快照 |
| 推理中间状态 | 明确合规边界后按需记录 |

这里有一个容易被忽略的原则：**记录“做了什么”还不够，还要记录影响决策的关键上下文。**

如果只记录最终输出，却不记录模型看到了哪些检索结果、路由时有哪些候选、工具失败后累计重试了多少次，那么真正的根因仍然不可见。

## 四、Trace 树是怎么长出来的

Trace 不是后端根据时间戳拼出来的。父子关系必须在调用发生时就被写入，这个过程叫作 Context Propagation，也就是上下文传播。

### 1. `traceparent` 负责传递因果关系

在跨进程调用中，调用方会把当前 Trace 的身份放进请求元数据。基于 W3C Trace Context 时，最关键的字段是 `traceparent`：

```text
version-trace_id-parent_span_id-trace_flags
```

下游服务收到请求后：

1. 读取 `trace_id`；
2. 把上游的 Span ID 记为自己的 `parent_span_id`；
3. 创建新的 `span_id`；
4. 继续把新的上下文传给下一跳。

只要这条链没有断，不同进程、不同语言甚至不同 Agent 的执行步骤，都可以挂在同一棵 Trace 树下。

### 2. 同进程不等于不需要传播

在一个 Python 或 Node.js 进程里，上下文通常保存在异步上下文或协程局部存储中。模型 SDK、工具包装器和框架中间件从当前上下文中读取父 Span，再创建子 Span。

问题往往出现在这些地方：

- 新线程或线程池没有继承上下文；
- 后台任务脱离原请求生命周期；
- 消息队列只发送业务 Payload，没有发送 Trace Context；
- 自定义回调在错误的异步上下文中执行；
- 子 Agent 使用了另一套追踪 SDK，却没有接收上游上下文。

这些问题会产生“孤儿 Span”：数据确实上报了，却无法连接到原来的任务。

### 3. 多 Agent 交接如何进入同一棵树

假设差旅 Agent 把预订任务交给独立部署的 Booking Agent：

```text
Travel Agent
  └── invoke_agent: booking_agent
        │  HTTP / Queue / A2A / MCP
        ▼
      Booking Agent
        ├── chat: validate
        └── execute_tool: create_order
```

交接时，Travel Agent 不仅要发送航班、乘客等业务参数，还要发送当前 Trace Context。Booking Agent 以当前调用 Span 为父节点创建自己的入口 Span，于是两个 Agent 的执行过程仍属于同一个 `trace_id`。

![Context Propagation 将多个 Agent 串成一棵树](/blog-assets/agent-observability/fig-2-1.svg)

如果跨 Agent 边界没有传播上下文，后端只能看到两次互不相关的运行。此时即使双方日志都很完整，也无法可靠回答“这个 Booking Agent 任务是由哪个用户请求触发的”。

## 五、Token 和成本如何从 Span 上卷到整次运行

Agent 成本不是一笔单独发生的费用，而是整棵执行树逐步累积的结果。

假设一次运行包含以下模型调用：

| Span | 输入 Token | 输出 Token |
| --- | ---: | ---: |
| 理解需求 | 800 | 120 |
| 生成计划 | 1,100 | 180 |
| 工具失败后的第一次重试 | 1,900 | 140 |
| 第二次重试 | 2,700 | 160 |
| 最终回复 | 3,200 | 260 |

如果只看最后一次调用，会误以为这次任务只消耗了 3,460 Token。实际上整次运行共消耗 10,560 Token，而且输入 Token 在重试过程中快速增长。

正确的成本归因过程是：

1. 每个模型 Span 记录自己的用量；
2. 工具、检索和子 Agent 记录各自的外部成本；
3. 父 Span 聚合直接或间接子节点的用量；
4. 根 Span 得到整次运行的成本视图；
5. 后端按模型与价格表版本换算货币成本。

```text
trace_cost
  = Σ model_usage_cost
  + Σ tool_api_cost
  + Σ retrieval_cost
  + Σ child_agent_cost
```

这使我们可以同时回答两个问题：

- 这次运行一共花了多少钱？
- 钱具体花在哪些步骤上？

第二个问题更重要。没有逐 Span 归因，团队看到成本升高后，通常只能采取粗暴措施，例如缩短所有 Prompt 或切换更便宜的模型。逐 Span 数据则可能揭示真正原因是工具重试、历史消息重复注入、检索文档过多，或者某个子 Agent 出现循环。

![Token 从子 Span 汇总到 Trace 级](/blog-assets/agent-observability/fig-2-2.svg)

## 六、实战：定位一次成本翻 3 倍的 Agent 故障

回到开头的差旅助理案例。

用户看到的是：请求成功返回，但预订失败，费用却是平时的 3.1 倍。根 Span 仍然是 `OK`，因为编排程序捕获了工具异常，并让模型生成了一段解释性回复。

### 1. 先比较正常 Trace 和异常 Trace

正常运行：

```text
invoke_agent
├── chat: understand
├── retriever: policy
├── chat: plan
├── execute_tool: search_flights
└── chat: final
```

异常运行：

```text
invoke_agent
├── chat: understand
├── retriever: policy
├── chat: plan
├── execute_tool: search_flights   ← 第一次失败
├── chat: retry_plan
├── execute_tool: search_flights   ← 再次失败
├── chat: retry_plan
├── execute_tool: search_flights
└── chat: final
```

结构 Diff 很快暴露了两个事实：

- 异常 Trace 多出两轮“模型判断 + 工具重试”；
- 每一轮模型调用的输入 Token 都比上一轮更多。

### 2. 找到第一个产生坏输出的 Span

根因分析不应该从最后一个红色节点开始，而应该寻找**第一个让系统状态偏离正确轨道的 Span**。

在这个案例中，第一个坏 Span 是最早的 `execute_tool: search_flights`：

- 航班 API 返回了可重试错误；
- 工具包装层没有提供结构化错误类型；
- 编排器没有全局重试上限；
- 模型每次只看到“搜索失败，请重试”；
- 每轮重试又重新携带完整对话和历史工具结果。

后面的模型调用不是根因，只是在传播和放大这个错误。

因此，正确修复并不是反复修改系统 Prompt，而是：

1. 在工具层区分可重试与不可重试错误；
2. 为有副作用和无副作用工具分别定义重试策略；
3. 在编排层设置全局步骤数与单工具重试上限；
4. 把“已重试 N 次”和最近一次结构化错误写入状态；
5. 达到上限后转入降级、补偿或人工确认流程；
6. 避免每次重试无条件注入全部历史内容。

![失败 Trace 的根因回溯](/blog-assets/agent-observability/fig-3-1.svg)

### 3. 为什么根 Span 是 `OK` 仍然值得报警

从程序控制流看，这次任务确实正常结束了。但从业务语义看，任务没有完成。

这揭示了 Agent 监控中的一个关键区别：

```text
技术成功 != 任务成功
```

除了 Span Status，还需要记录任务级结果，例如：

- `task.completed = false`；
- `booking.created = false`；
- `tool.retry_count = 3`；
- `agent.step_count = 9`；
- `evaluation.task_success = 0`。

只有把技术状态、业务状态和质量评分放在同一条 Trace 上，告警才不会被“正常返回的错误答案”绕过。

## 七、Good Run / Bad Run Diff 与 Replay

单条 Trace 回溯适合寻找明显错误。如果 Agent 没有抛异常，只是“这次表现明显更差”，成功与失败运行的结构化对比通常更有效。

### 1. 两棵树应该比较什么

Good Run / Bad Run Diff 可以围绕以下维度展开：

- Span 树结构是否发生变化；
- 相同层级的操作耗时差异；
- 每个模型 Span 的输入、输出 Token 差异；
- 工具调用次数和参数差异；
- 检索候选与重排结果差异；
- 路由候选和最终选择差异；
- 模型 `finish_reason` 是否由正常结束变成长度截断；
- Prompt、模型、工具或 Agent 版本是否变化。

这种比较的本质，是寻找两棵执行树从哪一条边开始分叉。

### 2. Replay 不等于精确复现

在普通程序中，相同输入常常意味着相同输出。Agent 系统还受到模型非确定性、外部 API、实时数据、检索索引和并发状态影响，因此 Replay 更准确的含义是：**重建关键中间状态，并从某个节点重新执行。**

为了让 Replay 有意义，至少需要保存：

- 完整渲染后的消息，而不只是 Prompt 模板；
- 模型名称、版本与采样参数；
- 工具请求和响应原文；
- 检索结果及其顺序；
- Agent 状态快照；
- Prompt、工作流和工具版本；
- 必要时使用外部响应快照替代真实调用。

即便如此，Replay 仍然不能保证逐字输出一致。它的价值是复现约束和环境，观察系统是否仍然沿着相同的错误路径前进。

## 八、生产环境真正应该监控什么

Agent 上线后，不能只把 APM 看板复制一份。至少需要建立运行成本、性能、行为和质量四组指标。

### 1. 单次运行成本 `cost/run`

这是 Agent 系统最重要的新信号之一。

需要按以下维度观察：

- Agent 与版本；
- 模型；
- 任务类型；
- 用户或租户；
- 成功与失败状态；
- 是否发生重试或子 Agent 调用。

固定阈值往往不够，应结合任务类型的历史分布设置异常规则。例如，高于过去七天同类任务 p90 的两倍时触发调查。

### 2. p95 延迟与 TTFT

总延迟告诉我们任务多久完成，TTFT 告诉我们用户多久看到第一个响应。两者都要监控，并继续下钻到：

- 模型推理耗时；
- 检索耗时；
- 工具调用耗时；
- 子 Agent 排队与执行耗时；
- 重试带来的额外耗时。

### 3. 工具失败率与重试行为

建议至少监控：

- 各工具调用成功率；
- 超时率；
- 每次运行的工具调用数量；
- 单工具平均和最大重试次数；
- Agent 平均和最大执行步数；
- 重复副作用操作的拦截次数。

对 Agent 而言，“工具最终成功”并不能覆盖之前已经发生的五次失败。重试本身就是需要监控的行为信号。

### 4. 任务级质量

质量数据可以来自：

- 确定性业务规则；
- 用户显式反馈；
- 任务结果校验；
- LLM-as-a-Judge；
- 人工抽检。

关键不是单独生成一张评分表，而是把评分写回对应 Trace。这样才能从低分样本直接下钻到执行步骤，判断问题出在检索、模型、工具还是编排。

![从 Trace 到在线评估闭环](/blog-assets/agent-observability/fig-3-2.svg)

### 5. 一组可落地的告警

| 告警 | 示例触发条件 |
| --- | --- |
| 单次运行成本异常 | `cost/run > 同类任务历史 p90 × 2` |
| Agent 循环 | `step_count > 预期上限` |
| 工具重试异常 | 单工具重试超过 2 次 |
| 首 Token 变慢 | TTFT p95 连续多个窗口上升 |
| 任务语义失败 | 技术状态成功但 `task.completed=false` |
| 低质量运行 | 在线评分低于阈值或用户差评 |
| Trace 断裂 | 孤儿 Span 比例超过基线 |

告警阈值需要根据业务基线调整。这里真正重要的是告警对象：从“接口是否报错”扩展到“Agent 是否出现异常行为”。

## 九、采样：不要把最重要的异常丢掉

Prompt、Completion 和工具响应会让 Agent Trace 远大于普通 HTTP Trace。生产环境通常不能无差别保存全部内容，因此采样是必需的。

但简单的随机头部采样存在一个致命问题：请求刚进入系统时，我们还不知道它最终是否会变成高成本、低质量或异常循环。如果一开始就决定丢弃，真正有价值的故障可能永远不会留下证据。

更适合 Agent 的策略是分层保留：

### 1. 结构化元数据尽量全量

全量保留：

- Trace 与 Span 关系；
- 操作类型；
- 状态和耗时；
- Token 用量；
- 模型与工具名称；
- 版本和任务结果。

### 2. 内容按风险与价值采样

Prompt、Completion、工具原文和检索正文可以按策略采样：

- 正常低成本 Trace 只保留少量全文；
- 高成本、高延迟 Trace 保留全文；
- 工具失败和重试 Trace 保留全文；
- 低评估分或用户差评 Trace 保留全文；
- 涉及敏感数据的 Trace 先脱敏，再决定是否保留。

### 3. 优先使用尾部决策

尾部采样在 Trace 接近结束时，根据已经产生的数据决定是否保留。它能识别：

- 总成本异常；
- 执行步数异常；
- 子 Span 失败；
- 任务未完成；
- 在线评分低；
- 用户负反馈。

代价是采样器需要在内存或缓冲区中暂存更多数据。生产设计需要在保留价值、延迟、内存和观测平台费用之间做权衡。

## 十、上线后最容易踩的四类坑

Agent 可观测性系统本身也会成为新的成本、性能和合规风险源。上线前应重点检查四类问题。

### 1. 隐私：把生产数据送进了另一个数据仓库

完整 Prompt、工具返回和检索内容可能包含：

- 姓名、电话和身份证件；
- 医疗、金融或法律数据；
- 企业内部文档；
- API Key、Cookie 和访问令牌；
- 模型生成的敏感推断。

基本控制措施包括：

- 在数据离开进程前完成脱敏；
- 使用字段白名单，而不是只维护黑名单；
- 对不同工具定义不同的记录策略；
- 设置访问控制、审计和保留期限；
- 对敏感场景评估自托管或私有化存储；
- 不把完整内容放进 Metric Label。

### 2. 成本：观测账单超过模型账单

Agent Trace 可能包含长对话、文档片段和工具结果。全量采集时，数据量会随着调用次数和上下文长度快速增长。

控制方式包括：

- 元数据全量、内容采样；
- 限制单个 Event 和 Span 的最大体积；
- 大对象只保存哈希、引用或外部对象存储地址；
- 区分热数据和归档数据；
- 单独监控观测平台每日写入量与成本。

### 3. 可见性：数据很多，但关键链路仍然是断的

常见问题包括：

- 用户 ID、URL、Prompt 被误用为 Metric Label，造成基数爆炸；
- 消息队列没有传播 Trace Context，产生孤儿 Span；
- 流式响应尚未结束，Span 就提前关闭；
- 只记录模型输入输出，没有记录路由和检索状态；
- 随机采样恰好丢掉低频异常。

数据量大不代表可观测。真正的可观测性取决于数据能否支持因果推断。

### 4. 可重建性：记录了结果，却无法恢复现场

如果没有保存渲染后的消息、工具响应、检索结果和版本信息，几周后再看 Trace，往往只能知道“这里答错了”，却无法重建当时模型真实看到的上下文。

同时，遥测发送不应该阻塞 Agent 热路径。应优先使用异步、批量导出，并为缓冲区溢出、Exporter 失败和进程退出设置明确策略。

![Agent 可观测性的四类投产风险](/blog-assets/agent-observability/fig-3-3.svg)

## 十一、接入方式：你从哪里观测，决定你能看见什么

Agent 遥测通常有三条接入路径。

### 1. 进程内 SDK 或框架回调

它最接近 Agent 的内部状态，可以看到：

- 路由和工具选择；
- 检索候选；
- Agent 状态变化；
- Prompt 渲染结果；
- 自定义业务步骤。

代价是需要修改代码，并处理框架升级和自定义封装。

### 2. OpenTelemetry 自动埋点

自动埋点可以包装常见模型 SDK、HTTP 客户端和框架调用，把调用转成标准 Span，并通过 OTLP 发送到后端。

它降低了接入成本，也减少了对单一观测平台的绑定。但自动埋点只能理解通用调用，无法自动知道“这一步是风险审批”或“这次检索属于哪个业务阶段”。关键业务节点仍然需要手动补充 Span、Event 和属性。

### 3. 代理网关

模型代理位于应用与模型 API 之间，通常无需深入修改 Agent 代码，就能获得：

- 模型请求次数；
- Token；
- 延迟；
- 状态码；
- 基于价格表估算的成本。

它的盲区同样明显：代理知道 Agent 调用了模型，却不知道 Agent 为什么调用、看到了哪些检索结果，也看不到进程内的路由和状态变化。

可以用一句话概括三者的区别：

> 网关擅长回答“调用花了多少”，进程内埋点才能解释“为什么发生这次调用”。

实际系统常常组合使用：网关负责统一模型治理，OpenTelemetry 负责跨服务链路，业务 Span 负责补足 Agent 语义。

![三种 Instrumentation 路径的可见性差异](/blog-assets/agent-observability/fig-2-3.svg)

## 十二、工具选型：先分层，不要先背产品名单

Agent 可观测性工具更新很快，但底层角色相对稳定。先按职责分层，比直接比较产品功能表更可靠。

### 1. Emitter：谁负责产生 Span

Emitter 位于应用侧，包括：

- OpenTelemetry SDK 与自动埋点；
- OpenLLMetry 一类面向 LLM SDK 的 Instrumentation；
- OpenInference 一类扩展 Agent、Retriever、Reranker、Evaluator 语义的约定；
- 框架原生 Callback；
- 自定义业务埋点。

它们的任务是把模型、检索、工具和 Agent 步骤转换成结构化遥测数据。

### 2. 传输与采集：数据怎样离开应用

常见组件包括：

- OTLP；
- OpenTelemetry Collector；
- Agent 或 Sidecar；
- 消息缓冲与尾部采样处理器。

这一层适合承担路由、批处理、脱敏、采样和多后端分发。

### 3. Backend：数据存在哪里，怎样查询和告警

不同后端的侧重点可能不同：

- LangSmith 更贴近 LangChain、LangGraph 工作流；
- Langfuse 强调开源、自托管以及 Trace、Prompt、Eval 的组合；
- Phoenix 与 OpenInference、RAG 质量分析结合紧密；
- Braintrust 偏向 Eval-first 的实验和质量工作流；
- Datadog 等 APM 平台适合希望统一基础设施监控与 LLM 观测的企业；
- LiteLLM 等代理更适合作为统一模型入口和成本治理层，而不是完整替代进程内 Trace。

工具能力、定价、托管方式和产品归属都会变化，因此不应该仅凭一张“年度排行榜”做决定。

### 4. 五条真正有用的选型轴

选型时逐项回答：

1. **开放标准还是私有 SDK？** 能否通过 OTLP 导出，数据能否迁移？
2. **SaaS 还是自托管？** 数据驻留、合规和运维成本如何权衡？
3. **框架耦合还是框架无关？** 系统是否绑定 LangGraph、LlamaIndex 或自研编排？
4. **纯观测还是 Obs + Eval 一体化？** 是否需要数据集、Prompt 管理和在线评分？
5. **网关还是进程内？** 只看模型 API 边界是否足够？

一个重要的架构原则是：**尽量把 Emitter 与 Backend 分开选择。**

如果应用侧产生开放格式的数据，后端变化时不必重写全部埋点。真正的迁移成本通常集中在已保存的数据、查询、看板、告警和评估工作流，而不是初始化 SDK 的几行代码。

![Agent 可观测性工具分层](/blog-assets/agent-observability/fig-4-1.svg)

## 十三、从零落地的四个阶段

Agent 可观测性不需要第一天就记录所有内容。更可控的方式是分四个阶段推进。

### 第一阶段：先得到一棵完整的树

目标：链路不断。

- 为每次运行创建根 Trace；
- 覆盖模型、检索、工具和子 Agent；
- 打通 HTTP、消息队列和异步任务中的上下文传播；
- 记录状态、耗时与基础 Token 用量；
- 监控孤儿 Span 比例。

### 第二阶段：让 Trace 能解释问题

目标：从“发生了什么”升级到“为什么发生”。

- 记录 Prompt 与工具 I/O 的脱敏版本；
- 记录检索候选、重排和路由结果；
- 记录重试次数、步骤数和停止原因；
- 关联模型、Prompt、工具与 Agent 版本；
- 支持 Good Run / Bad Run Diff。

### 第三阶段：建立生产监控闭环

目标：在用户投诉前发现异常。

- 建立 `cost/run`、p95 延迟和 TTFT 基线；
- 监控工具失败、重试和循环；
- 把业务结果和在线评分写回 Trace；
- 使用尾部采样保留高价值异常；
- 将低分生产样本提炼为离线回归集。

### 第四阶段：治理观测系统自身

目标：让可观测性可以长期运行。

- 建立 PII 脱敏与字段分级；
- 设置采样、保留和归档策略；
- 监控遥测写入量与平台成本；
- 定期演练 Replay 和故障回溯；
- 验证 Exporter 故障不会阻塞业务；
- 建立 Trace 数据访问审计。

## 十四、一份上线前检查清单

在 Agent 进入生产环境前，可以用下面这份清单做最后评审。

### Trace 完整性

- [ ] 一次业务任务是否只有一个稳定的 `trace_id`？
- [ ] 模型、检索、工具和子 Agent 是否都能挂到正确父节点？
- [ ] HTTP、消息队列、后台任务是否传播 Trace Context？
- [ ] 是否监控孤儿 Span 和未正常关闭的 Span？

### 可解释性

- [ ] 能否找到每次工具选择和路由决策对应的 Span？
- [ ] 是否记录影响决策的检索上下文？
- [ ] 是否关联模型、Prompt、Agent 和工具版本？
- [ ] 能否比较同类任务的 Good Run 与 Bad Run？

### 成本与性能

- [ ] 是否能够计算单次运行总 Token 与总成本？
- [ ] 是否能够下钻到具体模型或子 Agent？
- [ ] 是否监控 TTFT、端到端延迟、步骤数和重试次数？
- [ ] 是否设置最大步骤数、超时和预算上限？

### 质量与告警

- [ ] 技术成功与任务成功是否分开记录？
- [ ] 在线评估结果能否写回对应 Trace？
- [ ] 高成本、高延迟、低质量 Trace 是否优先保留？
- [ ] 告警能否直接链接到相关 Trace？

### 隐私与治理

- [ ] Prompt、工具响应和检索内容是否在发送前脱敏？
- [ ] 是否禁止高基数字段进入 Metric Label？
- [ ] 是否明确数据保留时间、访问权限和删除机制？
- [ ] 是否监控可观测性平台自身的存储与费用？

## 结语：把 Agent 的黑盒变成证据链

Agent 的最大工程挑战，不是它偶尔会出错，而是它可能在没有异常、没有非 200 状态码、甚至输出十分流畅的情况下完成一次错误运行。

面对这种系统，仅记录最终答案是不够的。我们需要知道：

- 它看到了什么；
- 它做出了什么选择；
- 它调用了哪些模型和工具；
- 哪一步最先偏离正确路径；
- Token、时间和费用消耗在哪里；
- 修复后，同类运行是否真的变好。

Trace 提供执行骨架，Span 保存逐步证据，Metrics 发现趋势，Events 补充上下文，Eval 判断质量，Replay 与 Diff 帮助验证修复。它们组合起来，才构成完整的 Agent 工程反馈闭环。

因此，可观测性不是 Agent 上线后再补的一张看板，而是生产架构的一部分。

一个真正可运营的 Agent，不仅要能够完成任务，还必须能够回答：

> 这次运行为什么会得到这个结果？

当团队能够用一条完整 Trace 回答这个问题时，Agent 才真正从不可控的演示程序，变成了可以调试、监控和持续改进的生产系统。
