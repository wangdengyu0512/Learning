# 让两个自动系统的估算贴近现实：一套可解释的 PostgreSQL 性能调优方法论

> PostgreSQL 调优的核心，不是背参数，也不是看到慢查询就加索引，而是校准两个自动系统的判断：查询优化器在估算“哪个执行计划最便宜”，autovacuum 在估算“什么时候该清理旧版本”。当它们掌握的信息落后于现实，慢查询、错误计划、表膨胀和内存风险就会接踵而来。

很多数据库性能问题看起来毫无关联：

- 明明建了索引，查询却坚持全表扫描；
- 一条 SQL 昨天只要 200 毫秒，今天突然跑了 40 秒；
- 删除了大量数据，磁盘占用却没有下降；
- `work_mem` 已经调得很大，系统反而开始 OOM；
- 同一条查询，有时走 Nested Loop，有时走 Hash Join；
- 表越来越大，Index Only Scan 也突然变慢。

如果逐个记“标准答案”，很快就会陷入参数和经验法则的迷宫。更有效的做法，是把这些现象放进同一条因果链：

```text
现实中的数据与负载
        ↓
统计信息、索引、代价参数、内存、清理阈值
        ↓
优化器与 autovacuum 的估算
        ↓
执行计划与清理时机
        ↓
查询延迟、吞吐、膨胀和资源占用
```

你的任务不是替 PostgreSQL 接管方向盘，而是让它看到更接近现实的输入，并给它足够的资源做出正确选择。

## 一、先别改配置：调优必须从测量开始

“数据库慢”只是症状，不是根因。缺索引、统计信息过期、锁等待、表膨胀、内存不足和磁盘 I/O 饱和都可能表现为“慢”，但修复方式完全不同。

一套可靠的调优流程应该始终保持闭环：

```text
测量 → 定位 → 只改一个变量 → 复测
```

其中，测量最好从三个层次逐步收窄。

### 1. 实例级：整个数据库在等什么

先看 `pg_stat_activity` 中的等待事件：

```sql
SELECT
    wait_event_type,
    wait_event,
    count(*)
FROM pg_stat_activity
WHERE state = 'active'
GROUP BY wait_event_type, wait_event
ORDER BY count(*) DESC;
```

它回答的是全局问题：当前后端主要卡在磁盘 I/O、锁、WAL、客户端，还是根本没有等待、只是在消耗 CPU？

如果大量会话都在等待 `DataFileRead`，下一步应寻找制造最多磁盘读取的查询；如果集中在 `Lock`，就应该追踪阻塞链和长事务，而不是先去改缓存参数。

### 2. 查询级：谁消耗的累计时间最多

启用 `pg_stat_statements` 后，应优先按累计执行时间排序，而不是只盯平均耗时：

```sql
SELECT
    query,
    calls,
    total_exec_time,
    mean_exec_time
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 20;
```

一条每次只执行 5 毫秒、但被调用 5 万次的 SQL，通常比一条每天只跑三次、每次 15 秒的报表查询更值得优先优化。调优追求的是系统总收益，不是消灭看起来最吓人的单次数字。

### 3. 单条 SQL：时间究竟花在哪个节点

对目标查询执行：

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT ...;
```

这里有三个容易误读的地方：

1. **`cost` 不是毫秒。** 它是优化器用于比较候选计划的抽象代价。
2. **`actual time` 要结合 `loops`。** 一个内层节点单次只花 0.05 毫秒，但被执行 50 万次，累计代价仍然可能非常高。
3. **最重要的信号是估算行数与真实行数的差距。** `rows=10`、`actual rows=500000` 意味着优化器是在错误前提上选择计划。

还要同时观察：

- `Rows Removed by Filter` 是否巨大；
- `Buffers: shared hit/read` 中，磁盘读取是否过多；
- Sort 是否出现 `external merge Disk`；
- Hash 是否出现多个 batches；
- Index Only Scan 的 `Heap Fetches` 是否突然增加。

注意，`EXPLAIN ANALYZE` 会真正执行 SQL。分析 `UPDATE`、`DELETE` 或 `INSERT` 时，如果不想保留修改，可以放进事务后回滚：

```sql
BEGIN;
EXPLAIN (ANALYZE, BUFFERS)
UPDATE ...;
ROLLBACK;
```

## 二、第一个自动系统：查询优化器如何“猜”出执行计划

PostgreSQL 默认没有内建的 `FORCE INDEX`。优化器会枚举多种候选计划，为每一种估算代价，然后选择看起来最便宜的方案。

一个简化后的代价模型可以理解为：

```text
总代价 ≈ 预计读取的页数 × 单页代价
       + 预计处理的行数 × 单行 CPU 代价
       + 排序、哈希、并行等额外代价
```

问题在于，“预计读取多少页”和“预计处理多少行”都不是实时测出来的，而是根据统计信息推导出来的。因此，优化器选错计划时，首先应该问的不是“它为什么这么笨”，而是：**它依据的统计信息是否仍然代表当前数据？**

### 统计信息是快照，不是实时真相

`ANALYZE` 会抽样统计列的数据分布，并记录不同值数量、空值比例、常见值及频率、直方图等信息。优化器依靠这些数据估算条件的选择率。

例如，一列 `status` 只有四个值，优化器通常能较准确地判断 `status = 'cancelled'` 会返回多少行；而一个接近唯一的 `customer_id`，等值查询的选择率通常极低，更适合索引扫描。

但统计信息会过期。典型事故是：凌晨批量导入了 50 万条订单，却没有及时更新统计信息。早上的报表查询仍被估算为只返回 8 行，于是优化器选择 Nested Loop；实际却返回 50 万行，内层索引扫描也被执行了 50 万次，查询从几百毫秒恶化到几十秒。

这种场景的第一修复动作往往不是改 SQL，也不是新建索引，而是：

```sql
ANALYZE orders;
```

如果某个高基数列的默认采样精度不足，还可以只提高该列的统计目标，再重新分析：

```sql
ALTER TABLE users
ALTER COLUMN email SET STATISTICS 1000;

ANALYZE users;
```

核心思路始终不变：不强迫优化器选某个答案，而是修正它用来计算答案的输入。

### 为什么有索引仍可能走顺序扫描

索引不是“存在就必须使用”。优化器会根据查询命中数据的比例，在不同路径之间权衡：

- **Seq Scan**：命中大量行时，一次顺序读完整张表可能最便宜；
- **Index Scan**：只命中少量行时，快速定位最划算；
- **Bitmap Index/Heap Scan**：命中比例居中时，先收集位置，再批量回表；
- **Index Only Scan**：查询所需列都在索引中，并且可见性条件满足时，可以尽量避免回表。

因此，查询命中全表 40% 的数据时，即使有索引，顺序扫描也可能是正确选择。真正值得怀疑的是：选择率估算是否准确、随机读代价是否符合当前硬件，以及有没有更合适的索引路径。

### JOIN 算法的选择，本质上也是行数估算

三类常见 JOIN 各有适用条件：

- **Nested Loop**：外层很小，内层连接键有索引时非常高效；
- **Hash Join**：大批量等值连接时通常更合适，但哈希表需要足够内存；
- **Merge Join**：两侧已经有序，或排序成本可以接受时有优势。

最危险的计划通常不是 Nested Loop 本身，而是“优化器以为外层只有几行，所以选择 Nested Loop；实际外层却有几十万行”。看到内层节点的 `loops` 特别大时，要向上追查第一个估算严重偏离真实值的节点。

## 三、索引不是命令，而是给优化器提供一条更便宜的路

索引的作用不是保证“走索引”，而是把一种更低成本的候选路径加入计划空间。如果这条路径确实更便宜，优化器自然会选择它。

### 多列索引：围绕真实查询组织列顺序

假设查询是：

```sql
SELECT status, amount
FROM orders
WHERE customer_id = $1
  AND created_at > $2
ORDER BY created_at;
```

一个常见且有效的设计是：

```sql
CREATE INDEX idx_orders_customer_created
ON orders (customer_id, created_at)
INCLUDE (status, amount);
```

这里包含三个决策：

1. `customer_id` 是等值条件，放在前面；
2. `created_at` 同时承担范围过滤和排序，放在后面；
3. `status`、`amount` 只负责返回，不参与定位，放入 `INCLUDE`，为 Index Only Scan 创造条件。

“等值列在前、范围或排序列在后”是实用起点，但不是脱离数据分布的铁律。最终仍要用真实负载和 `EXPLAIN (ANALYZE, BUFFERS)` 验证。

### 除了普通 B-tree，还要知道三种针对性设计

- **覆盖索引**：通过 `INCLUDE` 携带返回列，减少回表；
- **部分索引**：只索引真正需要查询的少量数据，例如未处理订单；
- **表达式索引**：查询经常使用 `lower(email)` 等表达式时，直接为表达式建立索引。

如果是 `LIKE '%keyword%'` 这种前导通配查询，普通 B-tree 无法有效定位起点，通常需要考虑更匹配的索引类型和扩展，而不是继续堆普通索引。

### 索引也会收账单

每增加一个索引，写入都要维护更多索引项；索引自身也会膨胀；如果频繁更新的列被索引，还可能破坏 HOT 更新。

因此，索引设计不能只看读性能，还要问：

- 这张表是读多写少，还是写多读少？
- 这个查询是否真的高频或高成本？
- 能否用一个组合索引服务完整查询，而不是为每列各建一个索引？
- 新索引带来的写放大是否可接受？

正确顺序是：先用 `pg_stat_statements` 找到真正重要的查询，再设计最小必要索引，最后复测读取页数、执行时间和写入吞吐。

## 四、第二个自动系统：autovacuum 如何判断“该打扫了”

要理解 PostgreSQL 的表膨胀，必须先接受一个事实：`UPDATE` 通常不是原地修改。

在 MVCC 模型下：

- `UPDATE` 写入一个新行版本，并让旧版本等待回收；
- `DELETE` 先标记旧版本失效，而不是立即从文件中物理抹掉；
- 不同事务根据自己的快照看到不同版本，因此读写可以减少相互阻塞。

这套机制换来了良好的并发能力，也留下了一笔必须偿还的债务：旧版本会形成 dead tuples，需要 VACUUM 清理。

### 长事务为什么会导致膨胀

只要还有一个老事务持有旧快照，VACUUM 就不能回收那个快照可能仍然需要的版本。一个持续 40 分钟的报表事务，不仅可能持有锁，还可能让高频更新表在这 40 分钟里只产生垃圾、无法有效清理。

可以先查最老的事务：

```sql
SELECT
    pid,
    usename,
    state,
    xact_start,
    query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

长事务治理、合理的事务边界和超时设置，往往比单纯增加 autovacuum worker 更重要。

### 普通 VACUUM 做什么，又不做什么

普通 `VACUUM` 会把死元组占用的空间标记为可重用，但通常不会缩小表文件并把空间归还给操作系统。它还会维护可见性映射，这直接影响 Index Only Scan 是否需要回表检查可见性。

这解释了两个常见现象：

- 删除一半数据后，磁盘文件没有立即变小；
- Index Only Scan 的 `Heap Fetches` 突然增加，可能是高频写入后 VACUUM 没有及时恢复可见性信息。

已经严重膨胀并且必须立刻回收磁盘空间时，才考虑重写表的方案，例如在维护窗口使用 `VACUUM FULL`，或评估在线重整工具。它们与普通 VACUUM 的成本和锁影响完全不同，不能混为一谈。

### autovacuum 的问题通常不是没开，而是触发得太晚

autovacuum 会根据阈值判断一张表是否应该清理。可将核心公式简化为：

```text
触发阈值 = autovacuum_vacuum_threshold
         + autovacuum_vacuum_scale_factor × 表行数
```

如果比例因子是 0.2，那么一张十亿行的大表可能要累积约两亿个死元组才触发清理。对高频更新的大表，这往往过于迟钝。

比起粗暴地修改全局参数，更稳妥的方式是按表设置：

```sql
ALTER TABLE orders SET (
    autovacuum_vacuum_scale_factor = 0.01,
    autovacuum_vacuum_threshold = 1000
);
```

随后持续观察：

- `n_dead_tup` 是否长期增长；
- `last_autovacuum` 是否及时更新；
- autovacuum 是否能在下一轮写入高峰前完成；
- 是否存在长事务阻止清理；
- 表和索引的物理尺寸是否仍持续失控。

### HOT：从源头降低更新成本

当一次 `UPDATE` 没有修改任何被索引的列，并且当前堆页仍有空间时，PostgreSQL 有机会执行 HOT（Heap-Only Tuple）更新：新版本留在同一页，通过页内链条连接，不需要为新版本创建新的索引项。

这意味着两条实用原则：

1. 不要轻易给高频更新、低查询价值的列建索引；
2. 对高频更新表，可以评估降低 `fillfactor`，为页内更新预留空间。

索引设计和 VACUUM 从来不是两个孤立话题：索引越多，写入与清理成本越高；VACUUM 跟不上，表和索引又会反过来拖慢查询。

## 五、配置参数必须能映射回具体机制

调参数前，先回答一句：它影响的是优化器、内存、WAL、连接，还是 VACUUM？如果回答不出来，就不应该修改。

### 内存不是一个旋钮，而是四种不同用途

| 参数 | 作用 | 最容易犯的错误 |
|---|---|---|
| `shared_buffers` | PostgreSQL 真实使用的共享页缓存 | 以为越大越好，忽略操作系统页缓存 |
| `work_mem` | 每个排序、哈希等执行节点的工作内存 | 忘记它要乘以节点数和并发后端数 |
| `maintenance_work_mem` | VACUUM、建索引等维护操作的工作区 | 与普通查询内存混为一谈 |
| `effective_cache_size` | 告诉优化器系统可能有多少缓存，不实际分配 | 误以为调大会直接占用内存 |

最危险的是 `work_mem` 的乘法效应：

```text
峰值工作内存 ≈ work_mem × 单条查询的相关节点数 × 并发后端数
```

例如，`work_mem = 256MB`、典型查询有两个排序或哈希节点、并发后端达到 2000，仅理论上界就接近 1TB，远超一台 64GB 服务器的承受能力。

因此，OOM 的正确修复方向通常是降低全局 `work_mem`、减少真实并发后端，并对少量分析任务做会话级调整，而不是继续增加内存参数。

### 连接数也是内存问题

PostgreSQL 的每个客户端连接都会对应一个后端进程。把 `max_connections` 从几百直接调到几千，不仅增加进程调度成本，也会放大 `work_mem` 的乘数。

高并发 OLTP 更合理的做法通常是使用连接池，在事务级复用少量真实数据库连接。连接池并不只是“解决连接不够”，它同时在控制内存峰值和后端调度开销。

### 用代价参数描述硬件，而不是追求固定答案

`random_page_cost` 会影响优化器对随机读取的估价，从而改变顺序扫描与索引扫描的切换点。机械盘上的随机读取明显更贵，而 SSD、云盘和高缓存命中环境通常没有同样高的随机访问惩罚。

这类参数的正确用法是根据真实硬件和代表性查询进行校准，而不是从博客中复制一个数字。调整后，应观察计划是否发生符合预期的变化，以及真实执行时间和缓冲区读取是否改善。

### WAL 与 checkpoint：重点是摊平 I/O 峰值

写入先进入 WAL，脏页随后由 checkpoint 刷回数据文件。`max_wal_size` 太小时，checkpoint 可能被频繁触发；刷盘过于集中时，数据库会出现周期性 I/O 尖峰。

调优目标不是减少必须完成的总写入量，而是降低不必要的 checkpoint 频率，并把刷盘工作更均匀地分散到时间轴上。仍然要回到 wait events、WAL 统计和磁盘监控验证，而不是仅凭配置文件判断。

## 六、把知识变成一张故障排查表

线上收到“数据库变慢了”的告警时，可以按下面的顺序处理。

### 第一步：确认影响范围

- 是单条 SQL 慢，还是全库都慢？
- 是持续变慢，还是周期性尖峰？
- 是读慢、写慢，还是连接和锁等待？

### 第二步：从实例收窄到查询

1. 用 `pg_stat_activity` 看等待事件、阻塞和长事务；
2. 用 `pg_stat_statements` 按累计执行时间找头部 SQL；
3. 对目标 SQL 执行 `EXPLAIN (ANALYZE, BUFFERS)`。

### 第三步：根据证据归类

| 证据 | 优先怀疑 |
|---|---|
| 估算行数与真实行数差几个数量级 | 统计信息过期、采样精度不足、条件相关性难估 |
| `Rows Removed by Filter` 巨大 | 缺少合适索引，或过滤条件无法利用现有索引 |
| Nested Loop 内层 `loops` 巨大 | 外层行数被严重低估，JOIN 算法选错 |
| `Buffers read` 很高 | 大量物理 I/O、低效扫描、缓存不足或膨胀 |
| Sort 落盘、Hash 分批 | `work_mem` 不足，或查询处理的数据量本身过大 |
| `n_dead_tup` 持续增长 | autovacuum 触发太晚、清理速度不够或被长事务阻塞 |
| Index Only Scan 的 `Heap Fetches` 增加 | 可见性映射失效，VACUUM 没有及时跟上 |
| 周期性 I/O 尖峰 | checkpoint 过频或刷盘过于集中 |
| 大量连接且频繁 OOM | `work_mem × 节点数 × 并发数` 的放大效应 |

### 第四步：只改一个变量并复测

- 批量导入后估算失真：先 `ANALYZE`；
- 缺少低成本访问路径：设计最小必要索引；
- 大表积累过多死元组：按表调低 autovacuum 阈值；
- 长事务钉住旧版本：治理事务边界；
- 排序或哈希落盘：在并发预算内调整内存，或减少处理数据量；
- 连接过多：使用连接池压低真实后端数；
- checkpoint 尖峰：结合 WAL 和磁盘证据调整相关配置。

然后使用同样的 SQL、同样的参数和尽量接近的环境重复测量。一次同时改五个参数，即使性能提升，也无法知道哪项有效、哪项埋下了新风险。

---

## 结语：优秀的调优，是让自动化重新可信

PostgreSQL 并不缺自动化：优化器会自动选择扫描和 JOIN 算法，autovacuum 会自动回收旧版本，缓存、WAL 和 checkpoint 也都有自己的运行机制。

真正的问题通常不是“自动化不存在”，而是自动系统掌握的现实已经失真：

- 统计信息没有跟上数据变化；
- 索引没有覆盖真实访问模式；
- 代价参数仍描述着另一种硬件；
- autovacuum 的比例阈值不适合超大表；
- 长事务让本该清理的旧版本无法回收；
- 连接数和工作内存共同制造了远超物理内存的峰值。

所以，PostgreSQL 调优可以浓缩成一句话：

> **用测量找到偏差，用机制解释偏差，用最小改动校准输入，再用复测确认自动系统重新做出了正确判断。**

一旦建立这套思维，慢查询、索引、MVCC、VACUUM、内存和配置就不再是六组零散技巧，而是一套连贯、可验证、可以反复复用的方法论。
