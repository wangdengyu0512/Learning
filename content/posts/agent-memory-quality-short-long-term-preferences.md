用户第一次使用代码助手时说：“示例尽量用 TypeScript。”几天后，他在一个数据分析项目里又说：“这个项目统一使用 Python。”

下一次对话，Agent 应该用哪种语言？

如果系统只保存最后一句话，它可能把 Python 错当成用户的全局偏好；如果把两句话都塞进向量库，检索时又可能同时命中，让模型临场猜测；如果完全依赖最近聊天记录，换一个会话后偏好就消失了。

这正是 Agent 记忆体系真正困难的地方：**难点不是把信息存下来，而是判断信息属于哪个时间尺度、适用于什么范围、是否足够可信，以及在新场景中应该怎样使用。**

一个高质量的记忆系统至少要回答六个问题：

1. 什么信息只服务当前任务，应该留在短期记忆？
2. 什么信息具有跨会话价值，值得进入长期记忆？
3. 用户偏好是临时要求、项目约束，还是稳定习惯？
4. 新旧记忆冲突时，系统应该覆盖、追加，还是请求确认？
5. 检索到了记忆之后，如何避免它干扰当前任务？
6. 如何证明“有记忆”比“没有记忆”更准确，而不是只显得更懂用户？

本文不把记忆理解成一张向量表，而是把它视为一套持续运行的状态管理系统：

```text
事件进入
  ↓
短期状态更新
  ↓
提取记忆候选
  ↓
准入、归一、去重、冲突判断
  ↓
写入长期记忆
  ↓
按任务检索、过滤、排序
  ↓
注入当前上下文并影响行动
  ↓
根据结果更新、降权或遗忘
```

目标不是让 Agent “记得更多”，而是让它**在正确的时刻，以正确的置信度，使用正确范围内的记忆**。

## 一、先建立正确分类：时间尺度、内容类型和作用域是三条轴

很多设计从“短期记忆、长期记忆、用户偏好记忆”开始，但这三个概念并不处在同一个分类维度。

- 短期和长期描述的是**生命周期**；
- 用户偏好描述的是**记忆内容**；
- 全局、项目、任务描述的是**作用域**。

因此，“用户偏好记忆”既可能是短期的，也可能是长期的。

例如：

| 用户表达 | 生命周期 | 内容类型 | 作用域 |
| --- | --- | --- | --- |
| “这次回答不要展开原理” | 短期 | 表达偏好 | 当前回答 |
| “这个项目统一使用 Python” | 中长期 | 工作偏好 | 当前项目 |
| “以后代码示例优先用 TypeScript” | 长期 | 工作偏好 | 用户全局 |
| “我正在排查订单超时问题” | 短期 | 任务状态 | 当前线程 |
| “生产库已经从 MySQL 迁到 PostgreSQL” | 长期 | 业务事实 | 当前组织或项目 |

只按短期和长期分库，会丢失作用域；只按内容类型建表，又会忽略生命周期。更可靠的模型是同时记录三条轴：

```text
Memory = Lifecycle × Type × Scope
```

### 1. 按生命周期划分

- **瞬时状态**：单次模型调用中的中间结果，例如工具返回值、候选计划和局部变量；
- **短期记忆**：当前线程或任务需要持续使用的状态，例如最近消息、任务目标和未完成步骤；
- **长期记忆**：跨线程、跨会话仍有价值的信息，例如稳定偏好、历史事件和可复用经验。

### 2. 按内容类型划分

CoALA 等认知架构研究通常用工作记忆、情景记忆、语义记忆和程序性记忆描述语言 Agent 的记忆组成：

- **工作记忆**：当前正在处理什么；
- **情景记忆**：过去发生过什么；
- **语义记忆**：系统已经知道哪些事实；
- **程序性记忆**：某类任务应该怎样完成。

用户偏好通常属于语义记忆；一次部署失败及其处理过程属于情景记忆；从多次事故中沉淀出的排障流程属于程序性记忆。

### 3. 按作用域划分

- 当前调用；
- 当前线程；
- 当前任务；
- 当前项目；
- 当前用户；
- 当前团队或组织；
- Agent 全局。

作用域决定了一条记忆在哪里生效。前面的 TypeScript 与 Python 并不真正冲突：前者是用户全局默认值，后者是项目级覆盖值。问题只有在系统丢失作用域时才会出现。

## 二、短期记忆：不是“保留最近 N 轮”，而是维护当前任务状态

短期记忆经常被实现为聊天消息数组：保留最近 20 轮，超过长度就从头删除。这种实现可以支撑普通聊天，却不适合需要多步骤执行的 Agent。

原因很简单：**消息的时间顺序不等于信息的重要顺序。**

用户在第一轮提出的硬约束，可能比第十五轮的寒暄重要；工具在中间返回的订单号，可能在后续十步都要使用；一段很长的日志可能只需要留下一个结论。机械地截断消息，迟早会把仍然有效的任务状态删掉。

### 短期记忆应该保存什么

一个可执行的短期状态至少包含：

```ts
type WorkingMemory = {
  threadId: string;
  goal: string;
  constraints: string[];
  plan: Array<{
    step: string;
    status: "pending" | "running" | "done" | "blocked";
  }>;
  entities: Record<string, string>;
  pendingQuestions: string[];
  recentMessages: Message[];
  toolResults: ToolResultRef[];
  summary?: string;
};
```

这里的关键变化是：消息只是短期记忆的一部分，任务目标、约束、实体、计划和待确认问题都有独立位置。

### 用分区预算代替统一截断

可以把当前上下文预算分成几个区，而不是让所有内容竞争同一个消息窗口：

```text
系统与安全规则       20%
当前目标和硬约束     15%
任务计划与执行状态   15%
最近对话             20%
工具结果             15%
长期记忆             10%
输出余量              5%
```

比例不是固定标准，但“分区预算”这个思想很重要。它避免长日志、长网页或连续工具调用吞掉目标和约束。

### 压缩不是普通摘要

普通摘要倾向于追求可读性，任务记忆压缩则要追求**可继续执行**。一份合格的短期摘要至少应该保留：

- 用户最终目标；
- 已确认的事实；
- 仍然有效的硬约束；
- 已完成和未完成步骤；
- 关键工具结果的引用；
- 当前阻塞点；
- 用户尚未回答的问题。

压缩前后的判断标准不是“意思是否差不多”，而是：**Agent 能否只根据压缩结果恢复任务并继续工作。**

### 短期记忆晋升为长期记忆

不是所有短期信息都应该在会话结束时消失。会话中可能产生三类值得晋升的内容：

1. 用户明确要求记住的事实或偏好；
2. 多次任务都会复用的稳定信息；
3. 经结果验证、未来可以复用的经验。

晋升必须经过独立的写入策略。不能把整份会话摘要直接复制到长期存储，因为摘要中混合了临时计划、模型推断和用户事实，未来很难分别更新。

## 三、长期记忆：保存可演化的状态，而不是无限增长的历史

长期记忆的核心价值是跨会话连续性，但“持久化”不代表“永久不变”。现实世界中的事实会变化，用户偏好会改变，经验也会被新结果推翻。

因此，一条长期记忆不应该只有正文和 embedding。它至少需要内容、来源、时间、作用域、置信度和状态：

```ts
type MemoryRecord = {
  id: string;
  subject: string;
  predicate: string;
  value: unknown;
  type: "semantic" | "episodic" | "procedural" | "preference";
  scope: {
    organizationId?: string;
    userId?: string;
    projectId?: string;
    taskId?: string;
  };
  source: {
    kind: "user_explicit" | "user_implicit" | "tool" | "document" | "agent_inference";
    eventId: string;
  };
  confidence: number;
  importance: number;
  validFrom: string;
  validUntil?: string;
  status: "active" | "superseded" | "expired" | "deleted";
  supersedes?: string;
  createdAt: string;
  updatedAt: string;
};
```

### 语义、情景和程序性记忆需要不同治理方式

| 类型 | 示例 | 主要查询 | 更新方式 |
| --- | --- | --- | --- |
| 语义记忆 | 项目使用 PostgreSQL | 当前事实是什么 | 更新、替代、失效 |
| 情景记忆 | 10 月 3 日部署曾因连接池耗尽失败 | 过去发生过什么 | 追加为主，保留时间线 |
| 程序性记忆 | 发布前先执行迁移检查 | 这类任务怎样完成 | 版本化、验证后发布 |
| 偏好记忆 | 回答优先给结论再解释 | 用户希望怎样交互 | 按作用域覆盖、允许撤销 |

把这些内容放进同一个向量集合不是绝对错误，但不能使用同一套更新策略。事件历史不应因为新事件出现而被覆盖；当前事实不能只追加不失效；程序性规则不能仅凭一次成功就自动升级成全局流程。

### 长期记忆需要时间语义

至少要区分四种时间：

- **事件时间**：事情什么时候发生；
- **记录时间**：系统什么时候知道；
- **生效时间**：事实或偏好从什么时候开始适用；
- **失效时间**：什么时候不再适用。

例如，用户在 10 月 15 日说：“我们 10 月 1 日已经把数据库迁到了 PostgreSQL。”事件时间和记录时间相差两周。如果系统只保存 `created_at = 10 月 15 日`，就无法正确回答“10 月 5 日项目使用什么数据库”。

这也是为什么长期记忆不仅是语义检索问题，还包含时间建模问题。

## 四、用户偏好记忆：个性化的关键，也是最容易记错的部分

用户偏好能显著改善体验，但它比普通事实更模糊。

“项目数据库是 PostgreSQL”通常可以验证；“用户喜欢简洁回答”却可能只在某些任务中成立。用户在手机上希望简洁，在学习新概念时又可能希望展开；平时偏好 TypeScript，在数据项目中仍然使用 Python。

因此，偏好记忆必须额外记录四类信息：

1. **显式程度**：用户直接声明，还是系统从行为推断；
2. **适用范围**：全局、项目、任务还是单次回答；
3. **约束强度**：必须遵守，还是可以被任务需要覆盖；
4. **稳定程度**：一次性要求、重复倾向还是长期习惯。

### 偏好可以分成五类

- **表达偏好**：语言、篇幅、格式、语气；
- **交互偏好**：先执行还是先确认、是否展示中间过程；
- **工作偏好**：技术栈、工具、目录结构、文档规范；
- **内容偏好**：推荐主题、信息密度、示例类型；
- **风险约束**：过敏信息、禁忌、禁止执行的动作。

风险约束表面上也是偏好，但治理级别更高。例如“不要自动发送邮件”不应和“回答用表格”使用同一置信阈值或覆盖规则。

### 显式偏好与隐式偏好必须分开

下面两条记忆看起来相同，可信度却不同：

```text
用户明确说：“以后回答先给结论。”
系统观察到：用户连续三次跳过长解释，只看了摘要。
```

前者可以直接形成显式偏好；后者最多形成一个低置信候选。隐式行为可能受场景、时间和界面影响，不能轻易被固化成用户人格。

推荐采用以下策略：

- 单次行为不写入长期偏好；
- 多次一致行为形成候选偏好；
- 候选只用于低风险适配；
- 用户确认后再升级为显式偏好；
- 高风险约束不得仅靠行为推断；
- 用户明确纠正时立即降低或撤销旧偏好。

### 偏好覆盖不是简单的“最后写入获胜”

更合理的优先级是：

```text
当前用户明确指令
  > 当前任务硬约束
  > 当前项目显式偏好
  > 用户全局显式偏好
  > 当前项目推断偏好
  > 用户全局推断偏好
  > 系统默认值
```

于是，“全局优先 TypeScript”和“当前项目使用 Python”可以同时存在。系统不需要删除前者，只需要在当前作用域选出有效值。

### 不确定时，宁可不个性化

记忆系统常见的错误目标是“尽量使用记忆”。更可靠的原则是：

> 当偏好存在冲突、置信度不足或作用域不明确时，默认不使用，必要时向用户确认。

错误的个性化比没有个性化更损害信任。一个从未记住偏好的 Agent 只是普通；一个自信地记错用户偏好的 Agent 会显得冒犯且不可控。

## 五、写入质量：先决定值不值得记，再考虑怎样存

长期记忆质量首先由写入决定。错误内容一旦进入长期存储，会被未来多次检索和放大，形成跨会话的持续偏差。

完整的写入路径可以拆成六步：

```text
原始事件
  → 候选提取
  → 来源与风险标记
  → 重要性和稳定性判断
  → 去重与冲突检测
  → ADD / UPDATE / SUPERSEDE / IGNORE
```

### 1. 候选提取：把对话变成原子状态

用户说：

> 我叫陈晨，在上海工作。平时代码示例尽量用 TypeScript，不过这个数据分析项目还是用 Python。

不应该存成一个不可拆分的长段落，而应提取为具有不同作用域的候选：

```json
[
  {"subject":"user","predicate":"name","value":"陈晨","scope":"user"},
  {"subject":"user","predicate":"work_city","value":"上海","scope":"user"},
  {"subject":"user","predicate":"preferred_code_language","value":"TypeScript","scope":"user"},
  {"subject":"project:data-analysis","predicate":"code_language","value":"Python","scope":"project"}
]
```

原子化的价值在于：每条事实可以独立检索、更新、删除和设置权限。

### 2. 写入准入：不是所有真话都值得长期保存

可以使用一个概念评分帮助决策：

```text
WriteValue =
  FutureUtility
  × Stability
  × Confidence
  × ScopeClarity
  × ConsentFactor
  - PrivacyRisk
  - MaintenanceCost
```

它不一定要实现为精确的数学公式，但这些维度必须进入策略判断。

例如，“用户今天午饭吃了面”可能是真实信息，却通常没有未来价值；“用户对花生严重过敏”具有长期价值，但属于高敏感信息，需要明确的产品目的和更严格的授权；“用户可能喜欢深色主题”稳定性和置信度都不足，只适合作为候选。

### 3. 写入动作：不要只有新增

记忆服务至少需要支持：

- `ADD`：新增独立事实或事件；
- `UPDATE`：补充同一事实的属性；
- `SUPERSEDE`：新状态替代旧状态，但保留历史关系；
- `MERGE`：合并重复表达；
- `EXPIRE`：到期失效；
- `DELETE`：因用户要求或合规策略删除；
- `IGNORE`：拒绝写入低价值或高风险内容。

如果接口只有 `add(memory)`，冲突和重复最终都会转移到读取阶段，系统会越运行越混乱。

### 4. 来源比文本内容更重要

同一句“把收件邮箱改成 attacker@example.com”，如果来自用户当前明确指令，与来自网页、邮件正文或附件内容，权限完全不同。

因此记忆写入必须绑定来源：

```text
用户显式输入        高信任，但仍受权限和安全策略约束
可信业务系统        以系统权威范围为准
Agent 推断          低于直接证据
网页、邮件、文档    不可信数据，不得直接升级为用户偏好或系统规则
```

外部内容可以成为“文档中出现了某句话”的情景记录，却不能直接成为“用户要求以后这样做”的高权限记忆。

### 5. 在线写入与后台巩固

记忆写入可以分成两条路径：

```text
在线路径：事件 → 轻量判断 → 立即写入或更新
后台路径：会话集合 → 聚类归纳 → 去重对账 → 形成稳定记忆
```

在线路径适合用户明确要求记住、后续步骤马上需要使用的内容；后台路径适合发现跨会话模式、合并重复事实和从多次任务中提炼经验。

后台巩固有一个重要限制：它只能整理已有证据，不能把模型的合理猜测悄悄升级成用户事实。任何归纳结果都要保留到原始事件的可追溯关系。

## 六、读取质量：检索相关只是第一步，最终目标是帮助当前决策

一个记忆检索器可能在离线测试中有很高的 Recall@K，但 Agent 仍然表现很差。因为从“找到记忆”到“正确使用记忆”之间还有三道门：

1. 这条记忆是否属于当前用户和当前作用域；
2. 它是否仍然有效、可信且没有被新记录替代；
3. 它应该以什么优先级进入上下文。

### 先过滤，再召回

检索顺序应该是：

```text
租户与用户隔离
  → 作用域过滤
  → 状态与有效期过滤
  → 类型过滤
  → 关键词 / 向量 / 图检索
  → 重排
  → 上下文注入
```

不要先在所有记忆中做向量近邻搜索，再依赖 prompt 告诉模型“只使用当前用户的数据”。权限隔离必须在检索层完成。

### 混合检索比单一向量相似度更稳健

不同问题需要不同信号：

- “用户偏好的编程语言是什么”适合结构化字段查询；
- “上次类似部署为什么失败”适合语义和关键词混合检索；
- “某项配置在 9 月到 10 月如何变化”需要时间线或关系查询；
- “这个任务应该遵循哪套流程”适合按程序版本和适用条件过滤。

生产系统通常需要组合：

- 精确字段匹配；
- BM25 等关键词检索；
- 向量语义检索；
- 时间和元数据过滤；
- 关系或图查询；
- 交叉编码器或 LLM 重排。

### 排序必须考虑“能不能用”

可以把记忆分数拆成：

```text
MemoryScore =
  Relevance
  × ScopeMatch
  × Confidence
  × Freshness
  × Importance
  × SourceTrust
  × TaskCompatibility
```

语义相似度只是 `Relevance`。如果作用域不匹配、已经失效或来源不可信，即使文本再相似，也不应该进入上下文。

### 记忆应该分区注入，而不是混成一段文本

推荐把不同记忆以明确标签放入上下文：

```text
[当前任务]
目标、计划、阻塞点

[硬约束]
当前项目必须使用 Python 3.12

[用户偏好]
回答先给结论，再给必要解释

[相关历史]
2026-10-03：同类部署曾因连接池耗尽失败

[可复用流程]
发布前执行迁移兼容性检查
```

这样做有三个好处：模型更容易理解优先级，系统可以分别控制 token 预算，也能记录是哪类记忆影响了最终行动。

### 允许检索器返回“没有可靠记忆”

检索系统不应该被迫每次返回固定的 Top K。低于阈值、相互冲突或无法确认作用域时，空结果是正确结果。

高质量记忆系统需要具备弃权能力：

```text
未找到可靠证据 → 不注入记忆 → 使用当前输入或请求确认
```

这比为了“体现个性化”而使用一条勉强相关的旧记忆更可靠。

## 七、更新与遗忘：记忆质量不是写出来的，而是长期维护出来的

如果长期存储只增加不减少，系统最终会变成一座包含重复、冲突、过期和低价值内容的档案馆。检索成本会上升，错误命中增多，模型也更容易被无关信息干扰。

遗忘不是记忆系统的缺陷，而是保持质量的机制。

### 不同记忆采用不同遗忘策略

| 记忆内容 | 推荐策略 |
| --- | --- |
| 当前任务临时变量 | 任务结束后删除 |
| 登录验证码、临时链接 | 严格 TTL，通常不进入通用记忆 |
| 用户稳定表达偏好 | 长期保留，但允许用户修改和删除 |
| 项目当前状态 | 新状态替代旧状态，旧状态转历史 |
| 历史事故事件 | 保留时间线，降低默认召回权重 |
| 推断偏好 | 随时间衰减，长期未验证则删除 |
| 可复用工作流程 | 版本化，按效果重新验证 |

### 更新当前值，但保留时间线

对于会变化的事实，推荐同时维护“当前视图”和“事件历史”：

```text
current_state:
  database = PostgreSQL
  valid_from = 2026-10-01

history:
  MySQL       [2024-06-01, 2026-10-01)
  PostgreSQL  [2026-10-01, ...)
```

当前视图服务大部分在线查询，历史记录服务审计、时间推理和变更分析。只有当前值而没有历史，会丢失可解释性；只有历史而没有当前视图，又会增加每次读取的推理成本。

### 衰减不等于删除

记忆可以经历多个阶段：

```text
活跃 → 降权 → 归档 → 过期 → 删除
```

低频使用的情景记忆可以先降低默认召回权重，而不是立即删除；明确失效的临时信息应直接过期；用户要求删除的数据则不能只做“搜索不可见”，还要处理索引、缓存、摘要和派生数据。

### 访问频率不能单独决定价值

“很少被访问”不代表“不重要”。安全约束、灾难恢复流程和过敏信息可能长期不被调用，却在关键时刻具有极高价值。因此遗忘策略至少要综合：

- 最近访问时间；
- 使用频率；
- 业务重要性；
- 是否可从权威源重新获取；
- 隐私风险；
- 是否存在替代版本；
- 删除错误的代价。

## 八、安全与用户控制：记忆越持久，错误和泄漏的半衰期越长

一次普通回答中的错误通常只影响当前会话；一条错误长期记忆可能在数周后反复触发。一次提示注入如果进入长期记忆，也会从“单轮攻击”变成“持久化攻击”。

因此，记忆系统的安全边界必须高于普通 RAG。

### 防止记忆投毒

至少需要以下控制：

- 外部网页、邮件、附件中的指令默认视为不可信数据；
- 工具结果不能直接修改高权限用户档案；
- 写入用户偏好、身份和安全约束时检查来源；
- 高影响记忆写入需要确定性规则或用户确认；
- Agent 推断与用户陈述分库存储或显式标记；
- 每次写入保留原始事件、执行主体和策略版本；
- 对突然出现的大量记忆写入进行限流和异常检测。

### 数据最小化

不要因为“以后可能有用”就默认永久保存。写入前应该问：

1. 完成产品功能真的需要这条信息吗？
2. 能否只保存类别，而不保存原始敏感值？
3. 能否缩短保留时间？
4. 能否从权威业务系统按需查询，而不是复制一份？
5. 用户是否知道这条信息会被长期使用？

密码、访问令牌、验证码和私钥不应进入通用长期记忆。对于健康、财务、精确位置等敏感信息，还需要结合具体业务和适用法规设计独立策略。

### 用户必须能管理自己的记忆

一个成熟的产品至少应提供：

- 查看 Agent 记住了什么；
- 查看记忆来源和更新时间；
- 修改错误事实或偏好；
- 删除单条、某一类别或全部记忆；
- 暂停个性化和自动写入；
- 指定某条偏好的适用范围；
- 导出用户相关记忆。

“用户能删除”不能只停留在产品界面。底层还要覆盖主存储、向量索引、缓存、搜索副本、离线特征和由该记忆生成的摘要。

### 多 Agent 共享要采用最小权限

多个 Agent 不应因为属于同一个系统就默认共享全部记忆。推荐按资源建立明确授权：

```text
Agent A：可读用户表达偏好，不可读财务信息
Agent B：可读项目技术约束，不可读私人会话历史
Agent C：只能写入任务事件，不能修改用户档案
```

共享记忆的关键不是“大家都能看到”，而是“每个 Agent 只看到完成任务所需的最小集合”。

## 九、评估：不要只测“能否从长文本里找到一句话”

记忆系统的最终指标不是存储条数，也不是向量检索命中率，而是：**加入记忆以后，Agent 是否以可接受的成本更准确地完成了任务。**

LongMemEval 将长期对话记忆拆成信息提取、跨会话推理、时间推理、知识更新和拒答等能力。这种分类比单纯的长上下文“找针”更接近真实系统，因为 Agent 不仅要找到旧信息，还要识别新信息何时覆盖旧信息，并在证据不足时选择不回答。

### 分层评估比单一总分更有诊断价值

可以把指标分成四层。

#### 1. 写入层

- 候选提取 Precision / Recall；
- 原子事实拆分正确率；
- 作用域分类准确率；
- 显式与推断偏好区分准确率；
- `ADD / UPDATE / SUPERSEDE / IGNORE` 动作准确率；
- 敏感信息误写入率。

#### 2. 存储治理层

- 重复记忆率；
- 冲突发现率；
- 过期记忆清理成功率；
- 删除传播完成率；
- 来源可追溯率；
- 跨用户数据隔离失败率。

#### 3. 检索层

- Recall@K；
- Precision@K；
- 时间范围过滤准确率；
- 作用域过滤准确率；
- 旧版本误召回率；
- 正确弃权率；
- 检索延迟和注入 token 数。

#### 4. 任务层

- 使用记忆后的任务成功率；
- 用户重复说明相同信息的次数；
- 偏好遵循率；
- 因错误记忆导致的任务失败率；
- Agent 引用了记忆但使用错误的比例；
- 用户纠正或删除记忆的比例。

### 必须覆盖的测试场景

一套实用测试集至少包含：

| 场景 | 要验证什么 |
| --- | --- |
| 跨会话回忆 | 新会话能否找回稳定事实 |
| 多条信息组合 | 能否从不同会话组合出答案 |
| 时间查询 | 能否区分过去状态与当前状态 |
| 知识更新 | 新事实能否正确替代旧事实 |
| 偏好覆盖 | 项目偏好能否覆盖全局默认值 |
| 不确定性 | 无可靠记忆时能否拒答或询问 |
| 记忆投毒 | 外部恶意文本是否会污染长期记忆 |
| 用户删除 | 删除后所有读取路径是否都不可见 |
| 跨用户隔离 | 一个用户的记忆是否会泄漏给另一个用户 |
| 长期退化 | 记忆数量增长后质量和延迟是否恶化 |

### 做消融实验，而不是只测最终方案

建议至少比较：

```text
无记忆
vs 仅最近对话
vs 对话摘要
vs 纯向量记忆
vs 结构化用户档案
vs 混合检索与时间治理
```

这样才能知道改进来自哪里。例如，结构化偏好档案可能显著提升个性化，但对历史事件问答帮助有限；向量检索可能提高事件召回，却增加旧事实干扰。没有消融实验，总分提升很难转化为架构决策。

## 十、一个可落地的最小架构

不需要一开始就引入知识图谱、专用记忆模型和复杂多 Agent 协议。多数产品可以从下面的分层架构起步：

```text
┌──────────────── Agent Runtime ────────────────┐
│ 当前目标、计划、消息、工具结果                │
└───────────────────┬───────────────────────────┘
                    │
          ┌─────────▼─────────┐
          │ Memory Candidate  │  提取候选、来源和作用域
          │ Extractor         │
          └─────────┬─────────┘
                    │
          ┌─────────▼─────────┐
          │ Policy Engine     │  准入、风险、去重、冲突
          └──────┬───────┬────┘
                 │       │
       ┌─────────▼─┐   ┌─▼────────────────┐
       │ Profile DB│   │ Episode / Event  │
       │ 当前事实  │   │ Store            │
       │ 用户偏好  │   │ 历史事件与经验   │
       └──────┬────┘   └───────┬──────────┘
              └────────┬───────┘
                       │
             ┌─────────▼─────────┐
             │ Hybrid Retriever  │
             │ filter + search   │
             │ + rerank          │
             └─────────┬─────────┘
                       │
             ┌─────────▼─────────┐
             │ Context Builder   │  分区、预算、优先级
             └───────────────────┘
```

### 存储职责

- **线程状态库**：保存 checkpoint、任务状态和短期摘要；
- **关系数据库**：保存用户档案、偏好、当前事实、权限和版本关系；
- **事件存储**：保存带时间的交互、任务结果和变更记录；
- **向量索引**：辅助检索情景记忆和非结构化经验；
- **对象存储**：保存大型原始材料，记忆记录只保留引用；
- **审计日志**：记录谁在何时根据哪条策略读取或修改了记忆。

向量数据库是可选组件，不是记忆系统的定义。用户姓名、语言偏好和项目数据库这类字段，关系查询通常比向量相似度更准确、更便宜，也更容易更新。

### 核心接口

```ts
interface MemoryService {
  propose(event: InteractionEvent): Promise<MemoryCandidate[]>;
  mutate(candidate: MemoryCandidate): Promise<MemoryMutation>;
  search(query: MemoryQuery): Promise<RetrievedMemory[]>;
  resolvePreference(query: PreferenceQuery): Promise<ResolvedPreference | null>;
  explain(memoryId: string): Promise<MemoryExplanation>;
  delete(memoryId: string, actor: Actor): Promise<DeletionReceipt>;
}
```

这里特意把 `propose` 与 `mutate` 分开。模型可以提出记忆候选，但是否真正写入、更新还是拒绝，应该由包含确定性规则的策略层决定。

### 在线请求流程

```text
1. 加载线程 checkpoint
2. 解析当前用户、项目和任务作用域
3. 根据任务类型决定需要哪些记忆
4. 先查结构化事实和偏好，再检索相关事件
5. 过滤失效、冲突和低置信记录
6. 按区域和 token 预算构造上下文
7. 执行 Agent 推理与工具调用
8. 更新短期状态
9. 提取本轮长期记忆候选
10. 同步处理高优先级写入，其余进入后台巩固
```

### 可观测性

每次运行至少记录：

- 产生了哪些记忆候选；
- 哪些被写入、合并或拒绝，原因是什么；
- 检索使用了哪些过滤条件；
- 哪些记忆进入了最终上下文；
- 每条记忆的分数和来源；
- 最终输出是否实际使用了这些记忆；
- 记忆链路增加了多少延迟和 token。

没有这些信息，线上出现“Agent 为什么记错了”时，团队只能阅读整段对话猜测，无法判断错误发生在抽取、写入、检索还是使用阶段。

## 十一、分阶段落地：先把正确性做稳，再追求自动学习

### 第一阶段：显式、结构化、可删除

优先实现：

- 线程级短期状态；
- 任务摘要与 checkpoint；
- 用户明确表达的偏好；
- 结构化作用域；
- 来源、时间和版本字段；
- 查看、修改和删除接口；
- 严格的租户和用户隔离。

这一阶段可以暂时不做隐式偏好推断。显式记忆虽然覆盖面有限，却容易验证，能先建立用户信任和治理基础。

### 第二阶段：自动提取和混合检索

增加：

- 对话中的记忆候选提取；
- 去重、归一和冲突检测；
- 关键词与向量混合检索；
- 时间过滤和版本替代；
- 离线评估集和线上观测面板。

这一阶段的重点不是提高写入数量，而是控制误写入率。

### 第三阶段：巩固、经验学习和多 Agent 共享

在基础质量稳定后，再引入：

- 跨会话偏好模式识别；
- 情景记忆归纳为程序性经验；
- 基于任务结果调整记忆权重；
- 时间图谱和复杂关系推理；
- 多 Agent 之间的细粒度授权共享；
- 针对不同用户或任务学习个性化写入策略。

程序性记忆尤其需要谨慎。一次成功不代表流程可靠，至少要结合多次结果、失败案例和人工规则，避免把偶然路径固化成长期行为。

## 十二、把设计压缩成十二条原则

1. **消息历史不是完整记忆。** 它只是记忆形成的原始材料之一。
2. **短期记忆围绕任务状态组织。** 不要只保留最近 N 轮消息。
3. **长期记忆必须可更新。** 持久化不等于永久有效。
4. **用户偏好是一类内容，不是独立时间层级。** 它也有临时与长期、全局与局部之分。
5. **显式偏好和推断偏好分开管理。** 二者不能共享同一置信等级。
6. **每条长期记忆都要有来源、时间、作用域和状态。** 只有正文和 embedding 不够。
7. **写入动作不能只有新增。** 更新、替代、合并、过期和拒绝同样重要。
8. **先做权限和作用域过滤，再做语义检索。** 不要把隔离责任交给模型。
9. **允许系统没有答案。** 空检索和请求确认都是高质量行为。
10. **遗忘是质量控制机制。** 不受治理的记忆只会持续积累噪声。
11. **用户应能查看、纠正和删除自己的记忆。** 可控性是个性化的前提。
12. **以任务效果评估记忆。** 存得多、找得快都不等于用得对。

## 结语：真正的记忆不是数据库能力，而是判断能力

Agent 记忆体系最容易被低估，因为它在原型阶段看起来只是“把历史存起来，再检索回来”。但系统一旦长期运行，就会立即遇到更本质的问题：事实会变化，偏好有作用域，来源有可信等级，记忆会互相冲突，旧内容会失效，敏感信息必须删除。

因此，高质量记忆不是单点技术，而是一组协同工作的判断：

```text
什么值得记
→ 记成什么结构
→ 在哪里生效
→ 什么时候取回
→ 怎样影响当前任务
→ 何时更新或忘记
```

短期记忆保证 Agent 不丢失当前任务，长期记忆提供跨会话连续性，用户偏好记忆负责个性化；而来源、时间、作用域、冲突和用户控制把三者连接成一套真正可治理的系统。

最终，优秀的 Agent 不应该让用户明显感受到“它存了很多东西”。更理想的体验是：该记住的无需重复说明，临时要求不会被永久误解，改变过的信息不会继续生效，而用户始终知道自己可以查看、修改和删除这些记忆。
