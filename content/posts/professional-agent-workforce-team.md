一家制造企业收到供应商的延期通知。采购人员需要确认补货时间，供应链人员需要计算受影响订单，计划人员需要调整生产安排，财务人员需要核算加急成本，业务负责人还要决定是否调整对客户的承诺。

如果把这些工作交给 AI，问题很快会从“能否分析这份通知”变成一组组织问题：谁负责确定影响范围？谁有权提出采购变更？几个智能体的结论不一致时如何处理？方案批准以后由谁执行？执行完成后凭什么认定问题已经解决？

**专业智能体员工团队的设计，需要把专业能力、岗位责任、协作过程和业务验收连接起来，让每项工作都有明确的承接者、交付物和完成依据。**

本文延续[《从理解企业到自主运行：基于世界行为模型的企业级 AI 操作系统》](../enterprise-ai-operating-system-wbm/)中的 Agent Workforce 思路，展开数字员工的组织与运行方式。文中的岗位、协作规则和落地步骤是一套建议方案；订单、时间、金额及执行结果均为教学示例，不代表已经上线的系统或实际经营数据。

## 一、为什么需要专业智能体员工团队

### 1.1 业务工作具有连续性

对一个业务问题给出解释，只是工作的一部分。供应商延期以后，即使原因分析完全正确，企业仍然需要找到可行方案，获得授权，执行变更，跟踪后续状态。

这类工作具有三个特点。

首先，任务跨越多个专业领域。采购价格、库存可用量、生产能力和客户交期之间存在约束关系，一个局部最优方案可能损害整体结果。

其次，任务持续时间长于一次模型调用。供应商回复、人工审批、物料运输和生产排期都需要等待，团队必须能够保存进度，并在条件变化后继续工作。

最后，任务是否完成需要业务证据。生成了一份计划，并不能证明物料已经到货；提交了采购申请，也不能证明客户能够按时收到产品。

因此，团队需要管理从目标提出到结果确认的全过程。

### 1.2 专业化应围绕工作边界设计

把企业现有岗位名称全部复制成智能体，未必能形成有效团队。一个岗位是否值得独立设置，需要看它是否具有清晰的输入、专业方法、交付标准或权限边界。

例如，库存分析和采购分析可以并行进行，因为它们使用不同的信息、回答不同的问题。采购方案制定与采购执行也适合分开，因为执行涉及真实业务变更，需要单独控制授权。

如果两项工作始终使用相同上下文、没有独立交付价值，而且拆开后只增加反复传话，就可以由同一个员工承担。**团队规模应由任务依赖和治理需要决定。**

## 二、专业智能体员工的定义：身份、职责与交付

### 2.1 从能力名称走向岗位契约

本文把专业智能体员工定义为：**在明确业务范围和授权条件内，使用专业知识、技能与工具，持续承接工作，并按约定标准交付结果的数字工作单元。**

“员工”是组织管理上的表达。业务责任、权限批准和最终验收仍需映射到明确的人类负责人及企业制度。

建立岗位时，应先回答下面这些问题。

| 岗位要素 | 需要明确的内容 | 供应链分析员示例 |
| --- | --- | --- |
| 服务对象 | 服务哪个部门，由谁负责 | 供应链部门，供应链经理负责 |
| 核心职责 | 对哪类工作承担交付责任 | 分析物料异常对订单和生产计划的影响 |
| 工作输入 | 接收什么事件、对象和约束 | 延期通知、订单范围、当前库存、交期要求 |
| 专业方法 | 使用哪些规则、计算与判断方法 | 需求展开、可分配量计算、关键路径分析 |
| 标准交付 | 必须交付什么内容 | 影响清单、缺口计算、证据和未决事项 |
| 权限范围 | 可访问的数据和可执行的动作 | 查询授权范围内的订单、库存与计划 |
| 升级条件 | 哪些情况需要人工介入 | 库存口径冲突、关键数据缺失、影响超出范围 |
| 验收标准 | 如何确认本次工作合格 | 对象覆盖完整、计算可复核、结论有来源 |

这份契约也限定了岗位的能力声明。供应链分析员可以指出某个订单存在交付风险，但不能仅凭分析结果修改客户合同或批准额外支出。

### 2.2 区分岗位、员工和任务运行

岗位是一类职责的模板，员工是绑定具体配置与身份的工作承接者，任务运行是员工处理某次工作的执行过程。

例如，企业可以只有一套“供应链分析员”岗位模板，却为不同事业部配置不同的数据范围和规则版本。每位员工又可能在不同时段处理多个订单异常。

这种区分使组织能够分别管理岗位标准、员工权限和单次任务进度。一次任务失败，应根据原因调整任务、配置或岗位设计，不能把三者混为一谈。

## 三、专业能力如何构成：知识、技能、工具与经验

### 3.1 知识回答业务含义，技能规定处理方法

岗位知识包括业务术语、制度、操作规范、产品资料和历史案例。每项知识都应带有适用范围、来源与有效期。例如，同一种物料在不同工厂可能采用不同的检验要求，旧规则不能无条件用于新任务。

技能则把工作方法组织成可重复执行的步骤。一个“订单延期影响分析”技能，可以要求员工依次完成对象定位、需求计算、库存核验、关键路径识别和结果整理，并规定输入不足时如何退出。

对于数量、金额和日期等可以形式化处理的部分，应使用明确公式、规则或计算工具。模型负责理解问题、选择方法和解释结果，计算结果仍需保留可复核依据。

### 3.2 工具连接业务系统，权限限定动作范围

岗位可以配置查询订单、读取库存、创建调拨草稿等工具，但“配置了工具”不应自动等同于“本次任务获准执行所有动作”。

实际动作需要同时满足岗位权限、当前用户的委派范围、对象访问规则和具体审批条件。执行入口应根据这些条件校验请求，并记录动作对象、参数、结果与回执。

查询、拟定方案、提交申请和修改业务状态，应作为不同能力分别配置。这样，企业可以逐步扩大员工的工作范围，而不必一次开放整个系统。

### 3.3 经验进入组织知识前需要验证

团队在一次任务中形成的判断，应先保留为任务记录。只有经过复核，确认适用条件和失效边界，才适合进入可复用的组织经验。

例如，“某供应商这次接受了加急交付”可以作为历史事实保留；把它推广为“该供应商总能加急交付”则缺少依据。下一次任务仍需要核验当前产能和明确承诺。

建议区分四类信息：当前业务事实、任务中的假设、已经验证的经验，以及正式生效的制度规则。它们具有不同的使用条件和更新方式。

## 四、团队如何组织：专业分工与动态组队

### 4.1 用五类职责组织团队

原文提出协调、专家、执行和监督等角色。本篇在这一基础上，将人类业务负责人纳入团队责任设计。

| 职责类别 | 主要工作 | 应交付的内容 |
| --- | --- | --- |
| 团队协调员 | 确认目标、分解任务、管理依赖、汇总未决事项 | 工作计划、综合方案、整体进度 |
| 专业员工 | 在专业领域调查、计算并形成判断 | 有证据的分析和候选方案 |
| 执行员工 | 在有效授权内操作业务系统 | 执行记录、业务对象引用、结果回执 |
| 质量复核员 | 检查事实、规则、计算和交付完整性 | 逐项复核结论与返工要求 |
| 人类业务负责人 | 设定目标、处理关键取舍、组织审批和验收 | 业务决定及责任确认 |

这些职责不要求一一对应独立模型。初期可以由较少的员工承担多项兼容工作，但涉及授权或质量独立性的环节，应保留必要的职责分离。

质量复核也需要独立依据。仅让另一个智能体重复阅读同一份结论，无法保证发现共同遗漏的问题；复核应结合源数据、规则检查、重新计算或人工抽查。

### 4.2 从常设岗位池组建任务团队

企业可以维护稳定的岗位与员工目录，再按任务选择成员。

普通库存核验可能只需要一位分析员。涉及跨仓调拨的订单异常，需要加入交付计划和执行职责。涉及额外成本时，再加入成本分析和有资格的审批人。

动态组队应限制在已登记、已验证的岗位和工具范围内。协调员可以提出缺少哪种能力，却不能自行授予新权限。

任务结束后，临时团队可以释放资源，但任务证据、交接记录和后续责任必须保留。尚未完成的运输跟踪或客户确认，需要有明确承接者。

### 4.3 团队也需要容量和预算

数字员工的工作会消耗模型调用、工具服务、系统配额以及人工复核时间。组队时应为任务设置处理时限、调用预算、并行上限和重新规划次数。

多个团队同时需要采购专家时，应根据业务优先级与截止时间安排。超过处理能力的工作进入队列或转交替补，避免通过无限并行把拥堵转移到业务系统和审批人。

## 五、团队如何协作：从业务目标到任务验收

### 5.1 用工作单建立共同目标

“处理这次延期”缺少可执行边界。工作单需要写明业务对象、目标、约束、截止时间、负责人、交付物和验收条件。

对一次订单异常，可以把工作拆成两个关联阶段：首先形成并执行获批的处置方案，然后持续跟踪实际履行，直到完成业务验收。

阶段之间应有清晰状态。方案提交、审批通过、动作执行、效果观察和业务验收分别表示不同进展，不能用一个“已完成”覆盖整个过程。

### 5.2 让任务依赖决定协作方式

库存核验、采购询期和产能核验可以并行开展。综合方案依赖这些结果，业务审批依赖已经复核的综合方案，正式执行又依赖有效审批。

任务关系确定以后，协调员需要管理的是依赖是否满足、输入是否仍然有效，以及阻塞是否需要升级。

企业可以先为常见场景定义固定流程，在预留节点允许有限调整。例如，只有常规补货无法满足交期时，才启动替代供应商调查。这样既保留适应能力，也使流程能够检查和复现。

### 5.3 交接必须带上可验证的工作产物

专业员工不能只把一句“建议从异地仓调货”交给下一位员工。接收者需要知道这项建议依据什么、适用到何时，以及还有哪些条件未满足。

| 交接内容 | 示例 |
| --- | --- |
| 工作与对象引用 | 当前工作单、客户订单、物料和仓库编号 |
| 交付结论 | 发现 400 件候选可调拨库存 |
| 来源与时点 | 库存查询记录、质量状态、查询时间 |
| 计算与约束 | 订单需求、当前可分配量、调拨前置条件 |
| 未决事项 | 尚未完成资源预留，运输时效待确认 |
| 下一步动作 | 核验运输方案并申请资源预留 |
| 失效条件 | 库存被占用、质量状态变化或预计到货时间变化 |

接收者应检查交接是否完整。关键字段缺失时，任务可以退回补充或转人工处理。直接沿用不完整结论，会让不确定性在团队中逐步累积。

### 5.4 分歧处理需要规则

如果库存分析员认为库存充足，而生产计划员认为物料不可用，团队应先检查是否使用了相同的仓库、批次、质量状态和数据时点。

如果数据一致但方案不同，就根据共同约束比较交期、成本和资源影响。仍然无法取舍时，把分歧、证据和候选方案交给有资格的人类负责人。

多数智能体赞成某个方案，并不能替代事实核验和业务决策。协作规则应明确事实冲突、专业判断差异和管理取舍各自由谁处理。

## 六、团队如何理解企业：与 WBM、Data OS、Agent OS 的关系

专业团队运行在原文提出的企业 AI 操作系统框架之上。为便于落地，可以按下面的方式划分职责。

| 层次 | 关注的问题 | 向团队提供的支持 |
| --- | --- | --- |
| WBM：世界行为模型 | 业务对象是什么，动作受什么约束，会改变哪些状态 | 共享的对象、关系、状态、规则和动作语义 |
| Data OS | 当前事实和知识是什么，依据在哪里 | 受控数据视图、知识检索、来源与时效信息 |
| Agent OS | 工作如何执行、等待、恢复和记录 | 任务编排、运行调度、工具调用、授权校验、运行证据 |
| Agent Workforce | 谁承接什么工作，如何组织和验收 | 岗位、员工、团队、业务派工和绩效管理 |

这里的 WBM 是共享业务语义，不必被实现为独立的第四套运行平台。它的作用之一，是让不同员工对“可用库存”“订单完成”“交付承诺”等概念采用一致定义。

例如，库存分析员读取的是仓库库存记录，计划员关心的是可投入生产的数量，采购员关注的是尚未被覆盖的需求。团队需要通过共享定义明确：冻结库存是否可用、在途物料何时能够计入、质量待检批次是否满足生产条件。

在职责边界上，Workforce 确定岗位分工与业务优先级，Agent OS 将工作实例化为执行任务并推进运行；业务系统保有原始业务记录，Data OS 提供受控访问。员工推理产生的判断应作为分析产物保存，经过授权的业务动作才可以改变源系统状态。

团队工作台可汇总这些执行状态，但应引用执行系统的记录，避免形成两套互相矛盾的进度。业务验收结果也需要与对应工作单、执行任务和产物关联。

## 七、人如何管理团队：授权、监督与责任

### 7.1 按动作和条件设置自治范围

对同一个员工，可以允许其自动查询订单、生成分析报告和创建草稿，同时要求采购提交、库存占用或客户承诺经过审批。

每次审批应绑定具体方案版本、业务对象、动作参数、额度、有效期和关键前提。审批后的方案如果改变了供应商、采购数量或交期，就需要判断原审批是否仍然适用；超出批准范围的变化应重新审批。

这使授权可以落实到业务动作，而不只是给某个智能体一个笼统的“高权限”身份。

### 7.2 人工介入需要完整上下文

交给审批人的材料应说明目标、候选方案、推荐理由、成本、关键风险、依据和待批准动作。负责人应能直接看出自己需要决定什么。

业务负责人、动作审批人和验收人可以由不同人员承担，也可以按照企业制度兼任，但必须明确各自的责任。质量复核通过，不意味着自动获得业务审批；审批通过，也不意味着实际结果已经验收。

### 7.3 接管后需要处理在途动作

人工接管前，应暂停后续自动执行，并核对已经发出的业务请求。如果某次请求超时，团队必须先确认源系统是否已经受理，避免人工和智能体重复创建业务记录。

恢复自动运行时，应重新读取关键业务状态，检查旧计划、旧证据和旧审批是否仍然有效。接管期间发生的人工修改，需要进入后续执行上下文。

工作台因此应能够呈现当前目标、已完成动作、待确认结果、下一步动作、阻塞原因和负责人，使人能够真正介入任务。

## 八、完整案例：一支订单交付保障团队如何工作

### 8.1 先确定目标与事实

假设 2026 年 10 月 22 日上午，一家企业发现关键物料延期。以下为简化教学条件，均采用北京时间，暂不考虑生产损耗。

| 项目 | 示例条件 |
| --- | --- |
| 客户订单 | 产品 P，共 1,000 件 |
| 客户约定 | 2026 年 10 月 25 日 18:00 前全部签收 |
| 物料需求 | 每件产品使用 1 件物料 M，共需要 1,000 件 |
| 本仓可分配量 | 600 件，质量状态符合生产要求 |
| 常规补货 | 缺少的 400 件预计 10 月 26 日到货 |
| 异地仓候选库存 | 400 件，需确认质量、可分配性与运输安排 |
| 成本约束 | 额外支出不超过 8,000 元，仍须业务审批 |

本次团队目标是制定并执行满足约束的交付方案，持续跟踪至签收验收。如果没有可行方案，应在影响扩大前升级给负责人，明确需要调整的业务承诺。

### 8.2 组建团队并并行调查

协调员建立工作单，组织供应链分析员、采购专员、交付计划员、成本分析员、质量复核员和执行员工。采购经理负责相应动作审批，客户交付负责人承担整体业务验收。

供应链分析员确认物料缺口为 400 件，并检查是否还存在其他阻塞。采购专员核验常规补货和候选供应渠道。交付计划员核验异地调拨时效、生产能力和物流窗口。成本分析员根据这些方案计算增量支出。

这些调查可以并行，但都应引用相同的订单范围、需求数量和观察时点。成本分析遇到运输报价变化时，也必须更新对应方案版本。

### 8.3 形成可比较的候选方案

假设调查获得以下候选结果。其中到货与签收时间是附带条件的估计，尚未成为实际结果。

| 方案 | 预计关键进度 | 增量成本 | 主要前提与判断 |
| --- | --- | --- | --- |
| 等待常规补货 | 物料 10 月 26 日到货 | 0 元 | 无法满足原定签收时间 |
| 异地仓加急调拨 | 物料 10 月 23 日 08:00 前到厂，预计 10 月 25 日 16:00 签收 | 6,000 元 | 需成功预留物料、生产时段与运输资源 |
| 替代供应商采购 | 预计 10 月 23 日到货，仍需适配与检验 | 9,500 元 | 超出成本约束，检验完成时间未确认 |

协调员推荐异地仓调拨方案，并展开其关键路径：物料到厂后于 10 月 23 日 12:00 前完成检验，10 月 24 日 12:00 前完成生产，随后完成出库及运输，预计 10 月 25 日 16:00 签收。

该方案距离约定时间只有两小时余量，因此需要设置中途检查点和升级条件。任何关键节点延误，都应触发重新预测和人工介入。

质量复核员检查数量计算、批次质量、时间衔接、资源冲突和成本依据。在核验通过之前，候选方案不能被视为可执行承诺。

### 8.4 审批、执行与阶段确认

采购经理批准确定版本的方案与相应支出。执行员工在写入前再次核验库存、资源预留和审批有效性，然后完成获批的调拨、排产调整及运输申请。

如果原本的 400 件物料已有部分被其他订单占用，执行应停止并回到方案处理环节。旧查询结果和旧审批不能让已经失效的计划继续运行。

执行后，员工根据业务对象编号核对申请内容、源系统状态和回执。对于返回超时的请求，应先查询是否已经生效，再决定重试或人工核对。

这些检查通过后，可以确认“获批动作已执行”这一阶段完成。订单本身继续处于履行跟踪中。

### 8.5 跟踪实际履行并完成业务验收

团队继续跟踪物料到厂、检验、生产、出库、运输和签收。每个节点都应以相应业务记录为依据，更新剩余交付时间与风险。

假设该示例最终在 10 月 25 日 15:40 完成全部 1,000 件签收，实际增量成本为 6,000 元，并且没有未决异常。客户交付负责人核验签收记录、数量和费用后，确认本次工作达到约定目标。

最终验收报告应同时保留原始目标、批准方案、实际执行、偏差与处理过程。这样，企业既能确认结果，也能识别这次成功依赖哪些条件。

### 8.6 异常路径也是团队能力的一部分

| 异常 | 团队处理方式 |
| --- | --- |
| 无法确认异地仓库存 | 标记证据缺项，转交仓库负责人核验，保留候选状态 |
| 推荐方案未获批准 | 记录拒绝原因，更新约束并在预算内重新规划 |
| 调拨申请超时 | 核对源系统受理结果，避免直接重复提交 |
| 检验或生产节点延误 | 重算剩余关键路径，向负责人提交影响与备选措施 |
| 所有方案均无法满足交期 | 升级业务取舍，由有资格的人决定是否协商新的承诺 |
| 人工决定接管 | 暂停后续动作，交接在途请求、证据和未完成事项 |

团队的专业性，也体现在能够明确说明哪里做不到、缺少什么，以及应由谁继续处理。

## 九、团队如何成长：入职、评估与能力更新

### 9.1 上岗前验证完整工作能力

员工入职时需要绑定岗位版本、知识范围、技能、工具权限、业务负责人和评价标准。上岗验证应覆盖实际工作流程中的关键判断与动作。

可以先用历史任务回放检查分析与方案质量，再在隔离环境中验证工具使用、审批等待和异常恢复，最后进入小范围业务试运行。历史回放应使用当时可获得的信息，避免把后来才知道的结果放入输入。

至少应包含输入缺失、数据过期、权限不足、方案被拒绝和执行结果不确定等情况。只验证顺利完成的案例，无法说明员工能否持续承担岗位工作。

### 9.2 同时评价个人、团队与业务结果

个人评价关注岗位交付是否准确、完整、及时。团队评价关注整体工作是否达到目标，以及协作带来的成本和等待。业务评价则关注实际交付、成本和客户影响。

指标需要固定口径，避免用容易完成的任务掩盖复杂任务的问题。

| 指标 | 建议口径 | 管理用途 |
| --- | --- | --- |
| 业务目标达成率 | 达到约定目标的工作数 / 同期应验收工作数，未结项单列 | 评价业务结果与积压 |
| 按时验收率 | 截止时间前通过验收的工作数 / 同期到期工作数 | 评价交付时效 |
| 首次验收通过率 | 首次提交即通过的工作数 / 已首次提交验收工作数 | 识别质量与交接问题 |
| 异常接管率 | 因执行异常需人工接管的工作数 / 已启动工作数 | 识别运行稳定性 |
| 单次合格交付成本 | 统计期任务总成本 / 同期通过验收工作数 | 评价综合经济性 |

正常业务审批应与异常接管分别统计。人工介入增加可能来自权限设计变化，不能直接推断系统能力下降。

评价经济性时，应纳入模型、工具、人工复核、返工和运营成本，并与相近复杂度的业务基线比较。单个案例按时完成，不能证明系统已经普遍提高交付能力。

### 9.3 经验更新要经过发布流程

复盘应定位具体原因：知识是否过期，规则是否缺失，交接是否遗漏，工具是否失败，还是岗位本身承担了不合适的工作。

对应改进应形成候选变更，经过验证后发布，并保留回退路径。在途任务原则上固定所用岗位与技能版本；如果因重大错误必须更新，则显式暂停、迁移并重新验证关键结果。

员工退出岗位时，还需要回收权限、处理在途工作并移交后续观察责任。停用一个智能体，不代表相关业务任务自动结束。

## 十、企业如何落地：从首支团队到多团队协同

### 10.1 选择一个能够验收的业务流程

首个场景适合具备明确对象、稳定输入、可访问数据、已知审批路径和可验证结果，例如订单异常分析与获批处置。

启动前先记录当前处理周期、人工投入、返工原因与结果质量，并确定第一阶段到底验收什么。如果首期范围是完成分析和申请提交，就应以这一范围验收，实际履行结果另设跟踪任务。

### 10.2 用最小团队验证完整流程

初期可以设置协调、专业分析、执行和复核职责，由明确的业务负责人负责审批与验收。优先打通正常处理、缺项补充、审批拒绝、执行超时和人工接管这些路径。

与之配套的最小管理界面，应支持岗位配置、工作进度、待人工事项、交付证据和验收记录。企业需要看得见工作如何完成，才能决定是否扩大范围。

### 10.3 按验证结果扩大授权

| 阶段 | 工作范围 | 进入下一阶段前需要的依据 |
| --- | --- | --- |
| 辅助分析 | 读取数据、解释影响、形成建议 | 结果可复核，缺项与不确定性能够准确暴露 |
| 审批后执行 | 提交获批申请并核验业务状态 | 授权有效，重复执行和不确定结果得到处理 |
| 限定范围持续运行 | 自动处理已验证的常见任务并跟踪验收 | 质量、成本、接管和业务效果满足事先约定的门槛 |
| 多团队协同 | 共享专业员工，处理跨部门工作 | 容量、优先级、跨团队交接与责任归属可管理 |

这些阶段不必按固定时间推进。每次扩展前，应明确任务范围、评估样本和退出条件，用实际验证结果决定是否继续。

### 10.4 扩展时保持结果责任清晰

多团队协同时，一支团队的交付可能成为另一支团队的输入。采购团队完成申请创建后，交付团队还需要确认到货与生产影响；财务团队完成费用核验后，业务负责人仍需判断整体目标是否达成。

因此，跨团队协作应复用同样的工作单、交接和验收原则，并指定整体目标负责人。共享专家和共享资源也需要统一协调，避免每支团队都认为自己拥有最高优先级。

企业可以从一份岗位说明书、一张工作单和一条可验收流程开始。随着证据积累，再增加岗位、扩大授权和连接更多团队。每次扩展，都应能够说明新增能力承担了哪项工作，以及如何确认它完成了。
