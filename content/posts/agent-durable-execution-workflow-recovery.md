采购经理批准了一份方案：从供应商 A 采购 100 台设备。Agent 随即调用 ERP 创建订单。几秒后，执行进程退出了，日志的最后一行是“正在创建订单”。

新进程接管任务。它应该再调用一次 ERP，还是跳过这一步？

如果第一次请求没有到达 ERP，跳过会漏单；如果订单已经创建，再调用可能重复采购。即使重新问模型，模型也无法从本地日志中推断 ERP 是否已经提交了订单。

这就是 Agent 持久化执行要面对的问题：**当执行任务的进程消失以后，系统还能依据哪些事实，决定下一步怎么做？**

本文用同一个采购案例，逐步讨论恢复状态、固定决策、核对外部操作和补偿。Beldi、ExoFlow、RIFL 与 Sagas 提供分布式系统的机制基础；CIDR 2026 的工作流研究和 AgentRewind 补充工作流正确性与 Agent 环境恢复的视角。案例中的三层状态划分和接口设计是本文的工程推导，实验部分是可复现的设计方案，不是已执行的测量报告。

## 一、同一条流程，三个不同的故障点

先把采购任务写成一条简单的执行路径：

```text
查询库存 → 生成采购方案 → 等待人工批准 → 创建订单 → 通知申请人
```

这条路径并不要求所有步骤都由模型决定。模型可以负责比较供应商、解释采购理由；批准、创建订单和记录回执则应遵守明确的执行规则。现在，让进程在三个位置退出。

**故障 A：方案已经生成，尚未保存。** 内存里有供应商、数量和交货日期，但这些结果随进程一起丢失。如果方案还没有对外产生影响，可以重新生成，代价是额外的推理成本与可能变化的结果。如果方案已经提交审批，重新生成就可能让后续执行脱离审批人看到的内容。

**故障 B：ERP 已经创建订单，本地尚未保存回执。** 这时外部世界发生了变化，本地却没有确认记录。恢复不能只看当前节点；它需要一种方法确定原操作的结果。RIFL 讨论的正是这一类问题：请求可能已经完成，但客户端因为故障没有得到结果，随后不得不重试。[3](#reference-3)

**故障 C：任务正在等待批准，执行进程退出。** 此时没有必要重新生成方案，也没有订单需要核对。系统需要保存等待对象和唤醒条件，使后来的批准事件仍能找到这个任务，并由新的执行者继续处理。[5](#reference-5)

![采购 Agent 的三个故障点：决策丢失、等待接管与外部结果未知](/blog-assets/agent-durable-execution/failure-boundaries.svg)

三个故障分别暴露了决策保存、执行接管和外部结果确认的问题。只增加一条“失败后重试”的规则，无法同时回答它们。我们先确定需要保存什么，再讨论如何恢复。

## 二、恢复的对象：决策、进度与外部事实

“保存 Agent 状态”很容易被理解成把对话消息写进数据库。但一次能够继续执行的采购任务，至少需要区分三类信息。这里的划分用于分析职责，不要求实现时一定建立三张表。

| 状态层次 | 采购任务中的例子 | 恢复时解决的问题 |
| --- | --- | --- |
| 决策状态 | 库存快照、供应商报价、选定方案、方案版本 | 当时依据什么，决定做什么？ |
| 执行状态 | 已完成步骤、等待中的批准、下一项动作、定时器 | 工作推进到了哪里？ |
| 外部事实及其证据 | ERP 订单号、按动作键查询的结果、取消回执 | 哪些操作确实发生了？ |

对话记录可能保存了“我准备下单”的表述，却没有动作身份和外部回执。工作流记录可能说明“创建订单步骤尚未完成”，但这也不能证明 ERP 没有创建订单。外部事实最终由 ERP 决定，本地保存的是获取这些事实的证据和关联信息。

这三个层次还需要相互对齐。例如批准记录应指向确定的方案版本，创建订单动作应引用同一版本；否则单独看每条记录都合法，连起来却可能变成“批准 A、执行 B”。这是本文采购案例采用的业务约束。

AgentRewind 从另一个角度说明了状态对齐的重要性。这篇 2026 年的预印本同时记录 Agent 上下文与受控环境的检查点，以便在执行出错后返回较早状态并探索新的路径。它明确将环境恢复范围限定为工作区文件树；网络请求、外部服务调用等工作区之外的效果无法被撤销。[6](#reference-6)

因此，恢复到“下单之前”的上下文，不会让已经创建的 ERP 订单自动消失。检查点能覆盖哪些状态，直接决定了它能够提供什么恢复能力。接下来先讨论运行时能够控制的那一部分。

## 三、进程消失后，执行是怎样接续起来的

持久化执行需要把执行过程中的必要信息写入能够跨越进程故障的存储。执行者可以替换，任务身份和已经确认的结果应当保留。在满足存储可用、能够重新调度等条件时，新的执行者根据这些记录接续任务。[1](#reference-1)[5](#reference-5)

### 3.1 从“记住当前节点”到“保存恢复依据”

假设任务已经完成库存查询和方案生成，正在等待批准。一组简化的记录可以是：

```text
task = purchase-2048
inventory/read-v1  → 已完成，结果引用 inventory-snapshot-17
plan/create-v1     → 已完成，结果引用 plan-v1
approval/plan-v1   → 等待事件，批准对象为 plan-v1
```

有了这些记录，恢复者能够知道方案在哪里、批准针对什么、当前应该等待哪类事件。它不必保持原来的线程和调用栈，也不必在等待期间占用同一个 Worker。

真正的实现还要解决记录的持久性、步骤身份、并发接管和事件投递。Beldi 将函数执行和步骤关联起来，对通过其 API 进行的操作记录结果，并在重新执行时识别已经完成的操作；它还通过专门的数据结构和协议处理状态更新与日志的一致性。[1](#reference-1)

这里最容易漏掉的条件是：**业务写入与“这次写入已经完成”的记录，不能留下一个无人能够解释的提交间隙。** 如果二者位于同一可控事务中，可以一起提交；如果操作跨越到了 ERP，就需要第五节讨论的外部协议。

### 3.2 重放为什么不等于再次调用工具

可以把一种恢复方式理解为：重新运行控制逻辑，遇到已有可靠记录的步骤时，读取原结果；遇到未完成的步骤时，再按照该步骤的执行规则处理。

下面是概念伪代码，只说明已保存结果如何被复用。它省略了并发控制、租约、原子提交和版本兼容，因此不能直接作为生产运行时。

```python
def recorded_value(step_id, compute):
    saved = history.load_completed(step_id)
    if saved is not None:
        return saved.value

    value = compute()
    history.persist_completed(step_id, value)  # 持久化成功后才返回
    return value

# compute 适用于可重新计算的步骤。
# 有外部写入效果的步骤还需要动作去重和结果核对协议。
```

如果库存查询的结果已被保存，恢复控制逻辑时返回原快照，可以维持原先分支判断的依据。Beldi 对读取结果进行记录，原因就是这些结果可能影响后续外部操作；读取后、记录前发生故障时，只要该结果尚未导致外部可见效果，重新读取可以是安全的。[1](#reference-1)

这里恢复的是足以解释后续步骤的执行过程。调用某个工具的代码再次被控制流走到，不意味着它的外部效果就应该再次发生。

### 3.3 检查点和重放怎样配合

检查点保存某个时刻的恢复状态；日志可以记录检查点之间的输入、决策或步骤结果。恢复时可以先加载检查点，再利用后续记录重建进度。不同系统在记录粒度、重算范围和存储成本上有不同选择。[2](#reference-2)

| 方法 | 恢复时使用的依据 | 需要承担的成本或条件 |
| --- | --- | --- |
| 保存步骤结果 | 已完成步骤的输出及状态 | 持续写入记录，并保持记录一致 |
| 保存检查点 | 某个边界上的完整恢复状态 | 检查点之后的工作可能需要重做 |
| 依据依赖重新计算 | 上游输入、代码和依赖关系 | 重算结果必须满足下游的一致性要求 |

ExoFlow 将工作流执行与恢复管理分离，允许利用任务是否可确定性重算、外部效果是否可回退等语义，选择不同的恢复方式。其启发是：无需把所有中间数据都用同样的方式持久化，但必须知道省掉某次记录以后，恢复还能依靠什么。[2](#reference-2)

对于本文的采购任务，格式化展示文本可以重新计算；决定供应商的方案在提交审批和执行订单之前，需要先被固定下来。这就引出了模型调用的特殊之处。

## 四、模型会给出不同答案，怎样恢复同一个决策

设想第一次模型选择供应商 A，恢复后再次调用模型却选择了 B。只要两次结果都还没有被使用，这可能只是重新计算。如果 A 的方案已经得到批准，甚至已经创建订单，那么把 B 当成原结果继续执行，就会破坏前后的一致性。

这属于非确定性结果与外部效果的关系问题。ExoFlow 讨论了上游结果尚未持久化、下游已经看到结果时的恢复风险：上游重算得到不同结果，可能导致下游与外部系统之间出现不一致。[2](#reference-2)

据此，采购案例采用以下执行边界：

```text
生成候选方案
    ↓
保存方案内容、版本与必要的输入证据
    ↓
提交该版本审批，持久化批准结果
    ↓
保存引用该方案版本的订单动作
    ↓
执行外部请求
```

关键是前一步成功持久化之后，才允许下一步使用相应结果产生影响。这里固定的是可执行方案及其依据，不要求保存模型内部不可见的推理过程。

恢复时可以据此作出更具体的判断：

| 故障时的状态 | 允许的恢复行为 | 代价或约束 |
| --- | --- | --- |
| 模型结果尚未保存，也未向后传播 | 重新调用模型生成候选方案 | 可能重复计费，结果可能变化 |
| 方案已经保存，尚未提交审批 | 读取原方案并继续 | 不在恢复过程中悄悄替换内容 |
| 方案已经批准，订单动作尚未发送 | 检查执行条件，处理该版本动作 | 方案改变时需要新的批准关系 |
| 订单请求已经发出，结果未知 | 核对原动作 | 不能先换方案，再把原订单当作未发生 |

这套设计并没有保证模型 API 只被调用一次。结果到达与本地持久化之间仍然可能发生故障；在模型没有自行执行外部工具的前提下，重复调用的主要后果是额外计算和候选结果变化。如果模型调用本身包含不可控的外部操作，就必须把那些操作纳入动作恢复协议。

还要区分恢复与重新规划。恢复沿用已确认的事实接续执行；重新规划是业务上接受了一次新的决策。比如批准后供应商被停用，系统可以暂停原方案并产生新方案，但必须先解释旧方案有哪些动作已发生、哪些仍未知。模型选择了更好的方案，不会清除旧方案留下的外部效果。

## 五、最难的窗口：ERP 成功了，本地却不知道

前面的机制可以固定方案、保存批准并重建执行进度。现在回到开头的故障：ERP 已经创建订单，Worker 在保存回执之前退出。

![外部提交与本地回执之间的故障窗口，以及使用同一动作身份核对结果的恢复路径](/blog-assets/agent-durable-execution/commit-gap.svg)

这两次提交分别发生在 ERP 和工作流存储中。除非双方参与同一个原子协议，否则在本地多写一次检查点，也无法把它们变成一次原子提交。CIDR 2026 的工作流论文也专门讨论了外部服务边界及其对恢复保证的限制。[5](#reference-5)

### 5.1 为同一项业务动作保留同一个身份

RIFL 的做法是让请求具有可识别的身份，并保存完成记录；当同一请求再次到达时，系统识别重复并返回已有结果。操作效果与完成记录之间需要满足原子性要求，才能避免“操作已发生，去重记录却不存在”的问题。[3](#reference-3)

应用到采购案例，可以设计以下契约：

```text
任务：purchase-2048
方案：plan-v1
逻辑动作：purchase-2048/plan-v1/create-order
网络尝试：attempt-1、attempt-2、attempt-3
```

多次网络尝试使用同一个逻辑动作键。这个键应在发送前确定并持久化，不能每次重试重新生成。新尝试表示“再确认或推进同一项动作”，而不是“授权创建另一张订单”。

ERP 需要把动作键、请求内容摘要和订单结果关联起来：同键同内容返回已有订单；同键不同内容拒绝执行。订单写入与去重记录要么在同一事务中提交，要么由接收方提供等价的原子保证。只在 Agent 本地写“已经发送”，无法让 ERP 自动具备这些能力。

### 5.2 超时后先承认结果未知

超时提供的信息是“调用方在期限内没有确认结果”。它没有证明请求失败，也没有证明订单不存在。恢复流程因此需要保留结果未知的状态。[3](#reference-3)

对于支持按动作键查询的 ERP，可以采用以下规则：

1. 查到已提交订单，保存订单号和查询证据，完成本地动作。
2. 查到请求仍在处理，继续等待并安排后续查询。
3. 暂时查不到结果，检查查询的一致性与同键去重契约；若接收方保证并发和重试去重，可以用原键重试。
4. 缺少可靠查询和去重能力，保留未知状态，进入人工或业务核对流程。

第三种情况尤其容易处理错。最终一致的查询暂时没有返回订单，并不等于 ERP 从未接受原请求。恢复依据应来自明确的服务契约，不能来自“等了几秒，应该没创建”的猜测。

去重记录也有保存期限。若任务允许数天后恢复，ERP 却只保留数小时的动作键，原键在过期后可能被当成新请求。此时需要可长期查询的业务关联标识或人工核对，不能继续沿用过期前的保证。

### 5.3 exactly-once 要说清楚边界

在满足上述契约时，同一个逻辑动作可以经过多次网络尝试，同时只产生一个订单结果。这不意味着请求只发送一次，也不意味着任何 ERP 都天然支持这一语义。RIFL 的保证来自接收方对请求身份、完成记录及其生命周期的共同管理。[3](#reference-3)

另一个边界在业务层：两个 Agent 如果为同一采购需求生成了不同动作键，请求去重仍可能允许两个订单。采购案例还需要定义需求与有效订单之间的业务约束，例如由唯一约束、需求占用或审批规则防止重复履行。传输层去重不能代替业务上的重复判断。

并发恢复同样需要配合。运行时可以通过租约或条件更新协调接管，但旧 Worker 可能在失去执行权后仍有请求在途。外部动作的同键去重仍然有价值；仅在本地选出一个新 Worker，并不能撤回已经发送的请求。

## 六、恢复以后：继续、重新规划，还是补偿

确认事实只是第一步。一个任务等待了两天以后，原方案还是否允许执行，是另一项业务判断。这里需要把历史事实与当前条件分别处理。

### 6.1 等待状态也需要可恢复

在本文设计中，等待批准至少包含方案版本、批准事件的关联标识、截止时间和处理状态。批准事件即使到达时没有活跃 Worker，也应被持久接收并最终交给恢复者；事件重复投递不应重复触发订单动作。

如果恢复者发现批准与超时事件都已到达，应依据预先约定的截止时间和事件处理规则裁决。把“哪个 Worker 先醒来”当作业务规则，会让结果依赖调度时序。持久化工作流对消息和长时间等待的处理，为这类设计提供了基础。[5](#reference-5)

已经批准也不代表永远可以执行。本文采购案例规定，发送订单前重新检查当前权限、供应商状态和批准有效期。它是恢复过程中的新校验，应形成新的记录；旧的库存和审批证据仍用来解释原来的决策。

### 6.2 已发生的操作，需要业务上的补救

假设订单已创建，但运输资源无法安排。任务可能需要取消订单，或者改期交货。Sagas 将长事务拆分为一系列可提交的子事务，并为已提交步骤提供补偿事务，使长流程能够在后续失败时处理已经产生的效果。[4](#reference-4)

采购案例中的补偿需要结合订单状态定义：未发送给供应商时可能允许取消，已进入履约后可能需要协商，已经收货时则可能进入退货流程。补偿的目标由业务决定，不能假设每个动作都有一个能够恢复原状的逆操作。

补偿也可能超时，甚至在执行中再次崩溃。因此取消订单需要自己的动作身份、完成证据和核对路径。CIDR 2026 的工作流研究强调，补偿逻辑要在崩溃后可靠推进，同样依赖持久化执行。[5](#reference-5)

“取消任务”也需要遵守这一点。如果创建订单请求已经在途，停止后续调度不会自动撤回它。系统要继续跟踪原动作，确认结果后再决定是否发起取消订单动作。

### 6.3 回到检查点，适用于什么环境

对于主要修改本地文件的编程 Agent，恢复上下文与工作区文件后重新尝试，是另一条有价值的路径。AgentRewind 会恢复二者对应的检查点，并保留先前尝试的摘要来帮助下一轮决策。[6](#reference-6)

但它的工作区恢复不能撤销已经发送的邮件、创建的远程订单或其他外部服务效果。论文讨论的轨迹纠错与本文关注的进程故障恢复有交集，适用范围并不完全相同。把这种方法用于采购 Agent 时，外部订单仍需要单独核对和补偿。

| 恢复时确认的事实 | 本文案例采用的后续路径 |
| --- | --- |
| 原方案仍有效，外部操作已确认成功 | 复用成功证据，继续后续步骤 |
| 原方案尚未产生外部效果，但条件已变化 | 暂停旧方案，建立新方案及批准关系 |
| 已发生的操作违背当前业务目标 | 根据业务状态发起补偿 |
| 外部操作结果仍然未知 | 继续核对，必要时转人工处理 |

## 七、设计一个能暴露问题的故障注入实验

恢复设计需要通过可观测的结果来验证。只看 Worker 是否自动重启，不足以确认订单没有重复，也不能说明原方案被正确沿用。

下面是一组建议实验，尚未在本文仓库中实现或运行。表格描述的是待验证的行为，不是实测结论。

### 7.1 准备两个独立的持久化边界

使用一个执行采购流程的 Worker 和一个模拟 ERP。工作流记录与订单记录使用独立存储，使 ERP 提交后、Worker 保存回执前的间隙真实存在。Worker 退出以后，ERP 订单与工作流历史都应保留。

模拟 ERP 提供按动作键创建、按动作键查询两个接口，并能切换去重能力及查询可见性。模型可以先用可控桩替代：第一次返回供应商 A，第二次返回 B，用来确定性地暴露决策漂移；它只能验证恢复逻辑，不能代替真实模型成本或成功率实验。

准备三个实现，使用相同的故障点比较：

| 实现 | 保存内容 | 重点观察的问题 |
| --- | --- | --- |
| 整体重试 | 初始输入 | 是否重新生成方案，是否重复下单 |
| 步骤检查点 | 已完成步骤及结果 | 外部成功、本地未保存时怎样恢复 |
| 决策与动作恢复 | 决策结果、动作身份、回执及核对状态 | 是否正确复用决策并确认原动作 |

三个名称代表本实验的实现差异，不能据此断言所有检查点系统都缺少动作去重；真实系统通常会组合这些机制。

### 7.2 在提交边界终止进程

为避免随机故障没有命中关键窗口，可以在程序中设置可控暂停点。测试控制器收到“ERP 已提交”的信号后，终止 Worker，再启动新的恢复实例。ERP 故意延迟或丢弃原响应，使 Worker 无法通过正常返回获得结果。

| 故障点或注入条件 | 要检查的行为 |
| --- | --- |
| 模型结果已返回，但尚未持久化 | 可重新调用；未保存结果没有进入审批或订单动作 |
| 方案已持久化，随后 Worker 退出 | 恢复后使用原方案及版本 |
| ERP 已提交，本地尚未保存回执 | 使用原动作键查回订单或安全重试，订单数量保持为一 |
| ERP 查询暂时看不到已提交结果 | 不把暂时无结果当成明确失败，不生成新键绕过去重 |
| 两个恢复者同时处理同一动作 | 并发控制与接收方去重共同维持单一业务结果 |
| 取消订单已经提交，补偿回执丢失 | 能核对补偿结果，避免无限重复补偿 |

同时记录模型调用次数、ERP 请求次数、实际订单数、恢复耗时，以及未知状态是否得到处理。请求次数大于一并不必然表示失败；一个逻辑动作出现多个有效订单，才直接违背了本实验的目标。

验收可以写成三条可检查的约束：每个获批订单动作最多关联一个有效订单；每个成功状态都能追溯到外部结果证据；每个未知状态都安排了后续核对或有明确的人工责任人。若外部服务持续不可用，实验应如实呈现任务仍在等待，不能把“没有重复执行”误报成“已经完成”。

## 八、按恢复边界选择实现，而不是先选择框架

并非所有 Agent 都需要完整的工作流运行时。选择前，先确认任务持续多久、状态由谁控制、哪些步骤有外部效果，以及这些效果能否查询、去重或补偿。下面是基于前文机制的选择建议。[1](#reference-1)[2](#reference-2)[5](#reference-5)[6](#reference-6)

| 任务形态 | 可以优先采用的机制 | 还需要确认的边界 |
| --- | --- | --- |
| 单数据库内的短流程 | 本地事务、任务记录、必要的重试 | 提交结果如何返回及去重 |
| 主要生成可重算的中间结果 | 步骤结果保存、检查点、依赖重算 | 结果是否确定，是否已经被下游使用 |
| 跨天等待、动态分支、多次唤醒 | 持久化工作流、事件关联、定时器 | 事件重复、迟到以及旧版本实例 |
| 调用 ERP 等外部写接口 | 稳定动作身份、接收方去重、结果核对 | 去重期限、查询一致性、业务唯一性 |
| 主要修改受控文件环境 | 上下文与工作区联合检查点 | 网络和外部服务效果仍需另行处理 |

长期运行还带来代码演进问题。假设旧任务正在等待批准，新代码却在创建订单前插入了新的分支，恢复者就必须知道怎样解释旧记录。工程上可以选择保留兼容的执行版本、显式版本分支或状态迁移，并用旧实例验证升级后的行为。方案、工具参数和记录格式的版本，也需要保持可解释性。

回到开头的采购任务，一个可信的恢复结果可以表述得很具体：系统读到了已批准的 `plan-v1`，找到了它对应的订单动作，通过原动作键查到 ERP 已提交的订单，将证据保存后，继续处理通知。若查询仍不能确认结果，就停留在核对流程，直到获得足够依据。

持久化执行的价值由这些可解释的动作体现出来：进程能够被替换，已经确认的事实被保留，未确认的结果得到追踪，新的决策明确承接旧操作留下的影响。
