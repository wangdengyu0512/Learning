采购 Agent 已经生成方案，采购经理也点了批准。系统向 ERP 发出创建订单请求，随后 Worker 重启了。

恢复后的系统面对三个问题：请求有没有发出，订单有没有创建，下一步能不能再次调用？只保存一句“正在创建订单”，无法回答其中任何一个。

**持久化执行要保存的是足以继续推进任务的事实，以及跨越故障之后仍然成立的业务约束。** 它把一次进程内运行，变成可以跨进程、跨时间恢复的业务过程。

本文延续[重复采购单事故推演](../agentos-incident-duplicate-purchase-order/)。Temporal 的机制用于解释一种实现路线；业务幂等与核对责任仍需要具体系统承担。

## 一、先区分三种“继续执行”

一种常见实现，是捕获异常后重新运行整个函数。另一种实现，是每做完一个步骤就保存当前节点，重启后从这个节点继续。它们都能处理部分故障，但保证不同。

| 方式 | 保存什么 | 能解决什么 | 仍然需要处理什么 |
| --- | --- | --- | --- |
| 整体重试 | 初始输入 | 短暂故障后重新尝试 | 前面已经发生的副作用 |
| 节点检查点 | 当前状态和节点结果 | 减少重复计算 | 外部提交与本地保存之间的间隙 |
| 事件历史与重放 | 决策所需事件、命令与结果 | 重建控制流和等待状态 | 外部动作的重复执行与结果未知 |

Temporal 将工作流执行建立在持久化历史上，恢复时通过重放检查代码产生的命令与历史是否匹配。这里的重放有明确的确定性约束，不能理解为把所有外部请求原样再发一遍。[1][2]

选择哪种机制取决于任务复杂度。一个数据库事务内的短流程，可能只需要状态表和队列；跨数天审批、多次外部写入的任务，则需要更完整的恢复模型。

## 二、把任务、动作和尝试分开建模

采购任务的目标是满足一条需求。它可能需要查库存、选择供应商、预留预算和创建订单。创建订单又可能经历多次网络尝试。

| 标识 | 示例 | 何时变化 |
| --- | --- | --- |
| task_id | task-2048 | 新业务任务建立时 |
| action_id | act-po-01 | 新逻辑动作建立时 |
| action_revision | 3 | 已批准的业务意图变化时 |
| attempt_id | try-07 | 每次技术尝试时 |
| external_key | tenant-a:act-po-01:r3 | 动作语义版本变化时 |

同一动作版本的网络重试必须保留相同外部幂等键。若每次尝试都换键，外部系统看到的就是多次独立创建。

动作身份也不应该仅由请求参数散列生成。两次独立、合法的采购可能参数完全相同；相同参数并不意味着同一个业务意图。更稳妥的做法，是先分配并持久化动作身份，再用参数摘要验证这个身份对应的内容没有变。

下面是一份概念性记录：

```json
{
  "task_id": "task-2048",
  "action_id": "act-po-01",
  "revision": 3,
  "tenant_id": "tenant-a",
  "tool": "erp.purchase_order.create",
  "payload_digest": "sha256:...",
  "approval_id": "approval-19",
  "external_key": "tenant-a:act-po-01:r3",
  "state": "READY",
  "state_version": 8
}
```

这里的摘要应来自服务端规范化后的完整业务参数，金额单位、币种、默认值和行项目顺序都需要明确。摘要本身不构成授权，授权记录还要绑定对象、动作、批准人和有效期。

## 三、结果未知是一种需要处理的状态

如果接口返回“权限不足，未执行”，通常可以确认本次没有创建订单。如果连接在提交过程中断开，调用方却不能据此判断 ERP 有没有提交。

因此，执行状态至少应该表达下列区别。

| 状态 | 已知事实 | 下一步 |
| --- | --- | --- |
| READY | 意图已保存，允许派发 | 再校验执行条件后派发 |
| IN_FLIGHT | 一次尝试正在执行 | 等待回执或进入核对 |
| SUCCEEDED | 外部结果已被确认 | 保存证据，推进后续步骤 |
| FAILED_CONFIRMED | 已确认没有完成目标动作 | 按错误类别决定修复或重试 |
| UNKNOWN | 无法确认外部是否提交 | 按稳定动作键查询和核对 |
| COMPENSATING | 已确认副作用，需要业务补偿 | 执行独立的补偿动作 |

状态设计需要配合转换约束。例如，迟到的超时事件不能把 SUCCEEDED 改回 UNKNOWN；两个 Worker 更新同一动作时，需要版本条件或其他并发控制。

一次查询返回“未找到”也未必足以确认失败：请求可能仍在处理中，查询可能读到副本，外部索引可能尚未更新。适配器应声明查询的可见性和终态语义。没有这些保证时，恢复逻辑只能继续核对，不能擅自换一个键再创建。

## 四、把控制流和外部活动放在不同边界

一个可恢复的采购流程，可以分成两种工作。

控制流负责决定先做什么、等待什么、收到哪类事件后如何转移。外部活动负责查询数据库、调用模型、发送工具请求和读取 ERP 回执。

```text
接收需求
  → 获取证据并记录结果
  → 生成方案并记录结果
  → 等待绑定方案版本的审批事件
  → 建立并持久化业务动作
  → 执行或核对该动作
  → 根据外部事实验收
```

在使用确定性重放的引擎时，模型调用、任意网络 I/O 和不受控制的随机数不应直接出现在工作流决策代码中。它们的结果应经引擎支持的活动或其他持久化机制进入历史。[2]

已经写入历史的模型结果可以被恢复过程读取；如果模型请求成功后、结果写入历史前进程崩溃，活动仍可能再次调用模型。此时既可能重复计费，也可能生成不同方案。因此，应在发起不可逆业务动作前固定方案版本与审批绑定关系。

事件历史也不适合无限保存整个合同、完整模型上下文和密钥。可以记录不可变对象引用、内容摘要、解析版本和必要决策结果，并让对象存储的保留期限覆盖任务恢复窗口。

## 五、持久化派发不能替代外部幂等

考虑一次创建订单的提交顺序：

```text
1. 本地保存动作意图
2. 调用 ERP
3. ERP 提交订单
4. 本地保存成功回执
```

第 3 步和第 4 步之间存在跨系统间隙。无论本地状态表设计得多完整，都不能单独消除它。

本地事务可以把动作意图和待派发记录一同提交，再由派发器读取待派发记录。这能避免“保存了任务却忘记投递”，但派发器确认完成前也可能崩溃，所以消息仍可能重复。

完整设计需要两端配合：本地持久化动作身份和派发意图，外部系统按同一身份执行去重并提供结果查询。Temporal 的 Activity 文档同样强调活动应当设计为幂等；工作流可恢复并不自动使外部写入只发生一次。[3]

为 ERP 适配器定义契约时，至少问清五件事：

| 契约 | 需要的答案 |
| --- | --- |
| 去重范围 | 租户与动作键是否共同参与，是否覆盖并发提交 |
| 参数冲突 | 同键不同参数会拒绝，还是产生不明确行为 |
| 保留期限 | 幂等记录多久过期，是否覆盖最长恢复窗口 |
| 查询语义 | 能否查到处理中、成功和确定失败，是否有读延迟 |
| 业务约束 | 同一需求允许几张订单，撤销和拆单规则是什么 |

如果 ERP 没有同键去重，可以研究外部唯一业务编号和可靠核对接口。若这些能力也不存在，就应承认自动恢复的边界，把未知动作交给人工确认。

## 六、审批等待也是运行状态

采购经理可能第二天才处理审批。Worker 没有必要保持一个进程阻塞等待；等待条件和到期时间应由持久化运行时管理。

审批事件至少携带任务、动作版本、参数摘要、批准人和审批标识。重复事件需要去重，过期版本需要拒绝，已取消任务不能被迟到的批准重新激活。

“昨天批准过”还不能直接推出“今天允许执行”。执行前要重新核对当前权限、预算、对象状态和审批有效期。例如供应商昨天合格、今天被暂停，新执行必须服从当前规则。

取消也要区分请求与结果。取消一个任务，不代表已经到达 ERP 的请求被撤回。若订单事实上已经生成，系统需要进入撤销或补偿流程，并等待补偿结果被确认。

## 七、补偿是新的业务动作

创建订单后预算预留失败，是否应该取消订单？这取决于订单有没有发给供应商、是否已经收货，以及业务允许什么。

数据库回滚能够撤销同一事务内尚未提交的修改；跨系统补偿是在已经发生的事实之上执行另一项业务操作。取消订单也可能失败、超时或需要审批，所以它应拥有自己的动作身份、幂等键和核对路径。

补偿不一定按正向步骤简单倒序。预算释放和订单取消之间可能有业务依赖，已收货订单也可能需要退货而不是取消。设计时应列出每种状态允许的补救动作，以及无法自动补救时的负责人。

## 八、工作流升级要考虑运行中的任务

假设旧流程是“审批 → 创建订单”，新流程增加了“审批 → 风险检查 → 创建订单”。一个运行到一半的旧任务恢复时，新代码可能产生与历史不一致的命令。

可以按引擎能力选择版本路由、补丁分支、旧版本排空，或显式状态迁移。关键是保留正在运行实例所需的解释方式，并测试旧历史在新部署下是否仍可处理。[2]

版本管理还包括工具 Schema、模型配置、审批策略和证据解析器。若数据库迁移删除了旧流程依赖的字段，单纯回滚应用镜像也无法恢复兼容性。

长期任务应安排历史归档、历史长度治理与审计保留。引擎提供的历史切分机制需要保持业务任务关联，不能让新一段执行丢失原审批和外部动作证据。

## 九、最小实践：在提交间隙终止 Worker

实验使用一个本地 ERP 模拟器，提供“按动作键创建”和“按动作键查询”两个接口，且把订单持久化到独立存储。以下是建议实验，并非已执行的报告。

1. 固定一份采购方案，保存动作版本和批准记录。
2. 模拟器接到创建请求后提交订单，故意不返回响应。
3. 终止 Worker，重新启动一个恢复实例。
4. 恢复实例保持原动作键，查询并关联已有订单。
5. 同时检查本地动作记录和模拟 ERP 的订单数量。

然后加入以下变化，观察设计边界。

| 注入条件 | 应观察到的行为 | 验证对象 |
| --- | --- | --- |
| 两个恢复实例并发接管 | 本地竞争受控，外部同键去重 | 订单数与执行权版本 |
| 成功回执迟到 | 已确认成功不能被后续超时覆盖 | 状态转换记录 |
| 查询暂时无结果 | 保持未知或按契约同键恢复 | 动作键是否变化 |
| 审批后数量发生变化 | 停止旧版本执行，进入新审批 | 摘要与批准记录 |
| 幂等记录已过期 | 转核对流程，避免盲目重建 | 恢复决策依据 |
| 取消时原请求仍在处理 | 追踪原结果，必要时补偿 | 原动作与补偿动作 |

验收条件要写成业务不变量：一个获批动作版本最多关联一个有效创建结果；每个成功结论都有外部证据；每个未知动作都有明确的后续处理入口。

## 十、什么时候值得引入工作流引擎

如果流程很短、只修改一个数据库、无需跨天等待，状态表加事务可能足够。如果任务包含长期等待、动态分支、多次外部活动和复杂恢复，成熟运行时可以减少自行实现定时器、历史与接管机制的负担。

引入引擎仍需要承担业务建模工作。它无法替你决定一笔未知订单应该如何核对，也无法替你定义重复采购的判断标准。

一个可恢复任务最终应能解释：当前进度由哪些事实支撑，哪些外部效果已经发生，哪些仍然未知，以及下一步为什么不会违反已批准的业务意图。
