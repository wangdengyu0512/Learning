# 向量数据库：把语义变成几何，再把几何变成工程

很多人第一次接触向量数据库，是从一个看起来非常顺滑的 RAG Demo 开始的：把文档切块，调用 Embedding 模型，把向量写进数据库；用户提问时再生成一个查询向量，取回最相似的 Top-K 文档。

代码可能只有几十行，于是很容易得到一个错觉：**向量数据库就是“能存数组并按相似度排序的数据库”。**

这个定义没有错，但它只描述了演示阶段。真正进入生产后，问题会迅速变成另一组更难的问题：

- “相似”究竟用 cosine、内积还是 L2，选错会发生什么？
- 为什么数据量一大就不能继续全表计算距离？
- HNSW、IVF、PQ、DiskANN 到底分别牺牲了什么？
- 查询叠加 `tenant_id`、权限、时间范围后，为什么结果可能少于 Top-K？
- 为什么纯语义搜索会漏掉错误码、SKU、函数名和版本号？
- 写入接口已经成功，为什么用户立刻搜索却查不到？
- 删除了一批向量，为什么内存没有下降，召回还越来越差？
- 已经有 PostgreSQL、Elasticsearch 或 MongoDB，是否还要再引入一个专用向量库？

要回答这些问题，不能只背产品 API，而要抓住两次转换：

> **第一次转换：Embedding 把语义关系变成高维空间里的几何关系。**
>
> **第二次转换：向量数据库把昂贵的几何计算变成可持久化、可过滤、可扩展、可运维的在线系统。**

本文根据本地《向量数据库：把语义变成几何，再变成工程》系列材料整理、重构而成。原始材料中的产品版本、前沿能力与基准信息以 **2026 年 6 月**为时间截面；本文重点保留相对稳定的原理与决策方法，具体产品能力仍应以项目实际版本为准。

## 一、第一性原理：语义搜索为什么会变成最近邻搜索

传统数据库擅长回答确定性问题：

- `id = 42`
- `price BETWEEN 100 AND 200`
- `created_at > yesterday`
- `name LIKE '%vector%'`

这些条件都建立在“相等”“大小”或“字面包含”上。可用户提出的问题往往不是字面匹配：

- 文档写的是“重置账户密码”；用户问的是“我登不上去了怎么办”；
- 文档写的是“降低尾延迟”；用户问的是“为什么 P99 突然升高”；
- 图片里是一只柯基；用户搜的是“一只短腿牧牛犬”。

要让机器处理“意思接近”，必须先把语义映射到一个可以计算的位置。Embedding 模型完成的就是这件事：

```text
输入对象 x
   ↓ embedding model
向量 v = [v1, v2, ..., vd]
```

训练过程通过对比学习、上下文预测或其他目标，让语义相关的样本在向量空间中更接近，让无关样本更远。于是：

```text
语义相似
   ↓ 被模型编码
几何距离较近
   ↓ 转化为算法问题
寻找 query 的最近邻
```

这里最重要的不是“向量有多少维”，而是**相对位置**。Embedding 的某一维通常没有稳定、可命名的人类含义；真正有意义的是完整向量之间的方向和距离。

### 1. 稠密向量与稀疏向量是两种不同的检索哲学

“向量”并不都一样。生产检索中最重要的是两类：

| 维度 | Dense 稠密向量 | Sparse 稀疏向量 |
|---|---|---|
| 典型维数 | 数百到数千维，固定长度 | 可能对应整个词表，维度很大 |
| 非零元素 | 几乎每一维都有值 | 绝大多数维度为零 |
| 编码内容 | 压缩后的语义关系 | 词项是否出现以及词项权重 |
| 典型来源 | 神经网络 Embedding | BM25、SPLADE 等 |
| 擅长问题 | 同义改写、自然语言、跨语言语义 | 错误码、型号、专名、罕见 Token |
| 典型失败 | 精确标识符被“语义化”后丢失 | 换一种说法就可能匹配不到 |

稠密向量能召回“忘记密码”和“重置密码”，却可能把 `ERR_2087` 当成普通噪声；稀疏检索能准确命中 `ERR_2087`，却不理解“登不上去”和“登录失败”是同一类问题。

这不是谁更先进，而是两种表示保留了不同的信息。后面会看到，Hybrid Search 的价值正来自两者**失败模式互补**。

### 2. 多语言检索为什么可能直接成立

如果一个多语言 Embedding 模型在训练中对齐了平行语料，那么“一段中文”和“它的英文翻译”会被映射到相近区域。检索系统本身并不需要先做机器翻译，只要查询向量和文档向量处在同一个已对齐的空间中，就可以用中文查询召回英文文档。

但这不是向量天然具备的能力，而是模型训练赋予的能力。若文档和查询使用了不兼容的模型，或者一个模型只在单一语言上训练，两个向量即使维度相同，也不代表处在同一个语义坐标系中。

> **维度相同不等于向量空间兼容。模型版本、归一化方式和距离度量都属于 Schema。**

## 二、距离不是细节：cosine、内积与 L2 决定排名

有了向量，还必须定义“近”。常见的三种度量是：

```text
dot(a, b) = Σ ai × bi

cosine(a, b) = dot(a, b) / (||a|| × ||b||)

L2(a, b) = ||a - b||
```

三者关注的信息不同：

| 度量 | 关注什么 | 越大还是越小越相似 | 典型特征 |
|---|---|---|---|
| Cosine | 方向、夹角 | 越大越相似 | 消除模长影响 |
| Dot Product | 方向与模长共同作用 | 越大越相似 | 单位化后与 cosine 排名等价 |
| L2 | 两个端点的直线距离 | 越小越相似 | 同时受方向和模长影响 |

一个高频结论是：若所有向量都已经做 L2 归一化，满足 `||v|| = 1`，那么：

```text
cosine(a, b) = dot(a, b)

L2(a, b)^2 = 2 - 2 × dot(a, b)
```

此时 cosine、内积和 L2 会得到等价的排序，只是分数表达不同。很多系统因此在写入前统一归一化，然后使用计算更直接的内积。

真正危险的情况是：模型按 cosine 训练或推荐 cosine，但数据库却使用未归一化向量做 L2 检索。若向量模长受到文本长度、置信度或数据分布影响，排名会混入模型原本没有打算表达的因素。最终表现可能不是报错，而是某类文档系统性掉出 Top-K。

因此，向量字段的 Schema 不应只记录“768 维”或“1536 维”，还要记录：

- Embedding 模型与版本；
- 输出维度；
- 是否归一化；
- 使用 cosine、dot 还是 L2；
- 文档与查询是否使用同一种编码策略；
- 是否允许不同模型版本的数据共存。

> **距离度量必须匹配模型空间。用错度量不是性能问题，而是语义被另一把尺子重新解释。**

## 三、为什么需要 ANN：精确最近邻最终会撞上 O(N × d)

最直接的向量检索叫 Flat Search 或 Brute-force KNN：对查询向量与库中全部 `N` 个向量逐一计算距离，再取前 `K` 个。

若向量维度为 `d`，单次查询的计算量大致是：

```text
O(N × d)
```

在几万条向量上，这可能就是最好的方法：实现简单、无需建索引、召回率为 1，而且现代 CPU 的 SIMD 对连续浮点运算非常友好。

但当数据到百万、亿甚至十亿级时，问题不再只是排序慢一点：

- 每次查询要读取并计算的向量数量线性增长；
- 高维向量的原始存储本身就可能达到数百 GB 或 TB；
- 在线系统还要处理并发查询，带宽和 CPU 很快成为瓶颈。

于是系统开始使用 ANN：Approximate Nearest Neighbor，近似最近邻。

### 1. “近似”不是把距离算得更随便

ANN 的核心不是把每个距离粗略算一下，而是：

> **不再检查全部向量，只检查索引认为最有希望的一小部分候选。**

真正的近邻若没有进入候选集合，就会被漏掉。这个损失通过 `recall@k` 衡量：

```text
recall@k = ANN 返回结果中属于真实 Top-K 的数量 / k
```

例如精确搜索的真实 Top-10 中，ANN 找回了 9 个，那么该查询的 `recall@10 = 0.9`。

要评估索引，不能只看查询延迟。正确流程是：

1. 选取有代表性的查询集；
2. 使用 Flat Search 离线计算真实 Top-K，作为 Ground Truth；
3. 用 ANN 在不同参数下检索同一批查询；
4. 同时记录 recall、P50/P95/P99 延迟、QPS 和资源占用；
5. 选择满足业务 SLO 的参数点，而不是选择跑分最高的单一指标。

```python
from statistics import mean


def recall_at_k(exact_ids: list[str], ann_ids: list[str], k: int) -> float:
    truth = set(exact_ids[:k])
    predicted = set(ann_ids[:k])
    return len(truth & predicted) / k


scores = [
    recall_at_k(exact, approximate, k=10)
    for exact, approximate in evaluation_pairs
]

print("mean recall@10 =", mean(scores))
```

### 2. 高维空间为什么让传统树索引失效

KD-tree、R-tree 一类结构在低维空间很有效，因为它们可以用边界剪掉整片不可能包含答案的区域。但维度升高后，距离会出现“集中”现象：随机点之间的距离越来越接近，查询球体频繁跨过大量切分边界，剪枝能力迅速下降。

结果是树索引需要回溯访问越来越多的分支，最终接近全表扫描，还额外承担指针跳转和树遍历成本。

这就是向量索引转向图、聚类和量化的原因：

- 图索引不尝试用高维边界剪枝，而是沿邻接关系导航；
- 聚类索引先定位少量空间区域，再扫描区域内部；
- 量化索引压缩向量，用近似距离减少内存和计算；
- 磁盘图索引把昂贵数据放到 SSD，通过更少随机读控制延迟。

## 四、索引统一心智模型：在召回、延迟、内存三角中选点

索引名词很多，但它们都在回答同一个问题：

> **为了少检查一些数据，你愿意牺牲多少召回、多少内存，或者多少查询延迟？**

![向量索引在召回率、查询延迟与内存成本三角中的位置](/blog-assets/vector-database-engineering/02-index-triangle.svg)

### 1. Flat：精确答案，也可能是小数据的最优答案

Flat 不建 ANN 索引，直接扫描全部向量。

优点是：

- `recall = 1.0`；
- 无索引构建和调参成本；
- 写入简单；
- 很适合作为离线 Ground Truth；
- 小数据或二阶段候选精排时非常高效。

缺点是查询成本随 `N × d` 线性增长。不要因为“向量数据库必须有索引”而过早上 HNSW。先测 Flat 是否已经满足延迟预算；对小型知识库，精确扫描可能更便宜、更简单、更正确。

### 2. IVF：先找区域，再扫描区域

IVF（Inverted File）的思路是先用聚类把空间划分成多个 Cell：

```text
建索引：
全部向量 → K-Means → nlist 个质心 → 每个向量归入最近 Cell

查询：
query → 找最近的 nprobe 个质心 → 只扫描这些 Cell
```

如果共有 `nlist` 个 Cell，而查询只探测 `nprobe` 个，理想情况下扫描量可从 `N` 降到近似：

```text
N × nprobe / nlist
```

IVF 的核心参数分为两类：

- `nlist`：建索引时决定空间被切成多少格；
- `nprobe`：查询时决定看多少格。

`nprobe` 越大，越不容易漏掉落在相邻 Cell 的真实近邻，召回更高，但延迟也更高。当 `nprobe = nlist` 时，IVF 退化为扫描全部 Cell，失去加速意义。

IVF 的结构性问题是“边界漏检”：query 位于 Cell 边缘时，真实近邻可能在隔壁 Cell。另一个问题是聚类质心来自历史数据分布；数据分布持续漂移后，Cell 可能变得不均衡，需要重训或重建。

### 3. HNSW：在小世界图中从远到近导航

HNSW（Hierarchical Navigable Small World）是通用场景中最常见的默认索引。它把向量组织成多层邻近图：

- 上层节点少，长程边多，负责快速跨越空间；
- 下层节点密，包含全部点，负责局部精确逼近；
- 查询从高层入口开始，沿“更接近 query”的邻居移动，再逐层下降；
- 到最底层后，用一个候选队列扩展搜索，直到 Top-K 稳定。

三个关键参数分别影响不同阶段：

| 参数 | 阶段 | 调大后的收益 | 调大后的代价 |
|---|---|---|---|
| `M` | 建索引 | 图更密、可达性更好、召回上限更高 | 邻接边占用更多内存 |
| `ef_construction` | 建索引 | 建图质量更高 | 构建更慢 |
| `ef_search` | 查询 | 探索更多候选、召回提高 | 查询延迟增加 |

HNSW 的优势是高召回区间通常具有很好的延迟，支持增量插入，也不需要像 IVF 那样先训练全局质心。

它的代价同样明显：

- 全精度向量和图邻接结构通常都要常驻内存；
- 图的边本身有额外空间开销；
- 删除节点会破坏导航路径，通常不能简单物理摘除；
- 高频更新与删除会积累墓碑并降低图质量；
- 亿级数据的 RAM 成本可能压倒其他因素。

HNSW 不是“所有维度都最好”，而是典型的**用内存换低延迟和高召回**。

### 4. PQ：把向量压成短码

PQ（Product Quantization，乘积量化）解决的是内存问题。它把一个 `D` 维向量切成 `m` 个子向量，在每个子空间独立训练码本，然后不再保存每段的完整浮点数，而只保存“最接近哪个质心”的编号。

例如，一个 128 维 `float32` 向量原始大小为：

```text
128 × 4 bytes = 512 bytes
```

若切成 8 段，每段使用 8 bit 编码，那么压缩码只需：

```text
8 × 1 byte = 8 bytes
```

查询时通常使用 ADC（Asymmetric Distance Computation）：query 保持全精度，先计算它的每个子段到码本质心的距离表；库中每个向量只需按码字查表并累加近似距离。

PQ 省下了大量内存，但引入量化误差。越激进的压缩，近似距离越可能改变真实排名。因此它通常与以下机制组合：

- IVF + PQ：先用 Cell 缩小范围，再用压缩码计算距离；
- Oversampling：粗检索先多取若干倍候选；
- Rescore：再用原始或更高精度向量重新打分。

> **量化负责便宜地圈出候选，Rescore 才负责把排名救回来。**

生产中常见的压缩层级还包括：

| 表示 | 大致思路 | 优点 | 主要代价 |
|---|---|---|---|
| Float16 / Half Vector | 每个数从 32 bit 降到 16 bit | 省一半空间，精度通常较稳 | 仍然是稠密浮点存储 |
| Scalar Quantization | 每维映射到 int8 | 约 4 倍压缩，工程成本较低 | 有一定量化误差 |
| Product Quantization | 分段后存码本编号 | 压缩比高 | 需要训练码本，距离更近似 |
| Binary Quantization | 每维只保留极少比特 | 压缩极强、粗筛很快 | 必须 Oversample + Rescore |

### 5. DiskANN：让 SSD 进入索引设计

当 HNSW 的内存成本不可接受时，可以把图和高精度向量放到 SSD，把压缩表示和热点结构留在内存中。查询先用内存中的近似表示导航和粗筛，需要精确判断时再读取 SSD 上的原始向量。

DiskANN 一类方案的关键不再只是“少算几次距离”，而是“少做几次随机磁盘读取”。其 Vamana 图会有意保留一定数量的长程边，缩短任意两点之间的导航跳数，从而减少 SSD 随机 IO。

它适合这样的约束组合：

- 数据大到 HNSW 全量驻内存不经济；
- 可以接受毫秒级而不是极致亚毫秒延迟；
- 有高性能本地 NVMe 或合适的云存储层；
- 愿意用更复杂的冷热分层和缓存策略换取更低 RAM 成本。

### 6. 一张表看懂索引位置

| 索引 | 召回 | 延迟 | 内存 | 主要旋钮 | 常见适用场景 |
|---|---|---|---|---|---|
| Flat | 精确 | 随数据量线性增长 | 保存完整向量 | 无 | 小数据、Ground Truth、候选精排 |
| IVF / IVFFlat | 可调 | 中等 | 仍保存完整向量 | `nlist`、`nprobe` | 内存尚可、接受聚类训练 |
| HNSW | 高 | 低 | 高，图边额外占用 | `M`、`ef_construction`、`ef_search` | 通用在线检索默认起点 |
| IVF-PQ | 中等，可用 Rescore 提升 | 中等 | 很低 | `nprobe`、分段数、码本位数 | 超大规模、内存硬约束 |
| DiskANN / Vamana | 较高 | 受 SSD IO 影响 | RAM 较低 | 图度数、Beam 宽度、缓存 | 亿级以上、RAM 昂贵 |
| LSH | 波动较大 | 可预测性较弱 | 多哈希表可能膨胀 | 签名长度、哈希表数 | 特殊去重或低召回容忍场景 |

面对任何新索引，都可以先问四个问题：

1. 它如何减少候选数量？
2. 它把什么放在 RAM、SSD 或对象存储？
3. 它牺牲的是召回、延迟还是写入成本？
4. 哪个参数能在查询期调整，哪个参数必须重建索引？

这比背诵索引名称更有迁移能力。

## 五、索引库不等于数据库：FAISS 与向量数据库的分界线

FAISS 能高效完成最近邻搜索，但“能算 Top-K”不等于“能作为在线数据库运行”。

可以把能力拆成两层：

```text
算法层：Flat / IVF / HNSW / PQ / GPU KNN

系统层：持久化、WAL、增量 CRUD、过滤、分片、副本、API、监控、恢复
```

索引库主要提供算法层；向量数据库则要补齐系统层。

| 能力 | 索引库 | 向量数据库 |
|---|---|---|
| 最近邻搜索 | 核心能力 | 核心能力之一 |
| 持久化与崩溃恢复 | 通常需要自行封装 | 通常内建 |
| 增量 Upsert / Delete | 受索引类型限制 | 面向在线更新设计 |
| Metadata 过滤 | 通常较弱或没有 | 生产核心能力 |
| 网络服务 API | 进程内调用为主 | HTTP / gRPC / SDK |
| 分片与副本 | 自己实现 | 产品能力的一部分 |
| 一致性模型 | 调用方负责 | 通常提供可选语义 |
| Compaction / Rebuild | 调用方组织 | 通常有后台生命周期 |

因此，“有了 FAISS 为什么还要向量数据库”的答案不是“后者的 ANN 更快”，而是：

> **FAISS 是索引算法的实现；向量数据库把索引包装成可长期运行、可增删改查、可过滤、可恢复、可扩展的服务。**

但也不要反过来认为数据库一定优于索引库。离线批处理、单机实验、模型评测或进程内候选检索，直接使用 FAISS 可能更轻。只有当系统出现持续写入、删除、并发查询、跨语言访问、高可用和运维要求时，数据库能力才真正产生价值。

向量数据库的核心操作可以归纳为四个动词：

- `upsert`：按 ID 新增或覆盖记录；
- `query/search`：按距离返回 Top-K；
- `filter`：叠加租户、权限、时间、来源等结构化条件；
- `delete`：逻辑删除，并在后台物理回收。

表面 API 很简单，复杂度几乎都藏在这四个动词的执行语义里。

## 六、生产第一难题：ANN 与 Metadata 过滤的根本冲突

真实查询很少只问“全库最相似的 10 条”。更多时候它会带上：

```text
tenant_id = 'tenant-a'
AND department IN ('engineering', 'support')
AND created_at >= '2026-01-01'
AND acl_tags CONTAINS 'employee'
```

问题在于，HNSW 的边和 IVF 的 Cell 是按向量几何关系组织的，它们并不知道 `tenant_id` 和 ACL 的存在。把过滤条件叠加到 ANN 上，至少有三种策略。

![向量检索中后过滤、前过滤和索引内过滤三种策略对比](/blog-assets/vector-database-engineering/03-filtering.svg)

### 1. Post-filter：先取近邻，再过滤

流程是：

```text
全库 ANN 取 m 个候选 → 应用 metadata 条件 → 返回剩余结果
```

它实现简单、速度也可能很快，但有一个严重问题：**结果可能少于 K，并且漏掉真正应该返回的近邻。**

假设一千万条向量里，只有 0.5% 属于 `category = finance`。如果 HNSW 只先取全库最近的 15 条，再删除非 finance 结果，那么最终可能只剩 0 到 2 条。

正确的 finance 近邻也许位于全库第 100、500 或 1000 名，但因为根本没有进入最初的候选窗口，后续过滤没有机会看到它们。

这不是“排序稍差”，而是返回数量和语义都不正确，而且通常不会报错。

缓解方法包括：

- Oversample：先取 `k` 的若干倍候选；
- 提高 `ef_search`：扩大 HNSW 搜索窗口；
- Iterative Scan：过滤后数量不足就继续从索引取下一批；
- 根据历史选择性动态决定 Oversample 倍数。

这些方法能缓解，却无法让固定候选窗口在任意选择性下都正确。

### 2. Pre-filter：先筛出合格集合，再搜索

流程是：

```text
metadata 过滤 → 得到合格 ID 集合 → 只在子集内做最近邻
```

直觉上它最准确，但在图索引里有一个反直觉问题：如果把不合格节点直接从可遍历图中移除，原本借助这些节点连接起来的路径可能被切断。合格节点仍然存在，却不一定可从入口高效到达。

当合格集合很小时，这反而不是问题：几百条数据直接 Flat Scan，既快又精确。当合格集合很大时，搜索既不能高效使用原图，又不能承担大规模暴力扫描，于是可能同时损失延迟和召回。

### 3. Integrated Filtering：让过滤进入索引遍历

更成熟的做法是把过滤条件下推到 ANN 算法内部：

- 不符合条件的节点不进入最终 Top-K；
- 但搜索仍可借助它的边继续导航，避免破坏图连通性；
- 若过滤选择性太强、图搜索不再划算，则回退到合格子集的精确扫描；
- 标量字段需要额外的 Payload / Scalar Index 协助快速判断。

这类方案没有消灭代价，而是把代价从“静默错误或召回下降”转移为“更复杂的实现、统计信息和运维策略”。这也解释了为什么 Metadata Filtering 是专用向量数据库的重要竞争力，而不是一个普通 `WHERE` 子句。

### 4. 过滤策略应由选择性驱动

选择性可以近似理解为“符合条件的数据占全库多少比例”。

| 合格子集规模 | 更合理的方向 |
|---|---|
| 几百或几千条 | 先过滤后精确扫描，简单且 recall=1 |
| 占全库很高比例 | Post-filter + 小幅 Oversample 可能足够 |
| 中等规模且查询频繁 | Integrated Filtering / Iterative Scan |
| 高基数多租户、每个租户占比很低 | 分区路由、过滤感知图或按租户分流 |
| 某些超级租户特别大 | 为大租户单独分区或独立索引 |

所以不要问“Pre-filter 和 Post-filter 哪个永远更好”，而要问：**过滤字段的基数、命中率分布和查询频率是什么？**

## 七、生产第二难题：Dense-only 会静默漏掉精确 Token

纯 Dense Retrieval 看起来很智能，却有一个危险盲区：它擅长压缩语义，也会顺手抹平某些必须原样保留的信息。

典型对象包括：

- 错误码：`ERR_2087`、`NPE-0042`；
- HTTP 状态码：`451`、`429`；
- SKU、订单号、UUID；
- 函数名：`ef_search`、`binary_quantize`；
- API 名、配置键、版本号；
- 人名、药名、设备型号等长尾实体。

用户搜索 `ERR_2087` 时，Dense 模型可能返回“错误处理”“日志排查”“服务异常”相关文档，却没有任何一篇真正包含这个错误码。结果语义上似乎合理，因此比报错更难发现。

### 1. Hybrid Search：让两路召回互相兜底

一条典型的生产检索链路是：

```text
                         ┌→ Dense ANN ─────┐
query → 解析 / 改写 ─────┤                  ├→ RRF 融合 → Top-N → Rerank → Top-K
                         └→ Sparse / BM25 ─┘
```

- Dense 路负责同义表达、自然语言和跨语言语义；
- Sparse 路负责精确词项、罕见标识符和原词命中；
- 融合阶段把两路候选合并；
- Reranker 对少量候选做更昂贵但更准确的相关性判断。

### 2. 为什么常用 RRF，而不是直接相加分数

Dense cosine 分数和 BM25 分数不在同一个量纲中：

- cosine 常位于有限区间；
- BM25 没有相同上界，分布还会随语料变化；
- 不同模型的分数校准也不一致。

直接做：

```text
0.7 × dense_score + 0.3 × bm25_score
```

看起来直观，实际上权重很容易被某一路的数值范围支配。

RRF（Reciprocal Rank Fusion）绕过原始分数，只使用每一路的排名：

```text
RRF(document) = Σ 1 / (c + rank_i(document))
```

一篇文档只要在任一路排名靠前，就能获得较高融合分。它丢失了“第一名领先第二名多少”的信息，却获得了跨检索器的稳健性。

### 3. Rerank 为什么只能放在候选集后面

Cross-encoder Reranker 会把 query 与每篇候选文档一起输入模型，直接判断二者相关性。它比独立编码的 Dense Embedding 更准确，因为模型可以看到 query 与文档 Token 之间的交互。

代价是每个候选都要执行一次更重的推理，无法对百万文档全量运行。因此合理分工是：

- 第一阶段召回追求“别漏”，候选可以稍多；
- 第二阶段 Rerank 追求“排准”，只处理几十或几百条；
- 最后再把少量高质量上下文交给 LLM。

Hybrid 不是免费的：它意味着两套索引、两条更新路径、更多候选、一次融合和可能的一次模型推理。是否值得，应由业务查询中精确 Token、专名和代码类问题的比例决定。

## 八、写入、更新与删除：向量库也有生命周期和一致性

“写入成功”并不总等于“立刻可以通过 ANN 搜到”。一条记录通常经历：

```text
写入 WAL / 数据段
   ↓
进入 Growing Segment 或待索引状态
   ↓
后台接入 HNSW / IVF 等索引
   ↓
成为稳定可检索数据
```

![向量数据库写入、索引可见、更新软删与压缩重建生命周期](/blog-assets/vector-database-engineering/04-write-lifecycle.svg)

### 1. 写入可见性是一个窗口

许多向量系统为了写吞吐和查询性能，会把“数据持久化”和“数据进入高效索引”拆成两个阶段。最终一致模式下，写入 API 返回成功时，数据可能已经安全落盘，却还没有进入 ANN 的可见集合。

因此生产系统必须明确：

- 用户上传文档后是否要求立即可搜？
- 可以接受几秒或几分钟的索引延迟吗？
- 是否需要 Read-after-write？
- 查询是否应等待某个时间戳、LSN 或一致性水位？
- 批量灌库完成后如何确认所有 Segment 已可检索？

对离线知识库导入，最终一致通常足够；对“刚上传、立刻提问”的交互，可能需要有界一致、强一致查询，或者在应用层显示“正在建立索引”的状态。

### 2. Upsert 通常不是原地修改

图索引和不可变 Segment 都不喜欢原地改写。很多系统的更新更接近：

```text
写入新版本 + 标记旧版本失效 + 后台回收
```

这使按稳定 ID 的 Upsert 可以保持幂等，但也意味着高频更新会产生额外版本和墓碑。

### 3. Delete 往往只是 Tombstone

从 HNSW 图中物理删除一个节点，可能切断其他节点的导航路径。常见做法是：

- 给记录打 Tombstone；
- 查询时跳过已删节点；
- 图结构暂时仍保留它；
- 后台 Compaction 或 Rebuild 时再真正清理。

墓碑持续积累会带来：

- 内存和磁盘空间不能立即释放；
- 搜索会浪费候选预算在已删除节点上；
- 有效邻接关系变差；
- 某些活跃节点可能越来越难到达；
- 相同 `ef_search` 下召回逐步下降。

因此索引维护计划至少要观察：

- 删除与更新比例；
- 墓碑占比；
- 每次查询跳过的失效候选数；
- Recall 随时间的变化；
- Compaction / Rebuild 的耗时与额外空间；
- 重建期间如何切换新旧索引。

“数据库支持 Delete”只说明 API 存在，不代表删除在物理上廉价。

## 九、内存账、分片与存算分离

向量系统最容易被低估的是内存成本。假设有一亿条、1024 维的 `float32` 向量，仅原始数据就是：

```text
100,000,000 × 1024 × 4 bytes
≈ 409.6 GB
```

再叠加 HNSW 邻接边、对象头、ID、Metadata、索引辅助结构和运行时开销，实际内存会进一步增加。

“数据已经持久化到磁盘”不代表 HNSW 查询可以不占内存。持久化解决的是崩溃恢复；低延迟图搜索通常仍希望热点向量和邻接结构常驻 RAM。

### 1. 三种主要降本方向

第一种是降精度：

- Float32 → Float16；
- Scalar Quantization；
- PQ 或 Binary Quantization；
- 粗筛后使用高精度 Rescore。

第二种是水平拆分：

- 按 ID 或 Partition Key 分片；
- 查询能定位分片时定向路由；
- 无法定位时向所有分片扇出，再归并全局 Top-K；
- 副本承担高可用和读扩展。

第三种是分层存储：

- 热索引与压缩码在 RAM；
- 全精度向量在本地 SSD；
- 更冷的数据落对象存储；
- 查询依赖缓存、预取和更少随机 IO。

### 2. 分片不是免费扩容

把数据切到更多节点后，查询可能变成：

```text
query
  ├→ shard 1: local top-k
  ├→ shard 2: local top-k
  ├→ shard 3: local top-k
  └→ shard n: local top-k
               ↓
          global merge top-k
```

这会引入：

- 扇出带来的网络尾延迟；
- 某个慢分片拖累全局 P99；
- 每个分片局部候选数不足导致全局召回下降；
- 数据倾斜和热点租户；
- 副本一致性与索引版本切换；
- Rebalance 期间的额外 IO。

最好的分片查询是根本不扇出：如果 `tenant_id`、地域或业务域天然能成为路由键，就应让请求直接到目标分片。但高基数租户也不一定适合“一租户一物理分区”，否则分区数会爆炸。常见做法是把大量小租户哈希到有限分片，为少数超大租户单独隔离。

## 十、从约束反推选型，而不是从产品排行榜开始

向量检索的产品大致分为四类：

| 类型 | 代表性形态 | 优势 | 主要代价 |
|---|---|---|---|
| 进程内索引库 | FAISS 等 | 轻、快、算法丰富、适合实验与批处理 | 持久化、CRUD、过滤、服务化都要自己做 |
| 现有数据库 / 搜索引擎扩展 | pgvector、Elasticsearch/OpenSearch、MongoDB、Redis 等 | 少引入一个系统，数据与业务关系更近 | 向量能力与资源隔离可能不是最深 |
| 专用开源向量数据库 | Milvus、Qdrant、Weaviate 等 | 过滤、分片、索引和向量运维更专业 | 多一个要部署、监控、升级的服务 |
| 全托管服务 | 托管向量平台 | 快速上线、运维负担低、弹性更方便 | 长期成本、平台锁定和可移植性 |

真正的入口不是“哪个产品性能最强”，而是下面这组约束。

### 1. 先问能不能不增加新服务

如果业务数据已经在 PostgreSQL，而且规模与负载仍在单机或常规集群可承受范围，pgvector 往往值得优先验证。它的价值不只在向量性能，还在：

- 文档、权限、订单和向量可以同事务写入；
- 可以直接 JOIN 业务表；
- 避免双写失败造成“文档存在、向量缺失”的孤儿状态；
- 团队继续使用熟悉的备份、监控和 SQL 工具。

同理，如果团队已经成熟运行 Elasticsearch/OpenSearch，新增向量字段和 Hybrid Search 可能比再维护一个独立系统更划算。

> **少一个会独立故障、独立扩容、独立告警的服务，本身就是架构收益。**

### 2. 再看哪些硬约束会迫使系统升级

以下信号会让专用向量系统的价值变得更明显：

- 数据规模持续增长到单机内存和索引构建难以承受；
- 高 QPS 和高召回必须同时满足；
- 多租户与复杂 Metadata 过滤是主路径；
- 需要成熟的分片、副本、在线扩容和冷热分层；
- 需要多种向量索引、稀疏向量、多向量或 GPU 摄入；
- 向量工作负载会明显干扰现有 OLTP 数据库；
- 独立团队能够承担服务化运维。

### 3. 一个可执行的选型顺序

```text
是否已有 PG / ES / Mongo / Redis 等成熟数据栈？
  ├─ 是 → 先验证扩展能力是否满足规模、召回、过滤与延迟
  │        ├─ 满足 → 留在现有系统，减少运维面
  │        └─ 不满足 → 抽象检索接口，迁移到专用向量库
  └─ 否 → 数据量与并发是否需要分布式？
           ├─ 否 → 单节点向量库或嵌入式方案
           └─ 是 → 分布式专用库或托管服务
```

选型时至少应记录这些输入：

- 当前向量数与两年后的上界；
- 向量维度、模型升级频率；
- 写入吞吐、更新率、删除率；
- 查询 QPS 与 P99 延迟目标；
- 目标 `recall@k`；
- 过滤字段及其基数、选择性分布；
- 是否要 Hybrid 与 Rerank；
- Read-after-write 要求；
- 单租户和全局数据隔离方式；
- 可接受的 RAM、SSD、对象存储和托管费用；
- 团队运维能力与迁移成本。

### 4. 为未来迁移保留接口

即使今天选择最简单的方案，也应把不可逆决策显式化：

```ts
export type SearchRequest = {
  queryText: string;
  tenantId: string;
  topK: number;
  filters?: Record<string, unknown>;
  retrievalMode: "dense" | "sparse" | "hybrid";
};

export type SearchHit = {
  id: string;
  score: number;
  text: string;
  metadata: Record<string, unknown>;
};

export interface RetrievalStore {
  upsert(records: SearchHit[]): Promise<void>;
  search(request: SearchRequest): Promise<SearchHit[]>;
  delete(ids: string[]): Promise<void>;
}
```

这层抽象不能消灭数据库差异，但可以避免业务代码直接依赖某家 SDK 的 Collection、Namespace、Payload 或 Filter DSL。

迁移时仍要处理：

- 分数方向和范围不同；
- Filter 语义不同；
- 一致性与可见性不同；
- Upsert 和 Delete 行为不同；
- HNSW 参数不能机械映射；
- Hybrid 融合方式不同；
- 分页和游标语义不同。

所以“抽象接口”不是假装所有产品一样，而是把产品差异集中在适配层。

## 十一、把一个生产级检索请求完整走一遍

假设用户在多租户知识库中搜索：

```text
tenant_id = acme
query = "升级到 v2.6.1 后出现 ERR_2087 怎么处理？"
```

一条合理链路可以是：

### 1. 查询理解

系统识别出两类信号：

- 自然语言意图：“升级后出现错误，寻找处理方法”；
- 精确 Token：`v2.6.1`、`ERR_2087`。

因此不能只走 Dense。

### 2. 权限与路由

根据 `tenant_id = acme` 定位允许访问的分片、Collection 或逻辑范围，并叠加用户 ACL。权限过滤必须在检索链路中生效，而不能只依赖 LLM 自己“不引用不该看的内容”。

### 3. 两路召回

Dense 路把完整 query 编码为向量，在过滤感知 ANN 中寻找语义近邻；Sparse 路通过 BM25 或稀疏向量精确命中版本号和错误码。

### 4. 候选融合

分别取两路 Top-N，用 RRF 融合去重。若过滤选择性低，系统需要扩大候选窗口或迭代扫描，确保最后能凑够所需候选。

### 5. Rerank

将 query 与融合后的几十条文档送入 Cross-encoder，重新判断“这篇文档是否真的解释了 v2.6.1 中的 ERR_2087”。

### 6. 上下文组装

根据 `parent_doc_id` 去重，补充命中 Chunk 的前后文，控制总 Token 预算，并保留来源、标题、更新时间和权限信息。

### 7. 生成与引用

LLM 只能依据提供的证据回答；证据不足时应拒答或触发下一轮检索，而不是利用参数记忆编造处理步骤。

### 8. 可观测性

一次请求至少应记录：

- Dense 和 Sparse 各自候选；
- 过滤前后数量；
- RRF 与 Rerank 前后排名；
- 索引参数，如 `ef_search` 或 `nprobe`；
- 每阶段延迟；
- 最终引用的 Chunk；
- 是否命中缓存；
- 使用的 Embedding / Reranker 版本。

只有中间过程可见，才能判断失败来自模型、索引、过滤、融合、重排还是生成。

## 十二、评估：不要只测“搜得快不快”

一个向量检索系统至少有四组指标。

### 1. 检索质量

- `recall@k`：ANN 找回真实近邻的比例；
- `precision@k`：返回结果中真正相关的比例；
- `MRR`：第一个相关结果出现得有多靠前；
- `NDCG`：综合考虑多级相关性与排名位置；
- Hybrid 分桶评测：自然语言、专名、错误码、SKU、跨语言分别测。

### 2. 性能

- P50 / P95 / P99 延迟；
- QPS 与并发下的吞吐；
- 索引构建时间；
- 写入到可检索的可见性延迟；
- Filter 选择性变化时的延迟曲线；
- Compaction / Rebuild 期间的性能波动。

### 3. 资源与成本

- 每百万向量 RAM；
- 原始向量、压缩码、图边与 Metadata 的占比；
- SSD / 对象存储用量；
- Rerank 模型调用成本；
- 全量重建需要的临时双份空间；
- 托管服务按读写单元、存储和流量产生的费用。

### 4. 正确性与可运维性

- 过滤后是否稳定返回 K 条；
- ACL 是否可能越权；
- 重复 Upsert 是否幂等；
- Delete 多久后物理回收；
- 模型版本切换是否混用空间；
- 备份恢复后索引是否可重建；
- 单分片故障时系统是降级、超时还是返回部分结果。

尤其要建立按场景分层的测试集。一个平均 Recall 很高的系统，可能在错误码查询上几乎全部失败；一个平均延迟很低的系统，可能在低命中率过滤下 P99 突然爆炸。

## 十三、常见误区：看起来合理，实际上会埋雷

### 误区一：向量维度越高越好

更高维度通常意味着更高存储、内存和距离计算成本，但不保证对目标业务更准确。应在自己的语料、查询集和下游任务上评测，而不是把维度当作模型能力的单调指标。

### 误区二：上了 HNSW 就“保证性能”

HNSW 保证的是一种可调的性能—召回折中，不是无条件更快。数据很小时，Flat 可能更快、更简单，而且 recall=1。

### 误区三：Top-K 返回了 K 条，召回就没问题

数量正确不等于结果正确。ANN 可能返回 K 条，却漏掉真实 Top-K；Post-filter 还可能既少于 K，又漏掉更近的合格结果。必须用 Ground Truth 和业务标注评测。

### 误区四：数据库支持 Filter，所以过滤没有代价

API 能写 `filter` 不代表底层一定是过滤感知索引。要确认是 Post-filter、Pre-filter、Iterative Scan，还是 Integrated Filtering，并测试不同选择性下的 Recall 和 P99。

### 误区五：持久化到磁盘，所以不会吃很多内存

持久化与在线工作集是两件事。HNSW 的低延迟通常依赖图和向量常驻内存；磁盘只是恢复来源。若想真正降低 RAM，需要量化、DiskANN 或分层存储。

### 误区六：Delete 成功后空间会立刻下降

大多数图索引使用 Tombstone。逻辑删除立即生效，物理空间通常要等 Compaction 或 Rebuild。

### 误区七：只要有向量检索，就算完成了 RAG

向量库只负责候选检索的一部分。解析、分块、模型版本、Hybrid、Rerank、上下文组装、引用、拒答和评估同样决定最终质量。检索质量是生成质量的上限，却不是正确答案的保证。

### 误区八：专用向量数据库是 AI 项目的必选项

很多中等规模系统用 pgvector、Elasticsearch/OpenSearch 或现有数据栈就足够。专用库应该由规模、过滤、隔离、延迟和运维需求触发，而不是由“这是一个 AI 项目”触发。

## 十四、一套可以直接复用的设计清单

准备上线向量检索前，可以逐项回答下面的问题。

### 表示层

- 文档和 query 使用哪个 Embedding 模型？
- 维度是多少，是否归一化？
- 使用 cosine、dot 还是 L2？
- 模型升级时如何双写、回填和切流？
- 是否需要多语言、多模态或多向量表示？

### 数据层

- 一条记录代表文档、Chunk、图片还是实体？
- 是否保存 `parent_doc_id` 以便整篇删除和邻块扩展？
- 哪些 Metadata 是高频过滤字段，应显式建列或建标量索引？
- 是否保存 `model_version`、`source_version` 和更新时间？
- Chunk ID 如何保证幂等？

### 索引层

- Flat 是否已经满足预算？
- HNSW 的 `M`、`ef_construction`、`ef_search` 如何通过 Recall 曲线确定？
- 内存是否迫使使用 Float16、SQ、PQ 或 DiskANN？
- 量化后是否保留高精度向量用于 Rescore？
- 索引何时重建，如何原子切换？

### 查询层

- 查询中精确 Token 占比是多少？是否需要 Hybrid？
- Dense 和 Sparse 各取多少候选？
- 使用 RRF 还是经过校准的加权融合？
- 是否需要 Reranker？延迟预算是多少？
- Metadata 过滤采用什么策略？
- 权限条件是否在检索阶段强制执行？

### 一致性与运维层

- 写入多久可见？
- 用户是否要求写后即读？
- Delete 是逻辑还是物理，回收周期多长？
- 墓碑到什么阈值触发 Compaction / Rebuild？
- 分片键是什么，是否会产生热点？
- 是否能在单分片故障时安全降级？
- 如何监控 Recall 漂移，而不只是监控 CPU 和延迟？

如果这些问题没有答案，系统大概率仍处在 Demo 阶段。

## 十五、最后把整套知识压缩成五句话

1. **Embedding 把语义关系编码成高维空间里的相对位置，向量检索因此成为最近邻问题。**
2. **ANN 的本质是少看候选，用可测量的 Recall 损失换延迟与成本；所有索引都位于 Recall、延迟、内存三角中的某个位置。**
3. **HNSW 用 RAM 买高召回与低延迟，IVF 用空间分区减少扫描，PQ 用近似距离压缩内存，DiskANN 用 SSD 和更少随机 IO 扩大规模。**
4. **Demo 到生产的真正分水岭不是“会不会算 Top-K”，而是过滤、Hybrid、一致性、删除、分片、重建和可观测性。**
5. **不要从产品名字开始选型；先写清数据规模、Recall、P99、过滤选择性、一致性和运维预算，再让约束淘汰不合适的方案。**

向量数据库并没有让搜索脱离数据库工程。恰恰相反，它把模型、几何、索引、存储和分布式系统压到了一条查询链路里。

真正掌握它，不是能背出“HNSW 是分层小世界图”，而是遇到一个具体系统时，能够继续追问：

> **语义是怎样被编码的？索引少看了哪些数据？过滤会不会让候选消失？召回由什么兜底？写入何时可见？删除何时回收？当前最紧的约束究竟是内存、延迟，还是正确性？**

当这些问题能够被量化、测试和运维时，语义才真正从几何变成了工程。
