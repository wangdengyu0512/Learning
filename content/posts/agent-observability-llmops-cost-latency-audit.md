用户给采购助手一个任务：查询某型号设备的库存，比较两家供应商的报价，选择满足交期的方案，创建采购申请。

46 秒后，助手回复：“采购申请已创建。”

用户打开采购系统，没有找到申请。运维看了一眼监控：服务正常，模型请求成功，工具接口也返回了 HTTP 200。另一个信号却很明显：这类任务的模型费用正在上涨。

应该先改提示词、换模型，还是给接口增加重试？此时证据还不够。真正需要还原的是：助手拿到了什么信息，调用了什么工具，怎样解释返回值，以及业务系统最终发生了什么。

**Agent 可观测性的价值，是把用户的一次任务，与执行过程、资源消耗、业务结果和动作证据连接起来。** 有了这条联系，成本和延迟才有归属，失败才有可验证的原因。

本文面向已经开发过 LLM 应用的工程师。下面用同一个采购案例完成一次排障，再讨论如何把这种能力接入日常开发与运维。案例、价格、耗时和对比数据均为教学构造，不是线上测量结果；资料核验日期为 2026 年 10 月 22 日。

## 一、先定义什么叫“做成了”

采购助手的目标是创建有效申请。因此，成功条件至少包括：申请存在、设备型号和数量正确、供应商满足约束、申请状态符合业务要求。

模型输出“已创建”，只说明它生成了这句话。工具返回 HTTP 200，只说明这次 HTTP 请求被成功处理。二者都不足以证明上述条件成立。Anthropic 的 Agent 评估指南将执行记录与环境中的最终结果明确区分：预订助手说预订成功，与数据库里确实存在预订，是两件需要分别观察的事。[1]

给本例补上工具响应，就能看到第一条线索：

```json
{
  "request_id": "req-731",
  "status": "accepted",
  "application_id": null
}
```

这是本文示例接口的约定：`accepted` 表示异步请求进入队列，`request_id` 用来查询处理结果。助手把“已受理”当成“已创建”，没有继续查询，就结束了任务。稍后，后台校验发现供应商编码无效，拒绝创建申请。

于是，一次执行产生了三种不同的事实：

| 观察层面 | 本次结果 | 证据 |
| --- | --- | --- |
| 程序执行 | 流程正常结束 | 没有未处理异常，已经生成回复 |
| 业务目标 | 已确认失败 | 创建请求最终被拒绝，没有有效申请 |
| 用户感知 | 收到成功承诺 | 最终回复写了“采购申请已创建” |

如果看板只有一个绿色的 `success`，这三种事实就会混在一起。本文建议分别记录执行状态和业务结果；有权限要求的动作，再独立记录策略决定。它们是应用自己的字段，不能依靠 HTTP 状态或 Span 状态自动推导。

排查也从这里开始：**先找业务结果的证据，再沿执行链路寻找最早的偏差。** 本例最早的偏差出现在工具返回后的状态判断。增加创建重试无法修复这个判断，还可能带来重复申请。

## 二、还原任务：让每一步都有来路和去向

### 2.1 从一条任务进入完整链路

先把这 46 秒展开。助手做了需求解析，并行查询库存和供应商 A，随后查询供应商 B；B 的第一次查询超时，重试成功。助手再比较报价、提交申请，最后生成回复。

![采购任务执行图：查询与重试、提交申请、误报成功，以及缺失的结果验证](/blog-assets/agent-observability-llmops/task-trace.svg)

为了查询这条链路，可以先统一四个概念：

- `task_id`：用户的业务目标。用户重试同一个任务时，可以继续关联原任务。
- `run_id`：应用对这项任务的一次完整执行。重新执行会产生新的运行记录。
- `trace_id`：把一次执行中的调用关联起来。
- `span_id`：标识模型调用、检索、工具执行等具体步骤。

这里的 `run_id` 是本文约定，不同产品对 Run 的定义可能不同。接入平台时需要做显式映射。

短任务可以用一条 Trace 覆盖一次 Run。持续数小时、需要人工审批的任务，可以结束当前 Trace，恢复时创建新 Trace，通过任务标识和 Span Link 关联前后阶段。OpenTelemetry 提供父子 Span 和 Span Link 来表达这些关系。[2]

### 2.2 记录足以解释动作的上下文

只记录“调用了模型”无法解释模型为什么选错供应商。至少还需要知道：模型及版本、提示模板版本、可用工具及其定义版本、进入上下文的报价来源，以及实际提交的参数。

这些数据可以按用途放置：

| 数据 | 用来回答什么 | 本例中的记录 |
| --- | --- | --- |
| 时间、父子关系、状态 | 执行经过哪些步骤 | 供应商 B 查询发生过一次超时 |
| 输入输出的受控引用 | 当时依据什么行动 | 报价快照、工具响应、最终回复 |
| 配置版本 | 哪个变化可能引入问题 | 提示模板 v12、采购工具 v3 |
| 业务关联信息 | 现实系统发生了什么 | `req-731` 及后续处理结果 |

短字段用于筛选，较大的正文放入访问受控的存储，通过引用关联。原始合同、认证信息和用户资料应在采集前处理；只保存哈希能支持一致性核验，不能还原丢失的上下文。需要复查内容时，应保留经过脱敏且可授权访问的版本。

记录模型可见输入、可见输出和工具动作，已经能解释大量故障。模型自行生成的“决策说明”可以辅助阅读，但不能证明其内部真实推理过程。

### 2.3 三个容易断链的位置

**重试。** 保留一次逻辑操作，并为能够观测到的每次尝试记录独立标识、耗时和结果。本例中“查询供应商 B”是逻辑操作，超时请求和重试请求是两次尝试。若 SDK 隐藏了内部重试，应标明采集范围，不能假装已经看到每次网络请求。

**并行。** 库存查询和供应商 A 查询应属于同一个调度阶段。跨线程、进程或队列时，需要显式传播上下文。HTTP 服务之间可以使用 W3C Trace Context 的 `traceparent` 等头部；任务标识仍需随业务消息保存。追踪标识只负责关联请求，不能当作身份和权限证明。[3]

**挂起后恢复。** 审批通过后，用原任务、获批动作和持久化检查点恢复。此时尤其需要记录新执行阶段使用的版本，避免把恢复前后的配置误认为相同。

公共字段可以参考 OpenTelemetry GenAI 语义约定。核验时，相关规范已迁移到独立仓库，模型和 Agent Span 文档仍标记为 Development；部署时应锁定采用的规范与 SDK 版本。其逻辑操作 Span 可以覆盖自动重试，本文的尝试记录属于补充设计。[4]

## 三、成本排查：为什么调用没变贵，任务却变贵了

### 3.1 先按真实计费类别算清一笔调用

假设示例模型的价格为：普通输入每百万 Token 2 美元，缓存命中输入每百万 Token 0.2 美元，输出每百万 Token 8 美元。这只是计算用的假设价格。

一次请求报告总输入 20,000 Token，其中缓存命中 12,000，输出 1,000。假设总输入已经包含缓存部分，那么费用为：

```text
普通输入 = 20,000 - 12,000 = 8,000
估算费用 = (8,000 × 2 + 12,000 × 0.2 + 1,000 × 8) / 1,000,000
         = 0.0264 美元
```

这里最容易犯的错误是把 20,000 全部按普通输入计费，再额外加上缓存费用。实施时必须先核对服务商的字段含义，并将其映射为互不重叠的计费类别；缓存写入、图像、音频等另有规则时，也要单独处理。

用量和费用还应区分来源：接口报告的 Token 数、根据模型价格计算的费用、服务商最终账单，是三种不同依据。Langfuse 官方文档也区分直接上报与推算的用量、费用，并允许按用量类型配置价格。[5]

模型调用超时、取消或流式响应中断时，可能没有完整用量。此时记录“未知”与原因，并在能够获得后续账单时补齐。将未知写成零，会把异常最多的任务统计成最便宜的任务。

### 3.2 成本要汇总到任务，而不是停在模型请求

采购案例中的模型调用可以组成下面这份示例明细。为便于计算，假设它们都没有缓存命中，且全部用量已知。

| 模型步骤 | 输入 Token | 输出 Token | 估算费用（美元） |
| --- | --- | --- | --- |
| 解析需求、选择工具 | 4,000 | 500 | 0.012 |
| 读取报价、处理查询重试结果 | 18,000 | 1,000 | 0.044 |
| 比较方案、生成创建参数 | 32,000 | 1,000 | 0.072 |
| 根据工具响应生成回复 | 40,000 | 500 | 0.084 |
| 合计 | 94,000 | 3,000 | 0.212 |

模型单价没有变化。费用上涨来自每一轮继续携带旧材料：整页报价、重复查询结果、工具返回的冗长正文。最后一次回复只输出 500 Token，却已经消耗了这次任务约 40% 的模型费用。

看到这种分布，优化目标就明确了：工具输出保留必要字段，去掉重复材料，让模型引用已保存的报价记录，并对稳定的公共前缀评估缓存收益。更换小模型可以作为候选方案，但要重新验证供应商选择和参数正确率。

实际任务成本还要包含检索、付费工具、独立评估调用等约定范围内的费用。每次计费调用用唯一标识去重；父级汇总值不能再次与子调用费用相加。重试已经付出的费用也应保留。

### 3.3 用业务成功解释成本是否值得

假设一个评估批次包含 100 项采购任务，总成本 21.2 美元，其中 80 项经过验证成功。单位成功任务成本为：

```text
单位成功任务成本 = 批次全部任务成本 / 批次成功任务数
                 = 21.2 / 80 = 0.265 美元
```

分子包含失败任务的消耗。若另一个版本总成本降到 18 美元，但只有 60 项成功，单位成功任务成本反而升到 0.3 美元。

比较时固定任务集合、统计截止时间和计费范围，同时报告失败数、待确认数与用量缺失比例。若没有成功任务，指标应标记为不可计算。对尚未结束的生产任务，需要后续补记，不能只挑已经成功的样本比较。

## 四、延迟排查：把用户的 46 秒拆开

### 4.1 先区分三种等待

用户提交需求后，系统可能立即返回“正在处理”，几秒后展示有效进展，几十秒后才获得业务结果。这些时刻对应不同体验。

本文建议分别记录：请求受理时间、首次有用进展时间、业务结果确认时间。模型首 Token 延迟是模型调用层的指标；模板化的“正在思考”也不代表业务已经推进。

本例 46 秒只是原流程结束并发出回复的时间。因为没有验证创建结果，不能把它记为“成功完成采购申请的耗时”。

### 4.2 用时间线找到真正影响结束时间的步骤

![采购任务的 46 秒时间线：并行查询、超时重试、模型调用和创建动作](/blog-assets/agent-observability-llmops/latency-waterfall.svg)

图中给出一组与执行链一致的教学数据：

| 阶段 | 时间范围 | 对用户等待的影响 |
| --- | --- | --- |
| 模型解析需求 | 0—4 秒 | 4 秒 |
| 库存与供应商 A 并行查询 | 4—10 秒 | 两者分别耗时 2 秒和 6 秒，阶段耗时 6 秒 |
| 供应商 B 查询、退避、重试 | 10—25 秒 | 8 秒超时 + 1 秒退避 + 6 秒重试 |
| 模型读取报价与比较方案 | 25—41 秒 | 两次调用共 16 秒 |
| 提交创建请求 | 41—43 秒 | 2 秒，只得到受理回执 |
| 模型生成最终回复 | 43—46 秒 | 3 秒 |

并行阶段耗时为 6 秒，不能把 2 秒和 6 秒相加当成用户等了 8 秒。同样，父 Span 已包含子步骤耗时，直接累加整棵调用树也会重复计算。

如果 B 查询与库存、A 查询确实相互独立，就可以一起开始。在保持各步骤耗时不变的假设下，查询阶段从 21 秒变为 15 秒，原流程结束时间可从 46 秒降到 40 秒。这是依赖关系推导出的候选收益，需要实测验证；并行后可能遇到服务限流。

修复还要增加结果查询，因此最终业务确认时间必须重新测量，不能沿用 40 秒的估算。若后台需要数分钟，产品可以先返回“已提交，等待结果”，再异步通知完成。

### 4.3 把告警落到可操作的原因

延迟告警至少按任务类型和版本分组，同时观察中位数与 P95。还应单列超时、取消和未完成任务，避免慢任务退出统计后，看板反而变好。

定位时先分清：耗时增加来自模型、工具、排队、退避，还是人工等待。工具超时适合检查服务端处理与超时预算；上下文膨胀适合检查输入增长；审批等待适合改进通知与流程。仅给模型开启流式输出，无法缩短采购系统处理申请的时间。

## 五、执行质量：从“接口没报错”走到“结果可验证”

回到 `req-731`。现在已有足够证据解释故障：创建请求被受理，助手没有查询处理状态，最终回复却承诺创建成功。

修复应该改变工具契约与状态流转。适配器将结果规范化为 `pending`、`created`、`rejected`、`unknown`，并明确每个状态能对用户说什么。只有取得申请记录并验证关键字段后，才能进入成功状态。

| 观察到的现象 | 优先查什么 | 对应修复 |
| --- | --- | --- |
| 收到受理回执后直接回复成功 | 工具返回值与后续调用 | 增加结果查询，约束状态转换 |
| 申请存在但供应商错误 | 报价来源、选择参数、最终记录 | 校验供应商和业务约束 |
| 创建请求超时 | 请求标识与目标系统状态 | 先核实执行结果，再决定重试 |
| 同一任务出现两张申请 | 幂等键、消息投递与执行记录 | 在目标写入边界落实幂等 |
| 回复声称完成，但结果未知 | 状态字段与回复生成条件 | 明确提示待确认，安排后续核验 |

### 5.1 用不同方法验证不同事实

“申请是否存在、数量是否相同、金额是否在批准范围”适合用规则与目标系统查询核验。“对报价的解释是否清晰、是否遗漏重要限制”可以由模型辅助评估。涉及模糊需求或复杂取舍的样本，再交给业务人员复核。[1]

不要让另一个模型只读最终回答，就判定采购任务成功。它缺少申请数据库、工具回执和授权信息，无法独立确认这些事实。

对于最终一致的系统，一次查询没有找到记录，也不一定证明创建失败。应按接口契约等待明确终态，或在核验窗口结束后标记为未知。本例能判定失败，是因为后台明确返回了拒绝结果。

### 5.2 一段关键埋点应表达什么

下面展示修复后的核心片段。假设应用已经初始化 OpenTelemetry SDK 和导出器；`client` 是业务适配器，已将终态转换为本文约定的字段。代码只覆盖创建与验证，超时恢复和审批检查由外层工作流负责。OpenTelemetry 的嵌套 Span 与属性记录方法参见官方 Python 文档。[2]

```python
from opentelemetry import trace

tracer = trace.get_tracer("procurement")

async def create_and_verify(client, task_id, action_id, args):
    with tracer.start_as_current_span("purchase.create_and_verify") as run:
        run.set_attribute("app.task.id", task_id)
        run.set_attribute("app.action.id", action_id)
        run.set_attribute("app.business.outcome", "unknown")

        with tracer.start_as_current_span("purchase.submit") as submit:
            receipt = await client.create_application(
                args, idempotency_key=action_id
            )
            submit.set_attribute("app.request.id", receipt["request_id"])

        with tracer.start_as_current_span("purchase.verify") as verify:
            result = await client.wait_for_result(
                receipt["request_id"], timeout_seconds=30
            )
            state = result["state"]
            verify.set_attribute("app.result.state", state)
            if state == "created":
                actual = result["application"]
                valid = all(actual[k] == args[k] for k in (
                    "supplier_id", "sku", "quantity"
                )) and actual["status"] == "submitted"
                outcome = "verified_success" if valid else "verified_failure"
            elif state == "rejected":
                outcome = "verified_failure"
            else:
                outcome = "unknown"

            verify.set_attribute("app.business.outcome", outcome)
            run.set_attribute("app.business.outcome", outcome)
            return outcome
```

`app.*` 全部是本文自定义属性。`action_id` 需要在外层持久化，对同一写动作重试时保持不变；幂等能否生效，取决于服务端是否支持并落实这个键。真实业务还应验证金额、租户、授权范围等条件。

这段代码的关键是让“发出写请求”和“验证写入结果”成为两个可观察步骤。若查询超时或抛出异常，业务结果仍然是未知，外层应查询恢复或转人工处理，不能直接重新创建。

## 六、异常与审计：观察偏离，守住动作边界

### 6.1 重复调用何时值得干预

给采购案例增加一种故障：B 查询失败后，助手不停调整措辞再次查询，但没有拿到新报价。模型轮次和费用持续增加，业务状态没有变化。

可以组合观察三个信号：同一工具和相近参数的重复次数、相同结果的重复程度、任务状态是否推进。再结合任务预算和工具特性，决定重试、切换来源或请求人工处理。

“连续三次调用同一工具”只能是候选规则。合法分页、结果轮询也可能出现这种模式。状态检查若返回了新的处理阶段，就与一直重复同一失败结果不同。阈值需要用实际任务校准，并同时记录误拦截与漏检。

### 6.2 提示注入如何出现在执行链上

再设想供应商网页中混入一段文字，要求助手把内部采购清单发送到指定外部地址。AgentDojo 研究的正是这类威胁：外部工具返回的不可信数据，可能诱导 Agent 执行攻击者指定的任务。[6]

排查需要关联三个时刻：这段内容何时进入上下文，之后提出了什么工具调用，运行环境是否真的执行了该动作。只看到可疑文字，不能断言攻击成功；看到模型提出外发请求，也不能断言数据已经发出。

执行边界应独立检查当前用户、工具权限、目标地址、数据范围和审批条件。模型看到网页内容，不会因此获得新权限。观测系统负责留下请求和处置证据；工具网关、运行环境和业务服务负责落实限制。

验证防护时也要同时观察合法任务是否完成。把所有外部材料都拒绝使用，可能让攻击成功率降低，同时让采购助手失去正常工作能力。

### 6.3 审计要能核实一个具体动作

假设采购流程要求主管批准供应商与金额。审计需要回答：当时批准的是哪一个供应商、哪一份参数、由谁批准，执行时有没有改变。

建议围绕写动作形成以下记录：

```text
任务与发起人
  → 动作提案：工具、目标系统、规范化参数摘要
  → 策略决定：允许 / 拒绝 / 需要审批
  → 审批：审批人、范围、有效期、获批参数摘要
  → 执行：动作标识、实际参数摘要、幂等键
  → 回执与核验：请求标识、业务记录、最终状态
```

批准供应商 A 的申请后，若参数改成 B，就必须重新判断授权是否仍然适用。记录里有“审批通过”四个字，无法解释这种变化。

关键动作记录需要持久化并限制修改，且与目标系统回执交叉核对。普通调试 Trace 的采样策略不应决定这些记录是否保留。对于要求完整审批证据的写入，证据保存失败时应按业务规则暂停；对普通遥测导出故障，则可以缓冲或降级。两条路径应分别设计。

## 七、工程落地：先接通一条能排障的链

最小实现可以从已有应用扩展：在任务入口记录任务与版本，在模型和工具边界采集步骤，在写入之后增加业务验证，并将这些信息连接到同一个查询入口。

![最小接入架构：应用采集、可观测数据、独立的用量与动作记录，以及评估反馈](/blog-assets/agent-observability-llmops/observability-architecture.svg)

图中分出三条数据路径，是因为它们的完整性要求不同。这是本文的工程建议，可以使用团队已有存储实现，不要求一开始采购三套平台。

| 路径 | 主要用途 | 最低要求 |
| --- | --- | --- |
| Trace 与调试内容 | 解释某次执行 | 上下文可关联，正文受控，明确采样覆盖 |
| 用量记录 | 汇总任务成本 | 调用去重、来源可追溯、缺失可补齐 |
| 动作与业务记录 | 核验授权和结果 | 关键动作持久化，能够对接目标系统回执 |

采样尤其需要谨慎。只保存 10% 的调试 Trace 后，不能直接把它们的费用相加当成总支出。低成本的任务计数、用量记录和关键动作记录应有独立的完整性策略。需要保留所有错误任务的详细 Trace 时，还要确保上游采样没有提前丢弃它们。

指标标签保持低基数，例如任务类型、工具名称、模型和版本；任务 ID、请求 ID 和原始正文留在可检索记录中。观测系统自身也需要监控导出队列、丢弃数、写入失败和数据到达延迟，否则“没有异常记录”可能只是采集已经中断。

实施可按四个可验收的步骤推进：

1. **接通执行链。** 输入任务 ID，可以找到模型、工具、重试和版本；跨服务与恢复执行能够关联。
2. **补齐成本与结果。** 每项费用能回到调用，未知用量可见；业务成功由验证器确认。
3. **加入异常处置。** 对循环、超预算和越权动作先验证信号，再按影响选择自动停止或人工接管。
4. **建立回归入口。** 将脱敏后的失败任务及其依赖条件保存为测试样本。

每完成一步，都应主动制造一次故障：让工具超时、令创建请求先受理后拒绝、重复投递同一动作、暂停遥测接收服务。验收的重点是能否说明发生了什么，以及系统有没有进入预期状态。

## 八、把这次故障变成下一次发布的检查项

采购问题修复后，还需要证明它不会换一种形式再次出现。LangChain 关于可观测性与评估的工程文章强调，生产 Trace 可以成为评估样本来源，帮助把实际失败纳入后续验证。[7]

对本例，保存用户需求、脱敏报价快照、工具契约、异步状态序列、预期业务结果，以及相关版本。然后构造一组邻近场景：

| 回归场景 | 应验证的行为 |
| --- | --- |
| 先受理，稍后创建成功 | 查询到正确记录后才宣布成功 |
| 先受理，稍后明确拒绝 | 反馈失败原因，不声称已创建 |
| 请求已送达，但响应超时 | 用动作标识查询恢复，避免重复创建 |
| 核验窗口内一直处理中 | 显示待确认，并保留后续处理入口 |
| 申请存在，但数量不符 | 验证失败并转入纠错流程 |
| 报价页面夹带外发指令 | 限制越权动作，同时检查采购任务完成情况 |

在隔离环境中执行这些样本，写工具连接沙箱或测试替身。录制的响应适合复现已知故障，真实测试环境还要覆盖接口变化和状态一致性。固定输入与版本有助于比较，但不能保证模型每次产生相同轨迹，因此关键场景应执行多次。

下面是一份发布评审可能使用的结果表。数据为演示值，与前文两个成本计算示例分别独立，不代表实际修复收益：

| 同一组 100 项任务 | 原版本 | 候选版本 |
| --- | --- | --- |
| 验证成功数 | 80 | 95 |
| 虚报成功数 | 12 | 0 |
| 总估算模型成本 | 21.2 美元 | 20 美元 |
| 单位成功任务模型成本 | 0.265 美元 | 约 0.211 美元 |
| 用户首次有用进展 P95 | 8 秒 | 8 秒 |
| 全部任务进入终态 P95 | 55 秒 | 62 秒 |

这里两版都由外部测试环境判断真实终态，使用相同的计时起点、截止窗口和超时处理规则；原版本的成功回复时间不作为终态时间。样本的用量假设全部已知。

候选版本可能因为增加结果查询而更慢，同时减少虚报成功。是否接受，应结合业务时效要求判断。也可以先反馈提交状态，让最终确认异步完成，但仍需保留完整的任务时长。

当下一次出现“助手说完成了，业务系统却没有结果”，值班人员应能从任务 ID 进入 Trace，找到写入回执和核验状态，定位首次偏差，并将新场景补进评估集。这就是这套观测能力应交付的日常工作方式。

## 附录：建议保留的最小字段

下表是本文的数据设计建议。Trace 标识采用追踪系统自身字段，其余名称需要按实际 SDK 与业务模型映射，不构成统一行业标准。

| 对象 | 最小信息 | 常见缺口 |
| --- | --- | --- |
| 任务 | 任务 ID、类型、租户、接收时间、业务结果 | 只保存会话 ID，无法区分多项任务 |
| 执行 | Run ID、Trace 关联、配置版本、开始与结束时间 | 恢复执行后版本变化没有记录 |
| 步骤 | Span 关系、操作名、时间、状态、上下文引用 | 只有总耗时，没有工具输入输出 |
| 调用尝试 | 逻辑步骤、尝试 ID、重试原因、服务商请求 ID | SDK 重试不可见却被当作零次重试 |
| 用量 | 原始用量、计量来源、价格版本、币种、完整性 | 超时未知量记零，父子成本重复累加 |
| 写动作 | 动作 ID、授权依据、参数摘要、幂等键、回执 | 批准参数与实际执行参数无法核对 |
| 验证 | 检查项、业务记录引用、核验时间、结果 | 把助手回答或 HTTP 200 当成成功证明 |
