用户提交一个采购需求，智能体检索供应商、比较报价、发起审批，最后回复“处理完成”。接口没有报错，但采购单实际没有创建；模型调用发生了多次重试，成本明显上升；一个外部网页还诱导智能体把内部资料发送到陌生地址。

这类问题需要同时回答四个问题：钱花在哪里，时间耗在哪里，执行经过哪些步骤，以及哪些行为偏离了授权与任务目标。模型服务的成功率、应用日志和最终回答评分各自只能解释一部分。

**建立智能体可观测体系，就是把一次业务任务连接到可计量的资源消耗、可还原的执行过程、可核验的业务结果和可追责的动作证据。** 本文将它放在 LLMOps 的运营闭环中讨论：运行时采集数据，监控发现问题，审计还原事实，评估验证修复，再把改进送回发布流程。

本文按“建立智能体可观测体系”理解题意，面向工程实施。研究与规范检索日期为 2026 年 10 月 22 日。文中的采购场景、价格、阈值、数据结构和排期都是设计示例，不代表本仓库已实现相关平台，也不是任何服务商的实际报价。

## 一、从论文得到设计依据

以下材料回答不同层次的问题。论文用于支持设计方向；具体字段、告警阈值、账本结构和处置流程是本文提出的工程方案，不能直接视为论文已经验证的结论。

| 资料 | 研究或规范重点 | 对本文设计的启发 | 使用边界 |
| --- | --- | --- | --- |
| AgentOps: Enabling Observability of LLM Agents，2024 [1] | 通过工具映射研究，整理智能体生命周期中需要追踪的产物与数据 | 关联任务、模型、工具、配置和运行结果 | 分类框架不等于可直接部署的监控平台 |
| AgentSight: System-Level Observability for AI Agents Using eBPF，2025 [2] | 将模型交互语义与系统层行为关联 | 对命令执行、文件和网络访问补充系统侧证据 | 环境适配、采集权限和关联准确性需要独立验证 |
| AgentTrace: A Structured Logging Framework for Agent System Observability，2026 [3] | 从操作、认知和上下文三个层面组织运行时日志 | 记录动作、显式决策摘要及上下文来源 | 显式摘要不能证明模型内部真实推理过程 |

这些材料共同支持一种分层思路：生命周期元数据帮助比较版本，执行轨迹帮助定位问题，系统与业务回执帮助核实动作，评估集帮助检验改进。[1][2][3][4][5]

其中 AgentTrace 存在同名研究，本文特指 arXiv:2602.10133 的结构化日志论文；AgentOps 在本文参考文献中指论文，而非对同名商业产品能力的背书。

## 二、先定义观测对象和成功标准

采购任务的技术执行过程可能是：接收需求、检索合同、调用模型、查询库存、发起审批、写入 ERP、验证订单。每一步都可能成功，而任务仍然失败。例如，ERP 接口返回成功，但写入了错误供应商。

因此，建议将任务状态拆成三个独立字段：

| 字段 | 回答的问题 | 示例值 |
| --- | --- | --- |
| `execution_status` | 程序是否完成执行 | running、completed、failed、cancelled |
| `business_outcome` | 业务目标是否满足 | pending、verified_success、verified_failure、unknown |
| `policy_outcome` | 是否符合动作策略 | allowed、blocked、review_required、violation |

这三个字段都是本文建议的业务字段。HTTP 200 只能作为通信结果；模型生成“已完成”只能作为输出内容；最终业务成功应由可信系统回执、约束校验或人工复核确认。

任务还需要一组稳定标识：

| 标识 | 生命周期与用途 |
| --- | --- |
| `task_id` | 一次业务意图，可跨重试、审批等待和进程重启 |
| `run_id` | 一次具体运行，人工重新执行可以产生新的运行 |
| `trace_id` | 一段分布式执行轨迹；长任务可能关联多个 Trace |
| `step_id` | 一个逻辑步骤，例如“查询库存” |
| `attempt_id` | 一次实际尝试，用于区分重试与成本 |
| `action_id` | 一项可能产生外部影响的业务动作 |
| `event_id` | 一条持久化事件，用于去重和审计 |

任务是否成功、请求是否失败、是否发生违规都应能够分别统计。被正确拦截的越权请求属于策略正常工作；它不应自动计为基础设施故障。安全策略拦截率与实际违规执行率也必须分开。

## 三、总体架构：观测数据和审计证据分别落地

建议把系统划分为以下层次。表中的组件是职责划分，可由现有基础设施承担，无需一开始引入大量新服务。

| 层次 | 主要职责 | 输出 |
| --- | --- | --- |
| 任务入口与运行时 | 分配任务标识、记录配置版本、维护步骤关系 | 任务生命周期事件、根 Span |
| 模型适配层或网关 | 记录每次调用、重试、模型标识、Usage 和时间 | 模型 Span、用量事件 |
| 工具执行层 | 授权检查、执行、回执校验、幂等控制 | 工具 Span、动作审计事件 |
| 遥测采集层 | 统一格式、脱敏、限流、缓冲、导出 | Metrics、Traces、诊断日志 |
| 成本与审计写入层 | 幂等入账、状态更新、可靠持久化 | 用量账本、动作审计账本 |
| 查询与分析层 | 聚合统计、版本比较、规则检测、证据检索 | 看板、告警、审计视图 |
| 运营与评估层 | 分派处置、重现问题、验证修复、发布回归 | 事件工单、测试用例、发布结论 |

其中有两条可靠性要求不同的数据路径：

```text
业务运行时 ──遥测──→ 采集与脱敏 ──→ 指标 / Trace / 诊断日志
     │                                   │
     │                              看板、排障、告警
     │
     └──持久化事件──→ 用量账本 / 动作审计账本 ──→ 对账、审计、证据导出
```

普通诊断遥测可根据预算采样，允许明确计量的降级。成本事件和关键动作审计应采用可靠队列、事务消息或 Outbox 等机制，并通过幂等写入应对重复投递。这里的“全量”是设计目标，必须通过序列核验、积压监控和对账证明覆盖程度，不能由配置项直接推断。

不要让外部动作和一条尽力发送的日志承担原子性保证。对于创建订单这类动作，应先持久化动作意图，携带业务幂等键执行，再记录结果并查询目标系统确认。跨系统无法保证原子提交时，要显式保留 `unknown` 状态并进行恢复对账。

## 四、Token 成本：从调用统计到可对账账本

### 4.1 用量与金额是两个不同事实

Token 用量通常来自服务商响应或后续用量记录；成本还取决于模型、计费类型、缓存规则、服务层级、价格生效时间和合同约定。模型适配器应同时保留供应商原始用量和内部归一化字段，避免不同提供方的同名字段被直接相加。

建议账本至少包含：

| 字段组 | 关键内容 |
| --- | --- |
| 归属 | 租户、业务类型、任务、运行、步骤、尝试 |
| 调用 | 提供方、请求模型、实际响应模型、提供方请求 ID、状态 |
| 用量 | 原始 Usage、归一化 Token 分类、计量来源、数据完整性 |
| 计价 | 价格版本、生效时间、币种、计费单位、计费维度 |
| 金额 | 预计金额、观测用量计算金额、结算金额、调整记录 |
| 关联 | Trace ID、Span ID、网关记录 ID、创建与更新时间 |

对一次调用，先在适配器中建立**互斥的计费类别**，再计算金额。以下只演示一种文本调用的归一化方式：

```text
input_uncached = input_total - input_cache_read - input_cache_write

cost = (
    input_uncached   × price_uncached
  + input_cache_read × price_cache_read
  + input_cache_write× price_cache_write
  + output_billable  × price_output
) / 1,000,000
```

这个公式仅在提供方的 `input_total` 确实包含上述缓存子集，且这些子集互斥时成立。若原始输入字段已经排除了缓存 Token，就不能再次扣减；若缓存写入是额外附加费，也应单列附加费用。推理 Token、音频、图像和批处理计费必须根据实际账单定义映射，不能套用统一文本公式。

### 4.2 用一个例子验证归一化口径

假设某次调用输入 12,000 Token，其中缓存读取 8,000，输出 1,000，没有缓存写入。假设每百万 Token 的普通输入、缓存读取和输出单价分别为 2、0.5 和 8 个货币单位。

```text
普通输入成本 = 4,000 / 1,000,000 × 2   = 0.008
缓存读取成本 = 8,000 / 1,000,000 × 0.5 = 0.004
输出成本     = 1,000 / 1,000,000 × 8   = 0.008
合计                                      0.020
```

如果输出总数已经包含推理 Token，不能再把推理 Token 加入输出总数。这类重复计量经常比公式本身更值得检查。

### 4.3 重试、失败和取消也要记账

一个逻辑模型步骤可能有三次真实请求。每次请求都产生独立的 `attempt_id`，已产生的计费资源都归入任务成本。失败或取消不意味着没有费用；流式连接中断还可能导致客户端拿不到完整 Usage。

此时将用量状态标记为 `unknown` 或 `estimated`，不能写成零。估算用于预算控制，后续根据提供方记录补齐。建议使用下列状态表达证据层次：

```text
estimated → provider_reported → reconciled
```

状态更新不能被当作新增调用重复累加。金额更正可采用版本化记录或明确的调整分录，保留变化原因。

SDK 和网关可能同时观察到同一次调用，应约定一个主记账点。相同请求在两个采集点出现属于重复观察；真实重试属于另一笔消耗。用提供方请求 ID、内部尝试 ID和采集来源共同完成关联。

任务成本等于其归属的原始计费记录之和。父 Span 上的汇总成本仅用于展示，不再与子 Span 相加。多智能体共享一次检索或模型调用时，平台总成本只计一次，业务分摊规则单独定义。

### 4.4 看板指标和预算动作

| 指标 | 计算口径 | 用途 |
| --- | --- | --- |
| 单任务成本 P50/P95 | 按任务聚合全部尝试，再计算分位数 | 发现昂贵长尾 |
| 成功任务单位成本 | 同一已关闭任务批次总成本 / 已验证成功任务数 | 将失败浪费纳入经营效率 |
| 重试成本占比 | 非首次尝试成本 / 总成本 | 判断故障放大 |
| 缓存读取比例 | 缓存读取 Token / 可比较的输入 Token | 分析缓存利用 |
| 未知用量比例 | 用量不完整的实际调用数 / 全部实际调用数 | 衡量账本可信度 |
| 对账差异 | 与供应商相同周期、币种和费用范围比较的差额 | 定位漏报与定价错误 |

“成功任务单位成本”的分母为零时应显示无有效结果。跨日任务要明确按完成批次还是发生日期归属；未关闭任务不能悄悄从成本分子消失。

预算控制可分为调用前预留、调用后修正、接近预算时降级、超预算时停止新增调用。并发分支需要原子预留，否则每个分支单独通过检查仍可能造成总预算超支。对于已经发送且提供方仍在执行的请求，应预留不可取消成本的余量。

## 五、响应延迟：明确用户到底在等什么

一次任务有多个时间终点。首个网络字节、首个有效输出和业务动作完成代表不同体验，不能混在同一个延迟指标中。

| 指标 | 起点与终点 | 需要说明的边界 |
| --- | --- | --- |
| 接口响应延迟 | 服务收到请求到返回响应 | 异步受理接口只代表接收成功 |
| 客户端 TTFT | 发出模型请求到收到首个有效输出片段 | 不是响应头，也不是空白或心跳帧 |
| 流式完成延迟 | 发出模型请求到流结束或中断 | 标明完成、失败与取消状态 |
| 工具延迟 | 发起工具尝试到获得结果 | 与逻辑步骤的多次尝试分开 |
| 任务完成延迟 | 任务受理到业务结果确认 | 明确是否包含人工等待 |
| 人工等待时间 | 请求人工介入到恢复执行 | 单独展示，避免掩盖执行效率 |
| 排队等待时间 | 工作入队到实际开始执行 | 与模型执行和网络耗时区分 |

对只能拿到流式 chunk 的客户端，首个有效 chunk 是可测代理量，并不等于服务端生成第一个 Token 的时刻。类似地，chunk 间隔不等于逐 Token 间隔；不能把一个包含多个 Token 的 chunk 当作一个 Token。

OpenTelemetry 的 GenAI 规范区分客户端操作时长与模型服务端指标。本文核验到的 `gen_ai.client.operation.duration` 可用于客户端操作耗时；`gen_ai.server.time_to_first_token` 和 `gen_ai.server.time_per_output_token` 属于服务端指标。若只能从客户端测量 TTFT，建议使用显式的内部名称并注明测量边界。[6]

流式请求的 Span 应覆盖消费过程，直到完成、取消或异常。SDK 返回流对象并不意味着生成已经完成。取消事件还应记录是谁取消、何时请求取消、提供方是否确认停止。

并行任务的端到端耗时由关键依赖路径决定。比如两个工具并行执行，分别用时 2 秒与 3 秒，汇合阶段约为 3 秒加调度开销。把两个工具耗时相加会得到资源累计时间，不能用它解释用户等待时间。

P95 也不能跨服务直接相加。应该在完整任务样本上计算任务 P95，结合各阶段分布和慢请求 Trace 定位原因。

实践中建议按任务类型、模型版本、工具类别和发布版本观察 P50、P95、P99，并同时展示样本量、超时比例和取消比例。只统计成功完成的样本可能让大量超时后的看板显得更快。

## 六、调用链路：把任务、重试和外部动作关联起来

一次任务的诊断视图可以呈现为：

```text
task: 采购申请
└─ run: 第一次运行
   ├─ retrieve: 合同检索
   ├─ llm step: 生成采购计划
   │  ├─ attempt 1: 超时，用量待补齐
   │  └─ attempt 2: 完成，记录 Usage
   ├─ tool: 查询库存
   ├─ approval: 等待审批，关联审批事件
   ├─ tool: 创建订单，关联 action_id 和幂等键
   └─ verify: 查询订单并验证业务约束
```

这个视图需要由真实上下文传播构建，不能仅靠日志时间接近来猜测父子关系。HTTP 服务之间可传播 W3C `traceparent`、`tracestate`；消息、异步工作流和恢复执行还需要持久化必要的关联标识。[7]

建议按以下规则处理边界：

- 普通调用用父子 Span 表示包含或调用关系。
- 扇出任务保留共同父上下文，汇合时用 Span Link 或业务依赖表表示多输入关系。
- 审批等待和跨天任务使用任务 ID 连接多个执行片段，避免要求一个 Span 连续开放数天。
- 重启恢复创建新的执行片段，保留原任务、步骤及恢复原因。
- 跨租户或不可信入口检查传播策略，不把外部携带的标识当成可信身份。

父子 Span 与 Link 提供关联结构，但不自动证明根因。一次检索结果是否真正影响了后续动作，还需要显式的数据来源、引用关系和动作参数证据。

每次模型和工具调用建议关联以下版本信息：应用版本、Agent 配置版本、提示模板版本、模型响应标识、工具 schema 版本、检索索引版本、权限策略版本。对记忆读取，保留记录 ID 与版本；对检索结果，保留文档 ID、版本、片段引用和访问权限检查结果。

不要默认把完整提示词、所有文档和工具返回内容放入 Span 属性。常规查询可使用摘要、分类、长度和受保护引用；确需保存原文时进入受控内容存储。模型提供的显式计划或决策摘要只能作为观察材料，不能当作隐藏思维过程的完整记录。[3]

## 七、数据契约：公共语义与内部扩展明确分开

OpenTelemetry 的 GenAI 规范已迁移到独立仓库。本次核验的相关指标和属性仍处于开发状态，接入时应固定 schema、SDK 和转换规则版本，并保留迁移测试。[6]

不要因为历史博客中出现过某个字段，就把它视为当前稳定标准。对于 Token 统计，本文建议以内部账本字段形成稳定查询契约，再由适配层映射到选定版本的外部语义。

| 数据 | 标准或内部契约 | 说明 |
| --- | --- | --- |
| 客户端模型调用耗时 | `gen_ai.client.operation.duration` | 本次核验的官方指标，状态为 Development |
| 模型调用输入与输出用量 | `gen_ai.usage.input_tokens`、`gen_ai.usage.output_tokens` | 接入时按锁定版本和提供方映射核验 |
| 操作、提供方、模型 | `gen_ai.operation.name`、`gen_ai.provider.name`、模型相关属性 | 保留请求模型与响应模型的差异 |
| 任务完成耗时 | `app.agent.task.duration` | 本文自定义指标，单位秒 |
| 客户端首个有效输出耗时 | `app.genai.client.first_output.duration` | 本文自定义指标，不冒充服务端 TTFT |
| 成本与用量状态 | `app.cost.*`、`app.usage.status` | 本文自定义，关联价格与账本版本 |
| 动作、策略与证据 | `app.action.*`、`app.policy.*` | 本文自定义审计字段 |

指标标签宜选择有界维度，例如环境、业务类型、受控模型类别、结果类别和错误类别。`task_id`、用户 ID、提示词、完整 URL 和工具参数不应作为常规时序指标标签；它们适合进入索引受控的 Trace、日志或账本。租户维度如果数量很大，也应在分析存储聚合。

## 八、异常行为：从信号检测到可执行处置

异常至少包括运行故障、资源浪费、业务错误和安全偏离。一个慢请求可能是正常复杂任务，一个成功返回的请求也可能完成了越权动作。

| 异常类别 | 可观测信号 | 示例处置 | 容易误判的情况 |
| --- | --- | --- | --- |
| 重复调用或循环 | 相同工具与规范化参数反复出现，业务状态无进展 | 终止新增步骤、转人工或重新规划 | 合法轮询和状态最终一致性 |
| 成本异常 | 任务预计成本超预算，输入长度突增 | 缩减上下文、切换已验证策略、停止新增调用 | 长文档任务本来成本更高 |
| 延迟异常 | 任务 P95 上升、排队增长、工具超时 | 限流、切换依赖、触发超时恢复 | 人工审批时间被混入执行时间 |
| 权限异常 | 资源或动作不在授权集合内 | 执行前拒绝并记录策略决策 | 权限变更尚未同步 |
| 提示注入嫌疑 | 不可信内容要求改变目标或输出受保护数据 | 降低内容信任、约束工具动作、进入复核 | 正常文档中也可能包含命令文本 |
| 数据外发异常 | 敏感数据分类命中且目的地未授权 | 在出口或工具层阻断 | 仅凭关键词可能误伤正常业务 |
| 业务结果不一致 | 回复成功但目标系统不存在对应记录 | 标记失败或未知，查询并恢复 | 目标系统读延迟 |
| 多智能体协作异常 | 责任交接循环、结果冲突、缺失终验 | 设置唯一责任方并进入校验 | 有意设计的辩论或冗余执行 |

AgentDojo 说明提示注入评估需要考虑工具返回的不可信数据及完整任务执行。[4] 工程上应将检测点放在内容进入上下文、动作准备执行、数据离开系统等边界。仅扫描用户输入无法覆盖检索网页、邮件正文和工具返回造成的风险。

AgentSight 提供了系统侧观察思路，可以补充框架之外的进程、文件和网络行为证据。[2] 但系统事件与模型动作的映射仍需验证，不能因为时间相邻就断言因果；其部署也依赖实际操作系统、网络与权限条件。

多智能体异常分类可借鉴 MAST，但必须转换成自己的可测信号，例如交接次数、终验缺失、状态分歧，而不是直接把论文类别当作告警规则。[5]

建议让确定性策略负责不可违反的边界，让统计基线发现异常趋势，让语义评估提供嫌疑与解释。对于高影响动作，语义评估器不能成为唯一授权来源，也不能因为“没有检测到风险”就跳过权限检查。

阈值先在观测模式运行。例如“同工具、同参数五次调用且业务状态未变化”只是初始假设，应根据合法轮询窗口和误报样本校准。检测到循环后，停止新增动作不等于回滚已经执行的操作；补偿必须遵循业务规则。

## 九、审计：证明谁授权了什么，以及实际发生了什么

Trace 用于理解运行过程；审计还需要确认主体、授权、输入版本、动作结果和证据完整性。两者通过任务、动作和事件标识关联，但采用不同的保存策略。

建议每个重要动作记录以下证据链：

```text
用户或系统触发
→ 请求主体与代理身份
→ 目标资源、动作和参数摘要
→ 权限策略版本与决策
→ 必要审批及其约束范围
→ 执行尝试和幂等键
→ 目标系统回执
→ 业务结果验证
→ 异常处置与责任记录
```

审批应绑定具体动作与关键参数的摘要。审批完成后，如果收款方、目标系统或金额等关键参数变化，应重新验证审批适用性。只记录“某人点过同意”不足以证明这次动作获得授权。

证据保存需要同时考虑以下问题：

- **防修改：**限制追加记录之外的更新与删除；若使用哈希链或签名，需要独立保存校验锚点和密钥访问记录。仅在同一数据库中存哈希，无法抵御同时修改正文和哈希的攻击。
- **防缺失：**用序列、动作状态机和目标系统回执核对关键节点是否齐全；一份完整哈希链仍可能缺少根本没有被写入的事件。
- **防越权读取：**按租户、角色和事件范围授权，记录审计查询与导出动作。
- **最小化保存：**默认保留元数据和脱敏摘要，敏感原文进入单独加密存储，并明确用途和保存期限。

对于低熵敏感值，普通哈希可能被枚举反推。需要关联识别时，应考虑受控密钥的 HMAC 或令牌化，同时管理密钥版本和访问权限。

若关键审计写入失败，应按动作风险选择行为：高影响写操作暂停，普通诊断事件可进入缓冲并降级。这个决策应预先配置并经过演练，避免事故时临时选择。

审计能重建可见过程，但通常不能保证再次调用随机模型得到相同输出。复现应分为两类：证据重放使用已保存的输入、工具结果和版本；沙箱重跑重新执行并比较差异。前者验证历史事实，后者检验修复效果。涉及真实外部写操作时，应使用模拟或隔离环境。

## 十、看板、告警与问题处置

建议首先建设四个视图，而不是为每种组件单独制作一套互不关联的面板。

| 视图 | 首要问题 | 核心内容 |
| --- | --- | --- |
| 业务与成本 | 哪类任务值得继续自动化 | 已验证成功率、单位成功成本、人工接管率、预算消耗 |
| 延迟与容量 | 用户等待由哪里造成 | 任务延迟分位数、首个有效输出、排队、工具慢调用 |
| 运行轨迹 | 某次任务为什么失败 | Span、重试、版本、上下文引用、业务校验结果 |
| 行为与审计 | 是否发生未授权动作 | 策略拒绝、违规执行、外发事件、审批与证据完整性 |

每个告警都应包含影响范围、触发窗口、样本量、发布版本、关联任务与 Trace、处置责任方和第一步操作。没有后续动作的告警通常只会增加噪声。

服务目标需要根据业务类型制定。交互式问答可重点约束首个有效输出与完成时间；采购工作流则需要分别约束受理、自动执行和最终业务完成。若使用“95% 合格任务在 30 秒内完成”这样的目标，必须同时定义合格任务范围、观察窗口以及失败、超时和用户取消如何计入。这里的数字仅示意格式。

统计异常应与同类任务比较。发布后成本增加，可能是提示模板变长，也可能是流量转向复杂业务；通过任务类型、模型版本、输入长度和缓存情况分层，才能判断是否由发布导致。

问题处置可以形成固定流程：

1. 先确认业务结果与影响范围，判断是否需要暂停高风险动作。
2. 检查成本账本、任务耗时与 Trace，找出异常开始的位置。
3. 核对该位置的上下文来源、版本变化、策略决策和工具回执。
4. 形成故障分类及修复假设，选择降级、回滚、策略调整或业务恢复。
5. 将脱敏案例加入回归集，验证业务成功率、安全性和成本延迟变化。
6. 记录结论、责任人与验证证据，再决定是否恢复发布。

评估本身也消耗资源。线上语义评估调用应使用独立费用类别，并与用户请求成本区分展示；否则评估比例提高可能被误认为业务 Agent 变贵。

## 十一、采样、可靠性和观测成本

### 11.1 按用途制定采样策略

正常诊断 Trace 可以抽样，错误、慢请求和高成本任务可以配置更高保留率。Tail sampling 能在观察到结果后决定是否保留，但依赖缓冲容量、决策窗口和跨节点汇聚；不能承诺总能保留所有异常任务。

成本账本和重要审计事件不依赖 Trace 是否保留。需要全量汇总的成本、调用次数和任务结果，应从独立的可靠事件流或未采样聚合路径生成，不能直接从抽样 Trace 求和。

如果需要依靠抽样估算总体统计，应保存采样概率并评估偏差。对成本结算和关键动作审计，统计估算不能代替原始记录。

### 11.2 观测系统也需要被观测

最少监控遥测丢弃量、导出失败率、队列积压、账本更新延迟、未知 Usage 比例、缺失回执、孤立 Span、采集开销和存储增长。重复事件、乱序到达及晚到数据都应有明确处理规则。

持续时间尽可能在同一进程内用单调时钟测量；跨主机事件时间保留时钟偏差的不确定性。仅凭两个机器的墙钟时间差，不能精确推导网络或排队耗时。

计算总体平台成本时，可以定义：

```text
平台成本 = 模型费用 + 工具与计算费用
         + 遥测采集传输费用 + 存储查询费用 + 在线评估费用
```

这要求为原始内容设置独立容量限额和保存期限。把所有提示词、检索结果和中间输出永久保存，会同时增加存储成本和数据暴露面。

具体选型先验证职责适配：指标系统是否能聚合直方图，Trace 系统是否支持所需链接与查询，分析存储是否支持幂等更新，审计存储是否满足不可随意修改和访问控制要求。产品清单不能代替这些验收问题。

## 十二、分阶段落地和验收

### 12.1 第一阶段：建立可信数据底座

选一个边界明确的任务接入，不从所有 Agent 同时开始。完成任务与尝试标识、模型与工具埋点、流式完成计时、版本关联、Token 归一化及基本脱敏。

验收时给定一组已知调用，确认账本实际调用数量与真实请求一致；人为注入一次重试，检查两次尝试均存在；中断流式请求，确认状态为取消或异常，缺失 Usage 显示未知。

### 12.2 第二阶段：打通看板、对账和诊断

建立任务成本、延迟、业务成功率及失败分类看板。接入价格版本和账单对账，验证异步队列、并发分支和恢复执行的关联关系。

验收时从一个失败任务进入 Trace，再关联到用量记录、工具回执与版本配置。对指定测试集合，能说明每一项费用差异和每一个缺失字段，而非只展示整体平均值。

### 12.3 第三阶段：接入异常控制与审计

在工具动作边界接入权限、预算、审批与幂等控制，保存动作意图、策略决策、执行回执和业务验证结果。重复调用、提示注入和异常外发规则先运行观察模式，再根据误报结果决定自动处置范围。

验收时分别测试未授权动作、审批后改参数、重复消息、执行结果未知和审计存储故障，确认系统进入预先设计的状态。

### 12.4 第四阶段：形成持续评估闭环

把真实故障与安全案例脱敏后加入回归集，在隔离环境执行版本对比。比较任务成功率、攻击成功率、误拦截率、单位成功成本与延迟变化。人工复核一部分评估结果，并保存评估模型、规则和数据集版本。

AgentDojo 可作为提示注入评估方法的参考；多智能体失败分类可帮助组织样本。[4][5] 企业自己的工具权限、审批约束和写操作后果仍需要专门用例。

| 验证场景 | 注入方式 | 必须观察到的结果 |
| --- | --- | --- |
| 模型调用重试 | 首次请求超时后重试 | 两次尝试关联同一步骤，用量未知状态可补齐 |
| 流式取消 | 输出过程中由客户端取消 | 记录已等待时间、取消来源和用量完整性 |
| 并行执行 | 两个工具同时运行 | 任务耗时与关键路径一致，不把重叠时间重复解释为等待 |
| 提示注入 | 在检索文档放入改变任务的指令 | 保留来源，验证授权边界，分别统计攻击与合法任务结果 |
| 重复投递 | 同一动作消息发送两次 | 审计可见重复投递，业务写入符合幂等约束 |
| 未知执行结果 | 工具已接收后断开连接 | 标记未知，查询目标系统后再决定是否重试 |
| 采集器故障 | 停止遥测接收服务 | 业务按策略降级，账本与关键审计路径按设计恢复 |
| 价格变化 | 在价格切换点前后产生调用 | 分别引用对应价格版本，可重算但保留历史依据 |
| 审批范围变化 | 修改获批动作的关键参数 | 拒绝沿用不适用的审批并记录原因 |
| 审计证据缺失 | 删除测试环境中的关键事件 | 序列或状态核验发现缺口，不能显示为完整证据链 |

排期可根据团队已有基础设施安排，但每一阶段都应以这些可验证结果交付。真正可运营的体系，需要让成本账本可信、延迟口径一致、链路关联可用、关键动作证据完整，并使发现的问题能够进入修复和验证流程。
