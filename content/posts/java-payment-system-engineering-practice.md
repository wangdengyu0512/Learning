用户点击支付后，渠道已经扣款，支付服务却因为网络超时没有收到响应。几秒后，渠道回调到达；与此同时，用户重新提交请求，定时任务也开始查询这笔订单。

现在有三个入口试图修改同一笔交易。如果只在接口上加一个锁，锁过期以后怎么办？如果本地状态已经更新，通知订单服务的消息却没有发出去怎么办？如果用户看到超时后申请退款，又该依据哪个状态判断可退金额？

这些问题构成了支付后端的核心：**为一笔交易建立明确的业务约束，让重复执行不会产生重复资金效果，让结果未知的操作有办法查清，让每次状态变更都能追溯。**

本文以高级 Java 工程师参与支付模块设计与后端实现的职责为背景，使用 Spring Boot、Spring Cloud、MyBatis、Redis、RocketMQ 和 MySQL 组织一套参考方案。内容适合技术学习、设计评审和项目经验整理。

资料核对日期为 2026 年 10 月 21 日。Java 示例采用 Java 21 可表达的语法；数据库讨论以 MySQL 8.x InnoDB 为背景，RocketMQ 机制参考官方 5.0 文档。Spring Boot 与 Spring Cloud 的具体版本需要使用项目实际兼容组合。正文中的资料编号对应文末官方来源。

## 一、从业务约束出发，明确支付系统负责什么

### 1. 支付系统中的四种“完成”

业务方说“订单完成了”，技术实现必须先区分完成的是哪一步。

| 业务概念 | 表达的事实 | 示例 |
| --- | --- | --- |
| 业务订单完成 | 商品或服务进入约定的业务阶段 | 订单已确认，可进入履约 |
| 支付成功 | 渠道确认这笔支付取得成功结果 | 支付单记录渠道交易号与成功时间 |
| 账务入账 | 内部账务系统记录了资金或债权债务变化 | 生成记账凭证与账务分录 |
| 结算完成 | 按结算规则完成资金划付或结算确认 | 渠道完成某个结算批次 |

本文的支付模块负责支付指令、渠道交互、支付结果及退款状态。账务系统和结算系统作为协作边界：如果项目确实包含它们，需要进一步展开记账规则、账户体系和清结算流程，不能把“支付成功”直接写成“全部资金流程结束”。

设计评审时，先回答：哪个系统有权确认渠道支付结果，哪个系统决定业务订单能否履约，哪个系统记录账务事实？责任明确以后，再决定服务怎么拆。

### 2. 五条需要一直成立的业务约束

本参考方案把以下规则视为业务不变量，后面的 SQL、事务和补偿都围绕它们设计。

1. 同一业务支付意图重复提交时，返回同一个支付单；重复请求不能悄悄改变金额、币种或收款主体。
2. 同一支付单从非成功状态转为成功时，只产生一个稳定标识的支付成功事件。
3. 已确认的支付成功不能被旧的“处理中”通知覆盖；退款通过独立退款单表达。
4. 已成功退款金额与正在申请、处理或待确认的退款占用金额之和，不超过可退款的实付金额。
5. 每一笔长时间未终结的交易，都有下一次核查时间、处理责任和升级入口。

这些约束是本文选择的业务契约。若渠道支持多次扣款、预授权、分次捕获、撤销或争议处理，应建立相应模型，不能硬塞进一个简单支付状态字段。

### 3. 逻辑边界先于服务数量

建议先形成交易入口、渠道适配、支付结果处理、事件投递、退款和对账六个逻辑模块。是否拆成独立服务，由团队规模、容量差异、变更频率和故障隔离要求决定。

| 技术 | 在本文方案中的职责 | 需要额外设计的部分 |
| --- | --- | --- |
| Spring Boot | 承载接口、业务编排和应用配置 | 业务模型、异常语义和事务边界 |
| Spring Cloud | 支撑服务间调用及治理集成 | 超时预算、隔离粒度和降级行为 |
| MyBatis | 映射明确的 SQL 和返回结果 | 索引、锁范围、影响行数与事务配置 |
| MySQL | 保存支付事实、业务约束和恢复依据 | 唯一约束、并发更新与高可用验证 |
| Redis | 缓存、限流及可恢复的临时协调 | 缓存失效策略与锁失效后的约束 |
| RocketMQ | 传递支付领域事件 | 数据库与发送一致性、消费幂等及补偿 |

## 二、用一笔支付串起业务闭环

### 1. 正常链路和未知结果分支

先把请求到结果的关系写清楚。下面的步骤代表本文采用的处理顺序，其中事务 A 和事务 B 都是本地数据库事务。

| 步骤 | 执行方 | 处理内容与持久化结果 |
| --- | --- | --- |
| 1 | 业务系统 → 支付服务 | 提交业务支付意图、金额、币种和请求标识 |
| 2 | 支付服务，事务 A | 校验重复请求，创建支付单并提交 |
| 3 | 支付服务 → 渠道 | 使用固定渠道请求号发起支付；不持有步骤 2 的数据库事务 |
| 4 | 支付服务 | 解析渠道响应；无法确认结果时保存核查任务 |
| 5 | 渠道 → 通知入口 | 验签、校验业务字段，持久化待处理通知或同步处理结果 |
| 6 | 结果处理器，事务 B | 条件更新支付状态，并插入 Outbox 事件 |
| 7 | Outbox 投递器 → RocketMQ | 使用稳定 eventId 投递支付成功事件 |
| 8 | 订单服务 | 在本地事务内幂等处理事件，推进业务订单 |
| 9 | 查单与对账任务 | 主动核查未终结订单，发现并处理跨系统差异 |

调用渠道超时，只能说明当前调用方没有按时取得完整结果。此时，本方案把交易留在待确认范围，后续使用原渠道请求号查单；是否允许重发原请求，以及多久以后允许发起新的支付尝试，应遵守对应渠道协议。

### 2. 业务订单、支付单与支付尝试分开建模

一个业务订单可能先选择渠道 A，失败后改用渠道 B。建议根据实际产品规则建立以下关系：

| 对象 | 作用 | 建议标识 |
| --- | --- | --- |
| 业务订单 | 承载商品、服务与履约信息 | businessOrderNo |
| 支付单 | 承载一次确定金额和币种的支付意图 | paymentId、merchantPaymentNo |
| 支付尝试 | 记录一次渠道路由与请求 | attemptId、channelRequestNo |
| 渠道流水 | 记录渠道提供的交易标识与结果 | channelAccountId、channelTxnNo |
| 退款单 | 承载一次独立的退款意图 | refundId、merchantRefundNo |

本文后续 SQL 为便于讲解，采用一张支付单绑定一个有效渠道尝试的简化模型。如果需要自动切换渠道，必须另建尝试记录，并规定前一次尝试结果未知时的处理规则。

特别要区分**返回给调用方的响应去重**和**长期有效的业务唯一性**。即使接口幂等缓存已经过期，也不能重新创建同一个业务支付意图；长期约束需要落在持久化模型里。

### 3. 支付状态机要表达“尚未查清”

| 当前状态 | 接收到的事实 | 允许的处理 |
| --- | --- | --- |
| CREATED | 已开始渠道请求 | 转为 PROCESSING，记录请求身份 |
| CREATED / PROCESSING / UNKNOWN | 收到可信的成功证据 | 转为 SUCCESS，并产生成功事件 |
| PROCESSING | 网络超时、进程中断或响应不可解析 | 转为 UNKNOWN 或保持处理中，登记查单任务 |
| PROCESSING / UNKNOWN | 渠道确认该次尝试最终失败 | 转为 FAILED |
| CREATED / PROCESSING / UNKNOWN | 渠道确认关闭，且符合关闭协议 | 转为 CLOSED |
| SUCCESS | 收到重复成功或旧的处理中通知 | 校验一致性，返回已处理，不回退 |
| FAILED / CLOSED | 收到与终态冲突的成功证据 | 进入异常核实流程，查询渠道并保留证据 |

`UNKNOWN` 表示本地认知不完整，不表示渠道一定还在处理。它也可以建模成独立的结果确认字段，只要查询与补偿能够识别。

状态码不能简单按数字大小取最大值。成功与关闭、成功与退款之间的关系，需要依据业务事实判断。终态冲突也不能直接丢弃：一旦确认本地终态判断错误，应通过受审计的纠正流程修复，并保证成功事件只产生一次。

Stripe 官方文档明确说明异步事件可能重复、送达顺序也不保证，因此处理器应依据业务对象及事实推进状态，不能依赖收到通知的先后顺序。[8]

## 三、数据库模型：把正确性变成可以检查的约束

### 1. 金额、唯一键与核心字段

金额字段应携带币种和明确的计量单位。本文用最小货币单位的整数表示金额；不同币种的位数按业务及渠道规则处理。如果业务采用 `DECIMAL` 与 Java `BigDecimal`，应统一精度、舍入方式和输入转换规则，不经过二进制浮点数中转。

下面的 DDL 是教学用简化结构，省略完整审计列、渠道报文和退款明细。`CHECK` 的执行能力需核对实际版本；下例要求 MySQL 8.0.16 或更新版本。[15]

```sql
CREATE TABLE payment_order (
    id BIGINT NOT NULL,
    merchant_id BIGINT NOT NULL,
    merchant_payment_no VARCHAR(64)
        CHARACTER SET ascii COLLATE ascii_bin NOT NULL,
    request_hash BINARY(32) NOT NULL,
    amount_minor BIGINT NOT NULL,
    currency CHAR(3) CHARACTER SET ascii COLLATE ascii_bin NOT NULL,
    status VARCHAR(20) NOT NULL,
    channel_account_id BIGINT NOT NULL,
    channel_request_no VARCHAR(64)
        CHARACTER SET ascii COLLATE ascii_bin NOT NULL,
    channel_txn_no VARCHAR(128)
        CHARACTER SET ascii COLLATE ascii_bin NULL,
    refund_reserved_minor BIGINT NOT NULL DEFAULT 0,
    refunded_minor BIGINT NOT NULL DEFAULT 0,
    version BIGINT NOT NULL DEFAULT 0,
    next_query_at DATETIME(3) NULL,
    paid_at DATETIME(3) NULL,
    created_at DATETIME(3) NOT NULL,
    updated_at DATETIME(3) NOT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uk_merchant_payment (merchant_id, merchant_payment_no),
    UNIQUE KEY uk_channel_request (channel_account_id, channel_request_no),
    UNIQUE KEY uk_channel_transaction (channel_account_id, channel_txn_no),
    KEY idx_query_due (status, next_query_at, id),
    CONSTRAINT ck_amount_positive CHECK (amount_minor > 0),
    CONSTRAINT ck_refund_range CHECK (
        refund_reserved_minor >= 0
        AND refunded_minor >= 0
        AND refunded_minor <= amount_minor
        AND refund_reserved_minor <= amount_minor - refunded_minor
    )
) ENGINE = InnoDB;
```

业务单号是否大小写敏感，必须有统一约定。这里显式使用二进制排序规则表达精确匹配；如果标识允许非 ASCII 字符，需要替换字段字符集并保留正确的比较语义。

`channel_txn_no` 在请求初期可以为空。唯一范围应按渠道协议确定；本文假设同一渠道账户内交易号唯一。若渠道的唯一范围不同，应调整复合键。不要把所有渠道交易号都假设为全球唯一。

`request_hash` 来自规范化的关键业务字段，例如收款主体、业务支付号、金额和币种。同一幂等键遇到不同参数时返回明确的业务冲突，不能返回旧结果掩盖调用错误。Stripe 的幂等接口也会校验同键参数，但它的具体缓存时限和返回规则属于渠道协议，不能直接当成本系统统一规范。[9]

### 2. 用条件更新推进状态

下面的 SQL 由 MyBatis 执行。调用前已经完成渠道身份、金额、币种和订单归属校验。

```sql
UPDATE payment_order
SET status = 'SUCCESS',
    channel_txn_no = #{channelTxnNo},
    paid_at = #{paidAt},
    updated_at = CURRENT_TIMESTAMP(3),
    next_query_at = NULL,
    version = version + 1
WHERE id = #{paymentId}
  AND merchant_id = #{merchantId}
  AND channel_account_id = #{channelAccountId}
  AND channel_request_no = #{channelRequestNo}
  AND amount_minor = #{amountMinor}
  AND currency = #{currency}
  AND status IN ('CREATED', 'PROCESSING', 'UNKNOWN');
```

影响行数为 1，意味着当前事务赢得了这次状态转换，可以继续写入成功事件。影响行数为 0，需要重新读取并分类：是合法重复、记录不存在、参数不一致，还是终态冲突？这些情况的处理方式不同。

读取重复处理结果时，本方案使用同一主库事务内的当前读，例如按主键 `SELECT ... FOR UPDATE`，避免拿到旧快照或延迟副本的数据后误判。是否使用锁读，也应结合实际事务隔离级别与 SQL 顺序验证。[7]

### 3. 索引既影响耗时，也影响并发行为

接口按商户支付号查单，需要对应的联合唯一索引；查单任务按状态和下次查询时间扫描，需要与扫描条件相匹配的索引。不要只根据“某个字段出现过”决定建索引。

慢 SQL 排查时，本方案同时检查扫描行数、锁等待时间、事务持续时间和访问路径。死锁处理采用统一的加锁顺序、尽量短的事务，以及有界的事务级重试；数据库死锁发生后，应用需要能够重新执行被回滚的事务。[6]

重试对象必须明确。数据库中的幂等状态更新可以重新执行，事务外的渠道扣款不能因为某条 SQL 死锁就换一个请求号再调用一次。

## 四、Spring 事务：把边界放在可以兑现的地方

### 1. 本地事务包住事实变更与恢复依据

支付结果处理器需要原子地完成两件事：将支付单推进为成功，以及写入稍后需要发送的领域事件。两者使用同一 MySQL 实例、同一事务管理器和对应数据源。

MyBatis-Spring 官方文档指出，事务管理器使用的数据源必须与 `SqlSessionFactoryBean` 的数据源一致；注入的 Mapper 在 Spring 事务之外执行时，操作会自动提交。因此，不能仅凭项目里出现了 `@Transactional` 就认为所有 SQL 都处于同一事务。[2]

下面给出服务层伪代码。`VerifiedPaymentResult` 只允许由验签后的通知解析器，或经过认证的主动查单适配器创建；内部还要执行业务字段校验。

```java
@Service
public class PaymentResultService {
    private final PaymentMapper paymentMapper;
    private final OutboxMapper outboxMapper;

    public PaymentResultService(PaymentMapper paymentMapper,
                                OutboxMapper outboxMapper) {
        this.paymentMapper = paymentMapper;
        this.outboxMapper = outboxMapper;
    }

    @Transactional(rollbackFor = Exception.class)
    public ApplyResult applySuccess(VerifiedPaymentResult result) {
        int changed = paymentMapper.markSuccess(result);

        if (changed == 0) {
            PaymentOrder existing = paymentMapper.selectForUpdate(
                result.paymentId());

            // 校验商户、渠道账户、请求号、金额、币种及渠道交易号。
            if (existing != null && existing.matchesSameSuccess(result)) {
                return ApplyResult.ALREADY_APPLIED;
            }
            // 抛出异常使事务回滚，由入口或持久化任务进入核实流程。
            throw new PaymentResultConflictException(result.paymentId());
        }

        String eventId = "payment:" + result.paymentId() + ":succeeded:v1";
        outboxMapper.insert(PaymentSucceededEvent.from(eventId, result));
        return ApplyResult.APPLIED;
    }
}
```

所有将支付单推进为成功的入口，都调用这一个事务服务。回调、查单和对账只负责提供证据来源，不能各自复制一套“更新状态再发消息”的逻辑。

上述代码还依赖一条不变量：成功状态与 Outbox 事件从该机制启用起就始终原子产生。存量数据迁移或历史缺陷可能破坏这个前提，应额外检查“成功支付单却没有对应事件”的情况。

### 2. 事务不生效的排查顺序

Spring 默认代理模式拦截经过代理的调用，同一个对象内的自调用不会触发被调用方法上的新事务拦截。默认回滚规则通常针对运行时异常与 `Error`；受检异常是否回滚应依据显式规则及项目全局配置判断。[1]

因此，排查时依次确认：方法是否经过 Spring 代理、事务管理器是否正确、数据源是否一致、异常是否被吞掉，以及 SQL 是否转移到了另一个线程。

对于本文的命令式 JDBC/MyBatis 用法，异步线程不能被当作当前本地事务的自然延伸。若在事务里提交一个异步任务，应考虑原事务尚未提交、最终回滚或进程退出时，任务会看到什么数据。可靠异步工作使用持久化任务或事件表达。

### 3. 渠道调用放在短事务之外

支付发起采用三个阶段：

1. 在短事务里创建支付单，分配固定渠道请求号，并提交。
2. 在事务外调用渠道，设置连接、读取和整体调用预算。
3. 在新的短事务里保存已确认的结果，或登记下一次查单时间。

这样仍然可能在任意阶段发生进程退出，但数据库保留了恢复身份。查单任务知道应查询哪个渠道请求，而数据库连接和行锁也不会持续等待整个外部网络调用。

本地事务、TCC 和 Saga 各有作用范围。要把渠道接口纳入 TCC，需要渠道提供符合要求的预留、确认和取消语义；要做 Saga，需要定义可执行的业务补偿。实际项目中，不应把“扣款后退款”理解成数据库回滚，退款有自己的状态和失败处理。

## 五、数据库与 RocketMQ：让已提交事实最终发得出去

### 1. 先列出两种执行顺序的失败窗口

| 执行方式 | 中断位置 | 可能留下的结果 |
| --- | --- | --- |
| 先提交数据库，再发消息 | 提交后进程退出 | 支付成功，业务系统未得到通知 |
| 先发消息，再提交数据库 | 消息已可见但本地提交失败 | 下游收到本地不存在的成功事实 |
| 在数据库事务里同步发消息 | 消息已成功，数据库随后回滚 | 数据库事务无法回滚已经发布的消息 |
| 只注册提交后回调 | 数据库已提交，回调执行前进程退出 | 缺少可恢复的发送记录 |

本方案选择 Outbox 作为贯穿示例，并单独说明 RocketMQ 事务消息的适用边界。两种机制需要根据实际项目取舍，没必要对同一业务事件无目的地叠加两条投递链路。

### 2. Outbox 保存“还有一件事必须做”

支付状态和 Outbox 行在同一个本地事务里提交。Outbox 记录至少包含：稳定 `event_id`、事件类型、业务主键、负载与版本、投递状态、尝试次数、下次执行时间、租约到期时间、领取令牌和最近错误。

`event_id` 设置唯一约束。事件标识来自业务事实；同一事件被重新投递时，不能重新生成标识，否则下游无法判断重复。

| 投递器步骤 | 设计要点 |
| --- | --- |
| 领取到期任务 | 在短事务里领取有限批次，记录新的 claimToken 与 leaseUntil |
| 提交领取事务 | 释放数据库锁，然后进行网络发送 |
| 发送 RocketMQ 消息 | 使用原 eventId，按实际 SDK 判断发送结果 |
| 标记已发送 | 条件包含任务 ID 与 claimToken，防止旧执行者覆盖新执行者 |
| 失败或结果未知 | 记录重试时间，或等待租约过期重新领取 |

如果发送成功后进程退出，任务可能再次发送。因此这里追求的是在服务恢复、重试与持久化策略满足条件时的最终投递，并允许重复；不能宣称端到端恰好执行一次。

MySQL 的 `SKIP LOCKED` 可用于多个工作者领取队列式任务，但它跳过被锁定记录，返回的结果不是完整一致视图。因此，本方案只把它用于任务分配，不拿它判断全部交易是否已经对平。[7]

### 3. RocketMQ 事务消息的范围

RocketMQ 事务消息大致包含发送半消息、执行本地事务、提交或回滚消息，以及状态不确定时由 Broker 发起回查。回查需要依赖可持久化查询的本地事务结果；应用内存里的标记不足以支持进程重启后的判断。[3]

设计回查表时，应记录与消息关联的唯一事务身份、明确状态与必要业务证据。查询不到记录时，也要区分事务尚未完成、读取失败与已经确定回滚，按实际 SDK 协议返回相应结果。回查次数和保留期限需要结合部署配置安排兜底核查。

**事务消息建立的是生产端本地事务与消息可见性的协调关系。** 下游订单更新、账务入账、渠道扣款仍有自己的事务与恢复流程；不能把它描述为一次覆盖所有系统的全局提交。[3]

### 4. 消费幂等与业务变更一起提交

订单服务使用一张消费记录表，唯一键为 `(consumer_name, event_id)`。使用消费方名称，是为了允许不同业务消费者分别处理同一事件。

消费流程可实现为：

1. 开启本地事务，插入消费记录。
2. 执行订单状态校验和业务更新。
3. 同一事务提交后，才向 Broker 确认消费成功。

如果插入发生重复键异常，先结束当前尝试，再在新事务中核实已经提交的消费记录与业务结果；只对预期的消费记录唯一键冲突执行重复处理逻辑。不要笼统吞掉所有 `DuplicateKeyException`，也不要在事务已经标记回滚后继续提交后续业务。

如果步骤 2 失败，消费记录应随事务一起回滚；如果步骤 3 提交后确认丢失，下一次投递会命中已有记录。涉及外部调用时，再通过本地 Outbox 或该外部系统的幂等接口衔接。

RocketMQ 的重试策略与消费类型、客户端版本和配置相关。重试耗尽的消息需要死信处理入口、告警和受控重放，不能把“开启自动重试”当作完整恢复机制。[4]

## 六、幂等与 Redis：把临时协调和业务约束配合起来

### 1. 不同入口需要不同的幂等身份

| 场景 | 幂等身份示例 | 持久化约束 | 重复执行时的行为 |
| --- | --- | --- | --- |
| 创建支付 | 商户 + 业务支付号 | 支付单联合唯一键 + 参数摘要 | 返回同单；参数不同则拒绝 |
| 接收通知 | 渠道账户 + 通知事件号 | 通知收件箱唯一键 | 返回该通知的处理结果 |
| 确认支付成功 | 支付单 + 成功事实 | 状态条件更新 + 成功事件唯一键 | 校验事实一致，不再次产生事件 |
| 消费消息 | 消费方 + eventId | 消费记录唯一键 | 已提交则确认成功 |
| 发起退款 | 商户 + 业务退款号 | 退款单唯一键 + 额度条件更新 | 返回同一退款单 |
| 执行补偿 | 业务对象 + 补偿类型 + 事实版本 | 补偿任务唯一键 | 读取已有进度并继续 |

通知事件号去重与业务状态幂等需要同时存在。一个业务对象可能通过多个不同事件表达相同状态，所以事件 ID 不重复也不代表业务效果应重复执行。[8]

业务事务尚未完成时，同键请求可以返回“处理中”及查询入口。不要为了避免并发，让调用线程无限等待另一个执行者。

### 2. Redis 锁用来降低竞争，数据库承接业务不变量

临时锁可以使用带随机持有者标识和到期时间的原子写入。释放时需要原子地比较持有者标识，再删除；直接删除锁可能误删另一个执行者已经取得的锁。[5]

但即使解锁逻辑正确，执行者也可能暂停到锁已过期。Redis 官方文档还说明，简单依赖异步复制和主从切换可能破坏互斥保证。[5]

因此，在本文方案中，Redis 锁用于减少重复查单或降低热点争用，最终能否修改支付状态，仍由数据库条件、唯一约束和事务决定。对需要阻止过期执行者写入的外部资源，可进一步设计递增的 fencing token，但必须由被保护资源实际校验令牌，单独生成一个数字没有效果。

同样不能先在 Redis 标记“消息已处理”，随后才更新数据库。一旦数据库失败，后续重试就可能被错误拦截。消费去重与业务提交采用上一章的同库事务。

### 3. 缓存策略跟着业务后果选择

渠道展示配置、非关键订单摘要和短期查询结果，可以按容忍延迟的程度缓存。支付成功确认、退款额度计算和人工修复审核，需要读取本方案定义的权威记录。

热点查询可以通过本地短缓存、请求合并与有限时间的旧值回退降低压力；缓存失效后应限制回源并发。若对不存在订单使用短期空值缓存，还需考虑新订单创建时如何失效，避免把合法新记录误判为不存在。

Redis 故障时，缓存降级、限流降级和任务协调降级应分别设计。对于代价较高的写入入口，可采用更保守的本地并发限制；不要让所有实例同时把缓存流量无上限地转到 MySQL。

## 七、退款设计：给在途退款预留额度

### 1. 先解决并发退款的额度竞争

假设一笔订单实付 100 元，同时收到两个各退 80 元的申请。如果两个请求都先读取“已退款 0 元”，再分别创建退款，就可能超过可退额度。

本方案在支付记录上维护两个金额：`refund_reserved_minor` 表示在途占用，`refunded_minor` 表示已成功退款。退款申请在一个事务里创建唯一退款单，并执行额度占用；任何一步失败都回滚。

```sql
UPDATE payment_order
SET refund_reserved_minor = refund_reserved_minor + #{refundAmountMinor},
    version = version + 1,
    updated_at = CURRENT_TIMESTAMP(3)
WHERE id = #{paymentId}
  AND merchant_id = #{merchantId}
  AND status = 'SUCCESS'
  AND currency = #{currency}
  AND #{refundAmountMinor} > 0
  AND #{refundAmountMinor} <= amount_minor
      - refunded_minor - refund_reserved_minor;
```

调用方必须检查影响行数。金额非法、额度不足、币种不符与订单不存在，应有可区分的业务结果。

退款单创建、额度占用和后续发送任务在同一个事务里落地，渠道退款在事务外执行。为降低死锁概率，同类流程对支付单、退款单和任务记录采用一致的访问顺序。

### 2. 退款终态决定何时释放占用

| 退款结果 | 本方案的金额变化 |
| --- | --- |
| 渠道确认成功 | 将该笔金额从 reserved 转到 refunded |
| 渠道确认最终失败，且不会继续执行 | 释放该笔 reserved |
| 超时、处理中或结果未知 | 保留 reserved，继续查单 |
| 重复成功通知 | 根据退款状态条件更新，不再次移动金额 |

退款状态转换、支付单金额变更和退款事件写入必须在同一事务中完成。只有赢得退款终态转换的执行者，才更新对应金额。

Stripe 文档中的退款就存在待处理和失败情形，说明提交退款请求与最终退款成功需要分开表达。具体失败后是否允许重试、是否要新建退款身份，应遵循所接渠道协议。[10]

支付成功状态保持原支付事实，页面上的“部分退款”或“全部退款”可从退款信息派生。遇到拒付、撤销、争议或结算调整时，需要另外的业务事件和账务处理，不能只改一个支付状态覆盖历史。

## 八、主动查单、对账与补偿：让未知结果最终有结论

### 1. 三种机制各自发现不同问题

| 机制 | 主要触发条件 | 要回答的问题 |
| --- | --- | --- |
| 主动查单 | 请求超时、通知缺失、长时间处理中 | 这一笔渠道交易现在到底是什么状态？ |
| 业务补偿 | 已确认事实尚未传递或应用 | 已成功支付为何没有更新订单或发出事件？ |
| 批量对账 | 获取特定业务日期或批次的渠道记录 | 本地与渠道是否有遗漏、金额或状态差异？ |

查单可以缩短未知状态的持续时间，对账提供更全面的核验入口。两者共用结果处理器，但调度频率、成本和发现问题的范围不同。

对账任务也要先明确对象：交易明细、退款明细、手续费、结算金额和到账金额的口径并不相同。本文着重讨论支付与退款交易对账；如果负责资金对账，应继续定义渠道结算单、银行流水与内部账务的匹配关系。

### 2. 查单任务需要可靠调度身份

每个任务保存业务对象、渠道请求号、执行次数、下次执行时间、最近结果、租约与领取令牌。指数退避和抖动用来分散重试压力，具体间隔应依据渠道限额和业务恢复目标确定。

扫描到期任务时使用稳定排序、有限批次和与查询匹配的索引；大范围扫描可以采用游标分页。多实例领取采用数据库条件更新或短事务锁定，任务领取和网络查询分开进行。

进程退出后，租约允许其他实例重新领取。旧执行者返回时，更新任务记录需要校验领取令牌。即使发生重复查单，支付结果处理器也应只产生一次有效业务变更。

本方案把查询失败、渠道返回处理中、查到最终结果分别记录，避免将三类事件都折叠成“重试失败”。超过自动处理期限的交易转入可见的异常队列，保留查询入口和人工责任人。

### 3. 对账先验证输入，再比较数据

一次可恢复的对账批次建议按以下顺序组织：

1. 确定渠道账户、账单类型、业务日期、时区和截止口径。
2. 拉取账单并验证来源、完整性以及渠道提供的校验信息。
3. 将原始文件身份、校验值、获取时间和解析版本保存下来。
4. 将明细装载到批次隔离的暂存区，执行重复行、必填字段和金额校验。
5. 按渠道交易号、商户支付号等协议确定的键匹配本地记录。
6. 生成稳定的差异记录，再进入核实与修复。

文件不存在、下载不完整或解析失败，不能被解释为“渠道当天没有交易”。跨日支付、延迟出账、退款时间差和手续费口径，也需要与真实差错区分。

| 差异类型 | 首先核实 | 本方案的处理方向 |
| --- | --- | --- |
| 渠道成功，本地未成功 | 渠道账户、原请求号、金额和可信查询结果 | 调用统一结果处理器补齐状态与事件 |
| 本地成功，渠道记录缺失 | 账单是否完整、日期口径是否一致、查单结果 | 保留原事实，进入异常调查 |
| 两侧金额或币种不一致 | 原请求、回调、账单与映射关系 | 阻止自动金额覆盖，进入受控处理 |
| 本地退款未知，渠道退款成功 | 退款身份、金额及原支付关联 | 幂等推进退款状态和金额 |
| 支付成功，业务订单未更新 | Outbox、投递状态、消费记录和订单状态 | 重投原事件或执行受控业务补偿 |

“发现差异”不等于“可以修改数据”。每一种自动补偿都需要明确证据、前置条件和允许的状态变化；无法满足条件时保留差异，进入人工核实。

### 4. 补偿本身也需要验证

建议为补偿任务建立 `PENDING → RUNNING → SUCCEEDED` 的主流程，并增加等待重试、待人工处理等分支。任务执行成功后重新读取业务结果，必要时再次核对渠道，避免仅凭调用返回成功就关闭差异。

对人工修复，保存操作人、关联差异、证据、变更前后状态和复核结果。涉及资金事实的修复应通过受约束的业务命令执行；确需直接修复历史数据时，应有可审阅的脚本、执行范围和核对记录。

## 九、高并发治理：沿着完整链路分配容量

### 1. 先定义负载，再讨论 QPS

支付下单、渠道回调、状态查询、退款和对账消耗的资源不同。压测报告应分开描述它们的流量占比、数据分布、热点比例和外部依赖行为。

| 指标 | 建议统计口径 |
| --- | --- |
| 请求吞吐 | 按接口、渠道和业务类型区分 |
| 响应时间 | 同时记录 P50、P95、P99，以及超时比例 |
| 支付结果 | 分开统计接口错误、渠道拒绝、结果未知和最终成功 |
| 消息延迟 | 同时观察积压条数与最老未处理事件年龄 |
| 数据库压力 | 连接获取等待、慢 SQL、锁等待和事务持续时间 |
| 恢复能力 | 故障解除后恢复正常处理速度及清空积压所需时间 |

例如，采用稳定负载的容量近似，若到达速率为每秒 1,000 个请求，平均在某阶段停留 0.2 秒，则该阶段平均约有 200 个在途请求。**这是容量算例，不是项目实测，也不是线程池应固定配置为 200 的结论。** 排队、阻塞比例、突发流量和尾部延迟仍需要通过实验确认。

### 2. Java 线程池要有明确的过载行为

`ThreadPoolExecutor` 使用无界队列时，核心线程繁忙后通常继续排队，`maximumPoolSize` 不会按很多人的预期发挥扩容作用。`CallerRunsPolicy` 会让提交任务的线程亲自执行任务，因而可能把耗时传回接口线程。[11]

支付服务建议按业务代价区分执行资源：渠道调用、通知处理、对账和补偿不共享一个无限容量的线程池。每个池都定义有限队列、拒绝策略、执行超时和排队监控。

对于需要可靠完成的任务，不使用静默丢弃策略。进入持久化任务系统之前过载，可以明确拒绝并允许调用方安全重试；任务已经持久化，则由消费者和调度器控制处理速度。

并发工具也要放回边界内理解。Java 内存模型规定了 `volatile` 等同步动作的可见性关系，但复合读改写仍要用适当同步机制；同一 JVM 内的锁或原子变量也无法协调多个服务实例。[13]

例如，`volatile boolean processing` 无法表达跨实例的支付幂等，内存中的 `AtomicLong` 也不能作为多个实例共同维护的可退额度。局部计数和缓存可以使用并发工具，资金业务约束仍落在共享的权威数据模型上。

### 3. 超时、重试、熔断和隔离一起设计

对一条“入口 → 支付服务 → 渠道”的调用链，先定义入口可接受的总时间，再分配连接建立、读取响应、排队和重试预算。一次客户端超时并不能证明渠道已经停止处理，所以超时后的业务结果进入待确认流程。

重试必须有责任层。假设三层调用分别允许最多三次尝试，组合后底层可能承受最多 27 次调用；这是放大效应的算例。因此，需要控制总尝试次数、总时长、退避和可重试错误范围。

对支付写请求，重试沿用固定身份并遵守渠道协议。查询操作也应限频，防止渠道故障期间查单任务同时涌入。

Spring Cloud Circuit Breaker 的 Resilience4j 集成提供线程池与信号量隔离配置，可按渠道定义并发上限。[12] 但降级返回值要由业务决定：尚未受理可以明确拒绝，已创建支付单可以返回处理中和查询入口，不能因为熔断就伪造支付成功。

### 4. 数据库、缓存和消息要按瓶颈顺序调整

数据库连接池满时，先区分连接真的不足，还是连接被长事务、慢 SQL、锁等待或外部调用占用。单纯增加连接数可能把更多并发压到数据库；本方案通过缩短持有时间与限制入口并发，先让系统回到可控状态。

缓存优化要核实命中率与热点分布，消息优化要核实单条处理耗时和下游容量。若消费者都在等待同一个热点订单行锁，扩容实例并不会消除这个串行点。

对大规模历史数据，先评估合理索引、冷热分离和归档。采用分库分表之前，还要明确业务唯一性、渠道流水查询、跨分片对账和路由变更如何保持正确。容量方案应写出新增复杂度，不能只写吞吐收益。

### 5. JVM 排查需要证据链

当接口延迟升高时，可以按“流量变化 → 排队 → 线程状态 → 数据库与渠道耗时 → GC 与内存”的顺序建立假设，再用观测结果排除。

| 现象 | 优先收集的证据 | 待验证的方向 |
| --- | --- | --- |
| CPU 高且吞吐下降 | 线程栈、采样记录、热点方法 | 自旋、序列化、密集计算或重试 |
| CPU 不高但请求堆积 | 工作线程状态、队列、连接等待 | 锁等待、网络等待或资源耗尽 |
| GC 频繁且堆占用攀升 | GC 日志、分配速率、对象分布 | 队列积压、大批次对象或生命周期过长 |
| 少数请求延迟极高 | 调用链分段耗时、长暂停记录 | 热点竞争、慢查询或渠道尾延迟 |

Java 官方 `jcmd` 文档提供线程、JFR 和堆诊断命令，并标明部分操作的影响等级。例如堆转储可能产生较高影响，需要先确认磁盘空间、实例负载和采集窗口。[14]

优化后的验证必须回到相同负载和数据规模，比较延迟分位数、错误率及资金一致性结果。只展示平均响应时间降低，无法说明尾部超时和异常恢复是否得到改善。

## 十、交易安全与可观测性：能够判断一笔交易发生了什么

### 1. 验签以后还要校验业务事实

通知入口先按渠道协议验证签名与身份，再检查商户、渠道账户、原支付请求号、金额、币种和事件类型。不同渠道的签名原文和时间校验方式不同，应分别封装在适配器中。

以 Stripe 为例，官方文档要求使用未被修改的原始请求体进行签名验证。[8] 实际接入时，应防止过滤器、日志组件或 JSON 重序列化改变验签输入。

接收通知后，可以同步完成一个短事务，也可以先将验证后的通知可靠写入收件箱再快速应答。本文选择后者时，应保证应答发生在持久化成功之后，并具备异步处理失败的重试与告警；仅进入内存队列就应答，无法支持进程退出后的恢复。

重复通知返回什么状态码、什么报文，由渠道协议决定。验签失败、字段冲突和内部处理失败分别记录，避免用统一“成功”响应掩盖未保存的有效通知。

### 2. 日志围绕业务身份关联

建议结构化记录以下字段：`traceId`、商户、业务订单号、支付单号、渠道请求号、渠道交易号、退款单号、事件 ID 和补偿任务 ID。一次请求的 TraceId 不能替代跨日、跨重试仍稳定的业务身份。

支付日志保存必要证据及报文摘要，敏感字段按项目要求脱敏。签名密钥、访问令牌和完整敏感支付信息不进入普通业务日志。渠道适配器需要支持密钥标识与轮换，以便定位旧证书或旧密钥造成的通知验证失败。

### 3. 技术告警与业务告警相互验证

| 告警信号 | 可能影响 | 建议关联检查 |
| --- | --- | --- |
| UNKNOWN 交易数量或年龄上升 | 用户等待结果，业务迟迟不能推进 | 渠道超时、查单成功率及任务积压 |
| Outbox 最老未投递事件变老 | 支付事实未传递给订单系统 | 投递错误、租约回收与 Broker 状态 |
| 消费死信增加 | 业务状态更新停滞 | 错误分类、数据兼容性与依赖故障 |
| 回调验签失败突增 | 有效通知无法应用或存在异常请求 | 密钥轮换、原文读取和渠道配置 |
| 对账差异或未解决金额增加 | 存在数据遗漏或资金事实冲突 | 账单完整性、时间口径和近期变更 |

告警阈值应按基线、业务时段和影响范围设定。恢复以后还要核对未知交易、积压事件和差异任务是否处理完成，不能只看到接口恢复就结束事故。

## 十一、故障演练：把排查与数据恢复放在同一条线上

以下案例用于演练与设计评审，不能直接当作个人已经处理过的线上事故。

### 1. 渠道支付成功，本地长时间未知

**触发场景：** 渠道完成支付，但同步响应丢失，支付通知又因入口异常未成功保存。

**排查证据：** 从支付单找到原渠道请求号，检查调用超时、通知接收记录与查单任务。通过受认证的渠道查询确认商户、金额和交易状态，避免根据客户端页面或单条非权威日志直接认定支付成功。

**恢复过程：** 由统一结果处理器更新支付单并补齐 Outbox；观察消息投递和订单消费结果。若用户在此期间申请退款，先使支付事实得到确认，再走正常退款流程。

**验证结果：** 同一支付只产生一个成功事件；重复通知与再次查单不会重复推进订单；对应对账差异可以复核关闭。

**长期改进：** 检查通知入口可靠持久化、未知状态告警和查单调度是否存在缺口，并补充响应丢失与通知延迟的故障注入。

### 2. 支付高峰连接池耗尽

**触发场景：** 渠道延迟上升，而应用在数据库事务中持有连接等待渠道，随后接口线程与连接等待同时积压。

**排查证据：** 对齐渠道调用耗时、连接占用时长、活跃事务与线程栈。如果 SQL 执行本身很短，但事务持续时间很长，应继续检查事务中是否夹杂网络调用。

**止损与恢复：** 对异常渠道限制并发，降低非实时补偿任务的处理速率，让已经进入系统的支付继续按固定身份查清结果。恢复后核对所有未终结支付和退款，再验证连接等待是否下降。

**长期改进：** 将渠道调用移出数据库事务，建立短事务与持久化任务边界，按渠道设置隔离资源。容量复测同时观察连接等待、P99 和未知交易持续时间。

### 3. 消息积压与重复消费同时出现

**触发场景：** 订单服务下游变慢，部分消费超时；业务事务已提交的消息由于确认丢失而再次送达。

**排查证据：** 按消费者检查积压年龄、处理耗时、失败原因和消费记录。区分基础设施故障、数据错误和可恢复依赖失败，确认是否有单个问题事件持续阻塞处理。

**恢复过程：** 先缓解下游压力，按其容量调节消费并发；修复错误原因后重放原事件身份。已提交的业务结果由消费幂等识别，尚未提交的业务继续执行。

**验证结果：** 积压年龄回落、死信得到处理，订单状态与支付事实一致；重复投递不会生成重复业务动作。

复盘记录应包括影响范围、时间线、判断依据、止损动作、数据核对、修复责任与验证结果。真正能支撑个人经验的，是当时依据哪些证据做出判断，以及修复后如何证明没有遗漏交易。

## 十二、验证设计与个人工程成果

### 1. 测试断言围绕业务约束

| 场景 | 故障注入或并发方式 | 核心断言 |
| --- | --- | --- |
| 同键重复支付请求 | 多线程与多实例同时提交 | 一张支付单；同键异参明确报错 |
| 回调与查单并发成功 | 两个入口同时应用同一结果 | 一次成功迁移；一个成功事件 |
| 成功后收到旧状态 | 延迟投递处理中通知 | 成功不回退，保留处理记录 |
| 数据库提交后退出 | Outbox 已提交但尚未发送 | 恢复后事件最终发出 |
| 消息发送后退出 | Broker 已接收但未标记发送 | 允许重发，下游业务效果一次 |
| 消费提交后确认丢失 | 重复投递相同 eventId | 不重复修改业务订单 |
| 并发超额退款 | 同时申请超过可用额度的退款 | 成功申请总额不超过可退额度 |
| 退款结果未知 | 渠道超时后继续提交其他退款 | 未确认退款占用不会提前释放 |
| 任务租约到期 | 旧执行者暂停，新执行者领取 | 旧令牌不能覆盖新执行进度 |
| 对账输入不完整 | 截断文件或制造解析错误 | 批次失败，不报告对账一致 |
| 主从切换与数据延迟 | 在隔离测试环境切换依赖 | 不误判重复结果，检查持久化事实 |

这些是后续实现的验证清单，不代表本文已经执行了相应代码测试。真正落地时，数据库锁、事务、唯一键和消息重试需要在实际依赖上验证，单元测试中的内存替身无法完整覆盖这些行为。

### 2. 可靠性还依赖基础设施的持久化配置

应用使用了事务与 Outbox，并不自动保证所有已确认数据在任何故障下都不丢失。评审还应明确 MySQL 日志持久化、复制与故障切换策略，RocketMQ 的存储与复制设置，以及备份恢复和灾难恢复目标。

如果数据库切换丢失了已对外确认的交易，应用层幂等表也可能一起丢失。因此，要把目标 RPO、RTO 与故障演练结果纳入完整方案，并设计渠道查单、账单及审计记录如何帮助重建事实。

性能优化也不能未经评估就放宽持久化保障。应把实际配置、故障窗口和恢复代价写入评审记录，并依据项目目标作出选择。

| 能力方向 | 可补充的真实材料 |
| --- | --- |
