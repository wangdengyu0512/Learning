当一个团队准备建设业务本体时，手中通常不会有一份已经整理好的“本体需求说明书”。真正能够拿到的，往往是一堆来源不同、质量不一、彼此重叠甚至互相矛盾的材料：业务流程说明、数据库建表语句、接口字段、样例数据、制度文档、术语表，以及业务人员临时补充的几句话。

最直接的做法，是先给这些材料分类：数据库走结构转换，业务文档走大模型抽取，样例数据走字段推断。这个方案看起来清晰，却容易在一开始就制造错误边界。

一份需求文档中可能嵌着 SQL，一份 Excel 样例中可能包含字段定义，一段所谓“结果数据”也可能同时表达业务对象、状态枚举和对象关系。材料的文件类型，并不能决定其中每一段内容具有什么建模价值。

本体收集器采用的是另一条路线：**不先问材料属于哪一类，而是先问每一段内容能够证明什么事实。**

这使本体生成从“文件转换”变成了一条证据驱动的语义加工链路：

```text
材料收集
  ↓
文件预解析与原文切片
  ↓
片段角色和证据能力识别
  ↓
单材料语义事实抽取
  ↓
证据门禁与事实降级
  ↓
跨材料合并与冲突处理
  ↓
语义规范化与引用闭合
  ↓
确定性渲染 LinkML 本体
  ↓
结构校验与跨材料语义审计
  ↓
只读预览、人工确认、正式创建
```

这篇文章将沿着这条链路，说明本体收集器如何把混合材料转化为可验证、可追溯、可继续演进的业务本体。

---

## 一、本体收集器收集的不是文件，而是业务证据

“本体收集器”这个名称很容易让人联想到资料上传工具，但它真正收集的并不是文件本身，而是材料中可以支撑本体事实的证据。

用户可以提交三类输入：

- 文本材料，例如业务说明、规则、表结构和补充要求；
- 上传文件，例如 PDF、SQL、JSON、CSV、Markdown、XML、YAML 和 Schema；
- 场景名称，例如“门店库存管理”或“设备维保工单”。

其中，场景名称只负责本体的标题、名称和元数据。它不能证明某个业务对象存在，也不能证明对象具有某个属性。即使用户输入的场景名称与材料内容不完全一致，事实抽取仍然以材料为准。

文本材料按每次提交保留为独立来源。这样做的意义，不只是方便编辑和删除，更重要的是保留证据边界。后续生成报告能够说明某项事实来自哪份材料，而不是把所有文字拼成一段无法追踪来源的长文本。

文件上传后不会立即参与生成，而是先进入预解析阶段。复杂文档需要转换为可分析文本，数据库脚本和结构化文件需要提取有效内容。只有文件全部解析完成，材料规模也没有超过处理上限时，系统才允许开始生成。

这里形成了第一层质量门禁：**无法稳定读取的材料，不进入语义建模。**

---

## 二、不相信文件标签，只判断片段本身

材料进入分析阶段后，会被切分为带有稳定编号的原文片段，例如 `S0001`、`S0002`。后续所有对象、属性、关系和枚举，都必须能够回到这些片段找到依据。

切片之后，系统逐段识别内容角色：

| 片段角色 | 主要含义 | 是否可以直接支持本体事实 |
| --- | --- | --- |
| 业务语义 | 业务对象、职责、流程和关系 | 可以 |
| 结构定义 | 表、字段、Schema、主外键 | 可以 |
| 样例数据 | 实例记录、字段样值 | 有限支持 |
| 术语与规则 | 别名、枚举、约束和业务口径 | 可以 |
| 生成要求 | 用户对生成方式的要求 | 不可以 |
| 无关内容 | 与建模无直接关系的内容 | 不可以 |

同一份文件可以包含多种角色。一份业务方案的前半部分可能描述业务流程，中间附带数据库表，最后又包含几条生成要求。系统不会把整份文件一次性认定为“业务文档”或“数据库文档”，而是让不同片段承担不同作用。

同一个片段也可能同时支持多种事实。例如：

> 每张采购订单由唯一订单编号标识，必须关联一个供应商。

这句话至少可以支持四类事实：

- 存在“采购订单”对象；
- 存在“订单编号”属性；
- 订单编号是稳定标识；
- 采购订单与供应商之间存在关系，并且关系具有必需性。

因此，材料理解并不是简单的文本分类，而是一种片段级的证据能力识别。

---

## 三、先确定“能证明什么”，再抽取“有什么”

完成角色识别后，系统还要判断每个片段能够支持哪些事实类型：

```text
对象 entity
属性 attribute
标识 identifier
数据类型 datatype
必填 required
关系 relation
基数 cardinality
枚举 enum
约束 constraint
```

这一步非常关键，因为同一个词出现在材料中，不代表围绕它的所有约束都已经得到证明。

假设样例数据中连续出现十条订单记录，每条记录都有 `customerId`。这可以支持“订单可能具有客户标识字段”，却不能单独证明：

- 所有订单都必须包含客户标识；
- 客户标识在订单中唯一；
- 没有客户的订单在业务上绝不允许存在；
- 样例中出现的客户类型就是完整枚举。

样例只展示“目前看到了什么”，而必填、唯一和完整枚举表达的是“所有合法情况都必须怎样”。两者具有完全不同的证明强度。

类似地，用户写下“请尽量生成完整的对象关系”只是一条生成要求。它不能成为增加对象和关系的业务证据。否则，大模型会为了满足“完整”而补充常识性概念，最终得到一个看起来丰富、实际上无法追溯的本体。

本体收集器的核心约束可以概括为：

> 只有片段被确认能够支持某类事实时，后续抽取结果才允许产生该类事实。

---

## 四、数据库结构是强证据，但不是业务真相

数据库结构在本体建模中很有价值。它通常可以稳定提供：

- 字段名称和数据类型；
- 主键或候选标识；
- 非空约束；
- 外键和关系端点；
- 部分一对一、一对多关系线索；
- 枚举字段和受限值域。

因此，只要材料中出现可识别的 SQL、图数据库结构或 Schema，即使它被粘贴在普通文本中，系统也会把结构片段拆分出来，按照结构材料处理；剩余的业务描述则继续作为普通语义材料参与建模。

但“结构证据强”不等于“数据库就是本体”。数据库首先服务于存储、事务、查询和历史系统兼容，其中可能存在：

- 为多对多关联设计的中间表；
- 为性能冗余的宽表；
- 只承担技术配置的表；
- 快照表、日志表和历史表；
- 把多个业务概念压在一起的遗留表；
- 把同一个业务对象拆到多个系统中的表。

如果采用“一表一对象、字段全转属性、外键全转关系”的方式，得到的只是数据库模型的另一种表示。

本体收集器采用的原则是：**业务说明决定概念语义，数据库结构补充技术约束。**

例如，订单主表、订单扩展表和订单统计表可能共同描述同一个“订单”对象；订单明细表则可能具有独立业务身份，也可能只应表达订单与商品之间的关联。最终如何建模，需要结合业务材料，而不能只看表名。

---

## 五、每份材料先独立形成语义片段

材料理解完成后，每份材料会独立生成一份语义中间表示。它不是最终 YAML，也不是可直接发布的本体，而是一组经过结构约束的候选业务事实。

语义中间表示主要包含三部分：

```text
entities   业务对象及其属性
relations  对象之间的业务关系
enums      枚举及枚举值
```

每一项事实都必须携带证据。例如，一个“设备”对象需要对象证据，“设备编号”属性需要属性证据，如果设备编号被标记为唯一标识，还需要额外的标识证据。

将材料分开抽取有三个好处。

第一，证据来源清晰。系统可以知道“供应商”对象来自采购流程说明，而 `supplier_id` 的数据类型来自数据库定义。

第二，冲突更容易暴露。如果一份规则文档说订单必须关联供应商，另一份数据库结构却允许供应商字段为空，系统能够在合并时看到两条来源不同的判断。

第三，单份材料失败不会污染其他材料。结构不合法的抽取结果可以单独修复或重试，而不是重新处理全部上下文。

这一阶段还会统一标识命名：对象和关系使用稳定英文标识，字段使用英文属性标识，中文名称作为标题，业务含义作为描述。稳定标识负责机器合并，标题和描述负责业务表达。

---

## 六、证据门禁：宁可降级，也不凭空补齐

大模型擅长补全语义，但本体工程恰恰不能把“合理猜测”当成“已确认事实”。因此，模型完成抽取后，还要经过程序化证据门禁。

主要规则包括：

| 候选事实 | 证据不足时的处理 |
| --- | --- |
| 业务对象 | 删除对象 |
| 对象属性 | 删除属性 |
| 唯一标识 | 取消标识限定 |
| 必填约束 | 取消必填限定 |
| 数据类型 | 降级为字符串 |
| 关系或关系端点 | 删除关系 |
| 关系基数 | 取消基数限定 |
| 枚举引用 | 删除或降级为字符串 |
| 枚举值 | 删除无证据值 |

这里最典型的例子是 ID 字段。许多自动建模工具会默认给每个对象补一个 `id`，因为从软件设计角度看，这似乎总是合理的。但如果业务材料没有出现稳定标识，本体收集器不会自动制造主键。

没有标识的对象仍然可以保留，因为“对象存在”和“对象已经有稳定识别规则”是两件事。系统会产生告警，提示后续补充标识设计，而不是用虚构字段掩盖材料缺口。

证据门禁还会核对引文是否真实存在。模型不能自行改写一句话作为证据，只能引用已经编号的原文片段。引文无法定位时，系统需要修复证据；无法修复，则删除依赖该证据的事实。

这条原则让本体生成从“模型说了什么”变成“材料能够证明什么”。

---

## 七、跨材料合并不是简单覆盖

各份材料通过门禁后，系统开始合并对象、属性、关系和枚举。合并依据是稳定英文标识以及规范化后的语义结构，而不是只比较中文名称是否相似。

不同材料承担的职责并不相同：

| 材料 | 更适合回答的问题 |
| --- | --- |
| 业务说明 | 业务中有哪些概念，它们意味着什么 |
| 普通文档 | 概念如何被解释、使用和约束 |
| 数据材料 | 实际记录中出现了哪些字段和值 |
| Schema | 数据结构、类型和约束如何定义 |
| DDL | 主键、非空、外键等物理结构如何落实 |

当材料互相补充时，合并相对直接。例如，业务说明提出“维修工单”，数据库结构补充 `work_order_no`、创建时间和设备外键，规则文档再补充工单状态枚举。三份材料共同形成一个更完整的对象。

真正困难的是冲突。

假设业务制度规定“一张工单必须关联一台设备”，数据库字段却允许为空。此时不能简单得出“数据库优先”或者“文档优先”。业务制度表达目标规则，数据库表达当前系统状态，两者的冲突本身就是需要治理的信息。

合并逻辑会对结构事实进行裁决，同时记录无法静默解决的问题。字段类型、标识、枚举引用和关系端点等技术事实更依赖结构材料；标题、描述和概念边界则更依赖业务语义材料。

因此，材料优先级不是一张笼统的可信度排行榜，而是针对不同事实类型采用不同证据强度。

---

## 八、规范化：让所有引用真正闭合

跨材料合并完成后，本体还不能直接输出。多份材料独立抽取时，很容易产生悬空引用和命名冲突，例如：

- 对象声明继承一个并不存在的父对象；
- 关系指向已被证据门禁删除的对象；
- 属性引用一个没有成功合并的枚举；
- 同一个对象出现多个标识字段；
- 关系标识与对象标识重名；
- 同一概念因为命名差异被拆成多个对象。

规范化阶段负责关闭这些缺口。

无法闭合的父类引用会被移除，端点不存在的关系不能保留，找不到枚举定义的属性会降级为字符串。多个标识字段需要结合结构来源进行裁决，标识冲突则通过重命名或删除解决。

经过规范化后，结果至少必须保留一个具有证据的业务对象。如果所有对象都因证据不足或引用错误被移除，这次生成就没有形成有效本体，应当明确失败，而不是输出一个空壳文件。

---

## 九、大模型负责理解，程序负责最终渲染

完成合并和规范化后，系统形成 canonical IR，也就是本次生成唯一的标准语义表示。

canonical IR 中保存：

- 本体名称、标题、描述和版本；
- 规范化后的业务对象和属性；
- 对象关系及其方向；
- 枚举及允许值；
- 生成告警和证据统计；
- 本次生成的运行标识。

最终 LinkML YAML 不是由模型自由生成，而是由程序根据 canonical IR 确定性渲染：

```text
业务对象  → classes
对象属性  → attributes
对象关系  → 包含 subject/object 的关系类
业务枚举  → enums 与 permissible_values
```

这种分工很重要。让模型直接生成 YAML，看起来少了一步，却会引入格式漂移、字段遗漏、引用错误和不受支持的 LinkML 能力。确定性渲染则保证相同的 IR 得到稳定结构，也让格式问题能够由程序测试，而不是依赖模型“这次是否写对”。

渲染结果还要经过多层校验：

- 语义中间表示是否合法；
- 对象、关系和枚举引用是否闭合；
- 输出是否符合本体 Profile；
- YAML 是否能够被 LinkML 正确加载。

只有通过这些硬校验的结果，才能进入预览阶段。

## 十、语义审计不是第二次生成

程序能够检查结构，却很难判断业务含义是否完整。例如，系统可以确认关系端点存在，却未必知道“客户提交订单”是否被错误建成了“订单提交客户”；可以确认两个对象标识不同，却未必知道它们其实是同一个概念。

因此，在结构校验之后，还需要一次独立的跨材料语义审计。审计重点包括：

- 核心业务对象或关系是否遗漏；
- 是否存在材料没有支持的事实；
- 两个对象是否表达了同一概念；
- 关系方向和基数是否与材料冲突；
- 不同材料是否给出了互相矛盾的规则；
- 名称和描述是否存在歧义。

审计只输出问题、证据和修改建议，不直接改写本体。这样可以避免审计模型在指出问题的同时又引入新的事实。

审计问题可以按严重程度分为阻断级、复核级和建议级，但它本质上仍是一份辅助决策报告。对于需要业务判断的问题，最终决定权应当留给用户，而不是让模型在后台静默修改。

## 十一、为什么生成和正式创建必须分开

本体生成完成后，结果首先进入只读预览。用户可以检查对象、属性、关系和枚举，同时查看材料理解报告、生成告警和语义审计结果。

此时，本体还不是正式配置。

用户可以继续补充材料、删除错误材料或修改业务说明，然后重新生成。重新生成会以当前全部材料为输入，再次执行能力识别、事实抽取、证据门禁、合并和校验，而不是直接在上一次结果上追加几个字段。

只有用户确认后，系统才会创建正式本体：

```text
重新规范化本体内容
  ↓
校验 Profile 和引用完整性
  ↓
创建首个正式版本
  ↓
保存生成报告和验证信息
  ↓
创建配置元数据
  ↓
设置当前版本与已发布版本
  ↓
同步查询投影并记录历史
```

这些步骤需要在同一事务中完成。任何一步失败，都不能留下“有配置但没有版本”或“版本存在但配置头未更新”的半成品。

生成与创建分离，还建立了一条重要产品边界：**机器负责提出本体草稿，人负责决定它何时成为正式资产。**

## 十二、用一个订单履约场景串起整条链路

假设用户提交了三份材料。

第一份是业务说明：

```text
客户提交订单。每张订单包含若干订单明细，并由一个履约单跟踪发货过程。
```

第二份是数据库结构：

```sql
CREATE TABLE sales_order (
  order_id BIGINT PRIMARY KEY,
  customer_id BIGINT NOT NULL,
  order_status VARCHAR(32) NOT NULL
);
```

第三份是样例数据：

```json
{
  "order_id": 10001,
  "customer_id": 20008,
  "order_status": "PAID"
}
```

材料能力识别会得到不同结论：

- 业务说明支持客户、订单、订单明细、履约单及其关系；
- DDL 支持订单字段、数据类型、主键、非空和客户关联线索；
- 样例数据支持字段确实出现在实例中，并提供一个状态样值。

合并后，“订单”对象可以获得 `orderId`、`customerId` 和 `orderStatus` 等属性。`orderId` 的标识身份由主键定义支持，`customerId` 的必填性由非空约束支持。

但系统不能因为样例中出现 `PAID`，就断言订单状态只有一个值，也不能凭常识补出 `CREATED`、`SHIPPED`、`CANCELLED` 等枚举值。只有业务规则或完整值域定义出现后，才能形成可信的订单状态枚举。

同样，业务说明提到“订单包含若干订单明细”，可以支持订单到订单明细的一对多关系；但如果“履约单是否必须存在”没有明确材料，就不应自动把这条关系设为必填。

这个例子展示了整套逻辑的核心：不同材料共同补全一个对象，但每一个限定都必须由与之匹配的证据支持。

---

## 十三、当前能力边界

证据驱动能够降低幻觉和过度推断，但并不意味着本体生成已经完全自动化。

首先，临时解析材料不是长期材料资产。它们主要服务于当前生成会话，超过有效期或服务状态变化后，可能需要重新上传和解析。

其次，重新生成主要是全量处理。系统会基于当前全部材料重新形成一致结果，而不是复用上一次中间状态进行细粒度增量计算。

再次，语义审计不会自动修复问题。涉及概念边界、业务规则和冲突裁决时，仍然需要用户补充材料或进行人工编辑。

最后，材料生成主要负责本体 Schema，也就是对象、属性、关系和枚举。接口、动作以及对象如何连接真实运行数据，属于本体从“可描述”走向“可运行”的后续阶段。

这些边界并不是缺陷说明，而是在明确自动化的责任范围：收集器负责形成高质量、可追溯的本体起点，不替代领域专家完成所有业务决策。

---

## 十四、总结：把“生成本体”改写成“建立证据链”

如果把本体收集器理解成文档转模型工具，关注点会停留在支持多少文件格式、一次能够生成多少对象，以及大模型能不能把表结构写成 YAML。

但真正决定结果质量的，是另一组问题：

- 每项事实来自哪段材料？
- 这段材料能够证明对象存在，还是只能证明某个样值出现过？
- 数据库结构表达的是业务规则，还是当前系统实现？
- 多份材料冲突时，系统如何保留差异并完成裁决？
- 模型输出经过了哪些程序化门禁？
- 用户确认之前，生成结果是否已经污染正式资产？

本体收集器给出的答案，是建立一条完整的证据加工链：

> 以混合材料为输入，以原文片段为证据，以语义中间表示为核心，以程序化门禁、合并和渲染为保障，最终在人工确认后形成正式本体。

这条链路的价值，不只是让大模型“生成得更准”。更重要的是，它让本体中的每个对象、属性、关系和约束都能够被解释、被复核，也能够在材料变化后重新生成和持续演进。
