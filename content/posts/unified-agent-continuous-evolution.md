一次业务异常排查结束后，智能体交付了一份报告：异常发生在哪里、可能原因是什么、下一步应该如何处理。但任务的价值还可以继续延伸。它曾经查错数据源、调整时间窗口、识别出接口分页限制，也编写过一段用于关联订单与库存的脚本。这些经历能否帮助下一次排查？其他智能体能否直接复用已经验证的方法？

统一持续进化关心的就是这部分价值：**让每一次执行产生可验证的反馈，让有效经验进入后续决策，让成熟方法成为平台可以持续复用的能力。**

本文以业务异常排查为示例，结合 Reflexion、Voyager、Agent Workflow Memory、ACE、AFlow 与 CRAFT 六项研究，讨论一套企业智能体平台的设计思路。论文用于说明具体机制；文中的资产管理、发布流程与指标方案是工程建议，示例不代表生产实测结果。

## 一、“越用越好”究竟改善什么

假设业务人员提出一个任务：“查清昨天部分订单未按时出库的原因，给出处理建议。”智能体需要读取订单、库存、仓库任务和接口日志，并核对不同系统中的时间与业务状态。

第一次执行时，它可能先查询订单状态，再检查库存，最后才发现仓库任务已经生成，但被接口限流阻塞。后续遇到类似任务，如果平台能够识别这一模式，就可以更早检查任务流转与接口反馈，缩短无效探索。

这里包含四种不同的改进。

| 改进对象 | 希望产生的变化 | 需要保留的依据 |
| --- | --- | --- |
| 当前任务的行动策略 | 根据新证据修正下一步行动 | 工具反馈、错误信息、阶段验收结果 |
| 后续任务使用的经验 | 更快识别适用方法与常见陷阱 | 场景条件、成功方法、失败原因 |
| 可复用技能与流程 | 将重复操作变成稳定能力 | 输入输出、依赖、验证用例、版本 |
| 平台的能力组合 | 引入更合适的工具与执行路径 | 对比评测、兼容性、运行成本 |

这些变化可以发生在提示上下文、外部记忆、工具库和工作流中。Reflexion 通过语言反馈与情景记忆改善后续尝试，Voyager 通过积累可执行技能扩展行为，两者所描述的机制都不要求为此更新基础模型权重。[1][2]

因此，平台需要明确每次进化究竟更新了哪个对象。一次经验入库、一段技能代码发布和一次模型训练，应当拥有各自的版本、评价方法与生效范围。

## 二、自主探索：让每一步尝试都有反馈依据

面对未知路径，智能体首先需要把业务目标转化为可检查的完成条件。对于出库异常排查，找到一条可疑日志还不足以完成任务；系统需要说明异常订单范围、关联证据、原因判断和建议之间的关系。

在此基础上，可以设计以下执行循环：

**提出候选原因 → 选择验证动作 → 获取环境反馈 → 更新判断 → 决定继续、换路或结束。**

例如，智能体最初怀疑库存不足，但库存查询显示可用量充足。它应当降低这一假设的优先级，转而核查仓库任务。如果查询结果不完整，则先处理分页或权限问题，再使用结果作判断。

反馈至少需要区分三个层次：接口是否成功返回、返回内容是否满足检查条件、最终业务目标是否完成。接口返回成功只能证明调用完成，不能证明已经覆盖全部订单，更不能直接证明原因判断成立。

Reflexion 提供了一个研究参考：智能体将任务反馈转化为反思文本，保存到情景记忆中，用于影响后续尝试。[1] 在企业场景中，可以进一步要求反思包含“什么判断被证据推翻、为何调整方法、下一步如何验证”，使策略变化能够关联到具体依据。

探索也需要预算与停止条件。平台可以限制调用次数、执行时间和成本；在证据不足、反复失败或需要业务授权时进入待确认状态。涉及真实写入的尝试应遵循既有业务权限，离线探索则优先使用历史快照、模拟接口或隔离环境。这些边界使探索结果更容易比较，也避免把业务状态的随机变化误认为方法改进。

## 三、经验蒸馏：把一次经历变成可用的方法

原始轨迹记录了执行过程中发生的事情。可复用经验还需要回答：这段经历适用于什么条件，哪些步骤影响了结果，以及什么时候不能继续使用。

本文所说的“蒸馏”，指从轨迹中提炼方法、规则和案例，不特指模型参数层面的知识蒸馏。

以出库排查为例，原始记录可能包含数十次查询和大量重复日志。提炼后的经验可以表达为：“当订单已通过库存校验、仓库任务持续停留在待发送状态时，优先检查任务发送接口的限流与重试记录；若任务尚未生成，则先检查任务创建链路。”

这条经验保留了触发条件、行动建议和分支边界。它还需要附带来源证据与适用系统版本，以便后续核查。建议将经验条目组织为以下结构。

| 字段 | 作用 |
| --- | --- |
| 任务类型与适用条件 | 判断当前场景是否可以使用 |
| 推荐步骤与关键分支 | 指导后续行动 |
| 反例与失效条件 | 避免跨场景误用 |
| 来源轨迹与验证结果 | 支持回溯和质量判断 |
| 数据范围与可见权限 | 决定谁可以读取和复用 |
| 版本与复验时间 | 支持更新、降级和淘汰 |

ACE 将上下文视为持续演进的策略手册，通过生成、反思和整理积累经验，并使用结构化增量更新保留细节，缓解反复重写造成的内容丢失。[3] 这提示平台：经验维护应支持对具体条目的补充、修正和停用，而不是每次运行后整体重写全部记忆。

经验入库可以设计为“候选提炼—证据核查—适用性验证—批准复用”。单次成功只能证明某种方法在一个场景中奏效，不能直接证明普遍有效。应使用独立案例检查它在相似条件下是否仍然成立，并保留会导致失败的反例。

检索时也要检查适用范围。语义相似可以帮助找到候选经验，但租户、系统版本、权限和业务条件应参与筛选。每次使用后的结果再反馈给条目维护机制，使经验库能够持续修正。

## 四、流程提炼：让稳定路径成为标准能力

经验能够指导智能体如何思考，技能与工作流则进一步承载可重复执行的步骤。

Agent Workflow Memory 从过去的经历中归纳可复用工作流，并选择相关流程指导后续行动，在网页导航任务中验证了这一方法。[4] Voyager 则在 Minecraft 中建立持续增长的可执行技能库，让已有代码技能能够被检索和组合。[2] 两项研究分别为流程记忆和执行技能积累提供了参考，其实验结果仍有各自的任务环境边界。

在企业平台中，可以先识别重复出现的成功路径，再判断哪些步骤足够稳定，适合提炼成能力。例如，多次排查中都出现以下步骤：

**确定异常订单 → 核对库存 → 关联仓库任务 → 查询接口记录 → 输出带证据的原因分类。**

提炼时，需要把订单编号、时间区间、仓库编号等具体值转化为输入参数，保留“任务不存在”“状态不一致”“数据缺失”等条件分支，并补齐输出结构与错误处理。

高频只说明值得考虑复用。是否发布为标准能力，还取决于成功率、业务稳定性、参数化程度和维护成本。一个经常失败的流程，更适合先进入问题分析与评测集合。

建议将能力提炼划分为两个阶段：首先生成候选技能，自动整理实现与测试样例；随后根据独立验收结果决定是否发布。确定性较强的数据转换可以自动验证，涉及原因判断的流程则需要检查证据是否支持结论。

AFlow 将工作流优化建模为对代码表示的流程进行搜索，通过代码修改与执行反馈迭代改进结构。[5] 平台可以借鉴这一方法，对“先做哪项检查、在哪个节点增加复核、何时调用较强模型”等选择进行离线比较，再将有效版本投入实际任务。

## 五、资源反哺：让个体产出进入平台资产体系

执行过程中生成的脚本、查询模板、字段映射和校验规则，都可能具有后续价值。CRAFT 展示了一条工具积累路径：从任务代码解法中构建候选工具，经过验证、抽象和去重形成专用工具集，再在后续任务中检索使用。[6]

对于异常排查，智能体生成的订单与仓库任务关联脚本，可以进一步抽象成数据核对工具；被发现的分页缺陷，可以进入接口检查规则；一次误判，则可以进入回归评测集。由此形成三类互相支持的资产。

| 资产类型 | 示例 | 复用方式 |
| --- | --- | --- |
| 知识资产 | 场景经验、故障案例、判断条件 | 检索后辅助规划与判断 |
| 执行资产 | 脚本、工具、技能、工作流 | 直接调用或组合执行 |
| 评测资产 | 失败样本、边界案例、验收规则 | 比较候选版本与现行版本 |

个体产出进入平台目录时，需要有明确的责任归属和使用范围。特定租户的业务事实应保留在相应范围内；可共享的方法则需要抽离客户数据、凭证和环境专有配置，再验证其可迁移性。

统一资产目录建议记录资产标识、用途、输入输出、依赖、权限、来源、版本和维护负责人。还应保留资产之间的依赖关系：某个工作流用了哪个工具版本，某个经验依赖哪个业务规则，哪些评测支持了此次发布。

当接口升级时，这些关系可以帮助定位需要重新验证的技能与流程。平台也应能够暂停存在问题的版本、恢复已验证版本，并为正在运行的任务制定版本继续使用或迁移的规则。

这一层治理使经验共享拥有明确的交付对象：其他智能体获得的是可发现、可理解、可验证的能力，而不必重新阅读完整执行历史。

## 六、外部融合：把新能力接入同一套改进机制

内部积累逐步完善已知任务的处理方式，外部接入则可以扩展可处理的任务范围。例如，接入新的仓储查询接口，能够补齐原本缺失的数据；引入专用文档解析工具，可以帮助处理供应商提供的复杂附件。

为了实现插件式扩展，本文建议为每项能力提供统一的接入契约：描述用途与限制，声明输入输出、版本依赖、身份权限、超时与错误语义，并提供验证用例。

能力进入目录后，还需要让智能体能够发现与选择它。平台可以先根据任务类别、数据范围和权限筛选候选，再比较功能覆盖、运行质量与成本。对于核心业务流程，应先在代表性任务上验证，再逐步扩大使用范围。

CRAFT 的工具检索机制为“建立工具集并按需选用”提供了研究参考。[6] 跨系统身份、接口兼容、发布回退与生产监测，则属于本文建议补齐的平台工程能力。

新插件与内部生成的技能可以共用资产登记、评测和发布机制。这样，外部能力带来的新经验仍能进入持续积累过程，内部沉淀的流程也可以组合使用外部工具，形成双向促进。

## 七、统一闭环：将改进落实为可检查的版本变化

将前面的环节连接起来，可以形成一条统一的进化主线：

**执行与探索 → 采集反馈 → 提炼候选经验和能力 → 独立评测 → 版本发布 → 检索复用 → 收集新反馈。**

外部插件通过相同的验证与发布入口进入能力目录。失败案例进入评测集，既帮助发现问题，也用于检查后续改动是否重新引入旧错误。

在平台实现上，建议区分两个运行节奏。当前任务根据反馈调整下一步行动，使用已批准的能力完成交付；后台机制周期性分析多次执行，生成和验证候选资产。共享能力版本经过发布流程后，再进入后续任务，避免未经检验的单次反思立即影响所有智能体。

这里的“统一”，意味着任务、轨迹、经验、能力和评测之间能够通过标识和版本关联。运行框架提供执行记录，数据基座保存事实与记忆，调度系统供给计算和工具资源，持续进化模块负责提出、验证并管理能力更新。

判断平台是否改善，可以使用以下指标。

| 评价方向 | 建议指标 | 需要关注的解释条件 |
| --- | --- | --- |
| 任务效果 | 成功率、重复错误率、人工修订比例 | 使用相同验收口径，按任务难度分组 |
| 执行效率 | 完成时间、工具调用量、单次成功任务总成本 | 成本计入失败尝试与后台优化开销 |
| 资产价值 | 有效复用次数、跨场景复用表现、维护成本 | 区分被检索、被采用和实际有效 |
| 版本质量 | 独立评测表现、回归失败率、回退次数 | 保留独立测试集与现行版本基线 |

评价时，应记录模型、工具、数据和提示配置的版本。针对具有随机性的任务，可以重复运行或提供不确定性范围；必要时通过消融对比，区分记忆更新、工具替换和流程变化分别带来的效果。经验条目增加、调用次数增加，都不能单独证明质量改善。

## 八、从一个可验证场景开始积累

落地时，可以先选择一种任务频率适中、结果可核验、流程有重复性的场景，例如订单异常排查。先明确成功标准并保存完整证据，再分析最常见的失败，提炼少量可检验经验，最后将其中稳定的步骤升级为技能。

建议按以下顺序推进：

1. 建立任务与证据基线，明确哪些结果算成功、哪些情况需要人工判断。
2. 从已有记录生成候选经验，用独立案例验证适用范围。
3. 提炼重复且稳定的操作，形成带参数、依赖和用例的技能版本。
4. 建立统一资产目录，使其他智能体能够在权限范围内发现和使用。
5. 引入工作流搜索和外部插件，用相同的评价口径衡量改进。

回到最初的异常排查任务，第一次执行可能留下曲折的探索过程。经过提炼与验证，后续智能体能够更早检查关键链路，调用已有核对工具，并使用新增的仓储接口补齐证据。如果业务规则变化，旧经验能够被停用，相关流程能够重新接受评测。

**统一持续进化的价值，是让一次任务的成果在交付之后继续发挥作用，成为下一次决策、下一次执行和平台能力增长的基础。** 每一项增长都能够找到来源、解释适用条件，并通过实际任务检验。

## 参考文献与对应关系

以下年份采用 arXiv 首次发布年份。论文实验支持其各自方法与任务范围，本文没有将不同基准上的收益直接换算为企业平台收益。

[1] *Reflexion: Language Agents with Verbal Reinforcement Learning*. 2023. arXiv:2303.11366。对应语言反馈、反思记忆与后续尝试改进。论文入口：https://arxiv.org/abs/2303.11366

[2] *Voyager: An Open-Ended Embodied Agent with Large Language Models*. 2023. arXiv:2305.16291。对应自主探索、迭代程序改进与可执行技能库；实验环境为 Minecraft。论文入口：https://arxiv.org/abs/2305.16291

[3] *Agentic Context Engineering: Evolving Contexts for Self-Improving Language Models*. 2025. arXiv:2510.04618。对应策略手册、生成反思整理与增量上下文更新。论文入口：https://arxiv.org/abs/2510.04618

[4] *Agent Workflow Memory*. 2024. arXiv:2409.07429。对应从历史经历提炼流程并指导后续行动；实验包括 Mind2Web 与 WebArena。论文入口：https://arxiv.org/abs/2409.07429

[5] *AFlow: Automating Agentic Workflow Generation*. 2024. arXiv:2410.10762。对应代码表示的工作流搜索与执行反馈优化。论文入口：https://arxiv.org/abs/2410.10762

[6] *CRAFT: Customizing LLMs by Creating and Retrieving from Specialized Toolsets*. 2023. arXiv:2309.17428。对应任务工具的创建、验证、抽象、去重与检索复用。论文入口：https://arxiv.org/abs/2309.17428
