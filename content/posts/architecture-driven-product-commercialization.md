一款企业产品完成了功能开发，距离真正落地还有多远？

试点客户可能在日常查询时觉得很流畅，却在月底集中导出时报错；管理人员愿意购买，普通员工却因为操作复杂继续使用表格；技术团队能够完成部署，但每交付一个客户，都需要资深工程师驻场处理环境和数据问题。订单增加之后，收入增长，交付和支持成本也同步上涨。

这些问题需要在方案设计时一起考虑。架构决定产品如何运行，也决定团队如何交付、客户如何使用、问题如何恢复，以及服务承诺需要付出什么成本。

本文采用一条设计路径：

**明确业务价值 → 识别关键场景 → 定义质量要求 → 比较架构方案 → 建立交付能力 → 验证商业结果 → 根据运行证据演进。**

文中的案例、金额、容量和服务目标均为教学假设，用于演示推导过程，不代表行业基准或真实经营结果。具体项目应重新测量业务基线，并通过验证确定承诺。

**一、从业务目标开始，让架构有明确的服务对象**

设想我们准备开发一款面向中型制造企业的设备维修协同产品。现场人员提交故障，维修主管分派任务，工程师记录处理过程，管理者查看积压、响应时间和维修记录。

如果从功能清单出发，很容易列出工单、审批、消息、报表、权限和移动端。但这些功能还不能解释客户为什么购买，也不足以决定架构。

需要先还原客户的工作：故障出现后，现场人员通过电话和群聊找人；维修主管手动整理任务；处理结果缺少统一记录；遇到换班，责任和进度容易丢失。产品要改善的是发现、分派、处理和追踪之间的信息传递。

于是，可以把第一阶段的价值假设写成：在不增加主管管理负担的前提下，缩短从报障到首次有效响应的时间，让未处理任务有明确责任人，并保留可追踪的处理记录。

这里必须区分技术可直接影响的部分和业务共同决定的部分。页面速度能够直接优化，维修人员是否及时到场还取决于排班、备件和现场管理。产品不能用接口变快，替代对维修流程是否改善的验证。

CMU SEI 将业务目标与架构关键需求关联起来：业务目标需要经过识别和细化，形成真正影响架构的要求。[1] 在本案例中，可以建立这样的映射：

| 业务目标 | 关键场景 | 架构关注点 | 验证方式 |
|---|---|---|---|
| 减少报障后的等待 | 高峰期也能及时提交和看到任务 | 核心写入、通知时效、列表性能 | 负载测试与试点流程数据 |
| 避免责任和记录丢失 | 换班、重试、网络中断后继续处理 | 状态约束、幂等、审计和恢复 | 故障注入与业务对账 |
| 降低培训成本 | 一线人员首次使用完成报障 | 任务流程、默认值、错误提示 | 真实用户任务测试 |
| 缩短客户上线周期 | 导入设备、配置组织、开放账号 | 标准模板、配置校验、接入自动化 | 完整交付演练 |
| 支持持续盈利 | 客户增长后服务成本仍可承担 | 资源计量、交付复用、支持效率 | 单客户成本分析 |

购买者、使用者和运维人员还可能提出不同要求。管理者关注结果与预算，一线人员关注是否省事，客户 IT 关注身份接入、数据边界和运行保障。产品方案需要明确各方的验收条件，并指出它们之间的冲突。

同时记录预算、上线时间、团队人数、现有系统、客户网络和部署要求。约束写得越明确，后续技术选型越容易解释。

**二、把“稳定、快、好用”写成可验证的要求**

质量属性描述系统应当具备的运行和使用特征。SEI 提出的质量属性场景，包含刺激来源、刺激、环境、受影响对象、响应和响应度量，用于把笼统期待变成可分析的要求。[2]

“系统要快”缺少判断依据。更完整的表达应当说明：什么用户、在什么数据规模和负载下、执行什么操作、允许多少延迟和失败。

为了便于后续讨论，本文采用以下工作定义。这些维度可以重叠，不是互斥的分类标准。

| 维度 | 本文重点回答的问题 |
|---|---|
| 稳定性 | 在持续运行、负载波动和变更过程中，行为是否保持可预期，异常是否会扩大 |
| 高性能 | 在指定负载和资源条件下，能否满足响应时间、吞吐量和处理时效要求 |
| 易用性 | 用户能否容易学会、有效完成任务，并在出错后恢复 |
| 可用性 | 在用户需要服务时，关键业务是否能够成功完成 |
| 可运维性 | 团队能否观察状态、定位问题、安全变更并恢复服务 |

安全、数据完整性、可维护性和成本效率贯穿这些维度。AWS Well-Architected 将运营、可靠性、性能、安全、成本和可持续性纳入整体评估，提醒设计者同时观察多个目标。[3]

假设维修产品准备服务首批十家客户，我们可以先提出下面这组待验证目标：

| 场景 | 假设目标 | 需要固定的测量条件 |
|---|---|---|
| 核心任务查询 | P95 接口响应时间不超过 500 毫秒 | 百万级历史工单、指定查询组合、100 请求/秒、持续 30 分钟 |
| 工单提交 | 有效提交请求的成功率达到约定目标 | 明确统计窗口、请求分母、失败分类和超时阈值 |
| 通知发送 | 正常依赖条件下，99% 的通知任务在 60 秒内完成发送 | 分开记录进入队列、提供商接受、终端送达 |
| 新用户报障 | 首次使用者在没有口头指导时完成指定任务 | 真实角色、实际设备、统一任务说明，报告样本量和错误情况 |
| 故障恢复 | 对约定的区域级故障，RTO 为 60 分钟、RPO 为 15 分钟 | 明确灾害范围、恢复依赖、演练起止点和数据校验方式 |

接口 P95 是接口观测值，不能自动代表手机上的完整体验。用户实际等待还包含网络、页面加载和交互。通知提供商接受请求，也不能自动代表用户已经收到通知。指标名称应准确对应测量位置。

这一步的产出应当是可以共同签字确认的质量要求。每项要求都需要业务理由、负责人、优先级、验收条件和实现代价。对于无法同时满足的目标，应在方案评审中明确取舍。

**三、稳定性：控制异常传播，并保护业务状态**

本案例先识别三条关键链路：创建工单、领取任务、提交处理结果。月度报表、附件缩略图和历史统计具有不同的重要程度。它们应有各自的资源预算和降级策略。

例如，大批量报表可以进入后台队列，并限制每个客户的并发任务数。工单提交完成后，再由后台发送通知。即使通知供应商暂时不可用，已保存的任务仍应能在工作台查询。

超时、重试和退避需要共同设计。AWS Builders’ Library 指出，重试会增加下游负载，具有副作用的调用还需要处理重复执行；退避与随机抖动用于避免请求集中再次到达。[4] 因此，案例中应限制重试次数和总时长，避免网关、服务和客户端同时反复重试。

业务层面还需要明确状态规则。同一工单不能同时被两个人成功领取；终端因网络抖动重复提交时，不能创建两张维修任务。可以为创建请求设计业务幂等标识，为领取操作采用带状态条件或版本条件的更新，并明确冲突时的用户反馈。这是本案例的实现建议，具体方式需要结合数据模型验证。

对于“保存工单后必须触发通知”的要求，直接先写数据库、再调用消息系统，会留下其中一步失败的窗口。事务发件箱模式提供了一种处理双写问题的方案：业务变更与待发送事件在同一个本地事务中保存，由后台进程投递。投递仍可能重复，消费者需要幂等处理。[5]

如果试点规模较小，后台进程可以先扫描数据库任务表。是否引入独立消息系统，应由积压、吞吐、隔离和维护需求决定。

稳定性还涉及发布。案例中应让新旧版本在滚动更新期间兼容，数据库字段变更先保持兼容，再迁移数据，最后移除旧路径。回滚演练必须覆盖数据库状态，不能只验证旧应用进程能够启动。渐进变更和可恢复的发布过程也是运营设计的组成部分。[14]

**四、高性能：先定义用户等待，再分配性能预算**

本案例把用户操作分成三类：需要立即反馈的工单提交和列表查询、允许短暂等待的通知，以及可以后台完成的历史导出。分别设置目标，有助于把资源投入与用户期待对应起来。

对于列表查询，可以先画出真实调用路径：入口认证、权限过滤、工单查询、设备信息补充、结果组装和前端渲染，再通过测量定位等待时间。初期不应只按总请求量估算，还应覆盖大客户、冷缓存、复杂筛选、数据倾斜和批量任务并存的情况。AWS 性能效率指南强调基于代表性负载进行测试，并用测量结果支持配置与容量选择。[6]

假设压测发现主要等待来自工单列表扫描，那么本案例应优先检查查询条件、索引、分页和返回字段。假设主要等待来自同步导出，则应评估转为后台任务。缓存是否合适，要同时回答数据更新后允许多久不一致、如何失效，以及缓存故障后数据库能否承受回源。

容量模型可以先用一组明确的假设启动：

> 峰值请求量 ≈ 峰值活跃用户数 × 单用户操作频率 × 每次操作触发的请求数。

这个公式用于估算量级，不替代压测。还需要补充突发流量、后台任务和客户之间负载不均的影响，并以实测修正。

对于案例中的候选方案，可以比较三组结果：目标负载下的延迟、超过目标负载后的失败方式，以及满足同一目标需要的资源成本。一个方案在正常负载下很快，但过载后让全部租户同时失败，仍不适合直接承诺给客户。

**五、易用性：把首次使用、日常操作和异常恢复一起设计**

Nielsen Norman Group 将易用性分为易学性、效率、易记性、错误和满意度，并建议通过观察用户完成任务来评估设计。[7]

在维修产品中，首先要确定一线员工完成报障到底需要做什么。我们可以提出一个待验证设计：扫描设备标识，确认设备，选择故障类别，拍照并提交。能由设备和组织配置推导的信息自动填入，需要专业判断的信息留给维修人员补充。

首次使用的效率与熟练使用的效率要分别验证。新人是否理解字段，老用户能否快速重复操作，主管能否处理大量任务，管理员能否正确配置权限，都是不同的使用场景。

错误状态同样需要设计。附件上传失败时保留已填写内容；网络中断时说明任务是否已经提交；存在版本冲突时展示最新状态和后续操作。用户需要据此决定是否重试，后台则需要保证重试不会重复产生业务结果。

集成也是产品体验的一部分。面向客户开发者的接口，应提供清晰的权限范围、错误含义、分页规则、调用示例和兼容策略。面向管理员的初始化流程，应能指出缺失数据和配置冲突。上述内容作为本案例的设计要求，分别用接入演练和任务测试验收。

试点时，邀请真实报障人员、维修主管和管理员，给他们任务而非操作步骤，记录完成情况、耗时、求助和误操作。小样本用于发现问题时，应保留样本量和观察记录；要据此推断整个客户群体的完成率，则需要额外设计抽样与统计方法。

**六、可用性：围绕关键用户行为建立服务承诺**

Google SRE 区分三类概念：SLI 是服务表现的测量指标，SLO 是指标的目标，SLA 是对外约定，通常还涉及未达标的处理后果。选择指标应从用户关心的服务行为出发。[8][9]

对于维修产品，可以分别观察工单提交成功率、任务查询成功率和通知及时性。应用健康检查成功，只能证明被检查的部分正常，不能证明工单能够正确保存和显示。

假设工单提交采用请求型 SLI，案例可以定义为：在滚动 30 天内，符合事先约定条件的提交请求中，正确完成业务处理且在阈值内响应的比例。分母应覆盖约定范围内失败的有效请求，超时和系统异常不能因为没有进入应用日志就被漏掉。用户输入无效、计划维护等边界，应事先明确并保持统计一致。

如果 SLO 为 99.9%，相应错误预算为该窗口有效请求数的 0.1%。团队可以约定：预算消耗过快时减少高风险变更，优先修复主要失败原因。具体触发条件由团队制定，并根据运行经验调整。[8]

请求型比例不能直接换算成停机分钟数。如果采用连续 30 天的时间型可用性，且分母包含全部时间，99.9% 对应的不可用预算才是 43.2 分钟；采用其他窗口或排除规则，需要重新计算。

在本案例中，应用多副本、数据库故障转移、跨故障域部署和独立恢复能力都可以成为候选措施，但要根据故障范围逐项验证。还应考虑错误发布、误删数据和共享依赖异常，避免所有副本受到同一个原因影响。

RTO 表示恢复时间目标，RPO 表示可接受的数据恢复点目标。它们用于约束灾难恢复策略，需要通过演练验证。[10] 本案例提出的区域故障 RTO 60 分钟、RPO 15 分钟，意味着必须由业务方确认该灾害场景下的数据损失容忍度。对于完全不能接受已确认工单丢失的客户，应重新评估数据保护策略、故障范围和对应成本。

恢复验证应包括访问恢复、关键流程完成、权限正确和数据完整性核对。备份任务显示成功，还不足以证明恢复目标已经实现。[10]

**七、可运维性：让产品具备可持续服务的条件**

运维设计需要明确值班人员能够获得哪些证据、执行哪些动作，以及什么情况下需要升级处理。AWS 运营指南强调根据业务与技术信号建立可观测性，并通过运行手册和事件处理机制支持日常运营。[11]

本案例建议围绕同一业务请求关联入口记录、应用日志、数据库操作和后台任务，保留请求标识、租户标识、工单标识与错误类别。指标用来发现整体变化，追踪用于调查调用路径，日志用于提供具体上下文；采集范围、敏感信息处理和保留周期需要预先设计。[11]

告警则应对应需要采取的行动。可以先围绕提交失败率上升、通知积压超时、备份失败和容量逼近限制设计规则，每条告警说明用户影响、负责人、检查路径和临时恢复措施。单纯的资源波动可作为调查信号，其是否值得立即唤醒人员，需要结合业务影响决定。

接下来，设计两个经常被忽略的完整流程。

第一个是交付：创建租户、导入设备、接入身份、验证权限、发送测试通知、确认备份和移交管理员。第二个是升级：确认兼容范围、备份配置、执行迁移、验证核心流程，并在失败时恢复到可用状态。

私有化部署还需要建立受支持环境清单，约定网络、数据库、证书、存储和第三方依赖的维护责任。客户环境无法远程访问时，应提供经过脱敏的诊断包和可执行的检查步骤。这些是案例中的交付设计建议，需要在真实客户环境中演练。

可运维性的验收可以很具体：让另一位具备岗位能力、没有参与开发的工程师，依靠交付文档完成部署、升级和一次典型故障处理，并记录耗时、缺失信息和必须求助的环节。

**八、做出架构取舍：把选择、代价和演进条件写清楚**

有了质量要求，才适合比较具体架构。假设首阶段团队有六名研发人员，计划在三个月内完成十家客户试点，支持标准云服务，暂不承诺客户任意环境的私有化部署。

下面是一份候选方案，不是面向所有企业产品的标准答案：

| 范围 | 本阶段选择 | 选择理由 | 代价与复核条件 |
|---|---|---|---|
| 业务应用 | 模块化单体，工单、设备、权限保持明确边界 | 支持小团队共同交付，减少跨服务协作 | 模块不能独立扩容；出现独立负载或发布需求时复核 |
| 核心数据 | 关系数据库保存业务状态和待发送事件 | 便于表达事务、关联和状态约束 | 需要管理索引、慢查询和数据库容量 |
| 后台工作 | 独立工作进程处理通知与导出 | 允许不同的并发限制和重试策略 | 增加任务状态、积压监控和补偿处理 |
| 附件 | 对象存储保存文件，数据库保存引用 | 将文件生命周期单独管理 | 需要校验访问权限、上传状态和孤立文件 |
| 租户模式 | 共享应用与共享数据库，实施租户隔离 | 让试点成本处于可承担范围 | 必须验证越权、数据混用与资源争用风险 |
| 运行部署 | 根据可用性目标配置应用冗余、数据库保护与备份 | 覆盖已确定的故障场景 | 实际服务水平仍取决于整体依赖和演练结果 |

共享数据模型中的租户标识不能只依赖页面传入。案例应要求服务端从可信身份上下文确定租户边界，对查询、导出、附件、后台任务和管理接口分别验证授权；资源限制也应避免单个客户占满共享容量。隔离方式需要结合威胁模型和客户要求评审。[12]

每个重要选择可以用一页架构决策记录保存：背景、目标、候选方案、选择依据、负面影响、验证结果和重新评估条件。特别要写明没有解决的风险，避免候选措施被误读为已经达成的能力。

例如，当前选择数据库任务表，后续出现持续积压且优化后仍无法达到通知时效目标，才进入消息基础设施评估。当前选择共享部署，若目标客户愿意为独立资源与更高保障付费，则重新核算专属部署方案。

这样，演进由可观测的问题和商业需求触发，团队也能解释为什么当前不需要承担某些复杂度。

**九、把商业化能力纳入方案：产品如何销售、交付和收费**

商业方案需要描述客户买到哪些能力、在什么范围内使用、获得什么服务，以及供应方如何核算成本。Azure 多租户架构指南将定价与资源消耗、客户价值及服务层级关联起来，说明商业模型会影响技术设计。[13]

在维修产品案例中，可以先提出三种待验证的包装方式：

| 方案 | 目标客户需求 | 需要配套的能力 |
|---|---|---|
| 标准版 | 核心报障、派工和记录管理 | 标准开通、基础权限、明确配额与服务范围 |
| 专业版 | 多工厂协同、系统集成和高级分析 | 组织模型、接口权限、身份集成与可核算的任务用量 |
| 专属服务 | 特定隔离、部署或支持要求 | 独立交付方案、容量预算、升级机制与专属服务核算 |

这些划分是产品假设，需要用客户访谈和付费试点验证。安全隔离、必要的数据保护和基本可恢复性，应作为各版本共同的设计基线。

按账号、工厂或业务量收费，会带来不同的计量要求。按活跃账号收费，需要定义活跃的统计窗口；按工单量收费，需要说明重复提交、撤销和测试数据的处理规则；按资源用量收费，需要能够解释客户账单与使用行为之间的关系。[13]

因此，方案应同时设计权益判断、配额、用量记录、账单核对和套餐变更。客户达到限制时，是提示、限制非关键任务，还是启动人工确认，需要提前确定。在本案例中，核心报障不能因为客户不理解的突发计费状态而被意外阻断，具体处理规则应体现在产品体验和服务约定中。

成本核算则至少覆盖资源、第三方服务、交付、支持和客户专属变更。AWS SaaS Lens 建议建立租户维度的使用与成本视图，以支持业务和运营决策。[12]

用一个假设算例说明：某客户首年服务收入为 12 万元，归属到该客户的资源与第三方费用为 2 万元，支持费用为 1 万元，首次实施费用为 3 万元。如果使用管理分析口径，将这些直接归属费用扣除，则首年剩余 6 万元，比例为 50%。

这个比例只用于本例的单位经济性分析，不能直接称为完整净利润率；它尚未覆盖产品研发、销售获客、公共管理等费用，也不是会计口径的建议。下一年度还应重新估算续费收入、支持投入和升级成本，不能简单假设首次实施费用归零后收益自然改善。

标准化的价值也可以这样验证：若实施工时下降，而客户的成功使用率和服务质量保持在目标内，则交付改进有了可衡量的经营意义。反之，如果低价套餐带来大量专属改造，应重新审视套餐边界、定价和目标客户。

定制需求可以按三类处理：已有能力通过配置满足；具有重复需求的能力进入产品路线图；客户专属能力单独估价，并明确维护、升级和退出安排。选择需要由产品价值与长期服务成本共同支持。

**十、分阶段推动落地：每次投入都对应待验证的问题**

建议为本案例设置四个阶段，每个阶段都有交付物、负责人和继续投入的条件。以下是本文提出的实施框架，时间和门槛需要由实际团队确定。

| 阶段 | 需要验证的问题 | 核心交付物 | 继续投入的条件 |
|---|---|---|---|
| 需求与方案验证 | 痛点是否足够重要，客户能否配合 | 业务基线、关键流程、原型、技术风险验证 | 明确业务负责人、试点资源和验收口径 |
| 最小可行产品与试点 | 用户是否获得价值，方案是否满足基本质量 | 可运行产品、试点报告、质量验证记录 | 有实际使用证据，关键风险可控，出现付费依据 |
| 标准化商业交付 | 能否在新客户中重复交付 | 套餐、开通流程、实施手册、支持机制 | 新客户上线不依赖原开发者长期驻场，成本可解释 |
| 规模经营 | 增长后质量和成本是否仍可控制 | 容量规划、客户使用分析、成本分摊和版本策略 | 增长过程保持约定质量，服务负担处于可承担范围 |

试点应提前测量基线。例如，记录原流程中从报障到首次有效响应的时间分布，再在约定范围内运行产品。比较时保留故障类别、班次、人员配置等信息，避免把同期管理调整的效果全部归因于软件。

如果指标没有改善，先追查假设：用户是否使用，操作是否困难，通知是否及时，现场是否有可响应的人员。技术方案、产品流程和业务协作可能分别需要调整。

组织协作也要落实到具体决策。产品负责人负责价值与范围，技术负责人负责架构及质量证据，交付负责人负责客户环境和验收，运营支持负责人负责服务准备，销售负责人确保对外承诺经过能力与成本评估。小团队可以由同一人承担多个角色，但每项决定仍应有明确责任人。

遇到新增承诺，例如“所有客户都支持当天上线”或“提供更高服务等级”，评审材料应包含影响范围、实现路径、依赖条件、验证证据和持续成本。尚未验证的能力，需要明确作为目标或有条件的方案，而不能直接作为已具备能力销售。

**十一、用运行证据决定下一步投入**

上线后的看板应帮助团队回答四个连续的问题：客户是否获得价值，产品是否满足质量承诺，团队能否高效交付与服务，当前收入是否足以支持这些成本。

| 观察层面 | 本案例建议关注的指标 | 指标变化后的调查方向 |
|---|---|---|
| 客户价值 | 报障到首次响应时间、未处理任务积压、关键流程使用率 | 使用障碍、流程设置和客户执行条件 |
| 产品质量 | 提交成功率、查询延迟、通知及时性、恢复演练结果 | 关键路径、依赖故障和容量问题 |
| 交付服务 | 上线周期、人工配置工时、支持请求及重复问题 | 产品缺口、文档、自动化与客户边界 |
| 经营状况 | 付费转化、续费情况、单客户直接成本、专属变更投入 | 客户选择、套餐、报价与服务方式 |

这组指标是本案例的建议组合。指标之间的相关性只是调查线索，需要结合客户访谈、任务记录和技术证据判断原因。

运行目标还需要明确管理动作。可以约定按周检查错误预算、积压与重大故障，按月分析客户使用和成本，按季度复核架构决策及产品边界。故障复盘应留下可验证的改进行动，例如补充一种恢复演练、移除一项高风险人工操作，或修正一个会导致重复提交的交互。

演进决策则应写成条件句：当某类任务在代表性负载下持续无法达到目标，并且业务优先级足够高时，投入专项优化；当专属部署需求能够覆盖额外交付与服务成本时，建设相应能力；当某项定制反复出现并有共同业务语义时，将其转化为标准能力。

**十二、一份可直接用于方案评审的工作文档**

实际项目可以将前面的方法收敛为以下五张表，并附上原型、架构图和验证证据。

**表一：业务与范围**

| 字段 | 应填写的内容 |
|---|---|
| 目标客户与角色 | 购买者、使用者、管理员，以及各自的关键任务 |
| 当前问题与基线 | 现有流程、问题频率、影响及证据来源 |
| 价值假设 | 预期改善什么，哪些条件依赖客户配合 |
| 产品边界 | 本期覆盖范围、扩展方式和专属需求处理原则 |
| 验证安排 | 试点客户、观测窗口、负责人和继续投入条件 |

**表二：质量场景**

| 字段 | 应填写的内容 |
|---|---|
| 业务关联 | 该要求保护哪项用户任务或商业承诺 |
| 环境与刺激 | 数据量、负载、设备、依赖及故障场景 |
| 预期响应 | 系统应完成的行为及失败时的处理方式 |
| 指标口径 | 分子、分母、阈值、统计窗口和例外规则 |
| 验收证据 | 测试方法、原始记录、结果和剩余风险 |

**表三：架构决策**

| 字段 | 应填写的内容 |
|---|---|
| 决策与候选方案 | 解决的问题、备选方案和适用约束 |
| 选择依据 | 对质量、开发周期、交付和成本的影响 |
| 代价与风险 | 尚未解决的问题和可接受条件 |
| 验证结果 | 已完成验证、失败项及补救措施 |
| 复核条件 | 什么证据出现时需要重新选择 |

**表四：商业交付准备**

| 字段 | 应填写的内容 |
|---|---|
| 套餐和权益 | 功能、配额、计量方式、升级及限制处理 |
| 服务范围 | 支持时间、响应机制、依赖条件和服务目标 |
| 交付与升级 | 环境、导入、接入、验收、迁移和恢复步骤 |
| 数据生命周期 | 导入、权限、保留、备份、导出和退出处理 |
| 成本责任 | 资源、第三方、实施、支持及专属变更的归属 |

**表五：运营与演进**

| 字段 | 应填写的内容 |
|---|---|
| 观测指标 | 客户价值、质量、交付与成本的指标口径 |
| 检查机制 | 频率、负责人、异常触发条件和行动 |
| 事故与改进 | 用户影响、原因、改进负责人和验证方式 |
| 产品反馈 | 重复需求、未解决障碍与客户使用证据 |
| 投入决定 | 下一阶段目标、资源需求及预期收益假设 |

使用这些表时，区分“提出目标”“完成设计”“验证通过”和“已经承诺”四种状态。例如，恢复目标写入文档，只表示团队知道要达到什么；完成演练并保留证据，才说明当前方案在所测条件下具备相应能力。

产品负责人可以据此检查客户价值是否清晰，架构师可以检查关键质量是否有依据，交付团队可以确认实施条件，经营负责人可以评估收入与服务成本。方案评审最终需要形成可执行的决定：本期交付什么、以什么证据验收、由谁负责，以及出现什么变化时重新评估。
