前端 Agent 发现页面请求超时，把任务交给后端 Agent：“接口有性能问题，帮忙修一下。”后端 Agent 根据这句话增加了缓存，测试 Agent 验证接口恢复后宣布完成。但用户真正遇到的是：提交操作超时后再次点击，系统生成了两条工单。

在这个假设案例中，每个 Agent 都做了与自己理解一致的工作，整条链路却遗漏了原始问题。交接消息没有区分用户现象与原因假设，没有说明已经发生的业务副作用，也没有保留“不重复创建工单”这个验收条件。后续执行越顺畅，偏离目标就可能越难被发现。

跨 Agent 任务交接需要回答三个相互关联的问题：接收方如何获得足够的信息，系统如何确认谁负责继续执行，以及交接中断后如何恢复。这些问题分别涉及任务理解、执行控制和持久化状态。

本文面向基于大语言模型的 Agent 系统，重点讨论开发、分析和业务执行等任务在不同 Agent 之间的续接。论文用于提供失败分类、澄清机制、协作模式和记忆方法的研究依据；文中的字段、状态机、责任转移流程与实验方案是据此提出的工程设计，尚未经过本文自己的实验验证。

## 一、先说清楚：交接究竟转移什么

### 1.1 信息共享、委派和接管具有不同的责任语义

把一段文本发给另一个 Agent，可能意味着“请参考”“请帮忙完成一部分”，也可能意味着“从现在起由你负责”。如果这些含义没有区分，消息发送成功也无法证明责任已经交出去。

本文采用以下约定：

| 交互类型 | 接收方要做什么 | 原任务责任如何变化 | 典型例子 |
|---|---|---|---|
| 信息共享 | 阅读或更新知识，不必启动工作 | 原执行者继续负责 | 分享接口说明 |
| 子任务委派 | 执行一个具有独立产出的子任务 | 父任务负责人保留整合与验收责任 | 请测试 Agent 验证补丁 |
| 结果回传 | 提交产物、证据和未解决问题 | 由任务负责人判断后续状态 | 返回测试报告 |
| 任务接管 | 继续同一个任务的后续执行 | 接手确认后转移该任务的执行责任 | 原 Agent 退出，由新 Agent 续接修复 |

这些术语是本文的设计约定，具体框架可能采用不同命名。实现时应以实际控制流与状态变化判断语义，避免仅凭工具名中出现 `handoff` 就推断发生了责任转移。

委派和接管都需要交接上下文，但它们更新的任务记录不同。委派通常创建一个子任务；接管更新同一个任务的执行者。后文所说的单一所有者，也仅约束一个可独立提交结果的任务，不禁止系统拆分并行子任务。

### 1.2 四个维度共同决定交接是否可执行

一次完整交接可以分成四个维度：

- **目标与约束**：用户希望完成什么，哪些条件必须满足。
- **工作状态**：已完成哪些步骤，哪些结论有证据，哪些问题仍然开放。
- **资源与能力**：接收方能否访问输入、工具、产物和必要环境。
- **执行责任**：谁可以继续写入、提交结果，以及谁负责验收。

其中，权限需要由授权系统验证。交接包可以声明需要哪些能力，但发送方在文本中写下“你有权限”并不会赋予接收方实际权限。

本文采用的接手标准是：接收方能够说明目标、定位有效状态、读取必要材料、执行明确的下一步，并获得运行时确认的执行资格。传输层收到消息只是其中一个前置条件。

### 1.3 跨 Agent 与跨会话具有共同问题，也有不同边界

同一 Agent 的新会话可能拥有相同角色和工具，却失去了上一轮的工作记忆；不同 Agent 可能理解相似的任务，却拥有不同文件系统、权限和利益诉求。

《Why Do Agent Teams Fail Across Boundaries?》研究具有私有状态、代表不同主体的 Agent 交互，将发现与委派、事实依据与记录一致性、验证、行为与忠实性纳入失败分析。其研究环境比单一组织内部的共享工作区更复杂，不能直接将内部协作中的“大家都能看到同一份数据”扩展为普遍假设。[3]

本文后续的原子责任转移方案假设存在一个各参与方认可的权威任务存储。跨组织且没有共同协调方的场景，需要另行协商责任确认与争议处理机制；一份统一 JSON 无法建立共同信任。

## 二、交接为什么失败：把论文发现转化为检查问题

### 2.1 从协作边界观察错误

AgentAsk 聚焦 Agent 之间的消息交接，将交互错误归纳为 Data Gap、Signal Corruption、Referential Drift 和 Capability Gap，并提出在交互边上进行有选择的澄清。其研究强调澄清收益与成本、延迟之间的取舍。[1]

这些分类可以转化为接收方的检查问题。下表中的例子与检查方式属于本文的工程解释：

| 论文中的错误类型 | 交接中的具体表现 | 接收方可以检查什么 |
|---|---|---|
| Data Gap，信息缺口 | 只说接口超时，没有复现条件 | 缺少的信息是否会改变下一步行动 |
| Signal Corruption，信号损坏 | “可能与重试有关”被摘要成“重试导致故障” | 结论的证据与确定程度是否被保留 |
| Referential Drift，指代漂移 | “按刚才的方案修改”指向已经替换的旧方案 | 对象、文件和版本是否有唯一引用 |
| Capability Gap，能力缺口 | 接手者不能访问数据库或执行测试 | 工具、数据和权限是否实际可用 |

接收方无需对每句话追问。优先澄清那些会改变执行对象、外部副作用或验收结论的信息。例如，缺少文章标题风格通常可以先继续整理资料；缺少目标代码版本则可能使修复工作落在错误分支上。

### 2.2 局部交接正确，整条任务链仍可能失败

《Why Do Multi-Agent LLM Systems Fail?》提出 MAST 失败分类，覆盖系统设计、Agent 间失配，以及任务验证等问题。这提供了一个更广的观察范围：交接消息的质量之外，还需要分析角色定义、协作过程和完成判定。[2]

据此，本文把交接链中的工程风险分成三层：

- 理解层：目标变形、约束遗漏、指代不明、推测被升级为事实。
- 执行层：产物不可访问、状态过期、能力不匹配、责任重复或空缺。
- 验收层：没有核对用户目标、缺乏验证证据、过早关闭任务。

例如，后端 Agent 正确理解了“减少超时”，也确实缩短了接口耗时，但如果验收没有包含重复提交问题，整个系统依然可能交付错误结果。交接质量需要同时接受局部检查和端到端验收。

### 2.3 消息能被解析，不代表信息仍然完整

《When Messages Go Wrong》研究多 Agent 系统中的通信故障，讨论消息丢失、延迟和上下文失效等扰动如何影响任务信息，并观察到部分语义错误不会立即表现为执行失败。其结果也关注未受影响的信息路径能否保留后续 Agent 所需的证据。[4]

这支持一个值得验证的工程方向：同时保留简洁交接内容与可独立访问的原始证据。例如，正文中出现“测试通过”，接收方还应能定位测试报告、运行参数与代码版本。

不过，保留多个文本副本不等于建立独立证据。如果几个副本都来自同一个错误摘要，它们只能重复同一个错误。设计时应尽量引用工具原始输出、产物版本或可复现的检查步骤。

## 三、交接包设计：让下一位知道从哪里继续

### 3.1 围绕下一步执行组织内容

交接包可以视为任务在某个版本上的可读快照。它既要帮助模型理解工作，也要给运行时提供可校验字段。

本文建议采用三部分组合：一段便于快速阅读的摘要、一份结构化任务状态，以及一组可定位的证据与产物引用。摘要负责解释，结构化状态负责约束，引用负责支持核验。

| 信息类别 | 建议内容 | 主要解决的问题 |
|---|---|---|
| 身份与版本 | 任务 ID、父任务 ID、交接 ID、协议版本、状态版本 | 确定正在处理哪一次交接 |
| 目标与范围 | 用户诉求、当前任务范围、约束、明确不包含的工作 | 防止任务范围漂移 |
| 验收条件 | 可观察的成功条件、验证方法、验收角色 | 避免用“做完了”代替证据 |
| 工作进展 | 已完成、进行中、未开始、阻塞项 | 定位续接起点 |
| 已尝试方案 | 方法、结果、失败原因、适用条件 | 减少无效重复探索 |
| 事实与假设 | 结论类别、来源、适用版本、待验证内容 | 防止推测变成事实 |
| 决策记录 | 选择的方案、简短理由、关键取舍 | 保留必要的决策依据 |
| 产物与证据 | 文件或对象引用、版本、完整性信息、读取方式 | 使交接内容可追溯 |
| 执行条件 | 工作区、代码版本、工具能力、权限要求 | 判断接收方能否执行 |
| 后续行动 | 第一个可执行步骤、依赖、失败时的出口 | 降低接手后的探索成本 |
| 副作用记录 | 已发起操作、操作标识、已知结果、未知结果 | 避免恢复时重复写入 |
| 交接控制 | 发送方、候选接收方、当前所有者、期限与预算 | 约束责任转移 |

这是一份字段清单，不要求所有任务都填满。一个只读资料归纳任务可以省略外部写入记录；一个跨服务下单任务则应保留操作标识与结果核对方式。

### 3.2 事实、假设和建议分别表达

下面三句话承担不同作用：

- 事实：某次测试中，相同业务键的两个请求生成了两条工单，证据是指定版本的测试报告。
- 假设：服务可能缺少针对该业务键的原子去重机制，需要检查写入路径。
- 建议：先增加并发复现用例，再决定约束位置和修复方案。

如果把它们压缩为“数据库有问题，增加唯一索引”，接收方会同时失去证据范围、未解决问题和方案选择空间。

交接时应保留可解释的决策摘要，例如“选择服务端幂等保护，因为不同客户端可能提交同一业务请求”。无需记录模型的完整内部推理；接收方需要的是可核验依据、关键取舍和行动约束。

### 3.3 已尝试但失败的工作也有价值

“尝试增加超时时间，未解决重复创建”是一条有用记录，但还需要说明它在哪个代码版本、什么场景下失败。否则，后续 Agent 可能错误地把一个局部结果理解为任何情况下都不应调整超时。

推荐把一次尝试记录为：尝试目的、输入条件、执行动作、观察结果、证据引用和下一步影响。对任务不再相关的探索可以放到详细日志，交接摘要只保留会影响后续选择的部分。

### 3.4 引用需要同时满足可定位、可读取和版本明确

发送方本地的 `./logs/test.log` 在接收方环境中可能不存在；对象地址能够打开，也可能对应不断覆盖的最新文件。

因此，关键引用应带上所属工作区或对象存储、不可变版本以及读取方式。代码至少明确提交版本；未提交补丁还需要独立保存差异和未跟踪文件，仅记录分支名不足以恢复工作区。敏感材料通过受控接口按权限读取，凭据由运行环境提供。

摘要中的状态还应指明“截至哪个任务版本”。接收方开始执行前，将其与权威记录比较；发现不一致时，重新加载状态或拒绝接手旧快照。

## 四、上下文传递：保留足够信息，也控制阅读成本

### 4.1 四种传递方式的取舍

以下是可供实验比较的设计选项，而非已有统一性能排序：

| 方式 | 传递内容 | 适合的条件 | 需要控制的问题 |
|---|---|---|---|
| 完整历史 | 对话、工具调用和结果 | 历史较短，需要回溯细节 | 无关探索、过期指令与阅读成本 |
| 自然语言摘要 | 目标、进度、结论、下一步 | 简短任务或低成本续接 | 压缩时遗漏约束或证据 |
| 结构化状态 | 固定字段描述的任务快照 | 需要校验、持久化和自动恢复 | 字段缺失、语义模糊、模式演进 |
| 按需检索 | 摘要加证据和产物索引 | 历史较长或资料较多 | 检索失败、访问受限、版本变化 |

本文建议从“摘要 + 结构化状态 + 原始证据索引”开始，按任务增加必要细节。这个选择需要通过后文的实验验证，不能预先承诺一定比完整历史更快或更准。

### 4.2 将上下文分成必须读取和按需读取两层

接收方在第一次行动前必须看到目标、硬约束、当前阶段、验收条件、已知阻塞，以及尚未确认的外部写入。详细日志、被放弃方案的完整过程和背景资料可以按需读取。

可以用一个简单问题检查压缩是否合理：删除某条信息后，接收方是否可能执行错误动作、重复副作用，或错误地宣布完成？如果答案是肯定的，就应保留这条信息或强制读取对应证据。

例如，“数据库请求的响应尚未返回”看似是一条过程细节，但它决定接收方能否重试创建操作，应该进入必读层。一次无关搜索的全部网页结果则通常可以留在检索层。

### 4.3 任务状态、项目知识与经验记忆分别管理

Agent Workflow Memory 研究从历史经历中归纳可复用工作流程，并将这些流程提供给后续任务中的 Agent。其研究以网页交互任务为主要实验场景，不直接证明任何跨 Agent 交接协议的效果。[7]

在本文设计中，可以据此区分三类内容：

| 类型 | 回答的问题 | 示例 |
|---|---|---|
| 当前任务状态 | 这一次工作进行到哪里 | 已复现重复创建，补丁尚未提交 |
| 项目知识 | 这个系统通常如何工作 | 工单服务使用的测试框架和目录结构 |
| 可复用经验 | 类似问题可以怎样处理 | 排查超时与重复写入时的核对流程 |

恢复任务优先读取当前任务状态；项目知识用于补足环境背景；经验记忆提供候选方法。不能仅因为历史经验推荐某条排查路径，就覆盖当前证据所反映的新情况。

## 五、交接流程：确认理解之后，再提交责任转移

### 5.1 将交接状态与任务状态分开

交接是否成功与任务是否完成是两个不同维度。一个任务可能处于修复中，而针对它的新交接正在等待澄清；交接被拒绝，也不意味着原任务已经失败。

本文为一次交接定义以下状态：

| 交接状态 | 含义 | 谁负责当前任务 |
|---|---|---|
| PREPARED | 快照与引用已经持久化，尚未正式提出 | 当前所有者 |
| OFFERED | 候选接收方已获邀检查 | 当前所有者 |
| NEEDS_INFO | 接收方提出影响执行的澄清问题 | 当前所有者 |
| ACCEPTED | 所有权更新已由权威存储提交 | 新所有者 |
| REJECTED | 候选接收方无法接手 | 当前所有者；必要时由协调器重新分派 |
| EXPIRED | 超过交接期限，旧邀约失效 | 以权威任务记录为准，由协调器处理恢复 |

任务状态单独记录为待执行、执行中、等待输入、待验收、完成或失败。交接被接受时，任务通常仍处于执行中。

交接状态与所有权更新应在同一个事务或等价的原子操作中生效。这样，`ACCEPTED` 的含义才与“接收方获得执行资格”一致。

### 5.2 一个可落地的正常流程

1. 发送方到达可交接检查点，保存产物、未完成动作和副作用记录。
2. 发送方生成交接包，记录任务版本与当前所有者代次，持久化后提出邀约。
3. 接收方校验格式、范围、环境能力和关键引用，读取必需证据。
4. 接收方用简短文字确认目标与首个执行动作；存在关键缺口时提出针对性澄清。
5. 运行时验证任务版本、接收资格与交接有效期，原子更新所有者和执行代次。
6. 新所有者读取已提交的状态后开始执行；旧所有者后续提交受到代次检查限制。
7. 执行结果提交后进入验收，验收方按任务契约决定完成、返工或进一步交接。

第 4 步只能暴露部分理解偏差。即使接收方能够复述目标，也不能据此认定它具备实际能力，因此还需要第 3 步的资源检查与最终结果验证。

澄清问题应指向具体决策。例如：“证据中的版本与目标分支不同，应在哪个版本修复？”比“请提供更多上下文”更容易得到可以执行的回答。交接中的选择性澄清受 AgentAsk 启发，但本节的持久化与责任提交流程是本文的工程设计。[1]

### 5.3 用版本和执行代次阻止过期提交

对于一个任务，本文设计要求权威记录在任一时刻最多认可一个活动执行所有者。可以采用以下简化条件更新：

```sql
UPDATE tasks
SET owner = :receiver,
    owner_epoch = owner_epoch + 1,
    version = version + 1
WHERE task_id = :task_id
  AND owner = :sender
  AND owner_epoch = :expected_epoch
  AND version = :expected_version
  AND status = 'ACTIVE';
```

受影响行数为 1 才说明这一步更新成功。实际实现还需要在同一事务中校验交接记录状态与有效期、接收方授权，并将交接标记为已接受；这里的 SQL 仅展示版本竞争的核心条件。

后续写入携带新的 `owner_epoch`。任务存储、产物提交入口或工具网关需要检查它，否则旧 Agent 即使已经失去所有权，仍可能凭旧上下文继续提交。这个检查只能约束经过受控入口的动作，无法自动停止已经发出的外部请求。

若系统需要检测失联，可以在此基础上加入租约。租约过期触发恢复判断，不证明旧进程已停止。重新分派后仍需要执行代次检查，并核对在途外部操作。

### 5.4 交接期间发生新进展怎么办

最简单的实现是让发送方在短暂交接窗口内暂停发起新的写入。它仍是责任人，但只处理澄清与已在途操作的核对。

如果任务必须继续执行，则每次影响下一步的状态变化都递增版本。旧交接包因此失效，发送方重新生成快照，接收方重新检查。不能在一边持续修改工作区的同时，默认对方看到的摘要一直有效。

当交接确认消息丢失时，新所有者也不应凭猜测启动。双方查询权威记录：如果转移已经提交，返回同一次交接结果；如果未提交，按原交接 ID 重试或按期限结束邀约。消息回执与任务记录共同使用，后者决定执行资格。

## 六、故障恢复：先查明已经发生什么

### 6.1 交接去重与业务操作去重分别处理

交接去重回答的是“这次所有权转移是否已经完成”。业务操作去重回答的是“这个创建请求是否已经产生了工单”。二者需要不同标识。

建议至少保留 `task_id`、`handoff_id` 和 `operation_id`。同一交接 ID 的重试返回已经记录的交接结果；同一业务意图的写入重试沿用稳定的操作标识。所有者代次可以变化，原业务操作标识应保持可追溯。

AWS Builders’ Library 的幂等 API 资料讨论了超时后结果不确定的问题，并介绍由调用方提供请求标识的设计。它还强调，仅根据请求参数推断重复可能误判调用者意图。[8]

据此，跨 Agent 重试应沿用原业务意图的操作标识，而不是由新 Agent 为同一次创建随机生成新标识。反过来，两个参数相同但业务意图不同的创建，也不能被合并为一次。

### 6.2 外部写入未知时，查询优先于再次执行

假设原 Agent 已发起创建工单请求，服务实际完成了写入，但响应在返回途中丢失。此时交接包应记录操作为 `UNKNOWN`，附上请求标识、目标环境、关键参数与已知时间，而不是简单标注“失败”。

接收方的第一步是通过操作标识查询业务结果。查到成功则补记已有产物；确认操作未生效且允许重试时，再用原操作标识重试。如果目标系统既不支持幂等，也不能可靠查询结果，就应进入人工核对或明确的业务补偿流程。

运行时的所有权更新只能决定谁有资格继续发起动作，无法回滚一个已经发到外部系统的请求。因此，交接确认之前应尽量收敛在途操作；无法收敛时，必须把未知状态作为接手后的优先处理事项。

### 6.3 按失败时点选择恢复动作

下表描述本文协议预期的恢复行为：

| 失败时点 | 权威记录中应看到什么 | 恢复动作 |
|---|---|---|
| 快照尚未保存，发送方退出 | 旧检查点与当前所有者 | 从最近持久化检查点恢复，再核对副作用 |
| 邀约已保存，通知丢失 | 交接为 OFFERED，所有者未变 | 用同一交接 ID 重发通知 |
| 接收方检查后退出，尚未接受 | 所有者仍为发送方 | 等待到期或按策略选择新候选方 |
| 所有权转移已提交，确认消息丢失 | 交接为 ACCEPTED，新所有者已生效 | 查询记录并返回既有结果 |
| 新所有者接手后退出 | 已接受交接与最新任务检查点 | 协调器发起新的接管，递增执行代次 |
| 旧 Agent 延迟提交产物 | 提交携带旧执行代次 | 拒绝覆盖；必要时作为候选证据保存 |
| 外部写入结果未知 | 操作记录为 UNKNOWN | 查询业务事实，禁止盲目重发 |
| 交接引用的文件被更新 | 快照版本与产物版本不一致 | 读取指定不可变版本或重新准备交接 |

任务更新与通知发送之间也可能发生中断。可以让协调器扫描待投递交接，或将通知事件与状态更新一起持久化，随后重试投递。接收方始终按交接 ID 去重，不能假设通知只会出现一次。

### 6.4 跨工作区和跨框架时，显式传递资源语义

在共享仓库内，代码引用可能只需要仓库标识、提交版本和补丁；跨工作区时，还要说明依赖、运行参数、文件访问路径与未跟踪产物。依赖浏览器会话的任务，则需要考虑登录状态、会话有效期及是否允许迁移。

跨框架交接还应声明协议版本和字段能力。接收方对未知的可选字段可以按约定忽略，但对无法理解的硬约束、验收条件或副作用状态，应拒绝自动执行并请求兼容表示。

对不同信任域的 Agent，收到的文本作为带来源的信息输入。权限由本地策略实施，关键结论按证据核验。这一点尤其适用于上游材料中夹带的新指令：引用文档可以提供事实，不能自行更改任务授权。

## 七、完整案例：从超时排查到重复创建修复

### 7.1 明确任务关系，保留端到端责任

继续使用开篇的教学案例。协调器持有父任务 `I-042`：“解决用户提交超时后重复生成工单的问题”。父任务验收包含结果正确性和相关性能回归。

前端 Agent 最初负责修复子任务 `T-042` 的排查阶段。发现需要检查后端写入路径后，它将同一个子任务交给后端 Agent 接管。后端形成补丁后，委派测试 Agent 执行独立验证子任务 `V-042`。

| 阶段 | 交互类型 | 责任变化 |
|---|---|---|
| 协调器分配排查与修复 | 委派 T-042 | 协调器保留 I-042 的整合责任 |
| 前端交给后端继续修复 | 接管 T-042 | T-042 所有者由前端变为后端 |
| 后端请求独立验证 | 委派 V-042 | 后端保留 T-042 的修复与整合责任 |
| 测试提交结果 | 结果回传 | 后端根据报告修正或提交验收 |
| 协调器关闭问题 | 父任务验收 | 按 I-042 的完整条件判定完成 |

测试失败时，后端仍负责修复，不会因为“已经交给测试”就失去责任。这个区分使交接链中的职责可以直接映射到任务记录。

### 7.2 一份信息不足的交接

> 接口超时，可能是后端问题。我已经看过前端了，你检查一下数据库，修好后让测试验一下。

接收方无法判断是哪一个接口、在哪个环境复现、检查过哪些前端行为、数据库原因是否已验证，以及什么结果才算修好。它也不知道原 Agent 是否还有未确认的写入。

改善这段文本的关键在于补齐执行所需的状态，而不是把同一段模糊判断写得更长。

后端 Agent 读取复现报告和父任务性能契约，确认拥有测试环境查询能力。如果某个关键引用无法读取，就将交接置为待补充信息，指出具体缺失内容。

检查完成后的确认可以写成：

这段确认提供语义检查材料，运行时仍需执行授权与版本校验。若校验通过，在本例中将所有者改为后端 Agent，任务版本从 12 递增到 13，执行代次从 3 递增到 4。

如果前端在此之前更新了复现结论，任务版本已变化，这次接受就应失败并重新读取状态。这样可以避免后端基于已过期的“没有其他变化”假设继续工作。

### 7.5 测试交接明确补丁版本与验证范围

假设后端随后形成一个候选补丁，它应创建 `V-042`，交给测试 Agent 的内容包括补丁版本、相关变更、验收条件及其对应测试、运行环境、已知限制，以及哪些测试尚未执行。

测试报告至少区分通过、失败、未执行和无法判定，并记录实际验证的代码版本。一个测试环境问题导致未执行的用例，不能被折算为通过。

如果补丁在测试之后又发生修改，报告仍然是旧版本的证据。验收方需要判断哪些结论仍有效，并补做受影响的验证。最终关闭父任务时，协调器核对用户现象、正确性、性能及剩余限制，而不是只收集一句“测试通过”。

## 八、如何评价交接机制是否有效

### 8.1 先建立可比较的实验组

可以设置以下四组，每组使用相同任务、模型配置、工具权限和验收方法：

| 实验组 | 上下文策略 | 研究问题 |
|---|---|---|
| A | 完整历史 | 保留原始信息需要多少成本，接收方能否找到关键内容 |
| B | 自然语言摘要 | 压缩节省的成本是否伴随约束或证据丢失 |
| C | 结构化交接包与证据索引 | 显式字段是否改善续接和状态恢复 |
| D | C 加选择性澄清 | 澄清的收益能否覆盖额外成本与等待时间 |

四组都保留相同的最小运行时责任控制和授权机制，避免把“交接文本更好”与“只有一组能阻止重复写入”混为一谈。若要研究执行代次或副作用日志，则另设协议消融实验，并在隔离环境内进行。

建议同时报告同预算下的成功率，以及达到同等成功标准时的成本。摘要生成、证据检索、澄清与失败重试都计入端到端开销。不能只统计接收方收到交接包之后的模型消耗。

### 8.2 指标需要有明确的分母

| 指标 | 建议定义 | 判定方式 |
|---|---|---|
| 端到端成功率 | 满足全部必需验收条件的任务数 / 总任务数 | 独立验收与产物检查 |
| 关键约束保留率 | 接收方可获取且正确表达的关键约束数 / 标注的关键约束总数 | 任务标注与交接内容比对 |
| 首次续接成功率 | 无需额外信息补充即可执行正确首步的交接数 / 总交接数 | 轨迹检查；与澄清收益联合解读 |
| 错误接受率 | 关键材料不满足接手条件却被接受的交接数 / 条件不满足的交接数 | 缺陷交接集与接受记录 |
| 无效重复工作率 | 被标注为不必要重复的步骤数 / 全部执行步骤数 | 区分必要复核和无效重做 |
| 恢复成功率 | 故障注入后恢复并满足验收的任务数 / 注入故障的任务数 | 故障实验与最终验收 |
| 重复副作用率 | 同一业务意图产生额外副作用的操作数 / 发起写入的业务操作数 | 外部业务记录核对 |
| 单个成功任务成本 | 全部尝试总成本 / 成功任务数 | 包含失败尝试、准备、检索与重试 |

成功任务数为零时，最后一个指标应标记为不可计算，同时报告总成本与零成功结果。恢复到人工处理虽然可能是正确降级，也应与自动恢复完成分开统计。

首次续接成功率不应被单独用作优化目标。一个主动发现缺口并澄清的 Agent，可能降低这个指标，却提高最终成功率。评价应优先考虑任务结果和副作用，再比较效率。

### 8.3 用故障注入验证边界

实验除了正常任务，还应覆盖以下情况：

- 从交接包移除一个会影响行动的验收条件。
- 把“待验证假设”改写为确定结论。
- 替换文件引用，使其指向过期但可读取的版本。
- 重复发送交接通知，或丢弃接手确认消息。
- 在所有权提交前、提交后和外部写入后分别终止进程。
- 让旧执行者在重新分派后继续提交产物。
- 撤销一个必要工具能力，观察接收方是否报告阻塞。
- 让写入完成但响应丢失，检查是否先查询结果。

对每个故障预先定义正确行为。例如，缺少必要权限时，正确结果可能是拒绝接手并报告阻塞；它不应被要求绕过权限完成任务。

多次交接实验可以采用 1、3、5 次交接等预先选定的条件，观察关键约束和证据引用的保留情况。这些次数只是实验配置，不能预设错误会按某个固定公式累积。

对于模型输出的不确定性，应进行重复运行，报告样本量、配置、分组结果及不确定区间。语义性判断可以结合独立评审与人工抽样；明确的文件版本、状态变化和业务记录尽量自动核对。本文没有执行这些实验，也不报告未经测量的提升比例。

## 九、从文档模板到运行时能力

### 9.1 先实现一条可以完整验收的交接链

AutoGen 论文以可定制 Agent 之间的对话构建应用，展示了可编程交互模式；MetaGPT 则将标准化工作流程和专业角色引入多 Agent 协作，并强调中间结果的检查。这两类工作分别为交互组织和产物协作提供背景，但不能据此推断任何框架已自动实现本文的责任转移与恢复语义。[5][6]

实际落地可以分三个阶段：

| 阶段 | 实现内容 | 需要证明的能力 |
|---|---|---|
| 可读交接 | 目标、状态、证据、下一步与接手确认 | 新 Agent 能在必要材料充分时继续任务 |
| 可恢复交接 | 持久化任务记录、版本检查、交接去重、操作日志 | 中断后能够确定所有者和已发生的业务动作 |
| 可评估交接 | 故障注入、质量指标、成本统计与独立验收 | 能比较不同策略，并定位失败环节 |

不必在开始时支持任意组织、任意框架和任意任务。可以先选择固定角色、固定工具、隔离环境中的一条修复链，把状态变化与验收证据跑通，再扩展能力。

### 9.2 把判断职责分配给合适的组件

本文建议 Agent 负责解释目标、提炼状态、提出问题和生成候选方案；运行时负责版本、期限、所有者与状态迁移；工具网关负责能力与授权检查；产物存储保存可定位版本；验收组件按任务契约判断结果。

这样，Agent 可以判断“信息不足，需要澄清”，但不能靠一段自然语言覆盖过期版本，也不能通过宣布完成直接跳过必需验收。

流程日志至少记录任务 ID、交接 ID、父子关系、发送方与接收方、前后状态版本、执行代次、澄清理由、产物引用、外部操作状态和验收结果。记录足以重建事件顺序的结构化信息即可，不需要把所有原始上下文无差别复制到日志。

### 9.4 后续值得研究的问题

首先是如何判断信息已经足够。固定字段可以检查缺失，但无法完全判断某段语义是否足以支持正确行动。一个可研究方向是让接收方提出首步计划，再检查该计划的依据是否齐全。

其次是如何在预算内选择澄清对象。缺失信息可能存在于发送方、原始日志或外部系统中。系统可以比较查询成本、信息可靠性与任务影响，再决定向谁询问。

第三是如何处理长链路中的状态演进。任务跨越多个角色后，原始约束、后来修正的假设和新增验收条件需要保留明确来源与版本关系，避免被逐轮摘要抹平。

第四是如何在没有共同协调方的情况下确认责任。跨组织交接可能需要双方各自保留承诺与证据，并就超时、拒绝、撤销和争议解决达成协议。这超出本文共享权威任务存储的假设，需要单独设计和验证。

实施时可以从一个具体检查开始：让新的 Agent 只读取交接包与其中允许访问的证据，验证它能否说明当前目标、找到真实进展、识别未完成副作用，并执行正确的第一步。随后在交接前后注入一次中断，检查恢复后的行为是否仍满足同一组验收条件。

## 参考文献与适用边界

以下资料均在 2026 年 10 月 23 日核验了论文页面或官方正文。年份按所列来源的公开时间标注；两篇 2026 年 10 月论文按 arXiv 预印本引用。本文主要采用可核实的研究问题与方法描述，不复述未经本文复现的性能数字。

1. **AgentAsk: Multi-Agent Systems Need to Ask.** ACL 2026，长文论文集，2026 年 7 月，DOI：`10.18653/v1/2026.acl-long.1294`。[论文页面](https://aclanthology.org/2026.acl-long.1294/)。直接讨论 Agent 交互边上的错误和选择性澄清，支撑第二章及第五章的澄清设计；本文的持久化状态协议不属于该论文结论。

2. **Why Do Multi-Agent LLM Systems Fail?** arXiv:2503.13657，首次提交于 2025 年 3 月 17 日。[论文页面](https://arxiv.org/abs/2503.13657)。提出 MAST 失败分类，支撑对系统设计、Agent 间失配与任务验证的讨论；分类结果不能单独证明某种修复机制的效果。

3. **Why Do Agent Teams Fail Across Boundaries? A Failure Taxonomy for Agent-to-Agent Systems with Private States.** arXiv:2610.19342，首次提交于 2026 年 10 月 14 日，页面列示 v2 于 10 月 15 日修订。[论文页面](https://arxiv.org/abs/2610.19342)。研究不同主体、私有状态下的 Agent 交互，支撑共享工作区假设和验证边界的讨论；预印本结果应在其研究环境内解读。

4. **When Messages Go Wrong: Understanding Communication Faults in LLM-Based Multi-Agent Systems.** arXiv:2610.15459，首次提交于 2026 年 10 月 11 日。[论文页面](https://arxiv.org/abs/2610.15459)。研究通信故障及其传播，支撑原始证据保留和故障注入的设计动机；不据其特定实验推导普遍最优的协作拓扑。

5. **MetaGPT: Meta Programming for A Multi-Agent Collaborative Framework.** arXiv:2308.00352，首次提交于 2023 年 8 月 1 日。[论文页面](https://arxiv.org/abs/2308.00352)。提供标准化流程、角色分工和中间结果检查的研究背景，不作为跨运行时所有权一致性的证明。

6. **AutoGen: Enabling Next-Gen LLM Applications via Multi-Agent Conversation.** arXiv:2308.08155，首次提交于 2023 年 8 月 16 日。[论文页面](https://arxiv.org/abs/2308.08155)。提供可编程 Agent 交互模式的背景；本文引用论文，不依赖当前软件版本的具体 API 行为。

7. **Agent Workflow Memory.** arXiv:2409.07429，首次提交于 2024 年 9 月 11 日。[论文页面](https://arxiv.org/abs/2409.07429)。研究可复用流程记忆，间接支持区分当前任务状态与历史经验；其主要实验属于网页交互，不直接检验本文交接方案。

8. **Making retries safe with idempotent APIs.** AWS Builders’ Library，官方工程资料。[原文](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)。用于解释请求标识、重试与外部副作用，不属于多 Agent 交接的实验论文。
