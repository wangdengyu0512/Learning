只会调用大模型 API 的程序，还不能算一个完整的 Agent。

模型可以生成文本、选择工具、拆解任务，但它并不天然拥有文件系统、Shell、浏览器、长期会话、失败恢复与多智能体协作能力。真正把“模型的一次推理”变成“能够持续完成任务的系统”的，是模型外部那层运行时：它负责连接工具、管理状态、约束副作用、恢复中断任务，并决定整个执行循环何时继续、何时停止。

这层运行时通常被称为 **harness**。

如果说 LLM 是 Agent 的推理引擎，那么 harness 更像它的操作系统与控制平面：模型负责提出下一步行动，harness 负责让行动在真实世界中安全、可追踪、可恢复地发生。

本文根据《DeepSeek Harness 前沿工程实践》课程大纲展开，围绕一条主线讨论：

```text
可组合的插件运行时
        ↓
工具、沙箱与会话基础设施
        ↓
单 Agent 循环与多 Agent 编排
        ↓
从失败中生成、评测并发布新规则
```

重点不是罗列框架 API，而是理解其背后的工程设计：**为什么副作用必须可撤销，为什么会话应该事件化，为什么上下文压缩不能等同于粗暴截断，以及自进化为什么首先是一个发布治理问题。**

> **资料边界**：本文以用户提供的大纲为内容依据，写作日期为 **2026 年 10 月 7 日**，没有对框架仓库、API 名称和当前版本状态做联网核验。文中的 TypeScript 均为架构示意代码，不应直接视为 DeepSeek Harness 或 Cordis 的真实接口声明。

## 一、先理解 Harness：模型之外的“确定性世界”

一个最小的大模型调用通常只有输入与输出：

```text
prompt → model → response
```

但一个真正执行任务的 Agent 至少还要处理以下问题：

- 模型想调用工具时，谁负责参数校验与真实执行？
- 工具能否读写任意文件、启动任意进程？
- 任务执行到一半崩溃，怎样从中断位置恢复？
- 对话超出上下文窗口后，哪些信息应该保留？
- 一个复杂任务如何拆给多个子 Agent？
- 插件更新时，旧监听器、定时器和资源怎样清理？
- Agent 从失败中总结出的新规则，如何评测、审核和回滚？

因此，生产级 Agent 的真实结构更接近：

```text
用户 / 外部事件
       ↓
┌──────────────────────────────────────┐
│              Agent Harness           │
│                                      │
│  会话状态 ──> Agent Loop ──> 模型    │
│      ↑             │          │       │
│      │             ↓          │       │
│  日志与投影 <── 工具调度 <────┘       │
│                    │                  │
│          权限 / 守卫 / 沙箱            │
│                    │                  │
│          文件、Shell、网络、业务 API   │
└──────────────────────────────────────┘
       ↓
持久化、审计、评测与恢复
```

这里存在一条非常重要的责任边界：

- **模型负责概率性决策**：理解任务、选择工具、生成参数、判断下一步；
- **Harness 负责确定性控制**：权限、生命周期、超时、重试、终止、日志和恢复；
- **工具负责真实副作用**：修改文件、执行命令、调用系统、发送消息；
- **治理系统负责风险收敛**：审批、审计、评测、灰度、回滚。

Harness 的价值，不是替模型“变聪明”，而是把不稳定的概率输出放进一个可控的工程系统。

## 二、Cordis 的核心：把副作用纳入生命周期

按照课程大纲，DeepSeek Harness 的底层建立在 Cordis 插件框架之上。它的核心思想可以概括为三句话：

1. 一切能力都可以被组织成插件；
2. 插件产生的副作用必须能够撤销；
3. 插件之间通过上下文、服务和事件协作，而不是彼此硬编码。

这三个原则解决的是同一个问题：**怎样让一个长期运行、持续变化的 Agent 系统仍然保持可组合、可更新和可回收。**

### 1. Context 不是全局变量，而是能力作用域

很多插件系统最后都会退化成一个巨大的全局对象：所有模块都可以随意读写，依赖关系隐藏在代码深处，启动顺序一变就报错。

更健康的 Context 应该承担三种职责：

- 提供当前作用域可见的服务；
- 记录插件注册的资源与清理逻辑；
- 建立父子上下文，使能力可以继承，也可以隔离。

可以把它理解成“带生命周期的依赖容器”：

```ts
// 架构示意，不对应真实 API
interface RuntimeContext {
  provide<T>(name: string, service: T): Disposable;
  on(event: string, listener: (...args: unknown[]) => void): Disposable;
  effect(setup: () => void | (() => void)): Disposable;
  fork(scope: string): RuntimeContext;
}
```

Context 的关键不是“能存多少对象”，而是它知道这些对象属于谁，以及在插件离开时应该清理什么。

### 2. Effect：所有副作用都要有反向操作

监听事件、启动定时器、注册路由、打开文件、创建临时目录、占用端口，这些操作都会改变进程或外部环境。如果插件卸载时只删除代码引用，而没有撤销这些副作用，就会出现：

- 同一监听器被重复注册；
- 热重载后一个任务执行多次；
- 定时器和连接不断泄漏；
- 新旧版本同时响应事件；
- 测试之间互相污染。

因此，一个 Effect 应当同时描述“做什么”和“怎样撤销”：

```ts
// 架构示意
ctx.effect(() => {
  const timer = setInterval(flushMetrics, 5_000);

  return () => {
    clearInterval(timer);
  };
});
```

更复杂的工具插件也应遵循同样的结构：

```ts
ctx.effect(() => {
  const unregister = toolRegistry.register("search_code", searchCode);
  const tempDir = createWorkspace();

  return () => {
    unregister();
    removeWorkspace(tempDir);
  };
});
```

这背后是一种很实用的工程纪律：

> 每当代码执行一个“向前动作”，都要追问它的“反向动作”是什么。

只有副作用可逆，热重载、动态配置、测试隔离和故障恢复才有可靠基础。

### 3. Service 与 inject：依赖应该显式声明

插件不应直接从全局单例中抓取数据库、模型客户端或工具注册表，而应声明自己需要什么能力：

```ts
// 架构示意
const sessionPlugin = definePlugin({
  inject: ["storage", "logger"],
  apply(ctx) {
    const storage = ctx.service("storage");
    const logger = ctx.service("logger");
    // ...
  },
});
```

显式依赖带来几个直接收益：

- 启动时可以检查依赖是否满足；
- 测试时可以替换为内存实现；
- 服务变更时可以触发依赖插件重新装配；
- 插件不再依赖隐含的初始化顺序；
- 能够画出真正的运行时依赖图。

所谓“响应式依赖”，本质上是把依赖变化也纳入生命周期：当某项服务被替换或失效时，消费者不继续握着陈旧引用，而是重新绑定，或者进入明确的不可用状态。

### 4. 事件系统：解耦不等于只有广播

Agent 运行时中的事件并不都是“通知所有人”。不同业务语义需要不同分发模式。虽然具体框架命名可能不同，但工程上常见的五类语义包括：

| 分发语义 | 处理方式 | 适用场景 |
| --- | --- | --- |
| 广播 | 所有监听者都收到 | 指标、审计、状态变更通知 |
| 串行 | 按顺序逐个执行 | 有顺序要求的生命周期钩子 |
| 并行 | 多个处理器同时执行 | 彼此独立的读取或通知任务 |
| 短路 | 某个处理器给出结果后停止 | 权限判断、路由选择、缓存命中 |
| 瀑布流 | 前一个输出成为后一个输入 | prompt 增强、参数归一化、结果后处理 |

例如，工具调用前的处理更适合瀑布流：

```text
原始调用请求
   ↓ schema 校验
规范化参数
   ↓ 权限守卫
带授权上下文的请求
   ↓ 风险分类
执行计划
```

而审计事件更适合广播：执行完成后，指标、日志、追踪和会话记录可以分别订阅同一事件，彼此不必直接依赖。

### 5. 插件树、隔离与 HMR

当所有能力都是插件后，系统不再是平铺的模块列表，而是一棵插件树：

```text
runtime
├─ model-provider
├─ session
│  ├─ append-only-log
│  ├─ projection
│  └─ compaction
├─ tools
│  ├─ filesystem
│  ├─ shell
│  └─ browser
└─ agents
   ├─ planner
   ├─ coder
   └─ reviewer
```

插件树至少应支持三件事：

- **声明式配置**：用配置描述装配关系，而不是把全部启动逻辑写死；
- **隔离**：同名服务或工具可以在不同子树中拥有不同实例和权限；
- **热替换**：卸载旧插件、撤销 Effect，再加载新实现。

热重载真正困难的地方并不是重新执行一段代码，而是保证旧版本已经彻底退出。可逆 Effect 解决“清理”，作用域 Context 解决“边界”，显式依赖解决“重新装配”，三者共同组成 HMR 的基础。

## 三、Capability Seam：把外部能力接到模型世界

模型看到的工具描述，与系统里真正执行的能力之间，需要一条清晰的接缝。大纲将其称为 **Capability Seam**。

这条接缝不应只是一个 `Map<string, Function>`。一个生产级工具定义通常至少需要包含：

```ts
// 架构示意
interface ToolCapability<Input, Output> {
  name: string;
  description: string;
  inputSchema: JsonSchema;
  risk: "read" | "write" | "destructive";
  timeoutMs: number;
  idempotent: boolean;
  execute(input: Input, ctx: ExecutionContext): Promise<Output>;
}
```

这些元数据分别服务于不同角色：

- `description` 和 `inputSchema` 帮助模型正确选择工具；
- `risk` 帮助策略系统决定是否需要批准；
- `timeoutMs` 保护运行时不被无限阻塞；
- `idempotent` 决定失败后能否安全重试；
- `ExecutionContext` 承载用户身份、会话、工作目录、取消信号和审计信息。

工具系统的目标不是“让模型什么都能做”，而是把能力切成**最小、清晰、可授权、可观察的执行单元**。

### 一次工具调用应该经过完整流水线

```text
模型生成调用意图
       ↓
工具名称解析
       ↓
Schema 与语义校验
       ↓
身份、权限与风险守卫
       ↓
参数规范化 / 路径解析
       ↓
沙箱或远程执行器
       ↓
超时、取消、重试、幂等控制
       ↓
输出截断、脱敏、外部持久化
       ↓
结果写入会话日志并回填模型
```

任何绕开这条流水线的“快捷调用”，都可能成为权限、审计或恢复上的缺口。

### Code Mode 不等于无限制执行代码

让模型生成代码，再由运行时执行，能够降低大量细粒度工具调用的往返成本。例如，模型可以一次生成一段脚本，在受限环境中完成数据转换，而不是逐行请求工具。

但 Code Mode 会把风险集中到执行器上。至少要明确以下边界：

- 能访问哪些目录；
- 是否允许网络；
- 可以启动哪些进程；
- CPU、内存、磁盘与执行时间上限；
- 环境变量和密钥是否可见；
- 产生的文件如何回收；
- 哪些高风险动作仍需人工确认。

一个可靠原则是：

> 模型可以自由生成候选代码，但不能自由决定代码在什么权限下运行。

## 四、跨平台沙箱：隔离能力必须说明威胁模型

“在沙箱中执行”不是一个二值属性。不同隔离技术防御的威胁不同，不应只用一个 `sandbox: true` 配置掩盖差异。

| 层级 | 可采用的机制 | 主要解决的问题 | 仍需警惕 |
| --- | --- | --- | --- |
| 进程级 | 独立子进程、低权限账户 | 崩溃隔离、基础权限分离 | 内核共享、文件与网络边界不足 |
| 文件级 | 工作目录白名单、只读挂载 | 限制文件访问范围 | 符号链接、路径穿越、宿主挂载错误 |
| 资源级 | CPU、内存、进程数、超时配额 | 防止资源耗尽 | 配额配置不完整 |
| 网络级 | 默认断网、域名或出口白名单 | 防止数据外传与任意下载 | DNS、代理与内网访问 |
| 容器级 | namespace、cgroup、seccomp 等 | 更强的系统调用与资源隔离 | 容器并非虚拟机，配置错误仍可逃逸 |
| 虚拟化级 | 轻量 VM 或独立执行节点 | 强隔离与租户边界 | 启动成本、镜像治理与运维复杂度 |

Linux、macOS 与 Windows 的底层隔离机制不同，因此“跨平台”更合理的设计不是伪装成完全一致，而是：

1. 对上提供统一的执行契约；
2. 对下使用各平台适合的隔离后端；
3. 显式暴露当前后端的能力等级；
4. 当安全要求无法满足时拒绝降级执行。

例如，一个要求“无网络、只读仓库、不可见宿主密钥”的任务，如果当前平台执行器只能提供工作目录约束，就应该报告能力不足，而不是静默地以较弱隔离运行。

## 五、会话不是聊天记录，而是可恢复的事件历史

许多 Agent 系统把会话保存为一段不断增长的消息数组：

```ts
messages.push(userMessage);
messages.push(assistantMessage);
```

这种表示适合原型，却很难回答生产问题：某次工具调用到底有没有执行？参数经过了哪些修改？结果是否因超时而被丢弃？压缩前的原始内容还能否恢复？任务是从哪个父会话分叉出来的？

更稳健的做法是使用 **Append-Only Log**：所有重要变化都记录为不可变事件。

```ts
// 架构示意
interface SessionEvent {
  id: string;
  sessionId: string;
  parentEventId?: string;
  type:
    | "user.message"
    | "model.requested"
    | "model.responded"
    | "tool.requested"
    | "tool.started"
    | "tool.completed"
    | "tool.failed"
    | "context.compacted"
    | "goal.updated";
  timestamp: string;
  payload: unknown;
}
```

日志只追加，不原地修改。当前会话状态则由 Projection 投影出来：

```text
不可变事件日志
    ├─> 对话投影：给模型看的消息
    ├─> 工具投影：调用状态、耗时、错误
    ├─> 目标投影：当前目标与完成度
    ├─> 审计投影：谁在何时执行了什么
    └─> UI 投影：时间线、分支与运行状态
```

### 为什么 Projection 很重要

同一份原始日志可以服务于不同用途，而不需要把所有信息都塞进 prompt：

- 模型只看与当前决策有关的内容；
- 运维界面展示完整执行链；
- 审计系统保留原始输入、批准与副作用；
- 指标系统只统计时延、token、成功率；
- 调试工具可以重放某段历史。

日志是真相来源，消息数组只是其中一种视图。

### Fork、Resume 与崩溃修复

事件化会话让三个高级能力变得自然：

**Fork**：从某个历史事件创建新分支，保留共同祖先，但后续独立演化。

```text
A ─ B ─ C ─ D
        ├─ E ─ F    方案一
        └─ G ─ H    方案二
```

**Resume**：重建投影，找到最后一个稳定检查点，从未完成步骤继续。

**崩溃修复**：识别“已请求但未确认完成”的工具调用，根据工具幂等性决定重试、查询外部状态或交给人工处理。

这里最危险的情况是：外部操作已经成功，但进程在写入 `tool.completed` 前崩溃。如果工具不是幂等的，盲目重试可能导致重复付款、重复发信或重复创建资源。因此恢复机制必须结合：

- 幂等键；
- 外部状态查询；
- 明确的调用状态机；
- 高风险操作的人工仲裁。

## 六、上下文管理：压缩不是把旧消息删掉

长任务迟早会超过模型上下文窗口。最简单的方案是删除最早消息，但它可能一起删掉目标、约束、关键决策与失败经验。

更可靠的上下文管理需要先区分不同信息：

| 信息类型 | 示例 | 处理策略 |
| --- | --- | --- |
| 稳定目标 | 要交付什么、验收标准 | 始终保留或结构化存储 |
| 关键约束 | 不可修改某目录、禁止联网 | 高优先级保留 |
| 当前计划 | 正在执行的步骤 | 随进展更新 |
| 决策记录 | 为什么选择某方案 | 摘要后保留依据 |
| 原始工具输出 | 构建日志、搜索结果 | 外部存储，按需引用 |
| 已完成细节 | 中间推理与重复观察 | 压缩或淘汰 |
| 失败经验 | 哪些尝试无效 | 提炼结论，避免重复 |

一个可操作的 compaction 流程是：

```text
计算 token 水位
    ↓ 超过软阈值
冻结当前事件区间
    ↓
抽取目标、约束、决定、未完成事项、关键证据
    ↓
生成结构化摘要并校验
    ↓
保存 summary 与原始日志区间映射
    ↓
新上下文 = 稳定状态 + 摘要 + 最近事件
```

压缩后仍应保留“回到原文”的能力。摘要是工作视图，不应覆盖原始日志。

### 大型工具输出应该外部持久化

把完整构建日志、几万行搜索结果或二进制附件直接放入上下文，会迅速制造 token 浪费和注意力干扰。更好的方式是保存引用：

```json
{
  "artifact_id": "artifact_01J...",
  "kind": "build-log",
  "size": 284193,
  "preview": "TypeScript compilation failed with 3 errors...",
  "query_hint": "可按文件名或错误码检索"
}
```

模型先读取摘要和索引，只有确实需要时才请求局部内容。这样，**会话日志记录发生了什么，制品存储保存大对象，prompt 只装载当前有用的信息。**

### 跨会话搜索与谱系追踪

当会话可以 Fork，系统就不再只有一条聊天时间线，而会形成任务谱系。跨会话能力应支持：

- 按关键词或语义搜索历史事件；
- 查询某次任务的父会话与子分支；
- 追踪某条规则、代码或决策从哪里产生；
- 对比不同分支的结果与成本；
- 找到过去相似失败及其修复方式。

谱系不是附属 UI，而是 Agent 复用经验、评估策略和解释结果的基础数据结构。

## 七、从 Agent Loop 到长任务执行

有了工具、会话与上下文，才能建立真正可靠的 Agent Loop：

```text
读取目标和当前状态
       ↓
构造本轮上下文
       ↓
调用模型
       ↓
模型给出最终答案？ ──是──> 完成
       │
       否
       ↓
解析一个或多个工具请求
       ↓
守卫、批准、执行、记录
       ↓
将结果更新到会话状态
       └──────────────────↺
```

一个循环控制器需要比 `while (true)` 多考虑很多事情：

```ts
// 架构示意
while (!goal.isTerminal()) {
  budget.assertAvailable();
  cancellation.throwIfRequested();

  const context = await contextBuilder.build(session, goal);
  const decision = await model.decide(context);

  if (decision.type === "final") {
    await goal.complete(decision.output);
    break;
  }

  const results = await toolRunner.execute(decision.calls, {
    session,
    policy,
    sandbox,
    cancellation,
  });

  await session.append(results);
  await checkpoint.maybeSave(session, goal);
}
```

必须存在的控制项包括：

- 最大循环次数；
- token、时间与费用预算；
- 全局取消信号；
- 工具并发上限；
- 连续失败熔断；
- 重复动作检测；
- 人工批准节点；
- 完成与失败的明确状态。

没有这些约束，Agent Loop 只是一个可能无限消耗资源的概率循环。

### Preset：把角色、工具与权限打包

Agent Preset 可以把以下内容预组装为一个可复用角色：

- system prompt 与行为约束；
- 可用工具集合；
- 默认模型与参数；
- 沙箱等级；
- 费用与时间预算；
- 可访问的数据范围；
- 是否允许创建子 Agent；
- 输出格式和完成条件。

例如，“代码审查 Agent”应当默认拥有只读仓库权限，而不是继承“编码 Agent”的写文件能力。Preset 的价值不仅是方便创建角色，更是把**最小权限原则**固化到装配层。

### Goal：长任务的稳定锚点

对话历史会增长、压缩甚至分叉，但目标必须保持稳定。一个 Goal 至少应描述：

```ts
interface Goal {
  objective: string;
  acceptanceCriteria: string[];
  constraints: string[];
  status: "active" | "completed" | "failed" | "cancelled";
  progress: Array<{ item: string; state: string }>;
  budget: { tokens?: number; seconds?: number; cost?: number };
}
```

自动续跑不是简单地“再次调用模型”，而是：

1. 恢复 Goal；
2. 重建最新 Projection；
3. 找到未完成工作；
4. 检查预算与外部状态；
5. 从稳定检查点继续。

只要目标和进度被结构化保存，系统就不必依赖模型从一长串自然语言里猜测“我们做到哪了”。

## 八、Subagent：委派不是多开几个聊天窗口

子 Agent 适合处理可以清楚切分、彼此弱依赖的子任务，例如：

- 一个 Agent 检索文档；
- 一个 Agent 分析代码；
- 一个 Agent 设计测试；
- 一个 Agent 审查最终方案。

但 Subagent 需要严格定义继承与回收规则。

### 创建时继承什么

主 Agent 不应把全部上下文原样复制给子 Agent，而应只传递：

- 子目标与验收标准；
- 必需背景；
- 允许使用的工具；
- 权限和预算；
- 结果返回格式；
- 截止时间与取消信号。

### 执行时如何隔离

每个子 Agent 应拥有独立的：

- 会话分支；
- 工作目录或命名空间；
- token 与时间预算；
- 工具并发配额；
- 日志与追踪标识。

### 结束后怎样回收

子 Agent 完成、失败或被取消后，应撤销插件 Effect、停止进程、释放临时目录、关闭连接，并把结果压缩成主 Agent 可消费的结构，而不是把完整轨迹全部倒回主上下文。

```text
主 Agent
├─ 子任务 A ──> 结构化结论 A
├─ 子任务 B ──> 结构化结论 B
└─ 子任务 C ──> 结构化结论 C
        ↓
主 Agent 汇总、验证并做最终决策
```

如果没有预算隔离与回收机制，多 Agent 只会把单 Agent 的失控成本放大。

## 九、Workflow 与 Ralph：自主规划和固定策略的取舍

大纲区分了两种编排思路：模型驱动的 Workflow，以及固定策略的 Ralph。可以把它们理解为一条连续谱的两端。

### 模型驱动 Workflow

模型根据当前状态动态决定下一步，优点是灵活，适合：

- 开放式研究；
- 未知步骤较多的排障；
- 需求不断变化的复杂任务；
- 需要根据观察即时调整计划的场景。

代价是路径不稳定、成本难预测、评测更困难。

### 固定策略 Ralph

由程序规定循环结构、检查项和退出条件，模型只在局部节点做判断。它适合：

- 代码生成—测试—修复循环；
- 固定格式的数据处理；
- 强合规业务流程；
- 可枚举状态的运维操作。

优点是稳定、可测、容易设置硬边界；缺点是面对新情况时缺少灵活性。

工程上通常不必二选一。更可靠的方案是：

```text
确定性状态机控制主流程
        ↓
在有限节点调用模型做语义判断
        ↓
所有副作用仍通过工具守卫执行
```

也就是让模型负责“难以规则化的判断”，让代码负责“不能失控的流程”。

## 十、规则自进化：核心不是生成规则，而是安全发布规则

课程最高阶部分是 Agent 规则系统：Agent 从异常和失败中生成候选规则，经过评测与确认后进入运行时。

这听起来像“Agent 修改自己”，但从工程视角看，它更像一条特殊的软件交付流水线：

```text
线上异常 / 低分轨迹
        ↓
归因与案例聚类
        ↓
生成候选规则
        ↓
静态检查与冲突检测
        ↓
历史数据回放评测
        ↓
人工确认或自动门禁
        ↓
灰度发布
        ↓
持续监控
   ┌────┴────┐
指标提升    指标恶化
   ↓          ↓
扩大流量      自动回滚
```

### 1. 规则应该是有边界的数据对象

不要让模型任意重写核心运行时代码。更安全的方式是定义受约束的规则格式：

```ts
interface AgentRule {
  id: string;
  version: number;
  trigger: {
    event: string;
    condition: string;
  };
  action: {
    type: "add_guard" | "rewrite_input" | "require_approval" | "select_tool";
    config: Record<string, unknown>;
  };
  scope: {
    agentPreset?: string;
    tool?: string;
    tenant?: string;
  };
  provenance: {
    sourceSessions: string[];
    generatedBy: string;
    createdAt: string;
  };
  status: "candidate" | "approved" | "canary" | "active" | "retired";
}
```

规则是插件，意味着它也应该拥有明确的装载、卸载和 Effect 回滚过程。

### 2. 从异常中生成候选规则

不是每次失败都值得产生新规则。候选生成前应先判断：

- 这是偶发工具故障，还是可复现的策略缺陷？
- 现有规则是否已经覆盖，只是执行失败？
- 新规则会不会只修复一个样本，却伤害大量正常请求？
- 问题应该由 prompt、工具 schema、权限策略还是业务代码解决？

好的候选规则需要绑定证据：来源会话、失败类型、预期改善指标与潜在影响范围。

### 3. 评测必须同时观察收益与副作用

只检查“原失败案例是否通过”远远不够。至少需要四类数据集：

| 数据集 | 目的 |
| --- | --- |
| 失败回放集 | 验证规则能否修复目标问题 |
| 正常基线集 | 检查是否破坏原有成功路径 |
| 对抗与边界集 | 检查规则能否被绕过或误触发 |
| 成本性能集 | 检查 token、时延和工具调用是否恶化 |

可以将发布条件写成明确门槛：

```text
目标失败集成功率提升 ≥ 20%
正常基线集回归 ≤ 1%
高风险误执行次数 = 0
平均成本增幅 ≤ 5%
P95 时延增幅 ≤ 10%
```

具体阈值应由业务风险决定，但原则不变：**规则进化必须通过可重复评测，而不是凭一次成功案例上线。**

### 4. 确认、灰度与回滚

低风险的格式修正规则可以自动通过，高风险的权限、写操作和外部通信规则则应要求人工确认。发布后还要支持：

- 按租户、用户或流量比例灰度；
- 新旧版本并行对比；
- 记录每次命中与决策原因；
- 指标恶化自动撤销；
- 一键恢复到上一个稳定版本。

可逆插件机制在这里再次发挥作用：规则不仅能动态加载，也能无痕卸载。自进化系统真正依赖的，不是“模型会写规则”，而是底层运行时拥有可靠的生命周期与回滚能力。

## 十一、把各部分组合成一张生产架构图

将前面的机制放在一起，可以得到一个较完整的参考架构：

```text
┌──────────────────── 接入层 ────────────────────┐
│ API / Chat / IDE / Webhook / Scheduled Event  │
└─────────────────────────┬──────────────────────┘
                          ↓
┌────────────────── Agent 控制平面 ──────────────┐
│ Goal Manager                                 │
│ Preset / Policy / Budget                     │
│ Workflow / Ralph / Subagent Coordinator      │
└─────────────────────────┬──────────────────────┘
                          ↓
┌──────────────────── Agent Loop ────────────────┐
│ Context Builder → Model → Decision Parser     │
│       ↑                         ↓             │
│ Projection ← Session Events ← Tool Results    │
└─────────────────────────┬──────────────────────┘
                          ↓
┌────────────────── Capability Seam ─────────────┐
│ Schema → Guard → Approval → Sandbox → Runner  │
│        → Output Filter → Artifact Store       │
└─────────────────────────┬──────────────────────┘
                          ↓
┌──────────────────── 外部世界 ──────────────────┐
│ Files / Shell / Browser / DB / SaaS / MCP     │
└────────────────────────────────────────────────┘

横切能力：
- Cordis Context / Plugin / Effect / Service / Event
- Append-Only Log / Trace / Metrics / Audit
- Compaction / Search / Lineage / Checkpoint
- Eval / Rule Registry / Canary / Rollback
```

这张图揭示了一个容易被忽略的事实：Agent 工程的大部分复杂度并不在模型调用本身，而在模型前后的状态与控制系统。

## 十二、最常见的十个失败模式

### 1. 把所有能力放进一个万能工具

模型很难稳定选择参数，权限也无法细分。应该按业务动作和风险边界拆分工具。

### 2. 工具注册了，却没有反注册

热重载后出现重复监听和资源泄漏。所有注册动作都必须返回清理函数。

### 3. 相信模型生成的工具参数

Schema 合法不代表语义安全。路径、金额、收件人、SQL 范围等都要做二次校验。

### 4. 把“子进程”直接等同于“沙箱”

独立进程不自动带来文件、网络和内核隔离。必须根据威胁模型说明实际保证。

### 5. 只保存聊天消息，不保存执行事件

发生故障后无法判断副作用是否已执行，也无法可靠重放、审计和恢复。

### 6. 上下文满了就删除最早消息

目标和关键约束可能一起丢失。应使用结构化状态、摘要和外部制品存储。

### 7. Resume 时无条件重跑最后一步

非幂等工具可能重复产生副作用。恢复前要查询调用状态，并使用幂等键。

### 8. 子 Agent 继承主 Agent 的全部权限

任务拆分的同时扩大了攻击面。子任务应该使用更小的能力集合与独立预算。

### 9. 让模型控制退出条件

模型可能反复“再试一次”。终止、预算和熔断必须由 harness 硬编码控制。

### 10. 把自进化理解为线上自动改代码

没有回放评测、灰度与回滚的自修改，本质上是在生产环境进行无保护实验。

## 十三、一条循序渐进的实践路线

如果要真正掌握这套体系，建议不要一开始就做多 Agent 和自进化，而是按以下顺序推进。

### 阶段一：实现可撤销插件

目标：建立 Context、Service、Effect 和事件机制。

验收标准：

- 插件可以动态加载和卸载；
- 重复热重载不会增加监听器数量；
- 服务依赖缺失时能给出明确错误；
- 单元测试之间没有资源泄漏。

### 阶段二：实现安全工具循环

目标：完成模型请求工具、harness 执行、结果回填的闭环。

验收标准：

- 工具有 schema、超时、取消和错误分类；
- 读写类工具使用不同权限；
- 高风险操作支持人工批准；
- 所有调用都有可关联的追踪 ID。

### 阶段三：实现可恢复会话

目标：使用事件日志与 Projection 保存 Agent 状态。

验收标准：

- 进程重启后能够恢复会话；
- 能识别执行中的未决工具调用；
- 支持 Fork 与分支对比；
- 大型输出进入 Artifact Store；
- 上下文压缩后仍可追溯原始事件。

### 阶段四：加入 Goal 与多 Agent

目标：让长任务可续跑，并支持受控委派。

验收标准：

- Goal 有结构化验收条件和预算；
- 子 Agent 使用独立会话、权限和资源；
- 主 Agent 只接收结构化结果；
- 取消主任务时能递归取消并回收子任务。

### 阶段五：建立规则进化闭环

目标：从失败轨迹生成候选规则，并通过评测安全发布。

验收标准：

- 每条规则都有来源、版本与作用域；
- 发布前运行失败集、基线集和安全集；
- 高风险规则必须审批；
- 支持灰度、监控与自动回滚；
- 可以解释某次行为命中了哪条规则。

这条路线的顺序不能轻易颠倒。没有可逆生命周期，就很难安全热更新规则；没有事件化会话，就无法稳定提取失败样本；没有评测和回滚，自进化也就无从谈起。

## 十四、贯穿全文的五条工程原则

最后，可以把 DeepSeek Harness 大纲中的思想收束为五条更通用的 Agent 工程原则。

### 原则一：所有副作用都必须有所有者

监听器、定时器、进程、临时文件和规则都应归属于某个插件或会话，并随其生命周期结束而回收。

### 原则二：概率决策与确定性控制必须分离

模型可以建议做什么，但权限、预算、执行、终止与审计必须由确定性代码掌控。

### 原则三：原始历史与当前视图必须分离

Append-Only Log 保存事实，Projection 和 compaction 生成当前需要的视图。不要为了节省上下文而破坏历史真相。

### 原则四：并行能力必须伴随隔离与预算

Subagent 越多，不确定性和资源消耗越大。委派必须同时定义权限、配额、取消和回收。

### 原则五：进化首先是一套发布治理系统

生成新规则只是起点。真正困难的是证明它有效、没有明显回归、可以逐步上线，并能在异常时迅速撤销。

## 结语

从表面看，DeepSeek Harness 讨论的是插件、工具、沙箱、会话、多 Agent 和规则系统；从更深一层看，它讨论的是如何把一个概率模型放入长期运行的软件系统。

这套体系的演进逻辑非常清楚：

```text
先让组件可装卸
再让副作用可约束
然后让状态可追溯、任务可恢复
接着让 Agent 可以委派与协作
最后才让系统根据经验修改自身规则
```

模型能力决定了 Agent 的上限，但 harness 决定了它能否稳定地抵达那个上限。

真正成熟的 Agent 平台，不是让模型拥有最多工具、最长上下文或最多子 Agent，而是让每一次决策都有边界，每一个副作用都可追踪，每一次失败都能恢复，每一条新规则都能被验证和撤销。

当这些基础设施建立起来之后，“自进化”才不再是一个充满想象力的演示，而会变成一项可以评测、发布、监控和治理的工程能力。
