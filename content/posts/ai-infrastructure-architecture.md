一家企业准备同时建设三类 AI 能力：算法团队训练行业模型，应用团队部署实时推理服务，数据团队每天执行批量向量化和评测任务。最初的方案往往很直接：采购 GPU，搭建 Kubernetes，安装训练框架和模型服务。

真正进入生产后，问题会从“有没有卡”迅速变成另一组系统问题：一项多机训练能否一次拿到满足拓扑要求的全部资源；在线推理扩容会不会挤占训练任务；模型权重怎样从对象存储高效加载到节点；节点故障后训练从哪里恢复；同一块加速卡产生的成本应该归属哪个项目；一次模型响应变慢，究竟卡在排队、Prefill、Decode、网络还是外部工具调用。

这些问题共同定义了 AI 基础设施。

> **AI 基建不是 GPU 集群的同义词，而是一套把异构资源转化为可调度计算，把数据和模型转化为受治理资产，再把训练与推理转化为可交付服务的生产系统。**

本文面向企业自建或混合云场景，给出一套端到端参考架构。重点讨论平台边界、关键控制机制、容量与可靠性，而不是罗列产品。文中的指标、阈值和组件组合均为设计示例，生产环境需要按模型、硬件、数据等级和业务目标重新验证。

## 一、先定义 AI 基建的边界

传统基础设施主要交付 CPU、内存、网络、存储和应用运行环境。AI 工作负载在此基础上增加了四类特殊约束。

### 资源不再只有数量，还有拓扑与兼容性

训练任务申请“8 张 GPU”时，数量相同不代表性能相同。设备型号、显存容量、互联方式、NUMA 位置、驱动、固件、运行时和通信库共同决定任务能否运行。跨节点训练还受机架、交换网络和拥塞状态影响。

因此，AI 资源目录不能只记录可用设备数，还应表达：

- 设备型号、显存、切分能力和健康状态；
- 节点内互联与设备到 CPU、网卡的拓扑；
- 节点间网络域、机架和故障域；
- 驱动、运行时、框架及算子兼容矩阵；
- 已验证的训练和推理性能档案。

### 作业同时具有批处理和服务属性

预训练、微调、数据处理和离线评测通常是有开始、有终态的批作业；在线推理则是需要持续接收请求的服务。前者关注排队时间、整体完成时间、检查点与恢复，后者关注可用性、首 Token 延迟、吞吐和尾部延迟。

两者可以共享底层集群，却不能使用完全相同的调度和容量规则。批任务可以等待，核心在线服务通常需要预留容量；训练适合成组调度，推理则需要按流量扩缩容。

### 数据和模型都是一等资产

训练结果无法只由一个镜像版本解释。数据快照、代码、参数、依赖、随机种子、硬件环境、基础模型、Prompt、评测集与输出制品共同构成一次实验事实。

模型上线也不是复制一个权重文件。平台需要建立从数据到实验、模型、评测、审批、部署和运行指标的谱系，使一次生产响应能够追溯到明确的模型与配置版本。

### 性能、质量与成本必须一起优化

GPU 利用率高，不一定代表系统产出高。一个持续运行但频繁重算的训练任务、一个批次很大却超出延迟目标的推理服务，都可能显示很高的设备忙碌度。

更有意义的目标是：在质量和服务等级约束下，提高单位资源产生的有效训练进展、有效 Token 或成功业务任务数。

## 二、架构目标与设计原则

AI 基建应对使用者提供六类稳定承诺。

| 承诺 | 使用者关心的问题 | 平台需要建立的能力 |
| --- | --- | --- |
| 资源可发现 | 有哪些可用算力，是否兼容当前任务 | 资源目录、标签、健康检测、性能档案 |
| 交付可预期 | 何时开始运行，为什么排队 | 队列、配额、准入、预留、调度解释 |
| 运行可恢复 | 节点或进程故障后是否丢失进度 | 检查点、重试策略、租约、故障隔离 |
| 结果可追溯 | 模型由什么数据和代码产生 | 元数据、制品库、实验跟踪、模型注册表 |
| 服务可保障 | 延迟、吞吐和可用性是否达标 | 推理网关、容量保护、自动扩缩容、SLO |
| 成本可解释 | 资源消耗属于谁，优化是否有效 | 租户归属、计量、成本分摊、预算和 FinOps |

设计时可以坚持以下原则：

1. **意图、运行事实与计量事实分开保存。** 控制面记录用户希望运行什么，执行面报告实际发生了什么，计量系统记录可核验的用量。
2. **硬约束先于优化目标。** 数据位置、设备兼容、租户隔离和在线容量保护属于准入条件；成本与利用率只在可行集合内优化。
3. **长任务必须可中断、可恢复、可核验。** 失败后不能只知道“Pod 重启了”，还要知道从哪个检查点恢复、是否重复处理数据、训练步数是否连续。
4. **模型服务按请求形态管理容量。** 输入长度、输出长度、并发和延迟目标比单纯的请求数更能解释推理负载。
5. **平台能力通过接口和策略统一，而不是强迫所有团队使用同一框架。** 可以统一身份、制品、遥测、队列和发布契约，同时允许不同训练框架和推理引擎共存。
6. **自动化动作必须有边界和验证。** 自动扩容、抢占、降级和故障迁移都需要上限、适用条件、停止条件与回退路径。

## 三、总体架构：四个平面与八个能力层

可以把 AI 基建划分为四个平面。

- **管理面**：租户、项目、服务目录、配额、预算、策略、发布和审批。
- **资源面**：服务器、加速设备、网络、存储、集群和调度队列。
- **生产面**：数据处理、开发实验、分布式训练、评测、模型注册和推理服务。
- **治理面**：身份、安全、可观测、审计、质量、成本与风险管理。

```text
┌──────────────────────────────────────────────────────────────┐
│ 使用入口：Notebook / IDE / CLI / SDK / API / 控制台         │
└──────────────────────────────┬───────────────────────────────┘
                               │
┌──────────────────────────────▼───────────────────────────────┐
│ 管理面：租户 · 项目 · 配额 · 队列 · 预算 · 策略 · 发布       │
└───────────────┬──────────────────────────────┬───────────────┘
                │                              │
┌───────────────▼────────────────┐ ┌───────────▼───────────────┐
│ 训练生产面                     │ │ 推理生产面                │
│ 数据处理 → 实验 → 训练 → 评测 │ │ 网关 → 路由 → 引擎 → API │
│ → 模型注册 → 发布审批          │ │ 在线 / 异步 / 批量        │
└───────────────┬────────────────┘ └───────────┬───────────────┘
                │                              │
┌───────────────▼──────────────────────────────▼───────────────┐
│ 数据与模型资产：数据集 · 特征 · 向量 · 权重 · 镜像 · 元数据 │
└──────────────────────────────┬───────────────────────────────┘
                               │
┌──────────────────────────────▼───────────────────────────────┐
│ 资源面：队列调度 · Kubernetes · 设备管理 · 网络 · 存储       │
└──────────────────────────────┬───────────────────────────────┘
                               │
┌──────────────────────────────▼───────────────────────────────┐
│ 物理与云资源：GPU/NPU/CPU · 高速网络 · 对象/并行/块存储      │
└──────────────────────────────────────────────────────────────┘

贯穿能力：身份与密钥 · 遥测与 SLO · 安全策略 · 谱系 · 成本 · 审计
```

从能力层看，这套系统至少包含：物理资源、设备与集群、调度、存储与数据、训练、模型资产、推理、治理与运营。分层的目的不是制造更多平台，而是明确每类状态由谁负责。

例如，业务控制面可以批准一个 8 卡训练任务，队列系统决定它何时获得配额，集群调度器决定落在哪些节点，训练控制器负责进程组和失败恢复，实验系统保存参数与指标，计量系统记录实际设备时长。任何一个组件都不应该凭自己的局部状态宣称“任务已经完整交付”。

## 四、异构算力资源池

### 设备接入需要标准化生命周期

加速节点接入建议经过“发现、验证、基准测试、试运行、可分配”几个阶段。节点更换驱动、固件、内核或通信库后，兼容性和性能档案应重新验证，而不是直接回到资源池。

Kubernetes Device Plugin 可以把厂商设备作为可调度资源暴露给 kubelet；Dynamic Resource Allocation 进一步提供资源类、资源声明和更灵活的设备分配表达。NVIDIA GPU Operator 和 AMD GPU Operator 则分别用于自动化管理对应设备的驱动、设备插件、监控和相关运行组件。[1][2][3][4]

设备管理层应维护以下事实：

| 类型 | 关键字段 | 主要用途 |
| --- | --- | --- |
| 静态身份 | 厂商、型号、序列号、显存、节点、机架 | 资产管理与兼容判断 |
| 软件栈 | 驱动、固件、运行时、通信库、算子版本 | 复现和变更风险控制 |
| 拓扑 | NUMA、PCIe、NVLink 或同类互联、网卡亲和性 | 放置和性能优化 |
| 健康 | 温度、功耗、纠错错误、链路状态、隔离状态 | 准入和故障处置 |
| 性能档案 | 计算、显存带宽、通信、典型模型基准 | 集群选择与容量预测 |

### 切分、共享与独占是三种不同产品

整卡独占适合通信密集训练和需要稳定性能的推理。硬件切分可以提供更强的故障与资源隔离，时间片共享则提高轻负载场景的设备使用率，但性能受邻居影响更明显。NVIDIA MIG 是硬件切分的一个实现，能够把支持的 GPU 划分为相互隔离的实例。[5]

平台不能把三种交付方式包装成同一个“GPU 数量”。服务规格应明确：

- 可获得的计算、显存和媒体能力；
- 隔离级别与性能波动范围；
- 是否支持点对点通信和特定并行方式；
- 计量粒度、调度限制和故障影响范围。

训练任务是否允许共享设备，应由实测和作业类型决定。短时 Notebook、轻量评测和低流量模型可以考虑共享；大规模分布式训练通常需要更严格的资源独占和拓扑约束。

### 资源状态必须防止重复分配

管理面和集群控制器之间可能失联。资源分配应使用租约、唯一绑定记录和单调递增的 fencing token，避免旧控制器恢复后继续执行过期命令。

当节点状态未知时，不能立刻把同一资源重新分给另一任务。需要先隔离旧执行路径，确认进程终止或设备已重置，再恢复可分配状态。对外提供算力服务时，这也是防止重复计费和跨租户数据残留的基础。

## 五、队列、配额与拓扑感知调度

Kubernetes 默认调度器解决的是 Pod 放置问题，但 AI 平台还需要回答：哪个团队先获得资源，一组 Pod 是否必须同时启动，资源不足时谁可以借用，在线服务和训练作业怎样隔离。

### 三层控制模型

建议把资源控制拆成三层。

1. **准入层**：检查租户权限、预算、数据位置、镜像策略、设备兼容和最大规模。
2. **队列层**：按项目、优先级、配额、借用规则和公平策略决定作业何时被接纳。
3. **放置层**：在已接纳作业的候选节点中，按设备、拓扑、污点、亲和性和剩余容量进行绑定。

Kueue 在 Kubernetes 之上提供面向批工作负载的队列、配额、准入和公平共享能力，并可与多种作业控制器集成；Volcano 则提供队列、gang scheduling 及面向批处理的调度能力。[6][7]

### Gang Scheduling 保护分布式任务

一个 8 Worker 训练任务如果只启动 6 个 Worker，已占用的设备往往无法产生有效训练进展，还会阻塞其他任务。Gang scheduling 的核心是整组满足最小可运行资源后再开始绑定。

这不能被简单理解为“一次性创建所有 Pod”。平台还需要定义：

- 等待多久后释放预留；
- 部分节点准备失败时如何回滚；
- 参数服务器、主节点和 Worker 是否使用不同资源；
- 弹性训练是否允许缩小或扩大成员；
- 恢复作业能否优先回到相同拓扑。

### 公平共享不等于平均分配

不同团队的业务等级、预算和工作负载并不相同。一个可实施的策略通常包含保底配额、可借用容量、借用上限、优先级和抢占规则。

在线推理的保底容量应与训练队列分开保护。训练可以使用在线服务的临时空闲量，但扩容信号出现时需要在约定时间内归还。抢占前应判断训练作业是否有可用检查点、预计重算成本和剩余运行时间，避免为了回收一张卡浪费数小时计算。

### 拓扑是硬约束时必须进入调度模型

分布式训练的性能可能受节点内和节点间通信显著影响。调度器至少需要感知主机、机架、网络域和设备到网卡的亲和性。Kueue 的 Topology Aware Scheduling 允许工作负载表达所需拓扑级别并据此放置 Pod。[8]

拓扑感知不能替代基准测试。即使节点标签相同，网络拥塞、线缆故障和固件差异仍可能造成性能偏差。平台应把实际通信基准与拓扑元数据结合起来，隔离异常节点或链路。

## 六、网络与存储：决定集群上限的两条数据路径

AI 集群里至少存在三类不同流量。

| 流量 | 典型内容 | 主要要求 |
| --- | --- | --- |
| 训练通信 | 梯度、参数、激活、集合通信 | 高带宽、低延迟、低抖动、拓扑稳定 |
| 数据与制品 | 数据集、检查点、模型权重、镜像 | 高吞吐、并发读取、持久性与版本化 |
| 服务请求 | Prompt、Token 流、Embedding、API 调用 | 可用性、连接管理、尾部延迟与安全 |

### 训练网络要围绕通信模式设计

数据并行常使用 AllReduce 等集合通信；张量并行和流水线并行的通信频率与消息形态不同。NCCL、RCCL 等通信库会根据拓扑选择传输路径，但基础设施仍需提供匹配的网卡、交换网络、RDMA 配置和故障可见性。[9][10]

网络设计不能只看链路标称带宽。应测量不同消息大小、节点规模和并行策略下的有效带宽、尾部延迟、重传与抖动，并保留与训练吞吐的关联。

生产网络通常还要区分管理、存储、训练通信和业务接入流量。是否物理分离取决于规模与风险，但至少需要逻辑隔离、容量保护和独立观测，防止大规模权重加载拖慢控制面或在线请求。

### 存储需要分层，不应由一个系统承担所有负载

| 层次 | 适合保存 | 设计重点 |
| --- | --- | --- |
| 对象存储 | 原始数据、数据快照、模型权重、检查点、日志归档 | 低成本、持久性、版本和生命周期 |
| 并行或高性能文件系统 | 高频训练读取、共享数据集、临时检查点 | 聚合吞吐、元数据性能、并发访问 |
| 节点本地 NVMe | 数据缓存、权重缓存、临时 Shuffle | 启动速度、淘汰策略、故障后可重建 |
| 块存储 | 元数据库、队列状态、需要文件系统语义的服务 | 一致性、快照、恢复与 IOPS |

常见模式是以对象存储作为长期权威来源，把热点数据和权重预热到高速共享层或节点本地缓存。缓存只保存可重建副本，淘汰和节点故障不能破坏数据事实。

### 检查点是恢复协议，不只是一个文件

检查点至少要关联作业、训练步、模型状态、优化器状态、数据读取位置、分布式拓扑和代码版本。写入过程需要处理部分成功、重复提交和旧版本清理。

PyTorch Distributed Checkpoint 支持并行保存和加载分布式模型状态，并提供异步保存能力。异步检查点可以减少训练停顿，但会占用额外 CPU、内存和 I/O，且后台写入完成前仍存在丢失窗口。[11]

检查点频率可以用期望损失近似思考：

```text
单位时间期望损失
  ≈ 检查点开销 / 检查点间隔
  + 故障率 × 平均重算时间
```

间隔过短会让 I/O 持续干扰训练，过长则增加故障后的重算。应使用真实故障率、写入时间和恢复时间进行实验，而不是统一设置为固定分钟数。

## 七、数据与模型资产层

AI 平台不必把数据仓库、湖仓、特征库、向量库和模型库全部重建一遍。关键是明确每类系统保存什么权威事实，以及它们之间怎样关联。

### 数据集要可寻址、可复现、可治理

训练清单应引用不可变的数据版本或快照，而不是一个内容会持续变化的目录。数据版本需要记录来源、时间范围、过滤规则、标签规范、授权范围和质量报告。

数据处理链路应产出谱系：哪个输入快照经过哪个代码和参数，生成了哪个训练集。对于包含个人信息、商业机密或受许可约束的内容，还要记录可用目的、保留期限和地域限制。

### 特征、向量与原始数据的职责不同

特征库解决离线训练与在线服务之间的特征定义和一致性问题；向量库解决相似性检索及其索引、过滤和更新问题。它们都不应成为无法追溯来源的第二套原始数据仓库。

平台需要保存特征或向量对应的源数据版本、生成模型、切分策略和更新时间。Embedding 模型或文档切分策略变化时，应显式生成新版本，避免新旧向量静默混用。

### 模型注册表保存的是发布候选，不是所有实验文件

实验跟踪系统保存参数、指标和运行记录；制品库保存权重、分词器、配置、镜像和报告；模型注册表管理经过筛选的模型版本、评测证据、审批状态和部署别名。

MLflow Model Registry 提供模型版本、别名、标签和谱系相关能力，可作为这类控制面的实现之一。[12]

一次可部署模型版本至少应关联：

```yaml
modelVersion: risk-model-20261026-07
baseModel: foundation-model-v3
artifacts:
  weights: object://model-registry/risk-model/sha256-...
  tokenizer: object://model-registry/tokenizer/sha256-...
  imageDigest: registry.example.com/serving@sha256:...
lineage:
  datasetSnapshot: risk-dataset-20261020
  trainingRun: run-8f31
  codeRevision: 2d14c7a
evaluation:
  suite: risk-regression-v12
  report: object://evaluation/reports/report-8f31.json
release:
  status: approved
  approvers: [model-owner, risk-control]
```

模型别名适合表达 `candidate`、`champion` 等可变指针，但运行记录必须保存最终解析到的不可变版本，不能只记一个会移动的名称。

## 八、训练平台：从实验到可恢复生产作业

### 开发环境和生产作业需要不同边界

Notebook 适合探索、调试和可视化，不适合作为无人值守长任务的唯一运行载体。经过验证的代码和参数应提交为可重放作业，由训练控制器负责资源、进程组、状态和失败处理。

开发环境需要限制空闲时长、网络访问、数据挂载和可申请设备数。生产训练则应使用不可变镜像、版本化配置、服务身份和明确的数据输入输出。

### 训练工作流应拆成可缓存阶段

一个典型流程包含数据校验、预处理、训练、检查点、评测、模型转换和注册。每个阶段有独立输入输出与失败语义，适合由工作流系统进行编排。

```text
数据快照
  → 质量校验
  → 预处理 / Tokenize
  → 分布式训练
  → 离线评测
  → 格式转换 / 量化候选
  → 安全与合规检查
  → 模型注册
```

阶段缓存必须以完整输入签名为键，包括代码、参数、基础模型和数据版本。仅以文件名判断“已经运行过”会产生难以发现的陈旧结果。

Kubeflow Trainer 提供 Kubernetes 原生的分布式训练作业接口；Ray Train 提供面向多种框架的分布式训练抽象。选型时应重点验证故障语义、弹性能力、框架支持、日志体验和与现有队列系统的集成，而不是只比较支持多少算法。[13][14]

### 失败恢复要区分不同故障

| 故障 | 典型处理 | 不能忽略的问题 |
| --- | --- | --- |
| 单进程异常 | 同组重启或作业失败后恢复 | 其他进程是否仍在等待通信 |
| 节点失联 | 隔离节点，重新组建 Worker | 旧进程是否确实失效 |
| 设备错误 | 标记设备并触发诊断 | 是否存在静默计算错误 |
| 存储超时 | 有界重试并核验检查点 | 部分文件是否已写入 |
| 数据异常 | 停止并记录问题分片 | 跳过是否改变训练语义 |
| 抢占 | 保存或使用最近检查点 | 重算成本是否高于回收收益 |

自动重试应设置次数和总预算。相同错误连续发生时，无限制重启只会消耗更多 GPU，并掩盖根因。

### 训练指标需要连接系统与模型进展

除了设备利用率，还应观察：

- 样本或 Token 吞吐、Step Time 及其分位数；
- 数据加载等待、集合通信时间和计算时间占比；
- 有效训练时间、排队时间、恢复时间和重算时间；
- Loss、梯度范数、评测指标和数值异常；
- 单位有效 Token、单位检查点或单位达标模型的成本。

模型指标异常时，需要能下钻到数据版本、代码、节点和设备；系统变慢时，也需要判断训练是否仍在产生有效进展。

## 九、推理平台：把模型变成有服务等级的产品

推理平台的最小闭环包括接入、路由、排队、执行、扩缩容、观测和发布。

```text
客户端
  → API 网关：认证、租户、限流、请求大小
  → 模型路由：模型版本、区域、灰度、降级策略
  → 请求调度：优先级、批处理、长度与并发预算
  → 推理引擎：Prefill、Decode、KV Cache、并行执行
  → 输出处理：安全策略、流式返回、用量记录
```

### 在线、异步和批量推理应使用不同服务契约

| 模式 | 适合场景 | 关键目标 |
| --- | --- | --- |
| 在线同步 | 对话、搜索重排、实时决策 | TTFT、TPOT、尾部延迟、可用性 |
| 在线异步 | 长文生成、复杂多阶段任务 | 接单成功、排队可见、终态可靠 |
| 离线批量 | Embedding、评测、回填、数据生成 | 完成时间、吞吐、可恢复与成本 |

把长任务都塞进同步 HTTP 请求，会使连接、超时和重试变得脆弱；把交互请求都转成批处理，又会破坏用户体验。平台应让调用方明确选择服务类型。

### 容量模型要从 Token 出发

大模型推理通常包含 Prefill 和 Decode。输入长度影响 Prefill 与 KV Cache，输出长度影响 Decode 占用。一次请求的显存需求可粗略表示为：

```text
显存需求
  ≈ 模型权重
  + 所有活动序列的 KV Cache
  + 激活、通信缓冲和运行时开销
```

因此，扩缩容不能只看 GPU 利用率或每秒请求数。更有解释力的信号包括队列等待、活动 Token、KV Cache 占用、TTFT、TPOT、拒绝率和满足 SLO 的有效吞吐。

vLLM 使用 PagedAttention 管理 KV Cache，并支持连续批处理、前缀缓存以及张量并行、流水线并行等分布式部署方式。这些机制可以提高容量，但参数需要结合实际输入输出分布调优。[15][16][17]

### 自动扩缩容要识别冷启动和资源边界

模型副本启动可能包含调度等待、镜像拉取、权重下载、权重加载和图编译。若冷启动需要数分钟，单纯看到队列增长后再创建副本可能来不及。

可采用以下组合：

- 为关键模型保留最小热容量；
- 在节点本地预热常用权重，但仍以远端制品为权威来源；
- 根据流量周期提前扩容；
- 使用队列和准入保护系统，不承诺无限等待；
- 对低频模型评估共享服务、量化或按需加载；
- 将扩容上限同时约束在设备配额、预算和下游容量内。

KServe 提供基于 Kubernetes 的模型服务抽象、自动扩缩容和推理图等能力，可用于构建模型服务控制面；实际数据面仍需按模型类型和性能目标选择并验证。[18]

### 灰度发布要同时比较系统质量与模型质量

新模型上线不能只看 5xx 错误率。一次灰度至少应观察：

- 请求成功率、TTFT、TPOT、端到端延迟和吞吐；
- 输入输出长度分布是否一致；
- 业务准确率、拒答率、结构化输出有效率和安全指标；
- 单次有效请求成本；
- 新旧版本的样本量与统计不确定性。

发布记录应固定模型权重、推理镜像、运行参数、Prompt 模板、路由规则和安全策略。回退也必须回退这一组发布单元，而不只是把权重指针改回旧版本。

## 十、可观测性与 SLO

AI 基建的观测需要连接四层信号。

| 层次 | 代表指标 | 要回答的问题 |
| --- | --- | --- |
| 资源层 | 设备利用率、显存、功耗、错误、网络、存储 | 硬件和基础服务是否健康 |
| 作业层 | 排队、启动、Step Time、恢复、检查点 | 训练和批任务是否有效推进 |
| 服务层 | QPS、Token、TTFT、TPOT、错误、队列 | 推理是否满足服务目标 |
| 业务层 | 有效完成率、质量、人工接管、单任务成本 | 系统是否创造预期结果 |

### 统一关联标识

一次训练应能通过 `tenant_id`、`project_id`、`job_id`、`run_id`、`model_version`、`dataset_version` 和 `node_id` 串联日志、指标、Trace 与制品。一次推理请求则应关联租户、应用、模型版本、发布版本和用量记录。

这些高基数字段不应全部直接成为时序指标标签。可以在指标中保留有限维度，把请求级细节放入 Trace、日志或分析存储，避免监控系统基数失控。

OpenTelemetry 的 GenAI 语义约定项目为生成式 AI 的 Span、指标和事件定义公共语义，并已迁移到独立的官方规范仓库。规范仍可能演进，落地时应固定所采用的版本，并在模型网关或 SDK 层做统一映射。[19]

### SLO 必须按工作负载定义

训练平台可以定义：

- 已接纳作业在目标时间内启动的比例；
- 由平台故障导致的有效训练时间损失；
- 检查点成功率和恢复时间；
- 训练元数据与制品完整率。

推理服务可以定义：

- 在约定输入输出长度档位内的请求成功率；
- TTFT、TPOT 或端到端延迟达标率；
- 流式连接中断率；
- 满足质量门槛的有效请求比例。

不能把用户取消、平台限流和超长输入全部从分母中移除。哪些请求属于合同口径、哪些属于无效输入，需要事先定义。

### 告警面向影响，不面向每一个波动

设备温度偶发升高、单个请求变慢不一定需要叫醒值班人员。告警应优先覆盖持续错误预算消耗、队列失控、在线容量不足、训练大面积无进展、检查点连续失败和设备错误扩散。

仪表盘负责探索，告警负责行动。每条告警都应对应负责人、影响范围、初步诊断和可执行手册。

## 十一、安全、供应链与治理

AI 基建同时承载高价值数据、模型权重、代码和昂贵资源，安全边界需要进入平台默认路径。

### 身份与租户隔离

用户身份、服务身份和工作负载身份应分开管理。Notebook、训练任务和推理服务使用短期凭证访问被授权的数据与制品，不把长期密钥写进镜像或环境模板。

命名空间只是隔离的一部分。还需要配合网络策略、存储权限、设备清理、节点池边界、密钥管理、审计和资源配额。高敏感租户可使用专属节点池或独立集群。

### 软件供应链

训练镜像和推理镜像应经过依赖扫描、来源校验、不可变摘要和发布签名。构建系统保存可验证的来源信息，部署策略只允许批准的制品进入生产。SLSA 提供软件制品来源和构建完整性的分级框架，Sigstore Cosign 可用于容器和其他制品的签名与验证。[20][21]

模型文件同样需要摘要、来源和审批。不要因为权重不是可执行二进制，就忽略反序列化风险、恶意自定义代码和许可证限制。

### 数据与模型治理

治理控制至少覆盖：

- 数据来源、授权目的、敏感等级和保留期限；
- 训练数据删除或纠错后的影响分析；
- 基础模型与数据集许可证；
- 模型卡、评测报告、已知限制和适用范围；
- 高风险发布的人工审批与职责分离；
- 推理输入输出的留存、脱敏和访问审计。

NIST AI RMF 将 AI 风险管理组织为 Govern、Map、Measure 和 Manage 四组功能；其生成式 AI Profile 补充了生成式 AI 风险的实施建议。它们适合作为治理检查框架，但具体控制仍需结合行业法规和企业责任边界落地。[22][23]

### 平台自动化不能绕过授权

调度器可以自动选择节点，扩缩容器可以自动增加副本，运维 Agent 可以建议故障处置，但资源越权、数据跨域、生产发布和不可逆操作仍必须由独立策略与授权系统判断。

自动化组件不能同时拥有“提出操作、批准操作、执行操作、删除审计”的全部权限。

## 十二、容量规划与 AI FinOps

### 先区分已采购、可分配和有效容量

```text
已采购容量
  - 维修与隔离容量
  - 平台保留与碎片
  = 可分配容量

可分配容量
  - 排队、启动、故障、重算和低效损失
  = 产生有效结果的容量
```

只用已分配 GPU 时长除以总 GPU 时长，会把低效训练也算成成功利用。平台应同时报告：

- 物理可用率、分配率和设备活跃率；
- 有效训练时间占比和重算损失；
- 在线服务预留容量、实际消耗和峰值余量；
- 因拓扑、显存和配额造成的资源碎片；
- 单位有效 Token、模型版本或业务任务的成本。

### 成本应归集到稳定业务标识

每个工作负载必须关联租户、项目、环境、负责人和成本中心。共享平台成本可以按明确规则分摊，但应保留未归属成本，不能为了让报表完整而随意平均。

训练成本可以近似拆为：

```text
训练成本
  = 加速设备时长
  + CPU 与内存
  + 高性能存储与对象存储
  + 网络传输
  + 失败重算
  + 平台分摊
```

推理成本应按模型与流量档位核算。共享服务中，仅按请求数分摊会让短请求补贴长请求；可以结合输入 Token、输出 Token、占用时间、缓存命中和最低服务容量建立内部计量。

### 优化顺序从浪费开始

通常先处理以下问题，比立即采购更多设备更有效：

1. 清理无人使用的 Notebook、僵死任务和过期模型副本。
2. 减少数据重复复制、镜像和权重冷启动。
3. 找到数据加载、通信和调度造成的 GPU 等待。
4. 让批任务使用低谷容量，并保护在线服务保底。
5. 对模型做量化、蒸馏或并行策略调整，同时验证质量。
6. 在真实需求预测和交付周期基础上扩容。

预算控制不能只在月末报表中出现。提交大规模训练、扩大在线副本或跨区域传输前，应估算成本并检查项目预算；运行中则根据实际消耗和完成进展更新预测。

## 十三、高可用、多集群与灾难恢复

### 先明确哪些状态必须跨故障域保存

控制台可以短时不可用，但运行中的训练和推理不应因此立即停止。管理面、执行面和制品存储应解耦：

- 控制面保存期望状态、策略、队列和发布记录；
- 集群代理缓存已授权任务和租约，并持续回报运行事实；
- 对象存储保存数据、权重、检查点和归档；
- 关系数据库保存事务元数据，并具备备份与恢复；
- 计量事件允许补传、去重和重放。

管理面失联时，集群只在预先授权的资源与预算内继续运行，停止接受未经确认的新高风险任务。恢复后通过代次和序列号核对状态，旧命令不能覆盖新事实。

### 多集群首先是故障和治理边界

当规模、地域、设备类型或数据等级不同，可以引入多个集群。全局调度器负责根据硬约束选择候选集群，本地队列和调度器负责具体准入与放置。

跨集群不能假设网络和存储完全透明。需要显式处理：

- 数据和模型在目标区域是否可用；
- 复制时间、传输成本和数据驻留要求；
- 集群能力与软件栈是否兼容；
- 全局配额与本地实际用量如何核对；
- 集群失联时是否允许继续运行和扩容。

训练故障切换通常依赖远端可用的检查点，而不是迁移正在运行的内存状态。在线推理可以跨集群部署独立副本，通过全局流量管理切换，但需要避免同时依赖同一个故障域的模型仓库、身份服务或 DNS。

### 灾备必须通过恢复演练验证

需要定期演练元数据库恢复、对象制品恢复、集群失联、模型仓库不可用、节点大面积故障和区域流量切换。恢复时间目标和恢复点目标只有在演练中才有实际意义。

一次合格演练不只证明服务重新启动，还要核对：任务是否重复执行、检查点是否完整、计量是否连续、模型版本是否正确、租户权限是否仍然有效。

## 十四、技术选型：先确定控制问题，再选择组件

| 能力域 | 可评估方向 | 架构评审重点 |
| --- | --- | --- |
| 集群与设备 | Kubernetes、厂商设备 Operator、DRA | 驱动生命周期、兼容矩阵、升级和隔离 |
| 队列调度 | Kueue、Volcano、现有批处理调度器 | gang、配额借用、公平性、拓扑和抢占 |
| 训练控制 | Kubeflow Trainer、Ray Train、框架原生控制器 | 故障语义、弹性、框架支持、队列集成 |
| 工作流 | Kubernetes 原生工作流、企业调度平台 | 缓存键、重试、制品、事件与审计 |
| 实验与模型 | MLflow 或现有 MLOps 平台 | 谱系、注册、审批、开放接口和迁移 |
| 推理数据面 | vLLM、Triton、框架或厂商引擎 | 模型支持、延迟、吞吐、并行和可观测 |
| 推理控制面 | KServe、自研模型服务平台 | 发布、扩缩容、路由、多租户和服务契约 |
| 遥测 | OpenTelemetry、Prometheus 生态、日志与 Trace 后端 | 语义统一、基数、成本、保留和敏感信息 |
| 制品与供应链 | 对象存储、镜像仓库、签名与策略引擎 | 不可变版本、来源、访问控制和生命周期 |

选型验证应使用代表性场景，而不是只运行安装示例。至少包括：

- 8 卡或更大规模作业的成组准入和拓扑放置；
- Worker、节点和存储故障后的训练恢复；
- 长短请求混合时的推理尾部延迟；
- 模型冷启动、权重预热和节点扩容；
- 多租户配额借用、抢占和成本归属；
- 模型灰度、回退与全链路版本追溯。

不要因为某个组件同时宣称支持训练、服务、工作流和监控，就让它成为所有状态的权威来源。组件边界越宽，越需要验证故障时的真实行为和后续替换成本。

## 十五、分阶段建设路线

### 阶段一：资源标准化与可见

交付设备目录、节点接入、驱动与运行时基线、健康监控、租户项目、基础配额和成本标签。

验收重点是：任何已分配设备都能回答“属于谁、运行什么、软件栈是什么、是否健康、产生多少用量”。

### 阶段二：队列化训练与制品闭环

引入队列、成组调度、拓扑约束、训练作业模板、对象存储、检查点、实验跟踪和模型注册。

验收重点是：长任务能从故障中恢复；一次模型版本可以追溯到数据、代码、参数、制品和评测。

### 阶段三：生产级推理服务

建设模型网关、推理引擎池、发布与灰度、长度感知的容量指标、自动扩缩容、在线容量保护和用量归集。

验收重点是：代表性流量下满足 SLO；新版本可以小流量验证和完整回退；一次请求可定位到确定的发布单元。

### 阶段四：多集群治理与持续优化

增加全局资源目录、集群选择、跨区域制品策略、统一策略、风险审批、FinOps 和受控自动化运维。

验收重点是：集群失联和区域故障时行为明确；成本、质量与服务等级能够共同驱动容量和发布决策。

每个阶段都应交付可验证的用户路径，而不是只安装组件。平台成熟度体现在任务和服务经过故障、变更与容量压力后仍然可解释、可恢复。

## 十六、常见反模式

### 只看 GPU 利用率

高利用率可能来自无效重算、过度批处理或通信等待。必须同时查看训练进展、延迟、质量和成本。

### 用 Kubernetes 命名空间代替完整多租户

命名空间无法独立解决设备清理、存储权限、网络边界、密钥、预算和审计。多租户是一组控制的组合。

### 所有任务共享一个无边界队列

这会让大作业阻塞小作业，训练挤压在线服务，团队无法预测启动时间。应建立服务等级、配额和借用规则。

### 把 Notebook 当作生产调度系统

Notebook 断连、重启和环境漂移都可能让长任务失去控制。生产任务应进入可重放作业和工作流。

### 模型文件可以覆盖写

覆盖同一路径会破坏复现、回退和缓存一致性。制品应不可变，别名只作为指针。

### 自动扩容只看平均 GPU 利用率

平均值会掩盖排队、长请求和副本不均。扩缩容需要结合队列、Token、缓存和尾部延迟，并考虑冷启动。

### 先建统一大平台，再寻找使用者

没有代表性工作负载就很难验证调度、数据、推理和成本规则。更稳妥的方法是选择一条训练链路和一条推理链路，先打通可运行、可追溯和可恢复闭环。

## 十七、架构评审清单

上线前可以用以下问题进行评审：

1. 每种设备和软件栈是否有明确兼容矩阵及升级流程？
2. 多卡任务能否整组准入，并按必要拓扑放置？
3. 在线服务是否有不会被训练抢占的保底容量？
4. 数据集、代码、模型、镜像和评测是否使用不可变版本关联？
5. 节点故障后从哪个检查点恢复，最多损失多少进度？
6. 权重和数据冷启动是否会压垮存储或网络？
7. 推理容量是否按代表性输入输出长度和延迟目标验证？
8. 一次模型请求能否追溯到模型、Prompt、镜像和路由版本？
9. 高基数遥测、敏感 Prompt 和训练数据如何控制采集与保留？
10. 每份资源用量是否能归属到租户、项目、环境和成本中心？
11. 抢占、扩容、降级和故障迁移是否有上限与回退条件？
12. 管理面、模型仓库或单个集群失联时，系统行为是否经过演练？

## 结语

AI 基建的核心工作，是建立一条从资源到结果的可信链路：异构设备被准确发现和调度，数据与模型具备版本和谱系，训练能够恢复，推理拥有明确服务等级，成本能够归属，故障和变更都留下可核验事实。

当平台只能展示 GPU 数量时，它还是资源管理系统；当平台能够解释一个模型如何产生、为什么被发布、一次请求由哪个版本处理、发生故障后如何恢复，以及这些结果花费多少成本时，它才成为真正的 AI 生产基础设施。
