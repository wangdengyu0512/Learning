芯片研发已经被软件工具高度覆盖，但它仍然是一项以人为中心组织起来的工作。

工程师阅读规格，拆解任务，选择 EDA 工具，判断报告是否可信，在多个失败方案之间切换，并把跨越数周甚至数月的上下文维持在文档、脚本、会议和个人经验里。传统自动化解决了其中大量重复步骤，却没有接管“下一步该做什么、结果是否足够好、失败后如何恢复”这些研发责任。

AI-Native 芯片研发平台试图改变的正是这条责任边界：

> 不只是让工程师用 AI 写 RTL、生成测试或解释报告，而是让 AI 智能体在明确的授权和验收边界内，自主规划、调用工具、检查结果、修复问题并提交可审查的研发产物；人类从高频操作员转变为目标制定者、例外处理者和关键节点的裁决者。

这不是把聊天机器人接到 EDA 命令行，也不是用一个巨大的 Prompt 包住整个芯片流程。它要求把模型、工具、状态、上下文、评测、权限和运行环境组成一个长期工作的工程系统。这个系统还要把每次任务中的成功路径、失败模式和人工裁决沉淀下来，使下一轮研发比上一轮更可靠。

当这种改进不再依赖人手修改每一条规则，而能够由平台提出候选改动、在回归任务上验证、经过审批后发布，就开始接近一个工程上可讨论的目标：**递归自我改进，Recursive Self-Improvement，简称 RSI。**

本文讨论的不是遥远的全自动芯片工厂，而是一条可以逐步实施的路线：先建立可靠的 Agent Harness，再建立可执行的芯片研发评测，最后让平台在受控边界内改进自己的工作方式。

## 一、先定义 AI-Native：不是“用了 AI”，而是改变任务所有权

判断一个研发平台是不是 AI-Native，不能看它接入了多少模型，而要看**谁对任务闭环负责**。

假设工程师要求系统修复一个 CDC 问题。几种系统看起来都在“使用 AI”，但自主程度完全不同：

| 形态 | AI 做什么 | 人做什么 | 任务所有权 |
| --- | --- | --- | --- |
| AI 助手 | 解释报告、建议修改 | 找文件、改代码、跑工具、判断完成 | 人 |
| AI 自动化 | 根据模板修改并运行固定流程 | 处理异常、决定下一步 | 主要在人 |
| 受限 Agent | 自主检索、修改、运行 CDC 与回归 | 审批高风险操作和最终结果 | Agent 与人共享 |
| AI-Native 研发 | 接受目标，规划并闭环执行，提交证据包 | 在预设闸门裁决 | Agent 承担执行责任 |
| 受控 RSI | 平台还能提出并验证自身 Harness 改进 | 审批新的平台版本和能力边界 | 平台持续改进，人掌握治理权 |

这里最重要的变化不是界面，而是任务输入和输出。

传统助手的输入往往是一段问题，输出是一段文本。AI-Native 平台的输入应当是一份**任务契约**，输出则是一组能够被独立验证的工程事实：

```text
任务目标
  + 设计对象与允许修改的范围
  + PPA / 覆盖率 / 时序 / DFT 等约束
  + 可调用工具、算力与许可证预算
  + 风险等级和人工审批点
  + 完成条件与禁止条件
          ↓
Agent 自主执行
          ↓
代码 / 约束 / 测试 / 报告 / Trace / 风险说明
          ↓
确定性验收 + 专家裁决
```

因此，一个任务是否完成，不由 Agent 说了算。完成状态来自编译、仿真、形式验证、Lint、CDC/RDC、综合、STA、DRC、LVS、IR/EM、ATPG 等外部系统产生的证据，以及必要的人类签核。

这条原则贯穿整个平台：**模型可以提出判断，但系统必须用模型之外的事实确认判断。**

## 二、为什么芯片研发既适合 Agent，又比软件开发更难

代码领域成为 Agent 的先发场景，一个关键原因是结果可执行、可测试、可回滚。芯片研发同样拥有大量机器可读的反馈：RTL 能否编译，断言是否成立，回归是否通过，覆盖率是否达标，网表是否等价，时序是否收敛，版图是否通过 DRC/LVS。

[OpenROAD](https://openroad.readthedocs.io/en/latest/main/README.html) 所代表的开放式 RTL-to-GDSII 流程，也说明芯片研发中的大量步骤已经具备程序化调用和自动反馈的基础。Agent 不必凭语言直觉猜测物理实现是否成功，它可以真正运行流程并读取报告。

但芯片研发的困难也恰恰来自这些工具链。

### 1. 一个局部正确的修改，可能破坏另一个阶段

RTL 变得更易综合，可能降低可验证性；修复时序的逻辑改写，可能改变功耗、面积或 DFT 结构；后端拥塞问题，可能要求回到微架构甚至接口协议重新取舍。

软件 Agent 常以“测试通过”作为相对清晰的终点。芯片研发往往面对的是多目标约束：

```text
功能正确
  ∩ 时序满足
  ∩ 功耗受控
  ∩ 面积可接受
  ∩ 可测性达标
  ∩ 物理规则通过
  ∩ 项目进度与算力预算可接受
```

### 2. 反馈周期长且成本不均匀

Lint 可能几秒完成，完整回归可能持续数小时，物理实现与 Signoff 可能需要更长时间并占用稀缺许可证。Agent 如果没有成本意识，会把“多试几次”变成不可接受的算力和排队开销。

所以任务规划不只要回答“下一步最可能解决问题的动作是什么”，还要考虑：

- 哪个检查最便宜，适合先排除明显错误；
- 哪些任务可以并行，哪些会争抢同一许可证；
- 什么时候应该运行局部测试，什么时候值得启动全量回归；
- 预计收益不足时，是否应停止搜索并请求人类裁决。

### 3. 上下文跨越多个表示层

一个问题可能同时涉及自然语言规格、SystemVerilog、UVM、约束文件、网表、时序路径、波形、版图对象和历史评审结论。Agent 需要的不只是“更多 Token”，而是知道何时读取哪一种证据，以及如何在这些表示之间建立对应关系。

### 4. 错误成本和保密要求更高

芯片研发包含 PDK、IP、版图、规格、客户信息和供应链数据。许多团队工作在物理隔离网络中，不能依赖云端模型、在线包管理器或远程遥测。一次错误签核带来的也不只是线上回滚，可能是昂贵的流片风险。

公开基准同样显示了当前能力边界。[SWE-bench Verified](https://www.swebench.com/verified.html) 通过 500 条人工审核的软件工程任务评估 Coding Agent；面向芯片设计与验证的 [CVDP](https://arxiv.org/abs/2506.14074) 则尝试把规格对齐、RTL、验证和调试组织成可执行任务。它们共同说明：评测对象不是模型能否补全一段代码，而是模型、工具、上下文和执行循环组成的整个系统能否可靠交付结果。

因此，芯片研发 Agent 的核心竞争力不是单次生成质量，而是**长周期闭环能力**。

## 三、平台的五个平面：把概率性智能放进确定性系统

一个生产级 AI-Native 芯片研发平台，可以划分为五个相互制约的平面。

```text
                    人类目标与裁决
                          │
                 ┌────────▼────────┐
                 │    治理平面     │
                 │ 权限/审批/审计  │
                 └────────┬────────┘
                          │
┌────────────┐   ┌────────▼────────┐   ┌────────────┐
│ 上下文平面 │──▶│    控制平面     │──▶│  执行平面  │
│ 规格/状态  │   │ 计划/调度/循环  │   │ EDA/代码库 │
│ 证据/记忆  │◀──│ 检查点/恢复     │◀──│ 集群/存储  │
└─────┬──────┘   └────────┬────────┘   └─────┬──────┘
      │                   │                  │
      └───────────────────▼──────────────────┘
                      评测平面
                 验收/回归/版本比较
```

### 1. 控制平面：决定循环怎么转

控制平面也就是广义的 Agent Harness。它负责：

- 接收目标并生成任务图；
- 为任务选择模型、工具和执行环境；
- 保存状态、检查点和依赖关系；
- 控制超时、重试、并发、预算和终止；
- 在失败后切换策略或请求人类介入；
- 把每一步行动记录为可审计 Trace。

模型负责提出下一步，Harness 决定这一步能不能执行、在哪里执行、执行后如何记录，以及什么时候必须停止。

### 2. 执行平面：让动作真正发生

执行平面包括 RTL 仓库、验证环境、EDA 工具、脚本、计算集群、许可证服务器、制品仓库和实验工作区。

这里必须强调：EDA 工具不是 Agent 的“插件列表”，而是具有明确输入、输出、资源消耗和副作用的生产系统。每次调用都需要绑定：

- 工具与版本；
- PDK、库和约束版本；
- 代码提交和工作区快照；
- 命令参数、环境变量和资源申请；
- 许可证类型和最长占用时间；
- 输出报告、日志和退出原因。

如果这些信息不能复现，一条成功轨迹就不能成为可靠经验。

### 3. 上下文平面：提供当前决策需要的证据

上下文平面不等于向量数据库。它管理的是规格、任务状态、设计对象、运行结果、历史决策和长期经验之间的关系。它必须回答：

- 当前任务有哪些硬约束？
- 哪些结论已经被工具验证？
- 哪些只是 Agent 的假设？
- 这份报告对应哪个代码、约束和工具版本？
- 某条经验适用于哪些工艺、模块和设计阶段？
- 哪些信息已经失效，不能继续注入上下文？

### 4. 评测平面：独立判断系统有没有变好

评测平面保存任务集、验收器、基线、失败分类和版本结果。它既用于开发期回归，也用于运行期质量检查。

一个新的 Prompt、一项工具优化或一个新的规划策略，都不能因为“看起来更合理”就进入生产。它需要在固定任务切片上与旧版本比较，并证明收益没有以安全、成本或局部能力退化为代价。

### 5. 治理平面：保留人的最终控制权

治理平面定义 Agent 能读什么、改什么、运行什么，以及哪些动作需要批准。它还负责设计冻结、例外豁免、最终签核、事故追踪和版本回滚。

AI-Native 的目标不是把人移出系统，而是让人的注意力集中在机器无法独立承担的高价值判断上。

## 四、Agent Loop：从一句目标到可审查结果

Agent 是否可靠，很大程度上取决于循环如何设计。

一个适合芯片研发的循环，不应只有“思考—调用工具—观察结果”，而应该显式区分计划、执行、自审和外部验收：

```text
Observe   读取任务状态、约束和最新证据
   ↓
Retrieve  按需获取规格、代码、报告和历史经验
   ↓
Plan      生成或修订任务图，估算成本与风险
   ↓
Act       调用工具或修改受控工作区
   ↓
Inspect   解析结构化结果，更新事实与假设
   ↓
Review    独立检查修改是否遗漏约束或引入风险
   ↓
Verify    运行外部验收器，确认完成条件
   ↓
Commit / Recover / Escalate
```

### 1. 循环从任务契约开始

任务契约至少应包含以下字段：

```yaml
goal: 修复模块 A 的跨时钟域握手问题
scope:
  writable:
    - rtl/module_a/**
  readonly:
    - spec/**
    - verification/**
constraints:
  - 不得改变软件可见寄存器行为
  - 不得新增异步复位路径
acceptance:
  - lint_error_count == 0
  - cdc_new_violation_count == 0
  - targeted_regression.pass_rate == 1.0
budget:
  wall_time: 90m
  full_regression_runs: 0
approval:
  required_for:
    - 修改接口协议
    - 扩大可写范围
```

任务契约把自然语言目标变成执行边界。Agent 可以改变计划，但不能悄悄改变验收条件。

### 2. 状态必须在上下文窗口之外持久化

长任务不能依赖聊天记录作为唯一状态。计划、动作、证据和决策应写入结构化任务状态：

```text
Task
├─ Objective
├─ Constraints
├─ Plan DAG
├─ Completed Steps
├─ Current Hypotheses
├─ Evidence Index
├─ Pending Risks
├─ Budget Usage
└─ Approval State
```

模型每次被调用时读取当前投影，而不是从头重放全部历史。这样即使模型切换、进程重启或上下文压缩，任务也能继续。

### 3. 自我审查不能替代验收

可以让 Reviewer Agent 检查 Diff、质疑假设或寻找遗漏，但 Reviewer 与执行 Agent 可能共享相同盲点。真正的完成判断应尽量来自独立工具和固定规则。

例如，Agent 可以解释为什么某个 CDC 告警是误报，但把它加入豁免列表属于改变验收口径，应触发人工闸门，而不能由 Agent 自己批准自己的解释。

### 4. 失败需要分类，而不是统一重试

“失败后再试一次”会掩盖真正的问题。Harness 至少应区分：

| 失败类型 | 例子 | 推荐动作 |
| --- | --- | --- |
| 环境失败 | 节点宕机、存储不可用 | 在等价环境恢复 |
| 许可证失败 | License checkout 超时 | 延迟、换队列或降低并发 |
| 工具失败 | 进程崩溃、输出损坏 | 收集诊断并按策略重跑 |
| 方案失败 | 修改后测试不通过 | 回滚修改，更新假设 |
| 规格冲突 | 两份约束互相矛盾 | 请求人类裁决 |
| 权限阻断 | 需要修改范围外文件 | 申请扩权，不得绕过 |
| 预算耗尽 | 搜索收益持续下降 | 停止并提交现有证据 |

只有分类正确，恢复策略才可能正确。

## 五、上下文工程：管理注意力，而不是堆满窗口

在芯片项目中，把所有规格、代码和报告一次性塞给模型几乎总是错误的。上下文窗口有限，更重要的是模型的有效注意力同样有限。无关日志越多，真正决定下一步的约束越容易被淹没。

[Anthropic 对 Agent 上下文工程的总结](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) 强调即时检索、压缩和结构化笔记。放到芯片研发场景中，可以把上下文分为四层。

### 1. 宪法层：不可被任务自行改写的边界

包括安全规则、权限、签核政策、项目级硬约束和工具使用规范。它们由平台或项目负责人发布，不允许 Agent 在执行任务时自行删除。

### 2. 工作层：当前循环真正需要的信息

包括任务目标、当前计划、最近观察、关键假设、剩余预算和待处理风险。这部分应短小、结构化，并在每轮后更新。

### 3. 证据层：按需读取的原始材料

源码、波形、日志、时序报告、覆盖率明细、规格章节等不必常驻上下文。系统应先建立索引，再根据任务读取最相关片段，同时保留来源和版本。

### 4. 经验层：经过验证的跨任务知识

经验不能只是“上次 Agent 的总结”。一条可进入长期记忆的经验至少应携带：

- 适用条件；
- 采取的动作；
- 观察到的结果；
- 通过了哪些验收；
- 哪些情况下不适用；
- 来源任务与版本。

可以把它表示为：

```text
经验 = 条件 + 动作 + 可复现证据 + 适用边界 + 来源
```

### 5. 压缩不是摘要全文，而是保留决策充分统计量

当上下文接近预算时，不应简单截断最早消息。压缩器应保留：

- 未改变的目标和硬约束；
- 已确认事实及其证据引用；
- 被否定的方案和失败原因；
- 尚未验证的假设；
- 当前工作区和工具运行状态；
- 下一步计划与停止条件。

原始 Trace 可以归档，但下一轮模型只需要能够恢复决策所必需的信息。

上下文治理最终要解决的不是“记得更多”，而是三个问题：**哪些信息现在有用，哪些结论足够可信，哪些知识已经过期。**

## 六、工具契约：让 Agent 调用的是能力，而不是脆弱命令

如果让模型自由拼接 Shell 命令、解析数万行日志，再自行判断是否成功，平台很快会变得不可控。生产环境中的工具需要被包装成具有类型、权限和语义的能力。

一个工具契约至少包括：

```ts
interface ToolContract<Input, Output> {
  name: string;
  inputSchema: Schema<Input>;
  outputSchema: Schema<Output>;
  permission: PermissionPolicy;
  resourceClass: "light" | "simulation" | "formal" | "physical";
  timeout: number;
  idempotency: "safe" | "conditional" | "unsafe";
  execute(input: Input, context: RunContext): Promise<Output>;
}
```

### 1. 输入必须可验证

模块名、文件范围、工艺角、测试集、资源规格和超时应进入 Schema。Harness 在工具执行前验证参数，而不是让下游脚本猜测模型意图。

### 2. 输出必须结构化

Agent 可以读取原始日志，但核心事实应由确定性解析器提取：

```json
{
  "status": "completed",
  "tool_version": "<version>",
  "design_revision": "<commit>",
  "metrics": {
    "violations": 0,
    "warnings": 12,
    "runtime_seconds": 438
  },
  "artifacts": [
    { "type": "report", "digest": "<sha256>" }
  ],
  "diagnostics": []
}
```

这样 Agent 读取的是明确事实，平台也能跨版本统计成功率。

### 3. 副作用必须可预览、可追踪、尽量可逆

读报告和创建临时实验分支风险较低；修改共享约束、提交主干、占用大规模回归资源或生成豁免则风险更高。工具层应在执行前给出动作预览，在执行后保存变更集，并为可逆操作提供补偿路径。

### 4. 验收器与执行工具必须分离

执行工具负责产生候选结果，验收器负责判断结果。两者使用独立配置和只读输入，可以降低 Agent 为了“完成任务”而改写测试、过滤错误或放宽阈值的机会。

如果任务要求提高故障覆盖率，Agent 可以修改 DFT 配置和设计，但不能同时修改覆盖率阈值。需要改变目标时，应重新签发任务契约。

## 七、把芯片全流程变成可执行任务

“覆盖架构、设计、验证、DFT、后端”不能只体现在五个 Agent 名称上。每个阶段都要建立任务单元、工具边界、验收标准和人类闸门。

| 阶段 | Agent 可以自主承担的任务 | 机器验收 | 关键人工裁决 |
| --- | --- | --- | --- |
| 架构 | 需求分解、性能模型、参数搜索、方案比较 | 约束一致性、模型可复现、工作负载结果 | 架构与接口冻结 |
| RTL | 编码、重构、集成、告警修复 | 编译、Lint、CDC/RDC、形式等价、定向回归 | 跨模块协议变更 |
| 验证 | 测试计划、激励、断言、覆盖率收敛、Bug 定位 | 回归结果、代码与功能覆盖率、断言证明 | 覆盖率豁免、验证签核 |
| DFT | Scan/MBIST 配置、DRC 修复、ATPG 分析 | Scan 连通性、故障覆盖率、X 分析、测试模式 STA | 测试策略和覆盖率例外 |
| 后端 | 综合、Floorplan、P&R、时序与功耗优化 | PPA、拥塞、STA、DRC/LVS、IR/EM | Signoff 与 Tape-out |

### 1. 架构阶段：输出可运行模型，而不是漂亮文档

架构 Agent 可以从产品目标中提取约束，构造性能或功耗模型，生成多个微架构候选，并在工作负载上比较。但它提交的不应只是一份叙述，而应包含：

- 可运行的模型和版本化参数；
- 需求到设计决策的映射；
- 敏感性分析和边界条件；
- 未解决假设及其影响；
- 选择当前方案而放弃其他方案的证据。

人类在这里裁决的是商业与技术取舍，而不是替 Agent 重跑每一个实验。

### 2. RTL 阶段：修改范围比生成能力更重要

RTL Agent 应优先处理边界清晰、验收充分的任务，例如局部模块实现、告警清理、已知 Bug 修复和参数化重构。扩大接口、改变时钟复位策略、调整软件可见行为时，风险会跨模块传播，需要更高等级审批。

每次 RTL 修改至少绑定 Diff、Lint、定向仿真、受影响断言和综合影响。仅仅“代码能编译”不代表任务完成。

### 3. 验证阶段：让验证成为 Agent 的外部世界模型

验证 Agent 不只是生成 Testbench。它应维护从规格项到测试、断言、覆盖点和缺陷的追踪关系，主动识别没有证据支撑的需求。

对于失败用例，Agent 需要区分设计缺陷、验证环境缺陷、测试期望错误、随机不稳定和基础设施故障。不同分类应进入不同处理队列，避免把所有红灯都交给 RTL Agent。

### 4. DFT 阶段：把覆盖率数字放回工程约束中

DFT Agent 的目标不是无条件提高一个总覆盖率。它还要考虑 Scan 链结构、压缩配置、X 源、Pattern 数量、测试时间、功耗和物理影响。

对不可测故障的分类与豁免必须保留证据。任何降低验收口径的动作都应进入人工闸门，避免 Agent 通过修改统计范围获得“进步”。

### 5. 后端阶段：搜索必须带预算和停止条件

后端天然适合迭代搜索，但每次 P&R 或 Signoff 都成本高昂。Agent 需要使用分层漏斗：先运行便宜的代理检查，再把少量有希望的候选推进到昂贵阶段。

一个合理策略可能是：

```text
快速静态检查
   ↓ 淘汰明显不可行候选
增量综合 / 局部实现
   ↓ 比较 PPA 与拥塞代理指标
完整实现
   ↓ 只保留 Pareto 前沿候选
Signoff
```

自主并不意味着无限搜索。预算、机会成本和停止条件必须成为计划的一部分。

## 八、多 Agent 不是开会，而是按责任边界组织生产

把架构、RTL、验证、DFT 和后端各自命名为一个 Agent，并让它们在群聊中讨论，不会自然产生工程协作。有效的多 Agent 系统必须建立在清晰的制品所有权、权限和交接协议上。

### 1. 按工作边界拆分，而不是按角色名称拆分

一个 Agent 边界成立，通常因为它拥有以下至少一项独立性：

- 独立的输入和输出制品；
- 独立的工具与权限；
- 独立的上下文和专业知识；
- 可以单独验收的完成条件；
- 需要与其他任务并行执行。

如果两个 Agent 修改同一批文件、共享同一上下文、调用同一工具并接受同一验收，把它们拆开通常只会增加协调成本。

### 2. 协调者维护任务图，不替专家完成所有工作

项目级 Orchestrator 负责拆解目标、安排依赖、管理预算和汇总证据。专业 Worker 在自己的受控工作区中执行任务，Reviewer 则从独立视角检查结果。

```text
Project Orchestrator
├─ Architecture Worker
├─ RTL Workers
├─ Verification Workers
├─ DFT Worker
├─ Physical Design Workers
└─ Independent Reviewers
```

协调者不应把所有子任务原文、完整日志和中间推理复制进自己的上下文。子 Agent 应提交结构化结果：完成状态、变更摘要、证据引用、未解决风险和建议的下一步。

### 3. Agent 之间传递制品和证据，不传递未经验证的确信

例如，RTL Agent 不能只告诉验证 Agent“握手问题已经修复”。它应提交代码版本、影响范围、通过的定向测试和仍未覆盖的条件。验证 Agent 根据这些事实选择回归，而不是继承前一个 Agent 的结论。

### 4. 跨阶段反馈应成为一等任务

后端发现拥塞或关键路径时，不能把一段报告扔回上游。平台需要生成带因果证据的反馈任务：哪些逻辑锥、物理区域和约束导致问题，建议从微架构、RTL、约束还是 Floorplan 哪一层处理，以及每种方案的预期代价。

这种结构化反馈使跨阶段闭环可以被统计：哪类问题最常从后端回流，哪些设计模式频繁造成 DFT 或验证成本，哪些早期检查能提前拦截它们。

## 九、可靠性不是感觉：建立芯片研发 Agent 的 Evals

当一个 Agent 偶尔完成了一次复杂任务，最容易产生的误判是“能力已经具备”。但概率系统的关键问题是：换一个模块、换一份规格、换一次采样，它还能不能完成？

可靠性必须被度量，而且不能只看最终成功率。

### 1. 四层指标体系

| 层级 | 关键问题 | 示例指标 |
| --- | --- | --- |
| 结果层 | 任务到底完成了吗 | Pass@1、Pass@k、验收通过率、缺陷逃逸率 |
| 过程层 | 它以什么代价、通过什么路径完成 | 工具调用次数、无效重试、回滚率、人工介入率 |
| 工程层 | 对项目指标产生了什么影响 | PPA、覆盖率、收敛时间、许可证小时、算力成本 |
| 安全层 | 是否触碰不可接受边界 | 越权率、误改验收器、敏感数据访问、不可逆误操作 |

总成功率不能掩盖局部灾难。平台必须按阶段、任务类型、模块规模、工具链、工艺节点、上下文长度和风险等级分别统计。

### 2. 一条评测任务必须可以被重新执行

高质量任务集至少包含：

- 冻结的起始代码和环境；
- 对 Agent 可见的任务描述；
- 对 Agent 不可见或不可修改的验收器；
- 资源和时间预算；
- 允许的工具和权限；
- 人工确认的任务分类；
- 失败时可用于诊断的标准标签。

对于非确定性系统，同一任务应运行多次。只报告“最好的一次”会把重试预算伪装成能力。至少要同时报告首次成功率、限定预算内成功率、成本分布和尾部失败。

### 3. 从真实 Trace 中建立回归集

公开 Benchmark 适合验证通用能力，但企业最有价值的评测资产来自真实项目：

- 曾经消耗大量人力的 Bug；
- Agent 曾经误判或越权的任务；
- 工具输出异常、规格冲突和许可证故障；
- 容易被总指标掩盖的长尾模块；
- 专家认为简单、系统却反复失败的案例。

每次严重失败都应回答：它是否值得转化为一条永不回归的测试？如果只修当前 Prompt 而不建立回归任务，团队无法知道同类错误何时再次出现。

### 4. 结果评测与轨迹评测必须同时存在

两个 Agent 都可能让回归通过，但其中一个读取了禁止访问的答案、修改了测试、浪费十倍资源，或者依赖一次偶然成功。只看终点无法发现这些问题。

轨迹评测应检查：

- 是否在授权范围内读取和修改；
- 是否优先运行低成本、高信息量的检查；
- 是否正确处理工具错误；
- 是否在证据不足时表达不确定性；
- 是否保留完整的代码、环境和报告版本；
- 是否遵守停止与升级规则。

### 5. 发布门禁应是多约束判断

假设新 Harness 版本提升了 RTL 修复成功率，却增加了越权操作，或者让平均运行成本翻倍，它不能简单因为总分更高就上线。

一个实际的发布条件可以写成：

```text
核心任务成功率不下降
AND 高风险任务成功率达到阈值
AND 安全违规为零
AND P95 成本和时延在预算内
AND 关键任务切片无显著回退
AND 所有新增能力可审计、可回滚
```

评测的价值不是产生一个漂亮数字，而是让每次平台改动都承担举证责任。

## 十、人类在回路：把注意力放在不可自动裁决的地方

“Human-in-the-loop”不应退化成每次工具调用都弹出确认框。那只会让人类重新成为低效操作员，也会让审批变成机械点击。

合理的人类闸门应放在三类位置。

### 1. 目标与约束发生变化

例如修改架构目标、接口协议、时钟复位策略、软件可见行为、测试策略或 Signoff 标准。这些变化会改变任务本身，不能被视为原任务中的普通动作。

### 2. 机器证据无法唯一决定取舍

多个候选可能位于 PPA 的 Pareto 前沿，没有唯一最优解；某个 DFT 例外可能在覆盖率、测试时间与物理影响之间取舍；某项规格本身可能存在歧义。此时人类负责价值判断。

### 3. 动作风险超过 Agent 的授权等级

包括修改共享基线、合入受保护分支、提交豁免、发起大规模回归、触发 Signoff、发布新的 Harness 版本等。

为了让裁决高效，Agent 提交的不是一句“请批准”，而是一份**决策包**：

```text
决策问题
├─ 当前状态与阻塞原因
├─ 已验证事实及证据链接
├─ 候选方案和预期影响
├─ 风险、不可逆部分与回滚方式
├─ Agent 推荐及其置信依据
└─ 需要人类明确选择的选项
```

人类裁决本身也应成为数据：选择了什么、推翻了 Agent 哪个假设、依据是什么、是否形成新的政策。这样平台才能学习怎样更早发现需要升级的问题，而不是反复把同类歧义交给人。

## 十一、从项目数据到学习飞轮

真实研发会产生海量日志，但日志不等于经验。只有被整理成可查询、可验证、可复用的资产，数据才会提高下一轮研发能力。

可以把数据飞轮分为五个层次：

```text
原始事件
  ↓ 还原发生了什么
任务轨迹 Episode
  ↓ 标注成败与关键决策
故障模式 / 成功模式
  ↓ 提炼适用条件和可执行动作
Skill / Policy / Tool 改进
  ↓ 通过回归任务验证
新的生产版本
```

### 1. 原始事件层：保留事实

记录模型请求、工具调用、代码 Diff、环境版本、资源消耗、审批和验收结果。原始层不做过度解释，重点是完整与可追溯。

### 2. Episode 层：恢复任务因果链

把跨越多个进程、工具和 Agent 的事件组织为一次任务：目标是什么，采取了哪些行动，在哪一步改变了计划，最终为何成功或失败。

### 3. 模式层：从个案中发现重复结构

例如某类 CDC 修复总在接口假设上失败，某类回归错误通常来自环境而非设计，某个物理约束组合频繁导致拥塞。模式需要通过多条任务或专家复核，不能由单次轨迹直接升级为通用规律。

### 4. 能力层：把知识变成系统改动

经验可以进入检索库，也可以变成更可靠的工具、任务模板、验证规则、故障分类器、调度策略或新的评测任务。通常后者比一段自然语言记忆更稳定。

### 5. 发布层：用评测证明改进

任何经验进入生产前，都要回答：它提升了哪个任务切片？是否伤害其他切片？增加了多少成本？能否回滚？

真正的飞轮不是“数据越多，模型自然越强”，而是：

> 生产暴露真实问题，问题变成评测，评测推动系统改动，经过验证的改动再进入生产。

## 十二、从持续改进到 RSI：先改 Harness，再谈改模型

RSI 很容易被描述成“AI 不断让自己变聪明”。工程上更有用的定义是：

> 系统能够提出对自身能力栈的修改，使用外部评测验证效果，保留有效版本，并让改进后的系统继续参与下一轮改进。

这里的“自身”不只指模型权重。对于芯片研发平台，更现实、更可控的改进对象包括：

- Prompt 与上下文组装策略；
- 检索、压缩和长期记忆规则；
- 工具 Schema、解析器和错误恢复；
- 任务拆解、调度和多 Agent 协作方式；
- Reviewer、验收器和回归任务；
- Harness 的源代码与运行配置；
- 小模型、分类器或领域适配模型。

[Darwin Gödel Machine](https://arxiv.org/abs/2505.22954) 展示了一条重要路线：让 Coding Agent 修改自身脚手架代码，再由外部软件工程基准选择更有效的候选。[AlphaEvolve](https://arxiv.org/abs/2506.13131) 则把 LLM 生成、自动评估和演化搜索结合起来，用评估器驱动程序与算法的迭代。

二者最值得芯片研发平台借鉴的，不是“递归”这个宏大词汇，而是四个可操作部件：

1. 改动必须以版本化制品存在；
2. 效果必须由外部评估器判断；
3. 搜索过程需要保留多样性，而不是只沿单一路径爬山；
4. 新版本必须经过选择、归档和回归，不能直接覆盖生产系统。

### 1. RSI 的渐进层级

| 层级 | 平台具备的能力 | 主要风险 |
| --- | --- | --- |
| L0 可观测 | 完整记录任务与失败 | 只有数据，没有改进 |
| L1 经验复用 | 检索已验证经验和模板 | 经验过期或错误迁移 |
| L2 自动优化 | 自动提出 Prompt、工具或流程改动 | 对开发集过拟合 |
| L3 Harness 自修改 | 修改控制循环与 Agent 代码 | 引入系统级回归 |
| L4 开放式搜索 | 并行探索多种系统结构 | 成本、目标投机与治理失控 |
| L5 递归增强 | 改进后的系统提高后续改进效率 | 评测边界被系统利用 |

在真实芯片项目中，L2 到 L3 已经足够产生巨大价值，也足够危险。平台不应为了追求“自我改进”的名义跳过可观测、评测和发布治理。

### 2. 一个受控的自我改进流水线

```text
生产失败与机会发现
        ↓
改进 Agent 提出候选 Patch
        ↓
静态检查 + 单元测试 + 安全扫描
        ↓
历史任务回放 + 隐藏任务评测
        ↓
成本 / 安全 / 分任务切片对比
        ↓
影子运行，不影响真实设计
        ↓
人工审批
        ↓
小范围灰度 + 自动回滚
        ↓
正式发布并保留旧版本
```

改进 Agent 不得修改自己的隐藏测试、发布阈值和审计记录。评测基础设施与生产 Agent 之间必须有权限隔离。

### 3. 防止系统“优化错目标”

如果只奖励完成速度，Agent 可能减少必要检查；只奖励覆盖率，它可能生成大量低价值测试；只奖励工具成功率，它可能回避困难任务；只奖励人类满意度，它可能倾向于给出更自信的叙述。

因此 RSI 的目标函数必须是多维约束，包含正确性、安全、成本、泛化、可维护性和人类介入质量。还需要保留隐藏评测、对抗任务和跨项目验证，防止系统只适应已知回归集。

### 4. RSI 的真正资产是改进机制

一个项目中形成的具体规则未必能迁移到另一个工艺或 IP，但“怎样从失败生成任务、怎样验证改动、怎样发现回退、怎样安全发布”具有更强的通用性。

平台越成熟，竞争力越不只是拥有多少 Prompt，而是拥有一套能够持续制造、验证和交付新能力的系统。

---

## 十三、物理隔离环境：离线交付不是部署细节

对于芯片研发团队，物理隔离往往是设计前提。平台不能在开发完成后再考虑“怎样搬进去”，因为联网依赖会渗透进模型下载、容器构建、包管理、许可证、遥测、文档和故障诊断的每一层。

一个可持续的离线体系通常包含三个区域：

```text
联网构建区
  ├─ 获取模型、源码、依赖、镜像和漏洞信息
  ├─ 构建、测试、生成 SBOM 与签名
  ↓ 受控介质 / 审批通道
交换区
  ├─ 病毒与恶意代码扫描
  ├─ 哈希、签名、许可证与清单核验
  ↓ 批准导入
物理隔离研发区
  ├─ 内部 Git / 包仓库 / 镜像仓库 / 模型仓库
  ├─ Agent 平台、EDA 环境、计算集群
  └─ 本地可观测、备份、升级与回滚
```

[NVIDIA 的 Air-Gapped 部署文档](https://docs.nvidia.com/nim/large-language-models/latest/deployment/air-gap-deployment.html) 展示了预取模型与容器、在隔离区使用本地制品的基本模式；[NIST SSDF](https://csrc.nist.gov/pubs/sp/800/218/final) 则提供了软件来源、构建与漏洞治理的通用安全框架。落到芯片研发平台，还需要处理 EDA 与 PDK 的特殊约束。

### 1. 所有依赖必须显式化

安装和运行过程不得隐式访问公网。模型权重、Tokenizer、Python/Node/系统包、容器基础镜像、浏览器驱动、工具文档和许可证组件都要进入离线清单。

### 2. 制品必须可证明来源

每个交付包应包含：

- 版本与变更记录；
- 文件哈希和数字签名；
- SBOM 与第三方许可证；
- 构建来源和测试结果；
- 已知漏洞与处置意见；
- 安装、验证、回滚和兼容矩阵。

### 3. 模型与设计数据必须本地闭环

推理请求、Trace、Prompt、日志和评测数据不能通过遥测或崩溃上报流出隔离区。模型服务、Embedding、Reranker、评测模型和可观测系统都需要本地部署。

### 4. 更新机制必须适合长期运行

离线环境并不意味着永不更新。它需要更严格的批次化升级：联网区准备候选版本，交换区验证，隔离区先运行回归与影子任务，再灰度到部分队列。任何升级都要能回到上一套完整可运行版本。

物理隔离能力最终体现在一个问题上：**没有公网、没有临时下载、没有厂商远程介入时，平台能否被安装、诊断、升级和恢复。**

---

## 十四、7×24 运行：把 Agent 当生产系统，而不是长时间脚本

真实芯片项目中的 Agent 会跨小时、跨天运行，并同时占用模型、EDA 许可证、计算节点和大规模存储。平台需要具备分布式系统的基本纪律。

### 1. 调度器必须理解多种稀缺资源

普通任务队列只看 CPU 和内存远远不够。调度还应理解 GPU 型号、EDA 许可证、工艺环境、存储带宽、任务优先级和项目隔离。

全量回归、形式验证和后端实现不能被低价值探索任务挤占。预算应同时包含金额、Token、许可证小时、节点小时和最长墙钟时间。

### 2. 每个长任务都必须支持检查点和恢复

检查点不仅保存模型对话，还要保存：

- 当前任务状态与计划版本；
- 代码和约束快照；
- 已完成工具调用及制品哈希；
- 运行中的外部 Job ID；
- 已使用与剩余预算；
- 等待中的审批和锁。

恢复时先核对外部世界，而不是盲目重放动作。某个 Job 可能已在 Agent 进程宕机后完成，重复提交会浪费资源或产生冲突。

### 3. 工作区隔离与幂等性必须默认存在

每个候选方案使用独立工作区和命名空间。共享基线只通过受控合并更新。重复消息、进程重启或网络抖动不应导致同一提交被多次合入、同一审批被多次消费。

### 4. 可观测性必须还原因果，而不是堆日志

一次任务应能沿着以下关系追踪：

```text
项目目标
→ 任务
→ Agent 运行
→ 模型决策
→ 工具调用
→ EDA Job
→ 设计制品
→ 验收结果
→ 人工裁决
```

运维人员需要知道失败发生在哪一层：模型、Harness、工具包装、EDA、基础设施、许可证还是数据。只有因果链完整，平台才能统计真实故障率并改进恢复策略。

### 5. 生产目标应包括恢复能力

除了任务成功率，还应监控：

- 任务恢复成功率；
- 平均恢复时间；
- 重复副作用次数；
- 许可证无效占用时间；
- 因上下文丢失导致的重新执行成本；
- 需要人工接管但未及时升级的比例。

一个永不失败的 Agent 不现实。一个能够识别失败、限制损失、保存证据并恢复任务的系统，才有资格 7×24 运行。

---

## 十五、实施路线：从一个高价值闭环开始

建设这样的平台，最危险的方式是先做一个覆盖全部阶段的通用多 Agent 平台，再等待业务接入。更稳妥的路径是围绕真实任务逐步扩展自主边界。

### 阶段一：建立可观测的受限闭环

选择验收明确、风险可控、重复出现的任务，例如 Lint/CDC 告警修复、定向回归失败定位或报告归因。

目标不是展示一次成功，而是积累至少数十到数百条可重复任务，建立基线、失败分类和人工介入记录。

### 阶段二：让 Agent 对结果负责

加入任务契约、工具 Schema、独立验收器、预算、检查点和回滚。Agent 从“提出建议”升级为在隔离工作区交付候选修改和证据包。

### 阶段三：打通跨工具与跨阶段反馈

让一个任务可以使用多个工具完成闭环，并把验证、DFT、后端发现的问题结构化回流到设计阶段。此时再引入多 Agent 协作，而不是一开始就追求角色数量。

### 阶段四：形成跨项目经验资产

建设 Episode、故障模式、Skill 和回归任务的生产线。明确哪些知识仅属于当前项目，哪些可以经过脱敏和验证后提升平台公共能力。

### 阶段五：启动受控自我改进

允许改进 Agent 修改 Prompt、工具、策略和 Harness 代码，但只在沙箱和评测环境中生效。通过隐藏任务、影子运行、人工审批与灰度发布进入生产。

每个阶段的升级条件都应是量化结果，而不是功能清单。例如：

```text
成功率达到目标
AND 严重安全事件为零
AND 人工介入率持续下降
AND 单任务成本在预算内
AND 新版本在关键切片无回退
```

---

## 十六、什么样的人适合建设这个平台

这份工作的核心不是“会不会调用某个 Agent 框架”，而是能否把一个概率性系统变成可靠的研发生产力。

### 1. 理解 Harness 与上下文工程

能够说清 Agent Loop 如何转动、状态如何跨轮次持久化、工具为什么需要结构化契约、上下文如何检索与压缩，以及任务在什么条件下停止、恢复或升级给人类。

更重要的是，做过真实取舍：为什么某次重试应该发生，为什么另一种失败不应重试；为什么某条记忆可以复用，另一条只能留在当前项目。

### 2. 对可靠性做过度量

真正做过 Evals、成功率统计、Golden Set、回归任务集或线上 Trace 分析。能够讨论样本量、分任务切片、非确定性、多次运行、成本约束、评测污染和指标投机，而不只是展示几个成功案例。

### 3. 认同可验证的 RSI 路线

理解自我改进不是让 Agent 写一段反思，而是让系统改动可以版本化、执行、比较、回滚和积累。愿意把项目经验沉淀成任务、工具、验收器、数据集和发布流程。

### 4. 跟踪前沿并真正动手

不只读过 SWE-bench、Darwin Gödel Machine、AlphaEvolve、Reflexion 或相关工作，而是复现、改造或质疑过其中的机制：基准是否泄漏，搜索预算如何影响分数，Harness 改进能否迁移，评估器会不会被利用。

### 5. 能在受限环境中交付软件

具备物理隔离、离线安装、制品供应链、本地模型服务、可观测与升级回滚经验。能够接受一个现实：在研发内网里，不能用“连公网再试一次”解决依赖和诊断问题。

### 6. 芯片或 EDA 背景是重要加分项

理解架构、RTL、验证、DFT 或后端中的至少一个真实工作流，知道报告中的数字为何可能误导，也知道哪些签核责任不能被一句自然语言总结替代。

判断候选人的最好方式，不是关键词问答，而是要求他展示一个失败过的 Agent 系统：失败如何被发现，怎样变成评测，系统改了什么，指标是否真的改善，又付出了什么代价。

---

## 结语：不是让 AI 辅助造芯片，而是建设会学习如何造芯片的系统

AI-Native 芯片研发的真正门槛，不是模型能生成多少 RTL，也不是同时运行多少 Agent。门槛在于能否把自主行为放进一个严格的工程闭环：

- 目标被写成任务契约；
- 工具调用受到权限和 Schema 约束；
- 上下文在窗口之外被持续治理；
- 每个阶段拥有独立、可执行的验收标准；
- 人类在高价值节点裁决，而不是替系统收拾所有细节；
- 每次失败都能转化为新的评测和能力资产；
- 每次平台改进都经过回归、审批、灰度和回滚。

沿着这条路线，AI 首先接管边界清晰的单项任务，然后承担跨工具、跨阶段的研发闭环，最终参与改进承载自己的 Harness、工具和流程。

RSI 并不是一个突然到来的能力跃迁。它开始于一个朴素但严格的循环：**系统完成真实任务，外部证据判断成败，失败进入评测，评测推动改进，改进后的系统再回到真实任务。**

当这个循环能够长期、稳定、安全地运行，研发中沉淀的每一条经验就不再只属于某个工程师或某个项目，而会成为平台下一轮工作的起点。

这才是 AI-Native 芯片研发平台最终要建设的东西：不是一个会回答芯片问题的模型，而是一套能够持续学习如何把芯片做出来的研发系统。
