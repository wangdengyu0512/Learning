**新版 AI 的评测分数更高，只能说明它在这次实验里得分更高。要判断是否值得上线，还需要回答四个问题：测量是否对应目标业务、改善有多大、证据有多确定、成本与风险是否可接受。**

先给出本文贯穿案例的结论：两个采购 Agent 在同样的 100 个任务上，成功率从 82% 提升到 86%；其中 8 个任务改善，4 个任务退化。虽然净提升为 4 个百分点，但差异的近似 95% 置信区间为 **−2.78 到 +10.78 个百分点**，精确配对检验的 p 值约为 **0.388**。这批数据尚不足以确认新版具有稳定优势，也不能证明两个版本效果相同。

这个结论依赖后文说明的抽样与独立性假设。案例全部为人工构造的教学数据，代码可以复算；论文提供方法依据，不为这组虚构成绩背书。

读完本文，你应该能够写出这样的评测判断：在哪类任务、什么预算和评分规则下，新版改善了多少，仍有哪些不确定性，以及下一步应该灰度验证、继续收集证据，还是先修复退化。

## 一、先定义“更好”，再开始跑分

**实验开始前，应先写清楚要支持的决策。否则，即使分数算得准确，也可能回答了错误的问题。**

假设采购 Agent 负责读取需求、核对库存、选择供应商并创建订单。新版增加了规划步骤，可能提高正确率，也可能增加工具调用、延迟和费用。《AI Agents That Matter》指出，只关注准确率会掩盖 Agent 的成本问题，主张联合考察准确率与成本，同时明确评测面向的实际用途。[1]

因此，“新版更好”至少可能有三种含义：相同预算下成功更多、成功率相当时更便宜，或增加的收益足以覆盖额外成本。本次教学实验选择第一种，先约定：

| 设计项 | 本次实验的约定 |
| --- | --- |
| 目标总体 | 当前业务范围内允许自动处理的标准采购需求 |
| 独立任务 | 一条采购需求及其初始库存、权限和订单状态 |
| 主指标 | 给定预算内，无需人工修复的正确完成率 |
| 成功标准 | 对象、数量、金额和审批正确，且没有重复订单等违规副作用 |
| 运行预算 | 两个版本使用相同的时间、费用和工具调用上限 |
| 实际改善门槛 | 假设至少提升 3 个百分点才值得承担迁移成本 |
| 护栏 | 越权、重复订单、延迟、人工接管及费用，分别设定可接受标准 |
| 比较方式 | 同一批任务、隔离并重置的环境、同一评分规则 |

这里的 3 个百分点只是业务门槛示例，需要在看结果前确定。它与统计检验中的显著性水平是两个量：前者描述改善值不值得，后者参与控制统计判断的错误率。[2][3]

预算相同指上限相同，实际消耗仍要记录。一次运行可以包含预先允许的内部重试；超时、预算耗尽和人工修复后的完成，都应按约定归类。若想评价带人工接管的完整产品，可以另设“整体完成率”，并同时记录人工成本。

本节最实用的产出，是把这张表保存为实验协议。后续换模型、改提示词或升级评分器时，才能知道比较条件是否发生了变化。

## 二、分数为什么会变：先看数据是怎样产生的

**评测至少有两层不确定性：抽到了哪些任务，以及系统在这些任务上如何运行。两层数据需要分别保留。**

《Adding Error Bars to Evals》把评测题目视为从更大任务总体中抽出的样本，以此讨论总体能力、模型差异和实验规划。[2] 这个视角要求我们先说明推断目标：如果只关心固定题库的得分，它是该题库上的结果；如果要推断未来业务表现，就需要任务分布和抽样假设。

### 任务不同，结论的适用范围也不同

100 条简单采购需求与 100 条涉及缺货、替代品和权限异常的需求，衡量的是不同任务组合上的效果。增加数量可以提高一定条件下的估计精度，却不会自动让样本更接近生产流量。

建议把数据分成两个用途：一组按目标流量抽样，用来估计整体效果；另一组覆盖高风险和少见边界，用来发现失败模式。若为了覆盖困难场景而过度抽样，整体结果需要根据目标业务占比加权，并保留分层结果。后文的计算只针对未加权、独立抽样的简单案例。[2]

“1000 条记录”也不一定代表 1000 个独立任务。同一客户、文档或模板衍生的样例可能共享难度和错误原因。此时要识别独立分组，在分析和重采样时保留组内关联；否则区间可能过窄。[2]

### 同一任务重跑，也是一种实验

对同一需求重复运行，可以观察输出、工具路径或用户模拟带来的变化。数据应保存为下表这种结构，而不是直接把所有结果压成一个平均分：

| task_id | 旧版第 1 次 | 旧版第 2 次 | 新版第 1 次 | 新版第 2 次 |
| --- | --- | --- | --- | --- |
| T001 | 成功 | 成功 | 成功 | 成功 |
| T002 | 失败 | 成功 | 成功 | 失败 |
| T003 | 失败 | 失败 | 成功 | 成功 |

如果目标是估计任务总体上的平均一次运行成功率，可以先计算每个任务在各版本下的平均结果，再比较任务级差异。任务之间若独立，任务就是一种自然的分析单位。重采样时应成对保留同一任务两个版本的数据；存在更上层分组时，应进一步按独立分组处理。[2]

更多独立任务通常有助于扩大覆盖，更多重复运行有助于看清任务内波动。预算怎样分配，应结合先导实验和要回答的问题决定，不能把同一题跑十次直接解释为覆盖了十个新任务。

### 单次成功、至少一次成功、每次都成功，分别回答什么

τ-bench 通过任务结束后的数据库状态验证目标，并提出 `pass^k` 评价多次运行的一致成功情况。[4] 它与常见的 `pass@k` 含义不同：

| 指标 | 回答的问题 |
| --- | --- |
| 单次成功率 | 按既定运行策略执行一次，有多大机会成功？ |
| pass@k | 进行 k 次尝试，是否至少有一次成功？ |
| pass^k | 进行 k 次尝试，是否全部成功？ |

为理解差别，假设一个固定任务每次独立成功的概率都是 0.8。三次尝试至少一次成功的概率是 `1 − (1 − 0.8)^3 = 99.2%`，三次全部成功的概率是 `0.8^3 = 51.2%`。这是理想化计算；真实任务的难度不同、尝试之间可能相关，不能直接把整体平均成功率代入公式估计实际指标。

如果产品线上只执行一次，离线就应报告相应的一次运行效果。若产品允许多次尝试，还需要评估预算、失败副作用，以及系统能否识别并选择正确结果；“生成过正确答案”本身不能保证最终交付正确。

## 三、核心案例：从 82% 到 86%，到底改善了什么

**比较两个版本时，最需要估计的是它们的差异，并保留同一任务上的配对关系。** 这也是语言模型评测统计分析中的核心建议之一。[2]

### 先把平均分还原成任务结果

两个版本分别成功 82 次和 86 次，绝对提升是 4 个百分点；相对成功率提升约为 `4 / 82 = 4.88%`。报告时优先给出原始分子、分母和绝对变化。

因为使用的是同一批任务，我们还能得到完整的四格表：

|  | 新版成功 | 新版失败 | 合计 |
| --- | --- | --- | --- |
| 旧版成功 | 78 | 4 | 82 |
| 旧版失败 | 8 | 10 | 18 |
| 合计 | 86 | 14 | 100 |

从中可以读出：78 个任务共同成功，10 个共同失败；新版修好了 8 个，也让原本成功的 4 个退化。净改善是 `(8 − 4) / 100 = 4%`。

这张表既支持统计分析，也支持工程排查。改善和退化是否集中在某种工具、任务类型或异常路径，通常比“总分提高了”更容易转化成下一次修改。

### 给差异加上区间

令每个任务的差值 `d = 新版结果 − 旧版结果`，成功记为 1，失败记为 0。那么 8 个差值为 +1，4 个为 −1，其余 88 个为 0。

在任务对独立、来自目标分布等假设下，平均差值为 0.04。用任务差值的样本标准差除以样本量平方根，得到标准误约 0.03458；再用正态近似构造区间：[2]

```text
平均差值 ± 1.96 × 标准误
= 0.04 ± 1.96 × 0.03458
≈ [−0.0278, 0.1078]
```

换成更容易阅读的单位，就是 **−2.78 到 +10.78 个百分点**。点估计偏向新版，但估计仍不精确，区间包含退化、零改善和超过业务门槛的提升。

这里使用的是便于讲解的近似区间；本例只有 12 个不一致任务，小样本覆盖率可能偏离标称值。正式分析可以选择适合配对比例的区间方法，或保留配对和分组结构的 bootstrap，并核对相应适用条件。bootstrap 也不能修复样本代表性不足。[2][3]

95% 置信区间描述的是区间构造方法在重复抽样下的覆盖性质，不能直接解释成“真实差异有 95% 的概率位于这一次区间内”。比较版本时，也不能仅凭两个单独成功率区间是否重叠作出判断。[2]

### 检验回答的是另一个更窄的问题

对于配对的二元结果，可以使用 McNemar 检验。它聚焦不一致任务：在“两个版本边际成功率相同”的原假设下，改善和退化方向应具有相同概率。条件于 12 个不一致任务，8 次改善、4 次退化的双侧精确 p 值约为 0.388。[3]

如果实验预先采用 0.05 显著性水平，这个结果不能拒绝原假设。p 值不是“新版没有提升的概率”，也不描述改善有多大。

**没有发现明确差异，不等于证明两个版本相同。** 若要支持“性能足够接近，可以换成更便宜的版本”，应预先定义允许的退化幅度，并设计非劣效或等效分析。若要支持“至少改善 3 个百分点”，也需要直接围绕这个业务门槛形成证据；仅检验是否大于零还不够。[2][3]

对于本例，能够写下的结论是：“观察到净改善 4 个百分点，但尚未确认总体改善，更没有确认改善达到预设的 3 个百分点门槛。”

## 四、需要多少任务，应该在什么时候停止

**样本量取决于希望识别多小的差异、愿意承担多大的统计错误，以及任务结果的波动。不存在通用的‘测 100 条就够了’。**[2][5]

假设真实改善就是你关心的幅度，实验有多大概率检出它，这就是统计功效讨论的问题。低功效实验容易漏掉真实改善；而在低功效条件下被筛选出来的显著结果，还可能高估效应。《With Little Power Comes Great Responsibility》系统讨论了 NLP 实验中的这些问题。[5]

规划时，至少需要明确基线、最小关注差异、显著性水平、目标功效和实验设计。配对二元任务还需要估计不一致结果比例：两套系统总分相近，但错误是否发生在同一批任务上，会影响差异的不确定性。[2]

附录给出一个粗略规划例子：假设不一致结果占 12%，双侧显著性水平为 0.05、目标功效为 80%，识别 4 个百分点改善大致需要数百个任务；把目标改善减半到 2 个百分点，所需数量约增加到四倍。这是正态近似下的量级说明，12% 也是先导估计，不能直接当成正式验收数量。

这里还要区分两个目标：“当真实改善为 3 个百分点时检出差异大于零”，与“确认改善超过 3 个百分点”。后者需要围绕业务门槛另做规划，不能套用前者的样本量。

### 留出验收集，控制看结果的方式

开发阶段可以反复分析错误、调整提示词。用于这些反馈的样例，应归入开发或回归集合。最终候选方案、预算和评分规则冻结后，再在独立保留集上验收。《The Ladder》讨论了反复利用排行榜反馈带来的自适应过拟合，《AI Agents That Matter》也指出 Agent 基准保留集不足的问题。[1][6]

同样，普通固定样本检验不适合“每跑十条看一次，显著了就停止”。若需要持续监测并随时决策，应采用针对这种停止方式设计的序贯方法；否则就预先固定样本量与终点。相关方法可参考《Always Valid Inference》。[7]

本例已经看过 100 对结果，后续不能简单追加到显著为止。可以把本轮作为先导实验，用它规划下一轮独立确认实验。若正式实验同时比较多个候选方案或检验多个主假设，还应预先约定多重比较处理方式，避免只挑最有利的结果报告。[3]

## 五、评分系统也需要验证

**置信区间描述的是既定测量过程下的不确定性。评分规则本身存在系统性偏差时，增加样本不会自动消除偏差。**

采购 Agent 的最终回复可能很流畅，但订单数量错误、审批缺失，或者创建了两张订单。建议把评分拆成可以核验的条件：订单数据库检查执行结果，权限与审计记录检查操作合法性，人类或模型评判器处理解释是否清楚等开放问题。

τ-bench 使用最终数据库状态与目标状态比较，为结果验证提供了一个具体例子。[4] 在实际业务中，还需要根据成功定义补充过程约束；最终状态正确，不代表中途所有操作都符合规则。

《Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena》研究了模型评判器的位置偏差、篇幅偏好和自我偏好等问题。论文中的一致性结果来自特定数据与任务，不能直接替代本业务的校准。[8]

本例采用如下评分协议：

| 环节 | 具体做法 | 要解决的问题 |
| --- | --- | --- |
| 硬条件验证 | 检查订单、审批、库存及重复副作用 | 回复是否与实际结果一致 |
| 开放质量比较 | 隐去版本名称，随机呈现顺序；必要时交换顺序复评 | 评分是否受身份和位置影响 |
| 人工校准 | 抽查成功与失败样本，并额外覆盖高影响错误 | 哪些错误容易被评判器漏掉 |
| 争议处理 | 按固定规则由人工复核，并保存判定依据 | 模糊样例如何统一口径 |
| 版本记录 | 固定规则、模型、提示词和工具环境版本 | 分数变化是否来自评分变化 |

人工校准时，应分别查看不同失败类型上的误判与漏判。若真实失败占比很低，一个总是判成功的评分器也可能获得很高的总体一致率，因此不能只报告这个数。

最终保存的不应只有 `success=true`，还应包含足以复核结论的订单状态、工具轨迹或人工判定依据。

## 六、把结果写成一份可执行的决策

**评测报告要让读者看见证据支持到哪里，以及下一步怎样消除关键不确定性。** 以下结论形式将统计评测、成本约束和独立验收结合起来。[1][2]

对于本文案例，一份可以交付的报告摘要是：

> 在 100 个独立抽取的标准采购任务上，两版本使用相同运行预算与评分规则，各执行一次。旧版成功 82 次，新版成功 86 次，绝对改善 4 个百分点，其中 8 个改善、4 个退化。差异的正态近似 95% 区间为 −2.78 到 +10.78 个百分点，精确 McNemar 检验 p≈0.388。
>
> 本轮结果尚未确认新版优于旧版，也未确认达到预先约定的 3 个百分点改善门槛。当前教学数据没有费用、延迟与风险记录，因此不能据此完成上线判断。下一步应复核 4 个退化任务、补齐护栏数据，并以本轮作为先导信息规划独立确认实验。

面对不同结果，团队可以预先约定三种行动：

| 行动 | 需要看到的证据 |
| --- | --- |
| 进入灰度验证 | 达到预设的离线效果标准，关键护栏通过，费用和延迟可接受 |
| 继续收集证据 | 区间仍宽，覆盖不可接受的退化和有价值的改善，且没有必须先修复的故障 |
| 修复后重新评测 | 发现越权、重复订单等不可接受问题，或关键场景出现明确退化 |

离线评测之后，灰度或线上随机实验可以进一步观察真实用户行为、人工接管和业务结果。采购场景中若存在共享库存、预算等影响，需要据此选择分组边界与分析单位。上线后的实验设计可继续阅读[研发效能与实验设计](../developer-productivity-flow-efficiency-experimentation/)。

最终报告应保留适用范围：标准采购任务上的结果不自动适用于复杂跨国采购；模拟环境的证据也不能直接覆盖真实 ERP 的故障方式。没有观测到某类稀有事故，应如实报告样本量与零次观测，并继续做定向场景验证。

```python
from math import ceil, comb, sqrt
from statistics import NormalDist, mean, variance

# 每个元组代表同一任务的（旧版结果，新版结果）。
# 所有结果均为人工构造；任务对之间假设独立。
pairs = (
    [(1, 1)] * 78
    + [(1, 0)] * 4
    + [(0, 1)] * 8
    + [(0, 0)] * 10
)

n = len(pairs)
old_rate = mean(old for old, new in pairs)
new_rate = mean(new for old, new in pairs)
differences = [new - old for old, new in pairs]
delta = mean(differences)
se = sqrt(variance(differences) / n)
z = NormalDist().inv_cdf(0.975)
low, high = delta - z * se, delta + z * se

improved = sum(old == 0 and new == 1 for old, new in pairs)
regressed = sum(old == 1 and new == 0 for old, new in pairs)
discordant = improved + regressed

# 原假设下，条件于不一致任务数，改善方向服从 Binomial(m, 0.5)。
if discordant == 0:
    p_value = 1.0
else:
    tail = sum(comb(discordant, k)
               for k in range(min(improved, regressed) + 1))
    p_value = min(1.0, 2 * tail / 2**discordant)

print(f"任务数：{n}")
print(f"旧版：{old_rate:.1%}；新版：{new_rate:.1%}")
print(f"改善：{improved}；退化：{regressed}")
print(f"绝对差异：{delta * 100:.2f} 个百分点")
print(f"近似 95% 区间：[{low * 100:.2f}, {high * 100:.2f}] 个百分点")
print(f"精确 McNemar p 值：{p_value:.6f}")

# 粗略样本量规划，不用于直接确定正式验收数量。
# 对 d∈{-1, 0, 1}，Var(d)=q-delta²；小效应时用 q 近似。
# n ≈ (z_(1-alpha/2) + z_power)² * q / effect²。
# 这里要检出的是“差异大于零”，不是证明超过业务门槛。
q = 0.12
power = 0.80
for effect in (0.04, 0.02):
    planned = ceil((z + NormalDist().inv_cdf(power))**2
                   * q / effect**2)
    print(f"目标改善 {effect * 100:.0f} 个百分点：粗估 {planned} 对任务")
```

主要输出：

```text
任务数：100
旧版：82.0%；新版：86.0%
改善：8；退化：4
绝对差异：4.00 个百分点
近似 95% 区间：[−2.78, 10.78] 个百分点
精确 McNemar p 值：0.387695
目标改善 4 个百分点：粗估 589 对任务
目标改善 2 个百分点：粗估 2355 对任务
```

样本量近似源自均值差异的正态功效规划思路。[2][5] 精确检验的离散性、分层权重、任务分组和先导参数误差都可能改变最终需求，正式规划应使用对应设计的方法或模拟。
