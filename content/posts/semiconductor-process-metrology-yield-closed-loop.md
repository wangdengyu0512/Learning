# 用数据打通工艺、量测与良率：半导体制造闭环建设方法论

一家晶圆厂发现，某个产品最近三批晶圆的良率连续下降。

良率工程师首先看到的是测试结果：某一类 Bin Loss 明显增加，并且坏点在 Wafer Map 上呈现边缘聚集。量测工程师检查了 CD、膜厚和 Overlay，发现部分指标发生轻微漂移，但多数数据仍在规格范围内。工艺工程师开始比较 Recipe，设备工程师则排查 Chamber 状态、Alarm 和维护记录。

几支团队都有数据，却很难立即回答最重要的问题：

- 受影响的晶圆共同经过了哪台设备、哪个 Chamber？
- 当时使用的是哪个 Recipe 和版本？
- 哪组设备参数最早发生变化？
- Inline 量测的微小偏移是否真的导致了最终 Bin Loss？
- 异常来自本工序，还是由前序工艺、来料或设备维护状态共同造成？
- 找到原因以后，应该拦截哪些在制品，又应怎样调整后续批次？
- 调整完成后，怎样证明良率改善确实来自这次行动？

在很多工厂，这段分析依赖工程师从 MES、设备系统、SPC、FDC、量测数据库和 YMS 中分别导出数据，再用脚本或 Excel 人工拼接。即使最后找到了原因，分析过程、处置规则和验证结果也未必会沉淀下来。下一次相似问题发生时，团队仍要重新开始。

这说明企业虽然积累了大量数据，却还没有形成真正的数据闭环。

> **工艺数据描述“晶圆经历了什么”，量测数据回答“工艺做出了什么”，良率数据验证“这些结果最终创造还是损失了多少价值”。只有三类数据在同一制造上下文中被关联起来，分析结果才能进一步进入决策和控制。**

本文将从一片晶圆的完整制造链路出发，讲清楚工艺、量测与良率为什么难以打通，闭环系统应该怎样分层，FDC、SPC、虚拟量测、APC 和 Run-to-Run 分别处于什么位置，以及企业应当怎样从数据可追溯逐步走向受控自动化。

> 资料口径：本文基于截至 **2026 年 10 月 19 日**可访问的 NIST、SEMI 及半导体制造相关公开论文整理。不同晶圆厂的系统名称和职责边界可能不同，文中架构主要用于建立通用方法，不代表每家企业都需要采购或建设完全相同的系统。

## 一、真正的问题不是没有数据，而是数据没有进入同一个因果链

半导体制造天然是一个数据密集型行业。

一片晶圆会经过大量重复且相互依赖的加工步骤。光刻、刻蚀、薄膜沉积、离子注入、清洗、扩散和 CMP 等工艺不断叠加，每一步又会产生设备状态、Recipe 参数、传感器 Trace、Alarm、量测结果和缺陷记录。晶圆完成制造后，还会继续产生 WAT、CP、封装测试、FT 和可靠性数据。

从数据量看，工厂并不缺数据；真正缺少的是把这些数据组织成一条可以分析、可以干预、可以验证的链路：

```text
产品与工艺要求
  ↓
加工对象与工艺路径
  ↓
设备、腔体、配方与过程参数
  ↓
关键尺寸、膜厚、套刻、缺陷等量测结果
  ↓
电性、Bin、Wafer Map 与最终良率
  ↓
根因判断、处置与参数调整
  ↓
后续量测和良率验证
```

其中任何一个环节断开，闭环都会退化。

如果只有设备数据，工程师可以看见温度、压力和流量变化，却不知道这些变化影响了哪片晶圆、哪个产品以及多少良率。如果只有量测数据，可以判断 CD 或膜厚是否偏移，却未必能还原偏移发生时的 Chamber 状态。如果只有良率数据，可以确认损失发生了，却往往需要跨越多个工序和较长生产周期，才能回到最初的加工现场。

SEMI 在讨论半导体智能制造与数字孪生时，也把工厂数据区分为运营和良率两个相互关联的侧面，并指出现实中的数据库虽然通常能够交换信息，但连接深度仍不足以释放完整的智能制造价值。问题不只是有没有接口，而是数据是否具备共同的对象、时间和业务语义。[SEMI：Smart Manufacturing and Digital Twins for the Semiconductor Industry](https://www.semi.org/en/blogs/technology-trends/smart-manufacturing-and-digital-twins-for-the-semiconductor-industry)

因此，所谓“打通工艺、量测与良率”，并不是把三个系统的数据复制进同一个湖仓，也不是做一张同时展示几个指标的大屏。它至少包含四层含义：

1. **对象打通**：明确每条数据属于哪个 Lot、Wafer、Die、工序、设备、Chamber 和 Recipe；
2. **时间打通**：还原加工、量测、维护、异常和测试发生的先后关系；
3. **语义打通**：统一参数含义、单位、版本、规格和上下文；
4. **行动打通**：让分析结论能够触发拦截、复判、增测、维护、调参和效果验证。

前三层让数据可以被正确解释，第四层才让数据变成制造能力。

## 二、工艺、量测与良率分别回答什么问题

要建立闭环，首先要明确三类数据的职责。它们不是三张互相替代的报表，而是描述制造结果逐层形成的三个视角。

### 1. 工艺数据：晶圆是怎样被加工的

工艺数据不只包括 Recipe 中设定的目标参数，还包括加工过程中真实发生的状态。

典型数据包括：

- MES 中的产品、Lot、Wafer、Slot、工艺路线和过站履历；
- 设备、Chamber、Load Port、模块和加工位置；
- Recipe、Recipe 版本及参数设定值；
- 温度、压力、气体流量、功率、转速、时间等高频 Trace；
- Alarm、Event、设备状态和 FDC 特征；
- PM、清腔、换件、校准、耗材寿命和操作记录；
- 来料批次、光刻胶、靶材、气体和其他生产资源；
- 洁净室环境、公用工程和厂务数据。

它们共同回答：

```text
这片晶圆在什么时间，
经过哪台设备和哪个腔体，
使用什么版本的配方，
在怎样的设备状态和真实参数下完成加工？
```

需要特别区分**设定值**和**实际值**。Recipe 要求温度为某个目标值，不代表整个加工过程中实际温度始终稳定；系统下发了正确 Recipe，也不代表设备执行时没有漂移、震荡或短时异常。

### 2. 量测数据：工艺实际做出了什么

量测处在工艺过程与产品性能之间。它把不可直接判断的加工过程，转化为可以比较的物理或电性结果。

典型数据包括：

- CD、膜厚、刻蚀深度和侧壁形貌；
- Overlay、对准误差和关键图形位置；
- 均匀性、平坦度、粗糙度和应力；
- 缺陷数量、类型、尺寸、坐标和图像；
- Sheet Resistance 等 Inline 电性参数；
- 测点坐标、采样方案、量测设备和量测 Recipe；
- 实际量测值、虚拟量测值及其置信度。

NIST 在半导体量测规划中把先进量测、模型验证、制造过程建模以及设备和软件互操作标准列为重要方向，因为量测不仅用于最终验收，还贯穿研发、晶圆制造、先进封装和性能验证。[NIST：Metrology Gaps in the Semiconductor Ecosystem](https://www.nist.gov/system/files/documents/2023/06/05/CHIPS_Metrology-Gaps-in-the-Semi-Ecosystem_0.pdf)

量测数据回答的是：

```text
这次工艺输出了什么结果？
结果距离 Target 有多远？
是否仍处于规格限和控制限内？
空间分布、批次差异和时间趋势是否正常？
```

### 3. 良率数据：这些偏差最终造成了什么损失

良率数据关注的不是某个参数本身，而是产品最终是否具备预期功能，以及损失以什么模式发生。

典型数据包括：

- WAT、CP、FT 和可靠性测试结果；
- Die Bin、Soft Bin、Hard Bin 和失效代码；
- Wafer Yield、Lot Yield 和产品良率；
- Wafer Map、空间聚集和边缘、中心、环状等分布；
- Fail Bit、Fail Mode 和失效分析结果；
- 不同产品、批次、设备、工艺版本间的良率差异；
- 报废、返工、降级和质量成本。

良率数据回答的是：

```text
哪些 Die 或晶圆失效？
以什么模式失效？
损失集中在哪里？
哪些过程差异最终转化成了产品损失？
```

把三类数据放在一起，可以得到一个重要关系：

> **工艺数据更接近原因，良率数据更接近结果，量测数据则是连接原因与结果的中间证据。**

这也决定了闭环分析不能只从一个方向进行。既要从良率异常向前追溯工艺原因，也要从工艺和量测异常向后预测潜在良率风险。

## 三、为什么数据接进来了，问题仍然难以定位

许多工厂已经接入 MES、设备和测试数据，但“接入”不等于“打通”。真正困难的部分发生在数据关联和解释阶段。

### 1. 同一片晶圆在不同系统中没有统一身份

MES 可能以 Lot 和 Wafer 为主，设备系统记录 Carrier、Slot 和 Process Job，量测系统使用 Sample ID，测试系统则使用 Wafer ID、Die 坐标和测试程序版本。

如果发生拆批、并批、返工、跳站、重测或 Wafer 更换位置，简单依赖字符串相等很容易产生错误关联。系统必须保存对象在制造过程中的身份变化，而不只是保留当前编号。

### 2. 数据粒度不一致

工艺 Trace 可能每秒产生多条记录，FDC 可能把一次 Run 压缩成几十个特征，量测只覆盖部分晶圆和测点，CP 则为每个 Die 产生测试结果。

因此，分析需要在多种粒度之间转换：

```text
毫秒或秒级传感器点位
  → Step 或 Phase 特征
  → Process Run
  → Wafer
  → Lot
  → Die
  → Product
```

如果直接把不同粒度的数据做表关联，既可能重复计算，也可能把 Lot 级结论错误归因给单片晶圆。

### 3. 量测天然存在抽样和延迟

物理量测通常受设备产能、节拍和成本限制，不可能对所有晶圆、所有工序、所有测点进行完整测量。实际生产中，少量采样结果经常被用于代表整个 Lot，而量测结果可能在后续工序已经开始后才返回。

这会带来两个风险：

- 未被抽中的晶圆可能已经偏离工艺窗口，却没有被及时发现；
- 当量测确认异常时，更多使用相同设备状态或参数的晶圆已经完成加工。

相关研究正是由此引入虚拟量测：使用设备传感器和过程数据预测未被实际测量晶圆的量测结果，再用真实量测持续校准模型。[Kang 等：Virtual metrology for run-to-run control in semiconductor manufacturing](https://doi.org/10.1016/j.eswa.2010.08.040)

### 4. 数据口径和版本会变化

同名参数可能来自不同设备型号，含义和单位并不一致；同一 Recipe 名称可能已经更新；量测设备、测试程序和规格限也会发生版本变化。

如果分析数据中缺少版本上下文，就可能把“测量规则变了”误判为“工艺变了”，或把两个不可比较的数据序列放在一起训练模型。

### 5. 相关性不等于可控制的因果关系

分析可能发现某个设备参数与良率下降高度相关，但它未必是可以直接调整的根因。

例如，腔体压力稳定时间延长与 Bin Loss 同时出现，背后可能是耗材老化、清腔周期变化、来料差异或前序膜厚变化。压力只是设备状态的表征，而不是唯一原因。若系统跳过工程验证直接调参，可能短期修正一个指标，却破坏其他工艺窗口。

因此，闭环必须区分三种结论：

- **统计相关**：两个变量在历史数据中共同变化；
- **工程解释**：变化关系符合工艺机理和设备知识；
- **控制因果**：在受控条件下改变输入，可以稳定改变目标输出。

只有第三类结论，才适合进入自动控制。

### 6. 分析系统与执行系统之间没有责任闭环

一条“某 Chamber 可能异常”的算法告警，不等于问题已经解决。还需要明确：

- 谁接收并确认异常；
- 哪些 Lot 或 Wafer 需要 Hold；
- 是否追加量测或重测；
- 谁决定维护、调参或继续生产；
- 使用什么指标判断处置有效；
- 多长时间没有改善需要回退；
- 结论怎样沉淀为后续规则。

如果没有这些状态和责任，系统最多是异常观察工具，而不是闭环系统。

## 四、闭环的基础：先建立一片晶圆的统一制造上下文

高质量闭环的第一项工程，不是训练模型，而是建立统一制造对象模型。

系统至少要能还原以下关系：

```text
Product / Technology
  ↓
Lot
  ↓
Wafer / Slot
  ↓
Process Route / Step / Operation
  ↓
Process Run
  ↓
Equipment / Chamber / Module
  ↓
Recipe / Recipe Version
  ↓
Trace / Event / FDC Feature
  ↓
Metrology / Defect / WAT
  ↓
Die / Bin / Yield / Failure Mode
```

这里最重要的对象是 `Process Run`。它表示某片或某组晶圆在特定时间、设备、腔体和 Recipe 上完成的一次真实加工。设备 Trace、Alarm、FDC 特征和维护状态应当先关联到 Process Run，再通过 Process Run 关联到 Wafer 和后续质量结果。

如果缺少这一层，加工数据往往只能按时间窗口粗略匹配。设备连续运行、并行腔体、批处理设备或发生返工时，这种匹配很容易出错。

统一上下文还应包含四类信息。

### 1. 对象主数据

定义工厂、区域、设备、模块、Chamber、产品、工艺路线、工序、Recipe、参数、量测项和测试项的唯一标识及层级关系。

### 2. 时间与事件

记录加工开始和结束、Recipe 下载、Wafer 进出腔、Alarm、PM、换件、量测、Hold、Release 和测试发生时间，并处理不同时钟源的同步问题。

### 3. 版本与有效期

保留 Recipe、工艺路线、量测方法、测试程序、规格限、模型和控制策略的版本，以及每个版本的生效区间。

### 4. 数据质量与血缘

说明数据来自哪个系统、经过哪些计算、是否缺失或补录、单位是否转换、特征由哪个算法版本生成。

SEMI EDA，也称 Interface A，由一组设备数据采集标准组成，覆盖公共设备模型、设备自描述、客户端认证、数据采集管理和公共元数据等能力，目的是支持设备数据的标准化、高速采集以及设备组件上下文表达。[SEMI：SEMI Standards and Smart Manufacturing](https://www.semi.org/en/about/SEMI_Standards)

但 EDA 解决的是设备数据如何被可靠发布和理解，并不会自动补齐产品、Lot、Wafer、工艺路线和良率语义。工厂仍需要把设备模型与 MES 加工履历、量测对象和测试对象连接起来。

> **设备联网解决“数据能不能拿到”，制造上下文解决“数据究竟属于谁、发生在什么条件下、能否与结果正确关联”。**

## 五、从采集到控制：闭环系统的五层架构

围绕一片晶圆的数据链，可以把整体能力分成五层。

### 第一层：数据源与采集层

这一层负责获得真实、及时、可追溯的数据。

| 数据来源 | 关键内容 | 闭环价值 |
|---|---|---|
| MES | Lot、Wafer、Route、Operation、过站、Hold | 建立加工对象和生产履历 |
| EAP、SECS/GEM、EDA | Recipe、Event、Alarm、Trace、设备模型 | 获取设备执行事实 |
| FDC | 特征、异常分数、故障分类 | 识别设备和过程状态异常 |
| SPC | 控制图、控制限、趋势和规则违例 | 判断过程是否发生统计漂移 |
| 量测与缺陷系统 | CD、膜厚、Overlay、缺陷和坐标 | 评价工艺输出 |
| WAT、CP、FT | 电性、Die Bin、Wafer Map | 评价产品功能和最终损失 |
| RMS、EAM、PM | Recipe 版本、维护、换件和校准 | 解释工艺条件变化 |

采集层的目标不是“数据越多越好”，而是关键链路不缺失、对象关系不错误、时间能够对齐。

### 第二层：制造上下文与数据治理层

这一层把来自不同系统的记录组织成可以分析的制造事实：

- 对象主键和跨系统映射；
- Process Run 与 Wafer 的关联；
- 参数名称、单位和设备模型标准化；
- Recipe、规格和测试程序版本管理；
- Wafer、Die 和量测点坐标转换；
- 数据完整性、及时性、准确性检查；
- 原始数据、加工特征和分析结果的数据血缘。

这一层看起来不像算法那样直观，却决定了后续结论能否被工程师信任。

### 第三层：特征与模型层

原始 Trace 很少能够直接进入良率分析。系统通常需要按工艺阶段提取特征，例如：

- 平均值、最大值、最小值、标准差和斜率；
- 达到稳定状态所需时间；
- 超限面积、波动次数和阶段间差值；
- 腔体累计加工片数、距上次清腔时间；
- 相邻晶圆、相邻 Lot 和同类设备的差异；
- Wafer Map 的中心、边缘、环状和局部聚集特征。

特征必须带上生成逻辑和版本。否则同名“平均压力”可能分别代表完整 Run、某个 Step 或去除异常点后的均值，分析结果无法复现。

### 第四层：分析与决策层

这一层按照问题复杂度逐步形成能力：

1. **描述发生了什么**：趋势、分布、Pareto 和 Wafer Map；
2. **诊断为什么发生**：设备、Chamber、Recipe、材料和时间窗口对比；
3. **预测将会发生什么**：虚拟量测、良率预测和设备健康预测；
4. **建议应该做什么**：动态抽样、Lot Hold、维护和参数补偿建议；
5. **判断行动风险**：模型置信度、适用范围和回退条件。

这里要避免把所有问题都交给一个黑盒模型。控制图、分层对比、方差分析、回归、树模型、时序模型和机理模型各有适用范围。能用清晰规则解决的问题，不必为了“智能化”强行使用复杂模型。

### 第五层：控制与执行层

分析结果最终要回到生产现场。常见动作包括：

- 告警并创建工程处置任务；
- Hold Lot、Wafer 或设备；
- 增加抽样、改变测点或触发重测；
- 调整派工，暂时避开高风险 Chamber；
- 触发 PM、清腔、校准或部件检查；
- 推荐 Recipe 或参数补偿；
- 通过 APC、Run-to-Run 自动更新后续 Run 的输入；
- 将结果写回 MES、YMS、FDC 或知识库。

闭环并不意味着所有动作都自动执行。告警、建议、审批执行和全自动控制，是不同风险等级。企业应根据工艺成熟度、模型可信度和潜在损失选择自动化边界。

## 六、SPC、FDC、YMS、虚拟量测和 APC 怎样协同

这些系统经常被并列介绍，但它们实际上处在不同的观察和控制位置。

### 1. SPC：过程是否发生了统计偏移

SPC 使用控制图和判异规则监测过程稳定性。它关注的不是一个值是否超过产品规格限，而是过程分布是否已经发生不应有的变化。

一个参数即使仍在规格限内，也可能已经连续向某个方向漂移；反过来，偶发的规格超限也不一定代表整个过程失控。SPC 为工程师提供的是统计过程状态。

### 2. FDC：设备或加工过程是否异常

FDC 更靠近设备和单次 Process Run。它从高频 Trace 中提取特征，检测传感器模式、阶段持续时间和设备行为是否偏离正常状态，并进一步进行故障分类。

FDC 可以较早发现问题，但单独使用时不一定知道异常是否影响产品。只有把 FDC 特征与量测和良率关联，才能区分“设备行为变化但对产品无影响”和“看似轻微却显著影响质量”的异常。

### 3. YMS：损失集中在哪里

YMS 从产品结果出发，通过 Bin Pareto、Wafer Map、设备对比、批次对比和历史趋势，帮助工程师识别损失模式及其潜在来源。

它擅长回答“哪些产品、批次、Wafer、区域或失效类型最值得优先处理”，但要定位到具体工艺条件，仍然需要制造上下文和设备数据。

### 4. 虚拟量测：为未被实测的晶圆补充质量估计

虚拟量测使用设备状态、过程参数和历史真实量测，预测当前晶圆的 CD、膜厚、Overlay 或其他质量指标。

它主要解决两个矛盾：

- 工艺控制希望尽快获得每片晶圆的反馈；
- 真实量测受成本和节拍限制，只能进行抽样且存在延迟。

虚拟量测不是取消真实量测。真实量测仍然用于提供基准、校准模型、监控漂移和确认高风险结果。2024 年发表的一项综述也指出，虚拟量测已经形成大量研究和应用探索，但数据质量、模型泛化、训练维护以及产业接受度仍是规模化实施的重要挑战。[Maitra 等：Virtual metrology in semiconductor manufacturing: Current status and future prospects](https://doi.org/10.1016/j.eswa.2024.123559)

### 5. APC 与 Run-to-Run：把反馈转化为后续参数调整

Run-to-Run 控制并不在单次工艺内部进行毫秒级动作，而是在一次加工完成后，根据量测或预测结果调整下一次 Run 的输入参数。

典型过程是：

```text
设定本次 Recipe 参数
  ↓
执行 Process Run
  ↓
获得真实量测或虚拟量测
  ↓
与 Target 比较并估计偏差
  ↓
控制器计算补偿量
  ↓
在上下限和工程规则内更新后续参数
```

已有研究将虚拟量测预测与 EWMA 等 Run-to-Run 控制方法结合，用于在真实量测只覆盖部分晶圆时提供更连续的反馈；也有研究把实时设备状态和 FDC 信息纳入控制器，以避免只根据量测结果调参而忽略设备条件。[IEEE：Advanced run-to-run controller with real-time equipment condition](https://doi.org/10.1109/ASMC.2018.8373161)

五类能力放在一起，可以形成完整分工：

```text
FDC：设备和单次加工是否异常
SPC：过程分布是否稳定
YMS：最终损失在哪里
虚拟量测：当前晶圆可能做成什么样
APC / R2R：下一次应该怎样调整
```

它们不是互相替代，而是共同连接“感知—判断—决策—执行—验证”。

## 七、制造闭环不是一种速度，而是三种速度

半导体制造中的问题反馈周期不同，不适合全部放进同一个控制回路。更合理的方式是建立三种速度的闭环。

### 1. 秒级到分钟级：设备异常闭环

链路如下：

```text
传感器与设备事件
  → FDC 或规则识别异常
  → Alarm / Interlock / Lot Hold
  → 工程确认和设备处置
```

典型场景包括：

- 压力、温度、流量或功率明显异常；
- Recipe 下载或执行错误；
- Chamber 突发漂移；
- 关键阶段持续时间异常；
- 设备部件失效或状态不满足加工条件。

这一闭环的目标是**尽快阻断风险扩散**。它更依赖设备数据和明确规则，对最终良率信息的依赖较低。

### 2. 小时级到批次级：量测控制闭环

链路如下：

```text
Process Run
  → 实际量测 / 虚拟量测
  → 与 Target 和控制限比较
  → APC / R2R 计算补偿
  → 调整后续 Run
  → 下一次量测确认
```

典型场景包括：

- 光刻 Overlay 补偿；
- CD 控制；
- 薄膜厚度控制；
- CMP 去除量控制；
- 刻蚀深度控制。

这一闭环的目标是**把过程输出保持在工艺窗口中心附近**，减少漂移积累后才被发现的风险。

### 3. 天级到周级：良率改善闭环

链路如下：

```text
良率或 Bin 异常
  → Wafer Map 和分层分析
  → 工艺履历与设备状态回溯
  → 根因候选与工程验证
  → 工艺、设备或抽样策略变更
  → 后续量测和良率验证
  → 规则与知识沉淀
```

它处理的是跨工序、跨系统、跨团队的问题，通常需要结合失效分析、DOE、机理判断和更长时间窗口的数据。

这一闭环的目标是**证明哪些过程变化真正导致了产品损失，并把一次性改善转化为可重复的控制机制**。

三种闭环并不是彼此隔离的。良率闭环发现的根因，可以转化为新的 FDC 规则、SPC 指标、动态抽样策略或 APC 控制变量；快速闭环积累的数据，又会持续提高长期良率分析的准确性。

## 八、案例：从边缘 Bin Loss 追溯到刻蚀 Chamber

下面用一个简化案例说明三类数据怎样共同工作。

### 第一步：良率数据定义问题

YMS 发现某产品最近多个 Lot 的特定 Bin Loss 上升。Wafer Map 显示异常主要集中在晶圆边缘，但并非所有晶圆都出现相同程度的损失。

团队首先按产品版本、测试程序、日期和 Lot 分层，排除了测试规则变化，并将异常范围缩小到一组连续生产的晶圆。

### 第二步：制造上下文缩小范围

系统沿晶圆加工履历回溯，并对同产品正常晶圆进行对照。结果显示，异常晶圆共同经过同一台刻蚀设备的某个 Chamber，而经过其他 Chamber 的晶圆良率相对稳定。

此时只能说明该 Chamber 是高优先级嫌疑对象，还不能直接认定为根因。

### 第三步：量测数据建立中间证据

进一步检查刻蚀后的 CD 和深度量测，发现异常晶圆的边缘区域存在方向一致的小幅偏移。单个测点大多没有超过规格限，但分布中心已经发生移动，并与 Wafer Map 的边缘失效方向相符。

量测数据把“某 Chamber”和“最终 Bin Loss”之间补上了中间证据：

```text
Chamber 差异
  → 边缘 CD / 深度偏移
  → 边缘 Die 失效增加
```

### 第四步：工艺与设备数据定位根因

团队把相关 Process Run 的 Trace 按工艺阶段对齐，发现该 Chamber 的压力稳定时间逐渐延长，边缘相关的均匀性特征也在缓慢漂移。维护记录显示，某类腔体耗材接近内部经验寿命，但尚未达到固定 PM 周期。

进一步比较清腔后和清腔前数据，漂移与耗材使用次数具有一致趋势。工程师据此提出根因假设：耗材状态变化导致腔体分布逐步偏移，最终通过刻蚀均匀性影响边缘 Die。

### 第五步：执行受控处置

工厂采取了四项动作：

1. Hold 尚未进入后续关键工序的高风险 Lot；
2. 对相关晶圆增加边缘测点；
3. 对目标 Chamber 执行维护和校准；
4. 在工程审批下，对短期过渡批次使用受限的参数补偿。

### 第六步：用量测和良率共同验证

维护后的首批晶圆先通过实际量测确认 CD 和深度分布恢复，再观察后续 CP 的 Bin Loss。只有两个层级都恢复，问题才进入关闭状态。

最终，工厂把这次经验转化为长期机制：

- 在 FDC 中增加压力稳定时间和均匀性趋势规则；
- 根据耗材使用状态动态调整抽样；
- 当置信度足够高时，提前触发维护建议；
- 在 YMS 中持续监控对应 Bin 和 Wafer Map 模式；
- 保存根因、措施、验证证据和适用设备范围。

这个案例揭示了闭环的真实顺序：

> **良率指出损失，量测建立过程结果证据，工艺和设备数据定位原因，控制系统执行动作，后续量测与良率共同证明改善有效。**

## 九、从数据可见到自动控制：四阶段建设路线

企业不应从“全厂自动调参”开始。更稳妥的路径是逐步提高数据可信度、决策确定性和自动化等级。

### 阶段一：数据可追溯

首先回答最基础的问题：

- 每片晶圆经历了哪些工序、设备和 Chamber？
- 每次加工使用哪个 Recipe 和版本？
- 当时的设备状态、关键 Trace 和维护背景是什么？
- 对应哪些量测、缺陷、电性和测试结果？

核心交付物包括统一对象模型、数据字典、跨系统主键映射、Process Run 履历和数据质量规则。

这一阶段的验收标准，不是接入多少张表，而是随机选择一片晶圆，系统能否完整、准确、可复现地还原其制造谱系。

### 阶段二：异常可定位

选择明确问题，例如某个高损失 Bin、某项关键 CD 或某类设备异常，建立：

- 产品、Lot、Wafer、设备和 Chamber 分层对比；
- Wafer Map 与量测空间分布关联；
- Trace 特征与质量结果关联；
- 根因候选排序和对照组分析；
- 从异常发现到工程关闭的处置流程。

这一阶段仍以工程师判断为主，系统负责缩小范围、组织证据和减少手工拼数。

### 阶段三：决策可推荐

当历史数据和处置流程逐渐稳定后，系统可以给出建议：

- 哪些 Lot 应当 Hold；
- 哪些晶圆需要增加量测；
- 是否应避开某个 Chamber；
- 哪类维护或校准动作最匹配；
- 后续 Run 可以使用什么参数补偿范围。

建议必须包含原因、证据、置信度、适用范围和预期影响，不能只输出一个分数。工程师审批结果也应回流系统，用于评估规则和模型质量。

### 阶段四：控制可自动执行

只有满足以下条件的场景，才适合逐步进入自动控制：

- 工艺目标和可控变量明确；
- 输入与输出关系经过工程验证；
- 数据及时性和准确性能够保障；
- 模型在适用设备、产品和 Recipe 范围内稳定；
- 有参数上下限、联锁和异常降级策略；
- 有真实量测持续校准；
- 有人工 Override、审计和快速回退能力。

自动化也可以分级：

```text
L0 仅展示数据
L1 自动告警
L2 给出处置建议
L3 人工审批后执行
L4 在受控边界内自动执行
L5 多工序协同优化
```

大多数工厂更现实的目标，是先在少数高价值、机理较清楚的工艺上达到 L3 或 L4，而不是追求全厂统一的“无人化等级”。

## 十、闭环项目应该怎样选择第一个场景

第一个场景决定团队能否建立信心。适合起步的问题通常具备五个特征：

1. **业务价值明确**：对应显著良率损失、报废、返工或量测瓶颈；
2. **对象范围可控**：集中在一个产品族、一道工序或一组同类设备；
3. **反馈周期适中**：可以在较短周期内获得量测或测试结果；
4. **数据基础较好**：Wafer 履历、设备 Trace 和质量结果可以可靠关联；
5. **动作可执行**：找到原因后，确实可以通过维护、抽样、派工或调参改变结果。

例如，“全厂良率智能分析”不是一个合适的首期场景；“某产品刻蚀后 CD 边缘偏移导致特定 Bin Loss，并集中在三台同型号设备”则更适合。

一个高质量场景应被写成可验证的问题：

```text
对象：哪些产品、工序、设备和时间范围？
现象：哪个量测或良率指标发生什么变化？
损失：造成多少报废、返工、周期或产能影响？
假设：哪些因素可能导致该现象？
动作：发现风险后能够做什么？
验证：用什么指标、经过多少批次确认有效？
```

这样，项目目标就从“建设平台”变成“关闭一个有价值的制造问题，并沉淀可复制能力”。

## 十一、怎样衡量闭环是否真正有效

只看最终良率并不够。良率会受到产品组合、设计版本、来料和多道工序影响，短期波动也可能掩盖系统价值。闭环应从四个维度衡量。

### 1. 分析效率

- 异常发现时间 MTTD；
- 从发现到定位的平均时间；
- 从定位到恢复的平均时间 MTTR；
- 每次分析需要导出的数据和人工工时；
- 根因调查中可自动获得的上下文比例。

### 2. 过程稳定性

- SPC 规则违例率；
- FDC 告警的准确率、漏报率和提前量；
- 关键量测指标的均值、方差和 Cpk；
- Chamber Matching 水平；
- 工艺漂移被发现前影响的晶圆数量。

### 3. 质量与经营结果

- Inline 量测合格率；
- 缺陷密度和关键缺陷类型；
- 目标 Bin Loss；
- Wafer、Lot 和最终测试良率；
- 报废、返工、降级和量测成本；
- Cycle Time 和设备利用率。

### 4. 闭环运行质量

- 告警确认率和建议采纳率；
- 从异常到关闭的完整闭环率；
- 处置后一次验证成功率；
- 自动控制覆盖的设备、产品和 Run 比例；
- 模型漂移、降级和人工 Override 次数；
- 错误 Hold、错误调参和回退次数；
- 根因与处置知识的复用率。

一个闭环系统即使暂时没有显著提高总体良率，只要能够把根因定位从数天缩短到数小时、减少受影响晶圆数量，也可能已经创造了明确价值。

## 十二、落地时最容易出现的七个误区

### 1. 先建大平台，再寻找业务问题

数据平台可以提供基础能力，但不能替代场景定义。没有明确指标、责任人和可执行动作，平台最终容易停留在数据查询层。

### 2. 把接口连通当成数据打通

系统能够传输文件，不代表 Lot、Wafer、Chamber、Recipe 和量测点已经准确关联。闭环最常见的错误不是算法不够先进，而是上下文错误。

### 3. 只保留汇总特征，不保留原始证据

FDC 特征适合快速分析，但当规则、窗口或算法需要调整时，仍要回到原始 Trace 验证。关键过程应同时保留原始数据、特征和生成血缘。

### 4. 把控制限、规格限和目标值混为一谈

规格限用于判断产品是否满足要求，控制限用于判断过程是否稳定，Target 则是控制器希望过程靠近的位置。三者用途不同，不能互相替代。

### 5. 只看模型准确率，不看错误动作成本

一个预测模型即使平均误差很小，也可能在设备维护后、新产品导入或异常状态下失效。进入控制回路时，需要同时评估置信度、适用范围、最坏情况和回退能力。

### 6. 一开始就追求自动调参

从相关分析直接跳到自动控制，会把数据错误、模型错误和工艺认知不足放大到生产现场。合理路径应经过离线验证、影子运行、建议模式、人工审批和受限自动执行。

### 7. 只有算法闭环，没有组织闭环

工艺、设备、量测、良率、IT 和自动化团队需要共同定义对象、规则、责任和关闭标准。否则系统即使找到问题，也可能因为没人接收、无法停机或缺少变更审批而无法行动。

---

## 十三、未来方向：从单点控制走向跨工序协同

当前大量闭环仍围绕单台设备、单道工序或单个量测指标建立。但最终良率是多道工序共同作用的结果，局部最优不一定等于全局最优。

未来闭环会沿几个方向演进。

### 1. 从单工序反馈走向前馈与反馈结合

前序量测结果可以提前影响后序 Recipe。例如前序膜厚发生可接受偏差时，后序刻蚀可以进行补偿，而不是等后序结果异常后再调整。

### 2. 从固定抽样走向动态抽样

系统根据设备健康、虚拟量测置信度、产品风险和历史稳定性动态决定哪些晶圆、哪些测点需要真实量测，把有限量测能力优先分配给高风险对象。

### 3. 从预测值走向带不确定性的决策

控制系统不只使用一个预测结果，还要知道结果有多可信。当置信度下降时，系统应自动增加真实量测、降低自动化等级或转入人工审批。

### 4. 从独立模型走向制造知识网络

设备、Chamber、Recipe、参数、量测项、缺陷模式、Bin 和维护动作之间的关系，可以逐步沉淀为可查询、可复用的制造知识。模型发现新模式，工程验证形成证据，验证结果再更新规则和知识。

### 5. 从单点闭环走向工厂级数字孪生

当设备状态、加工履历、量测、良率和调度数据能够在统一上下文中持续更新，数字孪生才不只是三维可视化，而是能够对生产状态进行推演、预测和优化的运行模型。SEMI 近年的半导体数字孪生工作也将数据互操作、模型可信度和部署挑战视为走向 AI 驱动自主工厂的重要议题。[SEMI：Digital Twins in Semiconductor Manufacturing](https://www.semi.org/en/digital-twins-in-semiconductor-manufacturing)

不过，无论技术怎样演进，闭环仍必须遵守一个基本原则：自动化等级不能高于数据、模型和工程认知的可信等级。

---

## 结语：数据只有进入控制回路，才会变成制造能力

打通工艺、量测与良率，表面上是一个数据集成问题，本质上却是重新组织制造认知和控制方式。

工厂需要完成三个转变：

- 从按系统查看数据，转向按 Wafer 和 Process Run 还原制造过程；
- 从事后解释良率，转向利用工艺与量测数据提前识别风险；
- 从依赖个人经验处置，转向以证据、规则、审批和验证构成可复用闭环。

真正的数据闭环，不是把工艺参数、量测结果和良率指标放在同一张大屏上，而是做到：

```text
每一次良率损失，都能回到具体制造过程；
每一次异常判断，都有工艺和量测证据支持；
每一次参数调整，都在明确边界内执行；
每一次改善，都由后续量测和良率共同验证；
每一次验证过的经验，都能沉淀为下一次更快的判断和行动。
```

当这条链路持续运行，数据才不再只是生产留下的记录，而会逐步成为工厂感知状态、解释问题、调整过程和积累知识的核心能力。
