# 前端 UI 设计不是玄学：一套工程师可推导的系统

很多前端工程师都经历过这样的时刻：功能已经正确，交互也能跑通，但页面就是“差一口气”。你知道它不够专业，却很难准确说出问题出在哪里，于是只能继续调圆角、换颜色、加阴影、挪几个像素。

这种做法的问题不在于不努力，而在于缺少一套判断系统。

UI 设计并不是只能依赖审美天赋。对产品界面来说，大量“专业感”都可以从几条稳定的原则推导出来：**先建立视觉层级，再用有限的色阶、字阶和间距阶表达层级，最后把这些决定沉淀成可复用的工程系统。**

换句话说：

> 专业的界面，不是装饰更多，而是让每一个视觉决定都有理由。

本文尝试把这套方法压缩成一条工程师可以直接使用的路径。

---

## 一、先别急着美化：UI 的第一任务是引导视线

用户打开页面时，不会先欣赏配色和圆角，而是在寻找答案：

- 这里最重要的是什么？
- 我应该先看哪里？
- 哪些内容属于一组？
- 下一步应该点击什么？

因此，UI 设计的核心不是“好看”，而是**视觉层级清晰**。

视觉层级可以理解为元素被用户注意到的先后顺序。一个专业界面会让主标题、核心数据或主操作先出现，辅助信息随后进入视线，元数据和低优先级内容最后才被注意到。

元素的视觉权重通常来自几个维度的共同作用：

- 尺寸：越大，越容易先被看到；
- 明度对比：与背景差异越大，权重越高；
- 色彩与饱和度：彩色通常比中性色更抢眼；
- 字重：粗体比常规字重更突出；
- 位置与留白：周围越空，元素越容易成为焦点。

这里有一个很重要的反直觉结论：**突出重点，不一定要继续加强重点，也可以主动降低其他元素的权重。**

例如一张用户卡片中，与其把姓名、邮箱、职位、更新时间全部加粗，不如只让姓名使用更大的字号和更高字重，把邮箱降为普通正文，把更新时间压到浅灰小字。信息没有增加，但阅读顺序已经出现。

### 五个可以直接操作的设计杠杆

当页面“看着乱”时，可以依次检查下面五项：

1. **对比（Contrast）**：最重要的内容是否真的最显眼？
2. **接近（Proximity）**：相关内容是否靠得更近，不相关内容是否拉开？
3. **对齐（Alignment）**：页面是否建立了少量、稳定的对齐轴？
4. **重复（Repetition）**：同类元素是否使用一致的颜色、圆角、字号和状态？
5. **留白（Whitespace）**：内容是否有足够空间表达主次和分组？

这五项并不是五种装饰技巧，而是五种信息组织方式：

- 对比回答“谁最重要”；
- 接近回答“谁和谁是一组”；
- 对齐建立秩序；
- 重复建立一致性；
- 留白为前四者提供发挥空间。

以后再遇到“说不清哪里不对”的页面，不妨把模糊的不适改写成一张 bug 列表：重点没跳出来、分组有歧义、对齐轴太多、组件不一致，或者页面过于拥挤。

## 二、色彩不是挑几个好看的颜色，而是建立一套层级

很多人从品牌色开始设计页面，但专业 UI 的大部分面积实际上并不是彩色，而是背景、表面、边框和文字所使用的中性灰。

一套实用的调色板，通常应该按照下面的顺序建立：

1. 先做中性灰阶；
2. 再做成功、警告、错误等语义色；
3. 最后加入品牌强调色；
4. 检查所有文字、图标和背景的对比度；
5. 为暗色模式重新绑定语义颜色。

### 为什么应该优先使用 OKLCH

Hex 适合机器存储颜色，却不适合人类推导颜色；HSL 虽然更直观，但它的 `L` 并不真正对应人眼感知到的亮度。同样的 HSL 明度下，黄色可能显得很亮，蓝色却显得很沉。

OKLCH 更适合构建设计系统，因为它把颜色拆成三个相对独立的维度：

- `L`：感知明度；
- `C`：彩度；
- `H`：色相。

需要同一个颜色的 hover 和 active 状态时，可以主要调整 `L`；需要一组视觉重量接近的成功、警告和错误色时，可以保持接近的 `L` 与 `C`，主要改变 `H`。

```css
:root {
  --brand:        oklch(0.62 0.19 255);
  --brand-hover:  oklch(0.68 0.19 255);
  --brand-active: oklch(0.54 0.19 255);

  --success: oklch(0.62 0.16 150);
  --warning: oklch(0.62 0.16 80);
  --danger:  oklch(0.62 0.16 25);
}
```

### 灰阶才是界面的骨架

一条好用的灰阶至少要覆盖这些用途：

- 页面背景；
- 次级表面和卡片背景；
- 分隔线与边框；
- 占位符和禁用状态；
- 次要文字；
- 正文；
- 标题和近黑文字。

灰阶也不一定必须完全无色。给所有灰色加入极低彩度和统一色相，可以形成偏冷或偏暖的整体气质，同时与品牌色更自然地协调。

```css
:root {
  --gray-0: oklch(0.99 0.01 255);
  --gray-1: oklch(0.97 0.01 255);
  --gray-2: oklch(0.93 0.01 255);
  --gray-4: oklch(0.71 0.01 255);
  --gray-5: oklch(0.58 0.01 255);
  --gray-6: oklch(0.44 0.01 255);
  --gray-7: oklch(0.28 0.01 255);
  --gray-8: oklch(0.18 0.01 255);
}
```

强调色之所以有力量，是因为它稀缺。一个实用的经验是让大部分界面保持中性，只在主操作、关键状态和品牌识别处使用强调色。如果按钮、图标、标题、背景和标签全部使用品牌色，页面就会再次失去层级。

### 可读性是一条硬边界

“高级感”最常见的误区，是把次要文字不断调浅。视觉上看起来更轻，却可能让内容在强光、低质量屏幕或弱视用户眼中直接消失。

工程落地时可以先守住两条基线：

- 普通正文与背景的对比度至少为 `4.5:1`；
- 大字、图标和关键 UI 边界至少为 `3:1`。

次要信息可以通过更小字号、较低字重和更弱的位置来表达，而不必把所有层级压力都压在“更浅的灰”上。

### 暗色模式不是反色

暗色主题至少需要重新考虑三件事：

- 不要用纯黑背景配纯白正文，近黑和近白通常更耐看；
- 暗色界面的层级更多依靠“表面亮度”，而不是阴影；
- 品牌色和语义色通常要适当提高明度、降低彩度，避免在暗背景上刺眼。

最稳妥的做法不是在组件里分别判断主题，而是让组件只引用语义 token，在主题切换时统一重绑这些语义变量。

## 三、排版不是调字号：字阶、行长和行高必须一起决定

排版最容易出现三种问题：字号随手填、正文撑满全屏、所有文字共用同一个行高。

解决它们，需要同时处理字阶、行长和行高。

### 用模块化字阶代替随手填值

字号应该来自一条有限的几何数列，而不是在 14、15、16、17、18px 之间反复微调。

以正文 `16px`、比例 `1.25` 为例，可以得到近似的字阶：

```css
:root {
  --text-xs:   0.8rem;
  --text-sm:   0.875rem;
  --text-base: 1rem;
  --text-lg:   1.25rem;
  --text-xl:   1.5625rem;
  --text-2xl:  1.953rem;
}
```

几何字阶的价值在于，相邻两档始终保持近似一致的比例差，因此每一级“变大”的感觉更均匀。密集后台可以选择较温和的比例，营销页则可以使用更大的比例拉开标题与正文。

### 限制正文行长

宽屏上让正文 `width: 100%` 是成本极高的默认值。阅读时，眼睛会在一行内多次扫视，并在行尾跳回下一行开头。行太长，回扫距离过大，容易跳错行；行太短，回扫又过于频繁。

通常可以把英文正文控制在约 45～75 个字符，中文长文控制在约 30～40 个汉字。实际 CSS 中，可以用 `ch`、`em` 或固定的 `max-width` 限制内容宽度。

```css
.article-body {
  max-width: 38em;
  margin-inline: auto;
}
```

很多阅读体验问题，只加这一条就能明显改善。

### 行高是关系，不是常数

正文常用 `1.5～1.7` 的行高，而大标题通常只需要 `1.1～1.3`。原因是：

- 行越长，行高应该适当增大，帮助眼睛找到下一行；
- 字号越大，行高比例反而应该减小，否则标题会显得松散。

因此，正确顺序是：**先确定字阶，再限制行长，最后根据字号和行长决定行高。**

层级也不需要通过堆叠多种字体来实现。大多数界面使用一个字体家族，再通过字号、字重和明度建立三层文字关系，就已经足够。典型组合是正文 `400`、小标题 `600`、主标题 `700`，再配合标题、正文和次要文字三档灰度。

## 四、间距要从尺度里选，布局要从模型里选

如果一个页面出现了 `7px`、`13px`、`19px`、`22px` 等大量相近值，通常意味着它没有空间系统。

### 建立一条间距阶

一条常见的间距阶可以是：

```text
4 / 8 / 12 / 16 / 24 / 32 / 48 / 64
```

它覆盖了三个层次：

- 组内关系：4、8；
- 组件内边距：12、16、24；
- 区块之间：32、48、64。

这样做的价值不仅是整齐，更重要的是让间距能够表达语义：**相关内容使用小间距，不相关内容使用大间距。** 表单中 label 与输入框之间可以是 4px，而两个字段组之间可以是 20px 或 24px。即使没有边框，用户也能自然判断归属。

### Flexbox 与 Grid 的选择口诀

不要先问“哪个属性能把它推到右边”，先问布局是一维还是二维：

- 一行或一列、尺寸主要由内容决定：用 Flexbox；
- 行和列都需要对齐、先有网格再放内容：用 Grid。

Flexbox 的本质，是先根据 `flex-basis` 得到初始尺寸，再计算剩余空间，最后通过 `grow` 或 `shrink` 分配它。`flex: 1 1 0` 会把 basis 归零后按比例分配，因此适合真正等宽；默认的 `0 1 auto` 则保留内容自然尺寸，不主动扩张。

Grid 更适合卡片墙、页面骨架和表格式结构。例如下面这一行，就能得到按容器宽度自动增减列数的卡片网格：

```css
.card-grid {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(240px, 1fr));
  gap: 16px;
}
```

布局中还应优先使用容器的 `gap`，而不是给每个子元素写 margin。`gap` 只出现在元素之间，不会留下最后一个元素的多余尾巴，也不需要 `:last-child` 补丁。

### 现代响应式：先流式，再断点

传统响应式习惯在多个视口宽度下不断添加 media query，但很多尺寸其实更适合连续变化。

```css
.page-title {
  font-size: clamp(1.5rem, 1rem + 2.5vw, 2.5rem);
}
```

`clamp()` 可以让字号或间距在上下限之间流式变化。对于可复用组件，则可以使用容器查询，让组件根据自己实际所在的空间改变布局，而不是只能读取整个视口的宽度。

```css
.card-wrap {
  container-type: inline-size;
}

.card {
  display: grid;
  gap: 12px;
}

@container (min-width: 400px) {
  .card {
    grid-template-columns: 120px 1fr;
  }
}
```

这样，同一个组件放在窄侧栏时可以纵向排列，放在宽主区时自动变成横向排列。

## 五、把设计决定变成代码：三层 Design Tokens

如果颜色、圆角和间距仍然散落在几十个组件里，前面的设计规则就只是建议，而不是系统。

更稳健的方式，是把设计值组织成三层：

1. **Primitive Token**：原始值，只描述“它是什么”；
2. **Semantic Token**：语义值，描述“它用来做什么”；
3. **Component Token**：组件局部变量，描述“这个组件如何使用它”。

```css
:root {
  /* Primitive */
  --blue-500: oklch(0.62 0.19 255);
  --gray-700: oklch(0.28 0.01 255);
  --space-4: 16px;
  --radius-md: 10px;

  /* Semantic */
  --color-primary: var(--blue-500);
  --color-text: var(--gray-700);
  --surface-page: var(--gray-0);
  --space-card: var(--space-4);
}

.button {
  /* Component */
  --button-bg: var(--color-primary);

  background: var(--button-bg);
  color: white;
  padding: 8px var(--space-card);
  border-radius: var(--radius-md);
}
```

三层间接并不是为了复杂，而是为了隔离变化：

- 更换品牌色时，调整 primitive；
- 切换暗色主题时，重绑 semantic；
- 某个组件需要例外时，再使用 component token；
- 组件本身始终不直接依赖具体颜色值。

无论使用 Tailwind、CSS Modules、CSS-in-JS 还是传统语义类，真正重要的都是让代码只能从有限尺度中选值。工具的意义，是把一致性从“靠自觉”变成“默认如此”。

## 六、动效是否流畅，取决于你修改了哪个渲染阶段

浏览器把 CSS 变成屏幕像素，大致会经过：

```text
Style → Layout → Paint → Composite
```

不同属性会从不同阶段重新开始计算：

- `width`、`height`、`left`、`margin` 会触发布局计算；
- `background`、`box-shadow` 等通常需要重新绘制；
- `transform` 和 `opacity` 通常只需要合成。

因此可以得到一条非常实用的动效原则：

- 位移使用 `transform: translate()`；
- 缩放使用 `transform: scale()`；
- 渐隐渐现使用 `opacity`；
- 尽量不要逐帧修改 `left`、`width` 或 `margin`。

```css
.drawer {
  transform: translateX(-100%);
  transition: transform 200ms ease-out;
}

.drawer[data-open="true"] {
  transform: translateX(0);
}

@media (prefers-reduced-motion: reduce) {
  .drawer {
    transition: none;
  }
}
```

多数 UI 微交互使用 150～300ms 就足够。元素进入通常使用 `ease-out`，因为它开头响应快、结尾缓慢收住；退出可以使用 `ease-in`。动画不是越多越精致，统一、克制且不阻塞操作才是目标。

## 七、一个组件的工作量，主要藏在状态里

“做一个按钮”不只是画出默认状态。一个可以上线的按钮至少要考虑：

- default；
- hover；
- focus-visible；
- active；
- disabled；
- loading；
- 成功或错误反馈。

同时还要把组件设计成三个维度的组合：

- `variant`：primary、secondary、ghost；
- `size`：sm、md、lg；
- `state`：交互与业务状态。

这里，视觉原则会真正变成组件 API：主按钮使用实心强调色，次按钮使用描边或弱背景，文本按钮进一步降低权重；不同尺寸只能从字阶和间距阶中取值；hover 与 active 状态从同一颜色推导；键盘焦点通过 `:focus-visible` 清晰呈现。

组件库的体量，往往不是“有多少个组件”，而是“组件数 × 变体数 × 状态数”。只设计默认态的组件，通常只能用于截图，不能用于真实产品。

## 八、设计系统解决一致性，现代感往往来自克制

当项目从一个页面增长到几十个页面，仅靠团队成员“记得保持一致”是不可靠的。完整的设计系统通常包含四层：

1. Tokens：颜色、字号、间距、圆角、阴影；
2. Components：按钮、输入框、弹窗、菜单等；
3. Patterns：表单、空状态、筛选器、数据列表等常见组合；
4. Documentation：什么时候用、为什么用、禁止怎样用。

设计系统的价值，不只是“组件看起来一样”，而是让大量视觉决定不再被重复讨论，使不一致更难发生。

但一致并不自动等于现代。界面仍然可能非常统一地显得陈旧，或者统一地像一个通用模板。

### 警惕“AI 通用脸”

常见的模板化界面往往同时出现这些特征：

- 全页面居中；
- 紫色或蓝紫渐变 Hero；
- Inter 加超大粗体标题；
- emoji 作为功能图标；
- 到处是药丸按钮；
- 所有卡片都使用大圆角和厚重阴影；
- 文案只说“智能、高效、强大”，却没有具体承诺。

这些选择单独看都不一定错，但全部叠加后，就会失去产品自己的判断。

让界面显得“有人决定过”，不需要加入更多装饰，反而可以从减法开始：

- 把厚重阴影改为 `1px` 边框加极淡阴影；
- 收敛到一套圆角、一套阴影语言；
- 选择一个有产品倾向的强调色，而不是默认蓝紫；
- 用左对齐和稳定轴线代替全居中；
- 用具体文案替代空泛口号；
- 提高真实信息密度，而不是用巨大留白掩盖内容不足；
- 为所有微交互使用统一的时长和缓动。

现代感经常不是“又加了什么”，而是“删掉了多少没有必要的默认值”。

## 九、一套可以直接使用的 UI 诊断流程

面对一个“功能没问题，但看起来不专业”的界面，可以按下面的顺序检查。

### 1. 层级

- 第一眼是否落在正确的元素上？
- 页面是否只有一个真正的主操作？
- 次要信息有没有主动降权？

### 2. 分组与对齐

- 相关元素是否靠近？
- 组内间距是否小于组间间距？
- 页面是否存在太多无意义的对齐轴？

### 3. 色彩

- 是否先建立了背景、边框、正文、标题的灰阶？
- 强调色是否足够稀缺？
- 文字和 UI 边界的对比度是否达标？
- 暗色模式是否重新设计，而不是简单反色？

### 4. 排版

- 字号是否来自有限字阶？
- 正文是否过宽？
- 标题和正文是否使用了合适的行高？
- 是否用一个字体家族就完成了层级？

### 5. 空间与布局

- 所有间距是否来自同一条尺度？
- 一维布局是否优先使用 Flex，二维布局是否优先使用 Grid？
- 元素间距是否用 `gap` 管理？
- 响应式是否可以先用流式尺寸和容器查询解决？

### 6. 工程实现

- 颜色、间距、字号是否已经 token 化？
- 主题切换是否只修改语义层？
- 动效是否只修改 transform 和 opacity？
- 组件状态是否完整？

### 7. 系统与美学

- 同类组件是否完全一致？
- 有没有大阴影、过度渐变、过多圆角等模板化特征？
- 页面中是否存在几个真正属于这个产品的明确选择？

完成这一轮检查后，原本模糊的“有点丑”，通常已经会变成一组可以排期、可以修复、可以验收的问题。

---

## 结语：把无限选择收敛成有限决定

工程师做 UI 最容易陷入的误区，是把设计理解成不断尝试：再调一点颜色、再挪两个像素、再换一个阴影，直到“感觉差不多”。

更可靠的方法，是先建立尺度和规则：

- 用视觉层级决定谁先被看到；
- 用对比、接近、对齐、重复和留白组织信息；
- 用 OKLCH 色阶、模块化字阶和间距阶限制选择；
- 用 Flexbox、Grid、流式尺寸和容器查询表达布局；
- 用三层 Design Tokens 沉淀设计决定；
- 用浏览器渲染管线约束动效实现；
- 用完整状态和设计系统把一致性扩展到整个产品。

最后你会发现，所谓“专业感”并不是某个神奇的颜色、字体或阴影，而是一系列清晰决定共同产生的副产品。

> 好的 UI 不是每个地方都很显眼，而是每个地方都知道自己应该有多显眼。
