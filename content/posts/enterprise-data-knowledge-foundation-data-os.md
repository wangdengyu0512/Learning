企业要让 AI 参与业务，首先需要解决一个很具体的问题：**当 AI 作出判断时，它究竟掌握了哪些事实，这些事实是否属于同一个业务对象、同一个时间范围和同一个权限范围？**

一家制造企业收到供应商的延期通知。采购负责人希望知道：哪些客户订单会受到影响，现有库存能否支撑生产，是否可以换用其他物料，以及哪些合同要求提前通知客户。

这不是一个仅靠阅读延期通知就能回答的问题。采购交期在 ERP 或供应商协同系统中，实物库存和冻结数量在 WMS 中，生产需求和物料分配在计划系统中，替代料规则在研发与质量系统中，客户交付承诺和违约条款又分别存在于订单与合同中。即使这些信息都可以访问，也仍然需要确认编码对应、数据时间、业务口径、版本效力和查询权限。

本文承接《从理解企业到自主运行：基于世界行为模型的企业级 AI 操作系统》中对 Data OS 的定义，以多源连接、语义统一、状态建模、可信追溯和权限继承五类能力为主线，展开一套面向智能体的数据与知识服务架构。[1]

这里的 Data OS 是本文讨论的工程架构概念。它可以由企业已有的数据平台、知识平台和业务服务共同实现，并不预设必须采购某一种产品，也不要求先替换现有系统。本文的分层、接口和建设路线是对原文的实施建议；文中的企业、编号、数量和时间均为教学示例。

## 一、建设目标：给智能体一个可以核验的业务上下文

### 1. 从一个完整的业务问题定义底座

如果把目标写成“接入企业全部数据”，项目很容易变成不断增加连接器和存储容量的基础设施建设。更有效的起点，是选择一组能够由业务人员判定对错的问题。

以物料延期为例，第一批能力问题可以限定为：

- 供应商通知中的物料和采购单，分别对应哪些企业业务对象？
- 在预计到货时间变化后，哪些生产需求出现缺口？
- 缺口会影响哪些客户订单，影响发生在什么时间？
- 是否存在已批准且适用于当前产品版本的替代物料？
- 哪些合同条款和内部流程适用于这次变更？
- 当前查询人能够查看哪些结果，哪些信息需要补充授权或由其他岗位处理？

这组问题同时定义了数据范围、语义范围、服务能力和验收边界。一个系统即使已经接入几十个数据库，只要无法回答这些问题，就还没有完成这个场景的底座建设。

### 2. 将事实、规则、推断与动作分开表达

为了让结果可以核验，本文建议把面向智能体的业务上下文分为四类内容。

| 内容类别 | 延期场景中的例子 | 应如何使用 |
| --- | --- | --- |
| 已确认事实 | 供应商已提交交期变更；某批库存处于质量冻结状态 | 附带来源、版本、时间和质量状态 |
| 适用规则 | 当前合同的通知条款；已批准的替代料适用范围 | 附带生效条件、版本和责任人 |
| 计算或预测 | 按指定计划版本计算出缺口；估算可能延迟的天数 | 附带输入、算法、假设和不确定性 |
| 待执行动作 | 调整计划、申请替代料、通知客户 | 进入业务流程并单独校验执行权限 |

供应商更新了预计交期，并不代表货物已经到达；存在物料缺口，也不意味着客户订单一定延期。中间还可能有库存调拨、计划缓冲、替代料和加急运输等条件。

底座应帮助智能体保留这些区别。否则，模型很容易把“可能影响”写成“已经发生”，或者把“某次成功使用过”解释成“本次已经允许使用”。

### 3. 用服务契约描述可信程度

“可信”需要落实到可检查的字段。每一项关键结果至少应能够说明：它描述什么对象，采用哪个业务定义，数据截至何时，来自哪里，经过什么处理，以及还有哪些缺失信息。

因此，本文将 Data OS 的交付目标定义为：**在明确授权和质量约束下，为任务提供带有业务语义、时间边界、来源证据和使用限制的上下文。**

这个目标也决定了验收方式。要检查的不只是能否生成一句自然语言回答，还包括回答中的对象能否定位、数量能否复算、规则能否核对、权限能否验证。

## 二、总体架构：从源系统到任务上下文

### 1. 四层处理链与贯穿全程的治理

围绕上述目标，可以将底座组织为四个逻辑层。这里的“层”表示职责，不要求每层部署一套独立产品。

| 逻辑层 | 主要职责 | 典型输出 |
| --- | --- | --- |
| 数据接入层 | 读取业务记录、接收变更、获取文档及权限元信息 | 原始记录、事件、文档版本、同步位点 |
| 存储与加工层 | 保留原始依据，清洗数据，解析文档，建立派生索引 | 标准事实、文档结构、查询视图、检索索引 |
| 业务语义层 | 统一对象身份、关系、指标、状态和规则适用条件 | 业务对象、关系网络、指标定义、规则绑定 |
| 知识服务层 | 按身份和任务组织查询，计算影响，组装证据 | 对象服务、指标服务、检索服务、任务上下文 |

身份权限、质量检查、血缘、版本、目录和审计贯穿这四层。例如，一份合同在接入时应记录访问规则，解析后的条款应继承相应限制，条款摘要被用于回答时还需要重新检查调用者的当前权限。

数据路径与治理路径应当一起设计。仅在最终页面隐藏敏感内容，无法约束已经进入模型上下文、缓存或日志的数据。

### 2. 数据在哪里保存，由访问需求决定

可以为不同数据选择不同的承载方式，但应先确认现有基础设施能否满足需求。

| 数据或访问需求 | 可采用的承载方式 | 必须保留的约束 |
| --- | --- | --- |
| 交易明细、历史快照、分析计算 | 现有数据库、数据仓库或湖仓 | 主键、口径、快照与保留策略 |
| 合同、制度、手册原件 | 文档平台或对象存储 | 原始文件、版本、页码与访问控制 |
| 精确编号和文本检索 | 数据库索引或全文索引 | 规范化规则、权限过滤和更新时间 |
| 语义相近内容检索 | 向量索引 | 来源文档、切片版本和过滤条件 |
| 多层依赖与影响关系 | 关系表、物化关系视图或图存储 | 关系类型、方向、来源和有效时间 |
| 高频状态变化 | 事件日志与状态视图 | 事件顺序、去重依据和重建方式 |

首个场景可能只需要现有数据库、文档平台和一个检索服务。只有在复杂关系遍历、数据规模或服务时延提出明确要求时，才有必要引入额外存储。

无论采用什么产品，都应明确：哪些记录是权威事实，哪些只是可以重新生成的视图和索引。索引更新失败时，系统需要知道它落后于哪个版本，而不是继续把旧结果当作当前事实。

### 3. 明确 Data OS 与 Agent OS 的接口

原文用 Data OS 承担数据与知识底座，用 Agent OS 组织智能体协作和业务执行。[1] 在本文的实施设计中，两者通过任务上下文和受控业务服务衔接。

Data OS 可以返回受影响订单、计算依据、适用规则与信息缺口。Agent OS 再决定如何组织补充查询、人工确认和后续流程。真正修改订单、调整计划或发送通知时，由执行链路重新检查权限、业务前置条件和对象版本。

这一区分也约束反馈过程。一次业务操作发起以后，应等待业务系统确认结果，再把确认事件纳入底座。智能体写出的“已完成”文本不能直接成为订单的新状态。

## 三、多源接入：让数据持续、完整地进入底座

### 1. 接入前先建立源系统责任清单

对每个业务字段，应确认谁负责解释、谁负责纠错，以及冲突时采用什么处理规则。

| 数据项 | 示例权威来源 | 接入方式 | 使用前需要检查 |
| --- | --- | --- | --- |
| 采购单及确认交期 | ERP 或供应商协同系统 | 增量同步或业务事件 | 是否为已确认版本，采购单是否仍有效 |
| 实物库存与冻结状态 | WMS | 增量同步或按需查询 | 仓库范围、批次状态和同步时间 |
| 物料需求与分配计划 | 计划系统 | 版本快照加增量 | 计划版本、需求日期和分配优先级 |
| 替代料适用关系 | PLM 或质量审批系统 | 版本同步 | 产品版本、工厂范围和批准状态 |
| 合同条款 | 合同管理平台 | 文档版本事件或定期同步 | 签署版本、补充协议和访问权限 |

权威来源应按字段和业务阶段确定。例如，合同中的承诺日期、供应商重新确认的预计日期和物流系统预测的到货日期，可以同时存在。它们表达不同含义，不应被覆盖成一个没有解释的 `delivery_date`。

### 2. 选择接入方式时明确时效和一致性要求

对于低频更新的制度，可以采用版本发布后同步；对于订单和库存，可以采用增量同步或业务事件；对于更新频繁、查询量有限且不适合复制的数据，可以按需访问源系统。

这里有两个需要分别回答的问题：业务允许数据延迟多久，以及一次分析中的各个数据源需要达到怎样的时间一致性。

库存来自九点，采购计划来自九点半，订单需求来自昨天，即使每个数据源都没有报错，组合出的结果也可能失真。跨系统无法获得统一事务快照时，应记录各源的观察时间、版本和已知滞后，并按场景规定是否允许继续分析。

“实时”应落实为服务承诺，例如库存视图最多允许落后两分钟，超时则重新查询或标记不可用于确认结果。这个数值应根据业务决策窗口确定，而不是作为所有数据的统一指标。

### 3. 将变更同步设计为可恢复过程

建议每条接入记录携带源系统标识、源主键、源版本或日志位点、事件时间、接收时间、操作类型和 Schema 版本。涉及权限时，还应携带能够关联权限策略的元信息。

这些字段使系统能够处理几个常见情况：重复消息不会反复生成相同业务变化；旧版本到达时不会无条件覆盖新版本；同步失败后可以从已确认位置继续；源系统删除或撤销记录后，派生数据能够收到对应变更。

如果采用先全量、后增量的方案，应明确全量快照与增量起点的衔接方式，避免快照期间发生的变更被遗漏。涉及库存等关键数据，还应定期按源主键、数量或校验摘要进行对账，发现静默丢失。

无法识别的对象编码、单位冲突或不兼容字段应进入待处理区，并保留原始记录。接入失败可以重试，语义不明确则需要责任人修正；这两类问题不能用同一种自动重试机制解决。

### 4. Schema 变化应传播到使用方

假设源系统把“可用库存”改成“物理可用库存”，同时将已分配库存移到另一个字段。即使字段类型没有变化，原来的缺口计算也可能已经失效。

因此，接入契约需要同时管理字段结构与业务解释。变更发布前，应检查受影响的映射、计算规则、查询服务和验收样例。无法保持兼容时，应发布新版本或暂停相关结果的确认用途，并向调用方返回明确状态。

## 四、语义统一：让跨系统数据指向同一个业务世界

### 1. 对象身份统一从精确映射开始

在延期场景中，供应商邮件中的料号、ERP 的物料编码和 PLM 的设计零件编号可能不同。应先定义企业物料对象，再维护它与各系统记录的对应关系。

| 企业对象 | 源系统 | 源标识 | 对应关系及范围 |
| --- | --- | --- | --- |
| 物料 M-017 | ERP-A | MAT-0017 | 当前采购物料记录 |
| 物料 M-017 | WMS-A | ITEM-887 | 指定工厂的库存品项 |
| 零件 P-017 的 B 版 | PLM-A | PART-017-B | 与 M-017 的生产适用映射，需明确生效范围 |

第三行不能仅因为名称相近，就被合并成同一个对象。设计零件版本和库存物料有不同的身份、生命周期和使用方式，应通过具有业务含义的关系连接。

模型可以协助发现候选映射，但对会影响履约分析的映射，应设置可核验的匹配规则、审核流程和撤销机制。暂时无法确定的关系应作为待确认信息返回。

### 2. 关系要携带适用条件

只记录“订单关联物料”还不够。需要进一步说明关联来自哪个计划版本，对应多少需求、何时需要、采用什么单位，以及该关系目前是否仍然有效。

围绕延期场景，可以建立以下关系：

| 关系 | 必要的业务属性 | 可以支持的问题 |
| --- | --- | --- |
| 供应商供应采购单行 | 供应商主体、物料、数量、交期版本 | 本次变更影响哪些采购承诺 |
| 生产需求消耗物料 | 产品版本、用量、需求日期、计划版本 | 缺口出现在哪一天 |
| 销售订单分配生产需求 | 分配数量、优先级、有效时间 | 哪些客户订单受到影响 |
| 替代物料适用于产品版本 | 换算比例、工厂、批准状态、生效时间 | 当前订单能否使用替代物料 |
| 合同约束销售订单 | 合同版本、条款编号、业务范围 | 应检查哪些履约约束 |

这里的关系用于表达依赖和约束。沿着关系找到订单，表示订单进入影响分析范围；是否实际延期，仍需要库存、产能、运输和计划规则的进一步计算。

### 3. 指标定义必须可以执行和复算

“现有库存够不够”需要转化成带有范围和时间的计算。对于本文的简化案例，可以定义：

```text
某时点可供本场景分配的数量
= 合格实物库存
- 已分配给其他需求的数量
- 本场景必须保留的安全库存
+ 截至该时点可确认使用的到货数量
```

这个公式成立的前提是：合格实物库存已经排除质量冻结数量，其他需求占用与安全库存之间没有重复扣减，到货数量也已经考虑入库检验和可用时间。实际企业的口径应由库存和计划责任人共同确认。

如果有多笔订单竞争同一库存，还必须先定义分配顺序。不能让每笔订单分别减去同一份库存，再把结果相加，否则会重复使用库存。

建议为指标记录名称、业务定义、输入范围、单位、计算逻辑、时间粒度、责任人和版本。业务术语表可以解释指标，受控查询或计算服务负责执行指标。

### 4. 语义变更也需要版本发布

对象合并、关系修正、计量单位变化和指标口径调整，都可能改变已有查询结果。应保存语义版本，并在发布前重跑受影响的业务样例。

历史报告需要说明当时使用的口径；按新口径重算时应生成新的结果版本。否则，审阅者会看到相同任务标识对应两个不同结论，却无法解释变化来自业务数据还是定义调整。

## 五、知识加工：让文档进入业务判断

### 1. 先确认知识适用范围，再组织检索

RAG 原始论文研究了将参数化模型与外部检索记忆结合的方法，为知识密集型语言任务提供了技术路径。[2] 在本文的企业场景中，检索还需要满足文档版本、权限和业务适用条件。

对一份合同或制度，可以先建立知识登记信息：文档标识、版本、责任人、审核状态、生效与失效时间、适用组织、关联对象以及访问策略。

同样一句“允许使用替代料”，出现在研发讨论稿、已批准技术变更单和历史复盘中，具有不同效力。应在检索前或检索过程中按任务需要筛选，而不是等生成回答时让模型自行决定哪个版本具有约束力。

### 2. 解析时保留能够解释条款的结构

一条合同义务可能同时依赖主句、例外条件、定义章节和补充协议。一个表格中的阈值也可能依赖列标题、单位和脚注。

因此，建议以章节和条款为基础组织知识单元，同时保留原始文件位置、标题路径、表格表头、交叉引用和相邻条款关系。切片可以服务检索，但不应把理解该条款所需的条件切断。

扫描件还需要记录识别质量。涉及金额、日期、比例等关键字段时，可以增加结构校验和人工复核要求。无法确认的数字应作为缺失或待核验项返回，而不是由模型猜测补全。

### 3. 抽取出的规则不能直接成为可执行规则

模型可以从文档中提取“适用对象、触发条件、要求动作和例外情况”，形成规则候选。候选经过业务责任人校验后，才适合进入受控规则库。

以替代料为例，文档里出现过两个物料名称，只能说明存在文字关联。要把它变成可执行的替代规则，还需要确认方向、比例、适用产品版本、工厂范围、生效时间和批准记录。

对于没有完成规则化的条款，底座可以返回原文与解释建议，并标注需要人工判断。引用条款能够提供依据，但不能自动证明一次业务行为符合全部约束。

### 4. 版本更新必须触达派生内容

建议把知识处理链登记为：原始文档版本、解析结果、知识单元、索引条目、摘要和被引用的结果记录。这样，文档修订或撤销时，才能定位需要重建、失效或重新评估的内容。

当前检索默认使用有效版本，历史审计则按授权访问当时使用的版本。历史记录的保留不等于继续允许它参与当前判断。

对于尚未确认优先级的冲突，应同时保留冲突证据和责任人。系统可以指出“两个有效来源对通知时限的表述不一致”，然后进入核验流程，避免生成一个没有依据的折中规则。

## 六、状态与事件：表达企业当前发生了什么

### 1. 事件、状态和分析结果分别保存

“供应商变更了预计到货时间”是一条事件；“采购单最新确认交期”是由已接受事件形成的状态；“销售订单存在交付风险”则是结合库存与计划计算出的派生判断。

建议将这些对象分开保存，并建立来源关系。这样，采购单后来恢复原交期时，可以重新计算风险状态，同时保留此前为什么触发过预警的依据。

### 2. 同时记录业务时间和系统获知时间

假设供应商在 2026 年 10 月 21 日 16:00 确认交期变更，平台在 10 月 22 日 09:00 才接收到通知。业务事件发生时间与系统获知时间不同。

审计时可能需要回答两个问题：按后来补齐的事实，10 月 21 日的实际情况是什么；站在 10 月 21 日当时的信息条件下，系统能够知道什么。

对于需要这种回溯能力的数据，可以分别记录业务有效时间和系统记录时间，并保存更正历史。这个设计不要求所有字段都采用复杂的时间模型，但关键交期、计划和规则版本应具备足够的时间信息。

### 3. 乱序与更正应作用于明确版本

如果一个旧交期事件晚于新事件到达，不能仅按接收时间覆盖当前状态。应结合源系统序号、对象版本或明确的更正关系判断事件顺序。

对已接受事件进行更正时，建议新增更正记录并引用被更正事件。状态视图根据规则重新生成，依赖它的分析结果被标记为需要重算。原始事件和原有分析记录则按保留策略继续保存。

### 4. 风险结论要区分已发生、推算与待确认

在本文场景中，可以把结果划为四种状态：尚未发现缺口、存在推算风险、确认存在计划缺口、关键数据不足。每种状态需要预先定义进入和退出条件。

例如，源系统不可用时，状态应进入数据不足或降级分析，而不是因为没有查到缺口就回到正常。后续补齐数据后，应生成新的分析版本，并说明状态变化的依据。

## 七、知识服务：按任务组装可使用的上下文

### 1. 将问题分解为可验证的服务调用

面对“哪些订单会延期”，建议把查询拆成一组有类型和边界的操作：定位采购单、展开物料需求关系、读取可用库存、执行分配计算、查找适用条款，再组装结果。

| 服务类型 | 主要输入 | 主要输出 |
| --- | --- | --- |
| 对象服务 | 企业标识或源系统主键 | 对象属性、版本、关联标识 |
| 关系服务 | 起点对象、关系类型、深度和时间 | 依赖路径与关系证据 |
| 指标服务 | 指标标识、范围、时间与参数 | 数值、单位、口径版本和输入摘要 |
| 知识检索服务 | 主题、对象、适用范围与版本要求 | 授权知识片段与定位信息 |
| 上下文服务 | 任务类型、对象、时间与质量要求 | 事实、计算结果、规则、证据及缺口 |

这种接口设计允许智能体参与理解问题和制定查询计划，同时让对象解析、权限判定和关键数值计算由确定的服务完成。

### 2. 按数据类型选择查询路径

订单编号和合同号优先走精确匹配；库存和缺口走结构化查询与受控计算；业务依赖走关系查询；制度和案例检索则可以结合关键词与语义检索。

服务可以对候选结果重排，但需要区分相似程度与业务可靠程度。检索得分高，只表示该方法认为内容相关，不能直接解释为事实为真的概率或规则适用的概率。

在联邦查询中，应限制访问范围、并发量和执行时间，并尽量将过滤条件下推到数据源。涉及反复使用的历史关联计算，可以建设受控物化视图，同时明确其更新频率与失效条件。

### 3. 返回结构化上下文，而不是无边界地拼接文本

下面是本文提出的一个简化响应示例，用于说明结果应具备哪些信息，并非某个现有产品的标准协议。

```json

  "task_type": "supply_delay_impact",
  "subject": { "type": "PurchaseOrder", "id": "PO-008" },
  "assembled_at": "2026-10-22T09:05:00+08:00",
  "data_cutoff": "2026-10-22T09:00:00+08:00",
  "semantic_version": "supply-v3",
  "plan_version": "PLAN-1022-01",

    }

  "calculations": [
```

`data_cutoff` 是结果采用的业务数据截止边界，各个 `source_ref` 还应能够解析出自身的观察时间和版本；该字段本身不保证跨系统一致快照。调用者身份、租户和授权范围由服务端从经过验证的凭据中取得，不能由模型在请求文本中任意声明。

实际响应还可以返回规则适用理由和更新提示，但应避免包含调用者无权获知的对象标识、证据名称或隐藏记录数量。权限过滤后的结果并不一定等于全企业结果，调用方必须知道服务承诺的查询范围。

### 4. 规定信息不足时的行为

建议将服务状态至少分为完整、部分、过期、拒绝访问和失败，并为每类状态定义调用方行为。

部分结果可以支持初步分析，但应附带缺失项；过期结果需要重新验证关键输入；权限拒绝不得被解释为业务对象不存在；失败也不应被转换成“没有风险”。

上下文长度不足时，应优先保留关键事实、规则适用条件和证据定位，再压缩解释性材料。让模型收到大量重复文档，却遗漏一条决定适用范围的例外条款，会降低结果的可核验性。

## 八、可信与权限：把依据和授权贯穿处理链

### 1. 证据需要覆盖结论的形成过程

W3C PROV 使用实体、活动和责任主体等概念描述来源与生成过程。[3] 借鉴这一思路，本文建议把底座中的关键结论关联到输入记录、加工过程、规则版本和责任主体。

例如，“订单 SO-B 存在 200 件物料缺口”至少需要能够回溯到库存快照、需求版本、分配顺序、到货可用时间和计算版本。合同条款只能为通知要求提供依据，不能替代数量计算的证据。

为每项结论附上一个文档名称还不够。应检查被引用证据是否支持该项结论，证据中的对象和时间是否匹配，以及是否存在尚未满足的适用条件。

### 2. 质量检查要影响结果可用性

建议把质量问题按业务影响分级。缺少展示性描述可以允许降级，关键物料单位冲突应阻断缺口计算，库存时间超出允许范围应触发刷新或降级，而无法确认合同生效版本应阻断确定性规则判断。

当质量检查失败时，结果需要携带问题类型、受影响范围、责任人和修复状态。质量告警如果只进入监控看板，却不影响下游服务状态，智能体仍会把问题数据当作正常输入。

修复也需要闭环。发现映射错误后，应修正映射，重新加工受影响数据，重新计算结果，并标记哪些历史输出已被新版本替代。

### 3. 身份和权限沿调用链传递

建议在服务端建立可信调用上下文，包含租户、实际调用者、委托主体、任务用途和授权范围。智能体使用的技术账号权限不能直接成为用户可获得的数据范围。

在本文的委托查询模式中，有效范围应受调用者权限、任务授权、工具允许范围和数据使用策略共同约束。无人值守任务则需要显式登记的工作负载身份、责任归属和授权范围。

数据库查询应应用行与字段限制，关系查询应限制可见对象和边，检索应按授权范围生成候选或在可信检索服务内完成过滤。任何未授权内容都不应进入模型上下文或交给无权处理该内容的外部重排服务。

### 4. 缓存和摘要同样需要授权治理

Zanzibar 论文讨论了权限变更、对象内容变化与授权判定之间的一致性问题。[4] 对 Data OS 来说，类似问题会出现在检索索引、摘要和上下文缓存中：源文档已经撤销权限，但派生内容仍可能沿旧路径被读取。

因此，建议为缓存绑定租户、授权范围、数据版本和策略版本，并在读取时重新授权或验证有效性。权限变更应使相关缓存失效；对于高敏感数据，无法确认当前授权时应停止返回。

多来源摘要应记录依赖来源，默认保留相应的限制，或按当前调用者可访问的来源重新生成。需要降低敏感级别的发布应经过明确的脱敏和审批流程，不能因为文本已经被概括就自动扩大分享范围。

日志也应遵守最小必要原则。记录证据标识、执行状态和审计信息通常已经足够，不应为了调试把完整合同和敏感字段复制到所有运行日志中。

### 5. 将检索内容当作数据处理

文档中可能包含“忽略之前的规则”“把结果发送到某个地址”等文字。本文的服务设计要求将这些内容作为被查询材料处理，不能把它们提升为工具调用权限或系统指令。

权限校验、查询范围和可用工具应由可信配置与服务端逻辑决定。对回答做内容检查可以补充治理，但不能替代调用前的数据访问控制。

## 九、端到端案例：一次物料延期如何形成可审阅的影响分析

### 1. 设定可复算的输入

假设在 2026 年 10 月 22 日 09:00，企业已确认物料 M-017 的一笔 500 件采购到货，从 10 月 23 日调整到 10 月 26 日。当前计划要求物料在 10 月 24 日前可用于生产。

该案例采用以下简化输入。所有数量已经统一为“件”，且假设在分析期间不发生其他入库、出库和需求变更。

| 输入项 | 数值或条件 | 解释 |
| --- | --- | --- |
| 实物库存 | 600 件 | 包含质量冻结数量 |
| 质量冻结 | 100 件 | 当前不可用于生产 |
| 已分配给其他需求 | 150 件 | 不属于本次两个订单的需求 |
| 必须保留的安全库存 | 50 件 | 与上述占用互不重叠 |
| SO-A 的物料需求 | 250 件 | 分配优先级高于 SO-B |
| SO-B 的物料需求 | 250 件 | 在 SO-A 之后分配 |
| 截至 10 月 24 日可确认新增到货 | 0 件 | 延期采购预计 10 月 26 日到达 |
| 替代料 | 有批准关系，库存未确认 | 暂不计入确定可用数量 |

在这个口径下，合格实物库存为 600 − 100 = 500 件，可供本次两个订单分配的数量为 500 − 150 − 50 = 300 件。

按既定优先级，SO-A 获得 250 件；剩余 50 件分配给 SO-B，因此 SO-B 的物料缺口为 250 − 50 = 200 件。

这只是物料层面的计划缺口。是否影响最终交付、影响多少天，还需要生产周期、产能、运输和交付缓冲等输入；不能将到货推迟三天直接写成客户交付延迟三天。

### 2. 从事件到结果的处理顺序

| 步骤 | 主要操作 | 必须留下的依据 |
| --- | --- | --- |
| 接收变更 | 校验采购单行和源版本，接受交期事件 | 原始事件、源版本、发生与接收时间 |
| 解析对象 | 将源记录映射到采购单、供应商和物料 | 企业标识及映射版本 |
| 展开需求 | 查询当前计划中依赖 M-017 的需求和订单 | 关系来源、计划版本和需求日期 |
| 核验输入 | 检查库存时间、单位、冻结与占用口径 | 数据快照与质量检查结果 |
| 执行分配 | 按批准的分配顺序计算 200 件缺口 | 输入摘要、计算版本和分配明细 |
| 补充知识 | 查找替代料条件、通知条款及适用流程 | 文档版本、条款位置和适用理由 |
| 组装上下文 | 分开输出事实、计算、规则和未知信息 | 上下文版本、授权范围和服务状态 |
| 交付流程 | 由负责岗位确认处置，再进入执行链路 | 人工决定、执行请求与业务回执 |

每一步都可以独立失败。替代料库存查询失败，不一定阻断已有物料缺口的计算，但应阻断“已经可以替代”的判断；当前合同版本无法确认，则不能给出确定的通知义务判断。

### 3. 一份可审阅结果应如何表达

在所有相关记录均已授权可见的条件下，系统可以输出如下示例：

> 按 2026 年 10 月 22 日 09:00 的库存数据和计划版本 PLAN-1022-01，本次可分配物料为 300 件。依照既定优先级分配后，SO-A 的 250 件需求得到覆盖，SO-B 仍存在 200 件缺口。采购单 PO-008 最新确认预计到货日期为 10 月 26 日，晚于当前计划要求的 10 月 24 日物料可用日期。替代料虽存在已批准关系，但可用库存尚未确认。当前结果可用于发起补充核验和计划评估，尚不足以确定客户最终交付延迟天数。

报告中应为库存、交期、分配过程和替代料规则分别附上证据定位。若需要建议联系客户，还应展示适用合同条款及其核验状态，交由有权岗位确认后执行。

这样的结果既给出了明确计算，也保留了进一步决策所需的信息缺口。业务人员可以针对缺失输入继续工作，而不必重新检查整段自由生成的分析。

### 4. 处置结果回流时保留事实边界

假设计划人员后来确认可以调拨 200 件合格物料。只有调拨申请获批、相应资源完成有效预留后，才能依据业务规则更新计划可用量。仅生成调拨建议，还不能解除风险。

后续真实到货、生产完成和订单交付事件继续进入底座，用于比较原分析与实际结果。经复核的经验可以进入案例知识库，但一次成功处置不能自动改写适用于所有订单的规则。

## 十、建设与验收：从一个场景形成持续运营能力

### 1. 第一阶段：圈定问题与最小数据范围

选择一个工厂、一类物料和一个明确流程，列出首批能力问题。每个问题都要有业务负责人、必要数据源、允许时延和可接受的回答边界。

这一阶段的交付物包括源系统责任表、最小对象模型、字段与语义映射、指标口径，以及一组人工确认的参考结果。数据缺失应记录为场景约束，而不是用模型补齐。

### 2. 第二阶段：打通可以核验的服务链

实现必要的数据接入、对象解析、指标计算、知识检索与权限校验。先让一个完整问题得到可复算的结果，再扩大数据源和问题范围。

每个结果都应具备来源、时间、版本和服务状态。同步失败、证据缺失和越权请求应有明确行为。这些行为也是接口的一部分，需要与调用方共同验收。

### 3. 第三阶段：用异常样例验证业务边界

验收集应覆盖业务正常路径和容易混淆的边界条件。

| 验收场景 | 预期行为 |
| --- | --- |
| 同名但不同编码的物料 | 不自动合并，返回明确对象或待确认状态 |
| 旧交期事件晚到 | 不覆盖已确认的新版本状态 |
| 同一批库存被多个订单竞争 | 按同一分配计划计算，避免重复使用 |
| 替代料批准已过期 | 不计入当前确定可用方案 |
| 文档正文更新但索引未更新 | 标记索引滞后，刷新或停止使用旧结果 |
| 用户权限在缓存建立后被撤销 | 后续读取不能继续返回受限内容 |
| 两个有效规则存在冲突 | 展示经授权的冲突依据并要求核验 |
| 关键数据源不可用 | 返回失败或部分结果，保留缺失项 |
| 历史结果需要复核 | 找到当时的数据、口径和规则版本 |

这些样例可以组织成稳定的回归集合。连接器、语义映射、文档解析策略和检索配置发生变化时，重跑受影响样例，检查业务结果是否仍然成立。

### 4. 分层评估，避免一个平均准确率掩盖问题

| 评估层面 | 建议指标 | 统计注意事项 |
| --- | --- | --- |
| 接入与时效 | 同步延迟、缺失记录率、源端对账差异 | 按数据源和关键字段区分 |
| 语义正确性 | 对象匹配准确率、待确认比例、单位与口径错误数 | 同时检查误合并和漏匹配 |
| 知识检索 | 有效证据召回率、失效版本命中率、引用支持率 | 依据人工确认的任务证据集评价 |
| 上下文质量 | 关键输入完整率、计算可复现率、缺失项识别率 | 区分完整结果与降级结果 |
| 授权治理 | 越权样例通过率、撤权生效时间、审计完整率 | 已知越权样例不允许上线通过 |
| 服务运行 | 成功率、尾部时延、单次任务成本 | 分别观察查询、计算和检索路径 |
| 业务使用 | 分析耗时、返工率、补充查询次数、问题解决率 | 与相同范围的人工基线比较 |

证据召回率需要已知的相关证据集，引用支持率则要检查引用是否真正支持结论。两者不能仅靠模型自评分数替代。

运行中未观察到越权事件，也不等于已经证明系统不会越权。上线前应通过已定义的权限样例，上线后继续监测策略变化和派生内容访问。

### 5. 用阶段交付表控制扩展范围

| 阶段 | 核心交付 | 进入下一阶段的条件 |
| --- | --- | --- |
| 场景定义 | 能力问题、数据责任、参考答案、时效要求 | 业务和技术共同确认范围与判断标准 |
| 最小服务 | 接入、映射、计算、检索、证据和授权链路 | 首批问题可复算，关键异常行为明确 |
| 稳定运营 | 对账、版本发布、回归验收、告警与修复流程 | 更新与故障能够被发现并恢复 |
| 扩展复用 | 新物料、新工厂或相邻业务场景 | 复用能力经过新范围验证，新增语义有责任人 |

扩展到新工厂时，应重新确认编码映射、库存定义、计划优先级和权限范围。已有服务可以复用，但业务定义是否相同需要证据。

### 6. 给每一项长期能力安排责任人

源系统负责人保证数据可解释、可纠错；领域负责人确认对象、指标和规则；知识负责人管理文档效力；平台团队负责接入、服务与运行；安全负责人维护授权策略；场景负责人验收业务结果。

当系统发现“合同存在两个有效版本”时，问题应能路由到具体责任人，而不是在日志中持续重试。当指标口径调整时，也应有人确认哪些历史结果需要重算、哪些报告需要补充说明。

这些责任安排决定底座能否持续更新。一次性接入和建库可以形成演示，版本管理、修复流程和业务验收才能支撑日常运行。
