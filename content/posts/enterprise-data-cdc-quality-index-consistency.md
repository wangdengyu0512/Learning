ERP 中的采购数量已经从 100 件改成 60 件，知识库仍然检索出旧数量。采购 Agent 引用了真实文档，也给出了正确链接，但依据已经过期。

这种错误不能仅靠更好的提示词解决。系统需要知道数据来自哪里、对应哪个版本、经过哪些加工、哪些派生产物需要更新，以及当前回答是否允许使用它。

**可信知识底座要维护从业务事实到派生视图的可核对关系。** 本文沿用虚构采购需求 PR-2048，讨论它从源系统到检索上下文的完整变化过程。示例事件、表结构和实验属于设计方案，不是已部署的数据平台。

## 一、先确定哪一层拥有业务事实

业务数据库、事件流、标准化对象和向量索引可以同时保存一条需求，但它们承担的职责不同。

| 层次 | 保存内容 | 对采购案例的责任 |
| --- | --- | --- |
| ERP 源系统 | 当前业务记录、事务约束 | 确认需求状态与订单事实 |
| 原始事件层 | 可追踪的源变更及位点 | 解释数据如何变化 |
| 标准事实层 | 统一身份、单位和版本的业务对象 | 支持跨系统查询与校验 |
| 派生视图层 | 搜索索引、向量、摘要、图关系 | 提供特定访问方式 |
| 上下文服务层 | 结合权限和时效要求的证据集合 | 为当前任务选择可用依据 |

在本文方案中，向量索引用于发现相关内容，不能自行宣布采购数量已经生效。涉及下单时，应回到具备权威性的业务服务核对当前状态。

不同任务可以有不同新鲜度要求。历史供应商分析可能允许小时级延迟；创建订单前核对预算，可能需要直接读取权威服务。先定义要求，才能判断数据延迟是否构成故障。

## 二、把全量快照与增量流接成一条连续历史

假设在上午开始导出 ERP 表，导出期间持续有人修改采购需求。如果先导出全部数据，再从导出结束时开始订阅增量，中间的变更就可能遗漏。

可行方案需要协调一致性快照与源日志位点，让“快照覆盖到哪里”与“增量从哪里接上”有明确关系。具体锁策略、隔离级别和恢复语义由数据库及连接器实现决定，不能把任意一次表导出当成一致快照。

Debezium 的 PostgreSQL 连接器文档说明了初始快照、日志流和恢复位点等机制，也列出了复制标识与权限方面的要求。[1] 实施时应按实际连接器和数据库版本验证，而不是自行猜测切换边界。

快照与增量可能产生覆盖或重复，因此消费端仍要具备幂等能力。初始化完成还应检查表覆盖范围、记录数量和关键业务聚合，避免把“连接器运行中”误认为“数据已经完整”。

## 三、一个事件需要哪些可追踪的信息

以下是经过适配器转换后的教学事件，不是 Debezium 原生格式。

```json
{
  "event_id": "erp-a:requirements:partition-2:offset-3817",
  "source": "erp-a",
  "tenant_id": "tenant-a",
  "entity_type": "purchase_requirement",
  "entity_id": "PR-2048",
  "operation": "UPDATE",
  "source_position": {"partition": "2", "offset": 3817},
  "entity_version": 18,
  "schema_version": 2,
  "occurred_at": "2026-10-22T02:00:00Z",
  "ingested_at": "2026-10-22T02:00:03Z",
  "after": {"quantity": 60, "unit": "piece", "status": "APPROVED"}
}
```

这里假设源系统提供针对同一实体单调递增的 `entity_version`。真实 ERP 未必具有这个字段，需要另行设计排序依据。

源位点也并非一个可以跨所有系统比较的整数。Kafka offset 只在对应分区内有意义，数据库日志位置有各自的结构和作用域，同一事务也可能包含多行变更。适配器必须明确可比较范围。

墙上时钟时间适合观察延迟，不宜单独承担实体版本排序：设备时钟可能偏移，多次更新可能落在同一时间精度内。

## 四、去重、顺序和事务一致性是三个问题

重复投递可以用唯一事件标识抑制，但去重不能解决旧更新覆盖新更新。消费端还要按实体身份验证版本。

下面的 SQL 仅适用于已经拥有可靠实体版本的标准事实表：

```sql
INSERT INTO requirement_current AS current_row
  (tenant_id, requirement_id, source_version, quantity, deleted)
VALUES
  ('tenant-a', 'PR-2048', 18, 60, false)
ON CONFLICT (tenant_id, requirement_id)
DO UPDATE SET
  source_version = EXCLUDED.source_version,
  quantity = EXCLUDED.quantity,
  deleted = EXCLUDED.deleted
WHERE EXCLUDED.source_version > current_row.source_version;
```

这里还需要在同一目标数据库事务中处理消费确认或应用记录。若把“已消费”先记下，再单独更新事实表，中间崩溃可能造成永久漏更新。

一条采购需求可能同时更新主表和行项目表。逐条事件落库不等于下游已看到完整事务。对要求一致快照的下游，可以按事务边界组装后发布，或通过业务聚合服务读取一致对象。

如果只能提供最终一致视图，应暴露当前水位与完整性状态，避免把半更新的对象当成可下单依据。

## 五、删除需要沿着派生关系传播

删除可以是硬删除、软删除、业务取消或权限撤销。它们的业务含义不同，但都可能使旧检索内容不再可用。

Debezium PostgreSQL 连接器区分删除事件与为日志压缩产生的 tombstone 记录。[1] 消费程序需要知道连接器配置及消息变换是否保留了这些信号，不能只处理带 `after` 内容的更新。

对于知识加工，可以建立以下派生清单：

```text
源对象 PR-2048 / 版本 18
  → 规范化对象 v18
  → 文本表示 v18 / 模板 t3
  → chunk-1、chunk-2 / 切分规则 c2
  → embedding / 模型 e4
  → 需求摘要 / 提示模板 s5
```

当源对象被删除，需要找到所有仍可服务的派生产物并使其失效。仅删除向量，不足以清除全文索引、摘要缓存和长期记忆里的副本。

为了防止迟到更新把已删除对象复活，可以保留受版本控制的删除标记。标记保留多久，应结合事件最大滞留时间、重放范围和恢复策略决定，不能随意清理。

## 六、把数据质量写成可执行约束

“数据不干净”太笼统。质量规则需要指明对象、检测条件和失败后的处理方式。

| 质量维度 | 采购案例规则 | 失败处理 |
| --- | --- | --- |
| 完整性 | 每条有效行项目都关联需求和物料 | 隔离异常对象，阻止作为下单依据 |
| 合法性 | 数量为正，单位与物料兼容 | 返回源系统修复或进入规则转换 |
| 一致性 | 单位与币种规范化后可复算聚合 | 保留差异与转换依据 |
| 唯一性 | 源系统内需求身份不冲突 | 停止合并，调查映射错误 |
| 新鲜度 | 更新延迟满足当前任务阈值 | 降级为直接查询或暂停动作 |
| 可追溯性 | 上下文可定位源对象和版本 | 排除无依据内容 |

质量失败不能只写日志后继续让 Agent 使用。可以划分“允许分析但不能执行”“允许带提示展示”“完全禁止服务”等状态，由任务类型选择可用范围。

要同时观察质量规则是否产生误报。一个供应商编号为空，可能代表草稿阶段的合法状态。规则应包含生命周期条件，避免把业务尚未完成误判为数据损坏。

## 七、索引更新可以采用代际发布

假设每份需求文档有多个切片。直接逐个删除旧切片、插入新切片，会产生新旧内容混合或短暂缺失。

一种设计是先构建新一代派生数据，再通过服务层的有效版本清单切换：

1. 读取源版本 18，生成该版本的所有切片。
2. 为切片写入源版本、加工版本和生成批次。
3. 检查数量、内容摘要、权限信息和索引可见性。
4. 将对象的有效索引代际从 17 切换到 18。
5. 经过安全窗口后清理旧代际。

不同搜索和向量产品提供的原子更新能力不同。如果后端无法原子切换，应由上下文服务根据有效版本清单过滤结果，并对一致性窗口作明确处理。

异步加工还需要防止反向覆盖：版本 18 的生成任务比版本 19 更晚完成时，只能保存为历史产物，不能再次成为当前有效版本。

## 八、权限撤销要有独立的传播目标

文档内容一天更新一次，权限却可能要求立即收回。把 ACL 更新与全文重建绑在一起，意味着员工离职后还要等待大批量向量任务完成。

建议把内容版本和权限版本分开管理：内容允许异步刷新，授权服务按当前策略限制读取。索引中的权限字段用于提前缩小召回范围，最终加载证据时仍应按风险与时效要求复核。

若授权服务不可用，高敏感查询应失败关闭或降级到可确定允许的内容。不能把“缓存还有数据”当成继续披露的理由。

这一设计还应覆盖已生成回答、会话缓存和长期记忆。哪些历史内容保留可见、哪些需要失效，由产品与组织的数据治理规则明确。

## 九、用对账发现静默错误

日志没有异常，不代表每条记录都已同步。连接器可能配置漏表，字段可能被转换错误，消费者也可能跳过无法解析的消息。

建议分层对账：先比较租户和对象类型的数量，再比较关键聚合与版本水位，最后抽查具体对象的源值和派生内容。

数量一致并不代表内容一致，内容哈希一致也依赖规范化方式。高影响字段可以单独计算校验，例如采购数量、币种、订单状态和对象归属。

血缘记录则回答另一个问题：一份错误摘要影响了哪些回答、任务和决策。OpenLineage 的对象模型将作业、运行和数据集作为描述血缘的基础，可以作为运行级血缘的参考。[2] 具体到文档切片和 Agent 证据，仍需补充对象级关联。

## 十、最小实践：追踪一条需求的变化

在测试环境准备一条需求及其两段文本表示，记录各层版本。以下实验关注可观察结果，不预设必须使用某个产品。

| 操作 | 检查点 | 通过条件 |
| --- | --- | --- |
| 数量从 100 改成 60 | 源事件、事实表、索引、上下文 | 服务切换后只使用新版本数量 |
| 重复投递同一事件 | 消费记录与对象版本 | 没有重复切片或重复业务动作 |
| 先到 v19，再到 v18 | 当前事实与有效代际 | 旧版本不能覆盖新版本 |
| 删除源对象 | 索引、摘要、缓存与记忆引用 | 对象不再进入可用上下文 |
| 撤销读取权限 | 新查询和缓存命中路径 | 在规定撤销窗口内拒绝读取 |
| 停止消费者再恢复 | 位点与源日志可用范围 | 无遗漏；超出保留范围时启动重建 |
| 故意删除一条目标记录 | 定期对账 | 能发现差异并进入修复流程 |

每次记录从源提交到事实更新、再到检索可用的时间。若日志保留时间不足以覆盖停机窗口，恢复计划需要重新快照或回补，不能假设“重启就能追上”。

修复时也要避免旧回补覆盖实时更新。可以让回补复用版本比较规则，或在隔离视图完成重建和核对后再切换。

## 十一、把数据服务契约交给 Agent 使用

上下文服务可以返回证据内容，同时附带源版本、更新时间、权限校验时间、质量状态与适用范围。

Agent 不应自行把“可能过时”升级为“可以执行”。执行策略可以要求：分析允许使用五分钟前的索引，提交采购则必须通过业务服务重新核对需求和预算。

数据底座由此提供的不只是检索结果，还包括判断这些结果是否适合当前任务的依据。每一项业务行动都能回到具体对象、具体版本和可复算的事实。
